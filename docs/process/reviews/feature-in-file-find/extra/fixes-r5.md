# Review r5 — b8a77c9cc (find mark by source position), on c18f75676

Scope: `git show b8a77c9cc` only. Probes ran in a throwaway worktree at b8a77c9cc.

## How the probes were built

- Rows were generated by a Python copy of the addon's own path: `ContentExtractor.chunk_text`
  (max 400, overlap 80, `strip()` at the whole text and at every chunk edge), `_merge_chunks`
  (overlap search 80..20, else `"\n"` join), `_positions` and `_snippet` (80 code points either
  side, `…` where cut). Source read with universal newlines, as `Path.read_text` does.
- Ground truth for a row in Markdown: re-render the source with that one occurrence replaced by a
  same-length non-matching string; the rendered occurrence that disappears is the right one (none
  disappears = the occurrence is not visible, so the right answer is no mark). Then compared with
  where `markFindOccurrences(..., textSource)` puts `find-mark-current`.
- Corpus: 147 real files from `docs/**/*.md`, 3 most frequent words each, up to 10 rows per term:
  **3910 rows: 3902 correct mark, 6 correct no-mark, 1 wrong mark, 1 missing mark** (both in one
  paragraph: the link-URL case, finding 2). Across all 1113 docs files and 78,080 rows, only 6
  snippets are not found in the source at all (finding 5).
- Synthetic cases: frontmatter LF / CRLF / blank lines after / none / knowledge `id:` frontmatter,
  nested lists, loose lists, blockquotes incl. nested, tables, fenced and indented code, HTML
  blocks and inline HTML (escaped, `html: false`), HTML comments, task lists, setext headings,
  repeated identical paragraphs, a long Japanese note: **all correct**. Failures only in the cases
  listed below.

## Findings

### 1. Knowledge editor preview: occurrences near the top of the note, and every occurrence in a short note, get no current mark

- **File:line**: `frontend/src/components/MarkdownPreview.tsx:469-474` (the `textSource` is the
  `source` prop), with `addons/knowledge/frontend/Editor.tsx:1248-1252,1484-1485` (passes
  `parsed.content`, the body without frontmatter, as `source`).
- **Claim**: I5 locates a row "in the file's source — the text the viewer renders from,
  frontmatter included". The knowledge editor hands `MarkdownPreview` only the body. The addon's
  snippet is cut from the whole file, so for every occurrence within 80 code points of the end of
  the frontmatter the snippet contains `…---\n` and the frontmatter's tail, is not in the body, and
  `locateTextRow` returns null: no current mark, no scroll. A note whose body is shorter than ~80
  characters loses it on every row. (When the snippet does repeat, the tie-break by `ordinal` is
  also off by the number of frontmatter occurrences, since ordinals are counted from the body.)
- **When**: every knowledge note has frontmatter (`id:`, `created:`, `tags:`). Searching a term in
  a note's title heading or first sentence or two in the knowledge editor's preview (the default
  view for a note), or any term in a short note.
- **Frequency**: 5. **Impact**: 4 (the row becomes current but no occurrence is outlined and
  nothing scrolls; near the top it is usually on screen, in a short note always is, so the user
  sees "no current mark" rather than a wrong one).
- **Evidence**: synthetic `knowledge_id` note (frontmatter + `# 予算メモ` + Japanese body), core
  viewer with full source: all 24 rows correct. Same note rendered as the editor does (body only):
  rows 1–5 (`会議` within the first ~80 characters of the body) give no mark, rows 6–24 correct.
  `fm_lf` note (short English body), body only: all 4 body rows give no mark; full source: all
  correct.
- **Introduced** by this commit (the rule is new). The fix belongs either in a `MarkdownPreview`
  prop carrying the full text and the body's line offset, or in the editor passing it; either way
  it touches the knowledge submodule or a new core prop.

  Note on reach: `ShellLayout.tsx:493-505` renders every Markdown file page through the
  `knowledge-edit` slot when the knowledge addon is installed, so this is not limited to notes the
  knowledge addon created; any `.md` with frontmatter viewed there is affected.

### 2. An occurrence the render hides (link URL, image, wikilink target, fence language) shifts the current mark onto the next visible occurrence in the block, and the block's last visible row gets none

- **File:line**: `frontend/src/lib/findMarks.ts` `chooseTextOccurrence`, the `k` loop and
  `current = first + k - 1` (b8a77c9cc:findMarks.ts ~437-447).
- **Claim**: `k` counts occurrences in the block's *source*. When the source has an occurrence the
  render does not show, every row at or after it in that block lands one occurrence later than its
  own: the hidden occurrence's row marks the next visible occurrence (a wrong mark, not none), each
  following visible row marks its successor, and the last visible row overshoots and gets none
  (the `starts[current] >= range.end` guard). The I5 text expects overshoot to give "no current
  mark"; in practice it gives a wrong one for every row but the last.
- **When**: a paragraph or list item containing a link, image or aliased wikilink whose hidden
  part contains the term, ahead of visible uses of it. Typical in clipped web pages and notes with
  links (`[docs](https://example.com/budget/...) ... budget`), and `[[budget-2026|the plan]]`.
  Also `![budget chart](...)` (alt is an attribute, not text), and a fence whose info string is
  the term. Reference-style links (`[docs][budget]`) give a missing mark rather than a wrong one.
- **Frequency**: 3. **Impact**: 4 (the scroll reaches the right block; the outline sits on a
  neighbouring occurrence in the same paragraph, or is absent).
- **Evidence**: corpus, `docs/developer-guide/backend-dev.md`, term `backend`: row 6 is inside
  `](../../.claude/rules/backend-conventions.md)` (hidden) and is marked on the visible
  "changing the backend" (rendered occurrence 5); row 7, which *is* that visible occurrence, gets
  no mark. Synthetic `See [the docs](https://example.com/budget/plan) for budget details and budget
  notes.`: row 1 (URL) → marks rendered 0; row 2 → marks rendered 1 (should be 0); row 3 → none
  (should be 1). Same pattern for `[[budget-2026|the plan]]`, `![budget chart](https://x/budget.png)`
  and ```` ```budget ````.
- **Introduced** (consequence of the approved I5 counting rule, so this is a design question for
  the human rather than a code slip). Counting only the source occurrences that render — e.g.
  counting over the block's inline tokens' `text`/`code_inline`/`fence` content instead of the raw
  line range — would close it.

### 3. CSV, JSON, SRT and VTT files in `TextLines` no longer get any current mark or scroll

- **File:line**: `frontend/src/lib/findMarks.ts` `locateTextRow` (snippet-in-source search) via
  `frontend/src/components/TextLines.tsx:93-98`.
- **Claim**: the addon indexes these through `_clean_by_type` (`addons/intelligence/app/extractors/text.py`):
  CSV cells re-joined with spaces and quotes stripped, JSON reduced to its string values joined by
  spaces, SRT/VTT stripped of cue numbers and timings and joined into one line. The snippet is cut
  from that cleaned text, so it is essentially never in the file the viewer shows. Every row is
  "snippet not found": no current mark, nothing scrolls, on every step through the bar. These files
  open in `TextPreview` → `TextLines` with find enabled.
- **When**: using find in any `.csv`, `.json`, `.srt` or `.vtt` file.
- **Frequency**: 2. **Impact**: 5 (stepping the bar never moves the page; in a long CSV the user
  cannot get to the occurrence from the bar, though the plain marks are all drawn).
- **Evidence**: plain-mode probe, one `<span>` per line as `TextLines` draws it. 20-row CSV, term
  `budget`: 0/20 marked at this commit; the same rows at c18f75676 (r4 scoring): 20/20 correct.
  10-cue VTT: 0/10 here, 10/10 at c18f75676. (For contrast, a 60-line log and 40 identical lines:
  60/60 and 40/40 correct here, 0/60 and 0/40 at c18f75676.)
- **Introduced** by this commit (regression from r4 for these four types). It follows the letter of
  I5 ("a snippet not found in the source gives no current mark"), so whether to accept it or keep a
  fallback for files the addon cleans is the human's call.

### 4. (one line) A row whose snippet spans a chunk seam the addon could not overlap is not found

`_merge_chunks` joins with `"\n"` and keeps duplicated text when a chunk is under ~21 characters
(a short heading followed by a >400-character block with no blank line, e.g. a long table). Rows
within 80 characters of that seam give no mark. Measured: 64/1113 docs files have such a seam, but
only 6 of 78,080 rows are affected. Frequency 1, impact 3. Pre-existing in the addon; surfaced by
the new rule.

### 5. (one line) Mermaid

After mermaid renders, `pre.mermaid-source` (which carries `data-source-lines`) is replaced by a
`div.mermaid-diagram` without it, so a row inside a top-level mermaid block finds no block and gets
no mark (correct per I5's "no mark"); inside a list item or blockquote the enclosing block is used
and its `k` includes the diagram source, whose SVG text may not match. Odd placement; frequency 0–1.
