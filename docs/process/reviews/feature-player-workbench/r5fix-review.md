## Findings

### F1. Hydration attribute mismatches below SidebarProvider are no longer repaired by the remount
- Where: frontend/src/components/SidebarProvider.tsx:103-117 (the change itself is correct; this is what it stops doing as a side effect).
- What goes wrong: before, the whole app subtree was hydrated once and then thrown away and mounted fresh on the client about 0.4 s later. That fresh mount silently replaced any attribute that differed between the server HTML and the client's first render (React does not patch attribute mismatches on hydration; it only logs "This won't be patched up"). With the stable tree, an attribute mismatch in any component under the provider now stays in the DOM until that attribute's value changes again.
- Evidence: rt5/hydr.test.tsx renders `<Provider><Child/></Provider>` with renderToString and then hydrateRoot. The child computes `data-mode` from a `useState(() => localStorage...)` initializer (server "a", client "b"). Old provider, after hydration: `data-mode="b"`, so the remount fixed it. New provider: `data-mode="a"`, the server value, which is stale. Both runs log the same React "attributes didn't match" error. The provider adds no mismatch of its own: `data-open` goes false→true correctly in both runs, and SSR output is identical.
- Normal-use trigger: needs a component that is SSR-rendered on first load and that reads client-only state (localStorage, window) in a render-time initializer, where the difference shows up only in an attribute. I checked the candidates: useIsMobile in FileDetailSkeleton gives a structural difference, which React does recover. useFolderViewMode and useFolderSort change structure or text. The tree pane hooks only mount after hydration (hasEverEnabled starts from the server snapshot of treeEnabled, which is false). The sidebar hooks read storage in effects. The file-page hooks run after the client fetch. None of these is an attribute-only mismatch on a server-rendered path, so I cannot show a concrete normal-use trigger.
- Frequency 0 (no concrete trigger shown), impact 3 (a stale attribute until the next change). Below the fix threshold. Recorded because it answers "what relied on the remount": a future storage-initialised attribute would now go quietly stale, where before the remount hid it.
