## Findings

### F1 [introduced] — `disabled` gates only the document press listener; a `label`ed scrim still dismisses while disabled (proposed bucket B, unreachable today)

The code is new in `63da8e0c`, so `[introduced]` without a parent run.

`DismissScrim`'s `disabled` sets `ignoring`, which only the capture `pointerdown` listener reads. The `label !== undefined` branch renders a `<button>` whose `onClick={() => onDismiss()}` is not gated, and which has no inline `pointer-events: none`. So `label` + `disabled` still closes on a click that lands on the scrim, and on Enter/Space from the keyboard.

Reproduction (scratch test, deleted):

```tsx
render(<DismissScrim onDismiss={onDismiss} label="Close" disabled><div role="menu">x</div></DismissScrim>);
fireEvent.pointerDown(button, { button: 0 }); // onDismiss calls: 0
fireEvent.click(button);                      // onDismiss calls: 1
```

Observed: `PROBE-LABEL afterPress 0 afterClick 1 inline pe (none set)`.

No user can reach this. The only caller that passes `disabled` is `AddButton`, and it passes no `label`. The only caller that passes `label` is `OverFrameSettingsPanel`, and it passes no `disabled`. It is recorded because the prop's docstring says "Ignore presses while true". A future caller, such as `FileActions` adopting the same fix, could combine the two props and expect that sentence to hold. Remedy for the supervisor to choose: gate the labelled branch as well, or narrow the prop to the unlabelled branch. Do not reword the docstring.

## Q2 — What did the fix break?

Nothing I could observe.

- **Other popups.** `disabled` defaults to `false`, and no other caller passes it. The full frontend suite at `63da8e0c` has 6652 passed and 1 failed. The failure is `IntelligenceAskPage … puts a ?q= seed in the box`, which passes when `src/addons/intelligence` runs alone (531 passed): it is load-flaky and outside this diff. Flipping the default to `true` (D4) fails 21 tests across 9 files: FileActions, FileAIActionsButton, FilterMenu, DismissScrim, WikiLinkAutocomplete, SidebarCollections, fixture parity, FolderPicker, ContextMenu. The default is held.
- **A press that arrives as `disabled` flips.**
  - Press that closes the dialog (on click, or on its own pointerdown): the menu scrim's capture listener was registered when the menu mounted, before any dialog listener. It runs first, still sees `ignoring = true`, and returns. The menu stays open, which is invariant 6's "first closes the dialog". It is not swallowed and does not dismiss wrongly (probe "pd-close": `menu? true dialog? false mounts 1`).
  - The next outside press closes the menu, and its click is swallowed (`outside click reached 0`).
  - `false` reported from a timer, then an immediate outside press: closes.
- **`pressInFlight` at mount.** Untouched. The scrim still mounts once, when the menu opens. With no remount on `false`, no second swallow is armed for the press that reports `false`. At the parent, the remounted scrim armed one. That is a difference in which click gets refused after an element has already unmounted, and jsdom cannot show what a browser targets there, so I make no claim.
- **The scrim that stays in the DOM while disabled.** `AddButton` passes no `label`, so it is the `div` branch with inline `pointer-events: none` (probe: `scrims 1 none`). An outside press while disabled neither closes the menu nor is swallowed: `click reached 1`, the same as the parent, which had `scrims 0`. jsdom does no hit-testing, so the evidence is the inline style, not stacking. The labelled branch is F1.
- **Initial value of `ignoring`.** Dead code, no finding (D3, D3b both live). The update effect is declared before the listener effect in the same component, so `ignoring` is always written before the listener exists.
