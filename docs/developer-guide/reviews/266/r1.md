## Findings

### F1 [introduced] — Reporting a dialog open remounts the entry, so any entry that holds its own dialog state loses the dialog the moment it reports it (proposed bucket A)

`AddButton` renders the menu as `menuOpen && (addonDialogOpen ? menu : <DismissScrim>{menu}</DismissScrim>)`.
The two branches put the menu `div` under different parents at the same child
position (`DismissScrim` component vs. the bare element), so React unmounts the
whole menu subtree and mounts a new one when `addonDialogOpen` flips. The
`AddonSlot` → `SlotEntryRenderer` → entry component below it is remounted with
fresh state.

An entry written the way `docs/ADDON-DEVELOPMENT.md` now prescribes — and the way
both existing dialog-raising entries are written (`addons/knowledge/frontend/CreateNoteMenuItem.tsx`,
`addons/intelligence/frontend/IndexDetailsMenuItem.tsx`: `const [open, setOpen] = useState(false)`;
`setOpen(true); onDialogOpenChange(true)`) — therefore renders its dialog for
zero frames: the `true` report remounts it with `open === false`. What is left
on screen is the menu with no scrim and no Escape handler, and no dialog.
Only the trigger or a row closes it. This is precisely the failure S2-15 set out
to remove ("押した瞬間に消えるダイアログ"), so P2-6's media_import dialog would
still vanish on press after this merges.

The tests do not see it because the mocked `AddonSlot` in `AddButton.test.tsx`
is stateless: it draws the portalled dialog whenever `slotDialog.current` is
true, whether or not it was remounted. Invariant 6 ("a press inside a dialog
portalled to body does not close the menu") holds for that stand-in, not for
any entry that keeps the dialog's open state in the component that reports it.

Reproduction (scratch test, since deleted; `frontend/src/components/__tests__/zzProbeRemount.test.tsx`):

```tsx
function Entry(p) {
  const [open, setOpen] = useState(false);
  useEffect(() => { mounts.current += 1; }, []);
  return (<>
    <button role="menuitem" onClick={() => { setOpen(true); p.onDialogOpenChange(true); }}>open dialog</button>
    {open && createPortal(<div role="dialog">the dialog</div>, document.body)}
  </>);
}
vi.mock("@/components/AddonSlot", () => ({ AddonSlot: (props) => <Entry {...props.props} /> }));
// render <ShortcutsProvider><AddButton addonProps={{drive:"d",path:""}}/></ShortcutsProvider>
// click Add, click "open dialog"
```

Observed at 1886c7c6: `PROBE mounts 2 dialog? false menu? true` — test fails.

Twin, `[pre-existing]`: the same probe against `FileActions` (`zzProbeRemountFA.test.tsx`,
same stateful entry via `../AddonSlot` mock) prints `PROBE-FA mounts 2 dialog? false`.
`FileActions.tsx` is not in `git diff 0ae8c2e7 1886c7c6`, so the result is the
same on the parent. That means knowledge's "Create note" and intelligence's
"Index Details" on the file detail `[...]` menu are measured to lose their
dialog in the same way today — reachable by a user, and the "reference
implementation" this PR copied is the source of the defect. Raising rather
than excavating (R-4 Scope); the introduced copy is what this PR adds.

Shape that would not remount (for the supervisor, not applied): keep the menu
at a stable tree position in both states, e.g. always render `DismissScrim`
and gate its listener, or render the scrim conditionally as a sibling placed
before an unconditionally-rendered `menu` (the scrim finds the menu through
`nextElementSibling`, so the sibling order is what must hold). A test for it
needs an entry mock that keeps `open` in `useState`.

The same remount happens on `onDialogOpenChange(false)`: the row that opened
the dialog is replaced, so a dialog that returns focus to its opener returns
it to a detached node. The new Escape test works around exactly that by
calling `screen.getByText("open dialog").focus()` by hand before the second
Escape.

Supporting mutation: M2 below (always render the scrim, which keeps the tree
shape stable) makes the probe pass (`PROBE mounts 1 dialog? true`) while two
suite tests fail. So the branch swap causes the loss, and the suite's
stand-in cannot tell a remount from none.

### F2 [introduced] — Home's `drive` field is not held: hardcoding it survives (proposed bucket A, low likelihood)

Mutation in `frontend/src/components/DriveHome.tsx`:

```diff
-            addonProps={{ drive: driveName, path: "", surface: "home", fileIds: [] }}
+            addonProps={{ drive: "media", path: "", surface: "home", fileIds: [] }}
```

Result: `DriveHome.test.tsx` 24/24 pass. The only case that reads the props,
"offers addon rows below its own, writing to the drive root", renders
`driveName="media"`, so it compares the constant to itself. Invariant 1 names
`drive` as part of what Home hands over, and a `drive` that is not the drive on
screen sends an addon's write across the drive boundary. A fixture that
observes this is cheap: render `driveName` as anything other than the literal
the assertion uses, or run the case with two names.

Related, inert: adding `extra: undefined` to Home's `addonProps` also survives,
because `toEqual` ignores keys whose value is `undefined`. No entry that reads
props by name can see the difference, so I am not counting it as a finding.

5. Reserved callbacks not overridable. Holds and held (M5, M5b killed).
6. After `onDialogOpenChange(true)`, a dialog press does not close the menu and
   Escape is not answered. After `false`, one Escape closes and focus returns.
   Holds for an entry whose dialog does not depend on its own component state
   (the test stand-in). It does not hold for an entry that keeps `open` in
   state, which both real dialog entries do: no dialog is left to press (F1).
   The Escape half holds (M1 killed).
7. Close without `false`, then the next menu dismisses on outside press and
   Escape. Holds for `onRequestClose` and for the trigger (M3 killed via the
   trigger case). The `closeMenu` clear is redundant with the effect (M4 live,
   inert).
8. Rows that never report still close on outside press and Escape. Holds and
   is held.

**Is anything missing from this list?** Yes, one item: *"Reporting a dialog open
or closed does not remount the addon entries; an entry's own state (its dialog)
survives the report."* Without it, invariant 6 can be met by a host that
destroys the dialog, and that is what happens today (F1). A second candidate,
for the supervisor to judge: *"While a dialog is reported open, the menu still
has a way out if the dialog goes away without reporting `false`"*. Today only
the trigger or a row closes it, and F1 is one route into that state.
