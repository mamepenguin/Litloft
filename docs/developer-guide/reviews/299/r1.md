## Findings

### F1 [pre-existing] Medium - a note saved from Ask still shows a raw message key as its origin (breaks inv 6 as written)

`addons/intelligence/frontend/askNoteFormat.ts:99` writes `origin: ask_answer` into the note's frontmatter, and `addons/knowledge/app/schemas.py:70` accepts `Literal["ask_answer", "source_capture"]`. `propertiesPanel.origin` in `messages-core/{en,ja}.json` has `webclip`, `detailed_summary`, `manual` and now `source_capture`, but no `ask_answer`, and no addon message file supplies it.

`OriginRenderer` (`PropertiesPanel.tsx`) relies on `t()` throwing to fall back to the raw value, but next-intl 4.9 with no `getMessageFallback` / `onError` configured (`src/i18n/request.ts`, `app/layout.tsx`) does not throw: it returns `namespace.key`. Probe at this SHA: rendering `<PropertiesPanel frontmatter={{ origin: "ask_answer" }} />` gives text `OriginpropertiesPanel.origin.ask_answer`. The parent commit has no `ask_answer` key either, so this predates the change.

It is the same defect class as the known-issues row this commit closes, reached by every Ask -> Knowledge save (MarkdownPreview and the knowledge Editor both render PropertiesPanel). The R-0 invariant 6 as declared ("every origin value the backend can emit") is not met at this SHA. Also note the `try/catch` in `OriginRenderer` does not do what it looks like: an invented custom origin also renders as `propertiesPanel.origin.<value>`, not verbatim - the existing test "renders unknown origin values verbatim" tolerates either outcome.

Suggested triage: either add the key in this PR (one line per locale, same shape as the fix) or narrow inv 6 and file a known-issues row. Supervisor's call.

### F2 [introduced] Low - Recently Viewed now uses a different icon in its own empty state than in the sidebar and Home

`EmptyState.tsx` variants `no-recent` and `no-recent-profile` (shown by `FolderContent.tsx:216` on `?view=recent`) use `Clock`. At the parent, the sidebar's Recently Viewed link was also `Clock`, so the sidebar link and the page it opens agreed. At this SHA the sidebar link and Home are `History`, and clicking it lands on an empty page drawn with `Clock`. Recently Added's empty state is `FilePlus`, which matches. Reproduction: compare `git show ac625d2b~1:frontend/src/components/sidebar/SidebarLibrarySection.tsx` (Clock) with `EmptyState.tsx` (Clock), and the same at `ac625d2b` (History vs Clock).

Does not break inv 5 as written (it names only sidebar and Home), which is the reason for the "missing from the list" note below. Bucket B unless inv 5 is widened.

### F3 [pre-existing] Low (test gap) - nothing holds that a search term is persisted for the drive it was made on (inv 4)

Mutations G8-G11 delete the `addToHistory` calls in `handleSelect` / `navigateToSearchPage`, or redirect them to another drive's key; all 70 GlobalSearch tests stay green. Reproduced at the parent (G8p: 69/69 green), so the gap predates the commit. This commit rewrote exactly those call sites (`setHistory(...)` -> `setHistoryData({ drive, ... })`), so inv 4 is currently asserted only by reading. The code at this SHA is correct (verified by reading: both calls pass the current `drive`). A test that submits a term on drive `main` and then asserts `localStorage["search-history:main"]` (and that `search-history:other` is untouched) would kill G8-G11.

## Is anything missing from the R-0 list?

- Inv 5 names only the sidebar and Home. Recently Viewed / Recently Added also appear as the `?view=recent` / `?view=recent-added` empty states (`EmptyState.tsx`); if the decision is "one icon per concept", the invariant should say every surface that names the concept (F2).
- Inv 6 is written against "every origin value the backend can emit", which includes `ask_answer` and is not met (F1). Either the list or the change needs to move.
- Missing: "Removing a recent term from the search modal removes it from the current drive only" (`handleRemoveHistory` was also rewritten; it is held by G5's test for state, but no test checks the other drive's key is untouched).
- Missing: "The inline-rename message is not cleared by navigating between folders of the same drive" - true at this SHA because the rename hooks are only mounted under `/drive/[name]` where `currentDrive` comes from the path, but nothing states it, and a later move of the tree pane onto an override-drive route (where `CurrentDriveProvider` nulls the override on every pathname change) would silently clear it.

## Checked, no finding

- **Search modal with `drive === null`** (non-drive pages): `history` is `[]` because `historyData.drive !== null`; the effect never loads; `handleRemoveHistory` / submit return early. Same as the parent.
- **Reopening on the same drive**: first render uses the previous `historyData` for that drive, then the effect reloads from storage. Opening is triggered by a click or keydown (discrete events), so React flushes the passive effect before paint; no flash of an empty body.
- **Drive X -> Y -> X while open**: `history` shows `[]` for the mismatched frame and reloads; no cross-drive term is ever offered (held by G1/G2's test, which also records every render's terms through the `SearchEmptyState` spy).
- **Highlight index across a drive change while the modal is open**: `selectedIndex` is not reset when `history` changes, only when `recentData` lands. Until then a highlighted row points at the new drive's list. The parent had the same staleness against the old list; no cross-drive term is reachable. Rare path (drive changes only via back/forward while the modal is open).
- **Other users of `useInlineRename`**: `FolderTreePane` (via `TwoPaneLayout`) and `useFolderCardRename` (via `FolderContent`), both under `/drive/[name]`, both below `CurrentDriveProvider` in `app/layout.tsx`.
