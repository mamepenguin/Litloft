The only other caller of `answer_question` is `app/evals/stages.py:293` (eval harness). So the `drive=None` skip is not reachable from a production Ask; invariant 1 is enforced there.
- **Core `files/bulk` semantics.** `backend/app/routers/internal.py:532-562` returns `file_to_response` (includes `drive`) for active rows only. The host's `filter-file-ids` (`internal.py:456-490`) also applies `active_file_filter()`, so "active only" in hydrate denies nothing the host filter would have allowed. No new false denial.
- **Hydrate 30 s cache.** Failures are not cached (`app/file_hydrate.py` returns `{}` before `_cache_set`), so a transient core outage does not leave a 30 s denial. A cached entry could keep a file that was trashed in the last 30 s passing the drive check, but the host filter call runs uncached before it and drops it. A file's drive does not change under the same id, so a stale entry cannot flip drive membership. No reachable leak or user-visible false denial found.
- **`search_files`.** Passes `context.drive` into `retrieve_with_keywords`, which applies `IndexedFile.drive == drive` in `app/search.py` plus the host filter; not touched by this change.

### F1 — Output-side drive gate in `get_related_files` is held by no test (Medium) [introduced]

- Invariant: 1 (relation ids registered as citations must not come from another drive).
- Evidence: `app/rag/tools/get_related_files.py:163-166` — mutant M14 (`drive=context.drive` → `drive=None` on the `candidate_ids` call) passes `tests/test_rag_tools.py` and the full `tests/` suite (2745 passed). The `drive=` argument on this line is created by this commit, so no parent reproduction is needed.
- Why it is not caught: `test_every_file_tool_gates_on_the_asks_drive` denies at the input gate, so the output call is never reached; `test_get_related_files_filters_cross_drive_output`'s `_access` ignores `drive`.
- Reachability today: core rejects cross-drive relations on create, so a cross-drive relation row needs an out-of-band edit; but the code comment on this very line says read does not enforce it, and this line is the only thing holding invariant 1 on that path.
- Suggested fix (not applied): in `test_get_related_files_filters_cross_drive_output` run with `ToolContext(drive="d")` and have `_access` return only ids whose (fake) drive equals the `drive` kwarg — e.g. `FORBIDDEN` in drive `"other"`, `ALLOWED` in `"d"` — so passing `drive=None` or omitting the output gate lets `FORBIDDEN` through and fails. Alternatively record the `drive` kwarg of both calls and assert `seen == ["d", "d"]`.

### F2 — No test holds that `ensure_access` keeps the host's denial (Low) [pre-existing]

- Invariant: the first access layer ("Ask applies access control twice", `design-decisions.md` LLM features).
- Evidence: `app/rag/tools/_access.py:73-82`. M10 (host filter replaced by `set(ids)`) and M8 (result iterates `ids` instead of `allowed`) both pass the full suite. M10 also survives at parent `5e9cbc6` (2738 passed) → pre-existing; M8 is on a line this commit creates but is the same gap.
- Why: the new parametrized test's `_host_allows` returns all of `{"A","B","C"}`, and every tool test monkeypatches `ensure_access` wholesale, so nothing distinguishes "host allowed" from "requested".
- Impact: in production the addon proxy validates `X-Lit-Drive` against the viewer's accessible drives, so drive equality nearly implies access today; the gap matters if a later change drops the host call or widens drive-less callers.
- Suggested fix (not applied): add one row to `test_ensure_access_keeps_only_files_in_the_asks_drive` where the host allows a strict subset, e.g. host `{"A"}`, hydrated `{"A":"d","B":"d"}`, drive `"d"` → expected `{"A"}` (kills M8 and M10).
