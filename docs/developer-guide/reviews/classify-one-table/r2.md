## The four questions the brief asked

**1. Is the regeneration script honest? Yes.** Extracted
`3a8841db:backend/app/services/filetype.py`, ran
`backend/scripts/record_classify_golden.py` against it inside the image, and
diffed the output against the committed fixture:

```
script-from-parent keys: 204   committed fixture keys: 204
only in script: []   only in fixture: []   value mismatches: 0
```

The fixture is exactly what the script produces from the revision it claims to
have come from. Round 1's B-3 ("nothing in the repository can re-derive it") is
answered. What is *not* answered is keeping it that way — **B-5**.

Run with no argument (its default — the working tree's own classifier), the
script produces a fixture differing in exactly the 30 compressed names. The
docstring's warning is accurate, and R17 shows the suite catches that particular
mistake.

**2. Does `names()` cover what invariant 2 claims? Partly.** The extension axis
is a rule (`types_map ∪ common_types ∪ _EXTENSION_TABLE ∪ _EXTRA_MIMES ∪
_SUBTITLE_EXTENSIONS ∪ suffix_map ∪ {.loft}` = 174) and the encoding axis is a
rule (`sorted(mimetypes.encodings_map)` = 5). The compound axis is **not**:
`COMPOUND_STEMS` is five names typed by hand, so the compressed dimension is
25 probes where the cross-product it is standing in for is 870. Measured
consequence in **B-3**.

Nothing in `suffix_map` or `encodings_map` is missed as a *key*: all six
`suffix_map` extensions appear as `sample.<ext>`, and all five encodings appear
in the cross-product. One latent trap: `COMPRESSED_SUFFIXES` matches with
`str.endswith`, which is case-sensitive, so a probe named `x.tar.z` would land
in the wrong partition. No such name exists today.

**3. The acknowledged survivor.** R13 confirms it: `.svg` set to `other` in the
table *and* the golden is green, at round 2 exactly as at round 1. But the
round is not neutral here — `test_a_compressed_name_is_other_whatever_it_wraps`
carries `assert _golden()[name] != DEFAULT_CLASSIFICATION`, which is a real
tautology detector for its 30 names: R14 (golden corrupted alone) and R17 (the
whole fixture self-recorded) both die on it. So the compressed partition is
now protected against the M27 shape and the single-extension partition is not.

The cheap check for the rest, not implemented: vendor
`3a8841db`'s `filetype.py` as `tests/fixtures/parent_filetype.py`, load it with
`importlib` in the test, and compute the expected value at test time instead of
reading a JSON file. Cost: ~230 lines of frozen code in the tests tree, and the
fixture file goes away. Buys: the golden stops being editable, so R13 becomes
unreachable rather than merely unlikely, and the "regenerate and diff" step
stops being a manual habit. The alternative — extending `test_filetype.py`'s 26
hand-written assertions past its current 13 extensions — buys one row per
assertion and never reaches 152.

**4. Did the `.svgz` measurement generalise further than it should? Yes.**
See **B-1**. The ffmpeg half of the claim is true and I reproduced it: a real
gzipped SVG and its plain twin both yield a **byte-identical 3425-byte JPEG**
through `generate_image_thumbnail`, because this image's ffmpeg carries the
`librsvg` decoder and librsvg reads gzip. The viewer half is false.

Invariant 8 speaks of buckets, and **no bucket moves** for a single-extension

## Findings

### B-1 `[pre-existing]` — `.svgz` is back in the `image` bucket, but the only image surface that can read it is the thumbnail.

Invariant 2 justifies the exception on one measurement: *"ffmpeg produces the
same thumbnail from it as from the plain SVG"*. That measurement is sound and I
reproduced it. The row it justifies puts `.svgz` into `file_type == "image"`,
which is the switch four other surfaces read.

Measured, surface by surface:

| surface | `.svg` | `.svgz` |
|---|---|---|
| `generate_image_thumbnail` (`thumbnail.py:412`) | 3425 B JPEG | **identical 3425 B JPEG** |
| `read_image_dimensions` (`scanner.py:464,675`) | None (Pillow cannot open SVG) | None |
| `extract_exif` (`scanner.py:469,679`) | None | None |
| `FilePreview` `<img src="/api/files/{id}/stream">` | renders | **does not render** |

The viewer is the divergence. `files.py:809` sets `Content-Type` from
`file.mime_type` — here `image/svg+xml` — adds `X-Content-Type-Options:
nosniff`, and sets **no `Content-Encoding`**; `grep -rn "Content-Encoding"
backend/app/` finds it only in `safe_image_fetch.py`. The bytes on the wire are
gzip. `FilePreview.tsx:148` sends every `file_type === "image"` through an
`<img>` tag (`FilePreview.test.tsx:175` fixes that deliberately, so that the
`Content-Disposition: attachment` this endpoint adds for `image/svg+xml` is
ignored as a sub-resource).

Served with exactly those headers and loaded in Chromium:

```
plain: complete=true  naturalWidth=200 naturalHeight=120
svgz : complete=true  naturalWidth=0   naturalHeight=0
```

**Failure scenario.** A drive holds `diagram.svgz`. It gets an image card with a
correct thumbnail, so it looks healthy in the grid. Opening it shows a broken
image with no error — the file-detail page for that file is empty. At
`872a98d9` the same file was `other` and got the generic file view, which at
least offers a download. Reproduced against `3a8841db`: identical, because the
parent also answered `("image", "image/svg+xml")`. Hence `[pre-existing]` — but
this commit is what brings it back, and it is the one row the commit adds.

**Prose.** `filetype.py:66` reads *"The gzipped SVG browsers render
natively."* Browsers render it when it arrives with `Content-Encoding: gzip`;
this app never sends that, and the sentence is the first thing a reader
debugging the blank preview would trust. **Delete that clause.** The rest of
the comment (ffmpeg, and why every other compressed name is `other`) is
measured and correct.

### B-2 `[introduced]` — the `.svgz` exclusion in `COMPRESSED_NOW_OTHER` is dead code.

```python
COMPRESSED_NOW_OTHER = {
    name for name in _golden()
    if name.endswith(COMPRESSED_SUFFIXES + COMPRESSED_ALIASES)
    and not name.endswith(".svgz")
}
```

`"sample.svgz".endswith(".gz")` is **False** — the last three characters are
`vgz`. `.svgz` is also absent from `COMPRESSED_ALIASES`, which lists five of
`mimetypes.suffix_map`'s six keys. So `sample.svgz` never enters the set, and
the clause that appears to be what protects it removes nothing. R6 deleted the
clause: **390 passed**, unchanged.

What actually keeps `.svgz` out of the moved partition is its omission from
`COMPRESSED_ALIASES`, which reads as an oversight against the comment directly
above it (*"`mimetypes.suffix_map`: one extension standing for two"* — six keys,
five listed).

**Failure scenario.** A reader completes the alias list from `suffix_map`, as
the comment invites, and adds `.svgz`. Nothing breaks (R11: 390 passed) because
the dead clause catches it — but the two mechanisms now disagree about which
one is load-bearing, and the next person to simplify either one has no test
telling them which. Deleting the clause and leaving a one-line note on
`COMPRESSED_ALIASES` saying the sixth key is the exception is the shape that
matches the code.

### B-3 `[introduced]` — the compound probe set is five hand-picked stems, and it never probes an audio or an archive payload.

`COMPOUND_STEMS = ("notes.txt", "clip.mp4", "page.svg", "backup.tar",
"sheet.csv")` covers `document`, `video`, `image` and `other`. Round 1 measured
the transitions as *document→other 185, image→other 116, **audio→other 90**,
**video→other 55**, archive→other 5*; two of those five buckets are unprobed.

R16 made `classify` peel one compression suffix and return the payload's answer
**only when the payload is audio or archive** — a direct violation of invariant
2 (*"A name carrying `.gz`, `.bz2`, `.xz`, `.Z`, `.br` … is `other`"*). Result:
**390 passed**, nothing objected. Under that mutation:

```
song.mp3.gz  ('audio',   'audio/mpeg')
a.zip.gz     ('archive', 'application/zip')
clip.mp4.gz  ('other',   'application/octet-stream')   <- probed, so held
```

`is_probeable_media("audio", "audio/mpeg")` is True, so `song.mp3.gz` goes to
ffprobe on every scan and lands in the Audio bucket with a player that cannot
open it — which is the exact class of harm the user's decision was made to
avoid.

**Why this is a B and not an A.** The code as committed satisfies invariant 2;
the mutation is what violates it. This is a hole in the parity set, not a live
defect. It is reported because it is the *same* hole round 1 filed as A-1 — a
probe set chosen on one dimension — one axis further in. The fix is the rule the
docstring already claims (*"derived from a rule rather than listed"*): replace
the five stems with the cross-product,
`[ "sample" + ext + enc for ext in sorted(exts) for enc in ENCODINGS ]`. That is
870 names instead of 25, a fixture roughly five times larger, and no new
judgement about which stems matter.

### B-4 `[introduced]` — the case test now reads `_EXTENSION_TABLE` on both sides, and it measurably lost a kill.

Before: `for extension, expected in _golden().items(): assert classify("SAMPLE"
+ extension.upper()) == expected`. After: `for extension in _EXTENSION_TABLE:
assert classify("SAMPLE" + extension.upper()) == _EXTENSION_TABLE[extension]`.

`review-workflow.md` detector rule 5: *"Never build the expected value out of
the observation. A derived expectation cannot catch a deletion — the removed
element leaves both sides at once."* That is literally what happens: delete a
row and the loop no longer iterates it.

Measured. R1 (delete the `.svgz` row) kills **2** tests as written. R18 — the
same deletion, with only the case test restored to its round-1 shape — kills
**3**, the third being
`test_the_extension_is_matched_without_regard_to_case`. The kill exists and
this commit removed it.

Nothing is left uncovered today: the golden's parametrized test catches every
deletion R1–R3 and R15 tried. So this is redundancy lost, not a hole opened —
but it is redundancy in the one place the branch has no independent oracle
(**B-3**, R13), and restoring it costs nothing: iterate the golden's `sample.*`
keys and compare to the golden's values, as before.

### B-5 `[introduced]` — the generator is committed and nothing can run it where the tests run.

`backend/Dockerfile.test` copies `app/`, `tests/` and `pytest.ini`;
`backend/scripts/` is not in the image. No test imports
`record_classify_golden.py` — the only reference anywhere is the docstring at
`test_classify_table.py:21`. So every mutation to `names()`, to
`COMPOUND_STEMS`, or to `_load` survives by construction, and the fixture is
re-derivable only by a human remembering to do it by hand with the right
`git show` and the right mount.

Round 1's B-3 asked for the generator so *"the fixture can be regenerated and
diffed instead of trusted"*. It can be — I did it, exactly. But the repository
holds no record of that, and nothing fails when it stops being true.

One concrete trap: the docstring says *"Run inside the test image"*, and the
only way to get the file into that image is a bind mount. Its no-argument
default resolves `Path(__file__).resolve().parents[1]/"app"/"services"/
"filetype.py"`, which from a mount at `/tmp/record.py` is `/app/services/
filetype.py` — a `FileNotFoundError`. The documented invocation and the default
cannot both be right. Making the path argument required removes the trap and
the tautology the docstring warns about in the same edit.

### B-6 `[introduced]` — round 1's B-1 fix works, but nothing holds it.

R4 confirms the fix: changing `LOFT_MIME_TYPE` alone now kills two tests where
at `872a98d9` it killed none. The single definition does its job.

R5 shows it is one-way. Re-inlining `"application/vnd.litloft.loft+json"` into
the table row and leaving the constant alone is **390 passed** — behaviour is
unchanged, so no test can see it, and B-1's whole hazard (constant and row
drift apart; `is_probeable_media` starts returning True for `.loft`; the scanner
hands a JSON pointer to ffprobe and `thumbnail.py:527`'s guard stops matching)
is silently back.

This is not a defect in `62f95b7d` — a fix that is correct today and not fenced
is the normal state of most code. It is recorded because the fix's durability
was the thing round 2 was asked to check, and the honest answer is that it
rests on nobody undoing it. The only detector I can name is a source-text one
(*the literal appears once*), which detector rule 4 puts last; I would not add
it.

### B-7 `[introduced]` — the decided behaviour change ships with no `docs/` page.

`CLAUDE.md`: *"Every change that alters what a user, an operator, or an addon
developer can observe must update the matching page under `docs/` **in the same

Round 1's A-1 named this explicitly as part of remedy (b): *"keep the

**Failure scenario.** A user upgrades with `logs/app.log.gz`, `notes.txt.gz` or

## Trajectory

> *Read the fix diffs in order. Does each round add a branch, a state or a
> prediction that the round before it also added?*

**Round 1 (`872a98d9`) removed state and added one prediction.** Production
code: `_CATEGORY_MAP`, `_ARCHIVE_MIMES`, `_DOCUMENT_MIMES`,
`_MIME_TYPE_OVERRIDES` and `_EXTRA_MIMES` — five tables and the `mimetypes`
call between them — collapsed into one `_EXTENSION_TABLE` and one `.get`. Tests:
it added `classify_golden.json` (a prediction) and the tests that read it.

**Round 2 (`62f95b7d`) added a prediction, and one branch inside the state
round 1 built.** Production code is `+7 −2`: one table row (`.svgz`), one
constant moved above the table, one comment. The row is a branch in the sense
that matters — an extension that is an exception to the rule the round before it
declared. The test side is where the weight is: three new module-level constants
(`COMPRESSED_SUFFIXES`, `COMPRESSED_ALIASES`, `COMPRESSED_NOW_OTHER`), one
parametrized test split into two, one dedicated `.svgz` test, and the golden
grown from 168 to 204 entries.

**So yes, literally: two rounds in a row whose fix adds a prediction.** But the
shapes are not the same shape, and I do not read this as a design being patched:

- Round 1's diff is net-removing in production code. Round 2's production diff
  is five lines. Neither round is "one more case the last one did not
  anticipate" in the implementation — the implementation is still one dict and
  one `.get`.
- Round 2's prediction *grew along the axis round 1's was measured to be blind
  on*. Enlarging an oracle after a reviewer showed it was chosen where the claim
  survives is the loop working, not the loop patching.
- Round 2 also produced a genuine convergence signal: the
  `!= DEFAULT_CLASSIFICATION` guard kills R14 and R17, two shapes that were
  invisible at round 1.

**What I would watch, and the one thing I would put in front of the
supervisor:** the `.svgz` exception is now carried in four places — a table row,
a comment justifying it, a dedicated test, and an exclusion clause in
`COMPRESSED_NOW_OTHER` that turns out to do nothing (**B-2**). And **B-1** shows
it does not actually work: the file gets a correct thumbnail and a blank viewer.
If a round three adds `Content-Encoding` handling, or a decompress step in the
stream endpoint, or an `.svgz` case in `FilePreview`, that is the third round
adding a branch for the same exception and the trajectory finding becomes real.

The move that ends the chain instead of extending it is available now and
**removes** things: drop the `.svgz` row back to `other`. That deletes a branch,
a comment, a test and a dead clause, restores invariant 2 to a rule with no
exception, and costs one thumbnail on a file the app cannot display anyway. I am
not assigning that — per R-4 the author does not assign C and neither does the
reviewer. I am reporting the shape and the diffs it rests on.
