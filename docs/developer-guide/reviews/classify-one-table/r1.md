## Findings

### A-1 `[introduced]` — a filename with a compression suffix changes bucket; 451 measured. Invariants 1 and 7.

The parent called `mimetypes.guess_type(filename)`, which consumes the **whole
filename**: it strips one `encodings_map` suffix (`.gz .Z .bz2 .xz .br`) and
expands `suffix_map` (`.svgz .tgz .taz .tz .tbz2 .txz`) before looking up a
type. The new `classify` consumes `Path(filename).suffix` — the last suffix
only. Those are different functions of the filename, and the change swapped one
for the other.

Measured, parent code vs new code in the same image, over
`{every ext in types_map} × {every encodings_map suffix}` plus the six
`suffix_map` extensions — 766 names:

```
BUCKET MOVED: 451   mime-only changed: 280
transitions: document→other 185, image→other 116, audio→other 90,
             video→other 55, archive→other 5
```

Concrete cases:

| filename | `3a8841db` | `872a98d9` |
|---|---|---|
| `page.svgz` | `("image", "image/svg+xml")` | `("other", "application/octet-stream")` |
| `notes.txt.gz` | `("document", "text/plain")` | `("other", "application/octet-stream")` |
| `talk.mp4.gz` | `("video", "video/mp4")` | `("other", "application/octet-stream")` |
| `backup.tar.gz` | `("other", "application/x-tar")` | `("other", "application/octet-stream")` |
| `bundle.tgz` | `("other", "application/x-tar")` | `("other", "application/octet-stream")` |

**Failure scenario.** A drive holds `diagram.svgz`. `scanner.py:288` calls
`classify(file_path.name)` on every scan and rewrites `file_type` / `mime_type`
on the existing row. Before the upgrade the row is `image` and the file appears
in the image bucket, the justified grid and the page-turner. After the upgrade
the next scan rewrites it to `other`; it leaves the image bucket, and per the
already-filed known issue *"A file reclassified out of video keeps the frame it
had"* the row keeps its old `thumbnail_path`, so a card in the `other` bucket
draws the old image thumbnail. Same path for `logs/app.log.gz`, `notes.txt.gz`
(`document` → `other`) and any `*.tar.gz` (mime `application/x-tar` →
`application/octet-stream`, which `files.py:1274` reads to choose
`inline` vs `attachment` for a ZIP entry).

**Why it is an A and not a B.** Invariant 7 is *"No bucket moves in this
phase"*, invariant 1 is *"the same `(file_type, mime_type)` for every
filename"*. 451 names move bucket. Nothing in the change sees it, and the
reason is the shape of the parity set, not an oversight in one row:
`test_every_answer_is_the_one_the_container_gave` builds every probe as
`"sample" + extension`, a single-extension name. Single-extension names are
precisely the dimension on which `guess_type(filename)` and
`Path(filename).suffix` agree. `review-workflow.md` detector rule 5: *"Pick the
dimensions the thing actually has, not the one where the claim survives."* A
test set that cannot see an A is an A.

**Honest note on direction, for the supervisor's triage.** For almost all 451
the new answer is the better one — a gzipped MP4 is not playable video, and
calling `notes.txt.gz` `text/plain` let a compressed blob into the text-write
and addon-read allowlists. `.svgz` is the one case where the compressed form is
itself the format. So the defensible remedies are (a) add the encoding-aware
handling back so phase 1 really is a no-op and move this in phase 2, or (b) keep
the behaviour, revise invariants 1 and 7 to exclude compound suffixes with the
round that prompted it (R-0 says the supervisor or the user revises, not the
author), record the move as user-visible under `docs/`, and add probes on this
dimension to the parity set. Either way the parity set needs names with more
than one dot in it.

### B-1 `[introduced]` — `.loft`'s mime is now written twice, and the copies may drift silently.

`filetype.py:31` states the row `".loft": ("video", "application/vnd.litloft.loft+json")`
as a literal. `filetype.py:194` then defines
`LOFT_MIME_TYPE = "application/vnd.litloft.loft+json"` independently, and that
constant is what `is_probeable_media` (`:212`), `chapters.py:126` and
`thumbnail.py:527` compare against. At `3a8841db` there was one definition:
`_EXTRA_MIMES[".loft"] = LOFT_MIME_TYPE`.

Measured (M20 / control C1): changing `LOFT_MIME_TYPE` alone **survives the
whole target set at `872a98d9`** and **is killed at `3a8841db`** by
`test_filetype::test_loft_classified_as_video`, which asserts the literal. The
commit removed the only thing that tied them together.

**Failure scenario.** Someone renames the vendor mime (a `+json` suffix fix, a
vendor-tree registration) by editing `LOFT_MIME_TYPE`, the table row keeps the
old string, the suite stays green. `classify("talk.loft")` still returns the old
mime, so `is_probeable_media("video", <old mime>)` now returns **True**:
`scanner.py` and `upload.py` hand the `.loft` JSON pointer to ffprobe, and
`thumbnail.py:527`'s guard stops matching, so the scanner tries to cut a
thumbnail out of a 200-byte JSON file on every scan of every `.loft` row.

M21 also shows the `.loft` guard inside `is_probeable_media` has no test of its
own at either SHA — deleting `and mime_type != LOFT_MIME_TYPE` is green. That
half is `[pre-existing]`; the duplication that makes it reachable is not.

Remedy: move `LOFT_MIME_TYPE` above the table and write the row as
`".loft": ("video", LOFT_MIME_TYPE)`.

### B-2 `[pre-existing]` — the table now states as decisions a handful of rows nobody would decide.

The header says the table holds *"what Litloft does with a file … for every
extension this project has decided about"*. Faithful transcription of the
parent means the file now asserts, in the project's own voice:

| row | states | what the file is |
|---|---|---|

| `.3gp` `.3gpp` `.3g2` `.3gpp2` → `audio` | audio | 3GP is predominantly a phone **video** container |
| `.mpa` → `("video", "video/mpeg")` | video | MPEG **audio** |

| `.xml` → `document`, `.rdf` `.xsl` `.wsdl` `.xpdl` → `other` | split | all XML |

`.ass` is the one with teeth: filed as `audio`, `is_probeable_media` returns

lands in the Audio bucket with no duration and no thumbnail. Reached by putting
a `.ass` subtitle beside the video it belongs to, which is where subtitle files
live.

Not fixable here — invariant 7 forbids moving a bucket in this phase, and I have
not verified these against a wider mime table. Recording them because the
mechanical change from accident to declaration is what makes them worth a
decision, and phase 2 is where that decision is made. `known-issues.md` already
carries the sibling entry for `.webp` / `.mts` / `.m2ts`.

### B-3 `[introduced]` — the table and the golden came from one measurement, and nothing in the repository can re-derive either.

This is the question the brief asked. Measured answer, in four parts.

**Was the table derived from the same run as the golden?** Every sign says yes,
and I cannot check it from the repository because **no generator is committed** —
the commit adds four files and none of them produces `classify_golden.json`.
What I could check is that the recording is faithful: running the parent's
`classify` live over all 168 golden keys in the test image gives
**0 mismatches** against the fixture. So the golden is an accurate snapshot of
`3a8841db`, and by transitivity the 151 table rows are right for single-extension
names. That verification lives in this review and nowhere else; after this round
nothing in the repository can perform it again.

**What does the comparison still catch?** More than a tautology, because the
golden is a frozen file rather than a value computed at test time. Measured: a
deleted row (M1–M6, M10), a changed `file_type` (M7, M9, M11), a changed mime
(M8), a changed `DEFAULT_CLASSIFICATION` (M16, M17), a lookup that stops being
an exact match (M12, M14), a reordered return (M13), an added row (M18, M19)
are all killed. No table row's value equals `DEFAULT_CLASSIFICATION`, so every
deletion is visible — that is what makes the deletion case work, and it is worth
knowing it depends on that.

**Would a row that is simply wrong be caught?** **No**, if it is wrong in both
copies. M27: setting `.svg` to `("other", "image/svg+xml")` in the table *and*
in the golden leaves the whole target set green — 304 passed. The suite cannot
distinguish "the project decided `.svg` is not an image" from "the recording was
wrong". The 26 hand-written assertions in `test_filetype.py` are the only
independent oracle, and they cover 13 extensions of 151.

**Does `test_the_golden_covers_every_row_of_the_table` close the gap?** Not
that gap. It asserts `set(table) - set(golden) == set()`, which catches a row
added without a recording (M19) and a fixture truncated below the table (M23) —
both real, both killed. It says nothing about whether any shared value is
right. It is a coverage assertion, not a parity assertion.

**Is a stronger check available?** Yes, and it is cheap. The parent's
`filetype.py` is one `git show` away and runs unmodified in the same image, so
the recording is reproducible from the repository's own history. Commit the
generator — `scripts/record_classify_golden.py` that takes a SHA, extracts that
file, runs both implementations over
`types_map ∪ common_types ∪ table ∪ {compound-suffix probes}` and writes the
fixture. Then the fixture can be regenerated and diffed instead of trusted, the
key set is derived from a rule rather than from a list, and the compound-suffix
dimension of **A-1** falls out of the same enumeration. Note also that this is
what makes the phase-2 edit safe: today, moving `.py` out of `document` means
hand-editing 151 rows' worth of oracle in two files at once, which is the exact
motion M27 shows is invisible.

Scope note: the key set itself is complete for its dimension.
`types_map - golden` is empty (all 152), and the 16 extra golden keys are
`mimetypes.common_types` entries plus `.loft` and the two subtitles — so no
extension the container's `mimetypes` knows was left out. Invariant 1 says
"all 160"; it is 168. Bookkeeping, not a defect.
