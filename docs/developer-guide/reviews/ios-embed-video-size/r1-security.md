# R2 security / contract review, core 99f214f16 + addon 6cba254 (read-only)

1. Trust boundary. EmbedFrames.didReceive (EmbedFrames.swift, ~L83-98) derives videoId only from message.frameInfo (isMainFrame, securityOrigin scheme/host, frame.request.url host and /embed/<11-char id> path) via the pure videoId(...). The body is consulted only after that guard passes. The handler is added with contentWorld Self.world (named "litloft-embeds"), and the user script is injected into the same world, so neither the main page's scripts nor YouTube's scripts (main world) can reach window.webkit.messageHandlers.litloftEmbed (isolated-world wrappers are separate; platform claim, unverified on device but is WebKit's documented contract and the page tests cover provider/foreign frames). Main-frame provider page: rejected by !isMainFrame. Provider host with another path or foreign scheme/host: rejected (tests foreignFrameReportsNothing). A hostile embed cannot name a different videoId: the id comes from its own frame URL, never the body. Residual (not a hole): a YouTube frame whose own URL is /embed/X reports for X, which is what the page asked for. Result: invariant 2 and 5 hold.

2. Input validation. size(from:) requires a [String:Any] body, w/h NSNumber that is not a CFBoolean (Bool excluded), finite, >0, <=16384; strings, NSNull (the announce postMessage(null)), arrays, missing keys all give nil. A nil size on a non-dict body falls through to the announce path, which is pre-existing behaviour (frames[videoId]=frame), so a bare {} or "x" from an embed frame re-registers the frame; pre-existing for the null case. Numbers reach the page only via JSONEncoder (Double) and evaluateJavaScript("window.__litloft?.receive(<json>)"); videoId is constrained by isVideoId to [A-Za-z0-9_-]{11} ASCII, so the JSON/JS interpolation cannot inject. The script itself reads videoWidth/videoHeight from the element, integers by construction. Page side: positive() is typeof number, finite, >0, and only width>height is used; no number reaches a string, URL, style or log. Note the page does not enforce the 16384 cap (only the shell does); harmless since only the comparison is used. Fractional values would be accepted and are harmless.

3. Worst case. A hostile or buggy embed can only influence whether a full screen on that .loft asks the shell for landscape, i.e. app orientation for the duration of the full screen (page.immersive landscape), which is user-reversible by closing full screen. Nothing opens/closes full screen, touches playback or progress (invariant 6: the subscriber only writes a ref). Flooding: events are loadedmetadata/resize, not polling (no timer in the script; the 1.5 s spike poll is absent). A frame's own JS (YouTube, or ads in nested frames, each judged by its own frameInfo) can dispatchEvent("resize") on a real video in a loop, since the isolated-world listener sees DOM events from main world; each fires a message, a JSON encode and an evaluateJavaScript on the main actor, with no coalescing. In the personal-tool LAN premise (YouTube is the only party, nested frames are not provider-judged embeds unless /embed/<id>) the cost is a self-inflicted CPU burn, not exploitation. No new logging was added on the size path (the log.info remains only on the announce and enterFullscreen paths); videoId is already logged public there (pre-existing).

4. Privacy. New outbound data: one video's pixel dimensions to the Litloft page that embedded it. No logging, no persistence, nothing sent off-device.

5. Contract compatibility. New shell + old page: receive() filters only on type being a string; listeners (nativeMedia apply on message.type==="media.state", shellImmersive on "page.immersive.applied", pong on seq) all check type first, so an unknown embed.size is ignored. Old shell + new page: embed.size never arrives, the reader returns null, and the addon's isLandscape returns false. BUT see finding 1: that is NOT "as in #426" because #426's addon (d80dc2a) asked for landscape for every non-/shorts/ URL, and 6cba254 (based on 78211bf, not on d80dc2a) replaces that, so the old shell + new page pair never turns sideways. Contract version stays 4 (ShellBridge.contractVersion) and the page has no version check for this feature, so the page cannot tell the shells apart. Fixture/test parity: the web side reads shell-contract.json "reports.embedSize" in embedVideoSize.test.ts (TypeScript hook against the sample) and the Swift side encodes EmbedSize and compares to the same sample via NSDictionary (ContractTests.embedSize) plus everyReportIsCovered set check: two different implementations against one sample, as detector rule 2 wants. One gap: the Swift check does not exercise the inbound script body ({w,h}) against the same sample, but that is a different channel and covered by EmbedFramesTests/page tests.
5b. Isolation. Same-id double embed on one page: both frames report for the same videoId and the last report wins in each hook instance (every YouTubeEmbed instance subscribes), so two embeds of one video with different sizes cross-talk; negligible (same video, same picture). Different ids: filtered by videoId. useEmbedVideoSize resets the ref on videoId change and the subscribe effect returns the unsubscribe; receiver is removed when the last listener leaves. Staleness: if the iframe survives while the component's effect re-runs (videoId unchanged), no reset; if the effect re-runs for the same id after the video's metadata already loaded, the shell will not re-send and the size is lost until the next resize event (effect deps [videoId] only, so this needs a videoId change; and a changed id means a new frame, so benign). Frame navigating to another video inside the same frame: resize/loadedmetadata fires again with the new picture and overwrites; frames[] stale-entry behaviour is pre-existing.

6. Repo rules. design-decisions: nothing in drive boundary, file state, watch history. "No core-to-addon dependencies": core does not import the addon; the addon imports @/lib/embedVideoSize from core (allowed direction). Merge order: addon CI checks out core ref develop (ci.yml L49, L150), so the addon's CI passes only after the core PR (with embedVideoSize.ts) is on develop, and the addon commit would fail to import against an older core; the core-first order is sufficient and the pointer bump after the addon merge is per CLAUDE.md. The addon branch also drops d80dc2a's behaviour, so the two addon branches must not both merge (see finding 3). comments.md: ShellBridge/EmbedFrames comments are mostly explanatory of the trap; "A frame is recorded when it loads and may have moved on" is pre-existing; embedVideoSize.ts "A message is whatever the shell sent, whatever its type says" is a comment on positive() that reads oddly but is not misleading; addon comment "Known only once the video has loaded; until then it asks for nothing." restates the code lightly (B, delete). tests.md/detector rules: `#expect(page.sizes.count >= 1)` in EmbedFramesPageTests.sizeIsReported is not an enumerating assertion over a set: repeated loadedmetadata/resize events legitimately yield more than one report and the next lines pin first.videoId and first.size exactly, so it is a deliberate lower bound; arguably it should be `!page.sizes.isEmpty` for honesty, no mutation survives either way (B, optional).

## Findings

1. [A][introduced] Old shell (contract v4, e.g. the #426 build) + new addon: a landscape .loft never turns sideways. Addon 6cba254 YouTubeEmbed.tsx isLandscape returns size!==null && width>height; with no embed.size ever delivered it returns false forever, whereas #426's addon (d80dc2a) asked for landscape for every non-/shorts/ URL. Invariant 7 ("older shell: .loft behaves as in #426") is violated for the supported pairing, and ShellBridge.contractVersion stays 4 so the page cannot detect it (nativeBridge.ts shellVersion/REQUIRED_* pattern exists for exactly this). The author's "no version bump needed" claim holds only for new page + old shell producing no crash, not for behaviour. Fix direction: bump the contract to 5 with a shellReportsEmbedSize gate and keep the d80dc2a rule as fallback below it, or restate invariant 7 as accepted loss with the user's approval (supervisor decides).

2. [B][introduced] No coalescing of repeated identical sizes: every loadedmetadata/resize from the frame costs a JSON encode + evaluateJavaScript. YouTube's own script can dispatch synthetic events on the video in a loop (isolated listener sees them). Worst case self-inflicted CPU in a personal-tool premise; a "same as last size" check in the script or onSize would bound it. EmbedFrames.swift script ~L68-75, didReceive ~L97.

3. [B][introduced] The addon's two unmerged branches (feat/landscape-fullscreen-in-the-shell d80dc2a, which is the PR #426 addon pin, and feat/loft-landscape-from-the-embed-size 6cba254 based on main/78211bf) both edit the same isLandscape slot in YouTubeEmbed.tsx and 6cba254 does not contain d80dc2a. If #426's addon is merged first, 6cba254 will conflict or, if rebased naively, double-define isLandscape; if the pointer is bumped to 6cba254 without d80dc2a, the core PR #426 test path expecting the /shorts/ rule differs. Merge order and rebase of the addon branch should be stated.

4. [B][introduced] Page-side positive() does not repeat the shell's 16384 cap, so invariant 3 is enforced only in the shell; harmless today (only width>height used). Optional.

5. [B][introduced] Addon comment "Known only once the video has loaded; until then it asks for nothing." restates the code; per comments.md delete.
