## Findings

### F1 — Clearing tags promotes a body that starts with `---` into frontmatter
- severity: medium (silent content change; rare input)
- label: [introduced] — parent leaves the file untouched (reproduced)
- invariant: **3** (body meaning changes)
- scenario: `.md` = `---\ntags:\n- a\n---\n\n---\ntags:\n- hidden\n---\nrest\n` (frontmatter holds only `tags:`, body opens with a `---` line). `PUT /api/files/{id}/tags {"tags": []}`.
- wrong result: disk becomes `---\ntags:\n- hidden\n---\nrest\n`; response and `File.tags` = `["hidden"]` although the request cleared them; rendered body goes from the whole block + `rest` to `rest`. Variant `---\ntags:\n- a\n---\n\n---\n\nSection text\n\n---\nmore\n` → disk `---\n\nSection text\n\n---\nmore\n`: `parse` now drops "Section text" from the body (non-mapping block), and every later tag write on the file is refused 422.
- cause: `new_text = ... if metadata else parsed.body` — with the last key removed the body is written with no block in front of it, so a body whose first line is `---` is re-read as frontmatter.
- evidence: probe P1/P1b at d7c4662a2 vs parent (parent: 200, file unchanged, body intact). Note: the frontend `withTags` (`frontend/src/lib/frontmatter.ts`, `return parsed.body` when metadata is empty) has the same shape — [pre-existing] twin on the chip-editor path, not re-derived here.
