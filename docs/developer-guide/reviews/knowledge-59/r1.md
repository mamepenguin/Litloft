## Findings

### 1. [introduced] B / low — no test holds that an in-flight earlier clip still triggers the duplicate notice

`frontend/ClipForm.tsx` submit: the new status filter is only pinned at its `failed` edge. Mutation F2 (`status === "ready"`, which also discards `fetching` jobs) survives both suites. With that mutation a bookmarklet pressed twice on the same page, or a Notes form resubmitted while the first clip is still fetching, sends a second clip without asking. No R-0 invariant covers the `fetching` case, so this is not an A under the current list; see the missing-invariant answer. The pre-change code had no status branch, so this gap is created by the change.

### 2. [pre-existing] B — Notes page "Open existing" does not open anything

`frontend/ClipSection.tsx` root: `onOpenExisting={() => setDuplicate(null)}` ignores the file id (P5: no `router.push`, dialog just closes). Invariant 3 as written ("open existing pointing at that successful note") holds only on the Add-menu surface. Same line at `origin/main`; not touched by this PR.

### 3. [pre-existing] B — Add-menu dialog closed before the duplicate lookup returns: silent

`frontend/ClipWebPageDialog.tsx`: if the dialog is closed while `findClipsByUrl` is pending and it returns non-failed jobs, `onDuplicate` sets state on the unmounted dialog; nothing is clipped and nothing is reported. Not a failed submit, so invariant 5 is not broken; same at parent (no `onFailed` existed at all). Adjacent to the known-issue row "silent when closed before the request is accepted", whose text covers only a failing request.

### 4. [pre-existing] (filed) "A clip whose article was written can still show as failed"

Met at the worker `finally`: a stop/cancel during `_on_done` (P-stop) or a `_mark_ready` DB error leaves the job `failed`; this PR adds the matching `knowledge.clip.failed` event, so such a clip now also toasts "could not be clipped". Consistent with invariant 1; the underlying status is the filed row.

### 5. [pre-existing] B — failed jobs reclaimed after a restart publish no event

`app/main.py` `_publish_fail` returns without emitting when `task.drive == ""`, and `reclaim_stale_jobs` builds tasks with no drive. So invariant 1 ("every clip job that ends failed publishes exactly one ... event") does not hold for reclaimed jobs on any failure path, including the new publish one. Held deliberately by `test_a_reclaimed_job_that_cannot_read_its_placeholder_reads_failed` (mutation B6 killed). The invariant text needs the exception rather than the code needing a fix.

(Filed, not met in a new way: "Clip web page from Add can miss its result toast" — core WebSocketProvider keeps only the last event; the new failed event is subject to it like the others.)

## Probed questions from the brief

- Double `knowledge.clip.failed` (hook path + finally): no. `_publish_clip` never calls `on_fail`; the only publish-path emit is the worker `finally`, guarded by `marked` (B4 killed).
- Failed after ready: no. `marked` is set only after `_mark_ready` commits; B3 killed by both ready tests. A raise inside `_mark_ready` before commit gives failed + event, which is finding 4's filed row.
- Failed on a job another worker reclaimed: not reachable in one process. The job is enqueued once by `POST /clips`; re-enqueue exists only on the fetch-retry path, before `_publish`; `reclaim_stale_jobs` runs only at startup. `_mark_publish_failed` does not re-check status/lease, but nothing else can hold the job at that point.
- Empty drive: `_publish_fail` skips the emit (B6 killed). Finding 5.
- Drive access: the failed event goes through `emit_addon_event(..., drive=task.drive)`, the same scoped bridge as `knowledge.clip.ready` (B7 killed).
- Failed filter with mixed jobs: `[failed newer, ready older]` offers the ready one (F1, F11 killed). `[failed, fetching]` offers the fetching placeholder (duplicate notice shown) — untested (finding 1).
- In-dialog actions changing search params: none. Inside ClipSection the only URL writers are Find (`router.push ?q=`) and AllNotes, both of which leave the landing. Core header actions that navigate (Quick Note -> file URL, settings) change the pathname and unmount the page. Duplicate "Create new"/"Cancel"/"Open existing" on the Notes page only set state.
- Bookmarklet arrival: the `[search]` effects also run on mount, but before the autosubmit lookup resolves, so the notice it opens is kept (P3). The existing "does not clip again when the reader goes to Find and comes back" test still passes.
- Toast double-report: the closed-dialog toast fires only for a rejected `createClip`/`findClipsByUrl`, which yields no job id, so ClipNotifier (which only toasts ids in `pendingClips`) cannot also report it. A failure while open shows only the inline error and `failed()` has already run, so closing afterwards does not toast (F5 killed).

## Is anything missing from the R-0 list?

1. **An earlier clip of the same URL that is still in flight (`fetching`) still shows the duplicate notice**; the failed filter removes only failed jobs. (Finding 1 survives because nothing states this.)
2. **Invariant 1 needs its exception stated**: a job reclaimed after restart carries no drive and publishes no event (finding 5). As written the list is unsatisfiable by the current code and a later reviewer would re-report it.
3. **Invariant 3 should name its surface** (Add menu), or the Notes page's non-navigating "Open existing" is an A against it (finding 2).
4. Optional: a job interrupted by a worker stop during publish is marked failed and announced as failed (P-stop). Whether that is intended belongs on the list, since it is now user-visible as a toast.
