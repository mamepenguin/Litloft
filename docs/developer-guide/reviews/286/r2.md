## 2. What `406ddb23` could have broken

### Callers of `getDriveTags` (grepped across `core-copy/frontend/src`, including all four addon trees)

- `components/EditableTagChips.tsx`: `getDriveTags(file.drive)`. The URL has no query, which is byte-identical to the parent.
- `components/sidebar/useSidebarData.ts`: `getDriveTags(currentDrive, currentFolderPath)`.
- `addons/knowledge/AllNotes.tsx`: `getDriveTags(drive, null, "text")`. This call is new in this branch.
- No other addon calls it. `addons/knowledge/api.ts` builds its own `/tags` URL and does not go through this function.

For the sidebar caller, the probe compared the parent `25c36857` implementation (`encodeURIComponent`) with `406ddb23`. The getter was deleted for the comparison. It tried 14 folder values: `undefined`, `null`, `""`, ASCII, `旅行/京都`, space, `+`, `&=`, `%20`, `'()!`, `~*`, `#?` and emoji.
- Every value decodes to the same `folder_path` (WHATWG `URL.searchParams`).
- `undefined`/`null`/`""` send no query, as at the parent.
- Three values differ in bytes → R2-3.

### Does the global stub leak?

The file stubs `URLSearchParams` in `beforeEach` and calls `vi.unstubAllGlobals()` in `afterEach`. `api.ts` resolves `URLSearchParams` at call time and caches nothing at import. The `vitest.config.ts` pool is `forks` with default isolation.

| run | want | result |

| new test file + probe file `zz_leak` (asserts native getter, `size === 1`, `name === "URLSearchParams"`), default config | live | 2 passed |

| **mutant**: remove `vi.unstubAllGlobals()`, default config | live | 2 passed (isolation contains it) |
| **mutant**: remove `vi.unstubAllGlobals()`, no-isolate single fork | kill | probe failed (shows the probe can see a leak) |

Result: no leak, even with isolation turned off.

Sweep: the branch diff (core `25c36857..406ddb23`, knowledge `5056e2c..79e7df6`) adds no other `.size` on `URLSearchParams`, and none of `toSorted`/`findLast`/`.at(`/`Object.groupBy`. The one `.size` in the diff is a `Set` inside a test.

## Findings

### R2-1 [introduced] A — the in-place refetch test covers `tag` and `sort` only; a folder-only or search-only change without a remount is not held (invariant 4; round-1 F-5 partly open)

Round 1 reproduced F-5 by changing the **folder** in place. The author's replacement test, `asks again when the scope changes in place`, changes `tag` and then `sort`. The list is remounted through a key built from the whole scope. Two partial-key mutants survive all 46 knowledge tests:
- F27b: `allNotesHref("", { ...scope, query: "" })`
- F27c: `allNotesHref("", { ...scope, folder: null })`

In the app, a rail folder link or a search submit is a client navigation that keeps `NotesPage` mounted. Under either mutant the heading and URL change but the rows stay those of the old scope.
Reproduction: a disposable probe appended to `AllNotes.test.tsx` rerenders `{view:all}` → `{view:all, folder:Knowledge}` and, separately, `{view:all}` → `{view:all, q:kyoto}`, then waits for a second `getDriveFiles` call. On `79e7df6` both pass (16/16). Under F27c the folder case times out, and under F27b the search case times out.
It is labelled `[introduced]` because `AllNotes.tsx` is new in this branch. A test that lets an A through is an A (R-4). This is detector rule 5, "pick the dimensions the thing actually has": the scope has four dimensions and the test changes two.

### R2-2 [introduced] B — the phone menus' checked state is not asserted (F16b still open, F43 added)

Inverting `isSelected` on the tag menu (F16b) or on the folder menu (F43) survives. `MenuRadioGroup` fires `onSelect` whether or not an option is checked, so the only effect is a wrong `aria-checked`/visual check on the phone menus. No declared invariant covers the checked state, so the bucket is B. Round 1 listed F16b under F-6, and the author's reply treats F-6 as addressed. It is recorded here so the supervisor sees that this part of F-6 did not close.

### R2-3 [introduced] B — `getDriveTags(drive, folderPath)` no longer sends the parent's exact bytes for some folder names; the server reads them identically

Measured with the getter removed, parent `25c36857` vs `406ddb23`:
- `My Notes`: `folder_path=My%20Notes` → `folder_path=My+Notes`
- `it's (draft)!`: `it's%20(draft)!` → `it%27s+%28draft%29%21`
- `~tilde*`: `~tilde*` → `%7Etilde*`

Both encodings decode to the same value in the browser (`URL.searchParams`). They also decode to the same value in the backend, measured in the `litloft-test` image: Starlette `QueryParams(...)['folder_path']` returns `'My Notes'`, `"it's (draft)!"` and `'~tilde*'` for both forms. So the sidebar's folder-scoped tags do not change for a user. The difference already existed at `b94e2bb8`, which introduced `URLSearchParams` here; `406ddb23` only removed `.size`. The answer to question 2's "same URL as before" is therefore: the same request, but not the same bytes. Only a test that asserts the literal parent URL for a folder containing a space would notice.
