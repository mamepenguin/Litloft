## Findings

### R3-1 [pre-existing] B (raise: contradicts the newly approved 8b) — a tag with an uppercase non-ASCII letter lists nothing, while the rail counts its notes

The list filter is `func.lower(Tag.name) == tag.lower()` (`drives.py`, `list_drive_files`). SQLite's `lower()` folds ASCII only, while Python's `str.lower()` folds Unicode. For `Übung` the two sides are `Übung` vs `übung`, so `tag=Übung` lists **0** in every case: exact, lower and upper. Meanwhile `/tags` counts 1 at the root, 1 in `Inbox` and 2 drive-wide (probe table in §1). The tag regex `^[\w\-]+$` accepts such names (`Übung`, `École`, `Москва`).

Reproduced identically on `develop` (`25c36857`) and on the parent `406ddb23`, both drive-wide: `Übung` counts 2 and lists 0. `8cdac7ff` does not change the list filter. It is labelled pre-existing, but 8b now declares exactly this equality, so the supervisor should decide whether 8b is scoped to it.

### R3-2 [introduced] A — two paths that break 8b are not held by any test: `null` folder serialized as `path=null` (F12) and a stale reply from the previous folder (F5)

Both are correct in the code. Both survive all 17 tests.
- **F12**: the no-folder rail would show no tags. The only caller passes `null`, the API test passes nothing, and the component test mocks the function.
- **F5**: after a quick folder change, whichever reply lands last sets the counts. My probe shows that the guard works on the code (`newtag 1` only), but no test does.

A test that lets an A through is an A (R-4). The first is `[introduced]` because the `path` parameter is new in `8cdac7ff`. The second is `[introduced]` because the folder-dependent effect is new in `c391082`.

### R3-3 [introduced] A — the backend `path` test seeds only active Markdown files, so the path branch is not held against trashed or missing notes or other kinds (B8b, B9)

`test_path_counts_only_files_directly_in_that_folder` has no trashed file, no missing file and no non-text file in the folder. Mutants that drop the active filter (B8b) or the kind filter (B9) **only when `path` is set** survive all 41 tests. Invariant 2 and 8b both depend on the path branch applying them. Today the property holds by construction, because the path filter is ANDed onto a query that already has both. What is missing is a test that holds it. `TestFolderScopedTagCountAgreement` in `test_api_tags.py` already has the parity form (count == listing total), but only for `folder_path`, not for `path`.

### R3-4 [introduced] B — the rail shows a count that the list contradicts while tags load or after they fail; the phone menu's keep-the-chosen-tag rule and the clearing on a folder change are not asserted (F4, F8, F9)

- With `tag=AI` chosen, every folder change clears `tags`. `shownTags` then synthesizes `AI 0` (current) until the reply arrives. If the tags request fails, `AI 0` stays next to a list of notes. At the parent `79e7df6` the rail showed no tag section in that state, so the synthetic count is new.
- F4, where the previous folder's counts stay visible during the load, survives.
- F8/F9, where the phone tag menu drops the chosen tag or hides when the folder has no tags, survive. 8b names only the rail, and invariant 7 covers failure only as "the list keeps working", so these are recorded as B. The slow case is reachable on any slow connection.

### R3-5 [introduced] A — a chosen tag in a different case from the tags table is listed as a second entry with count 0, while the list shows its notes (8b)

`shownTags` compares with `tag.name === scope.tag`, but the list matches case-insensitively. With `folder=Inbox&tag=ai` and a table row `AI` (3 notes), the rail shows `AI 3` (not current, link sets `tag=AI`) and **`ai 0` (current)**, while the list shows 3 notes. Measured by probe.

How a user gets there: a hand-edited or shared URL, or a rename. `replace_file_tags` renames the drive's `Tag` row to the newest casing, so after `AI` is re-saved as `Ai` elsewhere, an open or bookmarked `tag=AI` scope hits this on the next folder click. Before `c391082` the rail showed `AI 3` and no phantom entry. Round-1 F-10 recorded the missing selection; this finding is the new false count. The reach is low, but the wrong count persists after loading, which is exactly what 8b states.

### R3-6 [introduced] B — 8b's equality does not hold while a search is active

The rail counts ignore `q`. Choosing a tag keeps `q` (invariant 5), so the list shows the tag's notes that match the search, which is fewer than the count. Folder counts already ignored tag and search before this round, so this is likely the intended reading of 8b. It is recorded so the supervisor can confirm the wording ("the number of notes that choosing that tag lists in that folder").

## 6. Trajectory

Fix diffs in order:
1. `94822646`, `79e7df6`: tests only.
2. `406ddb23`: one condition swapped for one condition (`params.size > 0` → `qs`). No branch, state or prediction added.

5. `169e703`: tests only.

The answer is **no, not yet two rounds in a row.** Round 2 added nothing. Round 3 adds a branch and a prediction, but it implements an invariant revision the user approved (8b), not a patch for a missed case. The fabricated count-0 entry is where this round's defects sit: R3-4 (slow or failed) and R3-5 (case). Both are cases where the prediction is wrong. A round-4 fix that answers them with more handling would be the second consecutive round adding branches or predictions. Examples: a loading flag, a case-insensitive match, or a failure state for the synthetic entry. By the rule, that makes it a C candidate. A fix that **removes** the prediction would converge instead, for example by listing the chosen tag without claiming a count for it.
