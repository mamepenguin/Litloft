## Findings

### F-1 [introduced] A — a locked drive on `folder-counts` is not held by any test (invariant 3)

`test_unknown_drive_is_404_and_unknown_kind_is_422` only tries a drive name that does not exist. Mutant B2 keeps the existence check and removes `check_drive_access`. That leaks a locked drive's folder names and counts, and all 38 change tests stay green.
Reproduction: the reviewer probe `test_locked_drive_404` uses the `two_drives` fixture from `tests/test_target_drive_access.py`. It passes on `b94e2bb8` and fails under B2 (`assert 200 == 404`). The endpoint is new, so the label is `[introduced]` without a parent run. The code is correct at this SHA; only the test is missing.

### F-2 [introduced] A — the drive boundary on `folder-counts` is not held by any test (invariant 1 / drive boundary)

Every fixture in `test_drive_folder_counts.py` uses one drive. Mutant B4 drops `File.drive == drive_name`, and the change tests stay green. Under B4, `GET /api/drives/open/folder-counts` returns the locked drive's `Secret` folder.
Reproduction: probe `test_no_cross_drive` fails under B4 (`[{'path': 'Open'...}, {'path': 'Secret'...}]`) and passes on `b94e2bb8`.

### F-3 [pre-existing] — `GET /tags` has no unknown-drive or locked-drive test

Mutant B12 deletes `_validate_drive` from `list_drive_tags`, and every test in `test_api_tags.py` and the change's tests still passes. Only the reviewer probe kills it. At the parent `25c36857`, `test_api_tags.py` has no 404 assertion on the tags listing either (its only `404` is `PUT /files/{id}/tags`). Ledger item. It is also within invariant 3 as declared.

### F-4 [introduced] B (user-reachable; proposed R-0 revision) — `getDriveTags` drops every parameter on browsers without `URLSearchParams.size`

`frontend/src/lib/api.ts` `getDriveTags` now builds `params.size > 0 ? ... : ""`. `URLSearchParams.prototype.size` exists only from Safari 17 / Chrome 113 / Firefox 112. Next 16's own default target is `safari 16.4` (`node_modules/next/dist/esm/shared/lib/modern-browserslist-target.js`), and nothing polyfills the getter. There, `size` is `undefined`, `undefined > 0` is false, and the query string is silently discarded. Two effects:
- The existing sidebar folder-scoped tag list (`useSidebarData.ts` → `getDriveTags(drive, folderPath)`) becomes drive-wide. That is a regression for a caller this change did not mean to touch. At the parent it built the query from `folderPath` directly.
- The All notes rail's tags lose `type=text` and count videos and images as well.

Reproduction: the reviewer test `src/__probe__/allNotesProbe.test.tsx` P7 deletes the getter and calls `getDriveTags("d", "recipes")` and `getDriveTags("d", null, "text")`. It received `["/api/drives/d/tags", "/api/drives/d/tags"]` on `b94e2bb8`. It expected `?folder_path=recipes` and `?type=text`.
Related test gap: the URL wire of `getDriveTags` and `getFolderCounts` has no test. Mutants F35 (drop `type`) and F36 (drop `type` from folder-counts) survive the 1143 tests in `src/lib`, `src/components/sidebar` and `AllNotes.test.tsx`. F37 (drop `folder_path`) also survives and is `[pre-existing]` in shape. Suggested R-0 line: *"Existing callers of a changed core client function send the same request as before."*

### F-9 [introduced] B (possibly C — supervisor) — tag counts in the rail ignore the selected folder, so a tag promises notes the list then does not have

The rail always fetches `getDriveTags(drive, null, "text")`, so the counts are drive-wide. Tag links keep the selected folder, though. On the preview data (`動画`): with `folder=Inbox`, the rail shows `Litloft 1`. Clicking it goes to `?view=all&folder=Inbox&tag=Litloft`. `GET /api/drives/動画/files?type=text&path=Inbox&tag=Litloft` → `total: 0`, and the page says 0 件. The author's own `all-tag-1440.png` shows the same shape (`Knowledge #AI 0 件`). The spec says only "Tags with counts", so whether the counts should follow the folder is a design question. Recorded as B. Raise it if the supervisor reads it as a design error.

### F-10 [introduced] B — on desktop, a tag the rail does not list cannot be removed, and a differently cased tag is not shown as selected

The rail marks and toggles with `scope.tag === tag.name`, which is case-sensitive. The list filter is case-insensitive (`func.lower(Tag.name) == tag.lower()`). On the preview, `?view=all&tag=litloft` lists the `Litloft` note (`files?type=text&tag=litloft` → `total: 1`), but the rail's `Litloft` entry is not marked selected. Its link goes to `tag=Litloft` instead of removing the tag. When the tag in the URL is not in the rail at all (an old link, a tag renamed or removed, or the author's `tag=AI` screenshot), the "All" link and every folder link keep the tag. The desktop page then has no control that clears it. The phone tag menu does offer "any tag". The only way out on desktop is the back link to the landing.

### F-11 [introduced] B — rail labels truncate from the end, so a deep folder's own name can disappear entirely

The muted parent path and the leaf share one `truncate` span. Measured at 1440px on the preview (`rail width 248px`, Playwright, `folder=Knowledge`), 8 labels are clipped. For two of them the leaf is not visible at all:
- `Knowledge/docs/superpowers / specs`: 0 of 38px of `specs` visible.
- `Knowledge/docs/research / open-notebook`: 1 of 100px visible.

Two folders under the same long parent would render as identical rows, told apart only by their counts. The flat list exists to pick one folder.

## Security perspective — summary

- Locked drive: both endpoints call `_validate_drive` (existence + `check_drive_access`) as the first statement, before any query; probe `test_locked_drive_404` passes for `folder-counts` with and without `type`, and for `tags?type=text`. Test coverage gap: F-1, F-3.
- `type`: `Literal` param, 422 on anything else (live preview: `?type=bogus` → 422, `nope` drive → 404).
- Drive boundary: `folder-counts` filters `File.drive`; `tags` filters `Tag.drive` (join to `File` via `file_tags` unchanged from before). Probe `test_no_cross_drive` passes. Coverage gap: F-2.
- No new write surface, no path input on `folder-counts`.

## R-0: what is missing

1. *Existing callers of a changed core client function (`getDriveTags(drive, folderPath)`) send the same request as before, in every browser Next targets.* (F-4)
2. *`folder-counts` never returns a folder or count from another drive.* (named in the security brief, absent from the list; F-2)
3. *Changing the scope by client navigation, without a remount, shows the new scope's rows.* (F-5)
4. *A selected tag can always be removed from the page at every width.* (F-10)
5. Decide whether *a rail count equals the list total after clicking it* is intended (F-9); if yes it belongs in the list.
