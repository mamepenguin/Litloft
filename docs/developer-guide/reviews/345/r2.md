## The trajectory question

> Read the fix diffs in order — the seven commits of `origin/develop..3411c56c`,
> then `0100bf43`. Does the later work add a branch, a state or a prediction
> that the earlier work also added?

**Answer: no, not in the shape the rule warns about — with one exception, named
below.** `0100bf43` is one removal and one addition, not a round of special
cases. But it leaves one question answered twice and still open, and that is
where a third round would come from.

### What each part of the fix is

**The CR fold removes a branch.** Before it, the file was split into lines by
*two different rules* depending on which path it took: `splitPlainLines` on
`/\r?\n/`, or, for the coloured path, the HTML parser's own input-stream
preprocessing, which folds CR and CRLF on its own before `splitHighlightedLines`
ever sees the text. The fix normalises once, at the top of `decorate`, and both
paths then read one rule. That is a divergence deleted, not a case handled —
the loop converging.

I checked the fold is the *same* rule the parser applies, rather than a second
approximation of it. `content.replace(/\r\n?/g, "\n")` and the spec's
"replace CRLF, then any remaining CR" agree on all ten shapes I tried,
including `\r\r\n`, `\n\r`, `\r\n\r`, a trailing lone `\r`, and a file that is
nothing but CRs. On every one, both render paths produce the folded file
character for character and the same line count.

**The gutter is one idea in five declarations, not five patches.** `width` +
`margin-left` + the block's `padding-left` are a single mechanism — reserve a
column, pull the number back into it — and all three were there in the feature
commit `0ffb3491`. `padding-right` is the gap to the code, also original. The
fix changed three numbers (`3.5ch`→`5ch`, `1ch`→`0.75ch`, `1rem`→`0.5rem`) and
added exactly one declaration, `white-space: nowrap`, which is a guard against
the mechanism's own failure mode (a box narrower than its content), not a new
case. Five declarations, one idea.

### The exception, and it is the one to watch

**`decorate`'s limits are the same question answered a second time, and the
second answer is also wrong.** The feature commit declared two guards with a
comment asserting they bound the cost ("neither limit stands in for the
other"). Round 1 measured that they bound size and not time. `0100bf43` adds a
third guard on the same question and a comment asserting *that* bounds it. It
does not: **measured, a file that passes all three limits still freezes the
main thread for ~20 seconds** (finding 1). A fourth guard on the same question
would be the trajectory signal the rule is about; this is the second.

**And the fold was placed where it does not reach all three render paths.**
`decorate` returns `null` for an over-limit file, and that branch renders
`content` — the *unfolded* string — so the divergence the fix set out to
delete survives on the third path (finding 2). Worse, the fix's own correction
to the line count (now taken after the fold, closing round 1 boundary #5)
routes *more* files into that branch: a CR-only file that used to be decorated
wrongly is now correctly refused, and then drawn run-on.

So the honest shape is: this round removed one divergence and left a third of
it; and answered the cost question a second time without closing it. Neither is
a round of five-line special cases, and I am not calling the design wrong. But
both are the same question coming back, which is what to look at if there is a
round three.

## Findings

### 1. [MEDIUM] [introduced] `MAX_DECORATED_LINE_CHARS` bounds one line's cost, not a file's: ~20 s still passes every limit

`frontend/src/components/TextPreview.tsx:35,120`

The commit message and the docstring both present the per-line limit as closing
the quadratic cost round 1 found ("only a run this long is not [cheap]"). It
closes the *one enormous line* case and not the file case, because the two
limits compose multiplicatively: `MAX_DECORATED_CHARS` (512 KiB) allows **104**
lines of `MAX_DECORATED_LINE_CHARS - 1` characters each, and the per-line cost
is paid 104 times.

The grammars are quadratic *per unbroken run*, so total cost is
`n_chars × line_length` — maximised exactly at the longest line the new limit
allows. Measured in Node against this bundle's own `highlight.js`, 104 lines ×
4999 bare-alphanumeric characters (507.8 KiB, under every limit):

```
csharp       20.5 s      ini          13.7 s      graphql       3.4 s
c            18.3 s      php           8.0 s      bash          2.0 s
cpp          18.0 s      typescript    6.2 s      groovy        1.9 s
java         14.5 s      javascript    3.7 s      r             1.3 s
```

(`ini` extrapolated 13.7 s from a four-line probe and measured 13.3 s at full
size, so the linear-in-line-count scaling is checked, not assumed.)

Against round 1's numbers the fix is a real improvement — the worst case went
from ~12 minutes to ~20 seconds — but 20 seconds of frozen tab, with no cancel
and no progress, is not a bounded cost, and `.cs` / `.c` / `.cpp` are worse
than the `ini` the comment names. The reachable file is the same shape round 1
described: a name that says `.cs`/`.conf`/`.js` over content that is a bare
blob with no separators.

`[introduced]`: by the branch, not by this commit — `develop`'s `TextPreview`
imports no `highlight.js` and renders `{content}` directly. Filed again because
`0100bf43` claims to close it and does not.

Mutations: M-TS3 (limit removed) KILLED; M-TS4 (limit lowered to 100) survived
the unit suite, KILLED in the browser by the 120-character line in the
`code-viewer` fixture.

### 2. [MEDIUM] [introduced] The over-limit branch renders the unfolded content, so a CR-only file that trips any limit is still drawn run-on

`frontend/src/components/TextPreview.tsx:116,220-231`

The fold is a local inside `decorate`. When `decorate` returns `null`, the
component renders `body`, which is `content` — the string before the fold. So
round 1 boundary finding 3's observable survives on the third render path.

Measured in jsdom against the reviewed source:

```
6000 entries joined by bare CR, name big.log   -> 0 .code-line, 5999 CRs in the <pre>
one 6000-char line + "\rtail", name keys.ini   -> 0 .code-line,    1 CR in the <pre>
the same shape under every cap, name small.log -> 3 .code-line,    0 CRs   (folded)
```

And a raw CR in a text node is not a segment break in Chromium, so those CRs
draw nothing. Measured directly, `white-space: pre-wrap`, three "lines" joined
by each separator:

```
CR (\r) -> 1 visual row    U+2028 -> 1 visual row    U+000C -> 1 visual row
```

(The U+2028 and U+000C rows are a clean result, not a finding: neither is a
break on either path, so neither creates a divergence the fold would need to
cover.)

This is made *more* reachable by the fix, not less. `plain` is now taken from
the folded text (correctly — that is round 1 boundary #5 closed, M-TS6 KILLED),
so a CR-only file whose folded line count exceeds 5000 now trips the cap and
lands here, where it is drawn as one run-on paragraph. Before the fix it was
decorated, wrongly but legibly.

Invariant 4 says the text the block renders is the file with CR folded to LF.
On this path it is not.

`[introduced]` by `0100bf43` without a reproduction against the parent: the
fold, and the branch's relationship to it, do not exist at `3411c56c`.

### 4. [MEDIUM] [introduced] The screenshot detector cannot fail on a wrong number, only on a missing or a uniform one

`frontend/e2e-components/code-viewer-desktop.spec.ts:179-199`

The test is named "the number drawn beside a line is that line's number" and
compares the gutter strips of lines 1, 2 and 100 for inequality. Three strips
being pairwise different says the numbers are **distinct**, not that they are
**right**.

| mutation | numbers drawn | want | result |
|---|---|---|---|
| `counter-reset: code-line 100` | 101, 102, 200 | kill | **SURVIVED** (8/8 pass) |
| `counter-increment: code-line 2` | 2, 4, 200 | kill | **SURVIVED** (8/8 pass) |
| `content: "8"` | 8, 8, 8 | kill | KILLED |
| `counter-increment: none` (round 1 M32) | 0, 0, 0 | kill | KILLED |

I confirmed the two survivors are not equivalent mutants by hashing the strips
rather than reasoning about them: under `counter-reset: code-line 100` all three
strip hashes differ from baseline, so different ink really is on the page and
the test really did pass over it.

What the detector *does* hold is worth stating, because round 1's version held
nothing at all: it is real, it is not passing on antialiasing or on subpixel
offsets, and it is stable. `content: "8"` — identical glyph, three different
rows, three different `scrollIntoView` positions — produces byte-identical
strips and kills the test, so the differing-row hypothesis is measured and
dead. Two consecutive baseline runs gave identical hashes, and
`--repeat-each=8` is 64/64 green in 19.8 s. It is also machine-independent: the
strips are compared to each other within a run, never to a stored image.

So this is a detector that is weaker than its name, not a detector that holds
nothing. Closing it means comparing the strip against ink rendered from the
expected number rather than against the other lines.

### 5. [MEDIUM] [introduced] Nothing holds invariant 10 any more: a fold that double-spaces every CRLF file leaves the whole suite green

`frontend/src/components/TextPreview.tsx:116`

M-TS2: `content.replace(/\r/g, "\n")` instead of `/\r\n?/g` — i.e. fold the CR
but do not consume the LF after it, so every CRLF becomes two breaks.
**want=kill, SURVIVED**: 24/24 `TextPreview.test.tsx`, and 7680/7680 across the
whole unit suite.

Probed directly, under the mutant:

```

decorate("a\r\nb\r\n", uncoloured path)   ->  4 .code-line   (want 2)
```

That is invariant 10 — "a CRLF file is not drawn with every line
double-spaced" — on both render paths, with no test red.

The behaviour at the SHA is correct; the gap is coverage, and it is a gap the
fix created. The only CRLF case in the suite is
`codeLines.test.ts:29`, `splitPlainLines("a\r\nb\r\n")`, which tests the
splitter. `decorate` now folds before the splitter ever sees a CR, so that test
passes whatever the fold does, and invariant 10 is held only by the fold, which
nothing exercises with CRLF. The new test beside it covers bare CR only.

A two-line case — `show("a\r\nb\r\n", ...)` asserting 2 `.code-line` — closes
it, and is the same shape as the bare-CR test already added.

## Checked, nothing found

- **The fold is the parser's own rule, not a second approximation.**
  `content.replace(/\r\n?/g, "\n")` versus "replace CRLF, then remaining CR",
  on `\r\r\n`, `\n\r`, `a\rb\r`, `\r\r\r`, `a\r\nb\r\n`,
  `const s = "a\rb";`, `a\r\n\rb`, `""`, `"\r"` and a mixed file: identical on
  every one. On every one, both render paths reproduce the folded file
  character for character and agree on the line count, so `trailingBreak`
  means after the fold exactly what it meant before.
- **Folding before `hljs.highlight` rather than after does not lose text.** A
  bare CR inside a string literal becomes a real break and the grammar's
  colouring changes, but `ignoreIllegals` keeps the output's text identical;
  round-tripped on all ten shapes above.
- **`MAX_DECORATED_CHARS` is still measured on the unfolded content.** A 512
  KiB + 1 file of CRLF pairs that folds to under the cap is refused. Errs
  toward refusing, so nothing renders wrongly; worth knowing it is the one
  limit not taken after the fold.
- **The screenshot detector's clip arithmetic.** `x = round(row.left - gutter)`
  with `scrollIntoView({block: "center"})` first; no scrollbar, caret or
  citation mark falls inside the strip for lines 1, 2 and 100 in
  `code-viewer-many` (which passes no `highlight`). Two baseline runs
  byte-identical; `--repeat-each=8` 64/64 in 19.8 s.
- **Suites restored.** After the last mutation: 522 files / 7680 unit tests
  green, `pnpm tsc --noEmit` clean, `pnpm lint` 0 errors / 63 warnings.
  `git status` shows no tracked file changed.
