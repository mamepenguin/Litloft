## Findings

### F1 — `tsc --noEmit` fails at this SHA (CI `frontend (tsc / eslint)` goes red)
- Severity: HIGH (merge blocker). Bucket: B (breaks no declared invariant; blocks the PR). Label: [introduced]
- What: `typography.spec.ts` widens the global `Window.setTheme` to `(theme: string, colors?: unknown) => void`,
  while `reader.spec.ts` still declares `setTheme: (theme: string) => void` in the same `declare global`.
  Two differing declarations of one interface member are TS2717; the 2-argument call then fails TS2554.
- Evidence: `pnpm -s tsc --noEmit` at ba5492b11:
  `e2e-epub/typography.spec.ts(10,5): error TS2717 ... 'setTheme' must be of type '(theme: string) => void'`,
  `e2e-epub/typography.spec.ts(245,58): error TS2554: Expected 1 arguments, but got 2.`
  With the parent's `typography.spec.ts` checked out, `tsc --noEmit` exits clean. CI runs `pnpm exec tsc --noEmit` (`.github/workflows/ci.yml`).
  Playwright itself transpiles without type checking, so the e2e run stays green and hides this.
- Fix: give `reader.spec.ts` the same signature (it is a touch point in invariants.md that the diff never reached; see "First-round question").

### F2 — `useEpubReader`'s `theme` argument is now only an effect trigger; the value is never used
- Severity: LOW. Bucket: B. Label: [introduced]
- What: `open` and `theme` both take the name from `readAppearance()` (live `data-theme`), so the
  `theme: ReaderTheme` parameter of `useEpubReader` only appears in the effect's dependency list. A caller
  passing a theme that differs from `data-theme` would see its value silently ignored. Today the only
  caller (`EpubPreview`) derives it from the same attribute, so nothing a user can hit.
- Evidence: the parameter's value is read nowhere except the dependency list (`grep -n theme useEpubReader.ts`).
- Fix (optional): drop the parameter and subscribe to `data-theme` inside the hook, or name it as a
  trigger. Not required for this PR.

### F3 — The "dark to light" e2e for invariant 1 never starts dark; the dark→light switch is untested
- Severity: HIGH (the declared invariant's second direction has no test). Bucket: A (a test that lets an A through). Label: [introduced] (test created by this change)
- What: `preview.spec.ts` sets the starting theme with
  `page.addInitScript((theme) => document.documentElement.setAttribute("data-theme", theme), from)`.
  An init script runs before the document has an `<html>` element, so `document.documentElement` is `null` and
  the script throws; the page starts with **no** `data-theme` (light tokens from `:root`). The "dark to light"
  case therefore sets `data-theme="light"` on a page that is already light: `readTheme()` returns `"light"`
  before and after, the effect never re-sends, and the test samples a book that was light all along.
  (The "light to dark" case is valid only because the missing attribute happens to mean light.)
- Evidence (temporary probe spec, removed): with the same init script, `pageerror`:
  `null is not an object (evaluating 'document.documentElement.setAttribute')` (WebKit) /
  `Cannot read properties of null (reading 'setAttribute')` (Chromium); after load
  `data-theme` = `null`, `--bg-primary` = `#ffffff`.
  Mutation E15 (reader applies `theme` only when `d.theme === "dark"`, so a switch to light does nothing):
  **LIVE** across preview, typography and reader specs.
  The behaviour itself is correct: a probe serving `index.html` with `<html data-theme="dark">` showed the
  section body and reader root at `rgb(26, 14, 16)` at open, and `rgb(255, 255, 255)` after switching to light
  and resizing.
- Fix: set the starting theme so it exists before the app reads it, e.g. `page.route` the fixture HTML to put
  `data-theme` on `<html>`, or an init script that sets it on `DOMContentLoaded`/via the fixture's own query
  parameter; and assert the starting `data-theme` before the switch so this cannot go vacuous again.

### F4 — Invariant 2 (text colour `--text-primary`, links `--accent`) is held by no reader-side test

- Fix: add `bodyColor` and an unstyled `a:link` colour to `where()` in `typography.spec.ts` and assert them in
  the existing theme test (one assertion each), per spec-review F6's scoping.

## First-round question: places the diff reaches that are not in the touch-point list

- **The reader document's own `color-scheme`** (`root.style.colorScheme = name` in `applyTheme`). The touch
  points name only the reader `html` *background*. It is load-bearing for the fallback path (E4 is killed by
  the fallback test), and it also changes the reader document's UA surfaces (scrollbars, focus rings) under a
  dark theme. Candidate invariant: none beyond 1/3 — they already cover what it affects.
- **`useEpubReader`'s `theme` parameter** loses its only use; it is now just an effect trigger (F2).
- Inversely, two touch points the diff does **not** reach: `reader.spec.ts` (hence F1) and the
  `epubReaderChannel` tests (the parent sends and never parses `colors`, so no channel test is needed).
- Nothing else: no sanitizer, CSP, typography, progress, backend, endpoint or WS change.

## Security perspective

- **Input validation.** `readColors` accepts only a non-null, non-array object whose `bg`, `fg`, `link` are
  strings matching `^#[0-9a-fA-F]{6}$`, and returns a fresh object with only those three keys. Mutations
  M1–M7 are all killed except the equivalent M3. `;`, `}`, `url(`, `\`, whitespace and newlines cannot pass.
  A getter/`toString` TOCTOU is not reachable: structured clone drops accessors and refuses functions.
- **Other values reaching CSS.** The theme name is checked against `light`/`dark` on both `open`
  (`isValidOpen`) and `theme`; typography values are table lookups (`readTypography`); `OWN_ROOT_VAR` comes
  from the book's own computed font size, not a message; `SYSTEM_COLORS` are constants. No other message
  value is interpolated.
- **Origin/source.** The reader's listener rejects anything not from `parentWindow` at its own origin
  (unchanged, pre-existing); the parent posts with `window.location.origin` as target.
- **Fallback abuse.** A malformed `colors` only selects constant system keywords under the validated scheme
  name, so an attacker who could post would at most choose between the two themes' system colours. It never
  throws (e2e "a theme whose colours cannot be read" posts no `error`).
- **Parent side.** Colours are read from the app's own stylesheet tokens (all 6-digit hex in both themes); a
  book cannot influence them. No finding.
