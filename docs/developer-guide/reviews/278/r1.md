## Findings

### 1. "Skip" now appears only after the user has switched everything off, and pressing it saves those offs — LOW — [introduced]

`frontend/src/app/setup/steps/AddonPolicyStep.tsx:81-83` (`hasAnyToggleOn`) and `:155` (label).

Reproduction (temporary jsdom test, deleted afterwards): one drive `main`, one addon `intelligence`, `value={}`. Before any press the buttons read `["Back", "Next"]`. Pressing `main / intelligence` calls `onChange({ main: { intelligence: false } })`; re-rendered with that value the buttons read `["Back", "Skip"]`, and `goNext` carries that policy to `handleBeforeSubmit`, which PUTs it.

At the parent the untouched state read every switch Off, so "Skip" was the label of the untouched state and skipping stored nothing. With the reading flipped to default-on, the label now means the opposite: it shows only on a state the user built by hand, and that state is saved. `docs/getting-started/first-run-setup.md` (this PR) says "Skipping this step leaves every installed addon enabled on every drive", which the button now contradicts. S3 survives because `SetupWizard.test.tsx` clicks `skip ?? next` and the step's "offers a skip button" test has no addons.

Invariant: none on the list covers the label; it is the user-visible meaning of "Skip" that this change moved. Suggest to the supervisor whether the list should say what Skip does.

### 2. The sibling-preservation half of invariant 4 is not held by either new test — MEDIUM (test lets an A through) — [introduced]

`frontend/src/app/setup/__tests__/AddonPolicyStep.test.tsx` (`stores the opposite of what was shown, for that drive and addon only`) and `frontend/src/app/admin/settings/__tests__/AddonPolicySection.test.tsx` (same title). Code under test: `AddonPolicyStep.tsx:74` and `AddonPolicySection.tsx:120`, `const driveEntry = { ...(policy[drive] ?? {}) }`.

Mutations S4 and S6 replace the spread with `{}`, so pressing one addon on a drive erases every other addon already stored for that drive. All 121 tests pass. Both tests press a switch on a drive that holds nothing (`main` with `{photos: ...}` in the step; `bare: {}` in admin), so "every other addon's stored value is unchanged" is unobservable. S6-b shows a fixture can observe it: pressing `indexOff / intelligence` (drive already holding `knowledge: {index: false}`) kills S6, and the fixture change alone passes.

The tests are new in this commit and are titled for exactly this property; the same gap exists at parent (P-S4/P-S6 survive there with the old tests), so the code is fine and the hole is in the new tests. Invariant 4.

### 3. Nothing ties the frontend's `"index"` to the feature name the backend catalogue actually asks for — LOW — [introduced]

`frontend/src/lib/adminConfig.ts:37` (`isAddonOn` -> `"index"`), `backend/app/main.py:430`, `backend/tests/test_addon_policy_parity.py:78`.

Mutation B4 changes the catalogue's `is_addon_feature_enabled(drive, name, "index")` to `"enabled"`; 281 backend tests selected by `-k 'addon or policy or status'` pass. The parity test hard-codes `"index"` itself when it computes the table's `on` column, so it pins `is_addon_feature_enabled` but not which feature the backend uses to decide "addon on". After B4 a drive stored `{knowledge: {index: false}}` would still list `knowledge`, while both settings screens show it Off. `test_addon_navigation.py::test_drive_policy_still_governs_navigation` only uses bool shapes, which `_all` answers for any feature name.

`isAddonOn` is new in this commit, and invariant 1 defines "on" as what the catalogue does; invariant 7 claims the readings are tied. A fixture that could observe it: `/api/addons/status?drive=` against a drive stored `{addon: {index: false}}`, plus `{addon: {other: false}}` staying listed.

### 4. The wizard's addon-count memo losing its `addons` dependency is not caught — LOW — [introduced]

`frontend/src/app/setup/SetupWizard.tsx:196`.

W4 (drop `addons` from the deps) survives because in every fixture `/api/addons/status` resolves before the drives do, so a later dependency change recomputes the count. W4-late delays the addon list by 300 ms and the test `stores nothing for switches that were not touched, and counts them on` then fails; the delay alone passes. The count loop over `addons` is new in this commit. ESLint `react-hooks/exhaustive-deps` would warn but CI treats warnings as non-fatal. Invariant 5.

### 5. The shared table's per-row `features` map can be emptied without either side failing — LOW (B) — [introduced]

`backend/tests/fixtures/addon_policy.json`. T3 replaces the `false` row's `features` with `{}` and the frontend parity test still passes (the backend one would too: it loops the same map). The `toBe(9)` / `len == 9` detector pins rows, not the feature expectations inside each row, so a row can silently stop checking features on both sides at once. Only matters if someone edits the table; declaring the feature names once (e.g. assert each row's `features` keys equal `["editor", "transcription_cloud"]`) would close it.
