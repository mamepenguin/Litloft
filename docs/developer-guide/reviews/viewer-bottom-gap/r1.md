## Author notes checked

**(a) flex host.** Confirmed in part. A `flex flex-col gap-4` host breaks two
pseudo-fullscreen cases (M9b). In the mobile-inspector-sheet fixture it breaks
nothing at the current `TRAVEL_PX` (M9 live): a flex host also drops the
player's bottom margin, so travel is 72 there too. So the sticky travel is not
evidence against flex; the pinned-frame slot is. No action needed: the block
host is correct and the parity tests pin the class (M7).

**(b) travel 88 → 72.** True consequence, not a masked regression. Sticky is
constrained by the player's margin box; `space-y-4` gave the player a 16px
bottom margin (the fixture's `below` box always follows it), `[&>*+*]:mt-4`
puts the 16px on `below` instead, which does not constrain the sticky box. M8
reproduces exactly 88 with the old class, i.e. the difference is the 16px
margin and nothing else. The player is now pulled up 16px less at the end of
the scroll; `halfSnapUnderPlayer` stays `null` at both edges (assertions still
pass).

**(c) what counts as content.** Measured the real `MediaCanvas` in jsdom
(temporary probe, removed) for PDF desktop, EPUB phone, PDF phone: host
children are the player and the summaries box only, no text nodes; on a phone
the summaries box is `:empty` (heavySummaries is `null`). React emits no
whitespace text nodes between JSX children and does not create DOM for `""`,
`false`, `null`. `FileDescription` returns `null` without a description;
`ActiveSummaryHost` returns `null` without a summary; the intelligence
`DetailedSummarySection` returns `null` while loading / unsupported / no
status, and real UI otherwise (so padding appears exactly when a visible
section does, which is invariant 2). A `data-occupied="false"` companion is
non-empty yet `display:none`, so after a bled viewer it would keep 16px
(against invariant 4), but a companion needs `playerKind(file) !== null`, which
PDF/EPUB are not, so it is unreachable (finding 4, B).

## Touch points the diff reaches that are not in the list

- **The sticky player's travel on a phone, for every framed media kind.**
  Removing the player's bottom margin changes how far a sticky player is
  pulled up at the end of the scroll (88 → 72 at 667x375). Not in the list
  ("Not touched: … the resting strip"), but the one real behaviour change
  outside documents. It is an improvement and already held by `TRAVEL_PX`.
- **`.media-detail-player-aside`** (the `loft-metadata` slot, video/loft only):
  now takes `mt-4` itself instead of the player's `mb-4`. Same 16px; when it is
  `empty:hidden` it adds nothing (as before).
- Not reached: `FileDetailCanvas` hosts (no `p-4`, no host spacing class,
  `MediaPlayerBlock` there never gets `bleed`), the other e2e-components
  arrangements using `.media-detail-host` (no `data-bleed`).
- `[&>*+*]` vs a child's own `margin-top`: no later child of the real host sets
  one (`.reading-measure`, `.media-detail-below`, the summaries box, the aside
  carry none). The only host-child margin-top rule is the bleed's `-1rem`,
  which is on the first child and is unlayered, so it would win anyway. Note
  the arbitrary variant lives in `@layer utilities` after plain utilities, so a
  future child given `mt-*` as a utility would be silently overridden; an
  unlayered rule would win. No instance today.

## Findings

### 1. [introduced] Invariant 1's phone half is not held by any test (M13 live) — A candidate

Invariant 1 says a bled viewer with nothing below ends at the canvas bottom
"on a phone, where the resting strip begins" — the case the spec measured on a
Pixel 5. `document-bleed.spec.ts` has `canvas-bleed-alone` (desktop) and
`canvas-bleed-phone` (with `below`), but no phone arrangement with nothing
below. M13 (keep 16px padding under `[data-sheet-snap]` only) passes all five
tests. Remedy: one arrangement `canvas-bleed-phone-alone` (`phone`, `below=false`)
asserting `host.bottom === viewer.bottom`, or parametrise the alone test over
`phone`.

### 2. [pre-existing] The real `MediaCanvas` trailing boxes are not held empty (M12 live) — B

Invariant 1 now depends on every host child after a bled viewer being absent
or `:empty` (+ `empty:hidden`). The component fixture restates its own trailing
children (`<div className="empty:hidden" />`) instead of rendering
`MediaCanvas`'s, so removing `empty:hidden` from the real summaries box (M12)
passes everything, and on a desktop PDF without summaries the page would show
a bordered, padded strip under the viewer. Same at the parent commit (the
class was already untested), hence pre-existing. Cheap hold if wanted: a jsdom
row in `MediaShell.test.tsx` "document viewers bleed…" asserting that, with no
summary/description, every host child after `.media-detail-player` matches
`:empty` (jsdom evaluates `:empty`).

### 3. [introduced] The fixture's "content follows" child does not look like the real one (M15 live) — B

In the real canvas the section that follows a bled viewer and has content is
the summaries box, which always carries `empty:hidden`; in the fixture it is a
bare `<p>`. So a restore rule that excluded `empty:hidden` boxes (M15) passes
the suite while, in the app, a PDF with a detailed summary would lose the 16px
under it (invariant 2). Remedy: make the fixture's `below` a
`<div className="empty:hidden"><p data-testid="below">…</p></div>` (or the real
summaries class list), so the test's content-bearing child has the shape the
predicate must accept.

### 4. [introduced] `:not(:empty)` counts a `display:none` box with children as content — B, unreachable today

`.media-detail-below[data-occupied="false"]` is `display:none` but has
children, so after a bled viewer it would restore the 16px padding (against
invariant 4). Unreachable: `companion` is non-null only when
`playerKind(file) !== null`, and PDF/EPUB have no player kind. Recorded so a
future bled viewer with a companion is not surprised; no action.
