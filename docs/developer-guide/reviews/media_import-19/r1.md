## Findings

### 1. [introduced] The "Enter the IME still owns" tests do not isolate the two signals they name

Files: `frontend/Composer.test.tsx` and `frontend/ImportFromUrl.test.tsx`, test "does not import on an Enter the IME still owns".

Both fixtures (`renderWithConvertedUrl` / `openWithConvertedUrl`) fire `compositionEnd` on the real `Date.now` and, with no spy, the two keydowns follow within milliseconds, i.e. inside the grace window. So whichever of `isComposing: true` / `keyCode: 229` the guard fails to recognise is still swallowed by the grace branch (the first unrecognised Enter consumes the window, but the other one is recognised by its own signal).

Mutation evidence (core `frontend/src/lib/ime.ts`, run against both addon test files):
- IM1 `if (native.isComposing || native.keyCode === IME_KEY_CODE)` -> `if (native.isComposing)`: want=kill, got=live (Composer 15/15, ImportFromUrl 24/24).
- IM2 -> `if (native.keyCode === IME_KEY_CODE)`: want=kill, got=live.
- Control: Composer fixture variant with `Date.now` spied and advanced to `+COMPOSITION_GRACE_MS` before the keydowns: passes with the real guard (15/15), fails under IM1 (1 failed). So the fixture, not the guard, is why IM1/IM2 survive.

Invariant: none broken in the product code. Invariants 1 and 3 name the `isComposing` / 229 Enter per field; at field level those are held only through "the guard is called" (C1/D1 kill) and core `ime.test.ts` holds the signals. The test name claims more than it checks. Bucket B unless the supervisor wants these tests to hold the signals, in which case the fixture should move `Date.now` past the window (or skip `compositionEnd`) before the keydowns.

### 2. [pre-existing] Composer: a subscription URL submitted with Enter before the 400 ms classification finishes is imported as a single loft

`Composer.handleSubmit` reads `kind` from state, which is set by a 400 ms debounced `resolveSubscriptionUrl`. Reproduction (temporary test): resolve mocked to `{kind: "channel"}`, change the input to a channel URL, keyDown Enter immediately -> `createLoft` 1, `createSubscription` 0. Identical at d873450 and with 03df847's `Composer.tsx` swapped in (`createLoft 1, createSubscription 0` both). The dialog avoids this by resolving at submit. Not made reachable by this PR (the PR only removes the confirming Enter as a trigger). Invariant: none of R-0.

### 3. [pre-existing] Invariant 5's "typing resets needsSubscription" is held by no test

D8 (drop `setNeedsSubscription(false)` from the dialog field's onChange): want=kill, got=live at d873450 (24/24) and at 03df847 with its own dialog and test file (24/24). The PR did not touch onChange, so nothing is broken; but R-0 names this as unchanged behaviour and no test would notice if it changed. Related survivors of the same kind: C6/D7 (any non-Enter key submits) live at both SHAs.

## Is anything missing from R-0

Two candidates, both currently holding:
- The dialog: an Escape that ends a composition (Safari-style, within the window) or that the IME still owns does not close the dialog (P1/P2). This is ShortcutsProvider's guard, not this PR's, but it is the user path named in the brief and R-0 is silent on it.
- Composer: repeated Enter while an import is pending sends once (C7 live; invariant 4 covers only the dialog).
