## 1. The unlink covers the first `copy2` only — the thumbnail `copy2` still strands a full orphan, and the collision the commit says it fixed comes straight back

`copy_file` calls `shutil.copy2` **twice**. The commit wraps the first one
(`fileops.py:264-275`). The second — the thumbnail copy at `fileops.py:307` —
is still outside every `try` in the function:

```python
            new_thumb.parent.mkdir(parents=True, exist_ok=True)
            shutil.copy2(str(old_thumb), str(new_thumb))
```

By the time it runs, `new_full` holds a **complete copy of the source file** and
no DB row exists yet (`db.add(new_file)` is further down). If that call raises,
the exception leaves the function with nothing unlinked. `batch_copy` catches it,
rolls back, and carries on to the next id — which is exactly the state the commit
message says is now impossible ("the write is wrapped now, so a failed copy leaves
nothing behind").

Observed. Probe (added as `backend/tests/test_probe_r3.py`, removed afterwards):
two files both named `a.mp4`, the first seeded **with** a thumbnail via
`_seed_with_thumbnail`, batch-copied into `dest`; `shutil.copy2` is failed on its
**second** call (ENOSPC) so the file body lands and the thumbnail does not.

```
STATUS 200 {'copied': 1, 'errors': [{'id': 'RWa8Jao9Tui9', 'error': '[Errno 28] No space left on device'}]}
DEST   ['a.mp4', 'a_copy.mp4']
DBROWS [('dest/a_copy.mp4', 'PausGjD8so7k')]
```

`dest/a.mp4` is a real, full file that no `File` row points at. The file that
did copy was suffixed around it — `a_copy.mp4` — which is the same symptom as the
zero-byte shell, and worse in one respect: the shell was empty and obvious,
whereas this orphan is byte-identical to a legitimate copy, so the next drive scan
indexes it as a genuine second file and the user sees `a.mp4` and `a_copy.mp4`
with no way to tell which one the batch meant.

Reachable states: ENOSPC on `data/` (thumbnails live under `DATA_DIR`, frequently
a different filesystem from the drive), EACCES/EROFS on `THUMBNAILS_DIR`, or the
plain TOCTOU between `old_thumb.exists()` and the `copy2` two lines later (a
concurrent thumbnail regeneration or cleanup → `FileNotFoundError`). The same hole
is reachable through `POST /api/files/{file_id}/copy`, which has no loop to mop up:
the request 500s and `dest/a.mp4` is left on disk.

No test in the commit covers it — the new `test_a_failed_copy_leaves_no_file_behind`
seeds with `_seed` (no `thumbnail_path`), so the second `copy2` never runs and the
failure it injects can only ever be the wrapped one.

The fix is to put the whole span from the exclusive create to `db.commit()` under
one cleanup, not just the first write.

## 5. The new ghost test pins the rollback and nothing else — destroying the Missing record outright passes all 2137 backend tests

`test_a_failure_does_not_carry_a_ghost_into_the_next_commit` is the only test in
the repository that puts a Missing `File` at a copy destination. Its docstring
names the mechanism it is standing on:

> ``resolve_db_path_conflict`` retires a Missing record's ``file_path`` and
> flushes it before anything touches the filesystem … an unrelated file failing
> strands the Missing record's history under a placeholder nobody points at.

But every assertion it makes is taken **after a rollback**, on the path where the
copy failed. The retirement itself — what happens to that record when the copy
*succeeds* — is asserted nowhere, and it turns out to be held by nothing at all.

Mutation, `want=kill`: `fileops.py:198`, inside `resolve_db_path_conflict`,
`conflict.file_path = f"__missing_{conflict.id}_{new_rel}"` → `db.delete(conflict)`
(diff confirmed: 1 insertion, 1 deletion).

```
docker run … litloft-r3 pytest tests/ -q --no-cov
   →  2137 passed, 4 skipped  (209s)
```

**Survives the entire backend suite**, including the new test — because the only
file that meets a ghost in that test is the one that fails, and its `db.rollback()`
undoes the delete just as thoroughly as it undoes the retirement.

The behaviour it lets through is a direct contradiction of
`design-decisions.md`: *"Treat the DB not as an FS cache, but as an independent
source of truth that holds data which cannot be regenerated from the filesystem
(watch history, comments, tags, transcripts, embeddings)"* and *"Missing files
are not auto-purged. They are kept indefinitely until the user explicitly deletes
them."* The reachable sequence needs no error at all:

1. `dest/a.mp4` goes missing from disk; the scanner sets `missing_since` and the
   row keeps its watch history, tags and comments.
2. The user copies another `a.mp4` into `dest`. `_resolve_copy_filename` finds
   nothing on disk at that path, so the copy takes the name.
3. The row's history is silently gone, cascaded through `WatchHistory` and the
   rest — with no user action, no event, and nothing in the Missing view to
   notice its absence.

One assertion on the success path closes it. Probe
(`backend/tests/test_probe_r3.py`, removed afterwards): seed a Missing `File` at
`dest/a.mp4` with a `WatchHistory` row, batch-copy one real `a.mp4` into `dest`
with no failure injected, then

```python
        kept = db.get(File, ghost_id)
        assert kept is not None, "the Missing record was destroyed by the copy"
        assert kept.file_path == f"__missing_{ghost_id}_dest/a.mp4"
        assert kept.missing_since is not None
        assert db.query(WatchHistory).filter(WatchHistory.file_id == ghost_id).count() == 1
```

| | result |
|---|---|
| `db.delete(conflict)` | `AssertionError: the Missing record was destroyed by the copy` — killed |
| as shipped | `1 passed` — no false positive |

The existing test already builds this ghost; it needs a second, non-failing id
in the batch that lands on it, or a sibling case.
