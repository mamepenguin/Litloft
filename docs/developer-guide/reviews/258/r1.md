## 2. `POST /files/batch/copy` *does* raise per file, so a half-done copy is silent and re-pasteable

The fix's stated premise is that both endpoints answer 200 with a count and only
raise for the request itself. That is true of `batch_move` and false of
`batch_copy`.

`backend/app/routers/files.py`, `batch_move` (lines 462-476) has two handlers
inside the loop:

```python
            except HTTPException as e:
                db.rollback(); errors.append(...)
            except Exception as e:
                db.rollback(); errors.append(...)
```

`batch_copy` (lines 598-605) has one:

```python
        except HTTPException as e:
            errors.append({"id": file_id, "error": e.detail})
```

`fileops.copy_file` reaches the filesystem outside any `try`:
`target_dir.mkdir(parents=True, exist_ok=True)` (fileops.py:242), the
`os.open(..., O_EXCL)` (only `FileExistsError` is converted, :260-263) and
`shutil.copy2(...)` (:264). Only the later DB section is wrapped and re-raised
as `HTTPException(500)` (:303-319). So `ENOSPC`, `EACCES`, `EIO`, a read-only
destination drive, or the source vanishing mid-copy raises a bare `OSError`
out of the loop, and the whole request becomes a 500 — **after** earlier files
have been copied and committed one at a time (`db.commit()` per file, :309).

Frontend consequence, and it is the part this PR owns. `fetchJSON` throws on
any non-2xx (`api.ts:8-10`), so `batchCopy` rejects, `paste` rejects before
reaching either branch, and in `FolderBrowser.handlePaste` the rejection lands
in the empty `catch {}` (FolderBrowser.tsx:307-308). Therefore:

- no toast — `result.failed` is never computed;
- **no refresh** — `refresh()` sits after the `await` inside the same `try`, and
  `router.refresh()` after the `await` in `paste`, so both are skipped;
- the clipboard is kept.

The user sees a Paste that did nothing. Files *have* arrived; they are not on
screen. Pressing **Paste here** again copies every id a second time, and the
ones that landed become `name_copy`, `name_copy_2`. That is precisely the
duplicate the commit says cannot happen any more.

Reproduce without Docker by reading it, or with: two files on the clipboard,
target folder on a full or read-only volume, first file small enough to fit.
`copied` never reaches the client.

`batch_move`'s broad handler is the shape `batch_copy` needs; alternatively the
frontend must treat a rejected paste as "unknown, possibly partial" rather than
as "nothing happened".

This matters beyond the code: hako's 2026-09-13 entry shows the clearing rule
was chosen on the stated measurement "`batch/copy` も `batch/move` も、ファイル
単位の失敗では例外を投げません" — both endpoints, no per-file exception. That is
half right. `batch_move` was measured correctly; `batch_copy` was not, and the
decision was taken on it.

## 6. One of the two failure paths got a message; the other is still an empty `catch {}`

request-failure path exactly as it was:

```tsx

      await clipboard.paste(driveName, folderPath ?? "");
      refresh();

    } finally {
```
(FolderBrowser.tsx:304-311)

`fetchJSON` throws on every non-2xx (`api.ts:8-10`), so the whole class of
request-level refusals produces no toast, no refresh, and no change to the
banner — a Paste that visibly does nothing at all, which is the state the
commit message calls harmful.

Concrete inputs that reach it, without needing the backend bug in finding 2:

- The clipboard is in `sessionStorage` and survives a reload, so it outlives
  the `access_token` cookie. Copy in drive A, come back later, paste: the
  session is no longer unlocked for the target drive and
  `_check_target_drive_access` → `check_drive_access` raises **404**
  (`files.py:350-352`; deliberately 404 rather than 403). The whole request is
  refused before the loop, `copied`/`moved` never exist, nothing is said.
- `docker compose up -d --build` is the documented upgrade path; a paste during
  the restart is a fetch rejection. Same silence.
- `PUT /files/batch/move` with a `target_folder_path` the schema rejects → 422.
  Same silence.

`.claude/rules/review-workflow.md`: "Adding a reporting path means counting the
silent ones. A change that introduced a toast wired it into one of three failure
paths and left two `catch { /* non-critical */ }` in place." This is that shape
with two paths rather than three, and the remaining one is not even commented.

The fixture blesses it: "keeps the clipboard when the request itself fails"
asserts the clipboard survives and asserts nothing about what the user is told —
and `mockError` is in scope, already asserted on in the rows above it.

Reporting a rejection needs a second message key, not a reuse of
`clipboard.pasteFailed`: `result.failed` is unknown in this path, and the honest
statement is "the paste did not happen", not a count.
