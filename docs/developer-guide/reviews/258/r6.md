## 1. The copy and its source now share one `thumbnail_path` string, and purging the copy blanks the picture of the row that survives

`copy_file` used to set `new_file.thumbnail_path` only on the branch that had just
written a JPEG. `6a04f324` lifted that assignment one level out, so it now runs
whenever `old_thumb.exists()` — including the branch that deliberately writes
nothing because source and destination name the same file:

```python
            if old_thumb.exists():
                if not (new_thumb.exists() and old_thumb.samefile(new_thumb)):
                    new_thumb.parent.mkdir(parents=True, exist_ok=True)
                    shutil.copy2(str(old_thumb), str(new_thumb))
                    copied_thumb = new_thumb
                new_file.thumbnail_path = new_thumb_rel      # <- now also on the samefile path
```

In the case the comment above it names — an image that was moved out of a folder
and still points at the thumbnail it left there — `new_thumb_rel` is character-for-
character `source.thumbnail_path`. Two rows now hold the same pointer, and
`physical_delete` unlinks through the pointer without asking whether anybody else
is holding it (`fileops.py:674-678`).

### Who reaches it and how

1. Have an image (or PDF — anything whose `file_type` is not `"video"`, because
   `_move_thumbnail` is gated on video at all three call sites) at `one/a.png`.
   Its thumbnail is `<drive>/one/a.jpg`.
2. Move it to `two/`. The row is now `two/a.png` and still points at
   `<drive>/one/a.jpg`.
3. Copy it back into `one/`. `_resolve_copy_filename` finds `one/a.png` free, so
   the copy keeps the name, and its slot is `<drive>/one/a.jpg` — the source's.
4. Change your mind: delete the copy, then empty the trash.
5. **The original at `two/a.png` now renders the grey placeholder.** Its
   `thumbnail_path` still names `<drive>/one/a.jpg`; the JPEG is gone.

### Reproduction

`backend/tests/test_probe_r6.py`, added and then removed (tree restored with
`git reset --hard HEAD`; `git status` clean afterwards):


`get_thumbnail` (`routers/files.py:1194-1203`) falls through to
`PLACEHOLDER_THUMBNAIL` when the pointed-at file is gone, so the user sees a grey
tile rather than an error.

The next full scan repairs it (`scanner.py:440-443` regenerates when the stored
thumbnail does not exist), so the damage is bounded — but the picture is gone
until then, and on a drive that is scanned on a timer that is not "immediately".

Note what this is *not*: the hard-link case the commit's own new test exercises is
harmless, because unlinking one of two names leaves the other. The damage needs
the two pointers to be the **same string**, which is exactly the case
`old_thumb.samefile(new_thumb)` is reached by most often.

### Purge is not the only consumer that assumes one row per JPEG

- `scanner._relocate_thumbnail` (`scanner.py:170-198`) — **renames** it. On the next

  elsewhere, and renames the shared JPEG out from under the copy; whichever row the scan
  reaches second is regenerated, so the outcome depends on directory iteration order.
- `_move_thumbnail` (`fileops.py:100-108`) — renames it too, but only for
  `file_type == "video"`, which the shared state cannot reach.

## 4. The new cleanup unlinks a JPEG the request did not create, so a failed paste permanently destroys a Missing row's picture

```python

            try:
                copied_thumb.unlink()
```

`copied_thumb` is the *destination slot*, not a file this request brought into
existence. Three lines earlier, `new_thumb.exists()` was evaluated and may have been
**True** — the slot already held somebody else's JPEG, `copy2` overwrote it, and the
cleanup now removes it outright.

The commit's own new test states the outcome as the desired one:

```python

        assert kept.thumbnail_path == ghost_thumb_rel

```

So after a failed paste the Missing row is restored by the rollback **with its pointer
intact and its bytes gone**: `get_thumbnail` serves `PLACEHOLDER_THUMBNAIL`, and nothing
regenerates it, because regeneration needs the file on disk and this row is Missing
precisely because it is not. `.claude/rules/design-decisions.md` — *"Keep thumbnails for
missing files (they are reused on recovery)"* — is the rule this crosses.

## 5. The narrowed comparison is not where spelling breaks — the row lookup one line above it is, and round 4's defect is fully reachable through that door

The brief asks whether `conflict.thumbnail_path == path_thumbnail_rel(...)` can fail the
match because two spellings name one file. **It cannot**, and the reason is worth stating
precisely, because it also says where the real hole is.

For the comparison to be evaluated at all, this must first have matched:

```python
    conflict = (
        db.query(File)
        .filter(File.drive == drive, File.file_path == new_rel)
        .first()
    )
```

SQLite's default collation is BINARY, so that is a **byte-exact** comparison. And every
producer of `thumbnail_path` derives it from the same string as `file_path`, in the same
call: the scanner NFC-normalises `relative_path`, `folder_path` and the stem together
(`scanner.py:286-301`); `copy_file` builds `new_rel` and `new_thumb_rel` from one
`target_folder`; `move_file`, `rename_file` and `upload.py:226` do the same. So whenever
the row is found, its pointer is spelled the way `path_thumbnail_rel` spells it. (I looked
for a producer that spells them differently and found only the Markdown projection, which
is the case the narrowing exists for.)

**The hole is one line earlier.** A folder spelled in another case or normalisation
reaches the same directory on the deployment mount but not the same row, so the
retirement never runs at all — and everything round 4 added is bypassed.

### The mount folds; measured here, not quoted

```
$ docker run --rm -v <scratch>/foldtest:/m litloft-test-r6 python -c \
    "import os; print(os.path.exists('/m/DEST/a.jpg'), os.path.samefile('/m/dest/a.jpg','/m/DEST/a.jpg'))"
True True
```

`/m/dest/a.jpg` and `/m/DEST/a.jpg` are one file inside the container. This is the shape
every Litloft drive and `data/thumbnails` has on a macOS host.

### Reproduction

Probe (created, run, deleted). A live `one/a.mp4`, a Missing row at `dest/a.mp4` owning
`<drive>/dest/a.jpg`, then `POST /api/files/batch/copy {"target_folder_path": "DEST"}`.
The container FS is case-sensitive, so the folding of the *thumbnail slot* is staged with
`os.link` — one inode, two spellings, which is exactly what a folding mount presents:

```
CASE copy                200 copied=1 errors=[]
CASE ghost.file_path=    dest/a.mp4                      <- never retired
CASE ghost.thumbnail_path= test-drive/dest/a.jpg          <- still points at the taken slot
CASE ghost thumb bytes=  b'\xff\xd8\xff\xe0SRC-PICTURE'   <- the arriving file's picture
CASE ghost thumb via API= b'\xff\xd8\xff\xe0SRC-PICTURE'
CASE rows= [('DEST/a.mp4', 'test-drive/DEST/a.jpg'),
            ('dest/a.mp4', 'test-drive/dest/a.jpg'),      <- two rows, one physical file
            ('one/a.mp4',  'test-drive/one/a.jpg')]
```

Both halves of round 4's defect are back: the Missing view shows the picture of the file
that took its place, and on a real folding mount purging that row unlinks the one JPEG the
live copy is also using (with the hard link staged here, the second name survives; with
folding there is only one name). On top of it, the copy commits a **second row for one
physical file**, which the next scan will reconcile by marking one of them Missing.

`_resolve_copy_filename` does not save this: the ghost's file is absent from disk (that is
what Missing means), so the collision check passes and the copy keeps the original name.

**Label: behaviour defect a user can hit** — narrow, and **pre-existing**: it is not
introduced by `6a04f324`, and round 4 did not cover it either. I report it because the
brief asked exactly this question, and because the answer is "the comparison you added is
safe, the lookup above it is not". The fix is the same shape as the one the commit already
applied to `copy2`: compare paths the way the filesystem does. Since the lookup is SQL,
that means normalising `target_folder` at the boundary — `validate_path_safe` is the
asymmetry (`validate_filename`, right below it, already NFC-normalises), and case is a
mount property that only `os.path.samefile` on the resolved directory can settle.

### B2, and the directory cleanup generally

Dropping `_cleanup_empty_parents` from the new cleanup leaves `56 passed`. Not inert — a
fixture can list `data/thumbnails/<drive>/<folder>` after a failed copy — but the only
observable difference is an empty directory in a cache, so I do not call it a finding.

On the two things the brief asked about that line:

- **What it can remove that this request did not create**: it walks up from the
  destination's parent and removes every directory that is empty, up to
  `THUMBNAILS_DIR`. If the request created none of them (the folder's cache directory
  already existed and held only the JPEG this cleanup just removed), it removes them
  anyway. Nothing points at a directory, and every writer does
  `mkdir(parents=True, exist_ok=True)`, so the only cost is the race: a concurrent copy
  between its `mkdir` and its `copy2` loses the directory and fails with
  `FileNotFoundError`. That race already exists identically in `physical_delete`,
  `_move_thumbnail` and `scanner._relocate_thumbnail`; this line adds a fourth site rather
  than a new class. **Neither.**
- **What the shared `except OSError` skips**: if `copied_thumb.unlink()` raises, the
  directory cleanup does not run. That is the harmless ordering — an unlink that failed
  leaves the directory non-empty, so there is nothing to clean. The reverse (cleanup
  raising and skipping the unlink) cannot happen. **Neither.**

### `old_thumb.samefile(new_thumb)` raising (perspective 4)

`samefile` is `os.stat` on both sides and can raise `FileNotFoundError` — an `OSError` —
inside the broad `try`, which unlinks the destination and fails the copy with 500. Two
ways in:

- **TOCTOU**: `new_thumb.exists()` and `samefile` are separate syscalls; a thumbnail
  deleted between them fails the paste. C3 shows the suite notices the *always*-raising
  version, nothing could notice the race. Narrow enough that I do not call it a finding,
  and the same window exists on `old_thumb.exists()` → `copy2`.
- **Symlinks**: `Path.exists()` follows links, so a **broken** symlink at `new_thumb`
  reads as absent and `copy2` then writes *through* it, landing wherever it points —
  outside `THUMBNAILS_DIR` if it points outside. Nothing in `backend/app/` creates a
  symlink under `data/thumbnails`, so I could not reach it from any API call. **Neither**,
  recorded for the record.

## The span question, answered

> Does the span's contract — "whatever fails in between, the destination goes back to not
> existing" — now hold for everything the span creates?

**No, and in two different ways.**

1. **A write that is still not undone**: `project_markdown_thumbnail`'s JPEG under
   `<drive>/.markdown/`. Measured, finding 3. Round 5 counted the writes as two; there are
   three, and the third is the one whose name contains an id that ceases to exist on
   rollback, so nothing can ever reclaim it.
2. **A write that is undone too far**: the thumbnail slot is undone by *deleting* it, but
   the slot did not always start empty. For an occupied slot, "back to not existing" is
   the wrong target — "back to what it was" is — and the difference destroys the Missing
   row's picture. Measured, finding 4.

The directories are now handled (`_cleanup_empty_parents`), which was the other half of
r5's seam. The exclusive-create file is handled. `resolve_db_path_conflict`'s DB mutation
is unwound by the rollback on all three exits, including the new `thumbnail_path = None`
(A1/A2 both behave correctly on the failure path — the ghost's pointer comes back).

So the pattern r5 flagged has not ended: round 5 widened the cleanup to match round 3's
widened span, and in doing so (a) missed the third write and (b) made the second write's
undo destructive. That is the fifth consecutive round in which the sharpest finding lives
inside the previous round's fix.
