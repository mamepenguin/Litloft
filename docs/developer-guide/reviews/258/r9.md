## 5. [pre-existing] After a `move_file` of a **video** onto a Missing record's path, the moved file and the Missing record both name the same JPEG, and purging the record blanks the live file's thumbnail

## The question, answered

> With the prediction gone, is there any remaining path where a thumbnail outcome
> changes a DB row that is not the row whose thumbnail it is — or where a DB row's
> state is decided by something other than what was actually written?

**In `copy_file`: no.** `_rename_thumbnail_owner` is the only place a foreign row is
touched, it runs only in the `else:` of the write, and both of its terms are held —
the write must have happened (the `else:` mutation dies) and the retired row must
name exactly the slot that was written (the slot-identity mutation dies). I shot
both and both died.

**Three residues, all outside `copy_file` and all pre-existing:**

1. `move_file` / `rename_file` for a video: `_move_thumbnail` overwrites the retired
   record's JPEG and no row is updated to say so, so the record's pointer silently
   comes to mean the live file's picture (finding 5). Nothing in `copy_file` does
   this any more.
2. The swallowed second commit can leave the copy's own pointer NULL although the
   JPEG *was* written — a row's state decided by something other than the write, in
   the safe direction. It self-heals, and unlike r8 Finding 1a it really does:
   `scanner.py:439-441` repairs when `thumbnail_path != expected_thumb` **or** the
   file is missing, and a NULL pointer satisfies the first disjunct, after which
   `_relocate_thumbnail` regenerates and sets it. r8's stuck shape was
   `pointer == expected and file exists`; this one is not that shape.
3. `fills_thumbnail_slot == False` via `samefile`: the copy takes no pointer even
   though the JPEG at its own slot is its picture. Deliberate, documented in the
   code, and held by `test_copying_a_moved_file_back_where_its_thumbnail_stayed`.
