## 1. `conflict.thumbnail_path = None` also wipes a Missing **Markdown** row's projection, which nothing takes over — the picture is lost from the Missing view and its JPEG leaks permanently

**Label: behaviour defect a user can hit.**

The new line's whole justification is the comment beside it:

> The thumbnail cache key is derived from drive + folder + stem just as the path is, so whatever takes this path takes that slot too.

True for video, image and PDF. **False for Markdown.** `project_markdown_thumbnail`
(`backend/app/services/markdown_images.py:391`) names the projection

```
{drive}/.markdown/{markdown_file.id}-{source_image.id}.jpg
```

— keyed by *row id*, not by path. `copy_file` already knows this; it is exactly why its
thumbnail block is gated on `not _is_markdown_file(source)` ("Markdown thumbnails are
projections owned by the note ID, so they must be regenerated below instead of copied to
the generic path-based cache"). `resolve_db_path_conflict` has no such gate, and it now
clears the pointer for **every** Missing row it retires.

Two consequences, both measured:

1. The retired row loses its picture in the Missing view although the incoming file took a
   *different* cache slot. Nothing was ever in conflict.
2. `physical_delete` (`fileops.py:648-652`) unlinks the thumbnail through
   `file.thumbnail_path`. With the pointer cleared, purging the ghost — "the one action it
   is kept for", per the commit message — no longer reclaims the JPEG. There is no
   orphan-thumbnail sweeper anywhere in `backend/app/` (checked; only `cleanup_orphan_tags`
   exists), so the file is permanent.

### Who reaches it and how

A `.md` note whose first image is a `loft://` picture gets a projection on scan. The note
disappears out of band (moved in Finder, an external sync) → the scanner marks it Missing
and keeps the projection, by design. The user then pastes / moves / renames a file onto
that same path.

**Three call sites, not one.** `resolve_db_path_conflict` is called from `copy_file`
(`fileops.py:262`), `rename_file` (`:366`) and `move_file` (`:444`). The upload path does
*not* call it — `upload.py:273` revives the existing row instead — so it is three, not the
four the brief expected. The new line sits in the shared `else:` branch, so all three now
carry the side effect; only `copy_file` was under discussion.

### Reproduction

Probe file `backend/tests/test_zz_probe.py` (created, run, deleted; tree restored). It
seeds a live `one/a.md`, a Missing ghost row at `dest/a.md` carrying
`thumbnail_path = "{drive}/.markdown/{ghost_id}-abcdefghijkl.jpg"` with that JPEG on disk,
pastes the note into `dest/`, then purges the ghost.

```
PROBE before: ghost thumb -> 200 20 b'\xff\xd8\xff\xe0ghost-projection'
PROBE copy -> 200 {'copied': 1, 'errors': []}
PROBE after: ghost.file_path = __missing_ujVVLMqeJqPG_dest/a.md
PROBE after: ghost.thumbnail_path = None
PROBE after: projection on disk = True
PROBE after: ghost thumb -> 200 249 b'\xff\xd8\xff\xe0\x00\x10JFIF\x00\x01\x01\x00\x00\x01\x00\x01\x00\x00'   <- placeholder
PROBE purge -> 200 {'status': 'purged'}
PROBE after purge: projection on disk = True      <- leaked
```

The same thing through `PUT /api/files/{id}/move` — i.e. `move_file`, a caller nobody
looked at this round:

```
PROBE move -> 200
PROBE move: ghost.file_path = __missing_biz1rJOFonf0_dest/b.md
PROBE move: ghost.thumbnail_path = None
PROBE move: projection on disk = True
```

### How much of this the suite sees: one test, and it is a copy test

Mutation **M1** — delete the new line (`want=kill`):

```diff
@@ -202,7 +202,6 @@ def resolve_db_path_conflict(db: Session, new_rel: str, drive: str) -> None:
         # Leaving the pointer means the Missing row shows the new file's
         # picture, and purging the row — the one action it is kept for —
         # unlinks a thumbnail the live copy is using.
-        conflict.thumbnail_path = None
     db.flush()
```

Full suite: `1 failed, 2141 passed, 4 skipped` —
`test_copy.py::TestBatchCopy::test_a_copy_onto_a_missing_record_keeps_that_record`, and
nothing else. Killed as intended, but exactly one observer in 2146: neither `rename_file`
nor `move_file` has any test that notices the side effect the line just gave them.

### On the design rule

`.claude/rules/design-decisions.md`: *"Keep thumbnails for missing files (they are reused
on recovery)."* For a **retired** row, scanner recovery is already impossible — `file_path`
is `__missing_<id>_<path>`, which never matches a real path again, and the move-detection
index (`scanner.py:570-600`) keys on a match key this row cannot present. So clearing the
pointer costs nothing *on recovery*; what it costs is the Missing view's picture and the
purge-time unlink. For a path-derived slot that trade is right (the slot is gone anyway).
For Markdown it is pure loss.

The narrow condition is to clear only when the retired pointer **is** the slot being
taken — when `conflict.thumbnail_path` equals the path-derived expectation for `new_rel`.
That also removes any need to know which file types are path-derived.

## 2. A DB failure after the thumbnail copy restores the ghost row but not its thumbnail bytes — the Missing view then shows the new file's picture, which is the exact symptom this commit is titled after

**Label: behaviour defect a user can hit.** This is also the seam in the round-3 span; see
the closing section.

`copy_file` writes **two** files inside the broad `try`: the body at `new_full`
(`os.open` + `shutil.copy2`) and the thumbnail at `new_thumb` (`shutil.copy2`). The
cleanup unlinks **only** the body:

```python
    except Exception:
        try:
            new_full.unlink()
        except OSError:
            pass
        raise
```

`new_thumb` is untouched, as is any directory `new_thumb.parent.mkdir()` created. When the
destination slot already held a Missing row's thumbnail, that `copy2` **overwrote** it, and
the ORM rollback restores the ghost's `thumbnail_path` to a path whose bytes are now the
source file's picture.

### Who reaches it and how

The user pastes a video into a folder where a Missing row already holds that name — the
case the commit is about — and the commit's own third failure mode fires: a concurrent scan
holding the SQLite write lock, which is precisely what
`test_a_database_failure_leaves_no_file_behind` was added for. The paste reports an error,
the body is correctly removed from disk, and the Missing entry now shows the picture of the
file that failed to arrive.

### Reproduction

Missing ghost at `dest/a.mp4` with `{drive}/dest/a.jpg` = `GHOST-PICTURE`; live source
`one/a.mp4` with `{drive}/one/a.jpg` = `SOURCE-PICTURE`;
`fileops.remove_empty_folder_if_has_files` monkeypatched to raise `SQLAlchemyError`,
exactly as the commit's own new test does.

```
PROBE batch -> 200 {'copied': 0, 'errors': [{'id': 'dyPhl2yredkn',
    'error': 'Copy failed (DB error, filesystem reversed): database is locked'}]}
PROBE ghost.file_path      = dest/a.mp4                 <- correctly rolled back
PROBE ghost.thumbnail_path = 'test-drive/dest/a.jpg'    <- correctly rolled back
PROBE dest/a.mp4 on disk   = False                      <- correctly unlinked
PROBE bytes at ghost slot  = b'\xff\xd8\xff\xe0SOURCE-PICTURE'   <- NOT reversed
PROBE ghost thumb -> 200 b'\xff\xd8\xff\xe0SOURCE-PICTURE'
```

`GET /api/files/{ghost}/thumbnail` serves the source file's picture. The error string
handed to the user says "filesystem reversed"; for the thumbnail cache it is not.

Same shape with no ghost at all — the JPEG is simply orphaned for a file that does not
exist:

```
PROBE batch -> 200 {'copied': 0, 'errors': [... 'database is locked'}]}
PROBE dest/a.mp4 on disk = False
PROBE orphan jpg on disk = True
```

### Bounding the seam

I also shot the arm *before* the thumbnail copy — `fileops._is_markdown_file` monkeypatched
to raise `OSError`, which lands in the outer handler — and got
`PROBE orphan jpg on disk = False`. So the seam is exactly "anything that fails after
`shutil.copy2(old_thumb, new_thumb)` has succeeded", which is the whole inner DB block.
Recording whether the thumbnail was written and unlinking it in the outer handler closes it.

No test in the suite observes either the overwritten bytes or the orphan: the commit's own
`test_a_database_failure_leaves_no_file_behind` seeds sources with `_seed` (no thumbnail),
so its copy never reaches the thumbnail `copy2` at all.

## 5. `old_thumb != new_thumb` is a lexical `Path` comparison, and on the deployment filesystem two different strings are routinely the same file — the guard is narrower than the class of defect it names

**Label: behaviour defect a user can hit** — narrow: it needs a client that does not echo
back the API's own folder string. Stated either way below, as asked.

`Path.__ne__` compares the string parts. `shutil.copy2` compares with `os.path.samefile`.
Where those disagree, `SameFileError` is raised **inside** the broad `try`, the destination
is unlinked, and the copy fails with nothing copied — the failure the commit's own docstring
describes ("the copy did not happen, with nothing said").

Measured on this host, and then measured again *inside a container through a Docker bind
mount into it*, because that is the real deployment shape:

```
$ docker run --rm -v /private/tmp/.../cimount:/m litloft-test-r5 python -c '...'
container sees DEST/a.jpg: True
samefile: True
copy2 raised: SameFileError '/m/dest/a.jpg' and '/m/DEST/a.jpg' are the same file
```

and, separately, Unicode normalisation:

```
nfc==nfd: False 'ガイド' 'ガイド'
container sees NFD path: True
samefile: True
copy2 raised: SameFileError '/m/ガイド/a.jpg' and '/m/ガイド/a.jpg' are the same file
```

So both case-folding and NFC/NFD defeat `!=` while `copy2` still refuses.

**Reachability.** `dst_drive` cannot differ in case — `resolve_drive_path` requires exact
membership in `config.get_drive_names()`. The stem comes from the source's own filename. The
one component that reaches `new_thumb_rel` **unnormalised from the request body** is
`target_folder`: `validate_path_safe` (`fileops.py:193`) checks for a null byte, a leading
slash and `..`, and returns the string as given. Note the asymmetry with `validate_filename`
right below it, which *does* `unicodedata.normalize("NFC", ...)`. And `target_dir.mkdir(
parents=True, exist_ok=True)` will happily resolve `DEST` onto the existing `dest`. So
`POST /api/files/batch/copy {"target_folder_path": "DEST"}` (or an NFD folder name) against a
source whose thumbnail pointer is already stale in that folder — finding 3's journey —
produces `old_thumb = ".../dest/photo.jpg"`, `new_thumb = ".../DEST/photo.jpg"`, `!=` true,
`samefile` true, 500 and no copy.

**What I could not do:** reproduce it in the pytest container. Its `/tmp` is overlayfs —
case-sensitive and normalisation-preserving — so no fixture inside the test image can reach
it. I confirmed the two composing facts on the deployment filesystem instead (above), and I
confirmed by reading that nothing between the request body and `new_thumb_rel` normalises
`target_folder`. The Litloft frontend sends the path it received from the listing API, so
the UI does not reach this; an MCP client, a hand-written request, or a folder name typed on
macOS (which yields NFD) does.

The one-line form of the guard that closes the whole class is
`not (old_thumb.exists() and new_thumb.exists() and old_thumb.samefile(new_thumb))`, or
simply catching `shutil.SameFileError` around the copy and treating it as "already there".

## The round-3 span question, answered

> Does the span from the exclusive `os.open` to `db.commit()` actually close the gap, or do seams remain?

**One seam remains, and it is finding 2.** The span's contract, in its own comment, is
"whatever fails in between, the destination goes back to not existing". The handler
implements that for one of the two things the span creates. `shutil.copy2(old_thumb,
new_thumb)` writes a second file — sometimes over a file another row owns — and
`new_thumb.parent.mkdir(parents=True, exist_ok=True)` may create directories; neither is
undone. The observable consequence is not a stray byte on disk but a **wrong picture in the
Missing view**, i.e. the same class of defect the commit is named after, moved from the
success path to the error path.

Everything else I shot at the span held:

- The 409 is genuinely outside it and stays outside (M3 killed).
- The DB arm's rollback + reversal is genuinely inside it (M4 killed).
- Both of `batch_copy`'s rollbacks are held, each by its own parameter, with the failure at
  the front (M6, M7 killed).
- The arm before the thumbnail copy leaves nothing behind (probe: no orphan JPEG).
- The retirement performed *outside* the span by `resolve_db_path_conflict` is unwound
  correctly on all three exits I could reach — the HTTPException path, the OSError path and
  the SQLAlchemyError path — for both of the fields it now touches.

So the restructure did close the multi-handler gap it was for. What it did not do is widen
the *cleanup* to match the widened *span*: round 3 made one `try` cover two filesystem
writes and left the handler undoing one. Round 4 then added a third consumer of that second
write (the Missing row's slot), which is what turns a stray file into a visible wrong
picture. That is the same "a change of your own can move what out of scope means" shape, and
it is one more sample for the working read — round 5's sharpest finding *is* created by the
round before it, so I would not yet conclude the round-3 restructure ended the chain.
