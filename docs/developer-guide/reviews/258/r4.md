## 1. The DB arm of the new single cleanup is held by nothing — narrowing it to `except OSError` restores round 2's orphan and all 2139 tests stay green

The commit's whole claim is that one handler now spans the exclusive create to
`db.commit()`. Two of its three arms are tested (body `copy2`, thumbnail `copy2`);
the third — the `HTTPException(500)` the nested DB handler raises — is tested by
nothing, and it is the arm that only works because the outer `except` is broad.

Mutation, `want=kill`: `fileops.py:321` `except Exception:` → `except OSError:`
(diff confirmed: 1 insertion, 1 deletion). Both `copy2` failures are `OSError`,
so both existing tests keep passing; only the DB arm changes.

```
docker run --rm -v $PWD/backend/app:/app/app -v $PWD/backend/tests:/app/tests \
  litloft-r4 pytest tests/ -q --no-cov
   →  2139 passed, 4 skipped  (230s)
```

**Survives the entire backend suite.** What it lets through is precisely the state
round 3 was written to close, reached through the third door.

Probe (`backend/tests/test_probe_r4.py`, removed afterwards): two files both named
`a.mp4`, batch-copied into `dest`; `remove_empty_folder_if_has_files` raises
`SQLAlchemyError("database is locked")` on its first call — after the body is

| mutated (`except OSError`) | `copied: 1`, error `Copy failed (DB error, filesystem reversed): database is locked` | `['a.mp4', 'a_copy.mp4']` | `[('dest/a_copy.mp4', …)]` |

`dest/a.mp4` is a full, byte-identical copy that no row points at, the file that

## 2. The retired Missing record keeps `thumbnail_path` pointing at the slot the copy takes over — the ghost's thumbnail is overwritten, and purging the ghost deletes the live copy's

`resolve_db_path_conflict` retires the ghost's `file_path` and leaves every other
column alone. But a thumbnail path is derived from drive + folder + stem exactly
as a file path is (`scanner.py:127` `_expected_thumbnail_path`, and `copy_file`'s
own `f"{dst_drive}/{target_folder}/{new_stem}.jpg"`), so the copy that takes the
name also takes the **thumbnail cache slot**, with the retired row still pointing
into it. The new test asserts `file_path`, `missing_since` and `WatchHistory`,
and does not look at it.

Probe (`backend/tests/test_probe_r4.py`, removed afterwards), **success path, no
error injected**: a Missing `File` at `dest/a.mp4` carrying
`thumbnail_path = "test-drive/dest/a.jpg"` with its own bytes on disk; one real
`a.mp4`, seeded with a thumbnail, batch-copied into `dest`.

```
COPY thumbnail_path : test-drive/dest/a.jpg
GHOST thumbnail_path: test-drive/dest/a.jpg          ← two rows, one file
live thumb bytes    : b'\xff\xd8\xff\xe0fake-jpeg'   ← the source's; the ghost's is gone
PURGE: 200 {"status":"purged"}
LIVE THUMB EXISTS AFTER PURGE: False
```

Two distinct losses, neither needing an error:

1. **The copy overwrites the ghost's thumbnail.** `design-decisions.md`: *"Keep
   thumbnails for missing files (they are reused on recovery)."* A missing file's
   thumbnail cannot be regenerated — `_relocate_thumbnail` needs the source on
   disk and there is none — so the Missing view shows the *other* file's picture
   from then on. The retirement exists so the row's unrebuildable data survives;
   this is unrebuildable data that does not.
2. **Purging the ghost — the explicit user action the row is kept for — unlinks
   the live copy's thumbnail** (`physical_delete`, `fileops.py:641-645`, and
   `_cleanup_empty_parents` on its directory). The live row still points at the
   deleted path, so the grid shows a hole until a scan regenerates it, and the
   `files.purged` event names only the ghost.

Retiring `thumbnail_path` alongside `file_path` (or clearing it, since the bytes
are about to be overwritten regardless) closes both. The assertion that would have
caught it is one line in the test this commit already added:
`assert kept.thumbnail_path != copy_row.thumbnail_path`.

## 3. Move an image out of a folder, copy it back, and the copy fails outright — the thumbnail `copy2` is handed the same path for source and destination

The new test injects ENOSPC into the thumbnail `copy2`. There is a failure mode
of that same call that needs no injection at all, and the commit's rewrite of the
block did not touch it.

`_move_thumbnail` is called from `move_file` (`fileops.py:439`), `rename_file`
(`:360`) and the folder-rename path (`:1042`) behind `if file.file_type ==
"video" and file.thumbnail_path`. Images and PDFs have thumbnails too, so moving
one leaves its `thumbnail_path` pointing at the folder it came from. `copy_file`
then computes `new_thumb_rel` from the *destination*, and if the destination is
that old folder the two are the same file.

Probe (`backend/tests/test_probe_r4.py`, removed afterwards): an image
`dest/photo.png` with thumbnail `test-drive/dest/photo.jpg`; `PUT /move` into
`one`; then copy it back into `dest`.

```
AFTER MOVE file_path = one/photo.png | thumbnail_path = test-drive/dest/photo.jpg
BATCH COPY: 200 {'copied': 0, 'errors': [{'id': 'C_dmka7yGoah', 'error':
  "'…/data/thumbnails/test-drive/dest/photo.jpg' and
   '…/data/thumbnails/test-drive/dest/photo.jpg' are the same file"}]}
DEST: []
SINGLE COPY RAISED: SameFileError …
DEST: []
```

What the user sees: a copy that simply does not happen, for a file they can see,
into a folder they can see, with no explanation. `shutil.SameFileError` is a
`shutil.Error`, **not** an `OSError` — it reaches the outer arm only because that
arm is `except Exception`, which is the term finding 1 shows nothing holds.
Through `POST /api/files/{file_id}/copy` it is an unhandled exception and a bare
500.

Second, smaller: `batch_copy`'s `except Exception` arm puts `str(e)` straight
into the response body, so this failure hands the browser the container's
absolute thumbnail path (`/app/data/thumbnails/<drive>/<folder>/<stem>.jpg`).
Every other error in that list is an `HTTPException` detail written for a reader.

`if old_thumb.exists() and old_thumb != new_thumb:` closes the copy side. The
`file_type == "video"` gate on all three `_move_thumbnail` call sites is the
cause and is worth counting separately — it is the same shape as round 3's
finding, one call site fixed and the siblings left.
