## Finding 1 — a failed thumbnail publish permanently strands the ghost's JPEG and makes the copy display it

**The defect in one sentence.** `copy_file` retires the Missing record's
`thumbnail_path` to `NULL` *before* the copy runs, on the strength of a
prediction (`fills_thumbnail_slot`) that the fill will overwrite that JPEG —
but the fill happens after `db.commit()` and its `OSError` is swallowed, so when
it fails the ghost's pointer is durably gone, the ghost's JPEG is still on disk
with nothing that can ever reach it, and the copy's row now names that JPEG and
serves *the ghost's picture* as the copy's thumbnail.

This is the invariant this round exists to defend, broken in the direction the
round's own commit message names: **a thumbnail failure changed a DB row.** Not
the copy's row — the ghost's. The retirement is committed; the write it was
predicting is not.

**Who reaches it and how.** A user has a video at `dest/a.mp4` that went Missing
(the drive was unmounted during a scan). Its row is kept — that is the whole
point of Missing — and it still shows its picture in the Missing view. The user
pastes a different `one/a.mp4` into `dest`. The thumbnail cache directory is
full, or read-only, or the write races an ENOSPC: any `OSError` out of
`generating_file` / `copy2`. The paste reports success (correctly — that part of
round 7 works). Afterwards:

- the Missing row shows the placeholder, permanently;
- the pasted file shows **the Missing file's picture**, permanently, because
  the slot still holds the old JPEG and the new row was pointed at it before
  the write was attempted;
- purging the Missing row deletes nothing: `physical_delete` reaches a
  thumbnail only through `file.thumbnail_path`
  (`fileops.py:704-708`), which is now `NULL`. The JPEG is leaked for the life
  of the installation.

The last of those three is precisely the loss change (b) of this commit was
written to prevent ("the purge reaches the JPEG through this pointer and nothing
else ever will"). The fix closed the case where *nobody* writes the slot and
left open the case where somebody *tried and failed* to.

**Reproduction.** `backend/tests/test_r8_repro.py`, run against an unmodified
tree (no mutation — this is the shipped behaviour):


## Finding 2 — `move_file` and `rename_file` declare `takes_thumbnail_slot=True` for a pointer whose JPEG is not on disk, and then write nothing

**The defect in one sentence.** The two non-copy call sites compute

```python
takes_thumbnail_slot=file.file_type == "video" and bool(file.thumbnail_path)
```

but `_move_thumbnail` writes nothing at all when the JPEG the pointer names is
absent (`fileops.py:100-108`: `if old_thumb.exists():` gates the whole body), so
the caller says it takes the slot, takes nothing, and the ghost's pointer is
cleared anyway — the same permanent leak change (b) was written to close.

`copy_file`'s predicate is the sibling of this one **by role**, and it does test
existence:

```python
fills_thumbnail_slot = (
    old_thumb is not None
    and old_thumb.exists()          # ← move/rename have no counterpart
    and not (new_thumb.exists() and old_thumb.samefile(new_thumb))
)
```

Three call sites were changed; one of the three got the existence term.

**A second consequence at the same sites.** `file.thumbnail_path = new_thumb_rel`
runs unconditionally after `_move_thumbnail` (`fileops.py:424-425` for rename,
`fileops.py:504-511` for move), so when the JPEG was absent the moved row is
repointed at a slot that still holds *the ghost's* JPEG. The moved file then
displays the Missing file's picture.

**Who reaches it and how.** Any video row whose cached JPEG is gone while the
row still points at it. That is not exotic:

- The thumbnail cache under `data/thumbnails` is a cache — a user or an
  operator clearing it to reclaim space leaves every row pointing at nothing.
- It is also the state **this very commit now produces**: after Finding 1's
  failed publish, the copy's row names a JPEG that was never written. Moving
  that copy into a folder that holds a Missing record reaches Finding 2
  directly.

Then: user has `dest/a.mp4` Missing with its picture, moves `one/a.mp4` (a video
whose JPEG is absent) into `dest`. The Missing row loses its pointer, its JPEG
survives on disk with no handle, and the moved video shows the Missing file's
picture.

**Reproduction.** No mutation; shipped behaviour. `backend/tests/test_r8_repro.py`:

## The invariant, answered

> A thumbnail is a cache, not part of the transaction. A failed thumbnail
> publish must never affect the file's row.

**Direction A — does the row's success depend on the thumbnail? No.** Verified.
The fill sits after `db.commit()` and, critically, after the `except Exception:`
that unlinks `new_full` (`fileops.py:360-369` closes the reversal handler;
`371-379` is the fill). Nothing between them can re-enter it. Mutating the
swallow to a re-raise (M2) is killed by three tests, so the swallow is held. The
`except OSError:` is wide enough for everything `shutil.copy2` and
`atomic_write._atomic` document: `shutil.Error` and `shutil.SameFileError` are
both `OSError` subclasses, and `mkdir` / `mkstemp` / `chmod` / `os.replace` all
raise `OSError`. I found nothing non-`OSError` that either can raise here.

**Enumeration of the failure modes, and which side of the invariant each lands
on.** "the copy" = the new row and the drive file it names; "the ghost" = the
retired Missing row.

| how the thumbnail operation fails | the copy | the ghost |
|---|---|---|
| source JPEG absent at predicate time | ✅ predicate False, no pointer, no write (M4 holds it) | ✅ pointer kept |
| source JPEG vanishes between predicate and fill (a concurrent purge, a scan) | ✅ `FileNotFoundError` → `OSError` → swallowed; row keeps a pointer the scanner repairs *if the slot is empty* | ❌ pointer already NULL — **Finding 1** |
| destination cache directory cannot be created (`_atomic`'s `mkdir`) | ✅ swallowed | ❌ Finding 1 |
| ENOSPC part-way through the body of the JPEG | ✅ temp removed by `_atomic`'s `finally`; slot untouched (held by `test_a_thumbnail_that_fails_midway_leaves_nothing_in_the_cache`) | ❌ Finding 1 |
| `os.replace` refuses (EROFS, EXDEV) | ✅ temp removed, slot untouched | ❌ Finding 1 |
| `os.chmod` refuses | ✅ raised before the rename; same as above | ❌ Finding 1 |
| `shutil.SameFileError` | ✅ `OSError` subclass, swallowed. Unreachable in practice — the temp name is `mkstemp`-unique | ✅ |
| `old_thumb` is a dangling symlink | ✅ `exists()` False → predicate False | ✅ pointer kept |
| `old_thumb` is a symlink to a real JPEG | ✅ `copy2` follows it | ✅ |
| `old_thumb` is a directory | ✅ `IsADirectoryError` → swallowed | ❌ Finding 1 |
| the copy fails before `db.commit()` (body `copy2`, `os.open`, DB error) | ✅ fill never runs; it is after the `try` | ✅ retirement rolled back by `batch_copy`'s `db.rollback()` / session close |

**So: the invariant holds for the row the copy creates, on every path I could
reach. It does not hold for the other row the operation touches.** The
retirement of the Missing record's `thumbnail_path` is a DB write committed on
the strength of a filesystem write that has not happened yet, is not retried,
and whose failure is swallowed. That is Finding 1, and it is the same class of
bug as the one round 7 fixed, one row over.

**The second face — do the three call sites tell the truth about
`takes_thumbnail_slot`?**

| site | expression | truthful? |
|---|---|---|
| `copy_file` | `fills_thumbnail_slot` | truthful about *intent* at the moment it is computed, and the only site that checks the JPEG exists. Not truthful about *outcome*: the write it predicts happens ~80 lines and one commit later and can fail silently (Finding 1). |
| `move_file` | `file.file_type == "video" and bool(file.thumbnail_path)` | **no.** `_move_thumbnail` writes nothing when the JPEG the pointer names is gone; the caller still says True (Finding 2). Its own failure path (`old_thumb.rename` raising) is safe — the `try` rolls the retirement back. |
| `rename_file` | same expression | **no**, same untruth, and additionally untested (Finding 3). |

No site can say False and write anyway: the only other write into
`data/thumbnails` from these paths is `project_markdown_thumbnail`, which is
keyed by row id under `.markdown/` and never touches the path slot — provided
the guard in Finding 4 stays.

**Can two batch entries race on the predicate?** No path found. Entry *n+1*'s
`_resolve_copy_filename` runs after entry *n*'s file is on disk, so the second
entry is suffixed (`a_copy.mp4`) and computes a different slot
(`.../a_copy.jpg`). The only way two entries land on one slot is two different
extensions with one stem (`a.mp4` and `a.png`), which is the stem-collision item
already deferred.
