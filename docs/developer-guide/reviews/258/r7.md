## 1. The publish now happens after `db.commit()`, but it is still wrapped in the handler that deletes the destination — a failed publish commits the row and unlinks the file the row names

**Behaviour defect a user can hit.**

`copy_file` (`backend/app/services/fileops.py:275-372`) is shaped like this after
`598b3905`:

```python
try:                                    # outer — "owns" new_full
    shutil.copy2(old_full, new_full)
    new_file = File(...)
    with ExitStack() as pending_thumbnail:       # (S)
        ...
        staged_thumb = pending_thumbnail.enter_context(generating_file(new_thumb))
        shutil.copy2(old_thumb, staged_thumb)
        new_file.thumbnail_path = new_thumb_rel
        try:
            db.add(new_file); ...; db.commit()
        except Exception as exc:
            db.rollback(); raise HTTPException(500, ...)
    # (S) exits HERE — os.chmod + os.replace(temporary, new_thumb)
except Exception:
    new_full.unlink()                   # <- destructive
    ...
    raise
```

That is the whole point of the round-6 fix: the publish is moved *after* the
commit. But the outer `except` was left where it was, so it now also covers a
region that runs **after the row is durable**. `_atomic`'s exit does
`os.chmod(temporary, mode)` and `os.replace(temporary, target)`, both of which
can raise `OSError` (`EROFS` on a data volume remounted read-only, `EACCES`,
`EIO`, `ENOSPC` on the chmod's inode update). When either does:

* the row for `dest/a.mp4` is **already committed**, with `thumbnail_path` set;
* the outer handler then deletes `dest/a.mp4` from the drive;
* the caller is told the copy **failed**, and `files.created` is never emitted.

Before `598b3905` this could not happen: the thumbnail was published with
`shutil.copy2` *before* `db.add`/`db.commit()`, so nothing inside the outer
`try` ran after the commit. The defect is new in this commit.

### Who reaches it and how

Paste a file into a folder while the `data/` volume is full or has flipped
read-only (the ordinary docker symptom the rest of this branch is defending
against). The paste reports an error, but the pasted file now exists in the
library as an Active row with no bytes behind it, and **every later attempt to
paste the same file into the same folder is refused forever** — the phantom row
is Active, so `resolve_db_path_conflict` raises 409 rather than retiring it.

only the `os.replace` of the `.jpg` — the drive file's own `copy2` is untouched:

with a message: the `OSError` escapes `copy_file` uncaught (the inner
`except`→`HTTPException(500)` is only around the DB block), so it leaves the

single-file route does not.

### What would close it

The outer `except Exception` must stop covering anything that runs after
`db.commit()` — e.g. close the `ExitStack` explicitly before leaving the
protected region and treat a publish failure as "the copy succeeded, the
thumbnail did not" (clear `new_file.thumbnail_path`, or simply let the next scan
regenerate it), rather than as "reverse the filesystem".

## 2. The retirement still clears a slot the operation never takes — round 5's fix tests the *shape of the ghost's pointer*, not whether anything will write there

**Behaviour defect a user can hit.** This is the round-5 defect
("the retirement cleared a slot the copy never took") in the two cases the
round-5 condition does not cover. `598b3905` edits this exact block, so its
siblings-by-role are in scope.

`resolve_db_path_conflict` (`fileops.py:206-216`) clears the retiring Missing
row's `thumbnail_path` whenever it *names* the path-derived slot at `new_rel`:

```python
folder, _, name = new_rel.rpartition("/")
if conflict.thumbnail_path == path_thumbnail_rel(drive, folder, Path(name).stem):
    conflict.thumbnail_path = None
```

The justification is "the arriving file takes that slot, so leaving the pointer
means the Missing row shows the new file's picture and purging it unlinks a live
thumbnail". That justification is a statement about the **caller**, and it is
false for three of the reachable cases. The condition never asks the caller
whether it is going to write there.

### 2a. `copy_file` where the source has no usable thumbnail

`new_file.thumbnail_path` is only set inside
`if source.thumbnail_path and not _is_markdown_file(source)` **and**
`if old_thumb.exists() and not (new_thumb.exists() and samefile)`. A source with
no thumbnail row at all — a document, an audio file, a video the scanner has not
reached yet, or a file whose cached JPEG was deleted — writes nothing. The ghost
is stripped anyway.

**Who reaches it:** a video went missing from `dest/`; you paste another file of
the same name into `dest/` from a folder where it has no thumbnail yet. The
Missing entry for the old file loses its picture, permanently, and its JPEG
becomes unreachable by the purge that entry exists for.

### 2b. `move_file` / `rename_file` of anything that is not a video

`_move_thumbnail` is called only under `file.file_type == "video"`, at both
sites. Move an image onto a Missing image's path and nothing is written to the
slot, but the retirement already cleared the ghost's pointer. (The video gate
itself is on the "known, not fixed" list; the *ghost losing its picture and its
JPEG becoming unpurgeable* is a separate consequence of the block this commit
edits, and is not on it.)

`backend/tests/test_r7_probe2.py` (added by me, removed afterwards). No
mutation — stock `598b3905`.


Both lines are the two assertions the round-5 test
`test_a_copy_onto_a_missing_note_keeps_its_picture` makes for the Markdown case
(`kept.thumbnail_path == projection_rel`, and after the purge
`not projection.exists(), "the purge could no longer reach the JPEG"`), failing
here for the non-Markdown cases.

### Why the scanner does not repair it

A retired Missing row is not on disk, so no scan visits it and its cleared
pointer is never restored — the Missing view's picture is gone for good. The
stranded JPEG is later *reclaimed by the wrong owner*: the next scan of the
arriving file finds `thumbnail_path != _expected_thumbnail_path(...)` and
`_relocate_thumbnail` either regenerates over the slot (2a) or renames the moved
file's own thumbnail onto it (2b). So the bytes stop being an orphan only by
being overwritten, and if the arriving file is trashed and purged before the
next scan, the JPEG is orphaned with no row naming it at all.

### What would close it

The condition has to be "will this operation publish to that slot", not "does
the pointer spell that slot". The caller already knows: `copy_file` knows
whether it staged anything, `move_file`/`rename_file` know the video gate.
Deciding it in `resolve_db_path_conflict` from `new_rel` alone cannot be made
correct.

## 3. The guard that stops two rows sharing one JPEG only recognises the source's own JPEG — an active neighbour with the same stem still loses its picture at paste time

**Behaviour defect a user can hit** (pre-existing in effect; the finding is that
this commit's chosen discriminator leaves the twin standing).

Item 2 of `598b3905` introduces the invariant in its own comment:

```python
# The copy takes no pointer in that case; the slot belongs to the row
# already naming it, and two rows sharing one JPEG means purging either
# blanks the other.
```

and enforces it with `old_thumb.samefile(new_thumb)` — a test of whether the
destination slot is **the source's own** JPEG. `path_thumbnail_rel` keys the slot
on the *stem*, not the extension, so the slot can equally belong to **any other
row in that folder whose filename shares the stem**. That row is not the source,
so `samefile` is False, and the copy publishes over it and records the same
pointer.

### Who reaches it

`dest/` holds `a.png`. You paste `a.mp4` into `dest/`. `_resolve_copy_filename`
sees no filesystem collision, so no `_copy` suffix; `resolve_db_path_conflict`
finds no row at `dest/a.mp4`; nothing in the path notices `a.png`.

### Reproduction (`backend/tests/test_r7_probe3.py`, stock `598b3905`)

```
COPY: {'copied': 1, 'errors': []}
COPY POINTER:      test-drive/dest/a.jpg
NEIGHBOUR POINTER: test-drive/dest/a.jpg
SHARED POINTER: True
SLOT BYTES: b'\xff\xd8\xff\xe0fake-jpeg'          <- the video's frame
NEIGHBOUR SEES: b'\xff\xd8\xff\xe0fake-jpeg'      <- the picture now shows the video
SLOT AFTER PURGING THE COPY: False
NEIGHBOUR SEES AFTER PURGE: 200 <the placeholder JPEG>
1 passed
```

The picture `a.png` shows in every listing becomes the pasted video's frame the
moment the paste lands, and trashing + purging the copy blanks `a.png`
permanently — literally the sentence the commit's comment says it is preventing.

### Scope

The stem-keyed slot is systemic: the scanner computes
`_expected_thumbnail_path(drive, folder, nfc_stem)` the same way, so two files
with one stem collide there too, and this is not something `598b3905`
introduced. What is in scope is the shape of the guard it added. `samefile` on
the source's thumbnail answers a narrower question than the invariant it is
written to enforce. One query — "is any other row in this drive already naming
`new_thumb_rel`?" — answers the actual question, and subsumes the samefile case
the commit does handle.

I would not hold the PR on this one; it belongs with the byte-exact-lookup item
already deferred to its own PR, and for the same reason (the correct fix is a
lookup, not a `stat`).

## The span question, answered

> Does the span's contract now hold for everything the span creates and
> everything it overwrites?

**No — in one direction, and it is finding 1.** The contract itself is stated as
"from the exclusive `os.open` to `db.commit()`". `598b3905` moved a filesystem
publish to *after* `db.commit()` without moving the boundary of the handler that
reverses the filesystem, so the span now has a tail in which the row is durable
and the destination is still being deleted on failure.

Inventory of everything the request writes, and its state after a failure:

| write | after a failure | verdict |
|---|---|---|
| `new_full` (the drive file) | unlinked | ✅ — **except** when the failure is the publish itself, where the row is already committed and the unlink runs anyway (finding 1) |
| the staged thumbnail temporary `.<name>.XXXX.jpg` | unlinked by `_atomic`'s `finally` | ✅ (held by M11) |
| `new_thumb` (the cache slot), pre-existing bytes | never touched before the commit | ✅ — this is the r6#4 fix, held by M5 |
| `new_thumb`, when the slot was empty | never created | ✅ |
| the Markdown projection JPEG | unlinked, parents cleaned | ✅ (held by M9) |
| the retiring Missing row's `file_path` / `thumbnail_path` | rolled back — `batch_copy` calls `db.rollback()` on both arms; the single-file endpoint has no later commit and the session's close rolls back | ✅ measured (probe 4: `GHOST file_path: dest/a.mp4  pointer: test-drive/dest/a.jpg` after the body write fails through `POST /api/files/{id}/copy`) |
| the `EmptyFolder` delete | inside the DB block, rolled back | ✅ |
| `data/thumbnails/<drive>/<folder>/` (created by `_atomic`'s `mkdir`) | left behind, empty | on the "known, not fixed" list |
| `<drive>/<target_folder>/` (created by `target_dir.mkdir(parents=True)`) | **left behind, empty, in the user's library** | outside the declared span (it happens before the exclusive create), pre-existing, and the scanner will surface it as an `EmptyFolder`. Measured in probe 4: after a failed paste into `brand/new`, `DRIVE DIR LEFT: True  DRIVE DIR CONTENTS: []`. Not counted as a finding — it is not inside the span the commit is about — but it is the one remaining thing a *user* sees after a paste that reported nothing arrived. |

I found no path where the thumbnail is published and the row is not committed:
every exit from the `with` other than a clean one goes through the generator's
`finally` with the temporary still un-renamed, and the only `return` inside the
span is after the `with`.
