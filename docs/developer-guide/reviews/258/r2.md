## 1. The `db.rollback()` the new handler exists to add is held by nothing, and it is load-bearing

`batch_copy`'s new `except Exception` branch (`files.py:606-616`) carries a
six-line comment justifying the rollback: "the path-conflict step flushes a
delete that must not ride out on the next file's commit". That is true. Nothing
tests it.

Mutation, `want=kill`: delete line 615, `db.rollback()`, from the new branch —
keep the handler, keep the `errors.append`. Applied (`git diff`: 1 deletion in
`backend/app/routers/files.py`). Then:

```
pytest tests/test_copy.py -q --no-cov   →  15 passed
pytest -q --no-cov                      →  2133 passed, 4 skipped  (212s)
```

**Survives the entire backend suite.**

It survives because the commit's own new test,
`test_batch_copy_survives_a_filesystem_error_on_one_file`, fails **`b.mp4`, the
last id in the batch**. Nothing commits after the failure, so a rollback and no
rollback are the same run. The term the handler was written for can only be
observed when a *later* file commits.

What it costs when it is absent. `copy_file` calls `resolve_db_path_conflict`
(`fileops.py:256`), which for a **Missing** record at the destination path does
`conflict.file_path = f"__missing_{id}_{new_rel}"` + `db.flush()`
(`fileops.py:199-200`), and for a **Trashed** one `db.delete(conflict)` +
`db.flush()`. Both are flushed and uncommitted when `shutil.copy2`
(`fileops.py:264`) raises. Without the rollback they ride out on the *next*
file's `db.commit()`.

Probe (three cases, run against the mutated tree and then against `38331b56`):

| probe | mutated | at 38331b56 |
|---|---|---|
| a Missing record at `dest/a.mp4` keeps `file_path == "dest/a.mp4"` after the copy of `a.mp4` fails and `b.mp4` succeeds | FAIL — retired to `__missing_<id>_dest/a.mp4` | pass |
| a Trashed record at `dest/a.mp4` still exists after the same batch | FAIL — purged | pass |
| `b.mp4` lands in the DB exactly once when `a.mp4` fails first | pass | pass |

The Missing case is the damaging one and it is squarely against
`.claude/rules/design-decisions.md`: a Missing record is kept indefinitely so
watch history, tags and comments survive until the path reappears. Retiring its
`file_path` to a placeholder because an *unrelated* file in the same paste hit
ENOSPC means the real file reappearing at `dest/a.mp4` is scanned in as a brand
new row, and the old row is stranded under `__missing_…` with nothing pointing
at it. No user action caused it and nothing reports it.

Fixture, not implementation: the existing test needs the failing id **first**,
not last — `ids: [f2.id, f1.id]` with the same `fail_on_b` — plus one of the two
ghost rows above, which is what makes the rollback (rather than merely the
handler) the thing under test.

## 2. Continuing after a failure made the zero-byte orphan collide with the rest of the batch

`copy_file` creates the destination with `os.open(..., O_EXCL)` (`fileops.py:260`)
and only then writes it with `shutil.copy2` (`:264`). A `copy2` failure leaves a
**zero-byte file at the destination with no DB row**, and no handler removes it —
the `unlink` at `fileops.py:313` is reached only from the DB-write `try`, which
`copy2` never gets to. The commit says the orphan is out of scope. It is, as a
bug. What the fix changed is who meets it: the batch used to stop at the first
failure, and now it keeps going past the orphan it just made.

Probe, at `38331b56`, no mutation: two files both named `a.mp4`
(`one/a.mp4`, `two/a.mp4`), pasted together into `dest`, `copy2` raising ENOSPC
on the **first** call only:

```
POST /api/files/batch/copy {"ids": [a, b], "target_folder_path": "dest"}
→ 200 {"copied": 1, "errors": [{"id": <a>, "error": "[Errno 28] ..."}]}

AssertionError: zero-byte orphan left at dest/a.mp4;
                the surviving copy landed as ['a_copy.mp4']
```

So the file that *did* copy is named `a_copy.mp4` — `_resolve_copy_filename`
(`fileops.py:203-211`) tested `(target_dir / "a.mp4").exists()` and found the
orphan the previous iteration had just created. The name `a.mp4` is held by a
zero-byte file that is in no listing, and the next drive scan will index it as a
real, empty `a.mp4` sitting next to `a_copy.mp4`.

Under the pre-fix code the same probe returns **500 at the first file** and the
second is never attempted, so neither the suffix nor the second-file interaction
existed. Confirmed by mutation (`want=live`, to establish the old behaviour):
delete the whole `except Exception` branch, re-run — the request 500s, `copied`
is never reported, and the probe fails at `status_code == 200` instead.
(That mutation is otherwise `want=kill` and **is** killed, by
`test_batch_copy_survives_a_filesystem_error_on_one_file` — the new handler
itself is held.)

This needs no new error path to fix: `copy_file` can wrap the `copy2` in a
`try` that unlinks `new_full` before re-raising, exactly as the DB block already
does four lines below. Nothing currently asserts the destination is left clean
after a failed copy, for the batch endpoint or the single-file one.

own** — the `FileExistsError → HTTPException(409, "Target file already exists")`

the two calls (TOCTOU — which is what the `O_EXCL` is there for), or that
`os.open` fails that way for another reason.

Probe, `want=kill` on the mutated tree: a Missing record at `dest/a.mp4`, a
batch of `[a.mp4, b.mp4]` into `dest`, `app.services.fileops.os.open`
monkeypatched to raise `FileExistsError` for `dest/a.mp4` only.

```
mutated (no rollback in the HTTPException branch):
  FAILED test_409_from_o_excl_does_not_retire_a_missing_ghost
          AssertionError: path retired to '__missing_<id>_dest/a.mp4'
at 38331b56:
  4 passed
```

Without the rollback, `conflict.file_path = "__missing_…"` (`fileops.py:199`)
is left pending in the session and is committed by `b.mp4`. The Missing
record's real path is destroyed by a 409 on a *different* file, permanently:
when the file reappears at `dest/a.mp4` the scanner creates a new row and the
old one — holding the watch history, tags and comments the Missing state exists
to preserve — is stranded.

So both rollbacks this commit added are correct, both are needed, and the suite
would not notice either of them being removed again. The fixture that closes #1
(failing id **first**, plus a ghost row) closes this one too if it is
parametrised over the two ways `copy_file` fails after the flush: `copy2`
raising `OSError`, and `os.open` raising `FileExistsError`.

## 5. The commit gave a partial batch an event it never used to send, and nothing observes it

`files.py:617-618` emits `files.created` **after** the loop. Before this commit
an `OSError` escaped the loop, so the emit was skipped entirely — even though
`copy_file` commits per file (`fileops.py:310`) and the earlier copies were
durable on disk. Addons and every open tab were never told about them; the row
appeared only after the next scan or reload. With the handler in place the emit
now runs, carrying `copied_ids`.

That is a behaviour change in the right direction and it is not mentioned or
tested. Nothing in the suite reads the payload of this emit at all.

Mutation, `want=kill`: `files.py:618` →
`event_hooks.emit_from_thread("files.created", {"file_ids": body.ids})`, i.e.
announce the **source** ids instead of the ids of the copies. Applied (1
insertion, 1 deletion, proved by `git diff`), then the whole backend suite:

```
pytest -q --no-cov   →  2134 passed, 4 skipped   (249s)
```

Survives. (Clean baseline for comparison: `2134 passed, 4 skipped` with the
probe file present, `2133` without it — a suite test enumerates `tests/*.py`,
so adding a file adds a case; collection is `2137` clean, `2138` with the probe.
Both mutated and clean runs were taken under the same condition.)

The ids are not interchangeable: `copied_ids` are freshly generated
(`fileops.py:248`), `body.ids` are the originals. `event_hooks.emit` resolves
ids to drives itself and fails closed when it cannot
(`test_lifecycle_ws_events.py::test_unresolvable_ids_broadcast_nothing`), so the
wrong ids do not leak across the drive boundary — they make every consumer of
`files.created` (WS refresh, addon hooks) act on files that already existed
instead of the copies that were just made, and the copies are announced to
nobody.

`captured_emits` already exists as a fixture
(`tests/test_folder_and_file_create_events.py`). One case on the partial-batch
path — one file fails, one succeeds, assert the emitted `file_ids` equals the
one new id and not the two source ids — covers both the payload and the fact
that a partial batch emits at all.

## 6. The `throw` in the new `catch` reaches nobody — decide whether it should, or drop it

`ClipboardProvider.tsx:143` rethrows after the toast. There is exactly one

```tsx

```

Mutation, `want=live`: `throw error` → `return`. Applied (proved by `git diff`),
then `npx vitest run` from `frontend/`:

```
Test Files  456 passed (456)
     Tests  6590 passed | 2 todo (6592)   EXIT=0
```

Survives, and the only reachable difference is that `FolderBrowser`'s
`refresh()` runs after a refused paste instead of being skipped — a list reload
for a request that changed nothing. No second toast either way, so nothing is
reported twice; the empty `catch` is now genuinely empty rather than
swallowing the only report, which is what #6 of the last round asked for.

The fork: either the caller should do something with the rejection that the
provider cannot (it is the one that knows which screen was pasted into), or the
rethrow is a term that cannot vary independently of its neighbours and should be
folded away so the next reader does not go looking for the handler it implies.
I would drop it — the provider already owns the message, and an empty `catch`
kept alive only to absorb a rethrow nobody reads is the shape that made the last
round's finding possible.
