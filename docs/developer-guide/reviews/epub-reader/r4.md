## Findings

### R4-F1. The hostile walk still never loads the SVG spine section, so no browser test runs an SVG section through the reader

- Labels: `[introduced]`. `01cee4152` rewrote `walkHostileBook` to stop at `LAID_OUT - 1` (c4) and declared `c5-svg` unreachable. The hostile-book SVG vector was reached through the reader at `916ba3a72` whenever `c7` was removed (R3-F2, W1c). Invariant **1** (sanitizer alone). Severity **Low–Medium** (detector gap; the code holds today).
- The comment's premise does not hold as measured. With one more `turn("next")` past c4, foliate *does* load the SVG section into an iframe (`contentType image/svg+xml`, `lastLocation` stays at 5) in both engines (`zz-r4w`, deleted).
- Measured with W1b (SVG sections passed through unsanitized with their type) under the sanitizer-alone configuration: `__pwned = ["svg-doc", "svg-doc-onload"]` in **Chromium and WebKit**, but the committed suite is **71 passed**. Only one jsdom unit test fails. At baseline the same full walk gives `__pwned = null` in both engines, and with the policy alone (sanitizer stubbed) WebKit loads the SVG section and nothing runs.
- The new `sanitize.spec` "SVG document" vector calls `sanitizeMarkup` directly, so it does not cover the transform's dispatch by type.
- Direction: the walk should end with a turn into the SVG section and assert on `__pwned` after it. For example, assert that the last section's document was loaded, not that `lastLocation` reached it.

### R4-F2. An HTML-path section is now decoded by its own `<meta charset>`, not as the UTF-8 it was read as, so a stale declaration turns the chapter into mojibake

- Labels: `[introduced]` (text/html serving in `01cee4152`). Invariant: none. Severity **Low–Medium**. It needs a section that fails XML parsing *and* carries a `<meta charset>` that is not UTF-8. Converted Japanese books with a leftover `charset=Shift_JIS` are the realistic source. The whole chapter becomes unreadable, but nothing breaks security.
- Mechanism: zip.js `TextWriter` decodes every section as UTF-8. The sanitizer keeps `<meta charset>` (only `http-equiv` is dropped). The blob is written as UTF-8 bytes with type `text/html` and no charset parameter, so the HTML parser's meta prescan wins. Under XHTML serving (all earlier SHAs) the meta element is inert.
- Measured (`zz-r4`, deleted; a UTF-8 chapter with Japanese text, one `\u000b`, and a `<meta charset>`; Chromium and WebKit, identical):

| SHA | `<meta charset="Shift_JIS">` | `<meta charset="windows-1252">` |
|---|---|---|
| `15e18db86` | XHTML, `UTF-8`, text correct | XHTML, `UTF-8`, text correct |
| `916ba3a72` | refused (R3-F1) | refused |
| `01cee4152` | **text/html, `Shift_JIS`, mojibake** | **text/html, `windows-1252`, mojibake** |

  Control: the same chapter without `\u000b` (XML path) renders correctly at `01cee4152`.
- Shape that adds no branch: make the blob type say what the bytes are (`text/html; charset=utf-8`), because a transport charset overrides the meta prescan. Alternatively, treat `meta[charset]` like `http-equiv`. This is for the author to measure.

### R4-F3. A section that really is Shift_JIS-encoded shows a blank page

- Labels: `[pre-existing]`. The same result at `15e18db86`, `916ba3a72` and `01cee4152`: the section is decoded as UTF-8 by zip.js `TextWriter` before any code in this PR sees it, and the blob keeps the `encoding="Shift_JIS"` declaration (`characterSet` = `Shift_JIS`, no body text). ## 5. Trajectory

Reading `12fc6fc1a` → `916ba3a72` → `01cee4152`, against what was measured:

- **CSP probe: converged.** Round 1 added the outside-directory prediction, and round 2 replaced it with a timing and `blockedURI` prediction. `01cee4152` removes both and returns to the original two checks (eval, inline). Both are killed in both engines (P1, P2), and nothing new was added. This is the removal the rule looks for.
- **Sanitizer: mostly removal, plus one new state.** Removed: the two attribute rules (prefixed, `xmlns`) from round 1, and the XML-only strict re-parse of fallback sections from round 2. The round-2 `parsererror` refusal stays, now only for XML output. Added: a second output language (`text/html` with its own serializer), one value rule (`isScriptUrl`, which replaces two name rules), a guard on the `parsererror` check (`first.type !== HTML`), and a document-level branch for unknown roots. `REFUSED` is a value change, not a branch. The measured shape is layering, not a patch chain. C3/C4 and U3/U4 are each live alone because two rules overlap on every known vector, and no fix in this round targets a single vector.
- **The new state has its own reach, which is the round-3 pattern again.** R3-F1 was the new strict pass refusing legitimate books. R4-F2 is the new text/html output making a legitimate book's leftover `<meta charset>` meaningful. In both, a mechanism added to change what the browser parses brings in behaviour of that parser that the earlier shape never met. One round is not a trend, and this round removed more than it added. But if the next fix for the HTML path adds another special case (for example, a rule for `meta[charset]`), the round-3 trajectory is repeating on the new state. The shape suggested under R4-F2 (declare the blob's charset) is a value, not a branch. Task 3 was not measured, so the security reach of this state is unassessed; the supervisor should decide on the design with that gap in mind.
- **Walk detector:** `01cee4152` replaced the fixed 7 turns with a reached-set assertion (E1 kills a shortened walk), which improves the detector. But the declared endpoint excludes a loadable section (R4-F1).
