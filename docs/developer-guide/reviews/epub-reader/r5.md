## Findings

### F1. A UTF-8 XHTML or SVG section with a leftover `<?xml … encoding="Shift_JIS"?>` renders as the wrong text

- `[pre-existing]`: identical at `15e18db86`, `01cee4152` and `a0f0bb38e`, in Chromium and WebKit. Invariant: none. Severity **Low–Medium**, the same class as R4-F2.
- Mechanism: this is R4-F2's mechanism on the XML path. zip.js decodes the section as UTF-8. foliate's `XMLSerializer` output keeps the XML declaration (measured: the served text starts with `<?xml version="1.0" encoding="Shift_JIS"?>`), and the blob is `application/xhtml+xml` or `image/svg+xml` with no charset. The XML parser therefore decodes the UTF-8 bytes as Shift_JIS.
- Reach: this is likely more common than R4-F2, because it needs only a valid-XML chapter. Most EPUB sections take this path, and R4-F2 additionally needed a chapter that fails XML parsing.
- Relevance to this round: `a0f0bb38e` applied R4-F2's suggested value ("make the blob type say what the bytes are") only to `text/html`. M6, which applies the same value to every served type, fixes both the XHTML and SVG cases in both engines (`characterSet = UTF-8`, text correct, root still `html` / `svg`), and the e2e suite stays green. The unit tests fail on exact XML type strings, which is a test-side cost only. For the supervisor: the uniform value would also remove the `first.type === HTML ?` conditional (see Q3).
