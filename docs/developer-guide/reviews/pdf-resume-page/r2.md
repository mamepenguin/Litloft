## Findings

### R2-1. Going A → B → A while A's first read is pending: the first read's end lifts the gate on the second read

- Label: `[introduced]`. At `a87fef823` the return to A took the reload branch and started no second read (that was F1), so the first read's end was the right moment to lift the gate. The F1 fix starts a second read of the same file id; `finally` is scoped by file id (`current === id`), which both reads share.
- Breaks: **Invariant 5** (no save while the stored page is being read).
- Where: `frontend/src/lib/pdfPageProgress.ts:110` and `:126-128`.
- Reproduction (hook level, profile): A `documentLoaded(20)` with read1 deferred → rerender B → rerender A → `documentLoaded(20)` with read2 deferred → resolve read1 `{0,0}` → turn A to 3 → 1 s. Observed: `saveWatchProgress("file-aaaaaaa", 3, 20)` while read2 is still pending. Variant: read1 resolves `{9,20}` → `goTo(9)`, turn to 10 → `save(A,10,20)` while read2 pending.
- User effect measured: none beyond the letter of the invariant — read2 then finds `pageRef !== openedOn` and does nothing, so the saved page is the reader's own turn. Needs a slow server read and a switch away and back before it lands.

### R2-2. Opening full screen at a page other than the inline one is untested, and a wrong value overrides the reader's turn

- Label: `[introduced]` (`setFullscreenPage(page)` is new in `0f7e34f46`).

- Where: `frontend/src/components/PdfPreview.tsx:399` (`f` shortcut) and `:590` (button). The hook's `page` is `fullscreenPage ?? page` (`:146`), so the value the viewer is opened with is what the restore's `pageRef !== openedOn` check and the save effect see.
- Reproduction: mutations A1 (`setFullscreenPage(1)` in the button) and A2 (same in the shortcut) pass all 138 tests. Scratch test (profile, deferred read): PageDown ×2 inline → page 3 → open full screen → resolve `{6,8}` → 1.5 s → Escape.

## Question 3 — trajectory

Yes. Round one added the restore gate (`restoringRef`), the "reader has not moved" prediction (`pageRef !== openedOn`) and the "already written" prediction (`lastWrittenRef = saved`). This round:

- widens a state (`fullscreen: boolean` → `fullscreenPage: number | null`) and adds a branch (`goToReadingPage`: viewer ref or inline `setPage`);
- replaces the gate ref with state keyed by file id and adds a second reset site (`loadedRef = null` on switch);
- adds a prediction of the same kind as round one's `lastWrittenRef = saved`: `lastWrittenRef = openedOn` ("the opening page is not a turn"), plus a clamp on it.

It also removes two resets (the `restoringRef` and `lastWrittenRef` cleanup) and the `fileIdRef === id` guard, so it is not pure accretion. But each of R2-1 to R2-4 is again a case where "did the reader turn a page?" is inferred from page-number equality at a moment the code predicts (open, restore, switch, full-screen open), and fixing R2-1 would need another state (a per-read token), R2-4 another seed site. The design is being patched: three independent predictions (`openedOn` comparison, `lastWrittenRef` equality, the `restoring` gate) answer one question the component could state directly — a page change caused by the reader versus one caused by load/restore/URL.
