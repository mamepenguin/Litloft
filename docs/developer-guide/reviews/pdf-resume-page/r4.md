## Question 2: what this round broke

- **`turnTo` while full screen is open**: this is R4-1. It cannot report a page the viewer did not move to that is out of range: `enterPage` clamps, and `pageTurned` rejects anything outside `2..numPages`. It does report a `next` that the viewer already shows. In spread mode that includes the second page of the pair on screen (N3). The report is the named page, not `face.index + 1`. R3 already judged that harmless: restoring 5 reopens the same pair. The comparison the inline branch makes cannot be reused here, because `pageRef` is the inline page and not the viewer's face (M56 / B3).
- **`pageRef` assigned during render**: no finding. Nothing in `PdfPreview` renders in a transition, `useDeferredValue` or Suspense, so no render is discarded after setting it. StrictMode's double render writes the same value. Two keys pressed before a render cannot share a stale `pageRef`: `ShortcutsProvider` listens natively and each keydown is its own discrete task, flushed before the next. M45 (set in a passive effect) is killed. `movePage` still reads `numPages` from its closure, but the page-key context is enabled only when `numPages > 1`, in the same effect flush that swaps the handler, so the stale value is never the 0 of an unloaded document.
- **`turnFromRef` overwritten on every `countTurn`**: correct where it can be reached. Two turns in one batch (V1, `ArrowRight` ×2 inside one `act`) show 5 and report `[5]`. A batch that returns to its start (V2, `ArrowRight` + `ArrowLeft`) reports nothing, where cd7 reported `[3]`. `useSpreadPaging.turn` applies deltas through the updater, so the face after the batch is the sum and the start is the last rendered face. A goToPageRef move and a no-op key in the same batch (V6) are reported as one turn to the link's page. cd7 gives the same result, and a link and a key cannot share a batch from real events. Not a finding. Nothing holds the overwrite: R4-2.
- **Half-page steps of a split wide page**: V4 (spread, all landscape, opened on 4). `ArrowRight` ×3 gives halves 4, 5, 5 and reports `[5]` at HEAD, against `[4],[5],[5]` at cd7. A half step no longer counts as a turn, so it does not cancel a pending restore. That matches R3-1's premise that nothing moved. Not a finding.
- **The page box in full screen**: typing the page shown reports nothing (author test). In spread mode, typing 5 while 4+5 is shown (V5) leaves the face at 4+5 and reports nothing. cd7 reported `[4]`. Typing a page on another face is reported (existing test, M2 killed in r3).
- Full suite at HEAD: 532 files, 7226 tests green.

## Question 3: trajectory

Fix diffs in order:

- `0f7e34f46` (r1): added a state (`fullscreenPage`), a branch (`goToReadingPage`), a gate state (`restoringFile`) and a prediction (`lastWrittenRef = openedOn`).
- `8c1fea52d` (r1): removed a reset.
- `d7fe8c361` (r2 rebuild): removed every "did the reader turn?" prediction, including the viewer's `reportedIndexRef` index-change check. Added the `pageTurned` entry point and the `turns` counter.
- `cd7153ef1`: removed a reset, added tests.
- `0123a5c0a` (this round): inline, added one branch (`next === pageRef.current` → return) and one ref (`pageRef`, replacing a closure read, which is a fix of a different kind). Viewer, added two refs (`faceIndexRef`, `turnFromRef`) and a condition on the report: `face.index !== from`.
- `22fe419c6` (this round): removed a reset (the `null` start and its clear).

Answer:

- **This round added branches after two rounds that only removed them.** That is one round of adding, not two in a row, so the R-4 rule does not trigger.
- **The warning from round 3 did not come true in the form it predicted.** The exclusion is not per call site. Inline, one check in `turnTo` covers keys, box, links and the controller. In the viewer, one check in the report effect covers keys, swipes, taps, chevrons and the box.
- **The check the viewer gained is the one `d7fe8c361` removed.** `d7fe8c361` removed "report when the face index changed" and put a turn counter in its place. This round brings the face comparison back and places it behind the counter. The viewer now needs four pieces (`turns`, `reportedTurnsRef`, `faceIndexRef`, `turnFromRef`) to say one thing: after a reader action, report the face if it moved. Both R4-2 and V6 live inside that combination.
- **R4-1 sets up the next step of the same kind.** The natural fix is a third "did the page change" check, in the full-screen branch of `turnTo`. It would have to be written against the viewer's face, which `PdfPreview` cannot see (M56 shows the version that compares against the wrong page). If the next round adds that check, the pattern round 3 warned about has come back. It would be one check per component rather than per call site, but each new route would get its own equality test. A shape that removes checks rather than adding one: while the viewer is open, send reader moves from `turnTo` into the viewer as turns (`countTurn` + `enterPage`) and do not call `pageTurned` in `PdfPreview`. The viewer's single report effect then decides for links and the controller as well, and the full-screen branch loses its `pageTurned` call instead of gaining a check. This is for the supervisor to weigh. I did not implement or test it.
