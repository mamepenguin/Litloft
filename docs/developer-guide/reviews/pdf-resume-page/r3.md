## Findings

### R3-1. A key, tap or page-box entry that does not move the page is reported as a turn

- Label: `[introduced]`. At 8c1 turns were inferred from page changes, so a no-op press changed nothing.
- Breaks: **Invariant 10** (`?page=` writes nothing until the reader turns a page) and **Invariant 1** (a stored page is shown once the document loads). The revised Invariant 5 lets a *page turned* cancel the restore, and these presses turn nothing.
- Where:
  - inline: `frontend/src/components/PdfPreview.tsx:337-342`. `movePage` clamps and then always calls `turnTo`, so `PageUp` on page 1 reports 1 and `PageDown` on the last page reports the last page. `PdfPageInput` also commits a retyped current page (`:527`).
  - full screen: `frontend/src/components/pdf/PdfFullscreenViewer.tsx:162-169`. `navigatePrev` and `navigateNext` bump `turns` even when `useSpreadPaging`'s step is 0 at the first or last face. This happens for arrow and page keys, swipes, and edge taps. Only the on-screen chevrons are gated, by `canGoPrev`/`canGoNext` at `:503`/`:518`.
- Reproductions (component, 8-page document):
  - S1: profile, read held open. On page 1, `PageUp`, then the read resolves `{5,8}`. HEAD: page box `1`, nothing saved (restore cancelled). At 8c1: `5`.
  - S2: the same in full screen, pressing `ArrowLeft` on the first face. HEAD: the dialog shows page 1. At 8c1: page 5.
  - S3: the same, typing `01` + Enter into the page box. HEAD: `1`. At 8c1: `5`.
  - S4: stored 5, opened with `?page=8`, `PageDown`, unmount. HEAD: stored `8`. At 8c1: `5`. The stored 5 becomes 8/8, so the document counts as finished and leaves Continue watching. The route is realistic: a citation link to the last page (references), followed by one more key press.
  - S5: as S4, but in full screen pressing `ArrowRight`. HEAD: stored `8`. At 8c1: `5`.
  - Viewer alone: opened on page 8, `ArrowRight` gives `onPageTurned(8)`. Opened on page 1, `ArrowLeft` + `PageUp` give `onPageTurned(1)` twice.
- Mutations M20 (gate the viewer's `navigateNext` on `canGoNext`) and M21 (skip `turnTo` when the clamped page equals `page`) both leave the suite green, so no test requires reporting a no-op press.

### R3-2. `movePage` reads `page` from its closure, so a key pressed right after a restore turns from the old page

- Label: `[introduced]` (`d7fe8c361` replaced `setPage((current) => …)` with `turnTo(… page + delta …)`).
- Breaks: no invariant cleanly. What the user sees: the page jumps back near the start, and the stored page is overwritten with that wrong page.
- Where: `PdfPreview.tsx:337-342`. `useShortcuts` swaps in the latest handler in a passive effect (`hooks/useShortcuts.ts:27-29`), and `ShortcutsProvider` listens on `document` natively. A non-discrete render (the restore's `goTo`, the load clamp, a `?page=` navigation) commits the new page before that effect runs. A `PageDown` in that gap runs the previous `movePage`. The old functional update was immune.
- Reproduction (component, profile, read held open, `IS_REACT_ACT_ENVIRONMENT = false`): a `MutationObserver` fires `PageDown` as soon as "Selectable page 5" is in the DOM after the read resolves `{5,8}`. HEAD: page box `2`, 3/3 runs. At 8c1: `6`. In a browser the gap is the time between a default-lane commit and its passive-effect task. A `PageDown` queued while the restore renders, or a held key's auto-repeat, lands in it.

### R3-3. Nothing holds that swipes, edge taps or the full-screen chevrons report a turn

- Label: `[introduced]`. Reporting now depends on the call path: only the wrapped `navigatePrev`/`navigateNext` count. At 8c1 any `face.index` change was reported, whatever caused it.
- Breaks under mutation: **Invariant 6** and **Invariant 9**. A test that lets an A through.
- Where: `PdfFullscreenViewer.tsx:179-186` (the functions passed to `useViewerZoom`) and `:503-523` (the chevron buttons).
- Reproduction: M30 passes `pagePrev`/`pageNext` to `useViewerZoom`, and M31/M32 use them in the chevrons. All 145 tests pass under each. Scratch: at HEAD a touch swipe and a "Previous page" click each give `onPageTurned(2)`. Under M30/M31 the page still turns (`[2]`) but `onPageTurned` is never called. On a phone, where swipes and taps are the only way to turn, nothing read in full screen would be saved.

### R3-4. Nothing holds that the last page is saved

- Label: `[pre-existing]` to this round. The same mutation also survives at 8c1 (138 tests green). It is new to the branch relative to `develop`.
- Breaks under mutation: **Invariant 9**. Saving the last page is what marks a PDF finished and takes it out of Continue watching.
- Where: `frontend/src/lib/pdfPageProgress.ts:126`.
- Reproduction: M17 (`page > loaded.numPages` → `page >= loaded.numPages`). All 145 tests pass. A reader who finishes the document keeps the second-to-last page stored.

### R3-5. The react-pdf mock re-reads `onItemClick` every render, but react-pdf keeps the first one

- Label: `[pre-existing]` (mock from #363, `PdfPreview.test.tsx:74`). The code at HEAD is correct: `turnTo` is stable because its dependencies are refs and `[]`/`[write]` callbacks.
- Breaks under mutation: links followed in full screen go to the inline page instead of the viewer.
- Where: `react-pdf@10.4.1` `dist/Document.js:59-67` closes over `onItemClick` in a `useRef` initialiser. The mock at `PdfPreview.test.tsx:74` assigns `itemClick = onItemClick` on every render. `PdfPreview.tsx:147-153` (`turnTo`) is now the thing whose identity matters.
- Reproduction: M7 makes `turnTo` read `fullscreen` state (deps `[fullscreen, pageTurned]`). All 145 tests pass. With the mock changed to keep the first `onItemClick` (`useRef`), HEAD passes 72/72, and M7 fails "follows a link inside the document to its page, inline and in full screen".
