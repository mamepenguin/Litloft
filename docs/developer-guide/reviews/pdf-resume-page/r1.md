## F1. Coming back to a PDF before the other file finished loading skips the restore

- Label: `[introduced]` (new file `pdfPageProgress.ts`).
- Breaks: **Invariant 1**.
- Where: `frontend/src/lib/pdfPageProgress.ts:98-101`. `loadedRef` is only replaced by the next `documentLoaded`; the file-switch cleanup (`:89-93`) does not clear it. When the viewer goes A → B and B has not loaded yet (slow or failing PDF) → A, A's reload arrives with `loadedRef.current.fileId === "A"` and is handled as a "reload of the same document": no read, no `goTo`.
- `PdfPreview` is not keyed on `fileId` (`FilePreview.tsx:187`), so the same hook instance survives the switch in the right pane and the detail page.
- Reproduction (component level): seed `recently-played` with page 5 of 8 for `pdf123456789`; render → page 5 shown. `rerender` with `fileId="other1234567"` (no load fired), `rerender` back to `pdf123456789`, fire `lastOnLoad(pdfDoc)`. Observed: page box `1`, expected `5`. Hook level: same sequence, `goTo` called once instead of twice.

## F2. Full screen opened while the stored page is being read ends on page 1

- Label: `[introduced]` (the restore did not exist on the parent).
- Breaks: **Invariant 1** (narrow race: profile present, server read slower than `getViewerPreferences`).
- Where: `pdfPageProgress.ts:114` compares only the inline `page`; opening full screen does not change it, so the restore goes ahead and moves the inline page behind the viewer. `PdfFullscreenViewer` takes `initialPage` only at mount, so it stays on page 1, and `PdfPreview.tsx:655` (`setPage(last)` on close) hands back 1.
- Reproduction (component level, profile set, `getWatchProgress` deferred): open, wait for Full screen enabled, open it, resolve read with `{position: 5, duration: 8}`, press Escape. Observed: inline page `5` while the viewer was open, `1` after close. The stored record stays 5 (nothing written), so the reader sees page 1 now and page 5 on the next open.

## F3. A page turned while the stored page is being read is never saved unless the reader turns again

- Label: `[introduced]` (new file).
- Breaks: none of the declared list (see "Missing from the list" below).
- Where: `pdfPageProgress.ts:130` returns while `restoringRef` is set, and `:123` clears it in `.finally` without re-running the save effect (its deps `[fileId, page, write]` do not change). The turn is dropped, not deferred.
- Reproduction (hook level): `documentLoaded(20)` with a deferred read; rerender at page 2; resolve `{0,0}`; advance timers 2 s. Observed: `saveWatchProgress` not called; expected `("A", 2, 20)`. With a profile the read is a network round trip, so a quick PageDown on open is enough; closing the tab then loses the page.

## F4. Three guards that the declared invariants rely on survive mutation

- Label: `[introduced]` (new file).
- Breaks: a test that lets an A through. M31 breaks **Invariant 5**; M13 stops every save on the next file.
- Where: `pdfPageProgress.ts:91` (`restoringRef` reset on file switch), `:92` (`lastWrittenRef` reset), `:123` (the `fileIdRef.current === id` scope on the `finally`). The code is right; no test fails when any of them is removed (M12, M13, M31 below).
- Reproductions that kill them (hook level, all pass on HEAD):
  - M31 (`finally` unscoped): A read pending → switch to B → B `documentLoaded(10)` with its own read pending → resolve A's read → turn B to 4 → advance 1 s. Mutated: `save("B", 4, 10)` happens during B's read.
  - M13 (no `restoringRef` reset): A read pending → switch to B with `requestedPage: 3` → `documentLoaded(10)` → turn to 4 → 1 s. Mutated: nothing saved, and nothing ever will be for B.
  - M12 (no `lastWrittenRef` reset): A saves page 5 → switch to B, load, no stored page → turn B to 5 → 1 s. Mutated: B's page 5 not saved.

## F5. `?page=` past the end records the document as finished without a turn, and the `?page=` test holds only by timing

- Label: `[introduced]` (new file / new test).
- Breaks: none declared; bears on Invariant 2 ("the stored record is not touched by a `?page=` open" is what the test asserts but not what the list says).
- Where: `PdfPreview.tsx:320-321` clamps the requested page to `count` and then calls `documentLoaded`; the clamped page differs from the render before, so the save effect (`pdfPageProgress.ts:127-142`) writes `(n, n)`. A stale citation link (`?page=20` on an 8-page file) overwrites the reader's stored page with "finished".
  - Hook reproduction: `setup({page: 20, requestedPage: 20})`, `documentLoaded(8)`, rerender at page 8, 1 s → `saveWatchProgress("A", 8, 8)` called.
- The test `PdfPreview.test.tsx:1211` "opens on a requested page over the page read last" asserts `storedPage() === 5` before the 1 s delay has passed. In this harness the mock `Document` fires `onLoadSuccess` from a child effect before the hook's save effect, so a write of page 3 is already pending: waiting 1.2 s in the same test gives `3`, not `5`. Only M30 (delay 0) kills it. In a browser the load arrives after mount and nothing is written for an in-range `?page=`, so the test is not describing real behaviour either way; it should wait past `PDF_PAGE_SAVE_DELAY_MS` (and would then show the harness ordering).

## F6. Every full-screen turn now also redraws the inline page behind the viewer

- Label: `[introduced]`.
- Breaks: none declared.
- Where: `PdfPreview.tsx:652` `onPageChange={setPage}` drives the inline `page` while full screen is open, so the inline `<Page>` (`pageElement`, `usePdfPageBoxes`, `rasterCacheFor(pdf).want("inline", {visiblePages:[page]})`) follows every turn behind the dialog.
- Reproduction (component level, 4 × ArrowRight in full screen, `Page` mock render log): parent `548db06fc` → `[2,3,4,5,5]`; HEAD → `[2,2,2,3,3,3,4,4,4,5,5,5,5,5]`. Each turn now rasterizes a hidden second copy at inline size. The spec's goal (hook sees the full-screen page) can be met by feeding the hook the reported page without moving the inline viewer; that is a design choice for the supervisor.

## Missing from the invariant list (round 1 question)

1. **The page the reader leaves the document on is saved** (within the debounce, or on unmount / file switch). F3 and M13 break it; nothing in 1–8 says a turn must be recorded.
2. **Opening with `?page=` writes nothing until the reader turns a page.** F5 breaks it; the existing test claims it.
3. **Returning to a file in the same mounted viewer restores like a fresh open.** Implied by 1, but F1 shows the "once per fileId" design needs it stated per open, not per hook lifetime.
4. Possibly: **full-screen reading does not add drawing work to the inline viewer** (F6), given #368 was about PDF redraw cost.

## Other paths checked, no finding

- In-place `?page=` change on the same file while a read is pending: `:113` drops the stored page (killed by M2).
- File switch while full screen is open: the reset effect closes the viewer; no `onPageChange`/`onClose` fires for the old file; pending save flushes to the old id (M11, M15).
- Profile set/cleared mid-reading: `hasProfileRef` is read at write time; the write goes to the store matching the current profile. No cross-file effect.
- StrictMode double effects: cleanup flush has nothing pending at mount; `reportedIndexRef` guard prevents a spurious first report in the viewer.
- Video/audio: no player file touched; `saveProgress`/`getSavedProgress` unchanged (Invariant 8 holds).

## Observation (not a finding)

`PdfPreview full screen > follows a link inline again after the full-screen viewer has closed` failed with a 3 s timeout in two runs (M22, first M29 run) and passed on rerun of the same M29 mutation. It clicks Full screen without waiting for the button to be enabled. Treat M22/M29 results from that test as noise.
