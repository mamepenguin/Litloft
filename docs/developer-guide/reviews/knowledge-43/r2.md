The ref is cleared in the unmount cleanup, so one mechanism covers all of them. Measured (pristine, repro): S3 two dialogs, the second accepted first, then the first → `onRequestClose` once, `onDialogOpenChange` `[[true],[false],[true],[false]]`, both jobs toasted once each; S4 result first, dialog closed, late acceptance → no close, one error toast; S6 row unmounted by its host while pending → the late acceptance calls neither callback (`[[true]]`), the result toasts. ## Findings

### G1. The StrictMode reset of the dialog's open ref is not held: removing it passes every test and leaves the dialog open after an accepted clip in `next dev`
- Invariant: 3 (accepted → `onDialogOpenChange(false)` and `onRequestClose` once, dialog and menu close).
- Where: `frontend/ClipWebPageDialog.tsx:46-51` (`openRef.current = true` inside the effect). Core `frontend/next.config.ts` sets no `reactStrictMode`, so the App Router default (on in development) applies; `Harness` in `ClipWebPage.test.tsx` renders without `<StrictMode>`.
- Mutation N12: delete `openRef.current = true;` from the effect body. `want=kill`, **live** (41/41).
- Reproduction S1: the same row rendered inside `<StrictMode>`, submit, accept. Pristine: dialog gone, `onRequestClose` once (passes). With N12: the double-invoked effect leaves the ref `false`, so `accepted` never calls `onDone` — the dialog stays open after the clip is accepted and the menu never closes (S1 fails).
- Production builds do not double-invoke effects, so a built image does not hit it; `next dev` does, and the one line that prevents it is free to delete.
- `[introduced]` (the ref is created by `8a7e004`).

### G2. Closing the dialog while `POST /clips` is pending and the request then fails leaves the user with no word of it
- Invariant: none directly. 4 is written for a dialog that stays open; 11 covers only a late *acceptance*. Recorded because it is the other outcome at the seam item 11 was added for.
- Where: `frontend/ClipForm.tsx:63-64` (`setError` on a form that unmounted with the dialog); `frontend/ClipDuplicateDialog.tsx:44-46` likewise for Create new; `frontend/ClipWebPageDialog.tsx` has no failure path once closed.
- Reproduction S7 (pristine): open, submit (createClip pending), press Close, reject createClip with `Error("URL rejected: blocked")`. Observed: `toasts() = {success:[], error:[]}`, no `alert` in the document, `onRequestClose` 0 calls, `onDialogOpenChange` `[[true],[false]]`; reopening shows an empty URL field and no error. The clip was never created and nothing says so. (`routers/clips.py` `create_clip` returns 400 `URL rejected` for a structurally blocked URL before any placeholder is made.)
- Expected, by analogy with 11: the outcome of a clip the user sent is reported even when the dialog closed before the response.
- Unchanged by `8a7e004`: the failure path touches neither the ref nor the store. `[introduced]` (the dialog path is created by S2-16; same behaviour at `9db1ceb`).

## Trajectory

Fix diffs in order: `8a7e004` adds one ref (`openRef`, a state "is this dialog still the one the user is in") at the dialog, and one subscription (`subscribePendingClips` + `version`, with `added` in both notifier effect deps) at the pending set → notifier edge; `95d7c82` adds tests only. This is the first fix round, so there is no earlier fix whose shape it repeats. It adds a state and a prediction (that an early event is still `lastEvent` when the id is added — invariant 12's own condition) and removes none.

Would anything found here need another state or branch at that seam? **G1 does not**: the reset is already in the code; only a test is missing. **G2 would**: reporting a request failure after the dialog closed means the closed dialog's outcome has to reach something that outlives it — another branch through the same dialog → pending set → notifier seam the ref and the subscription were added to. A round-3 fix of that shape would make two consecutive rounds adding state at the same seam.
