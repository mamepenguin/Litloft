## Findings

### F1. Closing the dialog while a clip request is in flight does not detach it: the late acceptance closes a reopened dialog and the menu
- Invariants: 3 (`onDialogOpenChange(false)` / `onRequestClose` once each), 4 and 9 (the dialog keeps what was typed; open/close stay balanced), 5 ("Cancel … back to the menu").
- Where: `frontend/ClipWebPageDialog.tsx:62-65` (`accepted` → `onDone`), `:78` (`onCreated={accepted}`), `:44-58` (Escape shortcut stays live during Create new), `:94`/`:102` (backdrop and X are not disabled while submitting); `frontend/ClipWebPageMenuItem.tsx:42-46` (`handleDone`). `ClipForm` disables only the URL input and Clip button while submitting.
- Reproduction R1: open, submit (createClip pending), press Close, reopen the row, type another URL, resolve createClip.
  Observed: `onDialogOpenChange.mock.calls = [[true],[false],[true],[false]]`, `onRequestClose` called once, the reopened dialog is gone with its typed URL; a later `ready` for job 7 toasts "Clipped: T" for the clip the user closed. Inside `AddButton`, `onRequestClose` is `closeMenu`, so the menu closes as well.
  Expected: after Close the user is back in the menu, and nothing closes the menu or a second dialog without a user action.
- Reproduction R3 (duplicate prompt): `findClipsByUrl` returns one job, press Create new (createClip pending), press Escape (the prompt's Cancel button is disabled while submitting, but the parent dialog's Escape shortcut still calls `onCancel`), resolve createClip.
  Observed: the dialog closes on Escape, then `onDialogOpenChange.mock.calls = [[true],[false],[false]]` and `onRequestClose` once, so the menu the user escaped back to closes by itself.
- No test cancels with a request pending.
- `[introduced]` (files created by this change).

### F2. A result that arrives before `POST /clips` returns is never announced, and can surface later as a stale toast
- Invariant: 6 ("its `failed` one error toast").
- Where: `frontend/ClipWebPageDialog.tsx:62-63` registers the id only after `createClip` resolves; `frontend/ClipNotifier.tsx:23-39` looks at the set only when `ready`/`failed` changes.
- Backend path: `app/routers/clips.py` `create_clip` awaits `worker.enqueue(...)` before returning 202. `app/services/worker.py` `_process` → `fetch_html` → `BlockedURL` → `_fail(permanent=True)` → `app/main.py` `_publish_fail` emits `knowledge.clip.failed`. A host that resolves to a private address, a likely target on a home LAN, fails at DNS without fetching anything, so the event races the 202 on its way through core's proxy. The timing was not measured (docker is forbidden). The frontend consequence was.
- Reproduction R2: submit, emit `knowledge.clip.failed {job_id:7}` while createClip is pending, then resolve it.
  Observed: `toasts() = {success:[], error:[]}` and the dialog is closed, so the user gets no word at all. Id 7 stays in `pending` for the life of the tab.
  R2b: same, then remount the notifier while that event is still `lastEvent` (the header slot remounts, e.g. around a catalogue reload). The error toast appears then, detached from the action.
  Expected: one error toast for the job, when it fails.
- Differs from known item (a): the event is not replaced. A mounted notifier sees it before its id is pending.
- `[introduced]` (files created by this change).

### F3. Under the global `next-intl` test mock the notifier's effects re-run on every render, so effect-dependency mutations survive and set mutations hang the suite instead of failing
- Invariant: 6.
- Where: `frontend/ClipNotifier.tsx:23-39` (deps `[ready, t, success]` / `[failed, t, error]`); core `frontend/src/test/setup.ts:78` builds a new `t` on every `useTranslations` call. Real `next-intl` returns a memoised `t`, so in production these effects run only when `ready`/`failed` changes.
- Mutations against `ClipWebPage.test.tsx` as shipped:
  - M09 (drop `ready` from the ready effect's deps): **live**, 66/66. In production the success toast never appears.
  - M01 (`take` → `has`), M03 (`take` always true), M10 (failed effect ignores the set), M11 (toast on every `ready`), M12 (ready effect ignores the set): **timeout** at 180 s. Each toast re-renders the provider, which gives a new `t`, which re-runs the effect and toasts again. The suite loops instead of reporting the broken assertion.
- Control: the same test file with a per-file `vi.mock("next-intl")` whose `t` is cached per namespace (same message lookup) is green (24/24 pristine), and M01s, M03s, M09s, M10s, M11s and M12s are all **killed** there.
- So the remount and "once" claims of invariant 6 are held only where the mock happens to match production. The one dependency mistake that ships a silent notifier (M09) is not held.
- `[introduced]` (the notifier and its test are new; the setup mock is pre-existing core).

### F4. Invariant 9's "display condition changes after opening, the dialog stays" is not held
- Invariant: 9.
- Where: `frontend/ClipWebPageMenuItem.tsx:50-51` (the row is gated on `drive`, the dialog on `open` only).
- Mutation M30: `{open && (` → `{open && drive && (`: **live**, 66/66. With it, a dialog open when the row's condition turns false unmounts without `onDialogOpenChange(false)`.
- Reproduction R4 (pristine): rerender with `drive=""` after opening → row gone, dialog still present. The code is right today and no test keeps it so.
- `[introduced]`.

### F5. Where the two new manifest entries live is not asserted: moving either to another slot passes every test
- Invariant: 1 (row drawn via the Add menu) and 6 (the notifier must be mounted to announce).
- Where: `manifest.json:16-18`, `:30-32`; `frontend/__tests__/manifest.test.ts` checks the count (10), the id→component wiring, and a slot placement for `knowledge-media-capture`, `knowledge-create-note` and `knowledge-new-note`, but not for the two new ids. `ClipWebPage.test.tsx` declares its own catalogue rather than reading the manifest.
- M47: move `knowledge-clip-notifier` from `header-actions` to another slot: **live**. With it, no Add-menu clip is ever announced.
- M48: move `knowledge-clip-web-page` from `folder-actions-menu` to `header-actions`: **live**. With it, the row leaves the Add menu and a menu-row component renders in the header.
- `[introduced]` (entries created by this change; the neighbouring New note entry has a placement test).

## Is anything missing from the invariant list
- **Closing the dialog while a request is pending.** No item says what happens then: whether the clip is still sent and announced, and that the late response must not close the menu or a dialog opened since (F1). Items 3/5 are written for a user who waits.
- **Order of result and acceptance.** Item 6 assumes the id is pending before the result arrives. Nothing states the case where the result comes first (F2), or that a toast must not appear long after the action through a remount (R2b).
