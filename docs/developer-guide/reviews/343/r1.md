## The three Chromium claims: measured

Probe: a `<video>` with one `<track default>` (label `seed`), left explicitly
`disabled`, then the track replaced by a second `<track default>` (label
`fetched`), the way React reconciles the `<track>` children when `subtitles`
goes from `[]` to one entry.

Chromium (the version Playwright ships in this worktree):

```
after seed:      seed:showing
after disable:   seed:disabled
at addtrack:     fetched:disabled
microtask:       fetched:disabled
task0:           fetched:showing
after 400ms:     fetched:showing
claimC: same-value mode write -> change handlers run 0 times synchronously,
        1 time after a task; the mode read inside the handler is the current one
```

All three claims hold as stated.

Robustness of claim B, which is the one the design rests on: 150 trials at
normal speed and 60 trials under `Emulation.setCPUThrottlingRate {rate: 20}`,
**210/210** read `showing` at `setTimeout(..., 0)` from inside the `addtrack`
handler. It is ordering, not a race: Chromium applies `default` in a task
queued ahead of the one the hook schedules.

Cross-browser (not asked for, but the guard turns "read too early" into a
silent no-op, so it is worth knowing):

| engine | at `addtrack` | at `task0` | after 500 ms |
|---|---|---|---|
| Chromium | disabled | showing | showing |
| WebKit | disabled | showing | showing |
| Firefox | disabled | disabled | disabled |

WebKit behaves like Chromium, so the fix holds on iOS/Safari. Firefox never
turns the replacement track on at all, so there is nothing for the hook to
undo there and the `state === "off"` read makes it a no-op. No finding.

### What the survivors mean

M6, M7, M9 and M13 are guards nothing exercises. None of them is wrong, and I
would not add tests for M6/M7/M13 — they are ordinary defensive code.

M9 is the one worth naming, because it is the guard that turns "read the mode
before the browser has applied `default`" into *silence* rather than into a
wrong write: if the read lands early the hook returns and captions come back
on. M4 is that failure mode, and it kills. The measurements above show it is
not a live race in either Chromium or WebKit — 210/210 including 20× CPU
throttling — so the survivor is meant to survive. Recorded so a later round
does not have to re-measure it.

M5 (`addtrack` → `change`) surviving is the one gap I would call a real hole in
the tests: `change` is what the subtitle track picker already listens on
(`NativeSettingsRows.tsx:159`), and a hook that reasserted a stored preference
on every mode change would fight the picker. Nothing here would catch that
substitution. It is not worth a test of its own; it is worth knowing.

### Why the browser spec cannot pass for the wrong reason

Three independent kills, each hitting exactly one case:

- M3 (no hook) fails only case 2 — so case 2 is about the hook.
- M8 (no null guard) fails only case 3 — so case 3 is about the unset
  preference, and case 3 is a genuine control: it is the one that would go red
  if the arrival stopped turning the track on for any reason.
- M16 (the arrival stops changing the track set) fails cases 2 and 3 — so
  neither can pass in a run where the arrival never happened.

The arguments are declared constants compared with `toEqual`, not derived from
the observation (Detector rule 5), and both labels are load-bearing (M14, M15).
The one fixed sleep, `SETTLE_MS`, sits behind an `expect.poll` on the thing
asserted (Detector rule 3) and is not load-bearing (M10).

`spec-viewport.spec.ts` and `componentFixtureParity.test.tsx` both take the new
name into a declared set compared with `toEqual` against a directory read — no
`>=`, no derived expectation. `popup-dismissal.test.ts` 456 → 457 matches the
one added source file.

## Findings

### 1. Invariant 1 is still open while the browser's own controls are drawn

`frontend/src/components/VideoPlayer.tsx:72`, `:263-274`

`useReassertCaptions` is called inside `LitloftVideoControls`, which is
rendered only under `playerUi === "litloft"`. Under the browser's controls the
hook is unsubscribed, so a subtitle track arriving with the detail answer turns
itself on even for a viewer who has a stored preference of off.

Reproduction, run in real Chromium against the change's own fixture
(`#player-captions`):

1. Open the arrangement. `["Auto-generated:showing"]`.
2. Settings → press the Subtitles switch. `["Auto-generated:disabled"]`,
   `aria-checked="false"`.
3. Press the "Browser controls" switch. `<video controls>` appears, the Litloft
   controls unmount.
4. Press the arrival button (the detail answer landing).

Measured: `["Japanese:showing"]`. The viewer who turned captions off is
watching with captions on.

Bounded, which is why this is not worse than it is: pressing "Use Litloft
controls" remounts `MediaControlsContainer`, whose mount effect
(`MediaControlsContainer.tsx:93-100`) reasserts the preference — measured
`["Japanese:disabled"]` immediately after.

`[pre-existing]`. On `9f5e0e1c` there is no hook on any surface, so the same
sequence gives the same result; the change narrows invariant 1 to one control
surface rather than opening a new hole. The hook's docstring reasons about the
browser-controls case explicitly, so a reader may believe it is handled — it is
declined, not handled, and the reason given (a preference asserted over the
browser's own captions menu would undo it) is sound.

For the supervisor: invariant 1 as written is unqualified, and this path
violates it. Either the invariant names the control surface, or closing it
means recording the viewer's choice made in the browser's captions menu —
which nothing does today, because that menu never writes `captionsPreferred`.

### 2. `rename` drops the subtitle list the same way `save` used to

`frontend/src/components/FileDetail/hooks/useFileDetailData.ts:162`

```
const updated = await renameFile(file.id, newFilename);
setFile(updated);
```

`renameFile` hits `PUT /files/{id}/rename`, which goes through the same
`_to_response` with no `subtitles=` argument as `PUT /files/{id}` does
(`backend/app/schemas.py:1015,1036`); only `GET /files/{id}` fills it
(`backend/app/routers/files.py:618-623`). So this is the identical shape the
change corrected fourteen lines above, left in place.

It is not a defect *today*: the same PR's `known-issues.md` entry records that
`detect_subtitles` matches on the video's basename and `rename_file` renames
only the video, so after a rename the sidecars really are detached and `[]` is
the truthful answer. It becomes a defect the moment the backend rename is
taught to carry the sidecars along, and nothing in the code says that this line
depends on that.

`[pre-existing]` — unchanged from `9f5e0e1c`. Ledger.

Invariant 1 survives this path anyway: the track set is replaced by the
generated fallback track (`VideoPlayer.tsx:250-259`), `addtrack` fires, and the
hook turns it off.

### 3. The drawn switch lags the player by up to one media-clock tick

`frontend/src/components/player/MediaControls/hooks/useMediaControlsState.ts:120`,
`frontend/src/lib/mediaClock.ts:27-28`

Invariant 4 says the switch's drawn state comes from the player. It does — via
a poll at `MEDIA_CLOCK_ACTIVE_MS = 250` while playing and
`MEDIA_CLOCK_IDLE_MS = 1000` while paused. Inside that window the drawn value
is the pre-press one, and `SettingToggle` sends `!checked`, so a second press
inside the window sends the same value again and nothing changes.

Measured, two presses of the Subtitles switch with no pause between them:

```
HEAD               : ["Auto-generated:disabled"]  aria-checked=false
with M2 applied    : ["Auto-generated:disabled"]  aria-checked=false
  (M2 = the direct mc.setCaptions removed, i.e. the parent's handler)
```

Identical, so `[pre-existing]`. With a settled wait between presses the switch
works in both directions (measured below under invariant 5).

Worth recording because it is the residue of the reported symptom: the change
removes the case where the switch is *permanently* inert (preference and player
state out of step for good); it does not remove the case where it is inert for
one tick. `useMediaControlsState` already has the pattern for this —
`pendingSeek` and `pendingVolume` hold the requested value until the poll
confirms it — and captions have no equivalent. Ledger.

## The declared invariants, one by one

1. **Off stays off while watching that file.** Held under the Litloft controls,
   on all three paths: the detail answer (case 2 of the browser spec, killed by
   M3 and M4); a rename (the track set is replaced by the generated fallback,
   `addtrack` fires, the hook turns it off); a title edit (no track replacement
   at all now, `useFileDetailData.seed` case, killed by M1 and M11). **Open
   under the browser's own controls — finding 1.**
2. **A viewer who has never chosen keeps each backend's default.** Held. Case 3
   of the browser spec is the control, and M8 kills it: removing
   `captionsPreferred === null` from the early return makes the hook write
   `setCaptions(null)` and the untouched default goes off. Firefox never turns
   the replacement track on at all, so nothing is asserted there either.
3. **A press always reaches the player, including for the stored value.** Held.
   The new `MediaControlsContainer` case stores `false`, has the controller
   report `on`, and asserts `setCaptions(false)` after the press; M2 and M12
   both kill it. Verified it targets the fix and not the mount effect: with M2
   applied the press changes no state, so the effect at
   `MediaControlsContainer.tsx:93-100` does not re-run and nothing reaches the
   controller.
4. **The drawn state comes from the player, not from the preference.** Held —
   `useMediaControlsState.ts:120` reads `mc.getCaptions()`, untouched by this
   change, and the new unit case asserts the switch draws *checked* while the
   stored preference is `false`. Freshness caveat in finding 3.
5. **A picker choice survives off and on again.** Held. Measured with a
   two-track fixture in real Chromium:
   ```
   picked English : ["Japanese:disabled","English:showing"]  switch=true
   switch off     : ["Japanese:disabled","English:disabled"] switch=false
   switch on      : ["Japanese:disabled","English:showing"]  switch=true
   picker radio   : English
   ```
   The mechanism is `selectedCaptionTrack` in `mediaController.ts:117,189-202`:
   `setCaptions(false)` records the showing index before disabling, and
   `setCaptions(true)` restores it. The change does not touch it; the extra
   direct call in the handler runs ahead of the effect and both are idempotent.
   No test covers this.
6. **A metadata edit does not cost a file its tracks.** Held for the title/
   description save (M1, M11 kill). Rename caveat in finding 2.
7. **Playback position and watch history untouched.** Held. Nothing in the diff
   reaches `usePlaybackProgress`, `WatchHistory` or the progress endpoints; the
   `save` merge changes only the `subtitles` field of the file object, and
   `duration` / `initialTime` still come from the answer.

## Is anything missing from the list?

Four things. None of them is a defect I found; they are places where a mutation
could change behaviour and no declared sentence would notice.

- **Which control surface invariant 1 is about.** As written it is false under
  the browser's own controls (finding 1). Either it names the surface, or the
  gap is real and someone has to decide to close it.
- **Nothing outlives the player.** The hook's `setTimeout` and its `addtrack`
  listener are both released on unmount and on a preference change
  (`useReassertCaptions.ts:50-53`), and M6 shows nothing checks it. A timer
  firing against a torn-down controller is the failure the `try/catch` two
  lines up exists for, so the two belong to the same sentence.
- **A press must leave the YouTube controller with exactly one reassert
  interval.** The change makes a single press reach `setCaptions` twice — the
  handler, then the mount effect. For the native controller that is harmless.
  For YouTube each call runs `reassertCaptionsOff`, which does
  `stopReasserting()` before starting a new `setInterval`
  (`mediaController.ts:281-296`), so it is still one interval — but that is now
  load-bearing and nothing says so.
- **How fresh "drawn from the player" has to be.** Invariant 4 is satisfied by
  a value up to a second old (finding 3). If a press inside that window is
  meant to work, the invariant should say so, and the switch needs the
  `pendingSeek`/`pendingVolume` treatment.
