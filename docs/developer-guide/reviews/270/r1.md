## Findings

### F1 [pre-existing, made reachable by this change] — knowledge's Create note dialog now renders inside the file menu box, not in the dialog host (proposed bucket: raise to supervisor; browser-check item for invariant 7)

`addons/knowledge/frontend/CreateNoteMenuItem.tsx` renders `<CreateNoteDialog>` → `FileSaveDialog`
in place; `FileSaveDialog` does not portal (`fixed inset-0 z-[100]` returned directly). So the
dialog is a DOM descendant of FileActions' `role="menu"` box, which is
`absolute z-30 w-40 overflow-hidden rounded-2xl`, inside FileActionRow (desktop inspector, file detail
page, and `MobileInspectorSheet` via FileMetaBlock).

Reproduction (probe K1, real row, SHA): open menu → Create note →
`screen.getByRole("menu").contains(dialog) === true`.

At parent `ee9717ce` the same flow never shows a dialog (probe P3/P6/P7/P8 with a stateful row fail
at `waitFor(dialog)` after 3 s; bundledRows fails under M4), so this placement has never been visible
to a user before this PR. The code is unchanged knowledge code at the same pin, hence `[pre-existing]`.

Contrast in the same addon: `NewNoteMenuItem.tsx` (the Add menu row) portals `FileSaveDialog` through
`useDialogPortalTarget()`. Core's own comment in FileActions on `CollectionPicker` states the risk
directly: "Opened from inside the mobile Bottom Sheet, a dialog rendered in place is buried by the
sheet it was opened from."

What jsdom cannot tell, and needs a real browser (desktop and <640px sheet):
- whether the `z-[100]` overlay escapes the menu's `z-30` stacking context enough to cover the page
  (sticky header, inspector, peek row);
- whether a transformed / `backdrop-filter` ancestor (vaul drawer) makes the "fixed" overlay
  sheet-sized instead of viewport-sized, or clips it;
- a11y: a `role="dialog" aria-modal` nested inside `role="menu"`.

Invariant 7 ("the dialog stays on screen, and its fields accept input") is green in jsdom only
because jsdom lays nothing out and `fireEvent.change` ignores hit-testing. Remedy belongs in the
knowledge repository (portal as NewNoteMenuItem does), not in this core diff.

### F2 [pre-existing] — the reset effect that invariant 5 depends on is not held by any test (proposed bucket A as a test gap against R-0 #5; pre-existing, so supervisor's call)

Mutation M5: `if (!menuOpen) setAddonDialogOpen(false);` → removed.
- SHA: full 25-file suite 497/497 pass (survived). Existing "recovers when an addon closes the menu
  without clearing its dialog flag" closes via `onRequestClose`, whose own body calls
  `setAddonDialogOpen(false)`, so it never exercises the effect (and M6b, removing that call instead,
  also survives — the two are each other's backup, so neither is held alone).
- Parent `ee9717ce`: same mutation, `FileActions.test.tsx` 44/44 pass (survived) → pre-existing.

Paths a user can hit where only the effect clears the flag: a row's dialog is reported open and the
menu then closes by (a) pressing the trigger (scrim disabled, so the click reaches the trigger's
toggle), or (b) choosing a core item such as Move to Trash while a non-modal row dialog is up.

Killing fixtures (pass at SHA, fail under M5):
- P3: stateful row → open dialog → press trigger (menu closes) → press trigger (reopens) → press
  `document.body` → expect menu gone. Under M5 the menu stays open.
- P4: stateful row → open dialog → click Move to Trash → cancel → reopen → outside press → expect
  menu gone. Under M5 the menu stays open.

### F4 [pre-existing] — `disabled={anyDialogOpen}` and `disabled={addonDialogOpen}` are indistinguishable to the suite, and the difference leaves a menu no press can close (proposed bucket B)

Mutation M2: `disabled={anyDialogOpen}` → `disabled={addonDialogOpen}`. Survives all 25 files plus
the probes P1–P8.

Not inert: probe P9 — press trigger → Rename (menu closes, stand-in rename dialog up) → press trigger
(menu reopens with `renameOpen` true) → press `document.body`. At SHA the menu stays open, and
Escape is also off (`menuOpen && !anyDialogOpen`); under M2 it closes. The parent rendered the bare
menu in the same state, so the behaviour is unchanged by this PR.

Reachability: the real Rename / Move / Confirm dialogs and CollectionPicker are `fixed inset-0 z-50`
overlays, so the trigger is not pointer-reachable while they are up; only a keyboard path to the
trigger (no focus trap) would reach it. Invariants do not specify this state. Recorded for the
ledger, not a fix request.

## Round-1 question: is anything missing from the invariant list?

1. **Placement of an in-place row dialog in a real browser.** #7 says "stays on screen", but every
   check of it is jsdom. Suggest an explicit browser item: Create note from the file `[...]` menu,
   desktop inspector and <640px inspector sheet, overlay covers the page and the fields take
   pointer input (F1).
2. **The second named user-visible case, intelligence's Index details.** The removed ledger row names
   it; no invariant or test runs the real `IndexDetailsMenuItem` in FileActions. Its dialog portals to
   the dialog host with its backdrop *outside* `role="dialog"`, so a backdrop press is an outside
   press that only `disabled` stops from dismissing — the shape dialogRow's stand-in approximates but
   does not replicate (stand-in has no backdrop sibling).
3. **A row dialog's own dismissal paths** (Escape, backdrop, Cancel) closing both the dialog and the
   menu with focus on the trigger. #5 covers `onRequestClose` but not that a row's Escape still
   reaches the row while FileActions' shortcut is disabled. Probes K1/K2 pass at SHA; nothing in the
   suite holds them.
4. **Pressing the trigger while a row's dialog is up** — currently closes the menu and drops the
   dialog (probe K3, real row: dialog gone, menu gone, next opening dismisses normally). Unspecified;
   likely unreachable by pointer behind a full-screen overlay, but worth stating either way.
