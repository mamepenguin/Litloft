## New findings

### N1 [pre-existing to c9b31c6a — introduced by b1dcf95d, missed in r1; c9b31c6a's key does not fix it] inv none (user-visible) — a document opened from any list never gets its capture controller
- Where: `FileDetailContainer.tsx` `useEffect(() => { setDocumentCaptureController(null); }, [fileId])`.
- What happens: `PdfPreview`/`TextPreview`/`MarkdownPreview` publish their controller in a mount effect (`useDocumentCapturePublisher`, `PdfPreview` `onDocumentCaptureController?.(store)`). When the file is seeded, the viewer mounts in the same commit as the container's `[fileId]` effect. Child effects run first, so the container's effect nulls the controller the viewer just published. The publisher's deps (`onController` is the stable state setter, `store` is memoised) never change, so it is never re-published.
- User effect: `addonSlotProps.documentCaptureController` stays null. The knowledge addon's `MediaCaptureAction` ("capture page" / "capture selection") returns `null` for a PDF/text/markdown opened from a folder, search, collection or history list.
- Measured with a presenter stub that publishes on mount, like the real viewers. Values are `cc` seen by the addon slot props for these cases: seeded open / unseeded open / in-place move to a seeded file:
  - `c4dae008` (before the PR): `f1` / `f1` / `f2`
  - `b1dcf95d`: `null` / `f1` / `null`
  - `c9b31c6a`: `null` / `f1` / `null` (the view does remount, `f1,f2`, and is still wiped)
  - Mutant C5 (that effect deleted) at `c9b31c6a`: `f1` / `f1` / `f2`. No test fails with it deleted, so nothing holds this either way.
- Note: with `key={fileId}` the old viewer's own cleanup already publishes `null` on a change of file. That effect is what breaks the seeded path, and it no longer prevents anything.

### N5 [introduced] inv none — watch-history seeds are not FileItem-shaped
- The backend's `WatchHistoryItemResponse` (`schemas.py`) has no `subtitles`, `deleted_at` or `missing_since`. So a file opened from Continue watching / history is seeded with `subtitles: undefined` while `FileItem.subtitles` is typed as required.
- Every current consumer defaults it (`VideoPlayer`/`ShellVideoPlayer` `subtitles = []`, `TranscriptSection` `EMPTY_SUBTITLES`, `useShellCaptions` via the player default), so nothing crashes. A video with its own subtitle files first renders the intelligence VTT fallback track and asks the transcript for the fallback, then switches when the answer lands.
- This is inferred from the schema and the consumer defaults, not measured in a browser. The type lie is what a future `file.subtitles.length` would trip on.

## Trajectory

**Yes.** This round adds states, branches and a prediction of the same kind the original commit added. Each one handles one more case the original's seed introduced and did not anticipate:
- States: `failed`, and the entry's `id`.
- Branches: the container's not-found branch, the id guard in `setFile`, the trashed/missing skip in `seedFiles`, and the fullscreen host's catch.
- Prediction: "an entry whose id is not the current file is the seed of the current file".

Mapping each addition to its case:
- The original added `fresh` because a seed may be stale. This round adds `failed` because a seed may not exist on the server.
- It adds the id key and the id guard because a seed may be shown under the wrong file.
- It adds the skip because a seed may be trashed, and the skip then needs an eviction it does not have (N4).

The one change that goes the other way is `key={fileId}`. It removes the kept-view state and returns to the pre-PR "one mount per file" shape. What it leaves out is instructive: container state above the key still assumes the old "file is null between files" ordering (N1). And the new id key now overlaps the old `cancelled` guards, so two mechanisms guard inv 7 and the tests see only one (N2).

Only one fix round exists, so this is not yet the "two in a row" pattern. But the shape of this diff is patching, not converging. One simpler shape may be worth the supervisor's attention: key the whole `FileDetailContent` on `fileId` at the hosts, or move the key above the hook. That would make the entry id, the id guard and the `[fileId]` resets unnecessary, since a stale callback into an unmounted instance is inert. The capture-controller reset effect would still have to go.
