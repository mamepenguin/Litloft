## Findings

### F1 [introduced] inv 8 — fullscreen host draws a 404'd file from its seed, indefinitely
- Where: `frontend/src/components/FileDetailFullScreen.tsx:51-63` (catch is a no-op), `frontend/src/components/FileDetail/hooks/useFileDetailData.ts:66-88` (catch swallows; `file` stays = seed, `fresh` stays false).
- What breaks: when a seeded file answers 404 (trashed or missing after it was listed/opened in this session), the fullscreen host (`/files/{id}?collection=…|folder_play=1`) keeps showing the list's copy as if the file existed: page row with its title/folder, the full view with its player (which then fails to stream), all controls inert forever. No not-found, no way out except Back. `RightPaneFile` is fine: its own `.catch` switches to the `notFound` state. The host comment "FileDetailContent below renders its own error state" is false both before and after: `FileDetailContainer` has no error state (it renders the skeleton/spinner on `file === null`).
- Reachable: every file ever opened is seeded (`getFileShared` seeds its own answer), and folder_play's `CollectionPanel` lists with `getDriveFiles`. Open a track in folder_play, trash it from the detail view (`onAfterDelete` → `router.push(folder)`), press Back → `/files/X?folder_play=1` (server route does not 404-check in collection mode) → the trashed file is drawn from the seed. Same for a track the scanner marks missing mid-session, reached by next/prev.
- Evidence (same repro, both trees; test file removed afterwards):
  - hook: seed `{id:f1,title:"trashed"}` + `getFileShared` rejects 404 → SHA: `file.title="trashed", fresh=false` after settle. Parent (no seed store): `file=null`.
  - host: FileDetailFullScreen, `folder_play=1`, seed present, `getFile(Shared)` rejects → SHA: page row text `Back main clips Trashed clip`, `FileDetailContent drive="main"`. Parent: no row (`null`), `drive=""`.
- Note: in the parent the fullscreen 404 path was a spinner forever (no not-found either) — that part is pre-existing; what this change introduces is drawing a trashed/missing file as live.

### F2 [introduced] inv none (3 holds) — page-row rename is live during the seed window and drops the user's input silently

- Test coverage: the seed hook test covers `rename()` returning early, but nothing covers the page-row affordance.

### F6 [introduced] inv none (proposed missing invariant) — the view tree, players included, now survives a change of file
- Where: `useFileDetailData.ts:66-68` (effect sets `file = seed` instead of `null` on a `fileId` change) → `FileDetailContainer.tsx:112` never takes the `!file` branch, so `FileDetailPresenter` and everything under it (ShellLayout, MediaCanvas, FilePreview, the players) is kept and re-rendered with the next file's props. No component in the tree is keyed on the file id.
- Why it matters: in the parent every change of `fileId` went through `file = null` → spinner → full remount, so no player or per-file component in the detail view ever saw its file id change while mounted. Now it happens whenever the next file is seeded: collection / folder_play next track and the media-session "next track" in `FileDetailFullScreen` (folder_play tracks are seeded by `CollectionPanel`'s `getDriveFiles`; any track opened before is seeded by `getFileShared`), and any in-place `?file=` switch in `RightPaneFile` (e.g. a related-file link) to a listed file.
- Measured:
  - FileDetailContent harness with FilePreview replaced by a mount counter; open f1, rerender with f2 (seeded, request pending). SHA: mounts 1 → 1, preview already shows `f2`. Parent (same, no seed): mounts 1 → 2, preview absent while pending.
  - `LoftPlayer` mounted for A (content resolved), fileId changed to B with the .loft read pending: the embed is rendered with `fileId=fileBBBBBBBB, url=https://youtu.be/AAAAAAAAAAA` — B's id on A's video. LoftPlayer's code for this is unchanged; what is new is that the detail view reaches it.
- Inferred, not measured (needs a real browser): media_import `YouTubeEmbed` rebuilds its player on `[fileId, videoId]`, so for that window it runs `usePlaybackProgress({ fileId: B })` over A's video: resume reads B's stored position and seeks A's video to it, and a periodic/teardown save in that window would write A's clock and A's duration into B's watch history (non-regenerable data). For `VideoPlayer`, `usePlaybackProgress`'s teardown save for A runs after the `<video>` `src` has already switched (media load resets `currentTime`/`duration`), so A's last < 5 s of progress is dropped instead of saved on a mid-play switch. The window is one .loft read / one detail GET; the exposure is narrow, the class is new.
- Proposed R-0 addition: "Moving to another file inside a mounted host never attributes the previous file's player state (position, duration, content) to the new file id."

### F9 [introduced] inv none — player box ratio is always 16:9 while loading

A non-16:9 embed or a `GenericLinkCard` .loft changes height when content lands. Layout only; jsdom cannot hold it; ask whether the deviation was intentional.

## Is anything missing from the invariant list?
Yes, one item (F6): "Moving to another file inside a mounted host never attributes the previous file's player state (position, duration, content) to the new file id." Before this change a change of file always remounted the view, so the list did not need it; now a seeded next file keeps the tree. Secondary (F2): an action a viewer can start during the seed window is either blocked visibly or applied, never silently dropped.
