## 2. New findings

### N1 — the guard closes the "DB has no picture" case, not the "picture is gone" case, and for a `.loft` that state never heals

`[introduced]` · invariant 3 · `frontend/players/YouTubeEmbed.tsx:511-524`

`posterUrl` is `file.has_thumbnail ? getThumbnailUrl(file.id) : undefined`
(`frontend/src/components/FilePreview.tsx:101`), and `has_thumbnail` is
`file.thumbnail_path is not None` (`backend/app/schemas.py:1028`) — a DB column,
not a fact about the disk. The route has a second fall-through to the
placeholder that the fix does not close:

```
backend/app/routers/files.py:1176-1186
    if file.thumbnail_path:
        thumb_path = _validate_path(...)
        if thumb_path.exists():
            return _revalidating_image(request, thumb_path)
    if PLACEHOLDER_THUMBNAIL.exists():
        return _revalidating_image(request, PLACEHOLDER_THUMBNAIL)
```

So with `thumbnail_path` set and the JPEG absent, `has_thumbnail` is `true`,
`posterUrl` is defined, the cover is drawn, and the response is the same grey
320x180 `backend/app/static/placeholder.jpg` the commit message says it fixed —
a grey card over the player until ready, then fading out.

For most file types the scanner repairs this: `scanner.py:438-443` calls
`_relocate_thumbnail` whenever `(THUMBNAILS_DIR / expected_thumb).exists()` is
false, which regenerates or sets `thumbnail_path = None`. That branch is gated
on `gen_fn is not None`, and `get_thumbnail_generator` returns `None` for a
`.loft` **first, before any other test** (`thumbnail.py:527-528`). A `.loft`
therefore never enters the repair branch, so once its `thumbnail_path` points at
bytes that are gone, it stays that way: grey card on every open, permanently.

Reachable when anything removes files under `data/thumbnails` out of band — a
partial `data/` restore, a volume swapped without the thumbnails, a manual
clean-out. Not reachable through any endpoint (`admin.py` only *measures*
`THUMBNAILS_DIR`; there is no clear-cache route).

Secondary effect of dropping `onError` in the same hunk: on a request that
genuinely errors rather than falling back (placeholder.jpg itself missing → the
route raises 404; offline), the browser's broken-image mark is now drawn over
the player at `opacity-100` where before it was hidden. Low reachability, but it
is the case the deleted handler existed for, and nothing replaced it.

Reproduction: read `files.py:1176-1186`, `schemas.py:1028`, `thumbnail.py:527`
and `scanner.py:438` against `YouTubeEmbed.tsx:511`. At `03633c0` the cover was
unconditional, so this state was a strict subset of F2 — the fix narrowed F2
without reaching this branch of it.

### N2 — the rebuild the new test drives cannot happen; the one that can is untested

`[introduced]` · invariant 5 · `frontend/players/__tests__/YouTubeEmbedPlayer.test.tsx:211-232`

"covers the frame again when the player is rebuilt for another video" rerenders
the same mount with a different `url`. Nothing in the app does that: `url` comes
from `LoftPlayer`'s one-shot fetch keyed on `fileId`, and a `fileId` change
remounts through `FileDetailContent`'s `key`. The player effect's other deps are
`onMediaController` and `isInterrupted` (both stable — round 1 measured this) and
**`youtubeUi`**, which is the only one a user moves.

And `youtubeUi` moves more often than the toggle: `useYouTubeUiPreference`
starts `false` and hydrates from `localStorage` in an effect
(`useYouTubeUiPreference.ts:25-32`), so a viewer who has chosen the YouTube skin
gets a rebuild on **every** first open as well as on every toggle.

Mutation M11 — gate the cover on `!youtubeUi` as well as `posterUrl` — leaves
46/46 green. That deletes the cover outright for the whole YouTube-UI skin (the
first build *and* the rebuild), which is the state round 1's F3 was measured in,
and the suite does not notice. `mountPlayer` (`:93-111`), which every test in
the "player UI choice" block uses, passes no `posterUrl`, so no test in that
block can see the cover at all.

The code is right — the observation quoted under F3 above shows the cover
present and opaque in the YouTube skin and across the toggle. Only nothing holds
it. Round 1's F4 pointed at the "player UI choice" block ("the assertion has
somewhere to live", `:716-737` clicks exactly that button); the fix built a
synthetic trigger beside it instead.

### N3 — a class-substring assertion passes while the cover is invisible or outside the frame

`[introduced]` · invariant 1 · `frontend/players/__tests__/YouTubeEmbedPlayer.test.tsx:176-196`

The suite asserts `opacity-100` / `opacity-0` / `pointer-events-none` as
substrings of `className` and nothing about where the element is. Two mutations
that make the cover do nothing at all leave 46/46 green:

- **M12** — move the `<img>` **before** the `hostRef` div. Both are `absolute
  inset-0` with no `z-index`, so the later one paints on top: the iframe now
  covers the cover and the black flash the change exists to remove is back.
- **M13** — move the `<img>` out of the frame entirely, below the closing
  `</div>`, where `absolute` resolves against a wrapper that is not
  `relative`. The cover is somewhere else on the page.

This is the residue of F1 rather than a regression: at `03633c0` there was no
opacity assertion of any kind, so the same mutations live there too. Worth
recording because the fix's own comment calls the classes "the behaviour" —
they are half of it; the other half is DOM order inside `player-frame`, and that
is cheap to assert (`frame.children`, or that the cover is the frame's last
`<img>`) without needing a browser.

### N4 — `src={posterUrl}` is not held: the expected value is the URL the old code built

`[introduced]` · invariant: none · `frontend/players/__tests__/YouTubeEmbedPlayer.test.tsx:173, 182`

`POSTER` is `"/api/files/abc123456789/thumbnail"` — byte-identical to
`getThumbnailUrl("abc123456789")` (`lib/api.ts:343-345`). **M6** reverts
`src={posterUrl}` to the hardcoded `` `/api/files/${fileId}/thumbnail` `` while
keeping the guard, and 46/46 stay green. The test cannot tell "reads the prop"
from "rebuilds the same string from `fileId`", because the expected value is the
observation the previous implementation produced (`review-workflow.md`, detector
rule 5). No behavioural weight today — core's `posterUrl` *is* that URL — but the
prop is the contract the change was made for, and the day core hands a different
poster (a remote one, a cache-busted one) the cover would silently ignore it.
A distinct fixture value (`"/poster-for-this-test.jpg"`) fixes it.

### N5 — the embed-restricted card still draws the placeholder over a pictureless file

`[pre-existing]` · invariant 3 · `frontend/players/YouTubeEmbed.tsx:448-450`

The 101/150 branch draws `` src={`/api/files/${fileId}/thumbnail`} `` at
`opacity-40` behind the "watch on YouTube" message. For a file with no
thumbnail that is core's grey placeholder at 40% — exactly the defect F2 named,
in the sibling branch, unchanged. It predates the cover entirely
(`git show f17e4bf:frontend/players/YouTubeEmbed.tsx` line 442 is identical), so
it is not this change's to fix; but this commit is the one that brought
`posterUrl` into the component, and the branch is three lines from it.

## 4. Checked, no finding

- **`posterUrl` is the video's own picture for a `.loft`**, not something else.
  `media_import/backend/service.py:897` calls `_save_loft_thumbnail` with
  `_pick_video_thumbnail_url(info)` from yt-dlp plus a canonical
  `i.ytimg.com/vi/<id>` fallback chain (`:117`, `:603-625`); it sets
  `File.thumbnail_path` only on a successful download (`:587-596`). The avatar
  downloader (`:532-546`) writes subscription avatars, never a file's thumbnail.
  A `.loft` whose thumbnail download failed has `thumbnail_path` NULL, so
  `posterUrl` is undefined and no cover is drawn — invariant 3 holds for the
  common case.
- **Core does hand the prop to this embed, and only this embed's host.**
  `FilePreview.tsx:107-118` is the sole `LoftPlayer` caller;
  `registerMediaImportPlayers.ts:18` is the sole `YouTubeEmbed` registration.
  Both sides are tested in core (see the F2 row).
- **Pseudo-fullscreen does not rebuild the player**, so the cover cannot reappear
  on entering it: `useFullscreen` only swaps the frame's classes, and the player
  effect's deps (`fileId`, `videoId`, `onMediaController`, `isInterrupted`,
  `youtubeUi`) contain nothing from it. Round 1's note that a rebuild *inside*
  pseudo-fullscreen stretches a 16:9 cover across the viewport under
  `object-cover` is unchanged by this commit and still needs a real browser to
  size; the only reachable rebuild there is the `youtubeUi` toggle, whose button
  lives outside the frame and is not reachable while pseudo-fullscreen is on.
- **Nothing is drawn over the cover during the covered phase.** `MediaControls`
  renders after it in DOM order, but it is gated on `activeMc`, which is null
  until `onReady` — the same event that flips the cover to `opacity-0` — and it
  is not rendered at all when `youtubeUi` is true. After ready the cover is
  transparent and `pointer-events-none`. Invariant 6 holds.
- **Invariant 4 holds.** M10 kills; the 101/150 path returns before the cover is
  reached (`:439-466`), and `loadFailed` returns `null`.
- **No orphaned assertion on the removed attribute.** `data-covered` appears
  nowhere under `frontend/src`, `frontend/e2e-layout` or any addon's `frontend/`.
- **The prop makes the addon depend on core ≥ #328.** `LoftEmbedProps.posterUrl`
  is declared in core (`components/loft/types.ts`), so this addon commit does not
  typecheck against a core that lacks it. Fail-loud, not silent — but it inverts
  `CLAUDE.md`'s usual order: core must land before the media_import pointer bump,
  not after.

## 5. Trajectory

**This round removes a prediction; it does not add one.**

`03633c0` added one state (`playerReady`), one always-rendered `<img>`, a
two-direction opacity transition, a mirror attribute (`data-covered`), and an
`onError` handler that existed for a **predicted** response — "a file with no
thumbnail would otherwise show the browser's broken-image mark". That prediction
was false; the route answers 200.

`8814b33` deletes the mirror attribute, deletes the `onError` handler and the
comment that justified it, and replaces the unconditional render with a
condition whose truth is **measured in core** (`file.has_thumbnail`) rather than
guessed at in the addon. Net over the two commits: one branch removed (the error
handler), one added (the render guard), one prediction removed, no new state, and
the transition narrowed from two directions to one. Neither commit's fix handles
a case the other's fix also handled.

Per `review-workflow.md` R-4 that is the shape of a loop converging, not of a
design being patched. The one thing to watch is N1: it is the same defect class
as F2 in a branch the fix did not reach, so a third round that adds *another*
guard for the bytes-gone case would be the second round in a row handling one
more instance of "the thumbnail route lies" — at which point the right fix is
probably in the route or in `has_thumbnail`, not in the embed.
