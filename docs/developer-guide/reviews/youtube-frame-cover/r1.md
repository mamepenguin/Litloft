## F1 — every visual behaviour this commit adds survives deletion

`[introduced]` · invariants 1, 5 · `frontend/players/YouTubeEmbed.tsx:514-518`,
`frontend/players/__tests__/YouTubeEmbedPlayer.test.tsx:162-195`

The two new tests assert `data-covered`, an attribute that exists only for
them. It is a second encoding of `playerReady` and it renders nothing. The
attribute that actually produces the cover — the `opacity-0` / `opacity-100`
ternary and `transition-opacity duration-200` — is asserted by nothing.

Three mutations, each of which destroys the change's entire purpose, leave the
suite at 43/43:

- `"opacity-0"` always → the cover is never visible; the black flash the
  commit exists to remove is back, and the measurement table's "before" row is
  what ships.
- `"opacity-100"` always → the cover never lifts; the thumbnail permanently
  hides the playing video. This is the worst reachable state of the feature and
  CI is green on it.
- transition removed → a hard cut instead of a fade, i.e. the middle row of the
  commit's own measurement table (~80 ms of black).

Per `review-workflow.md` R-4, a test that lets an A through is an A.

Remedy shape: assert the classes that do the work, and drop `data-covered`
rather than assert on it — a mirror attribute cannot fail when the thing it
mirrors stops being wired to anything.

Reproduction: apply any of the three edits above to `YouTubeEmbed.tsx:514-518`,
then `pnpm vitest run src/addons/media_import/players/__tests__/YouTubeEmbedPlayer.test.tsx`.
Parent `f17e4bf` has neither the code nor the tests, so `[introduced]`.

## F2 — a file with no thumbnail is covered by core's grey placeholder, not by nothing

`[introduced]` · invariant 3 · `frontend/players/YouTubeEmbed.tsx:509, 519-523`

The cover requests `/api/files/{fileId}/thumbnail` unconditionally. That
endpoint does not 404 when the file has no thumbnail:

```
backend/app/routers/files.py:1176-1186
    if file.thumbnail_path: ... return _revalidating_image(...)
    if PLACEHOLDER_THUMBNAIL.exists(): return _revalidating_image(request, PLACEHOLDER_THUMBNAIL)
```

`backend/app/static/placeholder.jpg` is a real 320x180 greyscale image
(luminance range 70-165 — a grey card, not black). So:

1. the `onError` handler never fires on that path; and
2. what the viewer gets is a grey placeholder card covering the whole player
   region until the player is ready, then fading out. Invariant 3 says a file
   with no thumbnail "looks as it did before" — before, that region was the
   player's own black.

Every other core surface gates on `file.has_thumbnail` before it will render a
thumbnail: `frontend/src/components/FilePreview.tsx:101`, `FileCard.tsx:74`,
`JustifiedFileCell.tsx:63`, `RelatedFileRow.tsx:18`, `PropertiesPanel.tsx:255`,
`CollectionItemsPane.tsx:124`. This cover is the only place that does not.

The comment at `YouTubeEmbed.tsx:520-521` ("would otherwise show the browser's
broken-image mark") states a thing the backend cannot produce for a reachable
file. That is the prose kind R-3 says to report: it is why the gap is
invisible. Remedy is deletion, alongside the code fix.

Reachable when: a `.loft` opened between import and thumbnail generation, an
import whose thumbnail fetch failed, or a `.loft` file placed in a drive by
hand.

Suggested shape (cross-repo, core side): `LoftEmbedProps` gains `posterUrl`;
`LoftPlayer` forwards the `posterUrl` it *already receives and already uses*
for its own loading placeholder (`components/loft/LoftPlayer.tsx:22, 32, 57`);
the cover renders only when it is defined. That removes the imperative
`style.display` write as well.

Reproduction: read `files.py:1176-1186` against `YouTubeEmbed.tsx:509`. At
`f17e4bf` the non-restricted branch contains no `<img>` and makes no such
request, so `[introduced]`.

## F3 — on a rebuild the cover fades IN, over black, for 200 ms

`[introduced]` · invariant 5 · `frontend/players/YouTubeEmbed.tsx:516-517, 397`

Measured in jsdom (observation test, since removed): after clicking "Back to
the Litloft player", the poster is **the same DOM node**, and its class goes
from `… transition-opacity duration-200 opacity-0` to
`… transition-opacity duration-200 opacity-100`. The transition is on in both
directions, so the cover animates 0 → 100 over 200 ms.

Underneath it, the effect cleanup has already run `host.replaceChildren()`
(`:397`), so the frame is `bg-black` for that whole ramp. The rebuild therefore
shows black → thumbnail → black-free player, where the first open shows
thumbnail → player. The commit's measurement table covers only the first open.

Same node also means: no second network request on a rebuild (good), and the
inline `display:none` from F2's handler persists across the rebuild (measured:
`style.display === "none"` before and after) — correct for a thumbnail-less
file, but it is a latch that only a remount clears.

Related, same path: in pseudo-fullscreen the frame is `fixed inset-0` with no
aspect shim, so a rebuild there stretches a 16:9 thumbnail across the viewport
under `object-cover`, cropping it.

Sizing this needs a real browser (R-4: jsdom lays nothing out). Remedy shape:
carry the transition only on the uncovering state.

## F6 — the cover has no upper bound on its lifetime

`[introduced]` · invariant: none (see "anything missing") ·
`frontend/players/YouTubeEmbed.tsx:160, 289-291, 342-344`

`playerReady` is lifted only by `onReady` or `onError`. If the API script
loads but the player reports neither — iframe blocked, network lost after the
script, a `YT.Player` that never initialises — the thumbnail stays at opacity 1
over the frame for the life of the mount. It is `pointer-events-none`, so
YouTube's own controls remain clickable *underneath an opaque image*: the
viewer can hear audio and cannot see the picture, and nothing in the UI
explains it. There is no timeout and no other exit.

Before this commit the same stall showed a black frame, which is at least
honest about nothing having loaded.

## Checked, no finding

- **A change of file cannot leak state.** `FileDetailContent` renders
  `<FileDetailContainer key={props.fileId} …>`
  (`frontend/src/components/FileDetailContent.tsx:14`), and both hosts
  (`FileDetailFullScreen.tsx:171`, `folder/RightPaneFile.tsx:115`) go through
  it. So the whole player remounts on a file change: neither the latched
  `display:none` nor a stale `playerReady` can reach the next file. Without
  that key, F2's handler would blank the next file's cover permanently.
- **The cover cannot come back mid-playback.** The player effect's deps are
  stable in practice: `isInterrupted` is a `useCallback([])`, and
  `onMediaController` is a `useCallback` chain rooted in a prop that the
  collection host leaves undefined.
- **Error paths.** 101/150 → the `embedRestricted` branch replaces the frame
  entirely and draws its own thumbnail at `opacity-40`; other codes → the cover
  lifts and YouTube's error screen shows (M5, M10 both killed). `loadFailed` →
  the component returns `null`, so no cover survives. Invariant 4 holds.
- **Nothing walks the frame's children.** No `querySelector` in
  `components/player/hooks/useFullscreen.ts`, `components/player/MediaControls.tsx`
  or `lib/mediaController.ts`; `globals.css` only reaches
  `.media-detail-player > :first-child`, which is above this node. Adding a
  child between the host and `MediaControls` changes no stacking: `MediaControls`
  still renders after it, and during the covered phase it is not mounted at all
  (`activeMc` is null). Invariant 6 holds.
- **No extra request for a file that has a thumbnail.** The hardcoded URL is
  byte-identical to `getThumbnailUrl(id)` (`lib/api.ts:343`), which
  `LoftPlayer`'s loading placeholder has already fetched.
- **No `player-poster` testid collision** anywhere in core or the addons.

## Anything missing from the invariants list?

Two things, both about states the list does not name:

1. **A bound on the cover's lifetime.** Invariant 5 covers "uncovered again
   when it is ready" but nothing covers "never becomes ready". F6 is
   unreachable by the current list, which is why no mutation could target it.
   Suggested sentence: *the cover is never the last thing on screen — a player
   that reports neither ready nor error still ends with the frame uncovered.*
2. **The rebuild's direction.** Invariant 5 says a rebuilt player is "covered
   again", which F3 satisfies while looking wrong. Suggested sentence: *a
   rebuild covers the frame at once; the thumbnail is never seen fading in from
   black.*

Invariant 3's phrasing ("looks as it did before") was the right kind of
sentence and is what made F2 findable — it is violated, not missing.
