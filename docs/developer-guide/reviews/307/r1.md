## Findings

### F1 [introduced] Low — two drives sharing a container path share one set of addon switches
Invariant: 2 (a choice made for one drive changes another drive), arguably 1.
`SetupWizard.tsx` keys `addonChoices` by `d.path`. When two drives in `drives.json` have the same `path`, both drives' switches read one entry. `setAddonPolicy` also writes both names to the same key, and the last one wins in `Object.fromEntries`. The two drives can then never be set independently. Reproduction: P1 above, compared against the parent. The backend does not reject duplicate paths (`_validate_drives_payload` checks only duplicate names).
Reachability: low. `seed_drives_from_mounts` produces unique paths. A hand-authored `drives.json` with entries is migrated to `setup_completed` and never reaches the wizard. Only a hand edit made after the auto-seed and before finishing `/setup` reaches this. `DriveStep` already uses `key={drive.path || index}`, so the wizard assumed unique paths before this change too. Options for the supervisor: accept, or key by the drive's index, which the wizard never reorders.

### F2 [introduced] Medium (test gap) — no test finishes the wizard while the addon list is failed
Invariant: 4 ("nothing is saved that disables an addon"), and the doc promise "Continuing without it saves nothing".
The only failed-list test goes to the summary, checks the text, goes Back and retries, and never presses Finish while failed. M15 (while failed, save a policy that turns `knowledge` off on every drive) and M14 (throw on Finish while failed) both survive. The code is correct today (P2: PUT `{}` and completes). No test holds that, so an A-class regression of invariant 4 would pass CI.

### F3 [introduced] Low — while a Retry is in flight the summary claims `0 addon(s)`
Invariant: 4 (its spirit; the list has not failed *yet*).
`retryAddons` clears `addonsFailed` before the request resolves, and `addons` is still `[]`. During that window the step shows "You can skip and configure later" with no pending indicator, and `addonOnCount` is `0`. P3: a hung retry followed by Skip leaves the summary at `0 addon(s)` while every addon is enabled. If the retry later fails, the summary flips to "defaults". If the user presses Finish first, `{}` is saved, which is harmless. The same window exists for the *initial* load on the parent (`[pre-existing]`). The retry path is new code. Race against a successful retry: not reachable, because Retry is rendered only when `addonsFailed`, so at most one request is in flight and the earlier one has already settled.

### Pre-existing (named in the brief)

- **[pre-existing] `handleBeforeSubmit` ignores failed PUT /drives, PUT /passwords (and POST /auth/unlock) responses.** This change does **not** make it more reachable, but it changes what the user sees in one sub-case. If the drives PUT fails (for example `duplicate_name`, empty name, `path_not_found`) **and** the user renamed a drive **and** turned a switch on that drive, the policy PUT names the new name. The backend now answers `unknown_drive`, and the wizard shows "drive 'X' is not configured" and refuses to finish. Before this change the wizard finished silently. The message names the wrong cause. With no switch touched (policy `{}`), a failed drives PUT still completes setup with the drives unsaved, the same as on the parent. As written, invariant 3 ("A rejected drives/passwords … save is shown") is violated by this pre-existing path. The supervisor should decide whether the list keeps that wording.
