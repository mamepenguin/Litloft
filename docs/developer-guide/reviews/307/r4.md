## Findings

### F1 [introduced reach of a pre-existing inconsistency] Medium — Public Finish now wipes passwords while keeping the drives' `access_group`s; on the documented re-run path this locks everyone out
Invariant: none declared is broken (#11 asks for exactly `[]`); raised as a **bucket C candidate** for the supervisor.

- The wizard submits `drivesForSubmit = drives` unchanged in both modes; public mode does not clear `access_group`.
- `setup-status` pre-fills each row's `access_group` from `drives.json` while setup is incomplete, and `accessMode` defaults to `"public"`.
- `docs/getting-started/first-run-setup.md:9` tells the operator: "To re-run setup later, delete the sentinel and reload `/setup`."
- Re-run on an install with protected drives, leave the default Public, Finish:
  - drives are saved with their groups, passwords `[]`, complete-setup 200 (P2);
  - afterwards the protected drive is 404, `GET /api/admin/config/drives` is 403, and `PUT /api/admin/config/drives` is 403 — nobody can unlock, nobody can write; recovery is editing files on disk.
- At the parent (0e86ebcc) and develop, public Finish did not PUT passwords (the parent test asserted `passwordCall` undefined), so the existing passwords survived and the operator could still unlock. That difference is what this commit introduces.
- The fresh-install variant — the user types a group in the drive step, then leaves Public — produces the same lockout on develop (`drivesForSubmit = drives`, default `"public"`, passwords stays `[]`). That part is `[pre-existing]`.
- Shape question, not decided here: does "Public" mean "no `access_group`s" (strip or block them), or does public mode leave `passwords.json` alone when groups remain? Either is a design decision about what the access-mode step means, not one more case in the save sequence.

### F2 [introduced] Low (test gap, inv #3 / #11) — a failed public `[]` save is not held as stopping Finish
- FM5b (swallow the passwords PUT in public mode only) lives with 81/81 green.
- The only rejected-passwords test is protected-mode. The public `[]` body cannot fail validation, but it can fail with 500 `write_failed` (disk, EBUSY on a mis-mounted file). Swallowed, complete-setup would proceed and a planted or leftover `__admin__` password would survive the "successful" Finish — the exact state inv #11 forbids.
- The code is correct today (it `await`s `putPasswords`, which throws). What is missing is a public-mode variant of the rejected-passwords test.

### F3 [pre-existing] Info — the first-run window can still be closed by an attacker who calls `complete-setup` after a plant
- The first-run gate is exactly `setup_completed` absent (`_admin_or_first_run`); it never consults `is_admin`, which is why the owner's anonymous writes still pass after an `__admin__` plant (test (b), BM2).
- An attacker who plants `__admin__` and then calls `complete-setup` locks the owner out: both owner writes 403 (P1).
- The same outcome was available on develop with a drive group plus a group password plus `complete-setup` (P1b), so this commit adds no capability; 0e86ebcc shortened the route by one request. Already recorded as the round-3 race; one line here as asked. It is a design question about the unauthenticated first-run window (bucket C territory), not a defect of fda544a4.

## Trajectory answer

The four fix diffs in order:
- **dd40eadf** adds state (`addonChoices`, `addonsFailed`, retry) and a stop branch for a rejected policy save.
- **f574831a** repeats that stop branch for drives and passwords — the same kind of addition as round 1.
- **0e86ebcc** adds no wizard branch or state; it removes a contradiction in the backend validator (`__admin__` assignable) via one helper.
- **fda544a4** removes the `if (accessMode === "protected" && password.password)` guard around the passwords PUT. The mode still selects the body, but the save sequence now has one path instead of two, and nothing predicts what earlier writers left behind. Source diff +10/−10.

Plainly: the last two rounds removed or unified rather than added, so the loop is **converging**. No round after f574831a added a branch, a state or a prediction.

What remains is not a defect of this commit's mechanism but two design questions about the first-run surface: what "Public" means when drive rows still carry groups (F1), and an unauthenticated window that anyone on the LAN can close (F3). Answering either by adding another conditional to `handleBeforeSubmit` would restart the patching pattern; they belong to the supervisor as C candidates.

## Checked, no finding

- **Authorisation after a plant, before completion.** Gate is `setup_completed` absent only; owner's anonymous drives/passwords/policy/complete-setup all 200 after the plant (test (b); BM1, BM2 killed).
- **Replay after completion.** A fresh anonymous client replaying drives + passwords `[]` after a protected completion gets 403/403 and the file is unchanged (P3). `/setup` itself does not redirect when completed, but `setup-status` then returns `drives: []` and DriveStep's Next is disabled with no drives, so the Finish step is not reachable from a fresh load. A stale tab opened before completion can replay only if the caller is already admin, who could make the same writes from `/admin/settings`; its drives PUT (pre-existing) is the larger overwrite.
- **Protected mode, validator sees the just-saved drives.** `put_passwords` reads `_read_drives_from_disk()` per request after `put_drives` wrote atomically; `family` is 422 before the drives PUT and 200 after (P4). Order held by FM3.
- **Empty password in protected mode.** Removing `password.password` from the PUT guard cannot send `""`: PasswordStep's Next requires `password.trim().length > 0`, and any later Back to the step re-imposes it. A whitespace-only password is blocked by the same `trim` check.
- **Auto-unlock and redirect.** Unchanged by this diff. Public: after `[]` everyone is admin again, `/admin` loads (test (b) asserts `GET drives` 200). Protected: unlock before complete-setup, as before. The unlock response is not checked — identical on develop, `[pre-existing]`, not re-raised.
- **Switching-to-public test** drives a real failed protected Finish (policy 500), goes Back three steps, picks Public, and asserts both password bodies in order: the protected entry, then `[]`. FM1, FM2, FM4 kill it.
- **F2/F3 tests from round 3** now hold: BM3/BM3b (near-miss, put and append) and BM4 (no declared group) killed.
- **Protected mode replaces other passwords.** A protected re-run writes exactly one entry, discarding any other passwords; this is inv #11 as declared, and the doc line 69 now says so.
- **Docs.** `first-run-setup.md` step 2 and the Public bullet match the code. They do not mislead toward an insecure configuration; F1's lockout is a failure-closed outcome, not an exposure.
- **Comments.** The two new comment lines in `handleBeforeSubmit` describe the why and match the code.
