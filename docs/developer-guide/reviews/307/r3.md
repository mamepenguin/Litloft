## Findings

### F1 [introduced] Medium (security) — a password planted in the first-run window now survives a public-mode setup and locks the owner out of /admin
Invariants: none of #1–#10 names this. It is a security finding raised to the supervisor for triage.

What happens:
- While `data/setup_completed` is absent, `PUT /passwords` and `POST /passwords/append` are unauthenticated (`_admin_or_first_run`). That is the documented, intended window.
- With this commit, anyone on the LAN can write `[{password, ["__admin__"]}]` at **any time before the owner finishes**. They do not have to race the owner.
- The public-mode wizard never rewrites `passwords.json`, and the wizard never displays it (`setup-status` returns drives only). So the entry survives the owner's own successful finish.
- `is_admin()` sees no protected drive but a configured `__admin__` password. The owner gets 403 on /admin, and the planter holds admin (P1).
- Recovery is hand-editing `passwords.json`, because every GUI password write now needs admin.

Why it is `[introduced]`:
- The same plant at the parent and at develop is 422 (P1).
- The pre-existing route, a drive group plus a password, is undone by the owner's own drives PUT (P1b).
- What stays pre-existing is the race itself: an attacker who calls `complete-setup` or writes config *between* the owner's drives PUT and the owner's finish could lock the owner out before this commit too. That needs timing; the new plant needs none.

A benign reach of the same shape:
- A protected Finish saves drives and passwords, and then a later save is rejected (policy save or unlock).
- The user goes Back, picks Public and finishes.
- /admin stays gated by the password they typed and did not end up choosing.
- The same happens when an operator deletes `setup_completed` to re-run the wizard in public mode on an install that already has an `__admin__` password.

Shapes the supervisor may weigh (not decided here):
- the public wizard also writes `passwords.json` as `[]`;
- `complete-setup` refuses, or the wizard warns, when passwords exist that the wizard did not write;
- accept the window as is.

### F2 [introduced] Low (test gap, inv #9) — nothing holds `__admin__` being assignable when no drive declares an access_group
Invariant: #9. A protected first run with every drive public sends `groups: ["__admin__"]` (P2). Round 2 found the 422 for exactly this body.

- The code is correct today (P2). What is missing is a case in the parametrized test, or the integration test, with no `access_group`.

### F3 [introduced] Low (test gap, inv #10) — case and whitespace variants of the sentinel are not held as rejected

- M8, a normalising comparison, lives. It would accept and write `__ADMIN__`.
- `auth.is_admin` does not treat `__ADMIN__` as admin. An operator who typed it would get a saved "admin password" that grants nothing, and /admin would stay open to everyone when no drive is protected.
- Current behaviour is correct (P3). No test pins it.

## Trajectory answer

The three diffs in order:
- **dd40eadf** adds state (`addonChoices`, `addonsFailed`, retry) and a stop branch ("a rejected policy save ends completion").
- **f574831a** extends that stop branch to the drives and passwords saves. It adds no new kind of case, but it repeats round 1's branch.
- **0e86ebcc** adds no branch and no state to the wizard. Its frontend change is tests only. The backend change replaces two copies of the known-groups set with one helper that also contains the one constant the auth layer already defines. It removes a contradiction between two components (the wizard sends `__admin__`, the validator forbade it) at the component that was wrong according to the supervisor's decision. It does not special-case the rejection in the wizard.

Plainly, this round is **converging**, not patching: it is the first round whose fix does not add a stop branch or state. Its source diff is +8/−8 including the extraction.

The caution: F1 is a consequence of widening what the unauthenticated first-run window can write. If the answer to F1 is another conditional in the wizard's save sequence (for example "public mode also PUTs `[]`"), that would be the third round adding a save-path branch to `handleBeforeSubmit`. Such a round should be judged as a design question about the first-run window, not as one more case.

## Checked, no finding

- **Authorisation after setup.** PUT, append and delete passwords all depend on `_admin_or_first_run`, and after the sentinel exists that is `require_admin`. A non-admin or anonymous caller gets 403 with `__admin__` in the body and the file is unchanged (P4, M12 killed). An admin who adds `__admin__` gains nothing they did not already have: they could already rewrite every password and drive group. No path that the validator alone used to block is reachable by a non-admin.
- **Escalation via is_admin.** Unchanged code, but its two sentinel branches are held by existing tests (M9, M10 killed). Removing the only `__admin__` password through the GUI while no drive is protected makes everyone admin again. That is the documented graceful degradation, and it needs admin to do. An issued JWT keeps its `__admin__` claim until it expires after the password is deleted. That is pre-existing and the same for any group.
- **First-run race equivalence.** Before this commit, anyone in the window could already write drives plus a group password, or call `complete-setup`, and lock the owner out. The one new capability is F1 (a plant that survives the owner's finish).
- **GET masking.** The `__admin__` entry is masked like any other (P5).
- **Input variants.** Exact-match rejection is consistent with `auth.py` (P3). Non-string or empty groups still fail `missing_field` before the membership check, and the order is unchanged.
- **Config import rule.** `admin_config.py` uses `import app.auth as auth` and `import app.config as config`, and the helper reads `auth.ADMIN_SENTINEL_GROUP` through the module, so a monkeypatch applies. The new tests import `app.auth as auth` inside the function, like the file's other tests.
- **Integration test vs SetupWizard.tsx.**
  - The body matches `handleBeforeSubmit`: drives rows `{name, path, access_group}`, passwords `[{password, groups: [...entered, "__admin__"]}]`, and policy `{}` for Skip.
  - The path is the seeded `"{mount_root}/media"` that `setup-status` returns.
  - The wizard unlocks before `complete-setup`, and the test unlocks after. The swap is needed to observe the locked 404/403 first, and neither call depends on the other.
  - The test does not discriminate `__admin__` from `family`: holding `family` alone already makes the caller admin. The on-disk assertions in the parametrized tests carry that instead (M6, M7 killed).
  - The frontend test asserts the exact body and the drives-before-passwords order (FM1–FM4, FM3b killed). That closes round-2 F2.
- **Round-2 test edit.** The rejected-passwords test now uses a realistic `unknown_group` detail and types a group. It still asserts no policy, no complete-setup and no push.
- **Docs.** `settings-gui.md` ("Adding `__admin__` makes it an admin password") and `configuration.md` (the validator accepts `__admin__`; the wizard adds it in protected mode) both match the code. Neither leads an operator to an insecure configuration.
  - Pre-existing and not in this diff: `settings-gui.md` says "All except `setup-status` and `complete-setup` require admin authentication". During first run the writes are open, as `configuration.md` states. Relevant to F1 if the window is revisited.
