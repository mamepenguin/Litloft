## 3. What the fix could have broken

- **Removed `open({ scope })`.** No caller remains: grep over core `frontend/src`, `e2e-components`, all four addons at
  their gitlinks (`cloud-sync 812ea86`, `intelligence 095679a`, `knowledge 84ecdf0`, `media_import d8c8d9d`) and `docs/`
  finds only `open()`. `OpenHandler = () => void`, so a leftover `open({scope})` would be a type error; `tsc` is clean.
- **A registrant passing a new scope object every render.** Probe (vitest, disposable): a registrant that re-renders
  50 times with a fresh object while the modal is open with a query → `getDriveFiles` 1 → 1 call, `getWatchHistory`
  1 → 1; the link follows the latest object (`/n50?q=lens`). No request loop, because only `GlobalSearch` consumes the
  active scope and it keys its effects on `scopeType`. Browser: scoped modal open on the note, 5 s idle → 0 API requests.
  **But** a registrant that also *reads* the active scope loops (G3).
- **`scopeRemoved` across a change of scope during one opening.** Probe: remove on screen A, A unmounts and B (another
  kind) mounts → B's chip is absent; back to A → still absent. Browser: pressing Go to note while the modal is open
  after × leaves the chip off. This matches the user guide ("lasts until the modal closes") and R-0 #3/#11; the next
  opening is scoped again (browser: Esc, Cmd+K → chip back, focus in input). Judged sound: re-applying a scope the
  viewer just removed, because the page under the modal changed, would undo their action without them doing anything.
  Not a finding.
- **Recent files when the scope goes or comes with an empty query.** Probe: scoped → `plans.md` (text) only; registrant
  unmounts → `getWatchHistory(main, 8, "all")` without type, `clip.mp4` listed, `plans.md` gone; registrant back →
  scoped list again. Correct; the refetch is untested (G2).
- **Unscoped parity (R-0 #1).** `GlobalSearch.test.tsx` and `Header.test.tsx` unchanged since `afeba9ec` and pass;
  browser unscoped requests after the scope leaves have the parent's shape (table above).
- **Esc and focus.** Browser: Esc closes the scoped modal; Cmd+K reopens with chip and focus in input; × keeps focus.
- **Highlight when the scope vanishes mid-arrow.** Probe: second row highlighted, registrant leaves, same rows come
  back unscoped → highlight reset, Enter goes to `/drive/main/search?q=a`. Consistent with R-0 #6 (no highlighted row).

## 4. Findings

### G1 — Nothing holds the knowledge scope's dependency on `drive` `[introduced]` — bucket B

r2-18 survives all targets. With `drive` dropped from the `useMemo` deps, a `GoToNoteAction` that stays mounted while
its `drive` prop changes keeps registering a `seeAllHref` to the previous drive — exactly R-0 #8 — and since the fix now
reads the scope live, the modal would show it. The current code is right. I found no client-side path that keeps the
action mounted across a drive change (note → note in another drive needs an intervening non-note screen, which
unmounts it), so this is a test gap, not a user-reachable defect. Knowledge repo.

### G2 — Nothing holds the recent-files refetch when the scope goes or comes `[introduced]` — bucket B

r2-23 survives. Without `scopeType` in the recent-files effect's deps, removing the scope (×/Backspace) or leaving the
note screen with the modal open and an empty field shows no recent files at all (the stored scoped answer no longer
matches the type, and nothing fetches the unscoped one). "drops the scoped recent files as soon as the scope is
removed" asserts only the drop. Current code measured correct (probe above).

### G3 — A registrant that reads the active scope and passes an unmemoized object renders without bound `[introduced]` — bucket B

Probe: a component calling `useActiveSearchScope()` and `useSearchScope({ label: "Notes", type: "text" })` inline →
the vitest worker ran out of memory (`OOMErrorHandler`, `ERR_IPC_CHANNEL_CLOSED`). Cycle: new object → `updateScope`
sets provider state → `ActiveScopeContext` value changes → the reader re-renders → new object. The provider moved from
ref readers (no re-render) to React state, which is what creates the cycle. No registrant reads the active scope
today (only `GlobalSearch` does, and it registers nothing), and the addon docs say "Keep the scope object stable
(`useMemo`)", so not reachable now. Recorded because the failure is a hung tab rather than a wrong result, and the doc's
wording ("a new object replaces the registered one") does not say so. Remedy is the supervisor's call (e.g. skip the
update when `type`/`label`/`seeAllHref` are unchanged, or state the hazard); I fixed nothing.

### G4 — After a drive change with the modal open, the empty state lists the previous drive's search terms `[pre-existing]` — bucket B

Browser: the F1 path, at `/drive/テスト画像`, clear the field → the empty state lists `2026-08-10`, whose only stored
history is `search-history:動画`. `history` is loaded only in `openSearch`; the parent `afeba9ec` does the same
(`setHistory(drive ? getHistory(drive) : [])` only at opening, line 126). Clicking the term searches テスト画像 (the
current drive), so no destination crosses the drive; what crosses is the display of terms typed in another drive. The
fix makes the path reachable from a scoped opening too (a scoped modal hid terms), but it was already reachable from an
unscoped one. Ledger.

## 5. Trajectory

Only one fix round exists (`2041a640` + tests `a5ec34ca` + knowledge `84ecdf0`), so "two rounds in a row" cannot yet
apply. Reading its diff against `0dbd1a0d`/`e5ab7b79`:

**Removed:** the modal's `scope` snapshot state and its setter in `openWith`; the `openWith(nextScope)` parameter and
the `options?.scope ?? defaultScope()` branch; `GlobalSearchOpenOptions` / `open({ scope })`; the provider's
`defaultScope()` reader and the ref-reader indirection (`scopeRef` + `pushScope(() => scopeRef.current)`); the knowledge
button's own scope argument. The removed thing is a *prediction* — "the scope captured at opening is still the right
one when Enter is pressed" — which is what F1 falsified.

**Added:** `scopeRemoved` (a boolean in place of the snapshot — narrower state, not extra); provider `entries` held in
React state with a per-registration token; an `updateScope` action and a second effect in `useSearchScope`; a second
context (`ActiveScopeContext`) and `useActiveSearchScope()`.

It does not add a navigation-specific branch (nothing like "clear the scope when the drive or route changes"); the
drive-change case falls out of reading the registration live. That is the converging shape. The one new mechanism with
a cost is `updateScope` in state, which brings the stable-object requirement and G3. If a next round adds a guard for
unstable objects on top of it (e.g. comparing fields), that would be a branch added to handle a case this round's
mechanism created — worth watching.
