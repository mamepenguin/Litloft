### F2 — Knowledge EditorToolbar's `…` menu shows format rows that are also on the bar (container queries lose their container when portalled)
- Label: [introduced]
- Invariant: none listed; `addons/knowledge/frontend/EditorToolbar.tsx` states "one control, one place, at any one width". Candidate for the "missing" list: *a menu's contents render the same whether or not it is portalled* (it may depend on ancestor-scoped CSS: `@container` queries, `group-*`, descendant selectors).
- Severity: medium (user-visible on every phone that opens the note editor's `…`)
- Mechanism: `EditorToolbar`'s root is `@container`; the `OverflowMenu` rows use `pointer-coarse:@min-[352px]:hidden`, `pointer-fine:@min-[432px]:hidden`, `pointer-fine:@min-[534px]:hidden`. `OverflowMenu` now portals the panel to `<body>` below 640px, where there is no query container, so the `@container` condition is never true and the rows are never hidden.
- Reproduction (CSS semantics, Chromium via Playwright, 393px): `.c{container-type:inline-size} @container (width >= 352px){.row{display:none}}` — a `.row` inside `.c` computes `display:none`; the same `.row` appended to `<body>` computes `display:block`. So on a 393px touch phone the H1 row (on the bar at ≥352 container width) appears in the menu too; on a fine pointer at 500–639px the mid/full rows duplicate.
- At 3a8841db `OverflowMenu` rendered the panel inside the wrapper, inside the `@container` — no duplication.
- Not covered by any test in core; the addon is a submodule and was not re-run against this core commit.

### F3 — Crossing 640px with focus inside an open menu drops focus to `<body>`, after which Escape no longer closes the menu
- Label: [introduced]
- Invariant: 6 ("neither … breaks the menu") and 4 (Escape closes it)
- Severity: low (needs a keyboard-focused row plus a resize/rotation across 640px — e.g. a phone rotating 393→851, a tablet window resize)
- Reproduction (temporary spec, `player-menu-peek`, Pixel 5 project): open `View:`, focus the first `menuitemradio`, `setViewportSize(800×727)`; `document.activeElement` is `BODY`, and pressing Escape leaves `role=menu` count at 1.
- Mechanism: `layer()` returns a portal on one side of the breakpoint and a plain element on the other, so React sees a different child type at that slot and unmounts/remounts the scrim and the panel. The focused row is destroyed; the wrapper's React `onKeyDown` only receives keys from inside the React subtree, and `<body>` is not.
- At 3a8841db nothing changed element type on resize, so the focused row survived and Escape reached the wrapper.
- For contrast (not a defect): tapping outside after the round trip 393→800→393 still closes the menu; exactly one menu and one scrim exist at each step, none left in `<body>` at 800 (T4).

## Is anything missing from the R-0 list?
Yes, three items, all reproduced above:
- *A portalled menu's contents render exactly as they did in place.* CSS scoped to an ancestor (`@container` queries, `group-*`, descendant selectors) is lost in `<body>` (F2).
- *Keyboard Tab from an open menu's trigger reaches the menu's first row* (F1).
- *A focused menu keeps focus, and Escape still works, across a breakpoint change* (F3). Invariant 6 as worded ("does not break the menu") arguably covers it already.

## Considered, no finding
- Server snapshot `false` / hydration: menus are closed on the first render, so the portal branch never runs during SSR or hydration (M4 `() => true` is equivalent in practice and survives as expected).
- Escape from a row inside a portalled menu: React bubbles synthetic events through the portal to the wrapper's `onKeyDown`, so the menu closes and focus returns to the trigger (T2 passes). SortButton and FolderToolbar use the document-level shortcut registry, which the portal does not affect.
- Outside press closes the menu and swallows its click (T3). A press inside does not close it: `DismissScrim` still finds the panel through `nextElementSibling`, because the fragment keeps scrim and panel adjacent in `<body>`. Selecting a row closes the menu (T5).
- `useAnchoredDirection` on a portalled panel: below 640px the panel is `fixed`, so `measure` returns early and the portal changes nothing.
- FolderToolbar `disabled={moreDialogOpen}`: the dialog state lives in React, and Radix layers decide inside/outside by React tree, so a portalled parent menu is not treated as "outside".
- Two `MobileInspectorSheet` instances: only `FileDetailShell` renders one. Across an unmount/mount, React runs layout-effect destroys before new layout effects, so the var is not cleared after a new strip sets it.
- A different root font size makes `sm` (40rem) and `639.98px` disagree. Tried to reproduce with a Chromium profile font preference; the preference did not take effect. Not reproduced, not reported.
- `tsc --noEmit`: clean.
