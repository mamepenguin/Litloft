## Findings

### G1 — "crossing 640px with a menu open" is flaky at 11b111f3 (5 of 15 runs fail); its post-resize assertions race the re-render
- Label: [introduced] (the spec case is new in 11b111f3)
- Invariant: 6 (the case that is meant to hold it). Detector rule 3 ("wait for the thing you assert on, not for the request that starts it").
- Reproduction, unmodified tree at 11b111f3: `npx playwright test --config=playwright-components.config.ts player-menu-layer.spec.ts --repeat-each=15` -> 5 failed, 145 passed, all five in this case. Four fail at line 89 (`parentElement === document.body` expected true, got false after resizing back to 393px), one at line 86 (expected false, got true after resizing to 1024px). It also failed once in a single full component-e2e run (1 of 2 runs), unrelated to the mutation applied at the time. The config has `retries: 0`, so CI goes red about a third of the time.
- Mechanism: after `setViewportSize`, `await expect(menu).toHaveCount(1)` is already true against the pre-resize DOM, so it returns without waiting; the one-shot `evaluate(parentElement === body)` and the one-shot `locator("[data-dismiss-scrim]").count()` then run before or after the `matchMedia` change reaches React, whichever comes first. The same race means the count checks do not observe the post-resize DOM at all: a state with a leftover menu or scrim that appears only after the re-render is not what `toHaveCount(1)` measured.
- Fix shape (for the author): poll the asserted value (`expect.poll(() => menu.evaluate(el => el.parentElement === document.body)).toBe(...)`), then take the counts.

### G4 — The 16px case waits out the entry animation with a fixed `waitForTimeout(250)`

Deleting the wait (mutation MW) fails the case in 5 of 20 runs with `Received: 17`. With the wait, 30 repeats x 5 cases at 12 workers passed 150/150, so it is not flaky on this machine today; the margin is 50ms, and r1 F5 is the same pattern (`waitForTimeout(300)` in `e2e-layout/toolbar-menu.spec.ts`) already flaking under load.

- Fix shape: wait for the panel's animations to finish (`el.getAnimations()` settled) instead of a timer.

## Q3 — trajectory

One fix round so far, so the two-in-a-row test cannot fire yet. What each round did to the design:

- **fc3f0e7d** added a width-dependent state (the panel's DOM parent flips between the wrapper and `<body>` at 640px, via `useIsMenuSheet`), a published CSS variable (`--resting-strip`, a second state owned by the strip), and a prediction: *a panel renders the same wherever it is mounted*. r1 falsified that prediction (F2, container queries) and the width switch produced F1 (Tab order) and F3 (focus lost on crossing).
- **11b111f3** removed the portal from four call sites (OverflowMenu, SortButton, FilterMenu, FolderToolbar are back to 3a8841db apart from the lift), which is convergence. It also added a branch (`portalOnPhone && sheet`), prop plumbing through ViewMenu/ArchiveToolbar/PdfPreview, and a new prediction: *the menus whose trigger lives in the player box are exactly these three*. Nothing enforces that list (G2 shows even one of the three is unheld), and the width-dependent parent switch that causes F1/F3 is kept, now for three menus.

So: this round narrows the blast radius rather than patching a new case, but it does add a branch and a prediction on the same decision round 1 introduced. If a round 3 fix adds another branch to the same switch (e.g. focus restoration across the 640px crossing for F3, or a detector for player-box menus), that is the "two rounds in a row" shape and should go to the supervisor as C. The root cause — the player box's sticky stacking context on a phone — is still handled by moving individual menus out of it rather than at the box.
