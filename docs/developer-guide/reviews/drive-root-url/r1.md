## 1. The sidebar half of the normalisation is held by nothing — a mutation that unlights the whole column on `?view=library` leaves all 7495 tests green [introduced]

**File:** `frontend/src/components/Sidebar.tsx:55`

**Mutation:** `const activeView = normaliseDriveView(searchParams.get("view"))`
→ `const activeView = searchParams.get("view")`. `want=kill`, **got=LIVE** —
and not only in a focused set: the entire suite passes, 512 files, 7495 tests,
zero failures.

`normaliseDriveView` was introduced with exactly two consumers, and the spec
says why in its own words (§"`?view=library` is rewritten, not special-cased"):

> **Two consumers, not one.** … Normalising only the route layer leaves
> `/drive/{d}?view=library` rendering Library with **no sidebar row lit**,
> because both predicates would still see the string `"library"`.

That is exactly what the mutation produces. Walked by hand at
`/drive/main?view=library` with `activeView = "library"`:

- **Library row** (`href` = the bare base): `isSidebarLinkActive`'s
  `href === base` branch returns `atDriveRoot && !activeView && !activeTag`
  = **false**; the `libraryActive` override that actually decides it is
  `isLibraryRowActive` → `samePath` true → `return !activeView`
  (`libraryRowActive.ts:36`) = **false**.
- **Home row** (`href` = `${base}?view=home`): the `viewPrefix` branch asks
  `activeView === "home"` = **false**.
- Every other fixed row asks the same `viewPrefix` question with its own value.

So **no sidebar row is lit**, which breaks R-0 4 ("the same sidebar row lit")
and R-0 5 ("exactly one sidebar row is lit on `/drive/{d}`" — the alias renders
that same screen).

The spec named the test that would hold it, and it was not written:

> `components/__tests__/SidebarActiveRow.test.tsx` | Add a `?view=library`
> case: exactly the Library row is lit. **Nothing holds the alias's active
> state otherwise**, and it is the half of the normalisation that lives
> outside the route layer.

`git show 63481e0a -- .../SidebarActiveRow.test.tsx` is a one-line change
(`["Home"]` → `["Library"]`). Reading the file confirms it: its
`describe("which row the sidebar highlights")` block has cases for every
`FIXED_SIDEBAR_ROWS` view, for the decoded pathname, for pins, for folders,
for `?tag=`, and for `?view=not-a-view` — and none for `?view=library`.

`libraryRowActive.test.ts` cannot hold it either: it calls `isLibraryRowActive`
and `isSidebarLinkActive` with `activeView` passed in directly, i.e. **downstream
of the normalisation**, so it is blind to whether `Sidebar.tsx` normalises at
all. `page.test.tsx:116` holds only the route layer's half.

**What a user observes with the mutation applied:** `/drive/{d}?view=library` —
the URL the previous release's own sidebar linked to, so every existing bookmark
and back-button entry — renders the Library listing with the entire sidebar
column unhighlighted.

**Remedy:** the test the spec already specified. One case in
`SidebarActiveRow.test.tsx` setting `search = new URLSearchParams({view: "library"})`
and asserting `highlighted()` is `["Library"]` kills this mutation.

## 3. The Home row's off-drive href has no test on either side of this change [pre-existing]

**File:** `frontend/src/components/sidebar/SidebarLibrarySection.tsx:31`

**Mutation:** `const homeHref = currentDrive ? driveHref(currentDrive, "home") : "/"`
→ `const homeHref = driveHref(currentDrive ?? "", "home")`. `want=kill`,
**got=LIVE** on the full suite.

With the mutation, the sidebar's Home row on `/`, on `/admin`, and anywhere
`useCurrentDrive()` is null points at **`/drive/?view=home`** — a route with an
empty drive name. Nothing asserts the `"/"` arm.

The spec review (finding 13) said the fallback "has to survive —

that Favorites and Recently Viewed are *absent*; its one `a[href="/"]`

**`[pre-existing]`.** The parent has the same shape (`href={driveBase ?? "/"}`)
and the analogous mutation — `driveBase ?? "/drive/"` — passes the parent's
sidebar suites unchanged (22 files, 304 tests, all green).

Per R-4 scope this goes to the ledger rather than into this branch. Recording

## 4. `useFolderFiles`'s Library-root suite now exercises a prop combination the app cannot produce, and its docstring says otherwise [introduced]

**File:** `frontend/src/components/folder/__tests__/useFolderFiles.test.ts:678-682`
and the nine `settle({ folderPath: "", view: "library" })` calls under it.

The route layer no longer passes `view="library"` anywhere: `normaliseDriveView`
rewrites it to `null` before `page.tsx` reads it, and `[...path]/page.tsx` never
passed a `view` at all. So `{folderPath: "", view: "library"}` is now
unreachable, and the real Library-root state — `folderPath: ""` with **no**
view — is the one nothing in this file exercises.

It is inert rather than wrong: inside the hook, `view` only feeds the
`isFavorites` / `isRecent` / `isRecentAdded` / `isLiked` / `isAll` booleans
(all false for `"library"`), `buildListSnapshotKey`, and the reset key at `:354`
— none of which changes the request these tests assert on. So the suite still
kills what it killed. It is the docstring that would mislead:

```
/**
 * `/drive/{name}?view=library` arrives at the hook as `folderPath: ""`, so
 * these cases use that value. …
 */
```

A reader fixing something here would believe the alias still reaches the hook
carrying `view="library"` and could preserve it as load-bearing. **Delete the
`view: "library"` argument from the nine calls and delete that first sentence**
— do not reword it. The same dead combination appears in
`FolderBrowser.folderAnchor.test.tsx` (13 renders),
`FolderBrowser.paste.test.tsx:165,171`, `FolderBrowser.header.test.tsx:258`
(`describe("the Library root header")`'s `renderRoot`),
`uploadZoneHosts.test.tsx:57` and `accent-budget.test.tsx:503,532`; all are
inert for the same reason, and all would read truer with the prop dropped.

## 5. `isSidebarLinkActive`'s `href === base` branch now has no production caller [introduced]

**File:** `frontend/src/components/sidebar/isSidebarLinkActive.ts:32-34`

After the swap, the only href in the app equal to the bare `/drive/{d}` is the
**Library** row's — and `Sidebar.tsx:129` renders it as
`linkClass(libraryHref, libraryActive)`, where `libraryActive` is always a
boolean, so `active ?? isActive(href)` never evaluates `isActive`. Every other
row passes `?view=…`, a path segment, `/`, `/admin`, or an explicit override.
The branch is unreachable from the running app.

The spec chose this deliberately and said so ("kept as it stands, not removed …
unreachable only because `Sidebar.tsx:128` passes an explicit override"), and
removing it is worse: M19 shows the fall-through answers `true` at
`/drive/{d}?view=favorites` and `/drive/{d}?tag=soup`. So this is **not a
request to change anything** — it is recorded so a later round does not
re-derive it, and so the pairing is visible: the branch is now a second,
unused implementation of the Library row's rule, whose live implementation is
`isLibraryRowActive`.

One consequence worth noting for coverage: `libraryRowActive.test.ts`'s
`FIXED_ROWS` is derived from `FIXED_SIDEBAR_ROWS` with the Library row filtered
out, and since the swap moved `view: null` from Home to Library, **no row in
that derived table carries the bare base any more**. That integration table
used to exercise the `href === base` branch and no longer does. It is still
held by `isSidebarLinkActive.test.ts`'s own cases (M19, M20 and M21 are all
killed there, at `:112` and `:143`).

## Is anything missing from the R-0 list?

**R-0 3's second clause is factually false**, in the correct implementation, and
should be deleted rather than re-aimed:

> 3. `/drive/{d}?view=home` renders `DriveHome` and issues no
>    `GET /drives/{d}/files`.

`DriveHome.tsx:127-129` issues **three** `getDriveFiles` calls of its own
(recently added, favourites, liked), each of which is
`GET /api/drives/{d}/files?…` (`api.ts:92-94`). The clause is violated by the
code as shipped. It was rewritten once already — the spec review replaced
"sends no `view=home` to the file-list API" (unfalsifiable, since
`getDriveFiles` has no `view` parameter) with this — and the replacement traded
an unfalsifiable clause for a false one. The first clause of R-0 3 is the whole
invariant, and it is held: `page.test.tsx`'s `ROUTES` row asserts
`component === "DriveHome"`, which is what M1 (the `home` branch moved after
`view || tagFilter`) trips.

**Two items I would propose adding**, both mutation-observable and both held
today:

1. *"The breadcrumb's drive segment, a root file's back link, and an empty
   collection's add-files action land on the Library root, not Home."* This is
   the mirror of R-0 7 and it is the stated purpose of the change — the Problem
   table's six sites. Every declared invariant can hold while those six point
   back at Home and the change achieves nothing. It is held today: M43
   (`Breadcrumb.tsx:50` → `?view=home`) kills 6 tests across 2 files, M44
   (`FileDetailChrome.tsx:52`) kills 1, M45 (`CollectionDetail.tsx:365`) kills 1.
2. *"`/drive/{d}` lists the root folder's own children, not the drive
   recursively."* R-0 2 pins the `?tag=` widening; nothing pins the
   non-widening. It is held only inside
   `useFolderFiles.test.ts`'s Library-root suite, and only under the
   now-unreachable `view: "library"` spelling — see finding 4.

Everything else in the list is observable and held. R-0 1 is held by
`SUBJECT_BY_SCREEN`'s cross-folder row; R-0 2 by M5 and
`useFolderFiles.test.ts:775`; R-0 4 by `page.test.tsx:116` for the route half
and by **nothing** for the sidebar half (finding 1); R-0 5 by
`libraryRowActive.test.ts`'s `STATES` and `SidebarActiveRow`'s per-row cases;
R-0 6 half-held (finding 2); R-0 7 by M10, M29 and M30.

One R-0 1 clause is held only transitively, which is worth knowing rather than
fixing: `titleIcon={isLibraryRoot && !isSearch ? FolderTree : undefined}` can
be weakened to `!isSearch` with the whole suite green (M37), because
`PageHeader` renders `TitleIcon` only inside its `{hasTitle && …}` block
(`PageHeader.tsx:69-78`) and a cross-folder view has no title. The mutant is
equivalent — the icon cannot appear without the title the same invariant
already forbids — so the `isLibraryRoot &&` guard is redundant, not unheld.
