## Q1 — does `0cb7453a0` fix r1 F1 on every path?

The displacement r1 reported does not happen any more. A1 (the old shape) is now caught by the reduced-motion case in both arrangements and both orientations. Per-frame probing (`zz-probe8`: reduced motion, both arrangements, portrait and landscape, `--repeat-each 5`, 20 runs) found no sample where `#after-player` or the scroll position moved.

The paths:
- **Animated, entry and exit.** A2, A4, A5 and A7 are killed. A3 survives, as it did in r1 (N1).
- **Reduced motion, same-render.** The class and the marks change in one commit, so the slot opens and closes in the same layout as the frame. It holds.
- **Reduced motion, VideoPlayer, entry.** The mark lands one commit before `.fixed`. The slot needs `.fixed`, so the frame is still in flow and nothing moves. It holds.
- **Reduced motion, VideoPlayer, exit.** A frame with `.fixed` and no marks is painted rarely: 1 in 60 under S1. On that frame the slot is gone and `#after-player` jumps up 221px underneath a frame that covers the viewport. This is the known one-commit lag, so it is [pre-existing]. It is the only thing the sampler exemption currently absorbs.
- **The sibling row** keeps its place in the animated case (A7 is killed). The reduced-motion case never measures the row.

What else a `::before` on the wrapper changes:
- `:first-child` / `> :first-child` rules (`globals.css:1152`, `:1291`): none. A pseudo-element never matches `:first-child`, and in the app those rules target `.media-detail-player`'s first child (the bleed div in `FilePreview.tsx`), not the frame's wrapper.
- The row's position: the generated box is block-level, empty and has non-zero padding, so the row's `mt-2` does not collapse through it. The row's top is the same as it was under the padding. A7 is killed, so a slot below the row would be caught.
- Percentage basis: `padding-top` on the `::before` resolves against the wrapper's content width, which is the width the frame's own 16:9 box uses (`aspect-video w-full` in VideoPlayer, `paddingTop: 56.25%` on the frame in `YouTubeEmbed.tsx`). The wrapper's own padding resolved against the wrapper's parent. So the new basis matches the frame at least as well as the old one did.
- No caller's wrapper uses `before:` classes, or `flex`/`grid`, where a generated box would become an extra item. I checked VideoPlayer, ShellVideoPlayer, SameRenderPlayer and the `media_import` YouTubeEmbed at `929db331`.
- Under reduced motion the global `*::before { transition-duration: 0.01ms }` still reaches the box. It can only transition the percentage while the box exists (a rotation while pinned), and that happens under the opaque frame. I found no effect.

It is sound as a claim about what can be seen, as far as I could check: on the one frame it currently absorbs, the frame is opaque and fills the viewport. It is not sound as a test of invariant 5, and it blinds the reduced-motion case to the slot. See F1.

## Findings

### F1 [introduced] The sampler's exemption leaves the reduced-motion case unable to see the slot. With no slot at all under reduced motion, every test stays green
- Invariant broken by the surviving mutation: **5**, which the user revised to include "with reduced motion" and "any painted frame".
- Where: `frontend/e2e-components/pseudo-fullscreen-transition.spec.ts:204-206` (the exemption), used by the reduced-motion case at `:321-343`.
- Reproduction: A6 (the slot rule wrapped in `@media (prefers-reduced-motion: no-preference)`), then `CI=1 pnpm test:e2e:components pseudo-fullscreen-transition`.
- Observed: 12/12 pass. With A6 and the exemption removed (A6+S1), all 4 reduced-motion cases fail, with `#after-player` at 56 (portrait VideoPlayer, from 277), 89.6 (portrait same-render), and -228 / -227.4 (landscape) on every pinned sample. A2 is caught only by the animated cases' explicit `toBeCloseTo(after.top)` while pinned. The reduced-motion case has no such check, and while the frame is pinned every one of its samples falls under the exemption.
- So the reduced-motion case now holds only r1 F1's exit symptom (A1, a frame drawn in flow at the wrong place). It does not hold invariant 5 while the frame is pinned.
- Why the exemption is there: S1 shows it absorbs the [pre-existing] VideoPlayer lag frame (1/60). The test therefore encodes "the page does not move where it can be seen", which is narrower than invariant 5 as written. Either the invariant or the test has to move, and that is the supervisor's call.
- Is it visible? Under A6, the page moves only underneath an opaque full-viewport frame. A lasting effect would need the scroller to be clamped, for example when scrolled to the bottom of a short page. The fixture's 2000px `#after-player` can never clamp, so no current case can show a lasting effect.

### F2 [introduced] The test for invariant 10 stands in for "the drawn look" with an inline style, so it cannot tell the computed style from the inline style. Two realistic breakages make the frame jump to full size in Chromium, and every test stays green
- Invariant broken by the surviving mutations: **10**.
- Where: the test is `frontend/src/components/player/hooks/__tests__/useFullscreen.test.tsx:612-624`. It sets `frame.style.transform` / `frame.style.clipPath` to simulate a running animation. The code it guards is `useFrameTransition.ts:70-73` (`currentLook`) and `:225`.
- Reproduction: H3 (`currentLook` reads `frame.style`) and H4 (the look is read after `clear(frame)` cancels the running animations). Then vitest over `src/components/player` and the e2e spec, plus probe `zz-probe4` (r1's probe: Full screen, then Escape 120ms later, recording the visible frame height before each paint) and `zz-probe7` (exit after the frame settles, then a second press 80ms later).
- Observed at the SHA: the heights rise, stop, then fall (`…686,694,700 → 694,662,630…221`). The reversal falls, then rises (`…449,424,424,474,511…727`).
- Observed under H3: exit during entry goes `…694,700,727,727,…,727,221,221…`. The frame jumps to full size, holds there, then snaps to its slot with no shrink. The reversal goes `…450,428,727`, a jump to full. H4 gives the same exit-during-entry trace. vitest 343/343 and e2e 12/12 pass under both.
- In a real browser, a running Web Animation shows up only in the computed style, never in `element.style`. The test sets exactly the value that the broken implementation (H3) reads, so it passes for the wrong reason. No e2e case interrupts an entry or reverses an exit, and invariant 10 has no browser-level check.

## Trajectory

There has been only one fix round (`0cb7453a0`, `61cce0f28`), so "two rounds in a row" cannot be assessed yet. Reading the diffs in order:

- `0cb7453a0`, CSS: this replaces a mechanism rather than adding one. The slot moves from a property that can transition to a box that can only exist or not exist. There is no new branch, state or selector.
- `0cb7453a0`, test: this **adds a prediction**. The exemption ("frame covers viewport ⇒ page not checked") and `minSamples` exist to absorb one state: a `.fixed` frame without the hook's marks, from the caller's pin classes lagging the hook by a commit. The design had already accommodated that state once before the review, in CSS: the slot is keyed on `.fixed` as well as the marks, with a second selector on `data-fullscreen-moving` (`8ceea0900`, r1 N1). So the same lag has now been handled twice, once in the implementation and once in the test oracle. The second accommodation weakened what the test holds (F1).
- `61cce0f28`: this adds tests only, no branch or state in the code. F2 is about how strong those tests are, not about the shape of the design.

Watch for: if the next fix adds a third accommodation for the lag between pin classes and marks, whether a selector, a sampler rule or a predicted frame, that is the "design being patched" pattern. The supervisor should ask whether the hook should own the pin classes, or whether callers should apply them in the same commit, instead of each layer predicting the gap.
