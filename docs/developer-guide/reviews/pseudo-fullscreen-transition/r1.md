## Findings

### F1 [introduced] With reduced motion, the held slot opens and closes one painted frame late; on exit the frame is drawn 221px below its slot
- Invariant broken: **5** (the first element after the wrapper moves) on the reduced-motion path; invariant 6's "markers change in the same commit" holds, but the slot does not follow it.
- Where: `frontend/src/app/globals.css:1111-1114` (the `div:has(> .fixed[...]) { padding-top: 56.25% }` slot) meeting the pre-existing global override `globals.css:206-211` (`@media (prefers-reduced-motion: reduce) { *, *::before, *::after { transition-duration: 0.01ms !important } }`). `transition-property` defaults to `all`, so under reduced motion the wrapper's `padding-top` *transitions* over 0.01ms, and the first frame after each change is painted with the old padding.
- Reproduction: a throwaway spec in the worktree (`e2e-components/zz-probe.spec.ts`, deleted afterwards) that records, from a ResizeObserver callback after layout and before paint on every frame, the frame's classes/markers, the wrapper's computed `padding-top`, and `#after-player`'s top; `emulateMedia({ reducedMotion: "reduce" })`, click Full screen, wait 600ms, Escape, wait 600ms. Portrait 393x851, `--repeat-each 5`.
- Observed (every rm run, both arrangements; 0 bad samples in every non-rm run):
  - entry, VideoPlayer: `{fixed:true, pseudo:"true", after:56, pad:"0px"}` (inline 277) — hidden behind the opaque pinned frame.
  - entry, same-render: `{fixed:true, pseudo:"true", after:90, pad:"0px"}`, sometimes followed by an intermediate `pad:"65.27px"` / `"195.69px"` sample.
  - **exit, both arrangements: `{fixed:false, pseudo:null, after:498 (532), top:277, pad:"221.06px"}`** — the frame is back in flow but pushed 221px below its slot and the description with it, for one frame ~8ms before the correct sample. This one is visible.
- Cause confirmed: adding `.media-detail-player div { transition-property: none !important }` (diagnostic only, reverted) makes every rm run report 0 bad samples.
- Develop has no slot rule, so this displacement cannot happen there (the rule is created by this PR).
- Tests cannot see it: the reduced-motion e2e case (`pseudo-fullscreen-transition.spec.ts:317`) only checks the settled rect and `__animations.length`; it never samples `#after-player`, and never exits.

### F2 [introduced] Nothing holds that a reversed exit re-pushes the history entry; keying the history effect on `pseudoActive` (M09) makes Back leave the page and every test stays green
- Invariant broken by the surviving mutation: none of R-0 as written (8 only counts `history.back()` calls). It breaks a pre-existing contract of this hook: while pseudo-fullscreen is open, Back closes it instead of navigating. See "Missing from the list".
- Where: `useFullscreen.ts:418-443` (history effect keyed on `pseudoOpen`); the reversal path is `useFullscreen.ts:190-196`, new in this PR.
- Reproduction: throwaway spec (`zz-probe3`, kept outside the repo in `scratchpad/mut/probes/`), both arrangements, portrait: click Full screen, wait until settled, dispatch Escape, 50ms later reverse (`f` for VideoPlayer, the button for same-render), wait 700ms, read `history.state`, then `history.back()`, wait 700ms.
- Observed at the SHA: after the reversal `history.state = {litloftFullscreen:true}`; after Back the frame is unpinned and the page is still the fixture (`location.hash` kept). Correct.
- Observed under M09: after the reversal `history.state = null` (no entry pushed); Back leaves the page (`location.hash` becomes `""`, the fixture is gone). vitest 341/341 and e2e 12/12 still pass under M09.
- The vitest case "turns a shrink around on a second press without calling back() again" (`useFullscreen.test.tsx`, carrying block) asserts `back` was called once but never asserts a new `pushState` or that a later popstate exits.

### F3 [introduced] Exiting during the entry is untested: starting the shrink from the full look (M18) makes the frame jump, and every test stays green
- Invariant broken by the surviving mutation: none of R-0 (no invariant covers an exit that interrupts the entry). The spec states it: "Every animation starts from the frame's current look … There is no `finish()` jump on reversal."
- Where: `useFrameTransition.ts:225` (`const from = animationsRef.current.length > 0 ? currentLook(frame) : FULL_LOOK`).
- Reachable: Escape and `f` are live during the 300ms entry (the shortcut is registered while `pseudoOpen`), and so is popstate (an iOS back-swipe). Touch gestures are ignored while moving, so a touch-only user reaches it only through Back.
- Reproduction: throwaway spec (`zz-probe4`), both arrangements, portrait: sample the visible frame height before every paint; click Full screen, press Escape 120ms later.
- Observed at the SHA (visible heights): `…533,570,592,592,592,566,544,518…221` — rises, stops, falls. Continuous.
- Observed under M18: `…567,597,727,727,692,660…221` — jumps from 597 to the full 727 in one frame, then shrinks. vitest 341/341 and e2e 12/12 pass under M18.

## Notes (survivors that are not findings)

- **N1 — M25 (the `.fixed[data-fullscreen-moving]` slot selector) survives, and I could not produce the gap it covers on the animated path.** Per-frame sampling of the VideoPlayer exit under M25 (3 runs) showed no frame with the frame still `.fixed` after `data-pseudo-fullscreen` was removed: in headless Chromium the caller's follow-up commit lands before the next paint. The gap *can* be painted: under reduced motion one run caught `{fixed:true, pseudo:null}`. So the selector covers a gap a slower device can paint and this suite cannot. Not a defect.
- **N2 — M08 (`useLayoutEffect` back to `useEffect`) survives.** I also sampled the markers per frame under M08: no painted frame had `.fixed` without `data-pseudo-fullscreen` or without `html[data-player-fullscreen]`, in either arrangement, with or without reduced motion. In Chromium, React flushes the passive effects of that commit before the paint. As measured it behaves the same; nothing shows a behaviour this switch buys or breaks.
- **N3 — M16 (the "exit while still waiting to be pinned" branch) survives.** Without it, an exit that arrives before the frame reaches viewport size would run a shrink on a frame still in flow. For both real callers the window is shorter than one frame (the pin lands one commit late at most), so I found no user path into it. There is no test of it.
- **M06 / M01** are each equivalent alone (see the table). M35 (a reversal that keeps the old `entryReason`) only matters for a rotate-reversal followed by sitting up. That combination has no test, and I did not look into it further.
- **Could not reproduce, R-5 item:** `isPinnedSize` compares the frame's border box to `innerWidth/innerHeight` within 1px. If those ever differ from the `fixed inset-0` box on iOS (for example, a pinch-zoomed visual viewport, which iOS allows even with `userScalable: false`), the entry times out without animating, and the exit's post-finish watch (`useFrameTransition.ts:236`) matches on its first observation and drops the held inline look before the caller unpins. That would be a one-frame snap to full size. Chromium's `Emulation.setPageScaleFactor` does not change `innerWidth`, so I could not reproduce it here. Check it on a device.
