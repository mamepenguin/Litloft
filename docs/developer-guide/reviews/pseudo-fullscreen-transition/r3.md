## Q1 — does `91925de17` hold every invariant on every path?

On the paths the suite covers, yes: entry, exit, an exit that cuts an entry short, reversal, reduced motion, rotation and unmount, in both arrangements and both orientations (393x851, 851x393). K1-K5 and K9 are killed. `shrink`'s early path is reached by reduced motion, `animate:false`, rotation (`forget` leaves no capture) and unmount in the same way as before.

The points the brief asked about:

- **Callers.** All three pin with `fixed inset-0 z-50` and sit inline with `relative`: `VideoPlayer.tsx:219-221`, `ShellVideoPlayer.tsx:223`, and `YouTubeEmbed.tsx:485-490` at `929db331`. The test fixture's `SameRenderPlayer` does the same. No stylesheet rule sets `position` on the frame. The mini player (`MiniPlayerContainer.tsx:54`) makes an *ancestor* `fixed`. The frame stays `relative` there, so `isPinned` reads false inline. None of those ancestors has a transform, so a pinned frame still resolves against the viewport.
- **Pin changes, size does not.** The observer then does not fire again, which follows from the ResizeObserver definition, and I observed it. It happens when the inline frame's border box already equals the pinned box, for example a 640x360 viewport with a full-bleed frame. See F1 and F2.
- **`offsetWidth`/`offsetHeight`.** A transform does not change them, which is right for the pinned box. Both sides of the `shrink` comparison are rounded integers from the same layout, so the old 1px tolerance is not needed. A fractional viewport would put the carry's scale off by less than 0.5px out of 393. I could not produce a fractional pinned box here, because Playwright viewports are integers. The fixture pins at exactly `innerWidth` x `innerHeight` (393x851 and 640x360 measured).
- **The folded branch.** For an exit while the entry is still waiting for its pin, the new path also runs `clear(frame)`. With no animations and no marker yet, that does nothing, so the behaviour is the same. K8 shows the size check also sends that case to the instant path.
- **One behaviour change that breaks no invariant.** Suppose the entry's watch timed out but the frame did get pinned, for example on a device where the pin lands after 500ms. At `0cdfd1bd2` the exit was still animated, from `FULL_LOOK` to the captured viewport. Now it is instant, because `pinned` stays null. That is the same mechanism that stops the pinch-zoomed exit from growing.

## Findings

### F1 [introduced] When the inline frame already has the pinned box's size, the entry is sometimes not carried and the frame jumps to the top unanimated
- Invariant broken: **3** ("No frame is painted with the frame at viewport size and no transform").
- Where: `useFrameTransition.ts:98-110` (`watchPin`: a ResizeObserver is the only trigger, and `isPinned` is read only inside its callback) together with `:193-201` (the entry's `onTimeout` is a no-op).
- Reproduction: throwaway probe (`scratchpad/mut3/zz-r3-probe2.spec.ts` / `zz-r3-probe3.spec.ts`, copied into `e2e-components/` only for the run). Viewport 640x360, both arrangements. The inline frame measures 640x360 at top 56, the same size as the pinned box. Click Full screen, wait 700ms, count `Element.animate` calls, sample the frame before each paint.
- Observed at the SHA: in 4 of 30 runs (2 of 20 in probe2, 2 of 10 in probe3; both arrangements), 0 animations. The samples go `640x360@56 → 640x360@0F`, a snap. The exit is then instant as well. In the other runs the entry is carried.
- Mechanism: the observer's first observation can land before the commit that adds `fixed`. `isPinned` is false then, so it returns. The pin itself changes no size, so no second observation comes, and after 500ms the watch gives up.
- At `0cdfd1bd2` (second worktree): 0 of 30 uncarried. That tree broke invariant 3 in the same arrangement in another way, though. Its size test matched the *unpinned* frame, because the inline size already equalled the viewport. On the first run the VideoPlayer arrangement painted one frame at `640x360@112`, before it was pinned: the frame 56px below its slot. So the fix changes how this arrangement fails, but it still fails.
- Reach: this needs a viewport whose size equals the inline frame's box, which means a full-bleed frame and an exact 16:9 viewport. The spec's two orientations (393x851, 851x393) never produce that.

### F2 [introduced] (by the PR, since `3d16b9248`, and not changed by `91925de17`) With the same arrangement, the exit leaves the frame drawn 56px below its slot for about 490ms
- Invariant broken: none of R-0 as written. Invariant 2 holds once the watch times out, and invariant 5 holds because `#after-player` does not move. What happens is that an unpinned frame is drawn off its slot. The e2e oracle `expectCarried` would reject that frame (top 112 is outside [0, 56]), but no case runs at this size.
- Where: `useFrameTransition.ts:233-237`. The exit holds its last keyframe (`fill: "forwards"`) and waits in `watchPin(frame, false, …)` for an observation that never comes, because unpinning does not change the size. It clears only on the 500ms timeout.
- Reproduction: `zz-r3-probe3.spec.ts`, 640x360, both arrangements, `--repeat-each 5`: enter, wait 700ms, Escape, sample for 900ms, and count the samples where the frame is not `fixed` and still has a transform.
- Observed at the SHA: every run whose entry was carried (8 of 8) had 59-60 painted frames at `640x360@112` (not fixed, `translate(0, 56px)` held), over 482-491ms, before it dropped to `@56`.
- At `0cdfd1bd2`: identical, 10 of 10, 59-60 frames over 483-494ms.
- Same cause as F1. The observer stands in for a pin-change signal it does not carry.

## Q2 — is the author's cause right?

It is consistent with the code, and it reproduces in Chromium if `innerWidth` is made to behave the way the author says iOS does. I could not make Chromium's own zoom produce it:

- `Emulation.setPageScaleFactor(2)`: `visualViewport` becomes 196.5x425.5 at scale 2, but `innerWidth`/`innerHeight` stay 393x851. The pinned frame's `offsetWidth`/`offsetHeight` are 393x851, and `getBoundingClientRect()` of the inline frame does not change (`top 56`). Entry and exit keyframes are the same at both SHAs.
- `Input.synthesizePinchGesture` (scale 2, touch): the same arrangement shows `visualViewport.scale` 2, offset (98, 150), and `innerWidth` still 393. In the VideoPlayer arrangement the gesture did not zoom at all (scale 1). Behaviour is the same at both SHAs.
- With `innerWidth`/`innerHeight` overridden to 196x425 (an init-script getter, standing in for the reported iOS behaviour), 20 runs per tree:
  - at `0cdfd1bd2`: the entry is **not** carried (0 animations; the size test never matches), and the exit **is** animated. It grows `393x851 → 423x917 → … → 787x1704`, then snaps to `393x221@56` when the unpin clears the held look. That is the user's "grew and then shrank".
  - at the SHA: entry and exit are both carried with the correct keyframes (`translate(0px, -258.97px) scale(1)`). The exit shrinks from `393x851@0` to `@-259`, then `393x221@56`.
- What I cannot observe: whether iOS WebKit actually reports the visual viewport in `innerWidth` under pinch zoom, and whether its `getBoundingClientRect()` stays relative to the layout viewport, which the captured inline rect relies on. That needs the device.

## Trajectory

The fix diffs, in order:

- `0cb7453a0` (r1): **replaces** a mechanism (the slot moves from a padding that can transition to a `::before` that exists or does not). Its test half **adds a prediction**: the sampler exemption for a frame that covers the viewport, which absorbs the caller-lag state.
- `61cce0f28`, `a00e12694` (r1/r2): tests only. They add e2e cases for the interrupted entry and the reversed exit. No branch or state in code.
- `0cdfd1bd2` (r2): tests only. It **relaxes** a prediction: the sampler's minimum frame count becomes "the sampler ran".
- `91925de17` (R-5): **removes** a prediction and a branch. The prediction was "pinned ⇔ border box equals `innerWidth`×`innerHeight`±1"; `viewport()` and `isPinnedSize()` go. The branch was "still waiting for the pin", now folded into `!pinned`. It swaps one field of state (`viewport`, set at capture) for another (`pinned`, set on match). It adds no case.
- `1a8365fdc`: tests only (the failure message).

Answer to the question: no round's code fix adds a branch, a state or a prediction that the round before it also added. `91925de17` is the shape of a loop that is converging. It replaces an inference about the caller's pin with a reading from the frame.

What it leaves: the *trigger* for that reading is still an inference. A ResizeObserver stands in for "the caller changed its pin classes". It sees a pin change only when the size changes too, and it falls back on a 500ms timeout. F1 and F2 are that proxy's failure mode. r2 recorded a watch-for: the same caller/hook gap handled in CSS (the `.fixed` selectors), then in the test oracle (the exemption). A fix for F1/F2 that adds one more case would be the third accommodation of that gap. Examples: a special case for equal sizes, a MutationObserver alongside the ResizeObserver, a longer or smarter timeout. The r2 question applies then: should the hook be told the pin, or own it, rather than watch for it? The supervisor decides that. I have not assigned C.
