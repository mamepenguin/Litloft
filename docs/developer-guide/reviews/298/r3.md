### F1 — a collection that is loading or not found shows the toggle with no pane under it

`[introduced]` · R-0 #7 ("a screen without the tree pane … shows none") · `frontend/src/components/TreeToggle.tsx:24-25`, `frontend/src/components/CollectionDetail.tsx:198-221` · low

`CollectionDetail` mounts its own `TwoPaneLayout` only after `getCollection` resolves; the `loading` spinner and the `notFound || !detail` page return before it. `TreeToggle` decides by URL alone, and `/drive/<d>/collections/<id>` passes. So the toolbar offers the toggle while the collection loads and on its not-found page (which is also what a locked or mistyped collection shows). Pressing it on the not-found page writes the drive's stored tree flag with nothing visibly changing.

### F2 — below 768px with a file open, the toolbar toggle does nothing visible and arms a full-screen tree for later

`[introduced]` · none (R-0 #7 literally asks for the toggle here: the pane is mounted) · `frontend/src/components/Header.tsx:67-71`, `frontend/src/components/folder/TwoPaneLayout.tsx:93-98` · medium (user-reachable on a phone in the common "open a file from a folder" path)

Below `md`, `TwoPaneLayout` gives the aside `w-0` whenever a file is open, whatever the tree state. At the parent the only toggle on that screen was the file-detail chrome's, wrapped in `hidden md:flex`, precisely because it has no effect there (the comment removed at `FileDetailChrome.tsx` said so). The toolbar toggle has no width condition, so on a phone with `?file=` it is visible; pressing it sets `treeNarrowOpenStore` and flips `aria-pressed` to true, the aside stays `w-0`, and when the reader backs out of the file the folder is replaced by the full-viewport tree they did not ask for at that moment.

Reproduction: temporary test, `matchMedia` false for every query, pathname `/drive/main/videos?file=abc`, real `Header` + `DriveLayout` + `TwoPaneLayout` (RightPaneFile / FolderTreePane stubbed).

- `60a4ce29`: toggle slot classes `mt-3 self-start ml-11` (no width gate). Before click aside `w-0`; after click `aria-pressed=true`, aside `w-0 md:w-[280px]` (still 0 below md); after clearing `file`, aside `w-[100vw]` and the section `hidden md:flex` — the folder is gone behind the tree.
- `13e460cc`: rendering `Header` + `FileDetailChrome` with the same route gives one tree button, parent class `hidden md:flex`, none in the header.

### F6 — for part of the sidebar's 150ms slide-in, the toggle sits under the menu button

`[introduced]` · R-0 #7 ("clears the fixed menu button whether the sidebar is closed, over the page, or beside it") — violated only in the transition between the named states · `frontend/src/components/Header.tsx:22,68`, `frontend/src/components/AppShell.tsx:44,54-55` · low (cosmetic, transient; the menu button is `z-50` and keeps the clicks)

This is a defect this commit introduced, not noise. `Header` flips its margin from `ml-11` to `-ml-1` in the same render in which `AppShell` switches on `min-[1200px]:pl-60`, but only the padding is transitioned (`transition-[padding] duration-150 ease-out`). The toggle's left edge is `padding(t) + 16 − 4`; the menu button spans x=12–52; so the two overlap until the padding passes 40px. The direction matters: going inline → closed/over, the margin jumps to `ml-11` first and the toggle is always right of the button (no overlap); going closed/over → inline, it starts at x=12, directly under the button. At ≥1200px that direction happens (a) when the tree is switched off and the stored sidebar preference is open (`useOverlaySidebarWhen` releases, the provider restores `isOpen`), (b) when the menu button opens the sidebar inline, and (c) on every load at ≥1200 with the preference open, because the provider renders `isOpen=false` until hydration (`useSidebar` then returns `defaultValue`, which `Header` and `AppShell` read identically, so the pre-hydration frame itself is consistent: toggle at x=60, no padding). Arithmetic from the classes; not re-measured in a browser here — it agrees with the author's observation. At the parent the toggle lived inside the page column and moved with the padding, so it could not meet the fixed button.

### F7 — at ≥1200px with the sidebar preference open, pressing the toggle moves it 192px

`[introduced]` · none · `frontend/src/components/Header.tsx:68`, `frontend/src/components/folder/TwoPaneLayout.tsx` (`useOverlaySidebarWhen(treeBeside)`) · medium (design question; raise, do not fix here)

Tree off, sidebar beside: toggle at x = 240 + 16 − 4 = 252. Press it: the tree opens, `useOverlaySidebarWhen(true)` makes the sidebar overlay and closes it, the toggle goes to x = 16 + 44 = 60. Press again at 60 and it returns to 252. So the control that DESIGN.md now says "stays put whichever page or file is open" leaves the pointer on every press in the default wide configuration (sidebar preference defaults to open, `readStoredPreference`). At the parent the toggle rode in the page column: tree off + sidebar inline → 240 + 16 = 256; tree on + sidebar over → 280 (aside) + 16 = 296 — a 40px move. Offered for the supervisor as a possible C: the sidebar-state branch in `Header` exists to follow the menu button, and the tree toggle is the very control that changes the sidebar state it follows. Arithmetic from the classes; not measured in a browser.

"Before `useCurrentDrive` resolves" does not exist on drive routes: the provider parses the drive from the pathname synchronously, and decodes it the same way the layout decodes `params.name`, so the toggle and the pane read the same store key. On non-drive routes with a stale override the slot `div` renders empty; it has no width and sits before the spacer, so nothing moves.

## Trajectory question

In order: `e535760b` **removed** an option (PageFrame's `className`), a state a caller could set. `353bdf4a` is test-only (fixture lays the frame out in a flex column) and adds no branch in product code. `60a4ce29` removes a branch (`FileDetailChrome`'s `showTreeToggle`), removes three `leading` placements and the cross-file height prediction `headerAlignmentParity` encoded, and adds two things: a sidebar-state branch in `Header` (`ml-11` / `-ml-1`) and a route predicate in `TreeToggle` (the `/drive/` guard plus `includeStandalone`). No two consecutive commits each add a branch, state or prediction, so by the R-4 test this is **converging, not being patched**. One caution for the next round: the new `Header` branch is itself a prediction of another component's layout (MenuButton's fixed box and AppShell's padding), and F6/F7 are both consequences of that prediction. A fix to F6 that adds a transition, a delayed state or a second predicted offset would be the second consecutive add and should be read as the design being patched.
