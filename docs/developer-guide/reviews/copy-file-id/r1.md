## Findings

### F1 — MEDIUM [introduced] [needs-browser] The card / list / tree menu calls copyText from `requestAnimationFrame`, outside the click handler

- `frontend/src/components/ContextMenu.tsx:80` runs `item.onClick` inside `requestAnimationFrame`; the new
  `onCopyId` in `frontend/src/components/FileContextMenu.tsx:120-122` -> `handleCopyId` (`:97-104`) -> `copyText`
  -> `document.execCommand("copy")` therefore runs one frame after the click event has returned.
  `FileActions` (`frontend/src/components/FileActions.tsx:175-178`, `ActionMenuItem onClick={item.onClick}` at `:206`)
  calls it synchronously inside the click.
- Scenario to verify: Safari / iOS Safari on `http://<lan-ip>:3000` (no `navigator.clipboard`, so execCommand
  is the only path). WebKit gates `execCommand("copy")` on a user gesture being processed; a rAF callback is
  not one. If it returns `false`, every Copy ID from a card, list row or tree row opens the manual dialog,
  while the same action from the file page's "…" copies. Chrome/Firefox use transient activation (~5 s) and
  are expected to succeed.
- Invariant: none broken (the fallback dialog is the designed failure state), but the feature's primary
  target (phones on plain-http LAN) may never get the one-tap copy from the surface they use most.
  Invariant 6 holds positionally; the two surfaces differ in behaviour.
- Also check after `await` of a rejected `writeText` on a secure origin: the fallback then runs after a
  microtask/await; same question.

### F2 — MEDIUM [introduced] [needs-browser] "Fully selected" is asserted without focus; on iOS the dialog may open unselected

- `frontend/src/components/CopyIdDialog.tsx:19-25`: the open effect does `el.focus(); el.select()`.
  Mutations D2 / D14 (remove `focus()`) survive: both host tests check only `selectionStart/End`, which jsdom
  reports on an unfocused input. A selection on an unfocused input is not what Ctrl/Cmd+C or the iOS callout copies.
- On iOS Safari, `focus()` from an effect that runs after a rAF (F1) and/or an `await` is not a user gesture
  and is ignored, and the commit's own `copyText.ts:39-40` states iOS ignores `select()` on a read-only field.
  The `onFocus` reselect (`:37-38`) then never fires. Expected result on iOS: the dialog opens with nothing
  selected and the viewer must tap the field (the `onClick` reselect should then work — verify).
- Invariant 4 ("fully selected") holds in jsdom and is unverified where it matters. Test-side: add
  `expect(document.activeElement).toBe(input)` to the host dialog tests so D2 is killed.

### F3 — LOW [introduced] Dialog dismissal is untested on the card surface, and scrim / X are untested everywhere

- C7 (FileContextMenu dialog `onClose` no-op, `frontend/src/components/FileContextMenu.tsx:163-167`) survives:
  a card/list/tree Copy ID dialog that could not be closed would pass.
- D8 (backdrop without `onClick`, `CopyIdDialog.tsx:42-45`) and D9 (header X without `onClick`, `:59-65`)
  survive on both surfaces; the spec lists Esc / scrim / Close as dismissals.
- No R-0 invariant covers dismissal (see "missing from the list").

### F4 — LOW [introduced] [needs-browser] With focus off the ID field, Cmd/Ctrl+C in the dialog copies the *selected files* instead

- `CopyIdDialog.tsx:28-33` registers its context without `blocksLower`. `FolderBrowser.tsx:316-324` binds
  `ctrl+c` (editingOnly undefined -> fires only when no input is focused) to `clipboard.copy(selectedIds)` +
  `selection.clear()`.
- Scenario: in selection mode with files selected, right-click a card -> Copy ID -> the copy fails -> dialog.
  The viewer clicks the dialog's title or help text (focus goes to `<body>`, the input's selection is lost),
  then presses Cmd+C to "copy the selected ID" as the help text instructs. The FolderBrowser handler
  `preventDefault`s, puts the selected files on the file clipboard (paste banner appears) and clears the selection.
- Brushes against invariant 1 (the file clipboard changes while the Copy ID dialog is up), though strictly it is
  a keypress, not "choosing Copy ID". The same shape exists for RenameDialog, but this is the one dialog whose
  instruction is "press copy". Reachable only with a non-empty selection.

### F5 — LOW [introduced] Copied id and displayed id are read at different times in FileContextMenu

- `FileContextMenu.tsx:97-104` passes the `target.id` captured at click time to `copyText`, but on failure the
  dialog renders the *current* `target.id` (`:165`). If `target` changes during the `await` (secure origin,
  slow `writeText` rejection, viewer right-clicks another card meanwhile — the menu is already closed and the
  page is interactive), the dialog shows the other file's id. Practically unreachable on the http path
  (execCommand is synchronous). Invariant 4 ("value exactly file.id") in principle.

### F6 — LOW [pre-existing] [needs-browser] FileContextMenu renders its dialogs in place, not through the dialog portal

- `CopyIdDialog` in `FileContextMenu.tsx:163-167` is rendered where the menu is mounted (inside FileGrid /
  FileList / CarouselSection / ContinueWatchingSection / FolderTreePane), while `FileActions` portals it
  (`FileActions.tsx:339-347`). A `transform`/`filter`/`contain` ancestor would turn its `fixed inset-0` into a
  box inside that ancestor; a lower stacking context (sticky header z-20, mobile sheet) could cover it.
  RenameDialog / MoveDialog / ConfirmDialog / CollectionPicker in the same component have the identical
  shape, so this is the existing pattern (the spec's "Through DialogPortal" is not followed here, consistent
  with the siblings). Verify once in a carousel section and in the tree pane on a phone width.

## Is anything missing from the R-0 list?

1. **The dialog can be dismissed on every surface** (Esc, scrim, Close) — nothing declares it, and C7 / D8 / D9 survive.
2. **The ID field has focus when the dialog opens**, not only a selection range — invariant 4 as written is
   satisfiable by an unfocused input (D2 / D14).
3. **Copy from the card/list/tree menu succeeds where it succeeds from the file page** (same browser, same
   origin). Not testable in jsdom (F1); it belongs in the R-5 run on iOS Safari over plain http.
