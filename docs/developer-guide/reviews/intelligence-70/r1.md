## Findings

### F-1 [introduced] "Enter the IME still owns" tests do not hold either signal on their own (both files)

Summary: `does not ask on an Enter the IME still owns` (Page.test.tsx) and `does not search on an Enter the IME still owns` (search-compare.test.tsx) fire their `isComposing: true` and `keyCode: 229` Enters right after the setup helper's `compositionEnd`, with the real clock. The grace window is still open, so either Enter is consumed by the grace branch even when the signal it is named for is not checked. The `isComposing` Enter does not reset the window (it returns before the grace branch), so the 229 Enter that follows is also inside it.

Mutation evidence (core `frontend/src/lib/ime.ts`, diff shown before each run, tree restored and verified after):
- C1 `if (native.isComposing || native.keyCode === IME_KEY_CODE)` -> `if (native.keyCode === IME_KEY_CODE)`; want=kill in both addon tests; result: both addon IME tests pass (32/32, the only failure seen was the pre-existing flaky seed test, see F-4). Survivor.
- C2 same line -> `if (native.isComposing)`; want=kill; result 32/32 pass. Survivor.
- Core's own `src/lib/__tests__/ime.test.ts` kills C1 and C2 (`claims every key the IME still owns`), so the core hook is held; what is not held is the addon-level claim of invariants 2 and 4 as written.
- Fixture check: spying `Date.now` at 1_000_000 before the helper and advancing to `+ COMPOSITION_GRACE_MS` before the two Enters. Fixture alone: 32/32 pass (want=live). Fixture + C1: both addon IME-still-owns tests fail (want=kill). Fixture + C2: both fail (want=kill). So the fix is the fixture, not the code.

Invariants: 2 and 4 are not broken by the code, but the tests presented as holding them would let a grace-only guard through. Suggested bucket: B unless the supervisor treats the addon tests as the holder of 2/4 (then A per "a test that lets an A through").

### F-2 [introduced] search-compare test does not observe a non-Enter key triggering a search

Summary: new `search-compare.test.tsx` never presses a key other than Enter, so removing the `e.key === "Enter"` condition survives.

Mutation evidence: S4 `if (e.key === "Enter") void handleSearch();` -> `void handleSearch();`; want=kill; result 3/3 pass. Survivor (not inert: a `keyDown` of e.g. `{ key: "a" }` after the grace window, asserting 0 calls, would observe it). User-visible effect of such a regression: every keystroke fires a search request.

Invariants: none on the list (4/5 only speak about Enter). Raised as a candidate for the list; see "Missing from the invariant list".

Mutation evidence:

- Base `17a420d` `Page.test.tsx` has no `keyDown` at all, so both gaps predate this PR. Ledger item, not for this PR.

## User-reachable behaviour checked, no finding

- Composition ended by mouse click, then a real Enter within 100 ms: consumed, the next Enter sends. Humanly implausible; this is the core hook's accepted trade.
- Escape: neither field handles Escape; a consumed Escape only returns from the local handler, so nothing else is suppressed.
- `ragAvailable === false`: textarea is `disabled`, no key or composition events reach it; unchanged.
- `?q=` seed flow: the auto-run effect and seeded `useState` are untouched.
- Removing `composing`/`onCompositionStart`: in base, `composing` was read only by `handleInputKeyDown`; nothing else in Page.tsx referenced it.
- Not measurable here, for the R-5 device check: in the Ask textarea the consumed confirming Enter returns without `preventDefault` (base called `preventDefault` on it, since `composing` had already flipped false). If a browser performs a default line break for that post-`compositionend` keydown, the text would gain a newline (invariant 1 "the text stays"). jsdom performs no default actions, so no test here can show it either way; all core `isImeKeystroke` callers that return early appear to be single-line fields, so core gives no evidence either.
