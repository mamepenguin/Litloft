## 1. The one behaviour change in this commit is held by no test  [introduced]

`frontend/src/app/globals.css:1023`

The commit's only change to shipped behaviour is narrowing the selector to
`:root[data-player-fullscreen] [data-sheet-snap] [data-pseudo-fullscreen]`.
Reverting that narrowing is invisible to every suite.

Mutation (`want=kill`): drop the `:root[data-player-fullscreen] ` compound,
restoring the parent's selector exactly.

Result: **survived.**

- `pnpm test:e2e:layout pseudo-fullscreen` — 6 passed
- every jsdom test that reads `globals.css` as text, plus the player hooks —
  13 files / 337 tests passed
  (`mediaDetailTheaterCss`, `archiveJustifiedCells`, `MediaPlayerBlock`,
  `justifiedGrid`, `design-tokens`, `line-clamp-display`, `section-rows`,
  `tailwind-scans-addons`, `coarseNeedleSources`, `useJustifiedFlip`,
  `src/components/player/hooks`)

Nothing can catch it. The layout fixture's `marked` flag sets
`data-player-fullscreen` on the root and `data-pseudo-fullscreen` on the frame
**together** (`fixtures/pseudo-fullscreen.html:78-83`), so no fixture state
exists in which one is present without the other — which is the only state the
qualifier changes. `mediaDetailTheaterCss.test.ts` is the repo's text detector
over `globals.css`, and it reads the `.media-detail-player` rules only; it never
mentions `[data-pseudo-fullscreen]`.

Failure scenario: the qualifier reads as redundant next to the sibling rule two
lines above it, so a later tidy-up removes it and the tree stays green. The
frame mark is then back to granting `z-index: 60` to any element carrying it
inside `[data-sheet-snap]`, regardless of the root attribute — the state round
one measured and found inert. It is inert only because
`[data-sheet-snap] .media-detail-player` is `position: sticky; z-index: 10`
again once the root attribute is gone, and that box traps the 60. That guard
lives in a different rule, nothing ties the two together, and the qualifier was
exactly the thing that made the dependency unnecessary.

This is the same shape as round one's findings 1 and 2, one commit later: the
mechanism that makes the fix work is not held by anything.

## 2. The narrowing removed a kill: the suite no longer holds that the tier sits on the frame  [introduced]

`frontend/src/app/globals.css:1023`

The rule's own comment states the load-bearing claim — the tier goes "on the
frame rather than on the box", because a tier carried by an ancestor is what
iOS WebKit ignored. After this commit no test distinguishes the two.

Mutation (`want=kill`): drop the selector's subject, leaving
`:root[data-player-fullscreen] [data-sheet-snap] { z-index: 60 }` — the tier on
the shell, an ancestor, instead of on the frame.

Result at `0bf4ccb9`: **survived** — 6 passed. The shell then makes a stacking
context that outranks the chrome buttons (`fixed z-50`, a root sibling), so
every hit-test point still resolves to the frame.

Reproduction against the parent, to earn the label: I put the selector back into
`a6cf0a2c`'s form and applied the same mutation, giving
`[data-sheet-snap] { z-index: 60 }`.

Result at the parent's form: **killed** — 3 failed / 3 passed. Unqualified, the
rule also fires in the unmarked states, and the two "an unmarked pinned frame is
covered" tests plus one inline case catch it.

So the narrowing traded a kill away. Before this commit a mutant that moved the
tier off the frame onto an ancestor was caught (by accident — it was caught for
firing in the wrong states, not for the wrong subject); after it, the same
mutant is silent. Failure scenario: someone simplifies the rule onto the box
because "the box is the thing that was lifted before", every suite passes, and
on iOS the `.loft` goes straight back to drawing under the header — the exact
defect `a6cf0a2c` exists to fix, with no signal anywhere.

The fixture can hold this: it needs a state in which the frame carries the mark
and the ancestor does not, which is also the state finding 1 needs.

## The trajectory

**No. Round two subtracts where round one added, and it adds no branch, no
state and no prediction of its own.**

Read in order:

- `a6cf0a2c` removed `z-index: 60` from the box and replaced it with
  `position: static`, then **added** one DOM state (`data-pseudo-fullscreen` on
  the frame, with a write and a cleanup in `useFullscreen.ts`) and **added** one
  CSS rule keyed on it. Net: one rule became two, and one new piece of state
  entered the system.
- `0bf4ccb9` adds one **condition** to that rule, three tests, and deletes a
  clause of prose. It writes no new state, adds no code branch, and makes no new
  prediction about what the browser will do.

The condition is not "one more case the last round did not anticipate" in the
patching sense. It does not handle a newly discovered state — it makes that
state unreachable by construction, so the set of configurations the CSS has to
be right about shrinks. By the rule's own test ("a round that *removes* a
branch, a state or a prediction is the loop converging"), this round converges.

**What I would put in front of the supervisor instead** is not the shape of the
fixes but the branch both rounds are working on.

`docs/superpowers/specs/2026-09-21-loft-pseudo-fullscreen-unstick.md`, under
`## Checked, no action`, decides:

> **The `z-index: 60` lift is not kept as a belt-and-braces.** It is what the
> measurement showed to be ineffective on the surface that needed it; keeping it
> leaves a branch nobody can justify.

and `## The decision` says the frame should end up "a plain `fixed` box in the
root stacking context at `z-50`, above the header's `z-20`".

`a6cf0a2c` kept the `z-index: 60`, moved onto the frame, and `0bf4ccb9` spent
its only behavioural line refining it. Both rounds of review have now gone into
a rule the design document says should not exist.

I checked whether the divergence is justified rather than calling it a defect,
and it is. The spec's sentence accounts for the header (`z-20`) but not for
`ChromeButtons` (`fixed left-3 z-50`, later in the DOM), which beats a `z-50`
frame on document order. Mutation `z-index: 60` → `auto` (`want=kill`):
**killed** both "a marked pinned frame is on top everywhere" tests, on
`underMenuButton`. So the rule is load-bearing in Chromium, the reason is
measured, and `globals.css:1021-1022` records it. This is the design evolving
during implementation, which `CLAUDE.md` allows — but nothing but this report
says the spec was overruled, and that is a supervisor's call, not mine.
