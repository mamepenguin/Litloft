## Findings

### F1 — LOW [introduced] One Escape answers two layers: the new-folder field and the `…` menu

- Where: `frontend/src/components/folder/FolderToolbar.tsx:138-154` (new Escape layer,
  `editingOnly: false`) together with the existing field handler at
  `FolderToolbar.tsx:185` (`onKeyDown` → `Escape` cancels New Folder, no `stopPropagation`).
- Scenario: New Folder field is open (`creatingFolder`). User opens `…` with the keyboard,
  Tabs past the last row (nothing traps focus) into the name field (from 768px it follows
  `…` in DOM order), presses Escape. The field is cancelled **and** the menu closes and
  focus jumps to the `…` trigger — one key, two answers, and the focus the user had in the
  field's row is taken away.
- Reproduced in jsdom (scratch test, deleted):
  at `40863c3c` → `onSetCreatingFolder(false)` called, menu closed, focus on trigger;
  at `8d46f8ad` (parent `FolderToolbar.tsx` swapped in) → `onSetCreatingFolder(false)` called,
  menu **still open**, focus not moved. The difference is the new layer.
- Reachable only by keyboard: a pointer press on the field hits the `…` scrim first.
- Invariant: none of the declared eight (see "missing invariants").
- Reasoning only (jsdom cannot show stacking): the Add menu and `…` can also be open at
  once by keyboard (open Add, Tab out to the `…` trigger, Enter). Both layers are
  `OVERLAY_PRIORITY`; the later push (`…`) wins, so Escape closes `…` then Add — two
  presses, in a sensible order. Not a defect; noted because the plan listed it as a risk.
  The two cannot co-exist by pointer (each scrim swallows the press on the other trigger).

### F2 — MEDIUM [introduced] The `moreOpen` term of the Escape layer's `active` expression is held by no test

- Where: `FolderToolbar.tsx:152` (`moreOpen && !moreDialogOpen`).
- Mutation M11 (`!moreDialogOpen` alone) survives the **whole suite**. Under it the
  toolbar pushes an `OVERLAY_PRIORITY` Escape layer permanently, so on every Library
  listing Escape is taken by `closeMore()` (which also moves focus to the `…` trigger)
  instead of reaching lower layers — e.g. `Sidebar.tsx:257-262` `sidebar-overlay` (priority 0),
  so on a phone Escape would stop closing the sidebar drawer over a folder.
- Reproduced: a scratch test that registers a priority-0 Escape context beside a closed
  toolbar and presses Escape passes at `40863c3c` and fails under M11. The test file adds
  no "menu closed → Escape goes elsewhere" case.
- Invariant: none declared (see "missing invariants"); the regression is user-reachable.

### F3 — LOW [introduced] The flag-clearing effect is held by no test

- Where: `FolderToolbar.tsx:132-134`.
- Mutation M8 (effect removed) survives the whole suite. The only close path the test
  "does not survive the menu closing" (`FolderToolbar.bulkMenu.test.tsx:244`) takes is
  `onRequestClose` → `closeMore()`, which clears the flag itself (M7, removing that line,
  is also live on its own; only M7+M8 together are killed). The effect exists for close
  paths that bypass `closeMore()` — the trigger's own toggle (`setMoreOpen((s) => !s)`),
  reachable by keyboard Enter on a focused trigger while an entry has reported a dialog.
- Scenario under M8: entry reports dialog open → menu closed via the trigger toggle →
  reopened → Escape and outside presses are ignored for the life of that menu.
- Reproduced: scratch test (report dialog, click trigger, reopen, Escape on trigger →
  expect closed) passes at `40863c3c`, fails under M8.
- Invariant 6 (the path through which it would break).

### F4 — LOW [introduced] `OVERLAY_PRIORITY` on the `…` layer is held by no test

- Where: `FolderToolbar.tsx:153`.
- Mutation M13 (priority `0`) survives the whole suite. Effect: an Escape context of equal
  priority that (re)pushes after the menu opens would take Escape ahead of the menu
  (`orderContexts` sorts by priority, then later push). No such context re-pushes while
  the scrim is up in the current page as far as I can see, so today's user impact is low;
  the survivor is the finding.
- Invariant 6.

### F5 — LOW [pre-existing] Invariant 3's gate is derived in `FolderBrowser`, and two of its three terms are held by no test

- Where: `frontend/src/components/FolderBrowser.tsx:124` (`isLocation = !isSpecialView && !isSearch && …`).
- Mutations M26 (drop `!isSearch`) and M27 (drop `!isSpecialView`) survive the whole suite.
  Under either, `isWriteDestination` is true on search results / a special view whose
  `folderPath` is defined, so the bulk slot (and, already, the Add menu and paste) would
  render there. M25 (the tag-at-root term) is killed by
  `FolderBrowser.folderAnchor.test.tsx:477` and `FolderBrowser.paste.test.tsx:210`.
- The new cases "offers nothing on search results / a special view"
  (`FolderToolbar.bulkMenu.test.tsx:126-134`) pass `isWriteDestination: false` by hand, so
  they hold only `showBulkRows`'s single term, not the derivation their names describe.
- Labelled pre-existing: the derivation and its test coverage are unchanged by this commit;
  whether `FolderBrowser` actually passes `folderPath` on a search / special view was not
  measured.
- Invariant 3 (at Phase 3, once a declarer exists).

### F6 — LOW [pre-existing] Bulk rows are gated on "write destination", which includes a tag-filtered sub-folder and a type/trust-filtered folder

- Where: `FolderBrowser.tsx:130-131` (`folderPath !== "" || !tagFilter`) feeding
  `FolderToolbar.tsx:121`.
- A sub-folder with a tag applied, or any folder with a type/trust filter, is a write
  destination, so the slot renders there with `fileIds` = the filtered, loaded subset.
  Invariant 3 names only "a tag-filtered root"; the spec's §1 wording says "not search /
  tag filter / special views", and `## Checked, no action` defers Option B precisely
  because "`fileIds` means loaded rows, whose meaning differs per view".
- Pre-existing: at `8d46f8ad` the Add menu (and intelligence's AI rows in it) shows under
  the identical gate, so Phase 3 moves the rows without widening or narrowing where they
  appear. Raised as a question for the supervisor, not a defect in this commit.
- Invariant: none broken as written.

## Missing from the invariant list?

Yes, two, both observable and both violated by a surviving mutation or a reproduction:

1. **With the `…` menu closed (or an entry's dialog reported), Escape reaches the layers
   beneath the toolbar as it did before** — e.g. the phone sidebar drawer closes on Escape
   over a folder. (M11 breaks it with the suite green; F2.)
2. **One Escape closes one layer**: with the New Folder field focused while `…` is open,
   Escape cancels the field and leaves the menu as it was (or the reverse — pick one).
   (Currently both; F1.)

And one to decide rather than add blindly: invariant 3 names a tag-filtered **root**, but a
tag-filtered sub-folder and a type/trust-filtered folder still get the rows with a filtered
`fileIds` (F6). Either the list says so, or the gate changes in a later phase.
