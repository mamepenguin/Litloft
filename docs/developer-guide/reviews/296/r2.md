## Q1 — did the fix do what it claims for F1–F4?

- **F1** (New Folder field Escape also closing `…`): yes. `FolderToolbar.tsx:188-193`
  calls `e.stopPropagation()` on the synthetic event, which stops the native event before
  it bubbles to `ShortcutsProvider`'s `document` bubble-phase listener
  (`ShortcutsProvider.tsx:118`). Held by "answers an Escape in the New Folder field once"
  (N1 and N10 killed).
- **F2** (`moreOpen` term unheld): yes, "leaves Escape to the layer beneath while the menu is
  closed" kills M11 (N2).
- **F3** (flag-clearing effect unheld): yes, "does not survive the trigger closing the menu"
  kills M8 (N4).
- **F4** (`OVERLAY_PRIORITY` unheld): yes, "keeps Escape from a layer that registers after the
  menu opened" kills priority 0 (N3), and only because the layer registers late (S2).

What the `stopPropagation` could break, checked:

- **Other shortcut layers.** It only affects Escape pressed *inside that field*. Registry
  layers that could previously also answer that press are ones with `editingOnly: false`
  (e.g. Sort/Add menus, knowledge `CaptureBasket`, `QuickNoteContainer`); with the field
  focused, those were a second answer to the same key, which invariant 10 now forbids. No
  layer found that a user relies on to receive Escape *from the New Folder field*.
  `DismissScrim`'s `keydown` listener is capture-phase (`DismissScrim.tsx:80`) and is
  unaffected. No `window` keydown listener is mounted on a folder page
  (`DetailedSummarySection.tsx:734` is file-detail only).
- **Mobile row vs desktop bar.** `createFolderRow` is one JSX value rendered twice
  (`FolderToolbar.tsx:226` and `:423`), so both inputs carry the same handler. The test uses
  `textbox[0]` (the `md:hidden` row); the desktop copy cannot diverge from it.
- **IME.** `ime.isImeKeystroke(e)` returns before `stopPropagation`, so a composing Escape
  still bubbles; `ShortcutsProvider` has its own IME guard and ignores it, so `…` is not
  closed by a composition-cancel Escape. Moving `stopPropagation` above the IME guard (N7)
  is live and equivalent in jsdom. Unchanged from `40863c3c` in behaviour.
- **Other `onKeyDown` Escapes in `FolderToolbar.tsx` and its children:** `FilterMenu.tsx:73-78`
  and `ToolbarMenu.tsx:129-135` (Sort/View) already stop propagation; `AddButton` uses the
  registry. None left inside the toolbar tree. **Outside** the toolbar tree, on the same
  page, the same double answer remains — G1.

## Q3 — trajectory

`40863c3c` added: an Escape layer with the prediction `editingOnly: false` ("focus may be
anywhere, Escape must still close"), a state (`moreDialogOpen`), and a branch (the
flag-clearing effect). `69ec19be` adds **one branch** — `stopPropagation` in one field —
and no state; the rest of the commit is tests. That branch exists to contain a consequence
of round one's own prediction: an `editingOnly: false` overlay layer answers Escape from
*every* field on the page, and each field that handles Escape in React now needs its own
guard. G1 shows at least one more such site reproduced and two more by reading. So: this is
the first fix round, it adds a branch, and not yet two rounds in a row; but the shape of the
fix is per-site containment of a page-wide prediction, and a round three that follows the
same shape (adding `stopPropagation` to `FilterField`, `SelectionBar`,
`SidebarCollectionsSection`) would be the second consecutive round adding one — the
patching pattern. A shape that removes rather than adds would narrow the prediction
(where the `…` layer answers Escape) instead of guarding each field.
