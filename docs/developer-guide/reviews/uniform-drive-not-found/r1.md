# drive-oracle review, round 1

Reviewed: media_import `d67701568132eab0dc95f6a873f824dac55b2883` (parent `dd6545f`), worktree `review-wt2`.
Baseline: `pytest addons/media_import/tests` at d677015 -> 334 passed.

## Findings

### F1 — Invariant 4 (percent-encoded drive name decoded) is held by no test that uses the real lookup
- Severity: medium (a regression would lock every user out of every non-ASCII-named drive on all 20 routes, silently, with a 404 that reads as "locked").
- Label: `[pre-existing]` — the same mutation survives at parent `dd6545f` (M5p below). The change makes it more load-bearing: `check_drive_access` is now the only lookup, so the value passed to it is the only thing that decides existence.
- Invariant: 4 (and 2 for non-ASCII drives).
- Where: `backend/router.py:114-117` (`drive = unquote(...)` then `check_drive_access(drive, ...)`); the only test, `backend/tests/test_router.py` `test_percent_encoded_non_ascii_drive_is_decoded`, runs under conftest's fake `get_drive_access_group` that accepts every name. `backend/tests/test_drive_scope.py` uses the real lookup but only ASCII names (`secret`, `nosuch`), for which `unquote` is the identity.
- Reproduction: M4 (check the raw header, then unquote) and M5 (`check_drive_access(x_lit_drive, ...)`) -> 334 passed. M5 applied on top of the parent router -> only the 5 pre-existing oracle failures, the non-ASCII test still passes.
- Observation: with the real lookup and `drives.json` containing `動画`, the shipped code answers `X-Lit-Drive: %E5%8B%95%E7%94%BB` with 404 `File not found` / 200 `[]` (i.e. the drive is accepted). Under M5 it would answer 404 `Drive not found: %E5%8B%95...` and no test fails. A non-ASCII drive (accessible and locked) in `test_drive_scope`'s real-lookup `load_drives` would kill both mutations.

### F2 — `test_drive_scope` pins 5 of the 20 drive-taking routes; a route-local existence lookup survives on the other 15
- Severity: low (no route leaks today: every handler calls `_scoped_drive` first — see route table; the gap is a detector that cannot see a future per-handler lookup).
- Label: `[introduced]` (new test file).
- Invariant: 1 ("every media_import route").
- Where: `backend/tests/test_drive_scope.py:15-25` (`ROUTES`).
- Reproduction: for each handler, replace its `_scoped_drive(...)` call with a copy that answers an unknown drive with `404 "Drive not found"` before `check_drive_access` (mutation family L_*). Killed on `create_loft`, `get_loft_metadata`, `refresh_loft`, `generate_loft_stt`, `list_subscriptions` (1 failure each). Survives (334 passed) on `resolve_subscription_url`, `create_subscription`, `subscriptions_summary`, `patch_subscription`, `get_subscription_avatar`, `refresh_subscription_metadata`, `delete_subscription`, `sync_subscription`, `backfill_subscription`, `list_subscription_videos`, `retry_subscription_video`, `list_activity`, `list_watch`, `resolve_video_conflict`, `dismiss_video`.
- Observation: the list is hand-picked rather than enumerated. Detector rule 5 (declare the expected set) applies: declaring all 20 routes, or enumerating `router.routes` whose endpoint takes `x_lit_drive` and asserting the count with `toBe`-style equality (rule 1), would kill all 15.

### F3 — `test_drive_scope` compares status and JSON body only; a header that differs for unknown drives survives
- Severity: low (no such header today; probe shows identical header sets for locked and unknown on all 20 routes).
- Label: `[introduced]` (new test file).
- Invariant: 1 ("no header ... tells them apart").
- Where: `backend/tests/test_drive_scope.py:67-68`.
- Reproduction: M2 — in `_scoped_drive`, raise the same 404 and body for an unknown drive but with `headers={"X-Drive-Unknown": "1"}` -> 334 passed.
- Observation: the test asserts each case against a fixed expectation independently; it never compares the locked response to the unknown response. Comparing the two responses' `(status, body, headers minus date/content-length)` for equality per route would kill M2 as well as the body mutations.

All 20 routes answer locked and unknown identically at d677015; all 20 differed at the parent (F5 of the previous review was route-wide, not only the 5 routes the new test pins). Body/query `drive` mismatches (400) are evaluated after `_scoped_drive`, so they are only reachable for an accessible header drive and cannot distinguish locked from unknown. FastAPI validation 422s fire before the handler, independent of the drive.

Header input validation (GET /link/f1/metadata, real lookup): `%ZZ`, `%00`, `%2F`, `"   "`, `"secret "`, `SECRET`, raw latin-1 `é` -> all 404 `Drive not found: <decoded value>` — no 500, and each is indistinguishable from a locked drive of that name. `%73ecret` decodes to `secret` and gets the locked answer. Empty and absent header -> 400 (covered by `test_missing_drive_header_returns_400` / `test_absent_drive_header_returns_400`, killed by M8). Accessible drives with the real lookup: `drv`, unlocked `secret` (groups `["vip"]`) and `%E5%8B%95%E7%94%BB` for drive `動画` all pass the scope (404 `File not found` / 200 `[]`).

Invariant 5: every handler past `_scoped_drive` holds a name for which `config.get_drive_access_group` succeeded, i.e. a name present in `drives.json`; the later `config.get_drive_path` calls (`_validate_folder_path` on `sub["drive"] == scoped`, the loft manager on `request.drive == scoped`) therefore cannot raise for an unknown drive. No handler relied on the removed pre-lookup as its only guard. Holds, but it holds through core's `try/except ValueError` in `check_drive_access` (`backend/app/auth.py:186-191`); M6 (drop the check) is killed.

## Core `check_drive_access` (`[pre-existing]`, one line each)
- `[pre-existing]` `check_drive_access` answers unknown and locked with the same status and body (`auth.py:189-193`); the only difference is `get_drive_access_group`'s linear scan returning early for a found name vs. scanning the whole list for an unknown one — nanoseconds over a handful of entries, not observable over HTTP. Not filed as a finding.
- `[pre-existing]` `app/services/safepath.py:93` answers an unknown drive with a bare `404 "Drive not found"`, but its public callers (`routers/drives.py:754`, `:924`) run `_validate_drive` first, so it is not reachable as an oracle from those routes. Not filed as a finding.
