## Findings

### F1 [introduced] Medium — listing for a non-ASCII-capital tag now returns another rail entry's files on data an existing install can already hold (invariant 6)

Parent code creates two rows that differ only in ASCII case after a shared non-ASCII capital. Measured on parent:
`PUT f1 {"tags":["Übung"]}` -> 200, `PUT f2 {"tags":["ÜBUNG"]}` -> 200, rail `{'ÜBUNG': 1, 'Übung': 1}`
(parent lookup compares SQLite `lower(name)` = `'Übung'` against Python `'übung'`, never matches, inserts a second row).

With those rows present, at this SHA:
- rail `{'ÜBUNG': 1, 'Übung': 1}`, but `GET /files?tag=Übung` and `?tag=ÜBUNG` each list **2** files (both rows lower to `'Übung'` in SQLite). Parent listed 0. Invariant 6 ("returns exactly the files the tag rail counted for that tag") is broken in a new direction: over-listing instead of under-listing.
- `PUT f4 {"tags":["Übung"]}` still raises `IntegrityError: UNIQUE constraint failed: tags.drive, tags.name` (500): `.first()` returns the `ÜBUNG` row (index order), the rename branch sets it to `Übung`, the flush collides. `PUT ["ÜBUNG"]` happens to succeed because `.first()` hits the exact row. Which variant 500s depends on row order. Parent 500'd on both, so the 500 itself is [pre-existing]; the known-issue row removed from `known-issues.md` ("can be put on a second file without a UNIQUE violation") is not closed for such data.

Fresh data at this SHA does not reach this state (the second PUT reuses and renames the row: rail `{'ÜBUNG': 2}`); only rows written before the upgrade do. Probe: `scratchpad/r303-work/test_r303_probe.py::test_probe_legacy_nonascii_duplicates`, `tests3/test_r303_legacy_reach.py`.

### F2 [introduced] Low — "same tag" now means SQLite ASCII-lower in the DB lookups and Python Unicode-lower in dedupe/skip, and the two disagree (no declared invariant broken; triage B, or C if the equality definition itself is judged wrong)

The change makes `Übung` and `übung` distinct tags in every SQL path (the new test asserts rail `{"Übung": 2, "übung": 1}`), but these paths still fold with Python `str.lower()`:
`schemas.py` tag validators (`key = tag.lower()`, two sites), `merge_file_tags`' `existing_lower` skip, `services/frontmatter.py` dedupe.

Measured at this SHA: `PUT f1 ["übung"]`, `PUT f2 ["Übung"]` -> rail `{'Übung': 1, 'übung': 1}` (two tags). Then `PUT /api/files/batch/tags {"ids":[f1], "tags":["Übung"]}` -> **200, f1 still carries only `übung`**, and `?tag=Übung` lists 1 file. The request reports success and does nothing although the rail treats them as different tags. `PUT ["Übung","übung"]` likewise collapses to one.

Parent, same sequence: the second PUT reused and renamed the row (rail `{'Übung': 2}`), i.e. non-ASCII case variants were unified when typed in lower-then-capital order. At this SHA they never unify. The batch skip itself is [pre-existing] (parent reaches the same silent no-op in capital-then-lower order); what is introduced is that the split is now the defined behaviour in both orders and pinned by a test.
