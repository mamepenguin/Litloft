## Trajectory

Round 1 (`647b2873`) added `isinstance(scope, str)` in `_validate_scope`. Round 2 (`35235b3b`) adds `isinstance(meta, dict)` at the top of `register_in_process`. Neither round touched `main.py`'s control flow for loading (round 2 does not touch `main.py` at all), and neither adds a state or a prediction.

Plain answer: **this is the same guard applied to a sibling input, not a design being patched.** Round 2 handles the exact input round 1's review named (F5) one level up the same structure (container instead of field), and the shape already existed before this PR in `_navigation_error` (`not isinstance(nav, dict)` → "not an object", then `isinstance(placement, str)` before the set membership). The fix brings `ADDON_META` to the pattern the navigation validator already used.

Would a single validation shape cover both? Yes: a `_meta_error(meta) -> str | None` in the form of `_navigation_error` (object check, then scope type-and-membership) called by both `register_in_process` and `load_external_manifests` would cover both rounds and the manifest path, which today has no object check of its own — a JSON array manifest is refused only because `raw.setdefault` raises inside the `try` and is logged as a traceback ("Failed to load addon manifest"). That is a consolidation option, not a defect: both paths refuse today. If a third round added another type guard to one of the two paths separately, that would be the patching signal.
