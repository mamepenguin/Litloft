## F1: PageUp / PageDown in the contents list turn the book behind the open panel, and the list does not scroll

- Label: [introduced]. `EpubTocPanel` is a new file, and it is the first panel whose focus lands on `<button>`s. The typography panel's controls are `INPUT`s, which the provider counts as editing.
- Invariant: 4 ("scrolling ... the panel never ... move[s] the page ... or write[s] anything"). It is borderline, because the spec keeps ←/→ turning pages on purpose (PR-2 r1 F7). PageUp and PageDown are not mentioned anywhere in the spec or the invariants.
- What I did: I wrote a throwaway vitest probe (deleted afterwards) that reuses the TOC describe's `openWith(TOC)`. It opens the contents panel, which puts focus on entry 3, then fires `keyDown` on the focused entry with each of PageDown, PageUp, ArrowLeft and ArrowRight.
- Observed: the panel stays open, and the reader is sent `turn` `next`, `prev`, `left` or `right`. That is one turn per key, and a turn that moves the page posts `turned`, which writes WatchHistory. The `epub-reader` / `epub-reader-fullscreen` contexts match `pagedown` / `pageup` because a focused `BUTTON` does not count as editing. They call `preventDefault`, so the long list does not page-scroll either.
- What a user hits: in a long contents list (the author's example has 102 entries), PageDown is the ordinary key for scrolling a list. Here it scrolls nothing and silently turns the book underneath the open panel, which also saves a new place. The entry marked current in the list is then stale until the panel is reopened.
- Fix direction (supervisor's call): either declare PageUp/PageDown alongside ←/→ as keys that turn pages while the list is open, and say so in the invariants, or leave page turning out of the contexts while `openPanel === "toc"` so the list keeps its native PageUp/PageDown. The second option is a change of shape, not a new branch in the list's key handler: the spec notes that a React handler cannot stop the document listener.

## F2: "at its fragment" in invariant 1 has no detector: dropping the fragment survives

- Label: [introduced]. The `goToToc` path in `reader.js` is new.
- Invariant: 1 ("Selecting an entry shows that entry's target (its section, at its fragment when it has one)").
- What I did: mutation E3 in `reader.js`, `const href = state.tocHrefs[d.index].split("#")[0];`, with want=kill. I ran `e2e-epub/toc.spec.ts` on chromium and webkit.
- Observed: 20/20 passed, so the mutation survives. In the fixture `tocBook()`, the only fragment entry is `c3.xhtml#s`, and `#s` is the section's first element (`<h1 id="s">`). Going to the section start and going to the fragment land on the same page, and the test asserts only `lastLocation.section.current === 2`.
- What a user hits if this regresses: books that keep several chapters in one XHTML file (`book.xhtml#ch2`, `#ch3`, ...) are common in converted EPUBs. Every such entry would open at the file's first page, and CI would stay green.
- Fix direction: give the fixture a fragment target several pages into its section (for example an `id` on paragraph ~40 of a 60-paragraph chapter). Then assert that after `goToToc` the renderer's page is > 0, or that the anchor element is inside the visible range, besides the section index.

## F3: the list's focus fallback and edge clamping survive mutation

- Label: [introduced] (new file `EpubTocPanel.tsx`).
- Invariants: 8 ("focus is on it when it can be pressed, otherwise on the first entry that can") and 7.
- What I did:
  - K4: `: buttons.find((b) => !b.disabled)` was changed to `: buttons[0]`, with want=kill.
  - K8: the `Math.min(Math.max(..., 0), enabled.length - 1)` clamp was removed from ↑/↓, with want=kill.
  - I ran `EpubPreview.test.tsx` and `popup-dismissal.test.ts`.
- Observed: both mutations survive (136/136). In the fallback case the test uses ("the first entry that can be pressed when the current one cannot"), the first button, "Cover", is already enabled, so `buttons[0]` and "the first enabled" are the same button. No test presses ↓ on the last entry or ↑ on the first. With the clamp removed, that press does `enabled[len].focus()`, a TypeError in the key handler. On the real code my probe showed End then ↓ keeps focus on entry 5 with no error, so the code is correct today.
- What a user hits if the fallback regresses: a TOC that opens with a heading that has no link (`<span>Part I</span>`), read at a place before any selectable entry (`currentIndex` null, for example a cover outside the TOC). Focus would go to a disabled button, which is a no-op. Focus stays on the contents button, and ↑/↓ would not reach the list.
- Fix direction: add a case whose first entry has `fraction: null` and whose place has `tocIndex: null` and a fraction before the first target; expect focus on the first enabled entry. Also add ↓ on the last and ↑ on the first enabled entry, expecting focus to stay.

## F4: no CI detector for the scroll half of invariants 4 and 8 (list-only scroll, `preventScroll`)

- Label: [introduced] (new file).
- Invariants: 4 and 8.
- What I did: all three mutations had want=kill.
  - K1: `focus({ preventScroll: true })` changed to `focus()`.
  - K2: the `list.scrollTop = ...` assignment replaced with `current.scrollIntoView({ block: "center" })`, which also scrolls the page and `main`.
  - K3: the scroll block disabled (`if (false)`).
- Observed: all three survive. jsdom lays nothing out, and `e2e-epub` does not mount `EpubPreview`. The logic reads correctly: the button's `offsetParent` is the `absolute` panel, as is the list's, so `current.offsetTop - list.offsetTop` is the entry's offset in the list's content. The author's real-browser measurement covers today's tree.
- What a user hits if this regresses: someone "simplifies" the effect to `scrollIntoView`, or drops `preventScroll`, and opening the contents moves the page or the frame box on a phone. Nothing in CI fails. That is the exact regression invariant 4 names.
- Fix direction (optional, supervisor's call): a `frontend/e2e-layout/` case that opens the list with the current entry near the end of a long TOC. It would assert that `window.scrollY` and the frame box's `scrollTop` are unchanged and that the current entry lies inside the list's box. This is the same measurement the author took by hand. Not a defect in the code.
