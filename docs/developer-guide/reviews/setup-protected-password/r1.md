## Findings

### F1 — an anonymous LAN peer can take `/admin` on a Public install, in one request `[introduced]` — bucket B (security)

`_known_groups` now accepts `__admin__` on both write paths. Both are gated by
`_admin_or_first_run`, which after setup calls `auth.require_admin` →
`auth.is_admin`. On an install where `passwords.json` is `[]` **and no drive
declares an `access_group`**, `is_admin` returns `True` for everybody
(`auth.py:229-248`, the documented graceful-degradation branch). That branch
now also authorises writing the one group that ends it.

Failure scenario, measured end to end against the worktree at `33bffe3f`, with
`data/setup_completed` present, `passwords.json == []` and
`drives.json == [{"name":"d","path":…}]`:

```
anon is_admin: True
one-request sentinel plant -> 200        # PUT /api/admin/config/passwords
                                         #   [{"password":"attacker","groups":["__admin__"]}]
anon is_admin after  : False
anon GET /api/admin/config/passwords -> 403
drives still listed to anon: ['d']
```

The attacker then unlocks with `attacker`, holds `__admin__`, and is admin —
the same path `test_a_sentinel_only_password_earns_admin_on_a_drive_without_groups`
asserts. The owner is locked out of `/admin` with no way back through the UI:
`/admin/settings` is admin-gated, so recovery means editing `passwords.json` on
the host and restarting. Every drive stays publicly browsable throughout, so
nothing looks wrong from the drive picker.

`[introduced]`, measured with the same script against both commits:

| | one-request plant `["__admin__"]` | nearest parent-reachable path (PUT /drives adding `access_group: "g"`, then PUT /passwords `["g"]`) |
|---|---|---|
| `1fbfe074` | **422 `unknown_group`** | step 1 → 200, step 2 → **403** |
| `33bffe3f` | **200** | step 1 → 200, step 2 → 403 |

At the parent this class of request could only *deny* service: after step 1
`required = {"g"}` is no longer a subset of the attacker's empty group set, so
they lock themselves out along with everyone else and plant nothing. The change
turns that into a working, persistent takeover of the admin surface in a single
unauthenticated request.

The exposed configuration is exactly the outcome of choosing **Public** in the
wizard (`accessMode.publicUseCase` — "Recommended: family-only use"), plus any
pre-GUI install whose `passwords.json` is empty. Protected installs are not
exposed: their `passwords.json` holds an `__admin__` entry, so `is_admin` is
already `False` for an anonymous caller and the write is 403.

This is round 3 F1 of PR 307 (`docs/developer-guide/reviews/307/r3.md`) in the
window the setup token does **not** cover. The premise I was asked to check
rather than take — that the parent commits close the unauthenticated first-run
window — holds (see *Checked, no finding*). It is the post-setup window that is
open, and nothing in the parent change touches it.

Bucket: **B by the letter of R-4.** No declared invariant is violated —
invariants 1, 2 and 5 all speak about an install that chose Protected, and this
scenario is a Public install. R-4 says a B a user can actually hit is grounds to
raise a revision, and R-0 says only the supervisor or the user may revise the
list. Flagging it as the finding that should decide whether this ships.

### F2 — `complete-setup` clears the flag for a change the project documents as needing a restart `[introduced]` — bucket B

`33bffe3f` clears `data/restart_pending` when the wizard completes. The commit's
reasoning is that "this process re-read each of them as it wrote", which is true
of the caches: `put_drives` and `put_addon_policy` set
`config._drives_cache = None`, `put_passwords` sets `auth._passwords_cache = None`,
`main.py`'s `enabled_names` is computed per request inside the
`/api/addons/status` handler, and the addon `policy_client` self-heals on a 30 s
TTL. None of those needs a restart.

The scan does. `scan_all_drives()` runs once, from the startup lifespan
(`backend/app/main.py:275`); nothing else schedules one, and `put_drives`
touches no DB row (`backend/app/routers/admin_config.py:361-374` — validate,
`atomic_write_json`, clear the cache, return). `docs/admin-guide/settings-gui.md:90`
states the rule this breaks:

> - Adding / removing / **renaming** drives (scanner enumerates drives on boot).

Renaming a drive is step 3 of the wizard: `DriveStep` renders an editable `name`
field seeded from the startup mount scan
(`frontend/src/app/setup/steps/DriveStep.tsx:40`).

Failure scenario: `- /host/Videos:/app/drives/videos` in
`docker-compose.override.yml`. First boot seeds `{"name": "videos", …}` and
`scan_all_drives()` indexes the library with `File.drive == "videos"`. In
`/setup` the user renames it to `Movies` and finishes the wizard. `PUT /drives`
raises `restart_pending`; `complete-setup` clears it. The user lands on `/admin`
with no banner, opens `/drive/Movies`, and sees **nothing** — every listing
query is drive-scoped (`design-decisions.md`, "Drive-partitioned tables") and no
row carries `drive == "Movies"`. The only recoveries are the per-drive Scan
button in the folder toolbar (`useDriveScan`, reachable but unsignposted) or a
restart, and the change removed the one thing that told them to restart.

The same holds for a drive whose `path` the user edits, and for a drive row
added during first run — both reachable through `PUT /drives` with the setup
token.

The docs obligation in `CLAUDE.md` is unmet either way: if the behaviour is
kept, `docs/getting-started/first-run-setup.md:108` and
`docs/admin-guide/settings-gui.md:86-93` still describe the wizard's drive
writes as raising the banner.

`[introduced]`: `complete-setup` at `1fbfe074` does not touch the flag, so the
banner appeared and named `drives.json`. M5 confirms the new behaviour is what
`test_finishing_the_wizard_does_not_ask_for_a_restart` holds, and that test does
not exist at the parent.

Bucket B: the declared invariants say nothing about `restart_pending`, although
the second of the two commits under review is entirely about it. That gap is
itself worth the supervisor's attention.

### F3 — nothing holds the Protected-with-access-groups path `[pre-existing]` — bucket B

Mutation F3 replaces the `groupsWithAdmin` construction in
`frontend/src/app/setup/SetupWizard.tsx` with
`const groupsWithAdmin = [ADMIN_SENTINEL_GROUP];` — the drive groups are dropped
and only the sentinel is sent. All 92 tests still pass.

Failure scenario the survivor allows: the user sets `access_group: "family"` on
a drive in step 3, chooses Protected, types a password. `PasswordStep` shows the
group checkboxes and refuses to advance until all are checked
(`setup.password.groupsRequired`), so the user is told the password covers
`family`. Under the mutant the wizard writes `groups: ["__admin__"]`. Setup
finishes, the drive is protected, and unlocking with the only password in
existence does **not** reveal it — `filter_drives` matches `access_group`
exactly, and `__admin__` names no drive. The user is left with a drive they
cannot see and no second password to make.

Every new frontend test drives the branch where no drive declares a group
(`reachCompleteStepProtected` never sets one), and
`test_a_sentinel_only_password_earns_admin_on_a_drive_without_groups` names that
same branch on the backend. The path `AccessModeStep`'s own copy advertises —
"Restrict viewing per drive" — is the one nothing exercises.

`[pre-existing]`: the mutation survives at `1fbfe074` too; that construction is
older than this change. Recorded because `1a3a5da6` is the commit that makes the
write take effect at all — until now the whole `PUT /passwords` was a 422 the
wizard discarded, so what it sent could not be wrong in a way anyone could
observe. It can now.

## Checked, no finding

- **The first-run window is genuinely closed.** `_admin_or_first_run` requires
  the setup token whenever `data/setup_completed` is absent, on every write
  route, and `test_a_write_without_the_token_is_refused_and_changes_nothing`
  parametrises a missing, wrong and empty header across all six of them,
  asserting both config files are byte-identical afterwards and the sentinel is
  not written. The token is 192 bits from `secrets.token_urlsafe(24)`, compared
  with `compare_digest` on bytes, and never written to disk. The premise the
  brief asked me to check rather than take holds. F1 is the same attack in the
  window this does not cover.
- **The sentinel does not widen drive visibility.** `_known_groups` feeds only
  the two password validators. `_validate_drives_payload` is untouched, so it is
  no more (and no less) possible than before for a drive to declare
  `access_group: "__admin__"`. `filter_drives` and `check_drive_access` compare
  against a drive's own `access_group`, which an `__admin__` group never
  matches; in the probe above the anonymous caller still sees `['d']` after a
  sentinel-only password exists.
- **Graceful degradation is unchanged in shape.** `is_admin`'s
  `admin_configured` branch already looked for `__admin__` in
  `load_passwords()`; this change only made it possible to get such an entry in
  through the API rather than by hand. `load_passwords` accepts it (a non-empty
  string in a non-empty list) with no new branch.
- **Every rejection stops the wizard.** F6a/b/c each killed a test, one per
  config write, and `CompleteStep` checks `res.ok` on `complete-setup` itself and
  surfaces `detail.message`. `AdminConfigError.message` is `detail.message`, and
  `CompleteStep`'s catch renders `err.message`.
- **The auto-unlock is non-fatal and does not repeat the write.** F7 killed.
  `unlock` goes through `lib/api.fetchJSON`, which sends
  `credentials: "include"` — the same cookie behaviour as the raw `fetch` it
  replaced.
- **Public mode writes no password.** F4 killed. The guard is
  `accessMode === "protected" && password.password`, and the password step is not
  in `ORDER_PUBLIC`.
- **Write ordering is held.** F5 killed: drives before passwords, so a password
  naming a group is validated against the drives just written.
- **`restart_pending_flag()` is re-evaluated per call.** M8 and M9 each killed 9
  tests. The rename from `_restart_pending_flag` left no stale caller —
  `grep -rn _restart_pending_flag backend/` matches only two unrelated test
  function names, and all call sites (`main.py`, `admin_config.py` ×2,
  `internal.py`, `config_writer.py`) go through the public helper.
- **Layout and visual review.** Not applicable: the change adds no markup and no
  style, and nothing was claimed from jsdom about either.
- **PR 307's earlier findings.** Not re-derived. None of the findings in
  `docs/developer-guide/reviews/307/r3.md` or `r4.md` is made worse by this
  change; F1 above is r3 F1 relocated rather than repeated, and is filed as its
  own finding because the window differs.
