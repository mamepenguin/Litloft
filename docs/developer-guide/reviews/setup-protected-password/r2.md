## Findings

### F1 — the recovery this commit documents does not work on an install whose `drives.json` was not auto-seeded `[introduced]` — bucket B (prose, with a measured consequence)

`docs/admin-guide/settings-gui.md`, added by `5ba9495f`:

> To add the first admin password to a public install, re-run the wizard
> (delete `data/setup_completed`, restart, open the token's URL).

`_migrate_setup_sentinel` (`backend/app/services/drive_seed.py:120-134`) runs
from the startup bootstrap and **recreates** the sentinel whenever `drives.json`
holds at least one entry and `config._auto_seeded_marker()` is absent. That
marker is written only by `seed_drives_from_mounts()`. So an install whose
`drives.json` was produced by `configure.py`, or edited by hand — the
*Direct file editing* path the same document blesses, and every pre-GUI
install — gets the sentinel back on the very next boot.

Measured, deleting the sentinel and then starting the app:

| install | sentinel after the restart | `setup-status.completed` | wizard `PUT /passwords` with a valid token |
|---|---|---|---|
| wizard-seeded (marker present) | absent | `False` | **200** |
| hand-configured (no marker) | **recreated** | **`True`** | **403 `admin_grant_forbidden`** |

Failure scenario: a pre-GUI install, upgraded. `drives.json` was hand-written;
`passwords.json` is `[]`, which is what `configure.py` generates. The operator
decides to protect `/admin`. `/admin/settings` → Passwords → add an entry with
group `__admin__` → 403, and the message tells them to "re-run /setup". They
delete `data/setup_completed`, `docker compose restart backend`, and land on
`/admin` again: the wizard never opens, `setup-status` still says completed, and
the 403 repeats. Nothing in the UI names a next step.

**Remedy: delete the sentence.** The action that does work is already documented
two sections down under *Direct file editing* — put
`{"password": "…", "groups": ["__admin__"]}` into `passwords.json` and restart
the backend. If a pointer is wanted there, point at that.

`[introduced]`: the sentence is new in this commit. The behaviour it describes
wrongly is older — see F2.

### F2 — creating a sentinel entry now needs the sentinel, deleting the last one does not `[pre-existing]` — bucket B

`DELETE /passwords/{index}` and a sentinel-free `PUT /passwords` are gated only
by `_admin_or_first_run`. A viewer who holds every drive `access_group` is
`is_admin` by the documented all-groups rule (`auth.py:202-248`), so they pass
that gate — but they do not hold `__admin__`, so `_require_admin_to_grant_admin`
403s them on the way back in.

Measured end to end, drive `d` with `access_group: "fam"`, passwords
`[{fp,[fam]}, {root,[__admin__]}]`, caller unlocked with `fp`:

```
DELETE /passwords/1        (the only admin entry)  -> 200
PUT    /drives             (drops access_group)    -> 200
DELETE /passwords/0                                -> 200
  passwords.json == []   drives.json declares no group   =>  everyone is admin
anonymous PUT /passwords [{…,["__admin__"]}]       -> 403 admin_grant_forbidden
the owner's own PUT      [{…,["__admin__"]}]       -> 403 admin_grant_forbidden
```

So the install can be walked into the degraded state the guard exists to
protect, and from there no API caller can leave it.

`[pre-existing]`, measured with the same script against all three SHAs (only
`backend/app/routers/admin_config.py` differs between them, so it was swapped in
place):

| | anon plants on a Public install | a group-holder admin adds an admin password | the owner re-adds after the walk above |
|---|---|---|---|
| `cbca0262` (develop) | 422 `unknown_group` | 422 `unknown_group` | 422 `unknown_group` |
| `a1fa8d77` (round 1) | **200, planted** | 200 | 200 |
| `5ba9495f` | 403 `admin_grant_forbidden` | 403 | 403 |

Against `develop` the outcome is unchanged — refused then, refused now; only the
status code moved from 422 to 403, which is a better message for the same wall.
The one-way door is not this commit's doing. Recorded because F1 is this
commit's attempt to document a way through it, and because the asymmetry
(destroy without the sentinel, create only with it) is worth stating explicitly
now that the two paths are gated differently rather than identically.

The pre-existing sentence in `settings-gui.md` — "emits a warning if you delete
the last admin-grade password but allows the operation" — still reads as if the
operation were reversible. It is, for a sentinel holder, who is who rotates.
Left alone.

### F3 — three survivors in the new guard `[introduced]` — bucket B (detector gaps)

The shipped code is correct on every path measured below; what is missing is a
test that can tell it from a wrong one. All three mutations pass the full
88-test target set.

**R6 — `if auth.get_unlocked_groups(request):` in place of the sentinel test.**
This is exactly the rule the docstring argues *against*: any viewer who unlocked
any password could then grant admin. Nothing kills it, because every test caller
is either anonymous (no groups) or a sentinel holder (has `__admin__`). The
discriminating caller — one who unlocked a *drive-group* password — appears in
no test. Measured on the drive-`fam` install above:

| | `POST /append {groups:["__admin__"]}` | planted |
|---|---|---|
| shipped | 403 | no |
| R6 mutant | **200** | **yes** |

**G7 — fire only when `groups == ["__admin__"]` exactly**, rather than when the
list contains it. Same install, same caller:

| | `POST /append {groups:["fam","__admin__"]}` | planted |
|---|---|---|
| shipped | 403 | no |
| G7 mutant | **200** | **yes** |

**G4 — drop `isinstance(e.get("groups"), list)`.** That check is load-bearing

## Trajectory

> *Read the fix diffs in order. Does round 2's fix add a branch, a state or a
> prediction that round 1's fix also added?*

**No. This is one mechanism finished, not two cases handled.**

Round 1 (`a1fa8d77`) added one member to a set — `groups.add(auth.ADMIN_SENTINEL_GROUP)`
in `_known_groups` — plus the wizard's `__admin__` append and per-write error
propagation. Round 2 (`5ba9495f`) added `_grants_admin`,
`_require_admin_to_grant_admin` and one call on each of the two creating routes.

The evidence that these are one change and not a patch chain:

- Round 1 made `__admin__` a **writable value**. A writable value needs an
  authorization rule, and round 1 shipped the value without one. Round 2 supplies
  that rule and nothing else. It does not add a second member to round 1's set,
  does not widen `_known_groups` further, and adds no state to the wizard.
- Read as a pair against `develop`, the two commits move `__admin__` from
  *unwritable* (`cbca0262`: 422 on every path) to *writable under one stated
  condition* (`5ba9495f`: the wizard's token, or a caller already holding it).
  That is a single sentence of design, delivered in two commits.
- Round 2's diff **narrows**: the measured change is a 200 going back to a 403
  (F2's table, row `a1fa8d77` → row `5ba9495f`). A round that removes reachable
  states is the loop converging. R-4's test for patching — "each round handling
  one more case the last one did not anticipate" — is not met: round 2 handles
  the *same* case round 1 opened.

**The seam to watch, so round 3 is not a surprise.** The guard is stricter than
its own docstring argues for. The docstring's reason is graceful degradation —
a caller with *no* unlocked groups — but the implemented test is "holds the
sentinel", which also refuses a viewer who holds every declared `access_group`
and is admin by the documented all-groups rule (F2, RepD). That gap is not a
patch on round 1; it is a scope this guard chose, and the choice matches
`develop`'s outcome. But it is the most likely place for a round 3 to add a
branch — *"…or holds every declared access_group"*. If a round 3 does that, it
is the second consecutive round adding a branch to the same decision, and the
answer to this question changes. Flagging it now rather than letting it arrive
as a diff.

## Checked, no finding

- **The guard is on every route that can create a sentinel entry.** Enumerated
  from the routing table, not the diff. Three routes write `passwords.json`:
  `PUT /passwords` (`admin_config.py:434`), `POST /passwords/append` (`:516`) and
  `DELETE /passwords/{index}` (`:549`). `grep PASSWORDS_CONFIG backend/app addons`
  finds no fourth writer anywhere, in core or in any addon. `DELETE` removes by
  index and cannot introduce an entry, so both creating routes carry the call.
  The deletion asymmetry is F2.
- **The exemption is sound; the token is required, not assumed.** Measured with
  the sentinel genuinely absent — it has to be unlinked *inside* the running
  client, because `_migrate_setup_sentinel` recreates it at startup, which is why
  the existing tests unlink inside their `with` block. No token header → 403
  `setup_token_invalid`, `passwords.json` unchanged. With the token → 200, the
  entry written. `POST /append` behaves identically. `_admin_or_first_run` is a
  route dependency, so it runs before the handler: there is no ordering in which
  the handler's exemption applies without the dependency having demanded the
  token first. A sentinel created between the dependency's check and the
  handler's fails **closed** (the guard applies to a wizard write), not open.
- **No payload shape walks around it.** 15 shapes × `PUT` and `/append` = 30
  requests, anonymous caller, completed Public install, `passwords.json` reset
  between each. Nothing was planted in any of the 30. A sentinel inside a list →
  403 with the file unchanged, including a bare dict body, duplicate sentinel
  entries, a malformed sibling entry either side of the real one, and a masked
  `***` password (the guard answers before the validators, on purpose). `groups`
  as a string, a nested list, an int, or absent → 422 from the validators, which
  is where those belong. `__ADMIN__` and `xx__admin__yy` → 422 `unknown_group`:
  the guard does not fire and does not need to, because `_known_groups` holds
  exact strings. JSON cannot produce a tuple, so that shape does not exist.
- **The legitimate admin is unaffected.** Holding `root` (`groups: ["__admin__"]`):
  add a second admin password → 200; add a non-admin password → 200; delete an
  entry → 200; rewrite the whole list → 200. The `/admin/settings` flows are
  untouched.
- **Detector rule 5 on the new tests.**
  `test_a_write_carrying_no_sentinel_is_left_to_the_validators` declares its
  expectation (`422`, `unknown_group` present, `admin_grant_forbidden` absent)
  rather than deriving it from the response, and it fails for the right reason:
  the shipped answer is `422 unknown_group`, and G2 (`_grants_admin` always True)
  turns it into a 403 and fails the test. It is not G2's only killer — two older
  `unknown_group` tests fall with it — but it is the only test that pins both
  directions of the guard's scope on one request.
  `test_an_anonymous_caller_cannot_grant_itself_admin`'s
  `json.loads(passwords_json.read_text()) == []` is what kills R8, the
  write-then-403 ordering; without it that mutation would be invisible. No new
  test builds an expected value out of an observation, and none uses a lower
  bound.
- **Survivors that are meant to survive.** G5 (case-insensitive match) and G6
  (substring match) both make the guard *stricter*: they would 403 payloads the
  validators already 422, and neither lets anything through. R7 (guard after
  `_validate_passwords_payload`) only reorders two rejections — measured, no
  payload reaches the write under it, since validation raises first. R8 (guard
  after the write) is the ordering that matters, and it is killed.
- **Frontend.** `pnpm exec vitest run src/app/setup` → 92 passed;
  `pnpm exec tsc --noEmit` → clean. The commit touches no frontend file. The new
  403 renders through `PasswordsSection.describeError`, which prefers
  `detail.message` over an `errors.<code>` translation — so the missing
  `errors.admin_grant_forbidden` key is not a gap; that branch is unreachable for
  every error this router raises, which is pre-existing.
- **`config._restart_pending_flag()` is dead code.** No caller in `backend/app`;
  `main.py`, `admin_config.py`, `internal.py` and `config_writer.py` each build
  `config.DATA_DIR / "restart_pending"` inline. Identical at `cbca0262`, so it is
  `[pre-existing]` and out of this change's scope. Noted only because round 1
  mutated a public `restart_pending_flag()` that the dropped commit had
  introduced; there is no stale caller left behind by the drop.
- **Layout and visual review.** Not applicable: no markup and no style in the
  diff, and nothing is claimed from jsdom about either.
