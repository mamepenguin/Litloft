## Findings

### F1 — Two hard-delete paths still strand the tag — `[pre-existing]` — **A** (invariant 1)

The commit message says `physical_delete` is "the one place every purge path goes
through". It is not. Two places delete a `File` row outright without it, and both
leave the `Tag` behind:

- `backend/app/services/fileops.py:192` — `resolve_db_path_conflict`, the
  "Trashed → purge the ghost" arm, reached by every create / move / rename that
  lands on a path a trashed row still owns.
- `backend/app/services/upload.py:256` — the same reconciliation on re-upload.

**Failure scenario.** Tag `old.mp4` with `holiday`, the only file carrying it.
Trash `old.mp4`. Upload (or rename another file to) `old.mp4`. The ghost row is
hard-deleted, its `file_tags` row goes with it, and `Tag(holiday)` survives
attached to nothing — exactly the state invariant 1 forbids and the state the
deleted `known-issues.md` entry described (shows in the drive's tag list and in
the typed suggestions; selecting it finds nothing).

Reproduction (run as `tests/test_ghost_repro.py`, not committed):

```python
def test_ghost_purged_by_path_conflict_leaves_orphan_tag(client):
    _, db, drive_dir, _ = client
    ghost = _seed_trashed(db, drive_dir, "solo.mp4", ["holiday"])
    (drive_dir / "solo.mp4").unlink()
    fileops.resolve_db_path_conflict(db, "solo.mp4", TEST_DRIVE)
    db.commit()
    assert db.query(File).filter(File.id == ghost.id).first() is None
    assert _tag_names(db) == []          # AssertionError: ['holiday'] == []
```

Label evidence: the same file run against an image built from the parent
`a33d7364` fails identically (`1 failed`). The leak predates this commit, so
`[pre-existing]`.

It is bucketed **A** all the same, because it breaks invariant 1 as declared and
because this commit deletes the `known-issues.md` entry that recorded it. After
this commit the defect is neither fixed nor written down anywhere.

### F2 — Nothing holds the trashed/missing half of invariant 2 — `[introduced]` — **A**

Invariant 2 says a `Tag` attached to at least one file — **trashed, missing** or
active — survives every purge. The behaviour is correct at this SHA, but no test
can fail if it stops being correct: every surviving-tag test in
`backend/tests/test_purge_orphan_tags.py` uses an **active** file as the holder
(`test_a_tag_another_file_still_carries_survives`).

M14 narrows the orphan test to "no *active* file references it" and the whole
suite stays green (115 passed; full suite unaffected). That mutant is an A-class
defect: purging any one file in a drive would then strip every tag whose only
remaining holders are trashed or missing — user-entered data that
`design-decisions.md` lists as unregenerable, and that comes back wrong on
restore from trash.

Two tests close it (both pass at `ddc8c21a`, both kill M14):

```python
def test_tag_held_only_by_a_trashed_file_survives_a_purge(client):
    _, db, drive_dir, _ = client
    _seed(db, drive_dir, "kept.mp4", ["holiday"], state="trash")
    doomed = _seed(db, drive_dir, "doomed.mp4", ["holiday"], state="trash")
    fileops.purge_file(db, doomed.id)
    assert _tag_names(db) == ["holiday"]

# …and the same with state="missing" for the holder.
```

`[introduced]`: `test_purge_orphan_tags.py` is created by this commit, so there
is no parent to run the reproduction against.

### F3 — A bulk purge runs one full-drive orphan scan per file — `[introduced]` — **B**

`cleanup_orphan_tags` now sits inside `physical_delete`, which is the per-file
step of `purge_all_trash` (`fileops.py:767`), `purge_all_missing`
(`fileops.py:822`) and `main._run_purge_batch` (`main.py:92`). Purging a drive's
trash therefore issues N `SELECT tags.* FROM tags LEFT OUTER JOIN file_tags …
WHERE tags.drive = ?` scans instead of one, and all but the last can only find
what the previous iteration already deleted.

Breaks no declared invariant — the result is the same and invariant 4's
transaction shapes are untouched (M12 confirms the per-row commit is still held).
It reads wrong: the sweep is idempotent and drive-wide, so one call after the
loop would do. Placing it in `physical_delete` is what buys the "every purge path
goes through here" property, so this is a trade, not a mistake — recording it
because the cost scales with the size of the purge.

### F4 — Three callers still sweep every drive — `[pre-existing]` — **B**

`backend/app/routers/files.py:756` (`PUT /api/files/{id}/tags`),
`backend/app/routers/files.py:1578` (the markdown frontmatter tag projection in
`put_content`) and `backend/app/routers/internal.py:166`
(`POST /api/internal/files/{id}/tags`) call `cleanup_orphan_tags(db)` with no
drive. Editing one file's tags in drive A deletes orphan `Tag` rows in drive B.

`design-decisions.md` → *Drives*: `Tag` is drive-partitioned and "any
query/upsert on these tables must be drive-scoped". This commit introduces the
parameter that would scope them and does not pass it at these three sites.
Invariant 6 deliberately preserves the old behaviour, so it is not a regression —
and the rows reached are already-orphaned ones, which is why this is B and not A.
`file.drive` is in hand at all three call sites.

Label evidence: identical code at `a33d7364` (`git show a33d7364:backend/app/routers/files.py`).

### F5 — Invariant 4's chunk of 200 is held by no test — `[pre-existing]` — **B**
