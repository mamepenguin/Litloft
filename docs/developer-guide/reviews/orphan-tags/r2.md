## Findings

### F1 — The drive scoping this commit adds is held by no test — `[introduced]` — **A** (invariant 6)

Invariant 6, as revised for this commit, says: *"Editing one file's tags sweeps
orphans in that file's drive **only**."* That word is what `429e8402` bought at
`files.py:756`, `files.py:1578` and `internal.py:166`. Nothing can fail if it is
taken back.

MU9, MU10 and MU11 revert one call site each to `cleanup_orphan_tags(db)` — the
exact code at `ddc8c21a` and at `a33d7364` — and the target set stays at
**136 passed** every time. MU17 reverts **all three at once and runs the whole
backend suite**: `2330 passed, 4 skipped`, byte-identical to the unmutated run.
So this is not a gap in the chosen target set; no test in the repository
observes the difference.

The reason is structural, not accidental: the two tests that exercise these
endpoints' sweeps (`test_api_tags.py::TestOrphanTagCleanup::test_orphan_deleted`
and `test_internal_files_tags.py::…::test_orphan_tags_are_cleaned_up`) each set
up **one** drive, so "swept my drive" and "swept every drive" are the same
observation. The only test in the suite that seeds a second drive's `Tag` is
`test_purge_orphan_tags.py::test_a_purge_leaves_another_drive_alone`, and it goes
through `purge_file` — the `physical_delete` site, which was already scoped at
`ddc8c21a` and is why MU14 dies.

**Failure scenario.** Drive `photos` holds `Tag(2019)` orphaned by an earlier
purge; the user is about to re-attach it by tagging a restored file. A later
refactor (or a revert of these three lines) drops the `file.drive` argument.
Someone edits the tags of an unrelated `.md` note in drive `notes`; the
frontmatter projection at `files.py:1578` sweeps globally and deletes
`Tag(2019)` in `photos`. Nothing in the suite goes red. That is a cross-drive
write on a drive-partitioned table, which `design-decisions.md` → *Drives*
forbids outright, and tags are user-entered data the same file lists as
unregenerable.

**Bucket A**, by the R-4 rule *"a test that lets an A through is an A"*. It is
the same shape as round 1's F2 (correct behaviour, unheld), which was triaged as
A and fixed; this commit fixed F2's half and left its own half open.

**Label.** `[introduced]`: the scoping at these three sites does not exist at
`ddc8c21a` or `a33d7364`, so there is no prior behaviour for a test to have held.
The invariant it must satisfy was written for this commit.

**What closes it.** One test per site is not needed; one is. Seed
`Tag(name="holiday", drive="other-drive")` with no file, `PUT
/api/files/{id}/tags` on a file in `test-drive`, assert the `other-drive` row
survives — the same shape as `test_a_purge_leaves_another_drive_alone`, pointed
at a tag-write endpoint instead of a purge. That kills MU9; MU10 and MU11 need
the same assertion on their own endpoints.

### F2 — A file moved across drives strands its tag on purge — `[pre-existing]` — **A** (invariant 1)

Invariant 1 now reads *"This holds for **every** hard delete"*. It does not hold
for a file that changed drives.

`fileops.move_file` reassigns `file.drive = dst_drive` (`fileops.py:496`) and
touches nothing in `file_tags`. The rows keep pointing at `Tag` rows whose
`Tag.drive` is the **source** drive. `physical_delete` then sweeps
`cleanup_orphan_tags(db, file.drive)` — the *destination* drive — so the tag the
file actually carried is outside the sweep's filter and survives attached to
nothing.

Reproduction (`tests/test_r2_repro.py`, not committed; uses the existing
`two_drives` fixture from `tests/test_target_drive_access.py`):

```python
def test_cross_drive_move_then_purge_strands_the_tag(two_drives):
    _, db, open_dir, locked_dir = two_drives
    f = ...  # File(drive=OPEN_DRIVE, file_path="solo.mp4") with Tag("holiday", drive=OPEN_DRIVE)
    fileops.move_file(db, f.id, LOCKED_DRIVE, "")
    db.refresh(f)
    assert f.drive == LOCKED_DRIVE
    assert [t.name for t in f.tags] == ["holiday"]      # passes — the tag followed the file
    f.deleted_at = datetime.now(UTC); db.commit()
    fileops.purge_file(db, f.id); db.commit()
    assert db.query(File).filter(File.id == f.id).first() is None
    assert [(t.drive, t.name) for t in db.query(Tag).all()] == []
    # AssertionError: assert [('open', 'holiday')] == []
```

**Label evidence.** The same file fails identically against images built from
`ddc8c21a` (`assert [('open', 'holiday')] == []`) and from `a33d7364`
(same). `[pre-existing]` — `429e8402` neither introduced nor widened it. It is
reported because this commit is the one that extends invariant 1 to *every* hard
delete, and this is the hard delete it does not cover.

**Reachability.** The stranded row is not unreachable forever: any later
`physical_delete` or tag edit **within the source drive** sweeps it, because
those calls pass that drive. It is lost for good only when the source drive has
no file left to purge or to tag — e.g. the moved file was its last one. At
`a33d7364` the three tag-write sweeps were global, so a tag edit in *any* drive
collected it; after `429e8402` only an edit in the source drive does. That is the
answer to "did scoping lose a collection route": yes, this one — and the scoping
is still right, because `design-decisions.md` forbids the cross-drive write that
the old global sweep was performing.

The purge is not the only way the mismatch shows. `replace_file_tags`
(`files.py:157-171`) looks `Tag` rows up with `Tag.drive == file.drive`, so a tag
edit on the moved file creates **new** rows in the destination drive and orphans
the source-drive ones it detaches — and the sweep that follows, scoped to
`file.drive`, cannot see them either. Same root cause, reached without any
delete.

**Also worth the supervisor's attention, out of scope here:** a file living in
drive B while carrying `Tag` rows owned by drive A is itself a breach of the
drive partition, independent of purging. `move_file` should re-bind the tags into
the destination drive (the `Tag(drive, name)` unique key makes that a
get-or-create), at which point this finding disappears as a side effect. That is
a change to `move_file`, not to this branch.

### F3 — The sweep is a list of six call sites, and nothing guards the list — `[introduced]` — **B**

Round 1's F1 was that the "one chokepoint" claim was false. The answer in
`429e8402` is to add the two missing sites. Asked directly — *is the new shape a
chokepoint, or a list?* — it is a list:

| kind | site |
|---|---|
| hard delete | `fileops.py:194` `resolve_db_path_conflict` (trashed arm) |
| hard delete | `fileops.py:700` `physical_delete` |
| hard delete | `upload.py:259` `complete_upload` (trashed ghost arm) |
| tag write | `files.py:756` `PUT /api/files/{id}/tags` |
| tag write | `files.py:1578` `put_file_content` frontmatter projection |
| tag write | `internal.py:166` `POST /api/internal/files/{id}/tags` |

Each of the three delete sites is individually held (MU1, MU2, MU14 all die), so
the list is complete and correct **at this SHA** — this is a B, not an A.

What is absent is anything that fails when a seventh site appears. There is no
test in `backend/tests/` that mentions `cleanup_orphan_tags` at all
(`grep -rn cleanup_orphan_tags backend/tests/` → no match); every one of the
fourteen mutations above is killed by a behavioural test of one specific path.
The next `db.delete(<File>)` added anywhere in the backend inherits round 1's
defect silently, and the way that defect was found both times was a reviewer
grepping for `db.delete`.

`review-workflow.md` § *Detector rules* fits this case: a detector that
enumerates `db.delete(` against a declared set of `File`-deleting call sites and
asserts `toBe(3)` would go red on the seventh site. Rule 4 there says prefer a
test that calls the code over one that reads source as text — but there is no
behavioural test that can enumerate future call sites, and rule 1's "where the
set is meant to grow, the test is updated with the change that grows it; that
edit is the point" is exactly the property wanted here.

I verified the set independently rather than taking round 1's word:
`grep -rn "\.delete(" backend/app addons` finds `db.delete` on a `File` at
`fileops.py:192`, `fileops.py:698` and `upload.py:257` only. `fileops.py:136` is
an `EmptyFolder`, and the two `.delete(synchronize_session=…)` bulk deletes are
also `EmptyFolder`. The four checked-out addons (`cloud-sync`, `intelligence`,
`knowledge`, `media_import`) hard-delete no core `File` row.

## Trajectory

**Round 2's fix adds more of the thing round 1's fix added, and removes
nothing.** Read as diffs:

`ddc8c21a` introduced a prediction — *there is one chokepoint for hard deletes* —
and encoded it as one call to a newly extracted `cleanup_orphan_tags(db, drive)`
inside `physical_delete`, plus one new branch in `tagops` (`if drive is not
None`). Its commit message states the prediction: "the one place every purge path
goes through".

`429e8402` does not withdraw that prediction; it weakens it to *there are three
chokepoints* and enumerates them. The diff is two more calls to the same
function, three more arguments passed to it, and four tests for the three cases
round 1 named. `tagops.py` is untouched: no new branch, no new state.

So the two rounds are **the same move at a larger count**, which is the shape
`review-workflow.md` calls patching: "each round handling one more case the last
one did not anticipate". The count of hard-delete sites went 1 → 3 by
enumeration, and the enumeration was produced by a reviewer running `grep`, not
by anything in the design. Under the rule as written — *two rounds in a row whose
fix adds a branch, a state or a prediction* — this is a **candidate C**, and I am
reporting it rather than deciding it.

The evidence pointing the other way, stated so the supervisor has both halves:

- `429e8402` adds **no branch and no state**. `tagops.py` is byte-identical to
  `ddc8c21a`. Three of its six changed lines *remove* reach (`cleanup_orphan_tags(db)`
  → `cleanup_orphan_tags(db, file.drive)` narrows what the transaction may touch)
  — the rule names removing a prediction as convergence, and scoping a query is
  that in miniature.
- The three hard-delete sites are now a **closed, verified set** (F3), not an
  open-ended one: I re-derived it independently and found no fourth.
- Round 2 introduced no new failure of its own. F1 is an unheld invariant, F2 is
  older than the branch, F3 is a shape.

What would end the loop rather than extend it is a shape where a seventh site
cannot forget the sweep — routing the two direct `db.delete(conflict/existing)`
calls through a helper that owns the sweep, or an `after_delete` mapper event on
`File` — or, failing that, F3's detector, which makes the list fail loudly
instead of silently. Two of the three delete sites already sit in code whose
comment says it is freeing the UNIQUE slot, not purging a file, which is why they
were missed twice.

## Checked, no finding

- **Q1 — is `resolve_db_path_conflict`'s sweep reachable from every caller that
  hits its trashed arm, and does it share their transaction?** Yes to both. The
  callers are `copy_file` (`fileops.py:293`), `rename_file` (`fileops.py:401`)
  and `move_file` (`fileops.py:479`); the UI's paste / batch-move / batch-copy
  endpoints (`files.py:428`, `files.py:565`, `files.py:1353`) all go through
  those three. Each calls it *before* the filesystem operation and before its own
  `db.commit()`, and nothing commits in between — so `db.delete(conflict)` and the
  sweep are one unit. `copy_file` and `move_file` wrap the rest in
  `except Exception: db.rollback()`, which takes both back; `rename_file` lets an
  FS error propagate to the request teardown, same result.

  Probe (`tests/test_r2_tx.py`, not committed): `rename_file` onto a trashed
  ghost's path with `Path.rename` patched to raise `OSError`. After the rollback
  the ghost `File` row is present **and** `Tag(holiday)` is present. Passes.

- **Q2 — `complete_upload`'s sweep runs mid-function; can a later failure lose a
  tag?** No. The sweep at `upload.py:259` is followed by `db.flush()`,
  `probe_file_chapters` (its docstring's "never commits" is true — no `commit` in
  `chapters.py`), `untrack_empty_folder`, then the single `db.commit()`. Nothing
  between the sweep and that commit commits, so a failure rolls the tag back with
  the ghost row.

  Probe: `probe_file_chapters` monkeypatched to raise inside a real
  `POST /upload/{id}/complete`. After the rollback: ghost row present,
  `[('test-drive', 'holiday')]` present. Passes. (Unrelated and pre-existing: the
  uploaded bytes are already on disk at that path when this happens, so the FS
