## Findings

### F1 [introduced] — invariant 6 wiring untested: `mouseDragPans: false` survives flipped to `true` — severity A (test lets an A through)
The hook test covers `mouseDragPans` on the hook itself. No test covers the viewer passing it. Reproduction: in `PdfFullscreenViewer.tsx`, change `mouseDragPans: false` to `true`. All tests stay green (M21), but at that point a mouse drag on a zoomed page pans instead of selecting text.

### F2 [introduced] — invariant 7 untested: z-index and inertness survive removal — severity A (test lets an A through)
`z-[60]` → `z-10` (L1) and `useInertBackdrop(true)` → `(false)` (L2) both stay green. Only the portal to `document.body` is asserted. The spec's promised component e2e (Pixel 5 + desktop, "painting over chrome") is not in the commit, and `e2e-components/immersive-viewer-layer.spec.ts` does not cover the PDF viewer.

### F3 [introduced] — invariant 4 "a wide page is split into halves" is held only by the label — severity A (test lets an A through)
The test asserts `data-face="half"` and the `A`/`B` label. Removing the 200% width (`width: activeSplit ? "200%" : "100%"` → `"100%"`, M22) stays green. Nothing asserts `translateX(-50%)` either. The face stops being split on screen, but the test still passes.

### F4 [introduced] — double-clicking a word near a page edge turns the page twice and selects nothing — severity high (raise: invariant 6 names only drags)
Reproduced in the running app at 1184px viewport width, with spread mode on and pages 4–5 in view (`QDpWH-0a5M8K`). A real double-click at (230,330) on page 4's text, inside the left 25% edge band, took the viewer 4–5 → 2–3 → 1, and `getSelection()` was `""`. A mouse press shorter than 10px and 300ms counts as a tap in `useViewerZoom.onPointerUp`, and a mouse tap in an edge band pages. So each click of a double- or triple-click pages. The same happens to the single click a reader uses to clear a selection. In a pair the edge bands cover most of the outer halves of both pages, so word/line selection with the mouse turns pages there. The commit message says mouse input selects text, and `mouseDragPans: false` exists for that. But nothing stops a mouse tap from paging when the viewer is used for selecting. Not in R-0: invariant 6 covers drags only. See "Missing from R-0" below.

### F5 [introduced] — the quote button looks different from the viewer's own bar controls (measurement, no ruling)
Measured in the app with the light theme, at 1184px viewport width. `knowledge-media-capture` in `document-viewer-actions` renders as a 36×36 box with `background rgb(255,255,255)`, `color rgb(98,98,91)` and `border-radius 8px`: a white tile on the black gradient bar. The viewer's own buttons (spread, close) are 30×30 circles with a transparent background and white glyphs at 60–80% opacity. The entry keeps its `bg-bg-card text-text-muted` styling from the file action row. DESIGN.md "Over-video chrome" is the reference for whoever rules. At 338px viewport width the bar still fits (scrollWidth = clientWidth = 338), and the dialog covers the viewport.

### F6 [introduced in the new viewer; the inline viewer's behaviour is pre-existing] — an internal link annotation does not go to its page (differs from the spec)
The spec's input table says "Tap on a link annotation → follows the link (internal: go to page)". `<Document>` in `PdfPreview.tsx` has no `onItemClick`. In react-pdf 10.4.1 `Document.js` then falls back to `pages[pageIndex].scrollIntoView()`, or warns if the page is not mounted. In the full-screen viewer only the 1–2 pages of the face are mounted, so an in-document link (a table of contents entry) does nothing and does not change `index`. Found by reading the code; not reproduced in the app, because neither test PDF has internal link annotations. External links follow `externalLinkTarget`, which is unset. Not verified.

### F7 [introduced] — a failed full-screen render shows nothing (differs from the spec)
The spec says a render failure shows the existing `pdfRenderTooLarge` message. `PdfFullscreenViewer`'s `<Page>` has no `onRenderError`/`onRenderSuccess`, so a refused canvas leaves a white box. The whole-face `rasterPixelRatio` budget makes an area failure unlikely. Canvas dimension caps are not covered by an area budget. Low severity. Ask whether the omission was intentional.

### F8 [introduced] — survivors with no R-0 invariant behind them (bucket B, test gaps)
Each of these mutations stays green (table below): `showRightHalf` resets on spread/direction toggle and page-box commit (M4 M5 M6 M20); `resetKey` made constant — zoom carries across page turns (M7); `face.index`→`index` in the page capture and in the close hand-back — they differ once a pair starts before `index` (M10 M14); no selection clearing on face or half change (M11 M18); chrome not held while selecting — the quote button then auto-hides under a live selection (M17 L7); face budget from the first page only — a pair gets 2× the raster area (M13); pair's second width from the first page's aspect (pdfFace F5 — measured in the app, pages 4 and 5 are 527 and 522 px wide, so aspects really differ); full-screen page box commits n instead of n−1 (L9); PageUp in full screen made a no-op (L5); page-box fetch that throws instead of returning null — `Promise.all` rejects, so every page in the window stays unknown and nothing pairs (B5); the `inScope` part of the `f` gate removed (P4); `setFullscreen(false)` on file change removed — the viewer then reopens on the next file once it loads (P5); button enabled before load (P6); `setLoadedPdf(null)` on file change removed — `f` then opens the previous document's proxy (P8); `useViewerZoom`'s `mouseDragPans` default flipped to false — image and archive viewers stop panning on mouse drag, and none of their tests notice (Z2b).

### F9 [introduced] — the viewer's shortcuts sit at priority 0, so a context enabled after it opens wins (claim, not reproduced)
The spec says the viewer's `←`/`→` "wins over `useFileNav`'s file arrows". The viewer registers `pdf-fullscreen` at priority 0, so it wins only by push order (`orderContexts`). `file-nav` pushes when `neighbors` arrive. If `f` is pressed before the neighbours fetch resolves, `file-nav` lands above the viewer and `→` changes the file under an open viewer. PdfPreview's `setFullscreen(false)` on `fileId` change then closes it without calling `onClose`. With a normal click-to-open, the arrows go to the viewer: measured in the app, `→` went 3→4 and the URL did not change. The other search overlays use `OVERLAY_PRIORITY` for this reason. The archive viewer uses 0, the same pattern.

After clicking the frame, `→` went 3→4 and the URL stayed the same. Esc closed the viewer, the inline box showed 4, `body.style.overflow` was restored and no `inert` from the viewer was left (the one `inert` left is the collapsed folder tree's own).
- Invariant 3: after opening and paging 6 times, `read_network_requests` recorded no request containing the file id. Worker-side fetches may not show in this tool.
- Selection across a pair (kanri-gl.pdf, pages 2–3): a drag from page 2 into page 3 gave a 643-character selection. The range starts in `[data-pdf-page="2"]`, the button label switched to "Add selection to capture basket" and the chrome was held at opacity 1. A drag started in the black margin produced no selection, so no quote without a page.
- The scanned 225-page PDF has an empty text layer, so nothing in it can be selected: a property of the file.
- Side effects of the check: the spread preference was restored to `false`. Pressing a real `f` in this Chrome triggered another extension, so `f` was dispatched from script instead.
