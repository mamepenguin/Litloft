### G1 [introduced] — the M10 "equivalent" ruling is wrong, and the new pair test holds M10 only through jsdom's selectionchange events — test lets a wrong quote through (bucket: supervisor; affects invariant 5)
The r1 triage says M10/M14 are equivalent because "the paging normalises the index to the face start". It does not. `useSpreadPaging.turn` applies `next.index - index` and `pageForward`/`pageBack` return face starts only when you turn. Three paths leave `index` inside a pair: opening on the inline page (`initialPage`), the page box commit (`setIndex(n - 1)`), and the new `goToPageRef` (`setIndex(page - 1)`). Example: spread on, open on page 3. `index` = 2, face = 2–3, `face.index` = 1.
- M14 (`onClose(index + 1)`) is now killed by the new test "names a pair by its first page, to quote and to hand back" (V13).
- M10 (the capture effect writes `index + 1`) still survives that test (V12). An instrumented run shows why. The capture effect ran with `index 2, face 1` and wrote page 3. Then two `selectionchange` events in jsdom ran the second effect's `update()`, which rewrote page 2 from `face.index`. The browser has no selection event when the page boxes arrive, and that arrival is what turns the single face into the pair. So under M10 a browser quotes page 3 while the bar shows 2–3. The test is green only because of jsdom's event timing.
- Remedy for the test: assert the capture without letting a `selectionchange` reach the viewer, or assert it right after the boxes resolve. The current code (`face.index`) is correct. Only the hold is missing.

### G2 [introduced] — `goToPageRef` cleanup is unheld: removing it makes in-document links dead in the inline viewer after one full-screen visit (test gap, new code)
Mutation V3 deletes `return () => { goToPageRef.current = null; }`. After open → close, `fullscreenGoToRef.current` keeps the unmounted viewer's `setIndex` closure. `PdfPreview`'s `onItemClick` then routes every inline link there, and the call is a no-op. The PdfPreview test follows a link inline first and in full screen second, and never inline *after* a close, so V3 stays green. The lifecycle is correct as written: set on mount, nulled on unmount, set again on reopen. The file-change close unmounts the viewer the same way. Only the test is missing: follow a link inline after closing the viewer.
Note: react-pdf 10.4.1 captures `onItemClick` once, in `useRef({ scrollPageIntoView })` on the Document's first render. The handler survives this because it reads only a ref and a state setter. A handler that closed over state (e.g. `fullscreen`) would go stale. There is no comment saying so. If a code comment is wanted, this is one of the allowed kinds (a trap).

### G3 [introduced] — the render-failure message is order-dependent in a pair, and its clearing is unheld
`renderFailed` is one boolean for the whole face. Each `<Page>` sets it true on error and false on success. In a pair where one page fails and the other finishes after it, the message disappears while one page stays a white box. The message is shown only when the failing page reports last. Mutation V6 (drop `onRenderSuccess`) is also LIVE: nothing tests that the message goes away on the next page that draws, so a sticky message after one oversized zoom would pass. Low severity; no R-0 invariant covers the message.

### G4 [introduced] — the core never tests that it passes `tone: "on-dark"` (half of the F5 fix is unheld)
V8 (delete `tone: "on-dark"` from the viewer's slot props) is LIVE. The viewer test's `AddonSlot` mock reads only `documentCaptureController` and `fileId`. The addon side is held (A1–A4 killed). If the core stops sending the prop, the quote button quietly goes back to the white tile F5 measured. Bucket B, test gap. (This is the same shape as r1's M16.)
Addon check: with `tone` unset, the else-branch class string is byte-identical to the one at `ceb4ea1`, so the file-detail row is unchanged. The on-dark control is 36×36 (44 on coarse) with a 16px glyph. The bar's own buttons are 30×30 with 18px glyphs. The size gap is the deliberate floor from ADDON-DEVELOPMENT, not a defect.

### G5 [pre-existing: r1 P8, still live] — invariant 11 is only half held: `setLoadedPdf(null)` on file change survives (V21)
The new test "closes when the file changes, and stays closed on the next one" kills P5 (V20) but not P8 (V21). The r1 revision cites P8 as evidence for invariant 11. Under V21, between the file switch and the next document's load, the Full screen button and `f` are enabled against the previous file's proxy. That proxy is being torn down by react-pdf. The viewer would open on the old document under the new title. The test fires `lastOnLoad` straight after the rerender, so there is no window in which to press `f`. Suggest pressing `f` (or checking the button's `disabled`) before `lastOnLoad` in that test.

### G6 [pre-existing: r1 Z2b] — `useViewerZoom`'s `mouseSelectsText` default is unheld (Z5 LIVE)
If the default flips to `true`, the image gallery and the archive viewer stop panning a zoomed picture on mouse drag and stop paging on a mouse edge click. No test notices. The hook's Harness passes `mouseSelectsText = false` explicitly, so the hook tests never exercise the default, and the ImageGallery/ArchiveImageViewer tests do not click with a mouse. Checked: neither viewer passes the option (grep), so their behaviour at `a0b5df5a` equals the parent's. The regression does not exist today. Only the hold is missing.

### G7 [pre-existing: introduced by `3f1e6284`; the fix does not touch it] — ⌘K/Ctrl+K inside the viewer opens search *under* it and takes the keyboard: → stops paging (invariant 12)
Reproduced in the running app at `QDpWH-0a5M8K`. I opened Full screen and dispatched ⌘K from the focused dialog. The global search opened (`fixed inset-0 z-50`, portalled after the viewer's inert pass, so not inert) and focus moved to its input ("Search in 動画..."). `elementFromPoint` at the centre still hit the viewer (`z-[60]`), so the input is invisible. Then `→` left the page box at 1: the input counts as editing, so the viewer's arrows do not fire. The first Esc closed the invisible search (its `search-modal` context is pushed later at the same OVERLAY_PRIORITY). The second Esc closed the viewer. Invariant 12 says the keys the viewer binds reach the viewer. Here they reach an overlay the reader cannot see. `n` (quick note, `z-[100]`) opens *over* the viewer and is visible, so it is not this case. Fixing it means either the viewer gating the global chords while open or search painting above `z-[60]`. That is outside what this round changed, so raise it rather than extend the round.
The OVERLAY_PRIORITY change itself does not cause this: at priority 0 the search context also outranked the viewer.

### G8 [introduced] — a mouse on a coarse-primary device (iPad + trackpad) now has no way to bring the chrome or the arrows back except the keyboard or a finger (reasoned, not reproduced)
`useAutoHidingChrome` listens to `pointermove` only when `usePointerMode()` is `fine`. On iPadOS the primary pointer matches `(pointer: coarse)`, but a trackpad or mouse reports `pointerType: "mouse"`. At the parent, a trackpad click in the centre toggled the chrome and a click at an edge paged. At `a0b5df5a` both are dropped (`mouseSelectsText && s.pointerType === "mouse"`). The bar's own `onPointerDown: show` sits on an element with `pointerEvents: none` while hidden. So after the 2 s idle, a trackpad-only reader has no chrome and no on-screen arrows. Keys and a finger tap still work, so the reader is not locked out. Invariant 10 asks for exactly this mouse behaviour and says nothing about how the chrome returns. Bucket B; a supervisor call.
Answers to the other input questions:
- **Fine-pointer mouse:** the chrome returns on `pointermove`. That path is unchanged and is enough.
- **Stylus that reports `pointerType: "mouse"`** (some Windows tablet drivers in mouse mode): it is treated as a mouse. Taps neither page nor toggle, and a drag selects. This matches invariant 10's wording. A stylus that reports `"pen"` keeps taps and swipes (Z2: counting pen as mouse is not caught, want=live, and no invariant speaks for pen).
- **Image and archive viewers:** neither passes `mouseSelectsText`, so they keep the default `false`. The class-string and branch diff for them is empty. Behaviour is unchanged (see G6 for the unheld default).

## Trajectory answer (first fix round)
The fixes do not add a prediction, and the one new state is ordinary. `renderFailed` copies the inline viewer's pattern, and G3 shows that one boolean is the wrong shape for a pair.
- **`mouseSelectsText`** replaces `mouseDragPans`. It does not stack on top of it: one flag, one input type, two guards (move, up). It removes a branch as much as it adds one, because it takes the mouse out of tap classification entirely instead of adding a "double-click" or "near a word" special case. It is not yet a list of per-input exceptions. The pressure that would push it there is visible, though: G8 (a mouse on a coarse device) and a stylus that reports mouse. If the next round answers G8 by adding "unless the pointer mode is coarse" or "unless no text layer", the flag starts to encode device guesses. A watch item, not a C today.
- **`goToPageRef`** adds a second writer of `index`, beside the page box and the paging. It repeats `setIndex(n-1); setShowRightHalf(rtl)`, which the page box already does inline. That is now two copies of "enter page n" (V5 shows the second copy's half-reset is unheld). The mid-pair `index` this leaves is the root of G1. A small shared "go to page" in the viewer would remove a copy rather than add a third next round.
- **OVERLAY_PRIORITY** is a value change, not a branch.
- **The addon `tone`** is one enum value with one branch. It is fine as long as it stays a host fact ("sits on dark") and does not grow per-host variants.
