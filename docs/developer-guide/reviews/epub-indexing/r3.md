### What charging the XML reads costs a normal book (computed)

Five XML members can be charged: container, OPF, `encryption.xml`, nav, NCX (the NCX only when the nav gave no TOC). Each is capped at `XML_MAX_BYTES` = 1 MiB, and an over-cap or raising read is charged `cap + 1`. Worst case: 5 x 1,048,577 = 5,242,885 bytes, 25% of `BOOK_MAX_BYTES` (20,971,520). So the XML reads alone can never spend the budget; at worst 15.0 MiB is left for sections. A normal book's container + OPF + nav is tens to a few hundred KB, so its section budget moves from 20 MiB to about 19.7-19.99 MiB. The largest book measured in round 2 has 5.64 MiB of XHTML, so no measured book changes chunks or titles. A book whose sections total between roughly 19.7 and 20 MiB would now lose its tail sections' chunks (and heading titles if it has no TOC); none such was found.

### Budget and the character budget

With a TOC starting at section 1, a spent character budget stops every further read (neither heading nor text wanted), so the byte budget is not reached. Without a TOC, heading-only reads continue and are charged (caps3 / M14). No interaction found beyond that.

## Trajectory

*Read the fix diffs in order. Does each round add a branch, a state or a prediction that the round before it also added?*

**Yes, by the letter of the rule, in the byte budget.**

- Round 1, `29654c6`: adds a **state** (`bytes_left`), a **branch** (`if bytes_left <= 0: break`) and a **prediction** (an over-cap read cost `SECTION_MAX_BYTES + 1`).
- Round 2, `279eb67`: removes the round-1 charge line and its over-cap conditional, and moves the state into a `_ByteBudget` object threaded through four more functions. It adds a **branch** (the `try/finally` exception path) and a **prediction** (a read that raises is assumed to have decompressed `cap + 1` bytes). It also widens what the state covers (XML reads), which no test holds (M10).

So both rounds added to the same mechanism. The round-2 fix is partly consolidating (one charge site instead of a site in the loop; the over-cap special case now falls out of `len(data)`), which is the direction round 2's trajectory note asked for. But the new prediction is exactly where this round's finding sits (F1): "a raising read cost `cap + 1`" is right for r2-F2's hostile member and wrong for a small corrupt or zip-encrypted member, and the obvious round-3 fixes (charge 0 when `open` refused, charge by `compress_size`, cap the number of failed reads) each add one more case. `info.file_size` is not a safe replacement either: `ZipExtFile` truncates output to `file_size` but a single `decompress` call can still produce up to `cap + 1` bytes of work, so a lying header defeats it (measured, `scratchpad/r3/lie.py`: a 5,000,000-byte member whose headers declare `file_size` = 1 decompresses all 5,000,000 bytes in one call, then raises Bad CRC). That is the shape the rule calls a design being patched; whether it is a C is the supervisor's call.

Outside the byte budget: `6d6bf89` and `b173bc7` (round 1) removed or merged; nothing else was added in round 2.

## Findings

### F1. A small member that fails to read is charged 5 MiB, so four of them end the book

- Label: `[introduced]` (`279eb67`). Invariant: **1** ("a member over its cap or failing to parse loses only that member").
- Evidence: `_read_member` charges `cap + 1` whenever the read raises, whatever the member's size, including when `zf.open` itself raises before decompressing anything (zip-encrypted flag, unsupported compression method). For a section that is `SECTION_MAX_BYTES + 1` = 5,242,881. Four such charges exceed `BOOK_MAX_BYTES` (4 x 5,242,881 = 20,971,524 > 20,971,520), and `if budget.spent: break` drops every later section: no chunks, and in a book without a TOC no heading titles.
- Reproduction (test image, `scratchpad/r3/repro_small_bad.py`): a 10-section, 3,448-byte book, no TOC, sections 1..N made unreadable (each about 100 bytes).

  | unreadable | `5897d26` sections with chunks | `c36b5ed` `epub.py` |
  |---|---|---|
  | 3, zip-encrypted flag | 4-10 | 4-10 |
  | 4, zip-encrypted flag | **none** (0 titles) | 5-10 |
  | 3, flipped CRC | 4-10 | 4-10 |
  | 4, flipped CRC | **none** (0 titles) | 5-10 |

- Reach: low in practice. DRM'd books mark their members in `encryption.xml`, which `readable()` skips before any read, so they are not charged; zip-level encryption and CRC damage limited to individual members are rare. The budget rows in the test cover one large bad member (caps4), where `cap + 1` is also what was decompressed, so nothing holds the small case. M12 (charge 0 when `open` refuses) survives and would fix the zip-encrypted half; the bad-CRC half has no charge that is both cheap to state and safe (see Trajectory).

### F2. Two parts of the round-2 budget are not held by any test

- Label: `[introduced]` (`279eb67`). Invariant: none (the per-member caps of invariant 2 still hold; the worst case these allow is one extra read of at most 5 MiB, or about 5 MiB of XML read beyond 20 MiB).
- M7 (`left <= 0` -> `< 0`) survives. It was killed in round 2 (B2) by caps0/caps2, whose budgets were exact multiples of the member size. `279eb67` also charges the XML reads, so the budget no longer reaches exactly 0 in any row, and the boundary is unobserved.
