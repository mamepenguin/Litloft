## Findings

### F1. No bound on total work per book: a 13 KB EPUB holds the text worker for hours

- Severity: medium. Label: `[introduced]` (new file `app/extractors/epub.py`). Invariant: 1 in effect (the book does not fail other files' indexing, it stalls it; `_text_content_worker` in `app/indexer.py:1338-1370` takes one file at a time).
- Evidence: `app/extractors/epub.py` `_extract_sections`. Every cap is per member (`SECTION_MAX_BYTES`) or on *extracted* characters (`TEXT_MAX_CHARS`); nothing bounds decompressed bytes or parse work across the book. `budget` only drops by the Markdown a section yields, so markup with no text never spends it, and `wants_heading` is true for every section when the book has no TOC. Nothing dedupes sections that name the same member, so one member can be read and parsed up to `SECTION_MAX` = 2,000 times.
- Reproduction (`c3e4fa3`, test image): one 4.9 MB member of `<div><span></span></div>` repeated, referenced by N manifest items in the spine. The file is 12,936 bytes. `EpubExtractor().extract` with N=5 took 32.2 s (6.4 s per section, 0 chunks), measured with nothing else running. Linear extrapolation to 2,000 sections: about 3.5 hours. Distinct compressible members (no shared-member trick) cost the same per section at about 5-10 KB each on disk.
- Consequence: while one such book is in the queue, no other document (PDF, Office, HTML, EPUB) gets text-indexed. The spec treats an EPUB as attacker-controlled input and sets per-member caps, but no aggregate one.

### F2. The cascade that clears `document_sections` on delete ships from the ORM model, and no test covers the ORM model

- Severity: medium (test gap on an invariant). Label: `[introduced]` (new model, new DDL function, new tests). Invariant: 9.
- Evidence: `app/database.py:120` `Base.metadata.create_all(...)` runs before `_create_document_sections_table` (`app/database.py:207-209`), so the table on every install comes from `app/models.py` `DocumentSection` and the raw DDL is `IF NOT EXISTS` no-op. `init_search_db` on a fresh DB stores `FOREIGN KEY(file_id) REFERENCES indexed_files (file_id) ON DELETE CASCADE` in `sqlite_master`, SQLAlchemy's formatting, not the raw DDL's. `tests/test_document_sections.py:33-43` and `tests/test_epub_indexing_e2e.py:31-37` both build the table from the raw DDL and exclude the ORM one on purpose.
- Reproduction: mutant W06b (drop `ondelete="CASCADE"` from `DocumentSection.file_id`) passes the full suite. With W06b applied, `init_search_db` followed by `_purge_file("book1")` for a book with one title row raises `IntegrityError: FOREIGN KEY constraint failed` and leaves both the `indexed_files` row and the `document_sections` row. At `c3e4fa3` unmodified, the same script purges both.
- Consequence: no defect today; both definitions carry CASCADE. But the definition that is tested is not the one that ships. A future edit to the model alone passes CI and turns every titled EPUB into a file that cannot be purged (`purge_drive` logs and skips it).

### F3. EPUB Ask citations sent to the capture basket lose their section and show `section N`

- Severity: low. Label: `[introduced]`. At `afe25d1` an EPUB had no text index, so no Ask citation for it carried a `section N` location. Invariant: 5 (a bare spine number is shown although the section has a title), and on the note link the section is dropped. The link side is 6's concern but PR-A's `Page.tsx` produces it.
- Evidence: `frontend/Page.tsx:258-270` builds `locator: { seconds, page, label: parsed.label }`. For `section 3` that is `{ label: "section 3" }`. Core `frontend/src/lib/sourceCapture.ts:14-19` has no section field. Knowledge `frontend/CaptureBasket.tsx:66` shows `locator.label`, and `app/services/capture_markdown.py:24-33` returns link suffix `""` when neither `seconds` nor `page` is set.
- Reproduction (by reading; frontend not executed): an Ask answer that cites an EPUB at `section 3` with `section_title: "Chapter Three"`. Press "Add citation to capture basket", then commit. The basket row reads `section 3`, and the note line links `loft://<id>` with no `?section=3`. By contrast, the Ask "Save as Markdown" path (`askNoteFormat.ts`) writes `Chapter Three` and `?section=3`.
- Consequence: a user collecting book quotes into a note gets links that open the book at its start. The spec's `## Checked, no action` covers only search -> basket.

### F4. Ruby readings in section titles are dropped, but no test holds it

- Severity: low (test gap). Label: `[introduced]`. Invariant: none (3 covers chunks). It is the spec's ruby decision, and the plan's clarification 12 says "`rt`/`rp` also dropped from titles".
- Evidence: `app/extractors/epub.py` `_soup` decomposes `rt`/`rp`. That is the only thing that keeps readings out of nav/NCX labels and `h1`-`h6` fallback titles.
- Reproduction: mutant X32 (delete the decompose loop in `_soup`) passes the full suite.
- Consequence if regressed: a Japanese book whose headings carry ruby (common in vertical novels) shows titles like `漢字かんじ` on every search pill and citation.

### F5. First-occurrence mapping of a TOC target to a repeated spine file is untested

- Severity: low (test gap). Label: `[introduced]`. Invariant: none (titles only; numbering is unaffected).
- Evidence: `app/extractors/epub.py` `_toc_titles`, `first_section_of` keeps the first section per path. foliate's `resolveHref` / `getItemByHref` also resolves to the first match.
- Reproduction: mutant X22 (last occurrence wins) passes the full suite.

### F6. Small parsing rules with no test

- Severity: low (test gap). Label: `[introduced]`. Invariant: none.
- Mutants that pass the full suite:
  - X08: OPF namespace taken only from `package.tag`, not from root declarations. This only diverges from foliate for a package that binds the OPF namespace to a prefix it does not use, a book foliate cannot open either.
  - X14: nav item found by substring rather than token of `properties`.
  - X53: `media-type` not normalised with `strip().lower()`. A book declaring `Application/XHTML+XML` would index nothing.
  - X04: member cap boundary `>` vs `>=`, a one-byte difference.
- Consequence if regressed: a narrow class of books is misnumbered or unindexed. Only X53 is plausible in the wild.

### F7. `zip_names.decode_zip_filename`: the UTF-8-flag short-circuit is untested

- Severity: low (test gap). Label: `[introduced]` (the module is new in this repository). Invariant: none directly. If the name lookup misses, the member is silently lost, which invariant 1 allows.
- Evidence: `app/utils/zip_names.py:12-13`.
- Reproduction: mutant X44 (drop the `flag_bits & 0x800` check) passes the full suite. Without it, a UTF-8-flagged name whose characters all fit CP437 is re-encoded to CP437 bytes and decoded as CP932 (checked on the host: `Übersicht` -> `喘ersicht`, `ñandú` -> `､and｣`). The manifest href then misses its zip entry.
- Also see touch point 3: this is a new cross-container copy of core's module.

### F8. Sections declared as Shift_JIS or EUC-JP are skipped whole

- Severity: low. Label: `[introduced]`. Invariant: none (1 holds: the member is lost, nothing raises).
- Evidence: `app/extractors/epub.py` `_refuse_entities` runs pyexpat over the raw bytes. pyexpat rejects a multi-byte `encoding=` declaration before the root starts, which `_refuse_entities` turns into `_Refused`.
- Reproduction (`c3e4fa3`, test image): a one-section book whose XHTML declares `encoding="Shift_JIS"` (bytes encoded to match) yields 0 chunks and no title, and logs `EPUB section 1 skipped: multi-byte encodings are not supported`. The same with `EUC-JP`. UTF-8 and UTF-16 index normally.
- Consequence: EPUB requires UTF-8/16, so such books are non-conforming. The browser-based reader still displays them, though, so the book opens fine and is silently absent from search and Ask. Same effect on a nav/NCX in those encodings (titles lost).
