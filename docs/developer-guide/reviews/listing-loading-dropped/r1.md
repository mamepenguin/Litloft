## F1 — `loading` puts a Play button on surfaces where Play is forbidden

`[introduced]` · invariant 1 · bucket A
`frontend/src/components/folder/FolderToolbar.tsx:250`

`hidePlayAll` (line 105) is `isSpecialView || !!tagFilter || !!isSearch` and
line 221 folds it into `showPlayAll`. The new render condition is
`{(showPlayAll || loading) && …}` — `loading` short-circuits past
`hidePlayAll` entirely. So while the listing is in flight, a disabled **Play**
button is rendered on every surface where Play must never appear, and then
disappears when the data lands.

Reachable on: the search results page (`isSearch`), `?view=favorites`,
`?view=liked`, `?view=recent-added`, `?view=all`, and any tag-filtered listing
— `FolderBrowser` passes `loading` from `useFolderFiles` on all of them
(`FolderBrowser.tsx:582`). On the search page the window is
`paginatedLoading || semanticLoading` (`useFolderFiles.ts:326-330`), i.e. it
lasts until the semantic probe returns too.

Invariant 1 says the toolbar shows "the controls it will show once the files
arrive". On these surfaces Play is never one of them, so the change creates a
control that appears and then vanishes — the defect class the commit exists to
remove.

Evidence (probe rendered in each tree, then deleted):

| props | `6920c69c` | `fee20eda` |
|---|---|---|
| `isSearch loading` | Play present, `disabled` | absent |
| `isSpecialView loading` | Play present | absent |
| `tagFilter="x" loading` | Play present | absent |
| `isSearch loading={false} hasPlayableFiles` | absent | absent |

The committed test uses `defaultProps` with `isSpecialView: false` and no
`isSearch`, so neither new `it.each` row reaches this path.

Suggested shape (not applied): gate the placeholder on `hidePlayAll` as well,
e.g. `!hidePlayAll && (hasPlayableFiles || loading)`, and keep
`disabled={!hasPlayableFiles}`.

## F2 — the `…` menu's Play row is not held, so below 768 px nothing is held

`[introduced]` · invariant 1 · bucket A
`frontend/src/components/folder/FolderToolbar.tsx:310` vs `250`/`323`

`BAR_WIDE` is `hidden md:flex` (`ToolbarMenu.tsx:14`), so under 768 px the bar's
Play is not rendered at all and Play's only place is the `…` menu row at line
310. That row still tests bare `showPlayAll`, while the menu's View/Sort groups
just below it (line 323) were switched to the loading-aware
`!hideArrangingControls`. The two halves of the same decision now disagree.

Consequences: on a phone the change holds nothing for Play (invariant 1 unmet
there), and inside an already-open `…` menu the Play row still appears and
disappears across a reload, shifting "Selection mode" and "Rescan" under the
finger. A reload happens unprompted: `drive.structure_changed` /
`drive.file_updated` over WS call `reset()` (`useFolderFiles.ts:363-385`), which
sets `loading` true and clears the items in the same batch.

Evidence, `6920c69c`, empty folder, `…` opened:

- `loading: true` → menu holds 9 `menuitemradio` (View + Sort groups) and 2
  `menuitem` ("Selection mode", "Rescan"). No Play row.
- `loading: false, hasPlayableFiles: true, total: 3` → menu rows are
  `["Play", "Selection mode", "Rescan"]`.

Same defect as F1 and it wants the same single predicate for both call sites.

## F4 — an empty or media-free folder now flashes four controls it will not keep

`[introduced]` · invariant 1 (as written, it blesses this) · bucket B, raise to supervisor
`frontend/src/components/folder/FolderToolbar.tsx:111`, `250`

`loading` is used as "show the controls" rather than "keep whatever was there",
and the core cannot know the listing's shape before it answers. So on the
listings where the fix has nothing to hold, the shift is created rather than
removed, in the opposite direction:

- Ordinary folder with no audio/video (a notes or documents folder): a disabled
  Play appears during the fetch and leaves when the listing lands.
- Empty unfiltered folder: bar during load is
  `["Add", "Play", "View", "Sort", "Filter", "More actions"]`; once the listing
  is known empty it is `["Add", "More actions"]`. Four controls appear and go.
  On `fee20eda` that toolbar was stable throughout — probe on the parent:
  `folder+loading play: false sort: false`.

The two new `it.each` rows assert exactly this (`present=true` for
`loading && !hasPlayableFiles`; `present=true` for
`loading && total===0 && folderCount===0`), so the tests encode it. I am not
calling it A because the approved invariant list says in so many words that
"Play's place" is shown while loading, and invariant 2 only requires the
arranging controls to be hidden *once the listing has answered*. It is a
design question, not a contract violation, so it goes to the supervisor: the
change trades a shift on populated media folders for a new shift on empty and
media-free ones, and the measurement table in `invariants.md` records only the
home → Library and Library → folder paths, neither of which is an empty folder.

Two shapes avoid it without a listing skeleton: reserve Play's width with a
non-interactive spacer instead of a button, or hold Play only when this
subject was already known to have media (a sort change or a WS refresh of a
video folder — the case the fix is actually for — has that knowledge; a first
navigation does not).

## F5 — a disabled placeholder enters the tab order and the a11y tree unlabelled

`[introduced]` · none · bucket B
`frontend/src/components/folder/FolderToolbar.tsx:251-259`

The placeholder is a real `<button disabled>` with no `aria-busy` and no
`aria-hidden`, so the toolbar's focus order gains a stop when the data arrives,
and a screen-reader user browsing during load meets "Play, button, unavailable"
with nothing saying why — including on the surfaces of F1, where it is simply
false. Fixing F1/F2 removes most of the exposure; `aria-busy` or `aria-hidden`
on the placeholder would remove the rest. Not measurable in jsdom beyond the
attributes (`disabled` present, `aria-disabled` null).

## F6 — `loading` cannot stick true: checked, no defect

`[n/a]` · invariant 1 · no action

The brief asks whether a failed, aborted or empty-drive listing can leave the
disabled Play and the arranging controls on screen forever. It cannot, and it is
worth recording where that is enforced:

- `useInfiniteScroll.loadPage` clears `loading` in `finally`, guarded on
  `fetchIdRef.current === id` (`useInfiniteScroll.ts:108-112`); the `catch`
  branch above it only empties the items.
- every path that supersedes a fetch bumps `fetchIdRef` *and* schedules a new
  one: `reset()` increments it and bumps `epoch`, which is a dependency of the
  load effect (`useInfiniteScroll.ts:118-153`).
- `disabled: isRecent` is handled by `if (disabled) { setLoading(false); … }`.
- `semanticLoading` is the other half of the search-page `loading`
  (`useFolderFiles.ts:239-271`). Its awaits cannot reject: `fetchSemanticHits`
  wraps everything in `try/catch → []` (`semanticSearch.ts:38-56`) and
  `isSemanticSearchAvailable` → `getEnabledAddons` → `fetchAddonsStatus`
  catches too (`addons.ts:65-80`). The abort return skips
  `setSemanticLoading(false)`, but an abort only happens from the effect
  cleanup, i.e. with a re-run queued that sets it again and resolves.
- an empty drive answers with `total: 0` and `loading` false, which is
  invariant 2's path.

## Is anything missing from the R-0 list?

Three things, in the order I would add them.

1. **A surface where Play is never shown must not gain one while loading.**
   Invariant 1 names "Play's place", which reads as unconditional and is what
   F1 exploits. The list needs the negative half, written so a mutation
   violates it: *"On a search, a special view or a tag-filtered listing, the
   toolbar shows no Play at any point, loading or loaded."* Without it F1 is
   arguably in-spec, and nothing in the file says otherwise.

2. **Below 768 px, "Play's place" means the `…` menu row.** Invariant 1 is
   silent about which of the two call sites it governs, and only one was
   changed (F2). Either state that the bar and the menu answer the same
   predicate, or state that the mobile behaviour is deliberately unchanged.
   As written the list cannot distinguish the two, so a reviewer cannot call
   F2 a violation.

3. **The listing's own controls are supplied by `FolderBrowser`, from the same
   `loading` the listing renders with.** Every invariant is phrased about the
   toolbar's props, so all five survive M6 — the deletion of the change.
   Invariants about a component's internals cannot catch an unwired component;
   one line at the screen level fixes that.

Also worth noting, though I would not add it: the spec's §B holds "`Play`,
**and the item count**" to their places, and the count is not part of this
change (`FolderBrowser.tsx:503-545` still shows `settledTotal`, i.e. nothing,
until a subject settles). The approved invariants do not mention the count, so I
treat it as deliberately out of scope rather than an omission — but if the
supervisor believes §B was meant whole, the count is the missing half and F4's
flash is worse with it (the count appears in the same frame the controls leave).
