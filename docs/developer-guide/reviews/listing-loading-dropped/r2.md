## Part 2 — new findings

### N1 — the hold records the data, not what was shown, so a subject where Play is forbidden lends Play to the next one

`[introduced]` · invariant 1 ("no more, no less") · bucket **A**
`frontend/src/components/folder/FolderToolbar.tsx:116-125`, `237-238`

`lastKnown.playable` is written as `hasPlayableFiles` — a property of the data —
while what the bar renders is `showPlayAll = !hidePlayAll && …`. The two differ
on every subject where `hidePlayAll` is true (search, `?view=…`, a tag
listing): the bar shows no Play, but it records `playable: true` anyway. When
the next subject is a plain folder, `hidePlayAll` goes false and the recorded
bit is replayed, so the in-flight bar offers a Play that this bar never showed
and that the arriving folder may not deserve.

`hideArranging` does not have this problem: `hideArrangingControls` *is*
`liveHideArranging` whenever `!loading`, so that field records the rendered
decision. Only `playable` records the wrong quantity.

**Reachable from the sidebar, in one click, inside a single mounted
`FolderBrowser`.** `SidebarLibrarySection.tsx:61-77` and
`src/app/drive/[name]/page.tsx` put Library / Favorites / Liked / Recent /
Recent added / All on the **same route** (`/drive/[name]?view=…`), all rendering
`<FolderBrowser>` from the same position in the tree, so the ref survives the
navigation. `library` is not in `useFolderFiles`' `isSpecialView` set
(`useFolderFiles.ts:106`) nor in `FolderBrowser.tsx:123`, so `hidePlayAll`
flips from true to false across "Liked" → "Library".

Screen-level probe (real `FolderBrowser`, `useFolderFiles` mocked, the header
test's own harness plus a `files` fixture — appended, run, removed):

| step | develop `fee20eda` | parent `6920c69c` | **HEAD `88fe4cb7`** |
|---|---|---|---|
| `?view=liked`, answered, videos | no Play | no Play | no Play |
| render after the click (stale data, `reset()` still queued) | Play | Play | Play |
| **`reset()` done: in flight** | **no Play** | Play (disabled) | **Play (enabled)** |
| Library root answers: subfolders only | no Play | no Play | no Play |

The same at the component level for **search → folder**
(`?q=…` video hits → a folder): in flight, Play at `88fe4cb7`, absent at
`fee20eda`.

The one-frame flash in the second row is on develop too, so that part is
`[pre-existing]`. What is introduced is the third row: the wrong Play now stays
up for the whole fetch instead of one frame. The commit message says the bar
"keeps what it was already showing"; on this path it shows something it was
not.

Note the comment at `113-115` asserts exactly the property this breaks. If the
finding is fixed at line 118 (`playable: hasPlayableFiles && !hidePlayAll`, or
better, hoist `showPlayAll` above the ref and record that), the comment becomes
true. Do not settle it by editing the comment.

### N2 — the held Play is enabled, and pressing it during a reload does nothing

`[introduced]` · none of the revised invariants (old 3 was dropped) · bucket **B**
`frontend/src/components/folder/FolderToolbar.tsx:267-273`, `FolderBrowser.tsx:457-469`

Round 1 rendered the held Play as `<Button disabled>`; F5 objected to the
disabled placeholder and the shape change removed it. The button is now a live
`onClick={onPlayAll}` throughout the hold, and `handlePlayAll` opens with
`const firstPlayable = files.find(…); if (!firstPlayable) return;` — so during
any reload that clears the items it is a silent no-op.

Measured at HEAD: in flight, `present: true`, `disabled: false`, and a click
calls `onPlayAll` once (parent: `present: true`, `disabled: true`, 0 calls;
develop: absent).

Reachable without navigating: `drive.structure_changed` /
`drive.file_updated` over WS → `reset()` (`useFolderFiles.ts:376-384`), which
does `setItems([])` and `setLoading(true)` in one batch
(`useInfiniteScroll.ts:117-128`). The bar keeps an enabled Play, the press is
swallowed, nothing tells the user why. A reload that does *not* clear the items
(a sort change re-runs `loadPage` without `reset`) still plays, so the control
works sometimes and not others.

The revised invariants deleted the old "the Play held in place while loading
cannot start playback", so nothing in the list is violated — which is why this
is B rather than A. It is the natural candidate if the supervisor revises the
list again: *a held control either acts or says it cannot*.

### N3 — nothing holds F2's fix: the `…` menu's Play row can stop holding, silently

`[introduced]` · invariant 1 below 768 px; R-4 "a test that lets an A through is an A" · bucket **A**
`frontend/src/components/folder/FolderToolbar.tsx:322`

F2 was fixed the right way — one predicate (`showPlayAll`) for the bar at `267`

### N4 — the two `loading ? …` ternaries are dead, and hide the ordering they depend on

`[introduced]` · none · bucket **B**
`frontend/src/components/folder/FolderToolbar.tsx:126-128`, `237-238`

Because `lastKnown.current` is overwritten with the live values on every
`!loading` render *before* either is read, `loading ? lastKnown.current.X : liveX`
is identical to `lastKnown.current.X`. Rewriting both to read the ref
unconditionally leaves the suite green (M12), and moving the write below the
reads also leaves it green (M11) — the second one only because the ternaries
mask it.

So the code states a condition twice and depends on a statement order that no
test holds. Either read the ref unconditionally (two lines shorter, and then
M11 becomes a killable mutation), or keep the ternaries and drop the eager
write. Not a behaviour defect today.

### N5 — a first load still offers the arranging controls on a search, which revised invariant 2 forbids

`[pre-existing]` · invariant 2 · bucket **B**
`frontend/src/components/folder/FolderToolbar.tsx:111-112`

`liveHideArranging` includes `!isFiltered`, and `isFiltered` is true whenever
`isSearch`. So on the very first render of a search page the ref initialises to
`hideArranging: false` and View / Sort / Filter are on the bar before any
result exists. Revised invariant 2 says "a toolbar that has never seen a
listing offers no arranging controls and no Play".

Measured identical on develop (`first-load search sort: true` in all three
trees), so the change did not introduce it and R-4 keeps it out of bucket A.
Recording it because it is the one place the approved list and the shipped code
disagree, and a later reviewer given only the list would call it a violation.
Either the invariant needs "unless a filter or a query is the subject", or the
search page's first load needs to start from `hideArranging: true`.

## Checked, no defect

- **`lastKnown` under StrictMode.** Both renders of a pair carry the same
  props, so the write is idempotent. Measured with `<StrictMode>` around the
  toolbar: first-load-in-flight `sort: false, play: false`, held reload
  `sort: true, play: true` — the same as without it. (At the parent, StrictMode
  showed `sort: true, play: true` on a first load, i.e. round 1's F4.)
  Writing a ref during render is still against the documented rules and a
  transition render that React discards would leave the write behind; nothing
  in jsdom can produce that, and the values written only ever move the hold
  toward the freshest answered listing, so I have no reproduction to offer.
- **`loadingMore` (pagination).** `loadPage(page+1, true)` sets `loadingMore`,
  never `loading` (`useInfiniteScroll.ts:73-77`), and `FolderBrowser` passes
  `loading`. So an infinite-scroll append does not engage the hold at all, and
  `lastKnown` keeps tracking the growing listing. Correct.
- **A listing that errors.** `loadPage`'s `catch` does `setItems([])` /
  `setTotal(0)` and the `finally` clears `loading`, so a failed fetch is
  indistinguishable from an empty folder and the bar drops to
  `["Add", "More actions"]`. Same on develop; the hold cannot strand controls
  because `loading` always ends false (round 1 F6, re-checked).
- **`selectable`.** `setSelectable` is local `FolderBrowser` state and resets
  nothing; the toolbar reads it only for the `…` trigger's colour. No
  interaction with the hold.
- **Trash and Missing.** `src/app/drive/[name]/page.tsx:19-25` returns
  `TrashView` / `MissingView` before `FolderBrowser`, and neither renders
  `FolderToolbar` (only `FolderBrowser.tsx:572` does). Untouched.
- **Anything else reading the overridden props.** `loading` and
  `hasPlayableFiles` appear in `FolderToolbar` only at `116-128` and `237-238`;
  `total` and `folderCount` keep feeding `liveHideArranging` and nothing else.
  No other consumer is shadowed.
- **The toolbar's own unmount.** `hideToolbar` (`FolderBrowser.tsx:167`) drops
  the toolbar when a file is selected in two-pane mode, which resets the ref.
  Selecting or deselecting a file does not reload the listing, so the remount
  always initialises from an answered listing.

## Trajectory — read the two fix diffs in order

**This round removes a prediction; it is not another patch.** Plainly:

`6920c69c` added an input (`loading`), two conditionals (`!loading &&` on
`hideArrangingControls`, `|| loading` at the Play render site) and one rendered
state (`disabled={!showPlayAll}` on a placeholder button). Behind all three sat
one prediction: *a listing in flight will turn out to want view, sort, filter
and Play.* Every one of round 1's A findings (F1 Play where Play is forbidden,
F2 the phone menu, F4 the empty folder) is that prediction being wrong about a
different listing.

`88fe4cb7` deletes all three of those — the conditional, the render-site
conditional and the disabled state — and replaces the prediction with a record
of the last answered listing. It does not add a case per surface: search,
special views, tag listings, the phone menu and the empty folder are all fixed
by the same substitution, and F2 is fixed by *merging* two predicates rather
than by editing the second one. It also gained the detector round 1 was missing
(F3). One piece of state came in (the ref) and one branch (`if (!loading)`);
two conditionals and one visual state went out. By the rule's own test — "a
round that removes a branch, a state or a prediction is the loop converging" —
this round converges.

The caveat, and it decides whether a round 3 is convergence or patching: the
recorded value is the wrong quantity (N1). The fix that keeps converging is to
record **the decision the bar rendered** — hoist `showPlayAll` above the ref
and store that, so "the bar holds what it was showing" becomes true by
construction and `hidePlayAll` cannot be bypassed by the hold. The fix that
would turn this into patching is a subject key plus a case per transition
(search → folder, view → folder, drive → drive). If round 3 arrives shaped like
the second one, the pattern the rule warns about has started; nothing in these
two diffs shows it yet.
