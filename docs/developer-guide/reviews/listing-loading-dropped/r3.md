## Part 1 — verdicts on round 2's items

### N1 (the hold recorded `hasPlayableFiles`, not the rendered decision) — **the code changed, the defect did not**

The mechanical part was done: `livePlay` now folds `!hidePlayAll` in, and both
occurrences of that guard are load-bearing and separately held (M1 kills the
recorded one, M2 kills the read; see the mutation table). The committed test
passes.

But the reproduction N1 was written from is **still open**, at the screen level,
with the real `FolderBrowser`. See **N6**. Round 2's N1 named the path "Liked →
Library, one click, one mounted `FolderBrowser`"; measured at `da746aae` that
click still holds a Play through the whole fetch, byte-identical to `88fe4cb7`.

The cause is one layer below where the fix was applied: the render on which the
subject changes is **not** the render that answered the previous listing. It
carries the new subject's flags and the *previous* subject's counts, with
`loading` still `false` — and `if (!loading)` writes on it. `FolderBrowser`
already says so, in its own words, 100 lines above the toolbar call
(`FolderBrowser.tsx:471-474`):

> `!loading` is not enough to adopt a `total`: `reset()` lives in an effect, so
> on the render where the subject changes the hook still reports
> `loading: false` and the *previous* subject's `total`. A subject becomes
> trustworthy at mount or once a fetch for it has been seen to start.

So the fix records "the decision the bar rendered" faithfully — and the frame it
records is the stale frame. **Not fixed.**

## Part 2 — new findings

### N6 — the hold records the stale render, so Liked → Library still replays a Play for the whole fetch

`[pre-existing]` at `da746aae` · `[introduced]` by the branch, measured against
`fee20eda` · invariant 1 ("no more, no less") · bucket **A**
`frontend/src/components/folder/FolderToolbar.tsx:118`

`if (!loading)` treats every non-loading render as "a listing has answered".
One class of render is neither: the render on which the subject changes.
`reset()` lives in an effect, so that render has the **new** subject's
`isSpecialView` / `isSearch` / `tagFilter` and the **old** subject's `files` and
`total`, with `loading` still `false`. `livePlay` on that render is
`!hidePlayAll(new) && hasPlayableFiles(old)` — for Liked → Library, `false &&
true` → **`play: true` is recorded**, and then held for the entire fetch.

Folding `!hidePlayAll` into the recorded value cannot catch this, because on that
render `hidePlayAll` has *already* flipped to the permissive subject.

Screen level, real `FolderBrowser`, `useFolderFiles` mocked with the header
test's own fixture (probe appended to `FolderBrowser.header.test.tsx`, run,
reverted):

| step | `fee20eda` develop | `88fe4cb7` parent | **`da746aae` HEAD** |
|---|---|---|---|
| Z1 `?view=liked` answered, one video | `play:false sort:true` | `play:false sort:true` | `play:false sort:true` |
| Z2 the click — Library props, Liked listing, `loading:false` | `play:true` | `play:true` | `play:true` |
| **Z3 `reset()` done — in flight, items cleared** | **`play:false sort:false`** | **`play:true sort:true`** | **`play:true sort:true`** |
| Z4 Library root answers, subfolders only | `play:false sort:true` | `play:false sort:true` | `play:false sort:true` |

Z2 is the one-frame flash that exists on develop too. Z3 is the defect: on
develop the wrong Play is gone in the next frame; on this branch it stays up
until the folder answers. **Identical at the parent**, so this commit did not
introduce it and did not remove it.

Same at the component level for search → folder with the stale frame included
(`T1..T4`: `false, true, true, false`) — and identical at `88fe4cb7`. Note that
the *drive change* has the same shape (`countedSubject` includes `driveName`),
and `FolderBrowser` carries no `key`, so the ref survives it.

The remedy is not a case per transition. `FolderBrowser` already computes
exactly the gate this needs, for exactly this reason: `countedSubject` +
`trusted` (`FolderBrowser.tsx:475-492`), "a subject becomes trustworthy at mount
or once a fetch for it has been seen to start". The toolbar's hold is at the
wrong altitude — the screen knows when a subject becomes trustworthy and the bar
cannot. See the trajectory section; I am not proposing the fix.

The comment at 113-116 asserts the property this breaks ("Hold what this bar
last showed — the decision, not the counts it came from"). On this path the bar
holds the decision of a frame that mixed the new subject's flags with the old
subject's counts. Round 2 said not to settle N1 by editing the comment; that
still applies.

### N7 — the new test reaches the held state by a transition the app cannot produce, so it is green while N6 is open

`[introduced]` (the test is created by this commit) · R-4 "a test that lets an A
through is an A" · bucket **A**
`frontend/src/components/folder/__tests__/FolderToolbar.test.tsx:98-111`

the test that made N1 look closed. This is the same failure mode as round 1's
committed `it.each`, which used `defaultProps` and so never reached F1.

Both N6 and N7 are held by one test: drive the three frames
(answered-forbidden → stale → in-flight) at the `FolderBrowser` level, where the
stale frame is produced by the component rather than asserted by hand.

## Checked, no defect

- **The replay in the other direction.** Recording the rendered decision makes
  the hold *withdraw* across a forbidden subject rather than show something
  false: folder-with-media → search answered → folder in flight gives
  `play:false`, and Play appears when the folder answers (P1: `true, false,
  false, true`). Invariant 1 endorses that — the listing before showed no Play.
  This is the intended consequence of the change, not a new defect.
- **The ref write during render, with both reads unconditional.** The write
  precedes both reads and a mutation that moves it below them is now killed
  (M6). StrictMode is identical to non-strict at every step (P3: first-load
  `play:false sort:false`; answered `true true`; held reload `true true`;
  answered-empty `false false`). Writing a ref during render is still outside
  the documented rules and a discarded transition render would leave the write
  behind; jsdom cannot produce one and I have no reproduction. Unchanged from
  round 2 — except that N6 shows the write's *gate* is wrong for a reason that
  has nothing to do with concurrency.
- **Both `!hidePlayAll` are load-bearing, and each is held separately.** M1
  (drop it from the recorded value) is killed by the new replay test alone; M2
  (drop it from the read) is killed by the three `it.each` rows. They are not
  redundant: the recorded one stops a forbidden subject lending Play forward,
  the read one stops an allowed subject lending Play into a forbidden one.
- **`selectable` and `hideMutatingActions`.** `selectable` only tints the `…`
  trigger. `isWriteDestination` gates `leftActions` and `showBulkRows` and is
  outside the hold, so on an in-flight root tag listing held from a folder the
  bar is `play:false sort:true add:false` (P4) — Add leaves immediately while
  Sort is held. Inconsistent-looking, in no invariant, and identical at the
  parent.
- **Remount while loading.** `hideToolbar` (`FolderBrowser.tsx:167`) unmounts
  the toolbar when a file is selected in two-pane mode; remounting mid-flight
  re-initialises the ref from in-flight props and the hold is lost (P5:
  `play:true sort:true` held, then `false false` after remount). Reaching it
  needs a listing reload concurrent with deselecting a file. Identical at the
  parent; round 2 recorded the same reasoning.
- **Nothing else reads the three counts.** In `FolderToolbar`, `total` and
  `folderCount` appear only at line 111 and `hasPlayableFiles` only at 112. In
  `FolderBrowser`, `hasPlayableFiles` is derived at 439 and `folderCount` is
  `folders.length` at 583; `total` additionally feeds the settled-count
  machinery at 471-503 — which is the machinery N6 says the hold is missing,
  not a second consumer of the hold.
- **The bar's own two reads.** `{!hideArrangingControls}` on the bar (M17) and
  `{showPlayAll}` on the bar (M10) are both killed, at the component and the
  screen level.
- **The wiring.** Deleting `loading={loading}` from `FolderBrowser.tsx:582`

## Trajectory — the three fix diffs in order

**The answer changed from round 2. This is not converging, and I would put the
trajectory question's answer as yes: each round adds one more prediction about
when the props may be believed, and the next round finds the state where that
prediction is false.**

Round 2 called `88fe4cb7` convergence on the shape of the diff, and on that
measure it was right, and `da746aae` looks better still: it adds no branch and
no state, deletes two dead ternaries, and makes a previously-unkillable mutation
killable. By the letter of the rule — "a round that *removes* a branch, a state
or a prediction is the loop converging" — round 3 converges.

Measure the *predictions* instead and the three rounds line up:

| round | the prediction it added | the state that falsifies it |
|---|---|---|
| `6920c69c` | `loading` tells the bar what is coming | a search, a special view, a tag listing, an empty folder (r1 F1/F2/F4) |
| `88fe4cb7` | the last answered listing tells the bar what to show | the recorded quantity is not what was shown (r2 N1) |
| `da746aae` | the last `!loading` render *is* the last answered listing | `reset()` lives in an effect, so it is not (N6) |

Three rounds, three mechanisms, **one unchanged user-visible symptom**: the bar
offers a Play the previous listing did not. Measured at Z3 it is byte-identical
across `6920c69c`, `88fe4cb7` and `da746aae`, and absent on `fee20eda`. A loop
where the diffs shrink while the symptom is unmoved is not converging; it is
approaching the defect from progressively smaller distances.

The specific signal the rule asks for: round 2 wrote down, in advance, which
shape would mark this as patching — "a subject key plus a case per transition".
The fix N6 needs is a subject key. It is already written, one component up:
`countedSubject` + `trusted` in `FolderBrowser`, added for the item count for
the *identical* reason and carrying the comment that explains why `!loading` is
not enough. So round 4 either duplicates that machinery inside the bar — a third
piece of state on the same decision, and the shape round 2 named — or it accepts
what that machinery's existence says: **the bar cannot know when a subject
became trustworthy, and a hold keyed on the bar's own props is at the wrong
altitude.** The screen already tracks it.

That is a judgement about the design, so under R-4 it is not mine to assign. I
am reporting the two things the rule asks for: the answer to the trajectory
question is *yes, each round adds a prediction the round before also added*, and
the diffs it refers to are `6920c69c`, `88fe4cb7`, `da746aae` — `git show` on
each. The count also matters: this is the **third** round on the same symptom,
and round 2's own criterion for discarding a branch is two C findings.
