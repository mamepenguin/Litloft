## Findings

### 1. The single-axis cap is tested only with the type axis, so the case the commit is for can lose its cap unnoticed
- Label: [introduced] (the branch and the test are both new in this commit)
- Bucket: A (a test that lets a break of invariants 7/8 through)
- File: `frontend/src/components/folder/FilterMenu.tsx:107-113`; test `frontend/src/components/folder/__tests__/toolbarBarScope.test.tsx:251-268`
- Failure scenario: mutation F11 changes the single-axis guard from `isFiltering` to `typeFilter !== null`. All 336 tests still pass. With that code, trust-only "Unjudged only" (the long axis the commit message names) gets no cap below 640.
  Arithmetic at 320px, coarse pointer, en (needs a browser to confirm): content width 320 − 32 = 288. Add (md: 32 padding + 16 + 6 + ~26 + 6 + 14) ≈ 100. Filter (2 + 24 + 16 + 6 + 95) = 143. `…` = 44. Gaps 3 × 8 = 24. Total ≈ 311 > 288, so the row wraps. That is the regression the commit fixes.
  The test only renders `typeFilter="text"` ("Text", which is short). A single-axis case with `trustFilter="unreviewed"` and `typeFilter={null}` would kill F11.
- Reproduction: apply F11 and run `npx vitest run src/components/folder/__tests__/toolbarBarScope.test.tsx src/components/folder/__tests__/FilterMenu.test.tsx`. Everything passes.

### 2. "Play is in one place or the other" is checked on the overflow side only in the rest state
- Label: [introduced] (the overflow Play row is new in this commit)
- Bucket: A (a test that lets a break of invariant 3 through)
- File: `frontend/src/components/folder/FolderToolbar.tsx:302`; tests `toolbarBarScope.test.tsx:404-425`
- Failure scenario: mutations M26 (`showPlayAll && !selectable`) and M28 (`showPlayAll && !creatingFolder`) both survive.
  With either one, a phone user (<768px) in selection mode, or while the new-folder field is open, opens `…` in a playable folder. No Play row appears, and the bar Play is `hidden` below 768, so Play is in neither place.
  `STATES` checks the bar side for every state, including select mode and naming, but only in the jsdom class sense. The overflow side is checked only by "plays from the overflow and closes it" (rest state) and the four negative cases.
  A small `it.each` over the positive states (select mode, naming a folder, filtering) that asserts the overflow `menuitem "Play"` exists would kill both mutations.
- Reproduction: apply M26 or M28 and run the 12-file set. 336/336 pass.

### 3. Nothing in CI holds the one-row property, and at 320px the slack is only a few pixels
- Label: [pre-existing] for the missing layout detector (the parent's phone bar had no browser test either). The thin slack comes from this commit, because Add (about 100px) now shares the row.
- Bucket: A if invariant 7 is meant to be held by a test. Otherwise raise to the supervisor. `review-workflow.md` says jsdom cannot hold layout and points to `frontend/e2e-layout/`, which has no toolbar spec at this SHA.
- File: `frontend/src/components/folder/FolderToolbar.tsx:226`
- Failure scenario: mutation M32 (`gap-2` → `gap-6` on the bar) passes the whole suite. Arithmetic at 320px, en, two axes (capped at 64), coarse pointer: 100 (Add) + 112 (Filter: 2 + 24 + 16 + 6 + 64) + 44 (`…`) + 3 gaps.
  - With `gap-2`: 282 ≤ 288, about 6px spare.
  - With `gap-6`: 330 > 288, so it wraps.

  Any later edit that adds about 6px to any of these controls (a longer Add label, a chevron gap, a new addon inline button, a padding change) brings the second row back with no failing test. Needs browser measurement. The numbers are estimates from class arithmetic and label glyph widths.

### 4. The overflow Play wrapper's `role="presentation"` is not held
- Label: [introduced] (a line this commit creates)
- Bucket: B
- File: `frontend/src/components/folder/FolderToolbar.tsx:303`; test `toolbarBarScope.test.tsx:270-285`
- Failure scenario: mutation M11 removes `role="presentation"` and survives. The existing test walks up only from `role="group"` elements, and the Play wrapper contains a bare `menuitem`, not a group. Whether a bare generic `<div>` between `role="menu"` and a `menuitem` actually breaks ownership depends on the AT: ARIA 1.2 allows generic intermediaries. So this is a gap in the detector, not a demonstrated defect a user can hit, and it breaks no declared invariant.
- Reproduction: apply M11 and run toolbarBarScope. All pass.

## Is anything missing from the invariants list?

1. **Invariant 3 does not name the states in which Play must still be offered.** As written it lists only the negative states. Suggest stating that the overflow row and the bar button share one predicate, so that select mode, an open new-folder field and an active filter do not change where Play is offered (see finding 2).
2. **Which filter axis invariant 7 is about.** "One or two filter axes" does not say which single axis. The widest single-axis face is trust "Unjudged only" (en), or "検証済みのみ" (ja, 6 × 14px = 84px). The list should name the widest face, or the check can pass with "Text" (see finding 1).
3. **The new-folder field is now part of the sticky bar below 768px.** Before, the phone name field (and `folderError`) sat in a non-sticky row above the bar. Now it sticks and makes the sticky bar two lines tall while naming. Invariant 6 covers "once, on its own line", but not whether sticking is intended.
4. **Focus after choosing Play from `…`.** `closeMore()` returns focus to the `…` trigger. Invariant 4 covers "called once and menu closes" but not where focus lands. M23 (order swap) survives harmlessly today, but removing the `focus()` would not be caught by invariant 4's wording.
5. **Add's menu at phone width.** The Add menu is `absolute z-30` inside the sticky `z-20` bar, and it now opens from a bar at 320px instead of a static row. "The Add menu opens fully on screen and is not covered at 320px" is a browser-only property that the list does not declare.
