# r5 findings — EPUB reader controls

Reviewed commit: 3f567baab25656497423c02102a866d7b951fa6e ("fix: let a finger anywhere on the EPUB slider's row drag it"), on its own, in worktree /Users/libre/Sources/video_share-epub-controls. Parent fef2d1ae0.

## Findings

### F1 [introduced] A tap on the disabled bar seeks, and while the book is still opening that seek is never answered, so the bar sticks at the tap point

Bucket proposal: none of 1–10 names it; user-reachable, so it is grounds for the supervisor to revise R-0 (see R-4). The author does not assign.

- Real browsers deliver pointer events to a disabled `<input type=range>`. Measured with Playwright against a bare page (disabled range, opacity 0, full-row): Chromium, WebKit and Firefox, mouse and touch, all log `pointerdown`/`pointerup` on the disabled input (`input`/`change`/`mousedown` do not fire). React does not filter pointer handlers on disabled controls (it filters only mouse/click).
- HEAD adds `onPointerDown` → `dragTo` → `setDrag(value)` with no `disabled` guard, so the existing `onPointerUp` → `commit(true)` now has a `drag` to commit: `onSeek(fraction)` + `onPointerCommit()`. At HEAD~1 the only pointer path into `drag` was the native `change`, which a disabled range never fires.
- The bar is disabled while `place === null`, i.e. from mount until the reader's first `location`. The reader drops `seek` until `state.ready` (`public/epub-reader/reader.js`, `case "seek": if (!state.ready ...) return;`), so no `seeked` answers it, and `useEpubReader` holds `seeking` until that answer. `place = seeking ?? location.fraction` then shows the tap point for good: every later `location` is ignored, `pagesLeft` stays hidden, the chapter label follows the tap point, until the reader seeks again.
- Reproduced (temporary test, removed): boot → pointerdown/up at clientX 70 of a 100px row → `ready` → `location 0.4` → `location 0.45`: HEAD shows value `700` and no "left in chapter"; HEAD~1 shows `450` and passes. A second temporary test asserting "a tap on the disabled bar (after `ready`, before `location`) posts no seek" fails at HEAD (`[{type:"seek",fraction:0.7,id:1}]`) and passes at HEAD~1.
- Reachability: any EPUB large enough that opening takes a moment; the tap target is now the full 24px row, and on touch the knob is hidden while disabled, so nothing tells the reader the bar is inert. Also fires `onScrubbingChange(true)` while disabled (harmless inline; in full screen the chrome is already up).
- No test holds it: nothing drives pointer events at a disabled bar. SeekBar has no such guard either, but its `disabled` state has different consequences; that is not this change.

### F2 [pre-existing] A pointer release with the slider focused sends two seeks (commit, then blur commits the stale `drag` again)

`commit(true)` calls `setDrag(null)` then `onPointerCommit` → `focusBook()` → the input blurs synchronously inside the same handler, and the rendered `onBlur` still closes over the old `drag`, so `commit(false)` posts a second `seek` with a new id. Reproduced in jsdom by making the mocked `readerWindow.focus` blur the active element: 2 seeks at HEAD and 2 at HEAD~1. Not introduced; HEAD only widens how often a tap focuses the input (any point on the row). Real-browser synchronous blur on `contentWindow.focus()` was not measured. Likely consequence is an extra `seeked` round trip (the reader queues the second seek to the same target, which lands on the page already shown and reports no turn), so invariant 2 probably holds; not verified.

### F3 [introduced] Nothing tests the drawn knob and fill, which now are the only visible position, including the rtl mirror

B (test gap; no invariant names the drawn position). Before HEAD the native range drew its own thumb from `value` + `dir`. Now `visual` is computed separately from `valueAt`, and M11 (drop the rtl mirror from `visual`, so an rtl book's knob and fill show on the wrong side while `valueAt` still mirrors) survives, as does M12 (knob drawn while disabled). Both are inline `style` / presence and are checkable in jsdom without layout. Reasoned correct at HEAD: rtl `visual = 1 - shown/1000`, fill `right:0; width: shown`, knob at `visual`, which is where `valueAt` puts a finger at x.

### F4 [introduced] Mouse and touch map a point on the row to different values (up to half a thumb width)

B. Measured with Playwright (Chromium, WebKit, Firefox; 300px row, opacity-0 appearance-none range): a mouse press at 10px gives `pointerdown` → x/W = 33, then the native `input` → 0; a move to 290px gives 967 then native 964–966. With a mouse the native `input` fires after each pointer event and wins, so the committed value is the native one (thumb-width inset), which matches the knob formula `calc(v% + (0.5-v)*16px)` — the knob sits under the cursor. With touch the native range does not move, so the value is `clientX/W` and the knob is drawn up to 8px from the finger near the ends. Each mouse event renders twice with two values. Same design as SeekBar. No invariant affected; not reachable as a wrong seek, only as a small offset.

### F5 [introduced] The row test pins `rect.left` at 0, so dropping the offset survives

B (test gap). M18 (`clientX / rect.width` instead of `(clientX - rect.left) / rect.width`) survives because the mocked rect starts at 0. In the app the row starts at least `px-3` in, so the mutation seeks every finger a fixed distance off. A non-zero `left` in the existing test's rect would hold it.

### Checked, nothing found
- Keyboard: the input keeps `dir`, `value`, `onKeyUp` and `onBlur`; range keys are the native ones (M19 kills). Focus by Tab is unchanged (opacity 0 does not remove focusability); the ring moves to the track via `peer-focus-visible`, `peer` precedes the track, `--color-focus-ring` exists.
- `epub-reader-arrows` (and the full-screen set): `ShortcutsProvider` treats any focused `INPUT` as editing, and neither set is `editingOnly: false`, so a focused slider's arrows move the thumb only; no double handling. Unchanged by HEAD.
- `data-player-scrub` on the row: the input is the only pointer target in the row (track and knob are `pointer-events-none`), and useFullscreen uses `closest()`, so a touch starting on the input still resolves to the row. Touches on the position line below were not exempt before either.
- Tap with no move seeks to the tap point and returns focus (intended). `pointercancel` drops the drag without a seek, as before; `touch-none` makes it rarer.
- Invariant 8: `onScrubbingChange(true)` now starts at `pointerdown` instead of the first `change`; release/cancel/unmount paths unchanged. Invariant 9: `onPointerUp` still `commit(true)` (M20 kills). Invariants 1–7, 10: HEAD does not touch the reader, the hook, sanitizer or the frame; the outer bar keeps `h-10` (24px row + 16px `text-xs` line, `gap-1` removed).
- A non-primary mouse button (right click) also seeks to the point, via `pointerdown`; SeekBar does the same. Not raised further.

## Trajectory

HEAD adds no branch, state or prediction to the release/seek machinery that r1–r4 patched: `drag` stays the bar's only state, `commit`, the held-seek path in `useEpubReader`, `seeking`/`seeked` and the reader are untouched. It adds an input surface (`onPointerDown`/`onPointerMove` feeding the existing `setDrag`) and a drawn track/knob, following SeekBar. fef2d1ae0 only removed a test. So the r4 convergence holds; this is an independent input-surface change. The one thing it does to the old machinery is make an old path reachable: F1 is the r4-noted unanswered-seek path, now reached by a tap on the disabled bar while the book opens. Its fix shape (a guard on `disabled`, M21 stays green) removes a way in rather than adding a state.
