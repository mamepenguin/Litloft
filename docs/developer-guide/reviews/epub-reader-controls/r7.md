## Findings

### F1 [introduced] A value change that is not followed by a value-key keyup in the slider is never committed, and the bar stays stuck on it

With the blur commit gone, `drag` set by the input's `onChange` has exactly one committing exit: a `keyup` of a `VALUE_KEYS` key on the input. Two reachable ways to change the value without that:

(a) Assistive tech. VoiceOver (iOS swipe up/down, macOS increment) and TalkBack adjust a range through the accessibility increment action, which sets the value and fires `input`/`change` with no key events. Simulated in the harness (focus the input, native value setter + `input`/`change`, then focus moves to the book, then the reader reports a new location 0.3):

| engine | 81d7cfc16~1 | 81d7cfc16 |
|---|---|---|
| Chromium | `scrub true | scrub false | seek 0.5`, line shows 30% + pages left | `scrub true`, no seek; line stuck at `50%` + chapterAt label, no pages left, although the book moved to 0.3 |
| WebKit | same as Chromium parent | same as Chromium head |
| Firefox | no seek (iframe focus did not blur the input in this harness) | no seek |

(b) Keyboard: hold ArrowRight (auto-repeat moves the value), press Tab, release ArrowRight — the keyup lands on the next element. Chromium/WebKit parent: `… scrub false | seek 0.105`; head: `scrub true ×5`, no seek, line stuck at `10%` with the drag label and no page count. (Firefox's Tab did not leave the input here, so both commit.)

What the user sees at 81d7cfc16: the seek never happens; the bar keeps showing the uncommitted value (`shown = drag`) and stops following the book as pages turn; the page count is hidden. In full screen `onScrubbingChange(true)` is never answered, so the chrome is held up indefinitely — invariant 8 says the chrome "hides again normally once the drag ends", and this drag never ends. Recovery only by a later value keyup on the slider (which then commits the stale value plus the new step), a pointer press on the row, or leaving full screen (value dropped). No test drives either path (no test sends `change` without a keyup and then leaves).

Answer to the brief's question: no, a change without keyup is never committed at 81d7cfc16. Bucket: A if the supervisor reads invariant 8 as covering a keyboard/AT adjustment of the slider; otherwise B that a user can hit (screen-reader users cannot seek at all on iOS/Android), which is grounds for an invariant revision.

### F2 [introduced] The new "keyboard left focused" test forbids any blur commit, using a blur no browser now sends

`a pointer drag on a slider the keyboard left focused follows the pointer and seeks once` fires `blur` on the input after `pointerDown`, labelled "what a browser does with focus on a press that is not prevented". The press is now prevented, and measured in all three engines the input keeps focus during the press (`held active=INPUT`, harness scenario D). So the step simulates an event that cannot occur, and what the test actually holds is "blur never commits" (M2 kills it). That is the exact property behind F1: any fix that restores a commit on focus leaving will fail this test even though it would not reintroduce r6 F1 in a real browser. B (test models an impossible sequence); relevant to how F1 is fixed.

The pointer side of the bar is converging: every r6 pointer finding is gone, and all pointer-side mutations now kill.

But the removed branch was also the only backstop for the keyboard/AT side, which rests on a prediction that has been there since before r4: every `change` is followed by a value-key `keyup` on the input. F1 is that prediction failing. The obvious fix re-adds an exit for the same `drag` (a guarded blur commit, or committing non-key changes immediately), i.e. the next round would put back, in another shape, the branch this round removed. If it does, that is oscillation on the commit exits rather than convergence; the shape that would remove the prediction instead is committing a change that no key is holding (e.g. commit in `onChange` unless a value key is down), leaving `drag` only for the pointer.
