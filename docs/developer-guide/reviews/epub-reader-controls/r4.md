## Q2: what did it break?

Nothing user-reachable that I could reproduce. Each path the brief named:

- **A seek the reader never answers.** The hook's hold now has exactly two exits: the matching `seeked`, and the per-file reset. Nothing else releases it — later `location` messages do not (scratch R4G: seek to 0.7 unanswered, then locations 0.2 and 0.3 → slider stays 700, page count hidden). That is the design, so what matters is whether a seek can go unanswered:
  - `!state.ready`: the bar is disabled until the first `location`, and the reader only posts `location` after `state.ready = true`. Not reachable from the bar.
  - `isValidSeek`: the hook always sends a finite fraction in [0, 1] (`drag / 1000`) and a positive integer id. Not reachable.
  - Superseded pending seek: only a newer seek replaces `state.pendingSeek`, and the hook's hold is always the newest id, so an unanswered superseded seek is never the one being held. OK.
  - The seek's own move throwing: `.finally` still answers, `.catch` swallows. OK (mutation R2 is the only thing that would change this; no test reaches it, see table).
  - **Another move throwing while a seek is pending** [pre-existing shape]: `turn()` rethrows before `if (state.pendingSeek !== null) runPendingSeek()`, so the pending seek is neither run nor answered until the next turn, which then runs it. At 4ab06cdf3 this left the thumb on the real page; at HEAD it pins the thumb on the target until that next turn. I could not find a way to make a move throw in the vendored foliate: `View.goTo` catches, section-load failures are caught in `#goTo` and become `{}`, and `next`/`prev` go through `#turnPage`, which awaits only scroll promises. Recorded, not counted.
- **The answer arriving before the last `location`.** The paginator dispatches `relocate` synchronously inside `#scrollTo` → `#afterScroll` (non-scrolled layout; the debounced scroll handler only acts when `this.scrolled`), and the reader posts `location` from that handler, so every `location` of a seek precedes its `seeked`. The e2e "after the place it moved to is reported" holds this and alone kills R4.
- **Reader reload / remount.** The iframe and the hook's reset are both keyed on the file id; a late `seeked` from the removed frame fails `parseReaderMessage`'s source check. `seekIdRef` is not reset per book, so ids stay unique across books in one hook anyway. OK.
- **Full screen during a seek** (R4F): the hold is in the hook, so the full-screen bar mounts showing the target and releases on the answer. Better than 4ab06cdf3, where the swap dropped `released`.
- **`scrubbing` with keyed bars.** Changing file mid-drag now unmounts the bar, whose cleanup reports `false`; the drag does not carry into the next book (K1, and the mid-drag row of the new `it.each`). Invariant 8's full-screen exit path is the same unmount cleanup as before, unchanged.
- **One render with the previous book's place** after a file change, before the reset effect runs: same as `location` before this commit (and the unkeyed bar before it). Not introduced.

Invariants 1–10: `onSeek` is still called once per commit with the same fraction; the reader's `turn` and `turned` path is untouched (e2e "reports one turn, and lands where opening at the same fraction lands" passes in both engines — invariants 2, 3); `seeked` carries only an integer and writes nothing (1); no markup or href crosses (4); TOC handling, sanitizer, CSP, layout and full-screen re-layout are untouched (5, 6, 7, 10); `focusBook` on pointer commit is unchanged (9).

## Findings

### Finding 1: nothing holds that a `seeked` answers the seek it names; the "several seeks" e2e never supersedes one

- Label: [introduced] (test and reader code this commit creates).
- Invariant: none of 1–10. Bucket B by the list; it is a test that would let r3 Finding 4 come back.
- Mutation R7 (reader remembers the last received id and answers every seek with it) **survives** the e2e seek set (`-g seek`, 12 tests × chromium and webkit); `reader.js` is not loaded by the unit suite. Under R7, when seek B arrives while seek A is running, A's answer carries B's id, the hook releases B's hold on A's landing, and the thumb jumps to A's place and then to B's — r3 F4 again. The hook-side test ("the answer to an earlier seek does not release a later one") holds the hook only; it feeds ids by hand.
- The e2e "the last of several seeks sent together is answered" asserts `toContain(3)`. Logging the ids at HEAD: `[1,2,3]` in 6 of 6 runs (both engines, three runs) — every seek ran on its own, none was superseded, so the test never exercises the path the reader comment describes ("only the latest one is kept") — a seek arriving while another is running. Deleting it leaves no mutation alive that it alone kills (R1 and R5 are also killed by the other two tests).
- Scratch: adding `expect(new Set(ids).size).toBe(ids.length)` after the poll passed 6/6 at HEAD and killed R7. It is timing-dependent (it relies on some overlap happening under R7), so it is evidence, not the fix. What would hold it is a case where one seek arrives while another is still running (e.g. A into a section not yet loaded) with the answers asserted as exactly `[A, B]`.

## Q4: trajectory

Fix diffs in order, on the bar / hook / reader seek path:

- b2e05761f (r1): added an exit to the bar's mirrored `scrubbing` (unmount cleanup through a ref).
- 1498e5204: test wait only.
- cf4fb2e74: layout only.
- 4ab06cdf3 (r2 → r3): added a state in the bar (`released`) and a prediction ("the seek is answered when the reported fraction differs from the one at release").
- dc7ff6a32 (this): **removes** `released`, `landing`, `pending` and the `from === fraction` prediction from the bar. What it adds is not another case of the same kind: the reader states the answer (`seeked {id}`, unconditional, in `.finally`) instead of the bar inferring it, and the one piece of state (`seeking`) sits in the hook next to `location`, cleared by the reset the hook already had for every other per-book field. The three `seeking !== null ?` derivations in `EpubPreview` read one state; they do not handle a new case each. The file-change leak r2 and r3 each found is closed by keys, not by another exit.
- 1b62bd5cd: test only (and it is what makes K1 killable).

Does dc7ff6a32 add a branch, state or prediction of the kind the rounds before added? No: it replaces a predicted answer with a reported one and deletes the bar's lifecycle state. The only lifecycle handling left in the bar is b2e05761f's unmount exit for `scrubbing`, which still has a job (leaving full screen mid-drag) and now also covers the keyed remount. The loop is converging. What remains open (Finding 1) is a test for the protocol's own pairing, not a new case in the design.
