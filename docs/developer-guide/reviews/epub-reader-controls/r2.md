## Finding 1: the activity e2e's inline half still usually passes whatever the full-screen guard says, because the reader's pointer throttle swallows the inline moves

- Label: [introduced]. The move-count probe is code 56613405e creates. At eab502825 M51 was deterministically LIVE (r1). Now it is killed only intermittently.
- Invariant: none (reporting pointer activity inline is harmless; r1 F5 asked for this to be held because the test claims it).
- What I did: applied M51 (`if (e.pointerType === "touch") return;` in `installPointer`, i.e. drop `!state.fullscreen`) and ran `-g "activity" --repeat-each 6`. Result: **4 failed / 8 passed** of 12.
- Why: `state.lastPointerActivity` starts at 0 and `POINTER_ACTIVITY_MS` is 250. Measured the reader iframe's `performance.now()` at the first `page.mouse.move` right after `ready`: 179, 121, 122, 113 (Chromium) and 122, 95, 54, 60 (WebKit). It is always under 250, so the throttle drops every inline move no matter what the guard does. The new probe proves the moves reach the book (6 counted, `pointerType: "mouse"`, handler called 6 times), but not that the reader would have reported them. The full-screen half works only because it follows a 300 ms wait.
- Reproduction of the fix: a scratch copy of the test (not in the tree, since deleted) with `await page.waitForTimeout(300)` before the inline moves. Under M51: **12/12 failed**. Unmutated control: **12/12 passed**.
- Direction: let the reader's clock pass `POINTER_ACTIVITY_MS` before the inline moves, e.g. the same 300 ms wait the full-screen half already uses, or a wait on the reader window's `performance.now() > 250`.

## Q3: trajectory

There is one fix round so far, so no two consecutive fix rounds exist to compare. What 56613405e adds:

- **One new path for existing state:** the unmount cleanup is a third way to clear `scrubbing`, beside commit and `pointercancel`. It handles a lifecycle case the first design did not anticipate. The reason one was needed is that `EpubPreview.scrubbing` mirrors the bar's own `drag !== null` in a second component, so every way the bar can lose its drag must also be reported upward. If a later round adds another such exit (for example, file change mid-drag, which currently keeps the unkeyed bar's `drag`), that is the pattern the rule names. The shape that ends it is to derive the hold from the mounted bar rather than mirror it.
- **No new branch or prediction in `parseToc`:** the same three checks now return a blank instead of `continue`. The drop-accumulation loop goes away, which counts as convergence.
- Everything else is tests and a fixture.

Answer: no. This round does not repeat an addition from a previous fix round. The one watch item is the mirrored `scrubbing` state.
