### F2 [pre-existing] Paths that do not arrive as an unmodified arrow keydown still take r8 F1's route: a 1/1000 step, a seek to the page shown, and the thumb returns

834ad8805 changes only the keydown path; `onChange` is untouched, so anything that moves the native value by one step still seeks 1/1000 and snaps back.

- Modified arrows, measured (ltr book, from 0 %): Shift/Alt/Ctrl/Meta+ArrowRight each sent `seek 0.001` in Chromium and WebKit (`S:1 S:1 S:1 S:1`), value stayed 0. Harmless (no place lost; the one `turned` written was the page actually shown), but "left to the browser" means left to a no-op.
- A screen reader's increment on a native range (VoiceOver iOS swipe up/down, TalkBack) is, as far as I know, an accessibility value action, not a keydown, so it reaches `onChange` with the input's `step` (1/1000) and would snap back the same way. **Not measured** (no device/AT here); r8 already flagged this as unmeasured. Desktop screen readers in focus/interaction mode pass arrow keydowns through, so those now turn pages; Up = next / Down = prev matches a slider's increase/decrease.

Pre-existing: at 834ad8805~1 every arrow, modified or not, took this route (r8 F1); the commit narrows it, it adds none. Recorded so the supervisor can decide whether AT stepping is R-5 device work. A fix that detects "a one-step change" and turns it into a turn would be a new prediction (see Trajectory).

- **Focus** stays on the slider after every key in every scenario (invariant 9's pointer path untouched: `commit` unchanged).
- **Home/End/PageUp/PageDown** still seek: PageUp 0 -> 100 -> 199, PageDown -> 99, End -> 999 (ltr) / 969-970 (rtl, last page), Home -> 0; one `turned` each. (PageDown decreases a range's value, as native ranges do; unchanged.)
- **Invariant 2**: seek paths unchanged. A turn writes `turned` through the same reader `turn()` as a turn over the book.
- **Invariants 1, 3-7, 10**: reader, sanitizer, layout untouched; the keydown handler writes no state.
- **Invariant 8**: the keydown handler never touches `drag`, so `onScrubbingChange` is not called from a key. An arrow during a held pointer drag turns a page under the drag; the release then seeks the drag target (M14 live as declared; last wins).
- **Invariant 11**: a disabled input cannot be focused, so no keydown reaches it.
- **Full-screen chrome**: keydown on the slider shows the chrome (capture listener). When the chrome idles out it becomes `inert`, focus leaves the slider, and arrows then go to the full-screen shortcut set; pre-existing, one turn per press either way.

## Trajectory

Fix rounds since r4, what each did to the bar:
- fef2d1ae0: tests only.
- 3f567baab: value from position on the row, pointer capture, drawn track/knob - added a second writer.
- f4c34c1a5: input takes no pointer (removed the native writer); added a disabled guard and a drag-start gate.
- 81d7cfc16: removed the blur exit.
- e7addd813: removed the keyup exit, `VALUE_KEYS`, `byPointer`; `drag` pointer-only.
- 834ad8805: **adds a branch** (a keydown handler with a key table and a modifier guard) and a prop (`onTurn`). **No state, no prediction**: it does not model timing, key release or the reader's answer; it reuses the reader's existing `turn` command.

It is not two additive rounds in a row (e7addd813 removed), and the branch is a mapping the user chose rather than one more case of the drag machinery; the drag state is unchanged from r8 (one writer, one exit). The keyboard side went from "a local hold with exits" (r7) through "no local state" (r8) to "arrows are commands, everything else seeks" - a stateless split, not a patch.

What would mark patching next: a round that makes AT increments or modified arrows (F2) turn pages by recognising "a one-step change" or "a change with no keydown before it" - that is a prediction about which writer moved the value, the shape r3 found. Bucket A is empty; the reviewer's view is that the bar has converged and this is a reasonable place for the supervisor to stop, with F2's AT half left to an R-5 device check.
