## Q1: did it fix the jump?

For the case the user hit — a release whose seek lands on a *different* fraction, with no second drag before the answer — yes:
the thumb stays at the release point until the reader reports the new place (the new test, and R3 scratch runs agree).

What it broke comes from one fact: `landing` is decided by `released.from === fraction`, and `released` is never cleared.
"The reader has answered" is inferred from "the fraction changed", and that inference is wrong in both directions.

## Finding 1: a release that lands on the page already shown leaves the thumb at the release point and hides the page count until the next page turn

- Label: [introduced]. Reproduced at 4ab06cdf3, passes at 8c08c23d4.
- Invariant: none of 1–10 (they cover the reader's landing and WatchHistory, not the thumb). Bucket B by the list, but user-reachable and common.
- `reader.js` reports the start fraction of the page shown (`startFraction`). Any seek whose target falls inside the current page lands on the same page, reports the same fraction (or, if foliate does not relocate, nothing at all), so `released.from === fraction` stays true.
- Reach: a keyboard step on the slider is one step of 1000; in any book with fewer than ~1000 pages that is nearly always inside the current page. A short drag does the same. In a short book a page spans many steps.
- Observed (R3A, pointer 100 → 102, reader re-reports 0.1): slider value 102, and "left in chapter" is gone. R3C (keyboard ArrowRight, 100 → 101): slider 101, page count gone. Both pass at the parent.
- Stays that way until a page turn changes the fraction.

## Finding 2: turning back to the page the drag started from snaps the thumb back to the old release point

- Label: [introduced]. Reproduced at 4ab06cdf3, passes at 8c08c23d4.
- Invariant: none of 1–10; B by the list, but it shows a wrong place and chapter to the user.
- `released` survives the answer. Whenever the reader later reports `fraction === released.from` again, `landing` becomes `released.to` again.
- Reach: small drag forward one or two pages, then PageUp back to where you were (startFraction is deterministic for the same page, so the value is exactly equal); or follow an in-book link and come back.
- Observed (R3B): at 0.1, drag to 700, reader answers 0.68 (thumb 680, correct), reader then reports 0.1 → slider shows **700**, the label says "Two" (chapterAt(0.7)) while the page is in "Cover", and the page count is hidden. At the parent: 100 / Cover / page count.

## Finding 3: another book that opens at the same fraction shows the previous book's release point

- Label: [introduced]. Reproduced at 4ab06cdf3, passes at 8c08c23d4.
- Invariant: none of 1–10 directly; it is the same leak r2 flagged for `drag` (the bar is not keyed per file), now carried by `released` too. The existing test "another book starts with no place and no chapter from the last one" does not see it because it only checks before the new book reports.
- Observed (R3D): book A at 0, drag to 700 and release, move to book B before A answers (or after Finding 1 left A stuck), B reports fraction 0 → B's slider shows **700**, 70%, B's chapter at 0.7, no page count. Fraction 0 is the likeliest collision: every unopened book reports 0.
- Moving to another book never unmounts the bar (`FilePreview` / `EpubPreview` are not keyed by file id; only the iframe is).

## Finding 4: a second drag released before the first seek's answer still jumps, now to the first target

- The reader keeps only the latest pending seek while turning, but a seek already started still posts its `location`.

## Q3: trajectory

Diffs to the bar and its host, in order:

- b2e05761f (r1 fix): a third exit for the mirrored `scrubbing` state (unmount cleanup via a ref) — handling for a drag lifecycle case the first design did not anticipate.
- cf4fb2e74: layout only; no branch, state or prediction.
- 4ab06cdf3 (this one): a new state (`released`) and a **prediction** — "the reader has answered the seek when it reports a fraction different from the one at release".

Not two consecutive rounds by the letter (cf4fb2e74 sits between and adds nothing). But on the bar's drag → seek → answer lifecycle, yes, the state is being patched: every fix round on it has added a piece of state or an exit describing the same interaction from the bar's side (`drag`, then its mirror `scrubbing` plus a third exit, now `released` plus a guess about the reader). Findings 1–3 are that guess failing, and each obvious local repair adds another branch of the same kind: clear `released` on "any" location (but a same-page seek may post none — `turn()` posts `turned` only when `locationKey` changed, and nothing answers a seek as such), reset on file change (another exit, as r2 predicted for `drag`), handle an overlapping second release. That is the "one more case each round" shape.

The shape that removes it: make the answer explicit instead of inferred, and hold it where the file's state already lives.
- The reader answers every `seek` once it finishes, whether or not the page changed (e.g. post `location` unconditionally at the end of a seek's `turn`, or echo a seek id).
- `useEpubReader` keeps the pending target (set in `seek`, cleared by that answer, cleared with the rest of its state on a new file) and exposes the fraction to show as `pending ?? location.fraction`.
- The bar then keeps only its live `drag`, and renders the `fraction` it is given. `released`, the `from` comparison and the cross-book leak all go; per r2, keying the bar by file id (or deriving the hold from it) would do the same for `drag`/`scrubbing`.
