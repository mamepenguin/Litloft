## Findings

### F1 [introduced] Holding an arrow key on the slider no longer moves the place: each repeat seeks one step, the reader answers before the next repeat, and the thumb returns to the page it was on

At e7addd813 every `input` event seeks. An arrow key moves the range by one step (1/1000). A step forward from a page start lands on the page already shown; the reader answers `seeked`, the hook drops `seeking`, the controlled value goes back to the page start, and the next repeat steps from there again. At e7addd813~1 the repeats accumulated in `drag` and one seek went out on keyup, so a held arrow moved through the book.

Running app, focus on the slider at 0 %, ArrowRight held for ~1.5 s (45 repeats, 33 ms apart), released:

| engine | seeks sent | values during the hold | end |
|---|---|---|---|
| Chromium | 46, every one `0.001` | `1` each sample, back to 0 after each answer | 0 %, "3 pages left" |
| WebKit | 46, every one `0.001` | same | 0 % |

Harness, both versions, reader answering in 5 ms, ArrowRight held for 30 repeats from 0.300:

| engine | e7addd813~1 | e7addd813 |
|---|---|---|
| Chromium | 1 seek `0.331`, thumb 302→331, lands 0.320 | 31 seeks all `0.301`, values `301,300`, ends 0.300 |
| WebKit | same as Chromium parent | same as Chromium head |
| Firefox | same as Chromium parent | same as Chromium head |

The result depends on the reader's answer time against the key-repeat interval: with the stand-in reader at 30 ms the head is stuck; at 45 ms and 100 ms the head moves like the parent (31 seeks, each a step further, monotonic, no jitter). The real reader answers a same-page seek inside one repeat interval in both engines measured, so in the app the thumb is stuck.

What still moves: PageUp/PageDown (10 % per press; held PageUp sends one seek per repeat, 6 instead of 1, all landing), Home, End. Arrow keys forward do nothing; ArrowLeft goes back at most one page (measured in the app: from 10 %, four ArrowLeft presses seek 0.099, 0.098, 0.098, 0.098 and stay at 9.9 %).

A single arrow press being swallowed is [pre-existing]: at e7addd813~1 one press committed one step on keyup and snapped back the same way (harness `rtlLeft`, both versions identical). What this commit removes is the only way the arrow keys moved the place, holding them. The same mechanism applies to an assistive-technology increment if the AT steps by the input's `step` (1/1000); which step VoiceOver/TalkBack use on this input was not measured.

Invariants: none of 1–11 names keyboard scrubbing, so B that a user can hit (keyboard-only and screen-reader readers). Grounds for an invariant revision if the supervisor wants the keyboard path held.

Not in the snapshot tests: every keyboard test fires a single `change`; nothing sends a sequence of changes with `seeked` answers in between.

### F2 [pre-existing] No test drives the keyboard path in a right-to-left book

M5 (onChange seeks `1 - value` when `dir === "rtl"`) survives: the rtl tests use the pointer on the row or check only the `dir` attribute. At e7addd813~1 the same line was `setDrag(Number(e.target.value))` and also had no rtl keyboard test. Measured behaviour is right at head: the native value is logical, and WebKit's ArrowLeft in an rtl range decreases it (Chromium/Firefox increase it); head and parent identical in all three engines. B.

## Checked, nothing found

- Invariant 1: a React controlled value update does not fire `onChange`. Harness `external`: the parent's location moved twice (0.5, 0.62) with the slider focused; 0 seeks in all three engines, both versions. The input is `disabled` while `fraction` is null, so no change can come before the book is open.
- Invariant 2: reader unchanged; each seek that turns posts one `turned`. A held PageDown now sends one seek per repeat; the reader keeps only the latest pending seek, and `useEpubProgress.turned` restarts its 1 s debounce on each, so a burst writes WatchHistory once at the end. Repeated writes in a longer burst would be ordinary progress saves of pages actually shown, last one wins; not harmful.
- Seeks in flight: the hook's `seeking` is replaced on every seek and cleared only by the latest id, so while repeats are unanswered the thumb shows the latest target and does not go back (harness LAT 45/100: values strictly increasing). The only go-back is the answered case in F1. Superseded pending seeks are never answered; the hook does not wait on them.
- Invariant 8: a keyboard change no longer touches `drag`, so `onScrubbingChange` is never called from the keyboard (harness log empty for every key scenario at head; the parent logged `scrub true` per repeat). The new full-screen test kills M1.
- Invariant 9: pointer release still calls `onPointerCommit`; M8 kills. A keyboard change does not move focus (M3 kills).
- Invariant 11: a disabled input fires no change; the row's disabled guard is unchanged.
- Keyboard change during a held pointer drag (slider focused, mouse held on the row, arrow pressed): seeks the input's value at once and the release seeks the drag again; two seeks, last wins. Reachable only with both at once; harmless (M6, M7 live).
- Invariants 3–7, 10: reader, sanitizer, layout untouched by this commit.

## Trajectory

Fix rounds in order, with what each did to the bar's commit/hold machinery:
- fef2d1ae0: test-only.
- 3f567baab: added value-from-position on the row, pointer capture, drawn track/knob (a second writer of the value: added).
- f4c34c1a5: input takes no pointer; disabled guard; drag-start gate (removed the native second writer, added two guards).
- 81d7cfc16: removed the blur exit; one `preventDefault`.
- e7addd813: removed the keyup exit, `VALUE_KEYS` and the `byPointer` parameter; the prediction "every keyboard change ends in a value-key keyup" is gone; `drag` is now pointer-only.

e7addd813 removes a branch, a set and a prediction and adds none. The last two rounds each removed an exit, so the drag state has shrunk to one writer (the row) and one exit (release, cancel, unmount). On the pointer side the bar is converging.

F1 is what the removal cost, not a patch shape: the keyboard path now has no local state at all, and its displayed value comes back from the reader's page quantization after every step. The fixes that suggest themselves re-add a keyboard hold (a timer, a keydown/keyup pair, a "value key is down" flag) — i.e. the state or the prediction this round removed. If the next round does that, it is oscillation between r7 F1 and r8 F1 rather than convergence. Shapes that do not re-add state exist (e.g. a keyboard step no smaller than a page, or treating the keys as page turns), but choosing is the supervisor's; the reviewer does not assign C.
