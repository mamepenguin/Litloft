## Findings

### F1 [introduced] With the slider focused from the keyboard, a mouse drag on the row seeks to the press point, ignores the drag, and releases the full-screen chrome while the button is still held

Bucket proposal: user-reachable; touches invariant 8 ("the chrome stays up while the slider is dragged"). The supervisor assigns.

- Path: the input keeps focus after a keyboard adjustment (`commit(false)` does not hand focus back). A mouse press now lands on the row, which is not focusable, so the browser's mousedown default moves focus to body and blurs the input. Order: `pointerdown` → row `dragTo` sets `drag` (flushed, discrete event) → `mousedown` → input `blur` → `onBlur` → `commit(false)` seeks to the press point and sets `drag = null`, `onScrubbingChange(false)`. Every following `pointermove` is dropped by the new `drag !== null` guard, and `pointerup` → `commit(true)` finds `drag === null`, so no seek and no `focusBook`. Focus ends on BODY.
- At 3f567baab the press landed on the (already focused) input, so no blur, and the drag completed normally.
- Measured in real browsers (Playwright, Chromium / WebKit / Firefox; the real `EpubPositionBar` from each commit bundled with esbuild into a bare page with an iframe standing in for the book, `onSeek` logging; harness in the scratchpad, not in the tree). Scenario: focus the input, ArrowRight (keyup commits 0.101), then mouse down at 80 % of the row, move to 20 %, release:
  - f4c34c1a5: all three engines log `scrub true | scrub false | seek 0.8` (0.798 in WebKit/Firefox) and nothing after; active element BODY.
  - 3f567baab: Chromium/Firefox `… seek 0.181 | focusBook | … seek 0.181` (the r5 F2 double seek), WebKit `seek 0.806` then `seek 0.199 | focusBook`; drag followed in all three; active element the book iframe.
- Consequences: the book jumps to where the mouse went down, the drag has no effect, the release does not return keys to the book (body is still in scope for `epub-reader-arrows`, so the arrows turn pages from the parent; invariant 9 holds). In full screen `onScrubbingChange(false)` fires at the press, so the idle timer can hide the chrome while the button is held — invariant 8 by the user's view, though the bar itself no longer thinks it is dragging.
- Shape note (not a fix): this is the same "second writer" the commit set out to remove — the input's `onBlur` commit is still reachable from a pointer interaction, through the focus change the pointer causes.
- No test holds it: jsdom's `fireEvent.pointerDown` does not run mousedown focus.

### F2 [introduced] A touch tap on the row leaves focus on the page body, not in the book, so Space no longer turns pages afterwards

Bucket proposal: touches invariant 9 for Space only; reachable with a hardware keyboard on a touch device (iPad with keyboard, touchscreen laptop). Emulated, not measured on a device.

- A touch tap (no movement) is followed by compatibility mouse events after `pointerup`. `pointerup` → `commit(true)` → `focusBook()` focuses the iframe, then the compat `mousedown` lands on the row (non-focusable) and moves focus to body.
- Measured (same harness, Playwright `touchscreen.tap` at 70 %): f4c34c1a5 ends with `document.activeElement` = BODY in Chromium, WebKit and Firefox. 3f567baab ends with the iframe focused in Chromium and Firefox (WebKit at the parent did not seek on a tap at all, so it is not a comparison).
- A touch *drag* is unaffected (no compat mouse events; measured via CDP touch in Chromium: focus ends in the iframe at both commits). A mouse click is unaffected (mousedown precedes pointerup, so `focusBook` wins; measured, all three engines).
- With body focused, `epub-reader-arrows` (body counts as in scope) and `epub-reader` (PageUp/PageDown) still turn pages from the parent, so the arrows and Page keys hold. Space (`keyAction` in `public/epub-reader/core.js`: `" "` → next / shift → prev) is handled only inside the reader, so after a tap it reaches the parent page instead. In full screen the same: `epub-reader-fullscreen` has no Space binding.
- No test holds it (jsdom does not run compat mouse events or mousedown focus).

### F3 [introduced] The device fix itself is held by no test: letting the input take pointers again survives

B (test gap). M7 (`pointer-events-none` removed from the input and `z-10` restored, so the invisible native range is again the pointer target and the second writer is back) passes all 46 tests. The row tests dispatch straight to the row, and five older tests dispatch `pointerUp` on the input, which reaches the row's handler by React bubbling although no real pointer can hit the input any more. jsdom does no hit testing; the property is measurable in a real browser (e.g. `elementFromPoint` at the row's centre is the row, not the input), and `frontend/e2e-layout/` runs real boxes in CI. Whether that is worth a detector is the supervisor's call; iOS's own behaviour is not reproducible in Chromium in any case.

### F4 [pre-existing] Invariant 8's tests start the drag with `change` on the input, so a row drag that never reports scrubbing survives

B (test gap). M8 (`dragTo` calls `setDragState` instead of `setDrag`, so a pointer drag never calls `onScrubbingChange(true)` and in full screen the chrome can hide mid-drag) passes at f4c34c1a5 and also at 3f567baab (same mutation run against the parent's component and test file: 44/44 pass), so it is not introduced. What f4c34c1a5 changes is its reach: at the parent a mouse drag still went through the native `change`, so only touch lost the hold; now every pointer drag goes through `dragTo`, and `change` is reachable only from keys and assistive tech. "in full screen, the bar stays up while the slider is dragged…" and "a drag cut short by leaving full screen…" both drive `fireEvent.change(slider())`, a path no pointer takes now.

### F5 [pre-existing] r5 F2 (two seeks per release) is narrowed, not removed: a touch drag while the slider holds keyboard focus still sends two

Measured (CDP touch drag in Chromium, input focused by keyboard first): f4c34c1a5 logs `seek 0.2 | focusBook | scrub false | seek 0.2`; 3f567baab the same shape (`seek 0.181 | focusBook | … seek 0.181`). Without prior keyboard focus there is one seek at f4c34c1a5 in all measured cases (at the parent, Chromium/Firefox mouse drags sent two). So the commit removed the common path; the remaining one needs keyboard focus and a touch drag. `commit(true)` → `focusBook` blurs the input synchronously and the rendered `onBlur` still closes over the old `drag`.

## Trajectory

The r1–r4 rounds patched the release/seek state (copied `scrubbing`, a third exit, a guessed `released` landing), and the r3 reshape removed that state and prediction; r4 confirmed convergence. Neither 3f567baab nor f4c34c1a5 touches that machinery: `drag` is still the bar's only state, `commit`, `seeking`/`seeked`, the hook and the reader are unchanged.

f4c34c1a5 removes a writer: the native range no longer takes pointers, so `onChange` is fed only by keys and assistive tech, and r5 F2/F4 mostly go with it. It adds two conditions, `if (disabled) return` and `drag !== null` on move. Both put back something the native control used to do itself (ignore input while disabled; only follow a press that started on it), rather than predicting anything about the reader.

But there is a second trajectory. 3f567baab and f4c34c1a5 each move one more native-range behaviour onto hand-written code on the row (r5: value from position, drawn track and knob, capture; r6: disabled handling, drag-start gating, cursor, `touch-none`). F1 and F2 are the next two native behaviours this lost (focus on press; where focus lands after a tap), and fixing them would most likely add focus handling on the row. Each of these rounds adds a branch that makes up for a behaviour the previous round took off the input. The supervisor should decide whether that is converging on a SeekBar-style custom slider (a finite list: disabled, capture, focus) or the design being patched. The reviewer does not assign C. The input's `onBlur` commit is the one path that still lets a pointer interaction write the value through the native control, and it causes both F1 and F5.
