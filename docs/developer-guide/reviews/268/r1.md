## F1 [introduced] B (proposed) — `AddButton.bundledRows.test.tsx` first case waits for one lazy row and asserts on both; it fails under a loaded run on the unmutated SHA

Detector rule 3 ("wait for the thing you assert on"). `SlotEntryRenderer` loads each entry's addon module independently (`loadAddonSlotModule` per `addonName`, then a per-entry `Suspense` around a `React.lazy`), so "New note" (knowledge) resolving says nothing about "Import from URL" (media_import). The first case awaits only `New note` and then asserts the exact five-row list. It is also the first case in the file, the only one that runs with both module caches cold.

Reproduction, unmutated tree at 18492e45, no edits: running this file together with the 48 other test files that touch AddButton / FolderBrowser / FolderContent / FolderTreePane / DriveHome / FileSaveDialog / useCreateFile plus the two addons' row tests (`pnpm vitest run <49 files>`, pool=forks, ~6 s wall) failed on both unmutated runs, and again in every one of the ~35 batched mutation runs below, always this case and always the same diff:

```
FAIL  src/components/__tests__/AddButton.bundledRows.test.tsx > ... > offers exactly one note row, the addon's, after the core rows
- Expected + Received
  [ "Files", "Folder", "New Folder", -  "Import from URL",  "New note" ]
 ❯ AddButton.bundledRows.test.tsx:79:20
```

The same file alone passed 3/3. So it is a load-dependent false red, not a product defect; it breaks no R-0 invariant, but a CI worker under load (or `pnpm test` over the whole tree) can turn the PR red for nothing, and a reader "fixing" it by loosening the list would lose the exact-order detector.

Same shape in the `hides the row once %s settles to off` cases (wait for the other row, assert the off row absent). Measured, not assumed: with the policy gate removed from each row (M8a/M8b) and the case run alone (`-t`, cold caches), the case still failed 1/1 and 3/3, so today the absence assertion is not vacuous in practice; it rests on both modules resolving in the same tick, the property the first case shows does not hold under load.

Suggested remedy: wait for both rows (e.g. `await waitFor(() => expect(rows()).toEqual([...]))`), and in the policy cases await something that proves the off row's own module resolved.
