## Findings

### F1 — A — [introduced] — invariant 5 — tests/test_configure_presentation.py:137-149 (condition at configure.py:387)
The summary-note test only covers "both declined" (`all_declined`) and "both enabled" (`all_enabled`). The mixed cases are never run. So M13 (`bundled and not has_intelligence`), M14 (`bundled and not has_knowledge`) and M25 (a note printed when only intelligence is on) all pass the suite. Each breaks "when either is enabled it does not".
Reproduction: apply M13 or M14 → 39 passed.
The code at HEAD is correct: a direct run with intelligence n / knowledge y prints no note, and intelligence y / knowledge n prints none either. The gap is only that no test holds it. The test is new, so no parent run is needed. Fix: add the two mixed rows to the parametrize table.

### F2 — B — [introduced] — configure.py:272
`and any(d.iterdir())` cannot change the result, because `(d / 'backend').is_dir()` already implies `d` is non-empty (M9 inert). `d.is_dir()` is inert for the same kind of reason (M12). Also, `ensure_submodules_initialized` runs first and fills or exits on an empty addon directory. A reader may believe the non-empty check matters and "fix" around it. Deleting it changes nothing observable.

### F3 — B — [introduced] — tests/test_configure_presentation.py:131
The ordering assertion `listed == ["- cloud-sync", "- media_import"]` does not hold `sorted()` on macOS/APFS. Removing the sort (M10a) passes, because `iterdir()` already returns this pair in name order. On CI's ext4 the directory order is hash-based, so the same mutation may or may not be killed. Invariant 3 does not require an order, so this is not an A. If the order is meant to be held, add a bundled addon whose name sorts first but whose directory is created last (for example `aaa`, created after the others).

### F4 — B — [introduced] — configure.py:369
No test holds "no Bundled addons heading when the list is empty": printing the heading unconditionally (M17) passes. Invariant 6 speaks only of entries, so this is B. A user on a tree with no in-process addons would see an empty "Bundled addons" section.

### F5 — B — [introduced] — configure.py:371 and :388; docs/getting-started/installation.md (the Bundled addons paragraph)
Two things are wrong with the new lines. First, they send the user to `/setup` to turn bundled addons off. On a re-run after first-run setup finished, `/setup` no longer applies: `POST /api/admin/complete-setup` returns 409, and per-drive policy is edited at `/admin/settings`. The existing lines at configure.py:286-287 and :378-379 already say "/setup" this way, so this follows local convention; one line only. Second, "turn … off" overstates what the policy does for an in-process addon. Per design-decisions.md (Addons: implementation discipline) its routes keep answering, which the PR's own `docs/addons/overview.md` change says correctly. No code change is implied.

### F6 — B — [pre-existing] — tests/test_configure.py:211, 236, 265, 325
Answers `[..., "3000", "y", "y"]` are commented as "configure intelligence? y, generate? y". In fact the second `"y"` is used as `LLM_API_KEY`, and "Generate files?" gets EOF and takes its default. So these runs write `LLM_API_KEY=y` to `.env`. It is the same at `b4fb89c7`. The assertions still hold, and the default change does not touch it. A reader copying this answer list for a new test would get the prompt order wrong. Suggest deleting the comment.

### F7 — B — [pre-existing] — invariant 3 wording vs configure.py:422-424
"Adding or removing one [bundled addon] changes … no generated file" is not true in general. When `addons/cloud-sync/sync-config.json` exists, the override gains a `sync-config.json` mount line, so removing the cloud-sync checkout changes `docker-compose.override.yml`. The parent does the same, so invariant 4 is intact. The test's `build_tree` never creates `sync-config.json`, which is why it passes.
