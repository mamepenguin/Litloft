### F2. The clip dialog misses its own job's ready/failed event when another WebSocket event lands before React renders it; the suite's `emit()` can never produce that
- Invariant: 10'
- `frontend/ClipWebPageDialog.tsx:50-51, 69-86`; test mock `frontend/__tests__/AddMenuRows.test.tsx:25-45` (`emit` wraps each event in its own `act`)
- Reproduction (scratch test, real core `WebSocketProvider` with a fake `WebSocket`, dialog in the fetching stage for job 7):
  - `act(() => { send("knowledge.clip.ready", {job_id: 7, file_id: "clip7"}); send("files.updated", {...}); })` -> `router.push` called 0 times (expected 1). The dialog stays on "Clipping the page..." indefinitely.
  - same with `knowledge.clip.failed` followed by any event -> no error shown, dialog stays fetching (expected: error, form restored).
  - control: the same two events in two separate `act` calls -> navigates once (passes). Ready arriving before `POST /clips` resolves -> navigates once (passes).
- Why: the provider holds one `lastEvent`; `useWebSocket("knowledge.clip.ready")` returns `null` as soon as a later event of another name replaces it, so if both are committed in one render the effect never sees the ready event. The mock is shaped like the provider (one `wsEvent`), but every test delivers events one render apart, which is the only ordering under which the dialog works. In the browser the two messages are separate tasks; whether React commits between them is scheduler timing, and the core emits file events on the clip's own content write/rename plus any other activity on the drive, so this is reachable but not deterministic — not measured in a real browser.
- Observed vs expected: see above.
- [introduced] (file created by the change; the single-`lastEvent` provider itself is pre-existing)
