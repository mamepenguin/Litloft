## 4. The fold marker is the smallest target in the row and is the one element the new floor does not apply to

**[introduced]** — the marker is new in `bedcdcca`; so is `min-w-12`.
**Breaks: invariant 3** — "Every ancestor segment stays a working link (core) or
button (archive) pointing at the path it names. Shrinking changes what is legible,
never what is reachable." The marker is what five ancestors were replaced by.

### Reproduction

`folder-listing-header-deep` at 375px, measuring each `nav` child's label:

| label | `getBoundingClientRect` | `clientWidth` |
|---|---|---|
| `Household Archive` (ancestor) | 30 × 20 | 30 |
| **`…` (marker)** | **19 × 20** | **19** |
| `Screenshots` (ancestor) | 30 × 20 | 30 |
| `Archived-2026-…` (leaf) | 77 × 20 | 77 |

The spec declares `REACHABLE_PX = 24` — *"A link narrower than this holds no
characters and is not something a finger or a pointer can land on"* — and applies
it with `for (const a of m.ancestors) expect(a.clientWidth).toBeGreaterThan(REACHABLE_PX)`.
`m.ancestors` is `named.filter((el) => el !== leafLabel && el !== marker)`, so the
marker is filtered out of the one assertion written about hit area, and it is the
only element in the row that falls below the threshold.

It is 19px at **every** width, not only at 375: `flex-shrink-0` holds it at the
ellipsis plus `px-1`, so this is its designed size rather than a narrowing.

### Observation it predicts

A reader on a phone can press either surviving ancestor (30px) more easily than the
one control that reaches the five folders between them. Give the marker the same
floor — it is `flex-shrink-0`, so a `min-w-*` costs the trail nothing it was using —
and extend the `REACHABLE_PX` assertion over `m.marker` as well as `m.ancestors`.

## 7. The pixel of slack in `isCut` is not a precaution — one case is passing because of it

**[introduced]** — `isCut`'s `+ 1` and the collection case are both written by
this commit.
**Breaks: none** — the detector, not the behaviour.

### Mutation

`frontend/e2e-components/header-row-crowding.spec.ts:31`

```
-const isCut = (c: Cut) => c.scrollWidth > c.clientWidth + 1;
+const isCut = (c: Cut) => c.scrollWidth > c.clientWidth;
```

`want=live` (if the slack were only a precaution). Result: **1 failed** —
`the file-detail chrome during collection playback at 1024px`, at
`expect(isCut(m.leaf)).toBe(leafCut)` with `leafCut: false`.

Measured on that case: the leaf reports `clientWidth 540 / scrollWidth 541`. The

1024 in the collection case now means "cut by at most one pixel", and any change
costing that leaf two more pixels flips a case that has no margin. Where a case is
meant to say "this fits", it should have room to say it.

### Observation it predicts

allowance by a pixel, and the case passes with or without the slack. Until then the
slack is load-bearing for a case, and the next fixture edit that touches
`DEEP_LEAF` will move it across the line again.

# The trajectory

Read in order: `853c3a14`, `60a4ec5d`, `86df7069`, `bedcdcca` — the code hunks,
not the specs.

**Converging, not being patched** — with one thing named below to watch.

What each round did to the *prediction* about how a row resolves a width deficit:

- `853c3a14` **adds** P1: "give the deficit to the ancestors", as
  `shrink-[999]` applied through `isLast ? "" : TRAIL_ANCESTOR` — a branch
  deciding whether a segment may narrow at all. Two files.
- `60a4ec5d` **adds** P2, elsewhere and about something else: one placement
  (`isMobile && titleNode`) and one basis (`flex-1` → `flex-auto`) in
  `FileDetailChrome`. It does not touch P1.
- `86df7069` **removes** P1's branch: `isLast ? TRAIL_SEGMENT : TRAIL_ANCESTOR`.
  `min-w-0` becomes unconditional and the branch only decides *how eagerly*.
- `bedcdcca` **removes the premise under both of them.** P1 and P2 are guesses
  about how a deficit distributes across an unbounded number of segments; the
  fold makes the number of drawn segments a constant — drive, marker, and one or
  two tail items — whatever the depth. After it, the row's worst case no longer
  depends on the input. That is the opposite shape from a patch: it is the only
  round that made the problem bounded rather than adding a case to an unbounded
  one.

It adds no state. `foldTrail` is a pure function with no React state, no effect
and no ref; `bedcdcca` introduces no new `useState` or `useEffect` anywhere in
the diff.

What it does add, and why I still call it converging:

- `min-w-12` replaces `min-w-0` on the ancestors. This does not re-divide the
  branch `86df7069` collapsed — `isLast ? TRAIL_SEGMENT : TRAIL_ANCESTOR` has
  exactly the same shape and arity as at `86df7069`; one constant's value
  changed. A floor is a bound, in the same direction as the fold.
- `trail.ts` is a new module, but it is 8 lines of logic extracted so that two
  callers cannot drift — the same reason `TRAIL_ANCESTOR` was exported in
  `853c3a14`. Extracting a shared rule is not adding one.

**The one thing to watch**, stated so the next round can test it: `hidden
sm:inline` on the archive's entry count is a width-specific carve-out that exists
*because* this round's own floors made that row over-subscribed at a phone width.
Round 1's finding 7 was closed as B and, by the author's own README, "reopened by
the fold". A round that reopens a closed finding through its own mechanism is the
first half of the pattern R-4 describes. It is one round, not two, and the round
before it removed rather than added — so **not a C**. If round 4's fixes add a
second width-specific carve-out to the same row, that is the second consecutive
adding round and the design question is live.
