## 1. The `isLast` guard in `Breadcrumb.tsx` can be deleted and every suite stays green

**[introduced]** — `Breadcrumb.tsx:79` is a line this change adds.
**Breaks: invariant 1** (the trail's last segment is never clipped to nothing),
for the trail form used by the folder-listing header, trash, missing and
collection detail.

### Mutation

`frontend/src/components/Breadcrumb.tsx:79`

    -  className={`flex items-center gap-1${isLast ? "" : ` ${TRAIL_ANCESTOR}`}`}
    +  className={`flex items-center gap-1 ${TRAIL_ANCESTOR}`}

Result: `header-row-crowding` **11 passed**; `pnpm test` **7565 passed, 519
files, 0 failed**. `want=kill`, survived both.

A stronger form survives the new spec too: `const isLast = false;`
(`Breadcrumb.tsx:75`) leaves `header-row-crowding` at **11 passed**. Only
`src/components/__tests__/Breadcrumb.test.tsx:34` notices that one, and it
notices the *element name* (`SPAN` vs `A`), not the sizing.

### Why the spec cannot see it

The only core-trail fixture is `file-detail-chrome-deep`, and
`FileDetailChrome` always passes a `trailingSegment`
(`FileDetailChrome.tsx:126`). `isLast` is therefore `false` for every
segment in every case the spec runs, so the guard's true arm is never
evaluated and the leaf the spec measures is the `trailingSegment` node, not
a folder segment.

### Observation it predicts

Temporarily pass `trailingSegment={undefined}` from `FileDetailChrome.tsx:126`
(so the trail takes the folder-listing form) and measure the leaf's label at
768px on `file-detail-chrome-deep`:

| | leaf label width | needed | cut |
|---|---|---|---|
| guard intact (`60a4ec5d`) | 58.4px | 58px | no |
| guard removed | 28.6px | 58px | **yes** |

"Archived" loses half its characters on the folder-listing header, and no
test fails. The screens invariants 1 and 7 name — folder listing, trash,
missing, collection detail — have no measured case at all.

## 2. `flex-none` on the note row's name wrapper survives — the back control is starved instead, and nothing sees it

**[introduced]** — `FileDetailChrome.tsx:119` is a line this change writes.
**Breaks: invariant 8** ("neither is starved to zero width by the other").

### Mutation

`frontend/src/components/FileDetail/FileDetailChrome.tsx:119`

    -  <span className="flex min-w-0 flex-auto md:hidden">{titleNode}</span>
    +  <span className="flex min-w-0 flex-none md:hidden">{titleNode}</span>

Result: **11 passed**. `want=kill`, survived.

The brief's two named mutations *are* killed, so the pairing is held:

| mutation | result |
|---|---|
| drop `flex` → `min-w-0 flex-auto` | 1 failed (killed) |
| `flex-auto` → `flex-1` | 1 failed (killed) |
| `flex-auto` → `flex-none` | **11 passed (survived)** |
| drop `min-w-0` → `flex flex-auto` | 11 passed (survived; see note) |

### Observation it predicts

`file-detail-chrome-note` at 390px, measuring
`[data-testid='file-detail-back']` and the wrapper span:

| | back control | name |
|---|---|---|
| `60a4ec5d` (`flex-auto`) | 138.8px — folder name readable | 99.2px |
| `flex-none` | **26.9px** — chevron + ellipsis, no folder name at all | 211.1px |

The row reverses: the name takes everything and the back control keeps only
its chevron.

### Why the assertion meant to catch it cannot

`header-row-crowding.spec.ts:180` is `expect(isCut(m.back)).toBe(false)`.
`back` is `<a class="flex min-w-0 items-center gap-1 …">` whose label child
carries `truncate` (`FileDetailChrome.tsx:63`), i.e. `overflow: hidden`. A
truncating child's overflow never reaches its parent's `scrollWidth`, so
under the mutation `back` reports `scrollWidth 27 / clientWidth 27` while its
text needs ~139px — cut by every visible measure, `isCut` false.

Line 180 is also redundant against line 177: `back` sits inside `leading`,
neither has `overflow: hidden`, so any real overflow of `back` already shows
up as `isCut(m.leading)`. Removing `truncate`'s `overflow-hidden` from
`FileDetailChrome.tsx:63` fails at line **177**, not 180.

The other half of the guard, `expect(m.back.clientWidth).toBeGreaterThan(0)`
(line 181), is satisfied by 26.9px. The pair cannot distinguish "shares the
width" from "keeps only its chevron".

Note on the `min-w-0` survivor: it is redundant for `EditableTitle`, whose
button carries `truncate`, so the span's min-content contribution is already
0. It still binds for a `titleNode` that does not truncate itself, so it is
meant to survive.

## 4. The archive leaf's cut-ness is measured on the wrapper, the ancestors' on the label

**[introduced]** — `header-row-crowding.spec.ts` is created by this change, so
there is no parent to run it against.
**Breaks: none directly** — it is the reason finding 3 needed a fixture change
to surface.

`header-row-crowding.spec.ts:61-67` measures each ancestor's **inner label**
(`el.querySelector("a, button, span")`), which for the archive is the
`truncate` button. Line 58/73 measures the leaf as
`trail.lastElementChild` — the **wrapper span**, whose truncating button
child can never push its `scrollWidth` past its `clientWidth`.

### Mutation that shows the resolution

`ArchiveToolbar.tsx:155` → `flex items-center gap-1 min-w-0${isLast ? "" : " shrink-[999]"}`
(give the leaf wrapper `min-w-0`): **11 passed**, `want=kill`, survived.

Under the fully inverted guard the wrapper does report cut — but only at
`scrollWidth 14 / clientWidth 0`, i.e. once it is squeezed below the
`flex-shrink-0` chevron. Between "label fully readable" and "label at zero
width" the wrapper measures `scrollWidth == clientWidth` throughout, so for
the archive `expect(isCut(m.leaf)).toBe(false)` (line 120) and
`expect(m.leaf.clientWidth).toBeGreaterThan(0)` (line 121) are satisfied by
a bare chevron.

For the core trail the same lines *are* load-bearing, because there
`lastElementChild` is the `truncate` span itself
(`Breadcrumb.tsx:107-112`). Dropping `shrink-[999]` from `TRAIL_ANCESTOR`
kills exactly the two file-detail "gives way" cases and none of the three
archive ones — the asymmetry, measured.

Suggested shape: measure the leaf's label the same way the ancestors are
measured.

## 5. The phone case's selector finds the back control, not the rename control

**[introduced]** — `header-row-crowding.spec.ts:161` is created by this change.
**Breaks: invariant 8/9 coverage**, not behaviour.

`header-row-crowding.spec.ts:161` reads the rename control as
`leading.querySelector("button")`.

`backControl` is rendered before `titleNode` (`FileDetailChrome.tsx:106`,
`:118`) and is a `button` element whenever the host passes `onBack`
(`FileDetailChrome.tsx:66-75`). `querySelector` returns the first match in
document order, so in that variant `m.name` **is** `m.back`.

`FileDetailShell.tsx:153-165` passes `titleNode` and `onBack` together — a
Markdown note opened during collection playback is exactly that row.

### Reproduction

Add an `onBack` prop to `FileDetailChromeNoteArrangement` in
`fixtures/app.tsx`, beside `titleNode`, and re-run: **11 passed**. The element
the spec then measures as `name` is the BUTTON whose text is "Back", box
`left 12` .. `right 65.3`, while the rename control sits at `left 65.3` ..
`right 250`.

Lines 182-186 then assert about the back control twice and about the rename
control not at all — `m.name.clientWidth` positive, `m.name.right` inside
`m.leading.right`, and the overlap loop are all satisfied by a control that
was never at risk.

Suggested shape: find the rename control by the element the fixture puts
there (a `data-testid`), or by `leading.lastElementChild`.
