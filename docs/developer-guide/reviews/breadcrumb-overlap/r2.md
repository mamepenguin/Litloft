## 1. `truncate` on the trail's trailing segment — the one segment the code calls "routinely too long" — is reached by no measured width, and without it the name lays itself out over two lines

**[pre-existing]** — `Breadcrumb.tsx:117` is not a line `86df7069` writes. But `86df7069` is the commit that went looking for exactly this class of hole (its message: *"the fixture's last segment was short enough to fit whatever happened"*), closed it for the **folder** leaf, and left it open for the **trailing** leaf, which is the form every file-detail page draws.
**Breaks: invariant 1** — "the file's name is drawn inside the trail's own box at every width", for the `trailingSegment` form.

### Mutation

`frontend/src/components/Breadcrumb.tsx:117`

```
-  className="font-medium text-text-primary truncate"
+  className="font-medium text-text-primary"
```

Result: **17 passed**. `want=kill`, survived.

### Why nothing sees it

`truncate` is `overflow:hidden` + `text-overflow:ellipsis` + `white-space:nowrap`. On this span the `overflow:hidden` is also what resolves the flex item's automatic minimum size to 0 — it is the whole reason the trailing segment can narrow at all, since unlike the folder segments it is a bare child of the `nav` with no `TRAIL_SEGMENT` wrapper around it.

The fixture never asks it to. `DEEP_LEAF` measures 274px, and at 768px the trail has 660px with the ancestors squeezed down to 8–51px, so the trailing segment fits **exactly** — `scrollWidth 274 / clientWidth 274`. The class is dead weight at every width the spec runs.

### Observation it predicts

Lengthen only `DEEP_LEAF` (`frontend/e2e-components/fixtures/app.tsx:988`) to `"2026-09-annual-report-final-revision-board-approved-copy-for-distribution.md"`, and measure `file-detail-chrome-deep` at 768px:

| | `nav` height | leaf box | rendered as | suite |
|---|---|---|---|---|
| `truncate` intact | 20px | `cw 532 / sw 533`, one line | one line, ellipsised | **2 failed** (`isCut(leaf)` true where `leafCut: false`) |
| `truncate` dropped | **40px** | `cw 532 / sw 532`, two lines | **filename broken across two lines** inside an `h-12` row | **17 passed** |

The suite goes *green* when the guard is removed and *red* when it is kept. Every assertion in the case is horizontal — `isCut`, `clientWidth`, `leaf.right <= trail.right`, `documentScroll` — so a name that **wraps** instead of overflowing satisfies all of them. The spec cannot see the row grow a second line of text.

Also visible in that table: with the guard intact the long name reports `sw 533 / cw 532`. `isCut` compares two integer-rounded reads of a fractional layout, so a segment that fits to within a fraction of a pixel reports "cut", and `expect(isCut(m.leaf)).toBe(leafCut)` is an exact boolean. A fixture string landing on that boundary turns the suite red with nothing wrong.

## 3. `ancestors` is an enumeration with no count, and `Math.max(...ancestors)` is an expected value built out of the observation

**[pre-existing]** — the `ancestors` array and its assertions arrive with the spec at `853c3a14`/`60a4ec5d`; `86df7069` rewrote how they are gathered (lines 68-72) and applied detector rule 1 to `controls` (`toBeGreaterThan(0)` → `toBe(c.controls)`) without applying it here.
**Breaks: none observed** — vitest holds the behaviour.

`.claude/rules/review-workflow.md`, Detector rules 5: *"Never build the expected value out of the observation. A derived expectation cannot catch a deletion — the removed element leaves both sides at once."*

`frontend/e2e-components/header-row-crowding.spec.ts:152-154` is that shape exactly:

```js
expect(m.leaf.clientWidth).toBeGreaterThan(
```

and `m.ancestors.length` is asserted nowhere.

## 4. Invariant 5 describes a shape the code does not draw, and a reader acting on it would delete a control

**[pre-existing]** — `FileDetailChrome.tsx:99-105` dates from `27b27b39` (PR #110), well before this branch.
**Breaks: nothing in the code** — this is about `docs/developer-guide/reviews/breadcrumb-overlap/invariants.md`, which `86df7069` commits.

Invariant 5 reads: *"The file-detail chrome draws exactly one of its two forms at any width: the back control below `md`, the trail at `md` and above — **never both**, never neither."*

The `onBack` branch draws both on purpose:

```
onBack
  ? "flex min-w-0 flex-1 items-center md:max-w-[45%] md:flex-none"
  : "flex min-w-0 flex-1 items-center md:hidden"
```

Only the second form carries `md:hidden`. With `onBack` supplied — a file opened during collection playback — the back control and the breadcrumb are both drawn at `md` and above, and `FileDetailChrome.tsx:96-98` says why.

### Observation it predicts

An author holding invariant 5 and finding this branch will "restore" the invariant by adding `md:hidden` to the `onBack` arm, which removes the only control that can return to the collection at every width above `md`. Per the prose rule the remedy is **deletion**: strike "never both" from item 5, or the item.

This is also a coverage statement: the `onBack` form of the row — the one that draws both — has no measured case at any width, in either round.

## The trajectory

Read in order: `853c3a14`, `60a4ec5d`, `86df7069`.

**The loop is converging, not being patched.** Neither of the two fix rounds adds a branch, a state or a prediction that the round before it also added, and the third round removes one.

- `853c3a14` **adds** one prediction: `TRAIL_ANCESTOR = "min-w-0 shrink-[999]"`, applied through an `isLast` conditional that decides whether a segment gets the class *at all* (`isLast ? "" : TRAIL_ANCESTOR`, in two files).
- `60a4ec5d` does not touch that. It **adds a different** conditional in a different component — `isMobile && titleNode` placing one instance of the rename control in `FileDetailChrome` — a placement decision, not a second attempt at the sizing rule.
- `86df7069` **removes** the round-one prediction rather than adding to it. `isLast ? "" : TRAIL_ANCESTOR` becomes `isLast ? TRAIL_SEGMENT : TRAIL_ANCESTOR`: the branch no longer decides *whether* a segment can narrow, only *how eagerly*. `min-w-0` becomes unconditional for every segment of both trails. The diff is 6 changed lines in `Breadcrumb.tsx` and 4 in `ArchiveToolbar.tsx`; the remaining ~140 frontend lines are the detector, plus the committed review record.

The special case that said "the last segment is different in kind" was deleted and replaced by "every segment narrows, the ancestors narrow first" — one rule where there were two.

The one caution worth recording is not about branches but about the detector. Each round's fix has also extended the measuring spec, and the extension has each time been *a new case for the shape the last round missed* — `853c3a14` added the archive and file-detail cases, `60a4ec5d` added the note row, `86df7069` added the folder-listing row. Finding 1 is the next member of that series already visible: the `trailingSegment` form is still measured only with a name short enough to fit. That is a gap in coverage, not a design being patched — the sizing rule itself did not grow.
