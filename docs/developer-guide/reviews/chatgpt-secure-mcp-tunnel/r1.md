## Findings

### F1 — [introduced] The new tests never observe `tools/list`, so registration can drop every annotation — A

Severity: medium. Invariant 1 is about advertised metadata, not the private
tool objects.

`mcp-server/src/__tests__/toolMetadata.test.ts:16-24` loops over `allTools`
directly. It does not instantiate `McpServer`, exercise the registration path
at `mcp-server/src/index.ts:75-84`, or inspect a protocol `tools/list`
response. Mutation M1 removed `annotations: tool.annotations` from
`registerTool`; all five metadata tests still passed. The resulting server
would advertise none of the four hints even though the test named "annotates
every advertised tool" remained green.

This is introduced because `toolMetadata.test.ts` is new in this commit. Per
`review-workflow.md` R-4, a test that lets an R-0 invariant break is itself an
A finding.

Remedy shape: make the MCP entry point importable without auto-running, start
it with the SDK's in-memory or stdio transport, call `tools/list`, and assert
the exact declared metadata on the returned tools. Keep object-level tests
only where they add a narrower diagnostic.

### F2 — [introduced] Idempotency correctness is not asserted for any tool except Ask — A

Severity: medium. A false retry-safe hint can duplicate an additive write.

`mcp-server/src/__tests__/toolMetadata.test.ts:16-23` only checks that
`idempotentHint` is a boolean. The sole exact idempotency assertion is an
incidental field in Ask's four-field object at lines 34-40. Two wrong-value
mutations survived:

- M2 changed all GET-only tools from `idempotentHint: true` to `false`.
- M2b changed `upload_file` from `false` to `true`; both
  `toolMetadata.test.ts` and all 20 write-tool tests stayed green. Retrying the
  same upload can create another file, so advertising it as idempotent gives a
  client the wrong basis for replay after an uncertain result.

This is introduced in the new metadata test. It breaks invariant 1's explicit
idempotency-hint requirement.

Remedy shape: declare the expected idempotent tool-name set and compare every
advertised tool against it, just as the test already does for destructive and
open-world hints. The expected set must be a fixed declaration, not derived
from the observed annotations.

### F3 — [introduced] Ask's privacy disclosure can disappear without a test failure — A

Severity: medium. The disclosure is the only agent-visible warning that file
excerpts may leave the Litloft deployment.

Invariant 3 explicitly requires Ask's description to disclose possible
excerpt transfer to the configured LLM provider. M5 removed that sentence
from `mcp-server/src/tools/ask.ts:10-11`; both `ask.test.ts` and
`toolMetadata.test.ts` passed (7/7). The open-world boolean remained correct,
but it does not tell the model or user what data may be transferred.

This is introduced because both the disclosure and the invariant-test file
are new in this commit.

Remedy shape: assert on a stable semantic disclosure marker in the actual
`tools/list` description (for example, that Ask names both file excerpts and
the configured LLM provider). This is runtime tool metadata, not a source
comment or documentation-only mutation.

## Security and boundary checks

- Every handler still uses `LitloftClient` and the existing public `/api/*`
  paths. `request`, `requestRaw`, `requestSse`, and `requestMultipart` all add
  the configured `Authorization: Bearer` header; drive-scoped addon calls keep
  their `X-Lit-Drive` context. The diff adds no alternate auth, validation, or
  drive-access path.
- The annotation matrix matches the current MCP semantics in the unmodified
  code: reads are read-only/closed-world; replacement, relocation, and trash
  operations are destructive; URL fetching and Ask are open-world; permanent
  deletion is not exposed.
- Ask's shipped description discloses possible excerpt transfer. URL clipping
  remains routed through the existing Knowledge endpoint and its SSRF checks;
  pasted HTML does not fetch its metadata URL.
- The runbook keeps the tunnel outbound-only, recommends loopback, rejects
  plaintext LAN HTTP for the bearer token, tells operators to keep both keys
  in a service manager/secret store, scopes Litloft credentials by drive
  groups, explains JWT revocation limits, and does not claim the tunnel makes
  a publishable public plugin. These statements match the current official
  Secure MCP Tunnel guide.
- No credential value or private key was added; examples use placeholders.
