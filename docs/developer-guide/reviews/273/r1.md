### F7 [pre-existing] B — `useCollectionViewMode` requires `file_type === "document"` for `text`; backend and `dominantKind` do not

`fileToKind`: `if (file.file_type === "document" && isTextKind(...))`. Backend `_classify_kind_parts`
takes the suffix before `file_type` (`stray.md`, `file_type=other`, mime NULL → `text`, held by
`test_file_kind_filter`), and `dominantKind.ts` has no document condition. So a collection of such rows
is `other` while the same folder is `text`.
Mutation FM6: drop the `file.file_type === "document" &&` guard. Result: survived (4400 passed): no
fixture can see the guard either way. The guard is unchanged from the parent.
The docstring "Mirrors the backend dominant_kind classification" is false for this row; delete it
rather than reword it if the guard stays.

### F8 [pre-existing] B — no smart folder can hold `markdown` (or `text`), so the migration and invariant 4's smart-folder clause describe an unreachable row

`schemas.py` `_SMART_FOLDER_FILE_TYPES = {"video", "image", "audio", "document"}`, unchanged since it
was introduced in `bfb464d7` (`git log -G`). `SmartFolderCreate` / `Update` reject any other
`file_type`, so a `markdown` row could only come from a hand-edited DB, and saving a search narrowed to
Text fails with "could not save" (as it did for Markdown at the parent;
`SmartFolderSaveButton.tsx` documents it). The migration is correct and held (M13/M14 killed), but
it touches nothing in any DB the app wrote. For the supervisor: either invariant 4's clause is moot, or
the smart-folder vocabulary is the missing piece.
