## Findings

### H1 — the URL seed's `.trim()` is the commit's only production change to `SetupWizard.tsx`, and nothing holds it  `[introduced]`  **B**

F1 removes it and all 85 frontend tests stay green.

`047dd288`'s round-2 test "sends the token it verified, not what was pasted
around it" opens `/setup` with **no** `?token=`
(`SetupWizard.test.tsx:699`: `window.history.replaceState(null, "", "/setup")`)
and pastes into the field, so it walks `onChange`, not the URL seed. Every other
unlock test uses `SETUP_TOKEN = "a-valid-setup-token"`, which has no whitespace
to trim, and the default mock answers `200` for any verify body. So no test
ever seeds a URL token that the trim changes.

Measured against a scratch test (written, run, deleted; the tree is clean):
`/setup?token=%20tok%20` verifies `{"token":"tok"}` at `a56b1de1` and
`{"token":" tok "}` with F1 applied. Both paths are internally consistent —
verify and the later writes send the same string either way — which is why this
is not an invariant 5 break, and why round 2 filed the untrimmed URL as a B.

Worth naming because the trim moves behaviour in the **narrowing** direction,
not the widening one. `setup_token.setup_token()` returns `os.getenv(ENV_VAR)`
verbatim (`setup_token.py:31-34`), so `LITLOFT_SETUP_TOKEN=" abc"` makes the
backend's token `" abc"`. At `047dd288` the printed URL `/setup?token=%20abc`
verified `" abc"` and worked; at `a56b1de1` it verifies `"abc"` and the operator
gets "Invalid token" about a correct configuration. Round 2's G4 observed that
the typed path already 403s on such a token and the URL path did not; `a56b1de1`
levels the two by taking the working one away.

The default path never produces such a token (`configure.py:327`
`gen_secret()[:32]` is hex, and `configure.py:265` `.strip()`s a value read back
out of `.env`), which is why this stays a B rather than an invariant 8 break —
the backend still uses the variable as given.

### H2 — `completed` and `rejected` can be on screen together; only one of the two is reset on a resubmit  `[introduced]`  **B**

`UnlockStep.submit` (`UnlockStep.tsx:33-47`) opens with `setRejected(false)` and
never `setCompleted(false)`. `onChange` resets both, and F7 shows nothing holds
that reset either.

Measured in jsdom against the real component (scratch test, since deleted):

```
mount with ?token=… , verify → 404   ⇒  "Setup is complete"
press → again,        verify → 403   ⇒  "Invalid token" AND "Setup is complete"
```

The second assertion is the defect: `queryByText("Setup is complete")` is still
non-null after the 403 has rendered "Invalid token" beneath the same field.

Failure scenario, and it is the documented recovery path.
`docs/getting-started/first-run-setup.md:11` tells an operator who wants to
re-run setup to delete the sentinel, restart the backend, and open the new
token's URL. An operator who still has the old `/setup?token=…` tab open sees
"Setup is complete", goes and does exactly that, comes back to the same tab and
presses →. The restart minted a fresh token, so the old one 403s, and the screen
now carries two contradictory lines at once: the token is invalid *and* setup is
complete. Neither is a reason to reload, which is the only thing that clears it.

No declared invariant covers what the unlock screen says, so B. It is the kind
of defect a state added for one more case produces — see `## Trajectory`.

### H3 — any `404` from the verify endpoint becomes "Setup is complete", including one the backend did not send  `[introduced]`  **B**

`adminConfig.ts:136-139` maps on the status alone:

```ts
if (err instanceof AdminConfigError && err.status === 404) {
  throw new SetupAlreadyCompletedError();
}
```

`AdminConfigError` already carries the discriminator — `parseError` reads
`body.detail` and the class exposes a `code` getter (`adminConfig.ts:87-93`) —
and the backend does send `{"code": "setup_completed"}`
(`admin_config.py:300`). The frontend's own test feeds that exact body
(`SetupWizard.test.tsx:650`), so it passes either way: F5 and F6 kill the two
mutations that drop the mapping, but no mutation of the *body* is possible,
because the body is not read.

Failure scenario: any `404` reaching that URL that is not the sentinel guard —
a frontend container rebuilt against an older backend that has no
`setup-token/verify` route, or a rewrite that misses. `parseError` then fails to
parse the HTML body, `detail` is `undefined`, and a **fresh** install with no
sentinel at all tells the operator "Setup is complete" and leaves them on a
screen with nothing to press. That is the same wrong-cause defect round 2 filed
as G5, pointing the other way.

Narrow, and no declared invariant covers the message, so B. One extra condition
(`err.code === "setup_completed"`) closes it, and the getter for it already
exists.

### H4 — invariant 10 is held by nothing, and is already false in the tree it was written for  `[introduced]`  **A (invariant 10, as worded)**

Invariant 10, added by this commit: *"Whether setup is complete is asked through
`config.setup_completed_sentinel()` and nowhere else."*

Two measurements.

**Nothing enforces it.** M10 reverts `_admin_or_first_run` to
`config.DATA_DIR / "setup_completed"` and all 143 tests in the selection pass.
The same is true for the other four converted sites — the accessor and the
inline expression read the same live module attribute, so no runtime mutation
can distinguish them. A seventh call site is one line away from an inline stat
and nothing will say so. (The invariant is a claim about shape; R-0 asks for
invariants "written so that a mutation can violate it — an observable sentence",
and this one is not observable at runtime. A source-scanning detector could hold
it, and `review-workflow.md` detector rule 4 calls that the last resort.)

**It is false at `a56b1de1`.** `configure.py:586`:

```python
first_run = not (base / 'data' / 'setup_completed').exists()
```

`configure.py` runs on the host before any container exists, imports only
`json, os, re, shutil, subprocess, sys` and `pathlib`, and cannot import
`app.config`. So the repository asks the question in a seventh place that the
invariant forbids and that the accessor cannot serve.

Filed as an **A** because the letter of a declared invariant is broken in the
reviewed tree, not because anything a user can reach is wrong — all 2344 backend
tests pass and the behaviour of every converted site is unchanged (M8/M9 confirm
the accessor is call-time; the full suite confirms no caller of the renamed
symbol was missed, and no `_setup_completed_sentinel` reference survives anywhere
in the repo including the four checked-out addon submodules).

What this finding is really about is the invariant, not the code: as worded it
standardises *how* the question is asked, not *that* it is asked, and the defect
it was written after (round 1's finding 1 — a call site that forgot the check
entirely) would still have happened with the accessor available. The thing that
actually holds "every write route is gated" is the route-list detector, which
this commit fixed. Whether to revise the wording is the supervisor's call under
R-0, not mine and not the author's.

### H5 — "Setup is complete" is a dead end  `[pre-existing]`  **B**

`UnlockStep` renders the message as `text-xs text-text-muted` under the field
(`UnlockStep.tsx:90-92`). The → button stays enabled, pressing it repeats the
same 404, and there is no link to `/admin` or `/admin/settings`. `page.tsx`
renders the wizard unconditionally and `SetupRedirector` only ever redirects
*to* `/setup` (`SetupRedirector.tsx:13`), never away from it. The operator who
reopens the URL `configure.py` printed is stuck on a screen whose only control
does nothing.

`[pre-existing]` by reproduction: at `047dd288` the same operator got "Invalid
token" and was equally stuck; at `a33d7364` there is no unlock step, so the
wizard walks to the end and `POST /complete-setup` answers `409` with the
frontend's generic error. No commit in this chain introduced the dead end, and
round 2 recorded the missing `/setup` guard as `[pre-existing]` too.

`a56b1de1` changes only the wording, which is a real improvement over round 2's
G5 — but it makes the state *legible* without making it *exitable*, so the
screen now reads like something unfinished rather than something broken.

The same gap shows in `docs/`. CLAUDE.md requires a change that alters what an
operator can observe to update the matching page in the same PR; this commit
adds an operator-visible screen state and touches no page.
`docs/getting-started/first-run-setup.md` describes step 0 and the re-run
procedure (line 11) but never says what `/setup` does on an install that has
already finished, so the operator who lands on this screen has nothing to read
either. One line there would cover both halves.

## Trajectory

Read in order: `a9ce7e44` + `03a99eea`, `047dd288`, `a56b1de1`.

**No. `a56b1de1` ends the pattern round 2 named rather than continuing it.**
It is the first round in the chain whose fix *removes* branches, and it removes
exactly the two that produced rounds 1 and 2.

**The duplicated predicate.** `a9ce7e44` introduced "stat `data/setup_completed`
and branch on it" at four call sites; `047dd288` added a fifth, which is what
round 2 filed under its trajectory heading — six inline stats, one accessor used
by one of them. `a56b1de1`'s entire backend production diff is the opposite
move: `config._setup_completed_sentinel()` becomes public and all six sites call
it (`main.py:255`, `admin_config.py:223, 271, 299, 322`, `drive_seed.py:131`,
`+4 −4` and `+1 −1` and `+1 −1`). Five copies of a predicate collapse to one.
That is the thing round 2 said had not been added in either round.

**The derived comparison.** The detector's history is the same shape running the
other way. Round 1: a hand-written list of write routes, two of them missing
(F5). Round 2: the list plus a cross-check against `app.routes`, but compared
through two normalising comprehensions that projected `/passwords/{index}` onto
`/passwords` — a derivation that hid exactly the routes the check existed for
(G1). Round 3: both comprehensions deleted, a declared template column added to
each row, `assert routed == listed` with no transform on either side. Nine
mutations (M1–M7, M14, M15) all die, including round 2's two survivors verbatim.
Round 2 added a derivation; round 3 removed it.

**The one prediction it adds, and how to read it.** The frontend gains a state
(`completed`), an error class and three branches, and that addition is what H2
and H3 are about — the predicted cost of a state added for one more case. Two
things keep me from calling it the pattern.

First, it is not the second in a row on that surface: `047dd288`'s frontend
change *removed* state (three `.trim()` sites collapsed to one), and the unlock
screen has gained one message in three rounds, not one per round.

Second, round 2's backend 404 and round 3's frontend `SetupAlreadyCompletedError`
are the two ends of one mechanism — the endpoint that emits the state and the
screen that reads it — not two independent cases each anticipating the last
one's miss. Round 2 shipped the emitter without the reader, which is why the
same operator got "Invalid token" about a correct token, and round 3 shipped the
reader.

What is worth the supervisor's eye is that the reader is written more loosely
than the emitter: the backend sends a discriminator and the frontend matches on
the status code alone (H3), so the screen will say "Setup is complete" about any
404 including one that means the opposite. That is one condition, not a design.

**Net across the four diffs**: −5 duplicated predicates, −2 derived
comparisons, −1 test that blessed an unusable configuration, +1 state with two
defects in it. I read that as the loop converging.

  The `backend-conventions.md` `import app.config as config` rule is satisfied —
