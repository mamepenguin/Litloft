## Findings

### F1 — `POST /setup-token/verify` mints and logs a token on an install that has already completed setup  `[introduced]`  **A** (invariant 7)

`matches()` calls `setup_token()`, which mints lazily. On a completed install
`main.py` correctly mints nothing, so `_token` is `None`; `_admin_or_first_run`
never reaches `matches()` there either. `setup-token/verify` is the one path
that does, and it carries **no dependency at all**.

Failure scenario: an install with `data/setup_completed` present and
`LITLOFT_SETUP_TOKEN` unset. Any unauthenticated peer sends

```
POST /api/admin/config/setup-token/verify   {"token": "guess"}
```

Observed (probe run in the test container, fixture = completed install):

```
assert setup_token._token is None   # true at startup, as invariant 7 requires
→ POST /setup-token/verify {"token":"guess"} → 403
WARNING app.setup_token: Setup is not complete. Open /setup?token=txoBnKdhxaz0Gv13cd_miuPIqZNjfaXw, or enter this at /setup:
    setup token: txoBnKdhxaz0Gv13cd_miuPIqZNjfaXw
assert setup_token._token is None   # FAILS — a token was minted
```

Invariant 7 says "no token is minted, and nothing is logged". Both halves
break, and the log line asserts something false about the install ("Setup is
not complete"). It is also an unauthenticated, unbounded log-write primitive:
one line of ~140 bytes per request, repeatable, with an attacker-independent
but operator-confusing payload.

`[introduced]` without a reproduction against the parent: the endpoint and
`app/setup_token.py` are created by this change.

Note that the docs added in this change state the opposite —
`docs/reference/env-variables.md`: *"It has no effect once `setup_completed`
exists."* That sentence would lead a reader to conclude the verify endpoint
needs no sentinel check, which is the defect. Gating `verify` on the sentinel
absent (404 once complete) fixes F1 and F2 together and makes the sentence
true.

### F2 — `verify` keeps confirming the token long after the window has closed  `[introduced]`  **B** (invariant 3)

Same probe, second half:

```
POST /setup-token/verify {"token": <the real token>}  →  200 {"ok": true}
```

on an install where `setup_completed` exists, two protected drives are
configured and a master password is set. Invariant 3 reads "With the sentinel
present, the token grants nothing … a caller holding only the token is
refused." Every *config write* is indeed refused (M3, M16–M18 confirm), so the
literal security property holds; what does not is that an unauthenticated
endpoint keeps answering yes/no about a secret that is meant to be spent.

Concretely: `configure.py` writes `LITLOFT_SETUP_TOKEN` to `.env`
unconditionally and reuses it on every later run, so the value outlives setup
by design. Anyone who ever saw it — the install terminal, a pasted
`configure.py` transcript, `docker compose logs` in a screenshot — can
re-confirm it against a live server forever. It grants no write today; it is a
standing oracle for a value the operator has no reason to believe still
matters.

Bucket B rather than A because no declared invariant names the verify endpoint,
and the fix is the same one F1 needs. Raising it because whether the second
clause of invariant 3 was meant to cover `verify` is the supervisor's call.

### F3 — the UnlockStep verifies a trimmed token and then sends the untrimmed one  `[introduced]`  **A** (invariant 5)

`frontend/src/app/setup/steps/UnlockStep.tsx`: the button calls
`submit(value.trim())` and Enter calls `submit(value.trim())`, but `onChange`
stores `e.target.value` unmodified, and that stored value is what
`SetupWizard` puts in `X-Litloft-Setup-Token` for all four writes.

Failure scenario: the operator copies the token out of
`docker compose logs backend | grep "setup token"` — the log line is
`    setup token: <tok>\n`, so a copy easily carries leading spaces or a
trailing newline. They paste `"  abc123  "` and press →.

Probe (real `SetupWizard`, mocked fetch, full wizard walked to `/admin`):

```
VERIFIED: "abc123"   SENT: "  abc123  "
```

The unlock step accepts the token, the wizard advances through every step, and
then the backend 403s all four writes. `handleBeforeSubmit` does not check
`res.ok` on the drives, passwords or addon-policy fetches, so nothing surfaces
until `complete-setup` fails with the generic error string — after the operator
has entered drive names, an access mode, a password and addon choices. Nothing
was written; the token they hold is correct; the message tells them nothing.

Invariant 5: "A wizard run that supplies the token completes exactly as it
does today: the same writes, in the same order, with the same bodies." A run
that supplies a token the product itself accepted performs none of the writes.

Fix is one line — store the trimmed value (`onChange(e.target.value.trim())`,
or verify and propagate the same string) — but the missing `res.ok` checks are
what turn it from an error into a silent one; that part is `[pre-existing]`.

### F4 — a non-ASCII `LITLOFT_SETUP_TOKEN` is accepted by the backend and blessed by a test, but no client can present it  `[introduced]`  **B** (invariant 8)

`test_a_non_ascii_token_can_be_configured` asserts
`setup_token.matches("あいうえお") is True`, and `matches()` is written (and
commented) to make that work. The gate, however, is reached only through a
header:

```
node -e 'new Headers({"X-T":"あいうえお"})'
→ TypeError: Cannot convert argument to a ByteString because the character at
  index 0 has a value of 12354 which is greater than 255
```

and from Python the same:

```
PUT /api/admin/config/drives  headers={"X-Litloft-Setup-Token": "あいうえお"}
→ httpx/_models.py:82 UnicodeEncodeError: 'ascii' codec can't encode characters
```

So with `LITLOFT_SETUP_TOKEN=あいうえお` the wizard's unlock step succeeds (that
one goes through a JSON body), the operator is stepped past it, and then the
first write throws a `TypeError` inside `handleBeforeSubmit` before any request
leaves the browser. Same end state as F3, reached a different way.

The value *is* used as given (invariant 8 holds at `setup_token()`), so this is
B. `configure.py` only ever generates `os.urandom(32).hex()[:32]`, and the docs
say `openssl rand -hex 16`, so the default path is unaffected — but the test
asserts a capability the product does not have, which is the kind of test that
survives a later fix that removes it.

### F5 — nothing holds the token gate on the other two routes that write `passwords.json`  `[introduced]`  **A** (invariant 1; R-4 "a test that lets an A through is an A")

`POST /passwords/append` and `DELETE /passwords/{index}` both write
`passwords.json` and both correctly carry `Depends(_admin_or_first_run)` today.
No test holds that for the first-run branch.

M19b replaced their dependency with the **pre-change** gate — open while the
sentinel is absent, admin after — and the whole selection stayed green:

```
138 passed, 5 warnings in 2.03s
```

That is exactly the state this change exists to close, reintroduced on two of
the four routes, invisible. The reachable attack: during first run, after the
wizard's `PUT /drives` has established `access_group: g1`, an unauthenticated
LAN peer sends `POST /api/admin/config/passwords/append` with
`{"password": "mine", "groups": ["g1"]}` and holds a valid credential for the
operator's drive from that moment on; `DELETE /passwords/0` removes the
operator's own.

`test_setup_token.py::_writes()` enumerates four routes (drives, passwords,
addon-policy, complete-setup) and omits these two. Per the detector rules, an
enumeration that does not enumerate everything in scope is the failure mode
here — invariant 1 says "This holds for drives, passwords and addon policy",
and two of the password writers are outside the enumeration.

### F6 — the entire startup-mint block is unheld  `[introduced]`  **B** (invariant 7)

Three independent mutations of `main.py` all survive the full selection:

- **M13** delete the mint entirely → 138 passed. Nothing asserts the operator
  can find the token in the log before opening `/setup`; every test mints
  lazily through `setup_token.setup_token()` itself.
- **M14** mint unconditionally, sentinel or not → 138 passed. This is invariant
  7 stated as a mutation, and no test objects.
- **M24** move the mint ahead of `drive_seed.run_startup_drive_bootstrap()` →
  138 passed. The current order is what makes the upgrade path correct: the
  migration touches the sentinel for a pre-existing hand-configured install
  (`_migrate_setup_sentinel`, `drive_seed.py:113`) at `main.py:235`, and the
  mint at `main.py:255` then sees it. Reversed, every such install mints and
  logs a token on its first boot after the upgrade — invariant 7's exact
  wording — and the suite is silent.

B rather than A because the code as written is correct on all three counts.
Note the interaction with F1: once `verify` no longer mints, the startup mint
is the *only* minting path, and these are the tests that would hold it.

### F7 — the token on the wizard's password write is unheld, and losing it is unrecoverable  `[introduced]`  **B** (invariant 5)

FM5 removed `X-Litloft-Setup-Token` from the wizard's `PUT
/api/admin/config/passwords` and all 97 frontend tests stayed green. The
existing assertion — "sends the token on every config write and on
complete-setup" — walks the **public** path, where the password write never
happens, and then enumerates three URLs (`/drives`, `/addon-policy`,
`/complete-setup`).

Why this one matters more than the others: `handleBeforeSubmit` ignores
`res.ok` on that fetch, so a 403 there is silent, and the run still reaches
`complete-setup`, which succeeds. The operator ends with `drives.json`
carrying `access_group`s, `passwords.json` empty, and the sentinel written —
every drive 404s, `GET /drives` 403s, `PUT /drives` 403s. That is the lockout
described in `_admin_or_first_run`'s own docstring, and recovery is editing
`drives.json` on the host. It is also the second half of the known issue this
PR added to `known-issues.md`, reachable by a different route.

B because the header is present today. It becomes an A the moment the
enumeration is trusted.

### F8 — nothing asserts the minted token is unpredictable  `[introduced]`  **B**

M12 replaced `secrets.token_urlsafe(24)` with a 32-character string literal and
all 138 tests passed. `test_one_is_minted_when_the_variable_is_unset` asserts
`len(minted) >= 24` and that two calls agree — both of which a hardcoded
default satisfies. The one property that carries the whole change (an attacker
on the LAN cannot guess it) is the one nothing holds.

A cheap detector that does hold it: mint in two processes (or reset `_token`
and mint twice) and assert the two values differ.

## Checked, no finding

- **Every HTTP surface that writes the gated files.** `atomic_write_json`
  callers outside tests are `admin_config.py` (5: `PUT /drives`, `PUT
  /passwords`, `POST /passwords/append`, `DELETE /passwords/{index}`, `PUT
  /addon-policy`) and `drive_seed.py` (startup only, not an endpoint). All five
  routes carry `Depends(_admin_or_first_run)`. `setup_completed` is written by
  `POST /complete-setup` (now gated, M15 killed) and by
  `_migrate_setup_sentinel` at startup. No other router touches either file.
- **Token in a response body.** M22 and M23 are both killed by
  `test_the_token_is_in_no_response_body`. `setup-status` returns only
  `{completed, drives}`; the 403 detail is a fixed string naming *where* the
  token is, not the value.
- **Token in a `Referer`.** `/setup?token=…` stays in the address bar for the
  whole wizard, but the setup tree, the root layout and `globals.css` contain
  no `https://` subresource, so no cross-origin request is made from that page;
  the default `strict-origin-when-cross-origin` would strip the query anyway.
  The token does land in browser history and in the frontend container's
  request log — already true of the backend log it is printed to.
- **Brute force through the oracle.** Minted tokens are
  `secrets.token_urlsafe(24)` (192 bits); `configure.py` writes
  `os.urandom(32).hex()[:32]` (128 bits). Unbounded request volume does not
  reach either. No rate limit is needed for entropy reasons (F1's log-flood
  angle is separate).
- **Comparison soundness.** `None`, `""`, a near-miss one character short or
  long, a case flip, a leading or trailing space, and non-ASCII candidates are
  all covered by `test_a_near_miss_does_not_match` and
  `test_a_non_ascii_candidate_is_refused_rather_than_raising`; M8 and M9 (the
  two ways to reintroduce the `bytes`/`str` and `None` crashes) are killed hard
  (6 and 39 failures). `compare_digest` on unequal-length bytes returns False
  rather than raising. The `.encode("utf-8")` on both sides is the right fix
  for the `compare_digest` non-ASCII `ValueError`.
- **Timing.** M6 (plain `==`) survives and was meant to: no test here can
  observe timing. `compare_digest` is the correct call regardless.
- **`configure.py` hand-off.** `gen_secret()[:32]` is 32 hex characters, so
  nothing that `.env` parsing, `${LITLOFT_SETUP_TOKEN:-}` interpolation or a
  header encoder treats specially (`$`, `#`, space, quote, newline) can appear.
  `write_env_key` rewrites in place on re-run and `ExistingConfig` reads the
  value back, so `test_a_second_run_keeps_a_setup_already_in_progress_working`
  holds the reuse. An **operator-chosen** value containing `$` would be
  interpolated by compose before the container sees it — out of scope of
  invariant 8, and the docs prescribe `openssl rand -hex 16`.
- **The sentinel appearing mid-flight.** `_admin_or_first_run` stats the
  sentinel per request, so the gate flips to `require_admin` on the next
  request after `complete-setup`; `_token` staying in memory grants nothing
  after that (M3 and the post-completion tests). The sentinel *disappearing*
  mid-flight on a running process falls back to whatever `_token` holds, or
  mints and logs a fresh one — the documented recovery ("delete the sentinel,
  restart the backend") makes that deterministic.
- **`.env` exposure.** `.env` is gitignored (`.gitignore:22`).
- **GET routes.** `GET /drives`, `/passwords`, `/addon-policy` keep
  `Depends(auth.require_admin)` unchanged; the token does not reach them, so
  it cannot be used to read the seeded configuration.
- **Prose.** Reviewed only for statements that would lead to a wrong code
  change. One found, and it is F1's: `env-variables.md`'s "It has no effect
  once `setup_completed` exists." Everything else in the `docs/` diff describes
  the code as written.
