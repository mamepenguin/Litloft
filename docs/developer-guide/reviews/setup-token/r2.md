## Findings

### G1 — the route-list detector is blind to a write route added under a collection path that is already listed under the same method  `[introduced]`  **A** (invariant 1; R-4 "a test that lets an A through is an A")

`test_the_route_list_is_every_write_under_admin_config`
(`backend/tests/test_setup_token.py:99`) normalizes the routing table with

```python
(method, path.rstrip("}").rsplit("/{", 1)[0] if "/{" in path else path)
```

That collapses an item route onto its collection path. When the collection path
is already in `listed` under the same method, the new route lands on a pair the
set already contains and the assertion cannot see it.

Measured, twice, each added with **no dependency at all** — not "open during
first run", open always:

```
PUT /api/admin/config/passwords/{index}   → 143 passed
PUT /api/admin/config/drives/{name}       → 143 passed
```

(`PUT /api/admin/config/passwords` and `PUT /api/admin/config/drives` are both
in `_writes()`, so both new pairs vanish into existing ones. B13 shows the
detector does fire for a path shape the surgery leaves alone, and B20 shows a
listed route is then gated — so this is the one hole, and it is the whole gate.)

Failure scenario: the settings UI grows a "replace one password entry" call and
someone adds `PUT /api/admin/config/passwords/{index}` without
`Depends(_admin_or_first_run)`. Every test is green, including this detector and
including `test_a_write_without_the_token_is_refused_and_changes_nothing`, which
only walks the routes `_writes()` lists. An unauthenticated LAN peer then sends

```
PUT /api/admin/config/passwords/0
{"password": "mine", "groups": ["g1", "__admin__"]}
```

at any time — not only during first run — and holds admin on the install.

This is the class of defect the detector was added for. Round 1's F5 was two
password-writing routes missing from a hand-written list; `047dd288` replaced
the hand-written list with a cross-check that has a hand-shaped hole in the same
place. Invariant 1 ("**every** write route under `/api/admin/config`") is the
invariant this detector is the only holder of, so under R-4 the detector is an A.

Shape that closes it without surgery: put the literal FastAPI path template in
the enumeration (`"/api/admin/config/passwords/{index}"`) alongside the concrete
URL the request uses (`"/api/admin/config/passwords/0"`), and compare the
template side to `route.path` with no normalization on either side. Detector
rule 5's concern is the same one: the expected value here is declared, but the
comparison is made on a projection that throws away exactly the segment that
distinguishes the two routes.

`[introduced]` without a reproduction against the parent: the test is created by
`047dd288`.

### G4 — a token with whitespace can be URL-seeded or pasted but cannot be typed  `[introduced]`  **B** (invariant 8)

Measured in jsdom against the real `UnlockStep`:

```
typing "a", then " ", then "b"  →  field ends at "ab"
pasting "  x y  "               →  field holds "x y"
```

`onChange(e.target.value.trim())` on a controlled input re-renders the trimmed
string, so the space the operator typed is gone before the next keystroke lands.
Interior whitespace survives a paste and does not survive typing.

Separately, the URL seed is not trimmed: `SetupWizard.tsx:91-93` reads
`URLSearchParams.get("token")` verbatim, and that same state is what goes in the
header. So `/setup?token=%20abc` verifies `" abc"` and sends `" abc"` —
consistent, which is why this is not an invariant 5 break. All four entry paths
(URL, typing, paste, autofill — autofill fires `input`, so it takes the
`onChange` path) end at one string per path, and verify and send agree on every
one of them. FM1 and FM2 confirm round 1's F3 shape cannot come back.

What is left is that `LITLOFT_SETUP_TOKEN=" abc"` or `"a b"` works from the URL
and from a paste and 403s when typed, with "Invalid token" and nothing naming
the cause. Same family as F4 and B for the same reason: `configure.py` generates
`os.urandom(32).hex()[:32]` and the docs prescribe `openssl rand -hex 16`, so
the default path never produces one.

### G5 — `/setup` on a completed install now tells the operator their correct token is invalid  `[introduced]`  **B**

`verify` answers `404`; `verifySetupToken` throws on any non-2xx
(`adminConfig.ts:128`); `UnlockStep` catches everything into
`setRejected(true)` and renders "Invalid token".

Failure scenario: an operator reopens the URL `configure.py` printed after the
install finished — the token is still in `.env`, still correct. The screen says
their token is wrong. There is no completed-state guard on `/setup`
(`page.tsx` renders the wizard unconditionally), and `SetupRedirector` only
redirects *to* `/setup`, never away.

The change is a net improvement — before `047dd288` the same operator was
stepped past unlock and walked the whole wizard before anything failed — but it
names the wrong cause, and the wizard already has the right one: it fetches
`setup-status` on mount, whose `completed` field is exactly this state.

`[introduced]` by `047dd288`: at `03a99eea` the same request returned `200` and
the wizard advanced; at `a33d7364` there is no unlock step. B — no declared
invariant covers the message, and the missing `/setup` guard is `[pre-existing]`.

## Trajectory

Read in order: `a9ce7e44` + `03a99eea`, then `047dd288`.

**The production half of round 2 repeats round 1's shape.** `a9ce7e44`
introduced "stat `data/setup_completed` and branch on it" as the mechanism, at
three call sites (`_admin_or_first_run`, `get_setup_status`,
`post_complete_setup`) plus a fourth in `main.py`. `047dd288`'s entire backend
change is **a fifth copy of that branch**, at the one call site round 1 did not
anticipate:

```python
if (config.DATA_DIR / "setup_completed").exists():
    raise HTTPException(status_code=404, detail={"code": "setup_completed"})
```

That is the definition in R-4: a round whose fix adds one more branch handling
one more case the previous round did not anticipate. `03a99eea`, inside round 1,
was the same move at a smaller scale — it added the `if not candidate` guard
after the `bytes`/`str` case was found.

**The other half of round 2 removes state.** `UnlockStep` went from three
`.trim()` calls at three submit sites, with an untrimmed value in between, to
one `.trim()` at the single point where the value enters state. That is four
value-shapes collapsed to one, and it is the loop converging.

So round 2 is not two rounds of pure patching, and I am not calling the design
wrong. What I will name, because only a reader across rounds sees it, is the
shape that produced F1 and will produce the next one: **`data/setup_completed`
is stat-ed inline at six places** —

```
backend/app/main.py:255
backend/app/routers/admin_config.py:223, 271, 299, 322
backend/app/services/drive_seed.py:131
```

— and `config._setup_completed_sentinel()` already exists (`config.py:42`) but
is used by exactly one of them. F1 was a call site that forgot the branch. G1 is
a detector that cannot see a call site. A sixth endpoint is one line away from
the same bug, and the thing that would make it structural — "is setup still
open?" as one predicate the routes depend on, rather than a line each route
remembers to write — has not been added in either round.

That is the supervisor's call, not mine, and not the author's.

## Checked, no finding

- **Does the `404` leak what a `403` would not?** No, in either direction.
  `GET /setup-status` is unauthenticated and returns `{"completed": …}` to
  anyone, so the sentinel state is already public by design; the verify
  endpoint's status code discloses nothing that endpoint does not. The `404`
  body is `{"code": "setup_completed"}` and carries no token. B5 and B6 confirm
  the code is pinned, which is worth having for the frontend contract even
  though nothing security-relevant turns on it.
- **Invariant 4 after the guard.** `test_the_token_is_in_no_response_body` runs
  under the `first_run` fixture, so its two `verify` calls still reach the real
  403 and 200 paths rather than short-circuiting on the new `404`. The
  assertion still holds what it held.
- **The sentinel appearing between verify and the writes.** Unchanged by
  `047dd288`. `_admin_or_first_run` stats per request, so the writes fall to
  `require_admin` and 403; the wizard surfaces the generic error from
  `complete-setup`. Round 1 recorded this and the missing `res.ok` checks as
  `[pre-existing]`.
- **`drive_seed`'s migration firing mid-setup on a restart.**
  `_migrate_setup_sentinel` is guarded by `config._auto_seeded_marker()`
  (`drive_seed.py:125`), which the seeder writes on a fresh install, so a
  restart after the wizard's `PUT /drives` does not create the sentinel. The
  residual case (a fresh install where seeding found no mounts, so no marker)
  predates this change.
- **`B3` ordering.** Moving the guard below the payload validation survives and
  should: a malformed body on a completed install becomes `422` instead of
  `404`, and neither path calls `matches()`, so nothing mints. The current
  order is the better one — it answers before parsing attacker-controlled
  input — but no invariant rides on it.
- **The URL-seeded token reaching the header unchanged.** Held: every header
  assertion in `SetupWizard.test.tsx` walks `renderPastUnlock`, which seeds from
  the URL and asserts `toBe(SETUP_TOKEN)`.
- **`_writes()` entries individually.** B7 and B8 both die on the route-list
  test. B7 also takes `test_every_write_is_accepted_with_the_token` with it,
  because `DELETE /passwords/0` depends on `POST /passwords/append` having
  created index 0 — an ordering coupling inside the list, not a second holder.
- **`rstrip("0123456789")` on the listed side.** It would mangle a future route
  path ending in a digit (`/api/admin/config/s3`), but in the failing direction:
  the two sides stop matching and the test goes red. Noise, not a hole.
- **`routed.discard(("POST", ".../setup-token/verify"))`.** A hard-coded
  exclusion, but a narrow one: a later write under `/setup-token/…` has a
  different path and still has to be listed.
- **`setup_token()` itself.** B18 and B19 are both killed now (round 1's M12 and
  M10). `test_each_mint_is_a_fresh_secret` is a real detector — it declares 8
  distinct values rather than deriving the expectation from what it observed.
- **Prose.** Reviewed only for statements that would lead a reader to a wrong
  code change. `docs/reference/env-variables.md` and `docs/reference/api.md` now
  describe the code as written (round 1's F1 note is resolved). The comment
  added in `UnlockStep.tsx` states why the trim is at `onChange` rather than at
  submit, which is the F3 trap and is the kind `comments.md` allows. The commit
  message's claim about a dropped test is wrong, and that is reported as G3
  because it changes the triage, not as a prose defect.
