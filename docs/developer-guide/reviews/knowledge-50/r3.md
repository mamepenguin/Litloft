## Q2 — what it could break

### Card dropping by capacity: none reachable

`capacity = effective * rowsFor(effective)`: unmeasured (`columns = 0`) → floor 2 → 4; 2 columns → 4;
3 columns → 3; ≥4 columns → ≥4. `CONTINUE_LIMIT` is 3, so no count is below 3. Measured: the grid is
capped at 928px by the page column, and 4 columns need 1060px, so only 2 and 3 occur.

Width sweep (320, 360, 375, 390, 414, 480, 540, 600, 640, 700, 768, 800, 820, 900, 1000, 1024, 1100,
1180, 1280, 1440, 1920): **3 cards rendered at every width**, grid `scrollWidth − clientWidth = 0`,
document `scrollWidth = innerWidth`. 2 columns up to 820, 3 columns from 900. Every card 217px high
at every width (grid stretch). DOM order = row-major visual order (w1, w2 on row 1; w3 on row 2 at 2
columns), so tab order matches reading order. Before measurement the auto-fill template with capacity
4 cannot drop a card either.

### List semantics

No test queries `list`/`listitem` for Continue writing (`NotesPage.test.tsx` has none; the one
`listitem` query in `ClipWebPage.test.tsx` is the clip queue and still passes). Core's two shelves are
not lists either. Not a finding.

## Findings

### H1 [pre-existing] B (test) — nothing holds that Continue writing stays a `SectionRow`

Survivors at `af4cd86`: S3 (`<div className="flex snap-x gap-3 overflow-x-scroll">` in place of
`SectionRow`), S4 (`<div className="grid grid-cols-3 gap-3">`), S5 (put `w-60 shrink-0 snap-start` back
on the card inside the grid). S3 is a sideways shelf again; S5 forces 240px cards into 158–185px tracks
on a phone. The core detector matches the literal `overflow-x-auto` only, and "the shelf shape is
written once" names two core files. Reproduced against the parent with the knowledge suite: the
parent's scroller with `overflow-x-auto` → `overflow-x-scroll` is live as well. No R-0 invariant covers
layout, and jsdom cannot measure S5.

### H2 [introduced] B — Continue writing's count now depends on `SectionRow`'s capacity staying ≥ `CONTINUE_LIMIT`

At 3 columns the capacity is exactly 3. Raising `CONTINUE_LIMIT` to 4 (S7) is caught only because the
request arguments are asserted; the 4th card would then be sliced away silently at 900–1920px widths,
and a test updated along with the limit would stay green, because jsdom never measures and always gets
capacity 4. Not reachable at the shipped limit; nothing in the knowledge code shows the coupling.

### H3 [introduced] B — 640–880px viewports went from 3 columns to 2 + an orphan

The parent's `sm:grid-cols-3` gave three cards in a row from 640px. Now `columnsFor` gives 2 columns
below a 792px container, so at 640, 700, 768, 800 and 820 the third card sits alone on a second row
(measured). This follows core's container-derived rule and the spec's "2 on a phone"; it is recorded
because tablet-width viewports now read as a half-empty second row.

### H4 [pre-existing] B (test) — rendering fewer or reordered history cards is not held

S6 (`rows.slice(0, 2)`) and S8 (reverse) are live at `af4cd86` and, with the knowledge suite, at
`db6ee15`. The Continue writing tests use one history item. Invariant 2 speaks of the request and the
empty case, not of rendering every returned item, hence B.
