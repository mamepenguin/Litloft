### F1 — the test written for AllNotes' first page can never fail
`[introduced]` · invariants 2 and 9 · `frontend/__tests__/AllNotes.test.tsx:412-425`

```ts
expect(screen.queryByRole("link", { name: "Note a" })).toBeNull();
```

is a `<Link>` wrapping the title, the folder and the time, so its accessible
name is never `"Note a"`. Measured: with the gate deleted


— the row's name is `"Note aKnowledge·17:42Knowledge17:42"`.

Reproduction:

|---|---|---|
| `notesWithOpenings(files, openings)` (as shipped) | passes | 1024 pass |
| `const drawn = files;` (gate deleted) | **passes** | 1023 pass — the *other* AllNotes test fails |

### F2 — `_TEXT_MIMES` is a second copy of core's `text` listing rule, in another repository, held by nothing
`[introduced]` · invariant: none (nothing declared covers "a listed note shows its opening") · `app/routers/note_openings.py:33,64`

The endpoint now answers only for `text/markdown` and `text/plain`. The listings
that call it ask core for `type: "text"`, which core resolves in
`backend/app/routers/drives.py:211-241` as

```python
File.mime_type.in_(("text/markdown",))  OR  filename LIKE '%.md' / '%.markdown' / '%.txt'
```

— a mime **or a suffix**, and core's own comment says the suffix arm exists for
"rows whose mime was never recorded… one whose mime was never recorded may well
have been given the wrong `file_type` by the same writer".

So the set the listing returns and the set the endpoint will read are two
different rules that agree today only by arithmetic: in the runtime image
`mimetypes.guess_type` gives `.md`/`.markdown` → `text/markdown` and `.txt` →
`text/plain` (verified in the test image, Python 3.12.14). Any row the listing
admits by suffix whose stored mime is something else gets no opening, silently,
with a 200 and an empty entry.

I could not reach that state today: `File.mime_type` is `nullable=False
DEFAULT 'application/octet-stream'` in the model *and* in every `CREATE TABLE`
in `backend/app/database.py`, and the scanner always writes `classify()`'s
answer. Web clips are `.md` (`clips.py:68`). `.loft` (mime
`application/vnd.litloft.loft+json`, `file_type` `video`) and HTML clips are not
in a `type=text` listing at all, so the allowlist does not cost them anything.

What makes this worth recording is the direction of the coupling: the two rules
live in different repositories, and the one that decides what appears on screen
is core's. If core ever adds a suffix to `_KIND_SUFFIXES["text"]` — which is a
one-line change in a file that has no reason to know this addon exists — every
note of that kind appears in the list with no excerpt and every test stays
green. `review-workflow.md` detector rule 2 is about exactly this shape. The
cheap hold is a test that drives a `.txt`/`.md` row with a mime outside the set
and states which answer is intended.

The same `frozenset` literal is also duplicated inside this addon:
`app/routers/search.py:35` and `app/routers/note_openings.py:33` are
character-for-character identical, in the same package, with nothing importing
the other. `design-decisions.md` accepts duplicated code only where a container
boundary forces it (`frontmatter.py`, `credentials.py`); this one is two modules
in one process.

## What did not break

Checked against the brief's list, all measured at `1d55fdd`:

- **Every call site still gates.** `grep` finds exactly four
  `useNoteOpenings(` call sites (`AllNotes.tsx:73`, `NoteResults.tsx:31`,
  `NotesLanding.tsx:111`, `NotesLanding.tsx:177`) and each is paired with a
  `notesWithOpenings(...)` on the next line. `NoteRows` is only ever handed
  `drawn` / `cards` / `groupNotesByAge(drawn, …)`, never the raw list; the raw
  `openings.text` map it also receives is keyed lookup only. Mutating the
  helper's body to `return [...files]` kills **4** tests across 2 files.
- **Continue writing cannot disappear after being shown, and shows nothing it
  cannot fill.** Empty history → `rows = []` → hidden, as before. Failed history
  → `failed` short-circuits the new condition → the alert renders. Openings
  request fails → the hook marks every asked id answered → `cards = rows` →
  section appears complete. The only path that empties `cards` after they were
  filled is a drive or nickname change, which resets `rows` to `null` on the
  same pass — identical to `2952d94` and `ec68d7e`.
- **The section shift is reduced, not removed.** The commit's own test proves
  the ordering: it awaits `knowledge.notes.recent` and *then* asserts
  `knowledge.notes.continueWriting` is absent. So Recent notes is on screen
  first, and Continue writing is inserted above it when the openings land,
  pushing it down. That is one push where `ec68d7e` had two (heading, then
  cards) and the same one `2952d94` had. The R-0 measurement table already
  records this page-level shift as out of scope, so this is an observation, not
  a finding.
- **The drive header round-trips.** `encodeURIComponent` escapes both `%`
  (`%25`) and `+` (`%2B`), and `unquote` inverts both; `unquote` leaving a bare
  `+` alone is correct here (it is not form-encoded). `%`-containing names are
  covered by the same inverse. Matches the four sibling routers.
- **No guard became unreachable, and none became held.** The three refs are
  unchanged by this commit. `askedDrive.current !== drive` inside `settle` is
  reachable (the closure holds the old drive, the ref is written during the
  render that changes it); `onScreen` is reachable on unmount;
  `setState(NONE)` on a drive change is reachable. All three are still
  survivors (mutation table M8–M10), exactly as at `ec68d7e`. No new state,
  branch or ref was added to the hook.
- **`mime_type` really is in the response the gate reads.** Core's
  `POST /api/internal/files/bulk` returns `file_to_response(...)`
  (`backend/app/routers/internal.py:555`), whose `mime_type` field is populated
  (`backend/app/schemas.py:1026`). `app/routers/search.py:87` already filters the
  same field off the same call in production, so the gate is not fed by the
  fake alone.
- **Trash/missing notes cost nothing.** `/files/bulk` applies
  `active_file_filter()`, so such ids land in `not_found`, are never read, and
  their rows are still drawn (the hook answers every asked id). Same as
  `ec68d7e`.

## Trajectory — `2952d94`, `ec68d7e`, `1d55fdd` read in order

**The loop is converging, and the answer has not changed from round 2's.** One
qualification is below, for the supervisor rather than as a finding.

- **`2952d94`** carried a prediction about time — *the listing is complete, so
  draw it all at once*. It cost a nullable return (`Record<…> | null`), a
  derived `missing` array, an effect-cleanup `cancelled` flag, and four

  nullable return, `missing` and `cancelled` are gone; the four branches
  collapse into one expression. Its backend half added guards — `unquote`, the
  drive filter, `OPENING_BYTES`, two widened `except` clauses — each answering
  something the round-one code had not considered at all, not a further case of

  one `notesWithOpenings` call; `ContinueWriting`'s early-return condition is
  *replaced*, not extended. The hook gained no fourth ref, no new state and no

  Of the 174 inserted lines, 132 are tests. The production diff is about 40
  lines.

Both things round 2 flagged as where a further round would go wrong were
answered in the converging direction: the four call sites that were "drifting
