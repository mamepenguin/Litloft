## F1 — Pressing "Show more" removes every row already on screen until the new page's openings arrive
`[introduced]` · invariants 7 and 2 · `addons/knowledge/frontend/AllNotes.tsx:140`, `addons/knowledge/frontend/NoteResults.tsx:87`

`useNoteOpenings` returns `null` whenever *any* id in the listing is unanswered, and
both list components render nothing at all in that case
(`{openings === null ? null : …}` / `{openings !== null && <NoteRows …/>}`).
Appending a page puts 30 unanswered ids into the listing, so the hook goes back to
`null` and **the 30 rows already drawn unmount**. The list is empty for a whole
round trip, then all 60 rows appear. On the real app that is the page collapsing
under the user's finger, scroll position included — strictly worse than the growth
this change set out to remove, and it is the same shape for search results.

Reproduction (temporary probe hosted in the linked test path, removed afterwards):
render `NotesPage` with `view=all`, two pages of 30 from `getDriveFiles`, and
`fetchNoteOpenings` resolved for page 1 but deferred for page 2. Click
`knowledge.notes.showMore`, flush microtasks, count the rows:

| tree | rows on screen while page 2's openings are in flight |
|---|---|
| `2952d94` | **0** |
| `34b0743` (parent, same probe, per-row excerpt fetch left pending) | **60** |

Nothing in the suite holds this: `NotesPage.test.tsx` never mocks
`fetchNoteOpenings`, so in the tests it rejects immediately and the gate is never
observed closed for a second page.

A shape that keeps invariant 2 without this: hold back only the ids that are not
yet answered, i.e. render the rows whose openings are in hand and let a further
page's rows wait for their own answer (`files.filter(f => answered.has(f.id))`),
rather than gating the whole listing on the newest id.

## F2 — The endpoint reads whole files into the worker; the old path read 1 KB per note
`[introduced]` · invariant: none declared (see "anything missing") · `addons/knowledge/app/internal_client.py:173-186`, `app/routers/note_openings.py:51-58`

`get_file_content` issues `GET /api/files/{id}/stream` with **no `Range` header** and
does `r.text`, so the addon pulls the entire body into memory and then keeps the
first 1024 characters. Core's stream route only short-circuits to a small buffered
body for `text/markdown` / `text/plain` under 1 MB; everything else is streamed in
full, and the addon buffers all of it.

The caller chooses the ids: `POST /api/addons/knowledge/note-openings` with 200
arbitrary readable ids (a video drive, say) makes the knowledge worker read 200
whole files, 8 concurrently, each with a 30 s client timeout — while the core
proxy has already given up at its 15 s default, so the reads outlive the request
that asked for them. That is the worker wedged and the core saturated from one
`curl` by any viewer who can reach the addon on a drive.

Measured with `httpx.MockTransport` against the real `InternalClient`
(temporary `tests/test_zz_review_probe.py`, removed afterwards):

```
URL: http://backend:8000/api/files/vid1/stream
RANGE HEADER: None
BYTES READ INTO MEMORY: 50000000
```

At the parent this could not happen: the read lived in the browser and was capped
at the window it needed — `useNoteExcerpt.ts:24` sent
`Range: bytes=0-${EXCERPT_WINDOW_BYTES - 1}` (1024 bytes). The core frontend's own
text reader keeps an explicit cap for exactly this reason
(`frontend/src/lib/fileContent.ts:33-37`: "so a compromised upstream or a MITM with
a multi-GB response can't exhaust memory"), and core's Internal API content route
carries `CORE_INTERNAL_CONTENT_MAX_BYTES` plus a mime allowlist
(`.claude/rules/design-decisions.md`, "Internal API"). This new read path has
neither a byte bound nor a mime check.

Cheapest fix: send `Range: bytes=0-<n>` on this read (a dedicated
`get_file_opening`, so the webclip caller keeps full-body semantics), and/or refuse
ids whose mime is not a text note.

## F3 — Every gate that implements invariant 2 can be deleted and the suite stays green
`[introduced]` · invariant 2 (the thing the change is for) · `AllNotes.tsx:140`, `NoteResults.tsx:87`, `NotesLanding.tsx:112`, `NotesLanding.tsx:175`

Four separate mutations, each removing one component's "wait for the openings"
condition, all **survive** `pnpm vitest run src/addons/knowledge` (1018/1018 pass
each time):

- `AllNotes.tsx` `{openings === null ? null : …}` → `{false ? null : …}`
- `NoteResults.tsx` `{openings !== null && (…)}` → `{true && (…)}`
- `NotesLanding.tsx` `const rowsReady = page !== null && openings !== null` → `page !== null`
- `NotesLanding.tsx` `… || openings === null) return null` → drop the clause

Only `useNoteOpenings.test.tsx` holds the hook's own contract, and nothing connects
it to a rendered row: `NotesPage.test.tsx` does not mock `fetchNoteOpenings`, so in
the suite the request rejects at once and the gate is never seen closed. This is
the same blind spot F1 fell into — a test of "a row is drawn with its excerpt
already present, and is not drawn before" would have caught both. `NoteRow.test.tsx`
passes `openings` in directly, so it cannot see the gate either.

## F4 — A further page asked for early re-asks the previous page's ids and throws the first answer away
`[introduced]` · invariant 4 · `addons/knowledge/frontend/useNoteOpenings.ts:39-56`

`missing` is derived from `answered.asked`, which is only written when a request
*settles*. `key` therefore changes while the first request is in flight, the effect
cleanup marks that response `cancelled` (it is discarded even though it arrived),
and the replacement request asks for page 1's ids again together with page 2's.

This is reachable without any timing trick, because **"Show more" is rendered
outside the openings gate** (`AllNotes.tsx:166`): the button is on screen while the
rows are hidden, so a user who presses it during the first round trip takes this
path. Probe on `2952d94` (`NotesPage`, `view=all`, 30+30, first openings deferred,
Show more pressed before it resolves):

```
IDS PER REQUEST: [30,60]   TOTAL IDS ASKED: 90
```

60 notes, 90 ids read, and page 1 read twice on the server (F2 makes each of those
reads a whole file). The existing unit test misses it because it waits for the first
answer before appending the page.

## F5 — The landing's two sections read the same note twice
`[introduced]` · invariant 4 (letter kept, intent bent) · `NotesLanding.tsx:111` and `:174`

`ContinueWriting` and `RecentNotes` each own a `useNoteOpenings`, so the landing
issues two requests, and a note that is both recently-written and recent is fetched
by both. Probe with `nickname` set, watch history `[w1, r1]` and recent `[r1, r2]`:

```
LANDING REQUESTS: [["w1","r1"],["r1","r2"]]
```

Two requests match "one per listing", so this is not a breach; it is worth knowing
that the before/after measurement was taken with no `Continue writing` section (no
nickname), which is why it shows one request.

## F6 — The drive header is required and then plays no part: drive A's page reads drive B's note bodies
`[introduced]` · invariant 1 not broken; `design-decisions.md` "A drive is a security boundary" · `app/routers/note_openings.py:32,36`

`x_hv_drive` is checked for presence and never used again. `filter_file_ids` sends only
the ids, and core's filter keeps anything in **any** drive the caller has unlocked
(`backend/app/routers/internal.py:472-484` filters by `accessible_drive_names`, not by a
requested drive). So `POST /api/addons/knowledge/note-openings` with `X-Lit-Drive: photos`
happily returns the opening 1024 characters of notes in `work`:

```
DRIVE A : {'openings': {'in_other_drive': 'Body of a file in a different drive.'}}
OTHER   : {'openings': {'in_other_drive': 'Body of a file in a different drive.'}}
FILTER CALLS (no drive anywhere): [['in_other_drive'], ['in_other_drive']]
```

No privilege escalation — the caller can read those files directly — so this is not an
invariant-1 breach. It is a cross-drive read path added inside a drive-scoped addon,
which is the thing the drive rule exists to stop, and it is one line to close: keep only
the ids whose `drive` equals the header (the addon already has `get_file`/`bulk-state`
shapes for that), or state in the code why the endpoint is deliberately drive-blind.

## F7 — One transport error loses every opening in the listing, and F2 makes that the expected failure
`[introduced]` · invariant 5 satisfied (rows appear), excerpts all lost · `app/routers/note_openings.py:51-60`

`opening()` catches `InternalAPIError` only, and `asyncio.gather` is called without
`return_exceptions`. An `httpx.ReadTimeout` / `ConnectError` — exactly what the 30 s
client timeout produces for the multi-gigabyte read in F2 — escapes the handler:

```
RAISED OUT OF THE HANDLER: ReadTimeout slow
```

Ten notes, one slow, and the request 500s: all ten rows lose their excerpt. The
per-row path it replaced lost one row's excerpt. `tests/test_note_openings.py` covers
only `InternalAPIError`.

## F8 — `POST /note-openings` is missing from the addon's endpoint table

## F9 — Nothing holds the endpoint's fail-closed behaviour when the access filter itself fails
`[introduced]` · invariant 1 · `app/routers/note_openings.py:44-47`

The code is right (`InternalAPIError` → 502, nothing read). But the mutation that
makes it fall through —

```python
    except InternalAPIError:
        readable = body.file_ids
```

— **survives** `tests/test_note_openings.py` (6 passed). That is the one mutation on
this endpoint that turns a core outage into "return every id's text unchecked", and
the only invariant the file was written to defend. One test: filter raises, expect
502 and `OpeningsFake.fetched == []`.

## Smaller things, no fix asked for

- `viewer_id` is resolved as a dependency and never used (`note_openings.py:30`).
  `get_optional_viewer_id` has no side effect, so the parameter is dead. `[introduced]`
- The id cap boundary is untested: `>` → `>=` survives, since no test posts exactly
  `MAX_IDS`. Harmless direction, but the cap is one of the endpoint's two guards. `[introduced]`
- `_PARALLEL_FETCHES` and the semaphore are untestable as written — removing the
  semaphore entirely changes nothing any test can see. `[introduced]`
- `openings={fid: text for pair in results if pair for fid, text in (pair,)}`
  (`note_openings.py:61-63`) is `dict(p for p in results if p)` written the long way. `[introduced]`
- React's StrictMode double-invokes the effect in dev, so every listing sends the
  request twice there — with F2, twice the file reads. Production builds do not. `[introduced]`
- Prose that would mislead a reader (remedy: delete):
  - `useNoteOpenings.ts:21-22` "a page appended to the listing costs one request for
    its own ids" — F4 shows the reachable case where it costs a request for its own
    ids *plus* the previous page's.
  - `app/routers/note_openings.py:1-5` — the module docstring narrates the previous
    design and then describes the frontend's drawing rule from a backend router,
    which `comments.md` rules out on both counts and which F1's fix would falsify.
- No addon router checks per-drive policy (`is_feature_enabled` appears nowhere in
  `app/routers/`), and `/note-openings` follows its siblings in declaring no
  `addon_feature` in `manifest.json`, so a policy-off drive can still read note
  openings through the proxy. `[pre-existing]`, addon-wide.

## Is anything missing from the invariants list?

Yes — four things, and the two worst findings fall in the gaps:

1. **A bound on what the endpoint reads.** Nothing in the list says a note's opening
   costs a bounded read, so F2 (whole files pulled into the worker, any mime, 200 per
   request) breaks no declared invariant while being the most damaging thing here.
   Suggested wording: *"Fetching a listing's openings reads at most a few kilobytes
   per file, whatever the ids point at."*
2. **Rows already on screen stay on screen.** Invariant 2 is about a row's height
   *after* it appears and 7 is about a row's contents, so F1 (every drawn row
   unmounting when a page is appended) sits between them. Suggested wording:
   *"A row that is on screen is never removed by a later page or a failed opening
   fetch."*
3. **Drive scoping.** Invariant 1 is about readability, not about the drive in
   context, so F6 is outside the list. Suggested wording: *"The openings returned are
   those of files in the drive the request names."*
4. **The blast radius of one file failing.** Invariant 5 covers the request failing
   as a whole; F7 (one transport error losing all ten excerpts) is neither that nor
   forbidden. Suggested wording: *"One file that cannot be read costs that row's
   excerpt and no other's."*

Invariant 4 is also worth tightening to say what happens when the listing changes
while a request is in flight — F4 lives in exactly that hole.
