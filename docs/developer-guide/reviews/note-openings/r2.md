## New findings

### N1 — "Continue writing" now shows its heading over nothing, then grows when the cards arrive
`[introduced]` · invariants 2 (by its spirit; its letter says *row*), 9 satisfied · `addons/knowledge/frontend/NotesLanding.tsx:112,115`

`ContinueWriting`'s early return lost its openings clause:

```
- if (!failed && (rows === null || rows.length === 0 || openings === null)) return null;
+ if (!failed && (rows === null || rows.length === 0)) return null;
```

so once the watch-history rows land the section renders — heading, and a
`SectionRow` holding `cards`, which is empty until the openings answer.
Measured with the same probe at both SHAs (`nickname` set, history `[w1]`,
recent `[r1,r2]`, `fetchNoteOpenings` never resolving):

| | `2952d94` | `ec68d7e` |
|---|---|---|
| "Continue writing" heading on screen | **absent** | **present** |
| cards under it | 0 | 0 |

The landing therefore draws `Find` → `Continue writing` (empty) → `Recent
notes`, and when the openings arrive the cards appear and push `Recent notes`,
the clip entry and the connections entry down. That is the shift the change set
out to remove, relocated from the row to the section, and it is the one section
whose visibility rule changed in this commit — `RecentNotes` and `AllNotes`
already rendered their heading and count outside the gate at `2952d94`.

Invariant 2 is written about a row's height, and invariant 9 (a drawn row is
never removed) holds, so this breaks no declared invariant as written. It is the
kind of thing R-5 is for.

A shape that keeps the per-row draw without this: keep the section hidden while
`rows` is non-empty and `cards` is empty, i.e. restore the early return with
`cards.length === 0` in place of `openings === null`. Costs nothing on the
second visit and nothing when the request fails, because a failure marks the
ids answered.

### N3 — nothing in the suite holds "a row appears with its opening already in it"

### N4 — the opening-length test is asserted against the constant it is meant to pin
`[introduced]` · invariant 6 · `tests/test_note_openings.py` (`test_only_the_opening_is_read_and_returned`), `app/routers/note_openings.py:28-30`

```python
from app.routers.note_openings import OPENING_BYTES, OPENING_CHARS
...
assert OpeningsFake.fetched == [("a", OPENING_BYTES)]
```

The expected value is read from the module under test, so it moves with any
change to it. Mutation `OPENING_BYTES = OPENING_CHARS` (one byte per character
instead of four): `want=kill`, **survived** — 443/443, and `tests/test_note_openings.py`
alone 10/10.

What that mutation does in production: the router asks core for 1024 *bytes* and
then cuts the decoded text to 1024 *characters*, so a Japanese note (3 bytes per
character in UTF-8) returns about **341 characters** instead of 1024, and an
emoji-heavy one about 256. Nothing says so; the excerpt just gets shorter.

`review-workflow.md` detector rule 5 — *never build the expected value out of the
observation*. The literal `4096`, or an assertion that a 4096-byte CJK body
survives `OPENING_CHARS` characters of decoding, would hold it.

(The multiplier itself is right: 4 is the maximum UTF-8 encoding length, and the
boundary is safe — a partial character can only begin at byte ≥ 4093, which is
character index ≥ 1024, so the `U+FFFD` that `errors="replace"` produces is
always cut off by `text[:OPENING_CHARS]`.)

### N5 — the `unquote` that makes the new drive filter work on a non-ASCII drive name is held by nothing
`[introduced]` · invariant 10 · `app/routers/note_openings.py:50`

Mutation `drive = x_hv_drive` (drop the `unquote`): `want=kill`, **survived** —
443/443.

It matters because the encoding is real, not hypothetical. The frontend sends
`"X-Lit-Drive": encodeURIComponent(drive)` (`frontend/src/lib/api.ts:242`,
`AddonSlotsProvider.tsx:116`), and core's proxy forwards the **raw** header —
`_filter_request_headers` copies `request.headers` through with only the
hop-by-hop and viewer keys touched (`addon_proxy.py:244-269`); the decoded value
it computed for its own access check never reaches the addon. So for a drive
named e.g. `仕事`, `x_hv_drive` is `%E4%BB%95%E4%BA%8B`, which matches no
`f["drive"]`, `in_drive` is empty, and **every note in that drive silently loses
its opening** — the endpoint returns `{"openings": {}}` with a 200.

Every sibling router in this addon carries the `unquote` and a comment saying why
(`search.py:41-44`, `clips.py:98`, `distill.py:55`, `active_summary.py:42`). This
is the first one where the decoded value is compared against data rather than
only used to scope a query, which is what makes the mismatch silent instead of
loud. One test posting `X-Lit-Drive: %E4%BB%95%E4%BA%8B` with
`drive_of = {"a": "仕事"}` holds it.

### N6 — the second core round trip can 500, and only the first layer's widening is tested
`[introduced]` · invariant 5 · `app/routers/note_openings.py:55-57`

Mutation: narrow the outer handler back to `except InternalAPIError as e:`.
`want=kill`, **survived** — 443/443. `test_when_the_access_filter_fails_nothing_is_read`
raises `InternalAPIError`, so the `httpx.HTTPError` half of the widening — the
half round 1 raised as F7 — is unheld at this layer while its twin inside
`opening()` is held (B5 is killed).

The code is right, so this is a test gap rather than a defect. It is worth
closing because this commit *added* the layer: `fetch_bulk_files` is a second
synchronous core round trip on the path of every listing, and a `ReadTimeout`
there escapes as a 500 rather than the 502 the endpoint means to answer. The
client behaviour is the same either way (`fetchNoteOpenings` rejects,
`settle({})`, rows appear without excerpts), so invariant 5 holds — which is
exactly why nothing notices.

### N7 — the drive is re-derived with the fattest shape the client offers
`[introduced]` · invariant: none · `app/routers/note_openings.py:56`, `app/internal_client.py:358`

`fetch_bulk_files` → `POST /api/internal/files/bulk` → `file_to_response` for
every id: 22 fields including `tags`, `subtitles`, `trust_tier`, thumbnail URL
and every timestamp, for up to `MAX_IDS` = 200 files, so that one field
(`drive`) can be read off each.

`fetch_bulk_state` already exists on the same client
(`internal_client.py:331`) and returns `{"statuses": [{"id", "drive", "state"}…]}`
— the two fields this code wants and nothing else.

Not a defect: `File.tags` is `lazy="selectin"` (`backend/app/models.py:115-116`),
so it is one extra query for the batch rather than N+1, and `/files/bulk` applies
`active_file_filter()` while `/files/bulk-state` does not, which is a genuine
advantage here (trash and missing ids land in `not_found` and are never read —
handled correctly, since `in_drive` is built only from `meta["files"]`).
Recording it because the endpoint now makes two core round trips before it reads
a byte, and this is the larger of them.

### N8 — the endpoint still returns 1024 replacement characters for a binary file, and now holds the data to refuse it
`[introduced]` · invariant: none (8 is satisfied) · `app/internal_client.py:186`, `app/routers/note_openings.py:63-69`

`r.content[:max_bytes].decode("utf-8", errors="replace")` turns the first 4 KB of
anything into text. Round 1's F2 proposed two remedies — bound the read, **and/or**
refuse ids whose mime is not a text note; the triage took the first. So a caller
who posts 200 video ids **from their own drive** now gets 200 × 1024 `U+FFFD`
back, as "openings".

The blast radius is small — the reads are bounded (that is invariant 8, and it
holds), the caller can read those files directly, and the core UI never sends
non-text ids (every caller lists with `type: "text"`). It is listed because the
missing half is now one `and` away: `fetch_bulk_files` returns `mime_type` in the
same response the drive is read from, so `if f.get("drive") == drive and
f.get("mime_type") in _TEXT_MIMES` costs nothing. `search.py:35` already declares
that set.

## Trajectory — `2952d94` then `ec68d7e`

**This round removes a prediction. It does not add one.**

`2952d94` predicted something about time: *the listing is complete, so draw it
all at once*. That prediction cost a "not ready" value (`Record<…> | null`), a
derived `missing` array, an effect-cleanup `cancelled` flag, and **four**
call-site branches (`openings === null ? null : …`, `openings !== null && …`,
`rowsReady`, and the `|| openings === null` in `ContinueWriting`'s early
return).

`ec68d7e` deletes all of it. The hook's return type has no "not ready" state
left, the `cancelled` flag is gone, and the four branches collapse into one
expression repeated at each site (`files.filter(f => openings.answered.has(f.id))`).
What replaces the prediction is a fact the component already has — *is this
row's answer in hand?* Round 1's F1 and F4 were both consequences of that
prediction, and they fall out together rather than being handled one at a time.

The backend side does add: a second core round trip, a new client method, a new
constant. Those are **guards**, not predictions about timing, and each answers a
finding the round-1 code did not anticipate at all (it required the drive header
and then never read it; it had no byte bound). They are not the round-one
prediction being patched with a further case.

So by the test in `review-workflow.md` — *does each round add a branch, a state
or a prediction that the round before it also added?* — the answer here is no:
this is the round that removes one, which the rule calls the loop converging.

Two things I would watch if a third round happens, neither of them a C:

- The hook now holds three refs (`asked`, `askedDrive`, `onScreen`), one of
  which is mutated during render. Three of the four guards built out of them are
  held by nothing (FM6, FM7, FM9). That is where a further round would most
  likely find something, and the fix for it would be *removing* a ref, not
  adding a fourth.
- `files.filter(f => openings.answered.has(f.id))` is now written out at four
  call sites. N1 is already one of the four drifting from the other three.
