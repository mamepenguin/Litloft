## Findings

### F1 [introduced] bucket A — the backfill deletes a relation touching a note it could not read (invariant 7)

`sync_markdown_file_relations(..., claim_unmarked=True)` for a readable Markdown
file S deletes every unmarked `(S, X)` row that S's content does not link. The
unread guard exists only in `_remove_seeds_duplicated_by_markdown`; the claim in
the per-note loop never consults `unread_ids`. The pre-change knowledge addon
seeded `(source, note)`, and a source can be a Markdown file (note-from-file on a
`.md`, a capture or Ask citation of a note). When the citing note N is unreadable,
S's claim deletes `(S, N)` and N's own sync never writes `(N, S)`.

Reproduction: `src.md` "No links.", `note.md` with `source_file_ids: [src]`,
legacy `(src, note, related)`; make `note.md` unreadable (deleted on disk, over
1 000 000 bytes, or not UTF-8); run the backfill. Result: returns `False`, and no
row joins src and note (expected `(src, note)` kept). All three variants fail.

User-visible: the note and its source drop out of each other's Related files.
For the unmounted case it heals on a later start once N is readable (the sentinel
is not written). For an over-1 MB or non-UTF-8 note it never heals, because N is
never read — see F4.

### F2 [introduced] bucket A — a save landing inside the backfill's read→commit window is overridden (invariant 3)

The backfill reads the file, then resolves and commits the sync, without the
per-file text lock `PUT /content` holds and without re-checking the content.
Reproduction (deterministic via monkeypatch of `_read_markdown`): legacy
`(note, target)`, `note.md` "See [[target]]."; the patched reader returns the old
content and, before returning, a `PUT` saves "No links any more.". After the
backfill `note.md` has no link, yet `(note, target)` exists with
`origin = markdown`. It stays until the next save of note. The window is one
file's resolve queries during a one-time pass started after the full scan, so it
is narrow; it is an invariant break, not a likely one.

### F3 [introduced] bucket B — a note trashed or missing at upgrade keeps legacy outgoing rows that no later save removes

The backfill selects `active_file_filter()` notes only, but writes the sentinel
regardless of inactive Markdown files. Their legacy `(note, X)` rows stay
`origin = NULL`, and after restore/recovery the save path no longer deletes
unmarked rows.

Reproduction: `note.md` linking video V with legacy `(note, V)`; set
`deleted_at` (or `missing_since`); run backfill (returns `True`); clear the state;
`PUT` note without the link. 07de9066: `(note, V)` remains. e09ea968 (no
backfill): removed. Both `trash` and `missing` variants.

User-visible: after restoring a note from trash, or after a moved-away note is
recovered, removing a link from it leaves the target in Related files
permanently (no public delete endpoint). No R-0 line covers it (invariant 3 only
counts `markdown` rows), hence B; see "missing from the list". The existing test
`test_trashed_note_is_not_resynced` asserts the first half of this as intended.

### F4 [introduced] bucket B — the sentinel can be permanently unreachable, and each rerun deletes Internal API rows written since the previous start

`unread_ids` includes any active Markdown row whose content cannot be read, and
the sentinel is written only when it is empty. Permanent causes observed:
- a `.md` over 1 000 000 bytes or not valid UTF-8 (F1 variants return `False`);
- a row on a drive no longer in `drives.json` (`get_drive_path` raises
  `ValueError`, caught as unread; the scanner never visits that drive, so the rows
  stay active).

On every start the pass then resyncs every readable note with
`claim_unmarked=True`, so an unmarked `(N, X)` row written through
`POST /api/internal/file_relations` since the last start is deleted if N does not
link X — the exact class of row the change promises survives saves.

Reproduction: add an active `.md` File row on drive `retired` (not configured);
run backfill → `False`, no sentinel; `POST /api/internal/file_relations`
`(note, video)` where note.md has no links → 201; run backfill again → `False`,
and `(note, video)` is gone.

Bucketed B because no shipped writer at 1764bd6 creates `(markdown note, X)` rows
through the Internal API (knowledge no longer writes any; intelligence and
media_import could not be read, see below), and invariant 7's "second run changes
nothing" presumably means with no writes in between. If an intelligence writer
exists (e.g. promoted suggested relations), this becomes an A against invariant 2's
intent.

### F5 [introduced] bucket B — at the reviewed core SHA the knowledge submodule is still pinned to 143c562, which breaks invariant 9

`git -C wt-core submodule status` at 07de9066: `143c562 addons/knowledge`. That
addon still seeds `(source, note)` after creating the note, while core's create
sync now also writes `(note, source)`.

Reproduction (`test_old_knowledge_seed_is_removed_with_the_citation`): POST
`note.md` citing S → 201; Internal API POST `(S, note)` (what 143c562 does) → 201;
PUT the note without the citation. 07de9066: `(S, note)` remains; e09ea968: no row.

The spec orders the knowledge PR first and the bump in the core PR, and the main
checkout shows `M addons/knowledge`, so this is a sequencing check, not a design
defect: the bump must land in the same core PR. Two consequences if it does not:
invariant 9 fails for every new note, and the one-time backfill cannot clean the
duplicates because its sentinel is already written by then.

### F6 [introduced] bucket A (test gap) — nothing holds the backfill's wiring at startup or its position after the scan

M24 (start only `scan_all_drives`, never the backfill) and M23 (run the backfill
before the scan) both live in the repo suite: `conftest.py` stubs
`_run_relation_origin_backfill`, and nothing calls
`_scan_then_backfill_relation_origin`. The order is load-bearing: rules 1 and 5 of
the wiki resolver read `File.md_id` / `File.md_aliases`, which the scanner
projects (`scanner.py` sets both). Run before the scan with
`claim_unmarked=True`, a legacy `(N, T)` row for an id- or alias-form link to a
file the scan has not projected yet is claimed and deleted. New function, so
[introduced] without a parent run.

### F7 [introduced] bucket A (test gap) — invariant 8 on the create path has no detector

M22 (remove the try/except in `_sync_created_markdown_relations`, so a sync error
propagates) lives in the repo suite. Killed only by the review test
`test_create_sync_failure_keeps_file` (sync monkeypatched to raise → expect 201
and the file row + bytes present). Under M22 the request returns 500 after the
file row has committed, so a knowledge caller treats the create as failed
(`notes.py`/`distill.py` map it to 502) while the note exists, and retries write
`name-2.md`.

### F8 [introduced] bucket A (test gap) — the backfill's `file_id_b in synced_ids` guard has no detector

M12 (drop `row.file_id_b in synced_ids`) lives in the repo suite and in the
review tests. Under M12 an unmarked `(S, N)` is deleted when N is unreadable but a
marked `(N, S)` already exists (written by a save of N after the upgrade, before
the pass reached it). That deletes a row touching an unread file (invariant 7).
Reachability is low (needs a save and then N becoming unreadable before the pass),
so this is a detector gap rather than a live defect.

### F9 [introduced] bucket B — a note whose sync raises during the backfill does not block the sentinel (M11 lives)

M11 (drop `unread_ids.add(note.id)` in the `except` branch) lives. The code does
add it, so there is no defect today; nothing tests that a sync exception keeps the
sentinel unwritten and keeps the a-side dedupe guard. Recorded for the ledger.

### F10 [introduced] bucket B — knowledge `notes` dedupe of `source_file_ids` has no detector (K3 lives)

K3 (iterate `body.source_file_ids` instead of `dict.fromkeys(...)`) lives in the
knowledge suite. `note_origin_sources` has primary key
`(drive, note_path, source_file_id)`, so a duplicate id would raise
`IntegrityError` on commit, after the `.md` was written, and return 500. At
143c562 the second relation POST returned 409 and was dropped, so duplicates never
reached the insert. The code dedupes correctly now; only the test is missing.

### P1 [pre-existing] bucket B — Internal API `GET /file_relations?file_id=` returns both directional rows for mutual links

Still true at 07de9066 (unchanged `internal.py`; spec `## Checked, no action`).
Knowledge's own seeds no longer add a second row, so the doubling is now limited
to notes that link each other.

### P2 [pre-existing] bucket B — stale `(source, note)` seeds the note no longer cites are left

Still true for non-Markdown sources (`test_seed_the_note_no_longer_cites_is_kept`).
Not true for Markdown sources: the backfill's claim deletes `(S.md, N)` whenever
S does not link N, whether or not N still cites S (that is F1's mechanism when N
is unreadable, and a silent, correct-looking cleanup when N is readable and still
cites S, because N's sync writes `(N, S)`). The Checked-no-action entry therefore
describes only part of what the pass does.

## Knowledge callers and the cross-drive question

- `notes.create_note`: only ids whose bulk-state row has `drive == X-Lit-Drive`
  reach `note_origin_sources` (K1 killed). Trash/missing same-drive sources are
  recorded, as they were when the relation POST accepted them. Unknown ids land in
  `not_found` and are dropped. No cross-drive leak found. The wire shape matches
  core `files_bulk_state` (`statuses[].{id, drive, state}`).
- `distill` and `note_from_file` reject a cross-drive source with 400 before
  writing, and both write `source_file_ids: [source]` into the frontmatter, so
  core's create sync derives `(note, source)`; core also filters targets by drive.
- `captures.commit_captures` (`new` and `quick`) calls `create_note` with content
  from `build_capture_note`, which writes `source_file_ids` into the frontmatter.
  Appending to an existing note goes through `PUT /content` and `append_captures`
  merges the ids, so the save sync picks them up.
- **Not verified:** the `origin="ask_answer"` caller of `POST /notes` (the Ask →
  Knowledge save flow) composes `content` outside both reviewed trees
  (intelligence; `addons/intelligence` is not checked out in `wt-core`). At
  143c562 its citations became relations through the seed regardless of content.
  At 1764bd6 they become relations only if the composed content carries
  `source_file_ids` frontmatter or `loft://` links. If it carries neither,
  invariant 9 fails for every Ask-saved note. Needs a read of the intelligence
  frontend at the pinned SHA.

## Is anything missing from the R-0 list?

1. **Inactive notes at upgrade (F3).** Suggested: "A note restored from trash or
   recovered from missing reconciles the links it had before the upgrade on its
   next save" — or the deliberate opposite, stated.
2. **Rows written after the upgrade (F4).** Suggested: "The backfill never deletes
   a row created after the `origin` column exists", or "the sentinel is written
   even when some Markdown files are permanently unreadable". As written, invariant
   7's "second run changes nothing" is silent about writes between runs, and the
   sentinel can be unreachable forever.
3. **Concurrency (F2).** Suggested: "A save that completes while the backfill runs
   is not overridden by it."
4. **Core/addon pairing (F5).** Invariant 9 is only true with the submodule bump in
   the same core PR; worth stating as a merge condition, since the one-shot pass
   will not repair it later.
5. **Ask-saved notes.** Invariant 9 says "knowledge creates a note citing S"; it
   should name the Ask save path explicitly, since that is the one caller whose
   content this review could not see.

## Trajectory: d7cd07d9 → 07de9066

d7cd07d9 inferred who wrote a row from its direction (`file_id_a == note` means
the note's links wrote it). That assumption failed because knowledge wrote
`a = source`. 07de9066 removes that assumption **for the save path**: the writer
is recorded (`origin`), the sync touches only rows it recorded, and the
conflicting writer (knowledge seeding) is removed rather than special-cased. That
part is a removal, not a patch: the save sync has fewer branches than a
direction-plus-exceptions design would.

It does add a state (`origin` NULL / `markdown`), an adopt branch, a
`claim_unmarked` mode, and a migration pass with its own predictions (the unread
set, the sentinel, and "an unmarked `(T, N)` mirrored by a marked `(N, T)` is a
seed"). The adopt branch and the listing dedupe are consequences of the model, not
per-case patches. The backfill is where the old assumption comes back:
`claim_unmarked=True` treats every legacy unmarked `a = N` row as written by N's
links — exactly d7cd07d9's direction-implies-writer rule, applied to the rows
written before `origin` existed. Four of the five behavioural findings here (F1,
F2, F3, F4) are in that pass, and F1 is the same failure as R1 F1 in a new place
(a knowledge seed with a Markdown source is claimed by the wrong file). So: the
redesign removes the failed assumption from the steady state and reintroduces it
in the one-time migration, whose predictions are now what is being found wrong.
