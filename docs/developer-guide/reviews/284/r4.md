## 2. Findings

### J1 [introduced] bucket B — a legacy link row whose link the note's first post-upgrade save removes is never removed, and no path can remove it

`test_legacy_link_row_goes_when_first_save_removes_the_link[video,note]`:
`note.md` links T by `loft://`, legacy unmarked `(note, T)`; startup pass; PUT
note without the link → `(note, T)` remains at 853bdceb (FAIL x2), removed at
e4645012 (pass x2, the resync adopted it at startup).

The flip touches only rows whose `b` is a Markdown note that cites `a`; the legacy
rows the old save sync wrote are `a = note`, so they stay unmarked until a save
*that still links the target* adopts them. A save that removes the link does not
adopt, and invariant 2 forbids it from deleting an unmarked row. There is no
public DELETE for relations (`files.py` has only `GET /{file_id}/relations`), so
the viewer keeps seeing the removed link in the related panel indefinitely.

User-reachable on the measured copy: 16 unmarked rows with `a` = Markdown
(`Photography Hub.md` → four notes, `Files Link.md` → `ADDON-DEVELOPMENT.md`, 10
to media). Removing any of those links in the editor after the upgrade leaves the
row. This is F3 extended from "inactive at upgrade" to every note, and the
Checked entry "marked on the note's next save" holds only for a next save that
keeps the link. No R-0 line covers legacy `a = N` rows (invariants 2/3 speak of
NULL and marked rows separately), hence B; it is the kind of B that is grounds for
the supervisor to consider a revision.

### J2 [introduced] bucket B — a Markdown source's own link row is consumed by the flip when the note also cites the source

`test_markdown_source_link_row_survives_note_dropping_citation[loft,wiki]`: `s.md`
links `note.md` (`loft://` or `[[note]]`), the old sync wrote `(s, note)`;
`note.md` has `source_file_ids: [s]`. Startup pass → 853bdceb replaces `(s, note)`
with `(note, s, markdown)`. The note drops its citation and saves → no row joins
the two, though `s.md` still links `note.md` (FAIL x2; pass x2 at e4645012, whose
resync of `s` adopted the row before the dedupe).

`test_row_written_by_unreadable_markdown_source_is_not_changed`: same with `s.md`
not UTF-8 → the flip still rewrites `(s, note)` (FAIL; pass at e4645012). The flip
reads only the note, so whether the row's writer is readable never enters; this
does not break invariant 7 as worded (it names the note the flip reads), which is
why it is B.

The row is the same one for both writers (`uq_file_relations_a_b_kind`), so the
flip cannot keep both meanings. Recovery: the row returns on `s.md`'s next save.
Reachability on the measured copy: none today — none of the 6 Markdown → Markdown
`b` notes has a `loft://` link or `source_file_ids` (checked on disk,
read-only). It needs a note distilled from a Markdown source that also links the
note back.

### J3 [introduced] bucket B — mutual citations between two notes keep only one direction

`test_mutual_citations_keep_both_directions`: `a.md` and `b.md` link each other by
`loft://`, legacy `(a, b)` and `(b, a)`. At 853bdceb the result is one marked row:
processing note b marks `own = (b, a)` and deletes `(a, b)`; processing note a
then finds `(b, a)` — the same identity-map object it loaded as a seed, now
`origin = markdown` — in its seed list, finds no `(a, b)`, inserts it and deletes
`(b, a)`. A marked row is deleted by the flip, from a stale seed list. Pass at
e4645012. The lost direction returns on that note's next save; until then the
other note dropping its link removes the only row. The measured copy has 0 mirror
pairs.

### J7 [introduced] bucket B — the flip's cost grows quadratically with the seeds it touches, and uncited seeds are paid on every start

`test_timing_flip` / `test_timing_scale_uncited` (test SQLite in `litloft-test`,

Doubling the input quadruples the time. Same runs with only
`session.expire_on_commit = False` set by the test: 2 540 → 0.32 s, 5 080 → 0.63 s.
So the growth comes from the per-note `db.commit()` expiring every `File` and
`FileRelation` the pass loaded up front, not from reading files or parsing
frontmatter. When nothing matches (no unmarked row into a Markdown note) the query
is 0.03 s even at 25 400 notes.

Every seed whose note does not cite its source — stale seeds, or knowledge notes
without `source_file_ids`, like the capture → knowledge note row on the measured
copy — never flips, so its note is re-read on every start and the cost repeats.
At 5 080 such notes the startup is past the ~90 s healthcheck budget from G1 on
every start, not only the upgrade. On the measured copy the candidate set is 24
rows, so this is not reached there. The G1 finding's hung-mount note still holds
for the notes that are candidates.

## 4. Other questions from the brief

- **Wiki-link-only citations are not converted.** True
  (`test_wiki_link_does_not_flip`). The seed stays unmarked; the note's saves never
  remove it (invariant 2), and it is re-read on every start (J7). Same class as the
  "stale seeds" Checked entry.
- **`created_by`/`created_at` carried.** Observed carried on the row (H7), and
  `list_file_relations` puts `rel.created_by` into each item (code; H7 checks only
  the listed ids) — the viewer id the
  addon passed. A row the save sync writes has `created_by = NULL`, so after the flip
  a markdown-owned row can carry a viewer id. Nothing reads `created_by` for
  ownership; not a finding.
- **Cost when nothing matches.** 0.03 s for the candidate query at 25 400 notes /
  50 000 media rows with no unmarked row into a note (J7 table).
- **A `(source, note)` row an addon writes after the upgrade.** At the next start it
  becomes `(note, source, markdown)` when the note cites the source directly, after
  which the note's saves own it: dropping the citation deletes it. For the pinned
  knowledge (143c562, still seeding) that is the intended outcome
  (`..._after_restart` passes); for an explicit relation some other addon writes
  it is G2's class (J6). No shipped writer other than old knowledge.
- **`time.sleep` in the startup test.** Under the real code the flip is a plain
  call before `yield`, so `finished` is set before the `with` body in every run;
  the test cannot fail spuriously. Its kill depends on the rest of the lifespan
  finishing inside 0.3 s under a threaded mutant; P16 was killed 6 of 6 runs. The
  failing-flip test has no timing dependence.
- **Items in the spec's Checked, no action, still true:**
  - Legacy unmarked `(N, X)` whose link was removed outside the app stays: true — and now also inside the app on the first save (J1).
  - Notes trashed or missing at upgrade keep legacy rows (F3): true (R-C x2).
  - Internal API list returns both directional rows for mutual links: true, `internal.py` unchanged.
  - Stale seeds `(S, N)` N no longer cites are left: true; they are now re-read every start (J7).
  - ownership-r2 G1/G2 "replaced by the seed flip": G1 closed in the measured shape, reopened at scale by J7; G2 not closed (J6).

## 5. Trajectory: d7cd07d9 → 07de9066 (+ k 1764bd6) → e4645012 (+ k 3c6325f) → 853bdceb

- **d7cd07d9** added a prediction: `a = note` means the note's link wrote the row. Discarded.
- **07de9066** replaced it on the save path with recorded state (`origin`) and the
  adopt branch, and added a one-time pass carrying three predictions
  (`claim_unmarked` — the d7cd07d9 rule again for legacy rows; "an unreadable file
  blocks the sentinel"; "an unmarked `(T, N)` mirrored by a marked `(N, T)` is a
  seed") and one state (the sentinel).
- **e4645012** removed `claim_unmarked` and added none; it moved the pass before serving.
- **853bdceb removed** the full resync, the sentinel state, the seed-mirror
  prediction and "unreadable blocks the sentinel". **It added** one prediction and
  one branch:
  - prediction: *an unmarked `(S, N)` whose note N cites S by `loft://` or
    `source_file_ids` is a knowledge seed, and so belongs to N* — the flip hands the
    row to `b`;
  - branch: `own is None` → insert, else mark.

So the rule "two consecutive rounds each adding" is not met: e4645012 added
nothing, and 853bdceb is net removal (three predictions and a state out, one
prediction and a branch in). But the prediction it added is of the same family as
the one d7cd07d9 introduced and 07de9066 re-added: *the shape of a legacy row says
who wrote it*. d7cd07d9 read ownership from `a`; 853bdceb reads it from `b` plus a
citation. Every new finding in this round is that prediction being wrong for a row
another writer produced: J2 (a Markdown source's own link row), J3 (a mirror pair of
link rows), J6 (an Internal API reverse row), J5 (a cross-drive row). J1 is the
other side of the same choice — the rows it declines to guess about (legacy
`a = N` rows) are never resolved at all. For the supervisor: legacy rows carry no
provenance, and each round so far has either guessed it from shape (and been wrong
for some writer) or declined to guess (and left rows no path can remove). A further
round that adds a condition to the flip (drive check, source-state check, mirror
check) would be the second addition in a row to the same prediction.
