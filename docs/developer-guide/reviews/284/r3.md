## 2. Findings

Review tests: `scratchpad/own-r2/review/test_review_own_r2.py`.

### G1 [introduced] bucket B, user-reachable — the synchronous pass can keep the backend unhealthy long enough that `docker compose up` does not start the frontend, and it repeats on every start while the sentinel is unreachable

`_run_relation_origin_backfill()` now runs in the lifespan, and uvicorn does not
bind port 8000 until the lifespan finishes, so `/api/health` refuses connections
for the whole pass. `docker-compose.yml`: healthcheck `interval 30s, retries 3,
start_period 10s`; frontend `depends_on: backend: condition: service_healthy`.
The backend goes unhealthy after roughly 90 s of refused probes, and Compose then
aborts the frontend start ("dependency failed to start"); the upgrade command
`git pull && docker compose up -d --build` is exactly the run that carries the
pass. At 07de9066 the same work ran in a background task after the scan and did
not gate health.

Measured (review tests, test SQLite in the `litloft-test` container, local
tmpfs; a NAS read is slower, not faster):

| Markdown files | other rows on the drive | links per note | elapsed |
|---|---|---|---|
| 500 | 0 | 5 basename + 5 alias-rule | 16.1 s |
| 2 000 | 0 | 5 basename + 5 alias-rule | 198.1 s |
| 1 000 | 0 | 5 basename + 2 dangling | 11.7 s |
| 4 000 | 0 | 5 basename + 2 dangling | 76.3 s |
| 1 000 | 50 000 video rows | 5 basename + 2 dangling | 78.3 s |

Growth is super-linear: rule 4 (`File.filename ==`, no index on filename) scans the
drive's rows per wiki target, and rule 5 loads and JSON-parses every aliased
Markdown row per target that falls through (any dangling `[[link]]`). A library
of 1 000 notes beside 50 000 media rows is already at the edge of the healthcheck
budget.

Aggravating, from F4: while any active `.md` row is unreadable (retired drive,
over 1 MB, not UTF-8, a file deleted on disk while down until the scan marks it
missing) the sentinel is never written, so this cost is paid on every start, not
once. From code, not reproduced: a hung network mount blocks `path.stat()`
indefinitely, which now blocks startup rather than a background task.

No R-0 line covers startup, hence B; it is user-reachable on the upgrade itself,
which is grounds for the supervisor to consider an R-0 revision.

### G2 [introduced by 07de9066, not closed by e4645012] bucket B — while the sentinel is unreachable, each start's seed dedupe deletes an Internal API (T, N) row written since the previous start

The rest of F4. `_remove_seeds_duplicated_by_markdown` treats every unmarked
`(T, N)` mirrored by a marked `(N, T)` as a pre-upgrade knowledge seed. On a rerun
it cannot tell that from a row an addon wrote through
`POST /api/internal/file_relations` after the upgrade.

Reproduction `test_rerun_keeps_internal_api_reverse_row_written_after_first_run`:
retired-drive `.md` row (sentinel unreachable); `note.md` links video V; backfill
→ `False`, `(note, V, markdown)`; Internal API POST `(V, note)` → 201; backfill
again → `False`, `(V, note)` gone. Fails at e4645012 and at 07de9066. N12 (drop the
dedupe call) turns it green, so the dedupe is its sole cause.

User-visible only once the note drops the link: `(note, V)` is then deleted and
the explicit relation the addon wrote is gone with it. Same bucket reasoning as
F4 (no shipped writer of such rows identified).

### G3 [introduced] bucket A (test gap) — nothing holds that the pass completes before the first request (F2's fix)

N2 replaces the call with
`asyncio.create_task(asyncio.to_thread(_run_relation_origin_backfill))`, which
lets requests (and so note saves) interleave with the pass again — F2, an
invariant 3 break. The whole repo suite stays green: the new test records call
order with an instant stub, and the stub has finished by the time the `with`
body reads `calls[0]`. It observes that the backfill *started* first, not that it
*finished* before serving.

### G4 [introduced] bucket B (test gap) — the wrapper's `except Exception` is now load-bearing for startup and nothing runs it

N4 (drop the `except` in `_run_relation_origin_backfill`) lives in the repo suite:
`conftest.py` replaces the wrapper with `lambda: None` for every client fixture,
and the new ordering test replaces it too, so the wrapper never executes. Under
N4 any exception from the pass (a DB error, a bug) aborts the lifespan and the
backend never comes up; at 07de9066 it would have ended a background task. Killed
by review test `test_startup_survives_backfill_exception` (real wrapper, backfill
patched to raise, `/api/health` → 200). The code is correct today.

### G5 [introduced by 07de9066, same at e4645012] bucket B — a pre-upgrade seed (S, N) whose source was inactive at upgrade outlives the citation

Same class as F3, for the source end rather than the note. The spec's Checked
entry names only notes trashed or missing at upgrade.

Reproduction `test_seed_whose_source_was_missing_at_upgrade_goes_with_the_citation`:
video S, `note.md` with `source_file_ids: [S]`, legacy `(S, note)`; S
`missing_since` set; backfill → `True` (sentinel written; N's sync drops the
inactive S, so no `(N, S)` and the dedupe keeps `(S, N)`); S recovers; PUT note
(adds `(N, S)`), then PUT without the citation → `(S, note)` remains. Fails at
e4645012 and 07de9066. Before the branch the save sync reconciled every row
touching the note and removed it (the mechanism R1's R-C/R-E passed on e09ea968).
The removal of `claim_unmarked` does not change it: S is a video, so it was never
claimable.

### Items from the spec's Checked, no action, still true (one line each)

- Legacy unmarked `(N, X)` whose link was removed outside the app stays: true (repo test `test_unmarked_outgoing_row_no_longer_linked_is_kept`).
- Notes trashed or missing at upgrade keep legacy rows: true (R-C x2); see G5 for sources.
- Internal API list returns both directional rows for mutual links (P1): true, `internal.py` unchanged.
- Stale seeds `(S, N)` N no longer cites are left: true, and now also for Markdown S (the claim that used to remove them is gone), which makes the Checked entry accurate where R1 P2 said it was partial.

## 4. Trajectory: d7cd07d9 → 07de9066 (+ knowledge 1764bd6) → e4645012 (+ knowledge 3c6325f)

- **d7cd07d9** added a prediction: a row's direction says who wrote it (`a = note`
  ⇒ the note's links). Discarded.
- **07de9066** removed that prediction from the save path and replaced it with
  recorded state (`origin`), plus the adopt branch and create-path sync. It also
  added the one-time pass, and in it three predictions: `claim_unmarked` (the
  d7cd07d9 direction rule again, for legacy rows), "an unreadable file blocks the
  sentinel", and "an unmarked `(T, N)` mirrored by a marked `(N, T)` is a knowledge
  seed". **Knowledge 1764bd6** removed the conflicting writer (seeding) and added
  one branch (explicit same-drive check replacing the 400-as-check).
- **e4645012 removed one prediction and added none** in production code:
  `claim_unmarked` and its branch are deleted, not guarded, and
  `_scan_then_backfill_relation_origin` is gone. What it changed besides is
  placement (synchronous, before serving), which trades R1's concurrency window
  for a startup-time dependency (G1); that is a cost, not a new branch or state.
  Its test additions are detectors for R1 F7–F9. **Knowledge 3c6325f** is
  test-only.

So no: consecutive rounds do not each add a branch, state or prediction the
previous one also added. e4645012 is a removal, the loop is converging on the
save path. The residue is concentrated in 07de9066's migration predictions that
remain: the seed-mirror rule is what G2 finds wrong on reruns and what G5 cannot
reach, and "unreadable blocks the sentinel" is what makes G1 and G2 recur on every
start instead of once. If another round is fixing either of those by adding a
case (e.g. "only dedupe rows older than X", "skip retired drives"), that would be
the second consecutive addition to the same pass.
