## Findings

### F1 [introduced] bucket C — knowledge-seeded relations are no longer reconciled by the note that owns the citation

The change infers ownership from direction: "rows with `file_id_a == X` were
written by X's links". The existing writer of note citations uses the opposite
direction. The knowledge addon seeds `file_id_a = source, file_id_b = note`
(`addons/knowledge/app/routers/note_from_file.py` create_file_relation call,
same shape in `distill.py` and `notes.py`), and relies on "subsequent saves keep
it in sync via frontmatter" `source_file_ids`.

At d7cd07d9 the note's saves can no longer remove that row, and add a second
row in the other direction.

Reproduction (`test_knowledge_seed_row_after_citation_removed`): seed video S,
note N, insert (S,N,related); PUT N with `source_file_ids: [S]`; then PUT N with
the citation removed.

| | after cite | after uncite | public list of N | internal rows for S |
|---|---|---|---|---|
| e09ea968 | (S,N) | none | 0 | 0 |
| d7cd07d9 | (N,S), (S,N) | (S,N) | 1 | 1 |

User-visible: removing a citation from a knowledge note leaves the source in the
note's (and the source's) Related files permanently; there is no public
endpoint to delete a relation. This breaks none of the seven R-0 lines as
written (invariant 2 only speaks of rows with `a == X`), which is why it is also
the main "missing from the list" item below. Raised as C because the fix is a
choice about who owns a row (direction, `created_by`, or the addon writing
`a = note`), not a local patch.

### F2 [introduced] bucket B — Internal API readers now see two rows for one undirected link

Only the public listing dedupes. `GET /api/internal/file_relations?file_id=` returns
both directions.

Reproduction (`test_mutual_links_internal_count`): Y links [[x]], X links [[y]].

| | internal rows for X | public items for X |
|---|---|---|
| e09ea968 | 1 | 1 |
| d7cd07d9 | 2 | 1 |

The same happens for every cited knowledge note after its first save (F1 table,
"after cite"). Effects in readers at the pinned SHAs:
- intelligence `get_file_detail._fetch_relations_summary` reports `{"related": 2}` for one counterpart.
- intelligence `get_related_files` returns the counterpart twice (`outgoing` and `incoming`). Arguably correct given the new directional meaning.
- knowledge `connections_graph` dedupes by sorted pair, so the graph is right, but the doubled rows reach its `_MAX_RELATIONS` truncation threshold sooner.

No R-0 invariant covers Internal API readers.

### F6 [pre-existing] bucket B — the author's known candidate has the direction reversed; what remains is a markdown SOURCE save

Knowledge distill / note_from_file / notes seed rows with `a = source`, not
`a = note`. So at d7cd07d9 the note's own save never deletes them (F1 is the
consequence). What does delete them is saving the source when the source is
itself Markdown and does not link the note.

Reproduction (`test_markdown_source_save_deletes_seed`): src.md, note.md, insert
(src,note); PUT src with "edited source, no link". Rows afterwards: 0 at
d7cd07d9, 0 at e09ea968. At d7cd07d9 the relation is still shown if the note has
been saved once (its own (note,src) row survives); at the parent it was gone
until the note was saved again.

### F7 [pre-existing] bucket B — existing databases keep the old bug's data shape

No backfill ships with the change. Rows deleted by the old sync stay missing until
the linking note is saved again, and mutual links written by the parent exist as
one row. At the parent, Y links X then X links Y leaves only (Y,X)
(`test_mutual_links_internal_count` → 1 row). After upgrading, if Y drops its
link and saves, (Y,X) is deleted and X's link to Y disappears from both Related
files sections until X is saved. Same outcome at the parent, so not a
regression, but it is what an upgraded user will see.

## Is anything missing from the R-0 list?

1. Rows not written by the Markdown sync. Nothing says which saves may delete a
   `related` row written through `POST /api/internal/file_relations` (knowledge
   seeds `a = source, b = note`). Suggested wording: "Removing a
   `source_file_ids` entry from a note and saving removes that source from the
   note's Related files" or its deliberate opposite. F1.
2. Internal API readers. Invariant 5 covers only the public listing. Suggested:
   "`GET /api/internal/file_relations?file_id=X` returns each (counterpart,
   kind) at most once", or an explicit statement that it is directional and
   consumers must dedupe. F2.
3. Invariant 1 should say "including when another note that links the same
   target drops its link". F5 shows the current tests read it more narrowly.
