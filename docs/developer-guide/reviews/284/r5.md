## 2. What e4159ba3 broke — findings

### K1 [introduced by the branch; e4159ba3 makes the extra row permanent] bucket A (sequencing) — with the pinned knowledge, a created note gets two rows to its source and keeps one after the citation is removed

`test_pinned_knowledge_seed_gives_one_row_removed_with_citation` reproduces
knowledge `143c562`'s `note_from_file` sequence (`git show 143c562:app/routers/note_from_file.py`):
`POST /api/drives/{drive}/files` with `source_file_ids: [S]`, then
`POST /api/internal/file_relations {a: S, b: note}`. At e4159ba3: the create sync
writes `(note, S, markdown)`, the POST returns 201 and writes `(S, note, internal)`
→ **2 rows** join note and S; saving the note without the citation leaves
`(S, note, internal)`, and no core path ever removes an `internal` row (by design,
invariant 2). Invariant 9 fails on both counts. Same test: pass at e09ea968 (one
row, removed with the citation); FAIL at 853bdceb (two rows, but the seed was NULL
and a restart flip could still convert it while cited).

The fix is the submodule bump the spec already orders (knowledge 3c6325f stops
seeding). Recorded as A because the SHA under review pins 143c562, and because the
cost of deploying core ahead of the bump changed: every note created in that window
keeps an undeletable `(source, note)` row. Intelligence `get_related_files` reads
both directions, so it reports S as outgoing and incoming while cited.

### K2 [introduced] bucket B — a pre-origin row the note still links is replaced, not kept: new id, `created_at` = now, `created_by` dropped

`test_pre_origin_seed_keeps_created_by_when_note_cites_source`: NULL
`(S, note, created_by=viewer123)`, note cites S, note saved →
`[(note, S, None)]`. At e09ea968 the row was kept as is (counterpart matched in
either direction); 853bdceb's flip carried `created_at`/`created_by`. Effects a user
can see: the converted relation moves to the top of the "newest first" Related
files list (`files.py` orders by `created_at desc`); `relation_id` changes.
`created_by` is not rendered by the frontend (grep `frontend/src`). On the measured
copy this applies to the 19 source→note seeds (all 19 notes cite their source by
`loft://` and/or `source_file_ids`, checked on disk read-only), each on its note's
first save. No invariant names these fields.

### K3 [pre-existing] bucket B — deleting an `internal (N, T)` row through the Internal API leaves N's link to T unlisted until N is saved again

`test_internal_outgoing_row_deleted_leaves_link_unrepresented_until_save`: internal
`(N, T)`, N links T → only the internal row (`held_by_others`, invariant 3); DELETE
→ `GET /api/files/N/relations` is empty though N still links T. At e09ea968 the
outcome is the same (the existing row is taken as the link's, so no second row;
the DELETE removes the only one). Converse, also pre-existing: once N links T,
`POST (N, T)` is 409 (`test_internal_post_after_link_is_409`), so an addon cannot
claim an already-linked pair. No shipped writer does either.

### K4 [introduced] bucket B — ADDON-DEVELOPMENT.md's "a note linking the same file adds no second row" holds only for rows posted as `(note, file)`

A relation posted as `(file, note)` does get a second `(note, file, markdown)` row
when the note links the file (`test_j6…`; K1 is the same shape). An addon developer
following the sentence would write `(source, note)` seeds expecting one row — the
pattern that produces K1. Suggest deleting that clause.

### K5 [introduced] bucket B — three conditions in the new NULL-row branch cannot change which rows exist

From the mutation table: Q7 (`relation.file_id_b not in own`) and Q9
(`relation.file_id_a == file_id` in `held_by_others`) are unreachable —
`uq_file_relations_a_b_kind` forbids a NULL and a marked `(N, T)` coexisting, and a
non-NULL row with `a ≠ N` has `b = N`, which is never a target. Q5/Q6 (dropping
`a == N` or `b in target_ids` from the mark condition) leave the same row set: a
wrongly marked row is deleted by the `own` loop and the link re-inserted. What the
mark branch does preserve is row identity (K2's fields), which no repo test observes.
Note Q4: removing the mark branch outright (always delete, then insert) is **not**
safe — SQLAlchemy flushes the INSERT before the DELETE, the UNIQUE constraint fires,
and the whole sync rolls back; the repo suite catches it
(`test_legacy_outgoing_row_that_is_linked_is_marked`).

## 5. Trajectory

Fix diffs in order: d7cd07d9 (discarded) → 07de9066 (+k 1764bd6) → e4645012
(+k 3c6325f, tests) → 853bdceb → e4159ba3.

- d7cd07d9: added a prediction (`a = note` ⇒ the note's link wrote it).
- 07de9066: added a state (`origin`), an adopt branch, and a startup pass with three predictions and a sentinel state.
- e4645012: removed `claim_unmarked`, added nothing.
- 853bdceb: removed the resync, the sentinel and two predictions; added one prediction (an unmarked `(S, N)` cited by N is N's) and a branch (insert vs mark).
- **e4159ba3 removed** the whole startup pass: the flip module (96 lines), its lifespan call and ordering constraint, the startup disk reads, the 853bdceb prediction and its branch, and the 07de9066 adopt branch in its general form. **It added** one state value (`origin = "internal"`, so NULL no longer means "internal or legacy") and two branches in the save sync: the NULL-row rule (mark if linked outgoing, else delete) and the `held_by_others` subtraction.

Answer: 853bdceb and e4159ba3 both add a branch, so a literal reading of the rule
counts two rounds in a row. By shape, e4159ba3 is not the patching pattern: it adds
no prediction about who wrote a row — NULL rows are not attributed, they get the
pre-branch rule — and it is net removal in `backend/app` (+50 / −134). The branch
it adds replaces a prediction with recorded state rather than handling one more case
the flip missed; and Q5–Q7 show the mark branch is behaviourally delete-and-reinsert,
so it carries no hidden inference. What remains open is sequencing (K1), not the
design. The supervisor assigns C.
