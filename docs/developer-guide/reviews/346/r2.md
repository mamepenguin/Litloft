## R2-F1 — `test_empty_fallback_reraises_the_rss_failure` holds only "an HTTPError comes out", not "the fallback ran and came back empty"

`[introduced]` — the test is created by `d9ecefc`.

`addons/media_import/backend/tests/test_youtube_provider_network.py:276-295`

The test patches `_http_get_bytes` to raise `HTTPError(404)`, patches
`_yt_dlp_extract_flat` to return `[]`, and asserts
`pytest.raises(urllib.error.HTTPError)`. It never asserts that the
fallback was reached, so it cannot distinguish the behaviour it is named
for from "the RSS failure was never caught at all".

### The mutations that expose it

**N11**, `want=kill`: moved `raise exc` to the top of the `except` block,
so `_yt_dlp_headers` is never called on the fallback path.

```
7 failed, 17 passed
FAILED ...test_http_error_falls_back_to_yt_dlp_capped_at_rss_size
FAILED ...test_unparseable_body_falls_back_to_yt_dlp
FAILED ...test_non_feed_document_falls_back_to_yt_dlp
FAILED ...test_explicit_small_limit_survives_the_fallback
FAILED ...test_both_paths_failing_raises
FAILED ...test_response_phase_failure_also_falls_back
FAILED ...test_read_timeout_also_falls_back
```

`test_empty_fallback_reraises_the_rss_failure` is **not** in that list: it
passed with the fallback entirely removed.

**N5**, `want=kill`: dropped `OSError` from the `except` tuple, so an
`HTTPError` is not caught and escapes `_list_channel_via_rss` directly.
Four tests failed; again this one passed, because an `HTTPError` still
comes out of `list_items` — for the opposite reason from the one the test
is checking.

### Scenario

A later edit decides an `HTTPError` 404 means the channel is gone and
re-raises without trying yt-dlp. The seven tests above catch it, so the
practical exposure is small — but this test, the only one that pins the
behaviour `d9ecefc` was written to add, would stay green through a change
that deletes that behaviour. It is load-bearing prose, not a
load-bearing assertion.

### What a test would have to assert

Name the `_yt_dlp_extract_flat` patch and add `assert
mock_flat.call_count == 1` — the same line its two siblings
(`test_read_timeout_also_falls_back`,
`test_response_phase_failure_also_falls_back`) already carry.

## R2-F2 — the fix converts "RSS down, yt-dlp empty" into a permanently never-synced row, which is the exact population r1/F4 identified as the starvation driver

`[introduced]` — reproduced at both `d9ecefc` and `460298d`, below.

`addons/media_import/backend/subscription/providers/youtube.py:392-400`
together with `backend/subscription/manager.py:367-372`,
`backend/subscription/worker.py:180-183`, `manager.py:518-529` and
`backend/subscription/db.py:605`.

### The probe

A temporary test inserted one subscription row, patched
`_http_get_bytes` to raise `HTTPError(404)` and `_yt_dlp_extract_flat` to
return `[]`, ran `SubscriptionManager._sync_blocking(sid, None, None)`,
and read the row back. Same test, same fixtures, only
`providers/youtube.py` swapped between the two commits:

```
460298d:  raised=None       last_synced_at='2026-09-22T08:02:06...'  cooldown_until=None
d9ecefc:  raised=HTTPError  last_synced_at=None                      cooldown_until=None
```

That is F2 fixed, as claimed. The consequence is the second half:

```
PROBE rungs (never synced), five consecutive _apply_cron_backoff calls:
    last_synced_at=None  cooldown_until=now+60min
    last_synced_at=None  cooldown_until=now+60min
    last_synced_at=None  cooldown_until=now+60min
    last_synced_at=None  cooldown_until=now+60min
    last_synced_at=None  cooldown_until=now+60min
PROBE eligible order: the NULL-last_synced_at row comes first
```

### Why it matters

Before `d9ecefc` a subscription in this state completed its sync with
zero results. `_touch_last_synced_at` ran, the row acquired a
`last_synced_at`, and from then on it sorted with the healthy population
and its failures escalated up the ladder (60 → 240 → 1440).

After `d9ecefc` the same subscription raises. If it has **never** synced
successfully, `last_synced_at` stays NULL, so:

- `_next_backoff_minutes` returns the first rung on every failure
  (`state.ls is None` → `BACKOFF_LADDER_MINUTES[0]`), forever — measured
  above, five failures, all 60 minutes;
- `ORDER BY last_synced_at IS NOT NULL, ...` (added in `460298d`) puts it
  ahead of every healthy subscription on every sweep;
- `MAX_ENQUEUE_PER_SWEEP` (added in `460298d`) makes that head position
  scarce capacity.

Hourly demand is unchanged — the row was eligible every 60 minutes before
and is eligible every 60 minutes now — so revised invariant 8 ("within
capacity, every subscription is enqueued in a finite number of sweeps")
is not broken at the current population. What changes is *membership*:
`d9ecefc` moves a class of subscription out of the healthy tail and into
the permanent head group, and that group is the one r1/F4 showed cannot
leave. The two ingredients F4 named both came from round one; `d9ecefc`
supplies a new way to enter.

### Scenario

Inputs: a newly created channel subscription whose first cron sync lands
during the RSS outage this change targets, and for which yt-dlp is served
a consent or bot-check page. Every hour, forever: `list_items` raises,
`_apply_cron_backoff` writes `now + 60min`, `last_synced_at` stays NULL,
and the row is served before every healthy subscription on the next
sweep. It never escalates out of the way the way a previously-synced
subscription does.

### What a test would have to assert

`_next_backoff_minutes` must escalate for a row that has failed
repeatedly, whether or not it has ever synced — i.e. the ladder rung must
be inferred from failure count or from `cooldown_until` alone, not from a
gap that requires `last_synced_at` to exist. Today no test distinguishes
"never synced, first failure" from "never synced, fiftieth failure".

## R2-F3 — nothing constrains the `except` tuple from above: replacing it with `except Exception` leaves the suite green

`[pre-existing]` — the same mutant survives at `460298d` by inspection
(the only test that pins a non-caught type,
`test_rejects_non_canonical_channel_ref`, raises its `ValueError`
*before* the `try`, and the `IncompleteRead` / `TimeoutError` tests did
not exist then). Reported here because widening that tuple is the whole
content of `d9ecefc`.

`addons/media_import/backend/subscription/providers/youtube.py:380-385`

### The mutation

**N12**, `want=kill`: replaced

```python
except (
    OSError,
    http.client.HTTPException,
    ET.ParseError,
    _FeedUnavailable,
) as exc:
```

with `except Exception as exc:`.

**Result: survived. 308 passed.**

Round one killed every mutant that *narrows* the tuple (M4, M5, M6; and
N5, N6, N9, N10 here). No mutant that *widens* it is killed. The suite
holds "these shapes fall back" and holds nothing about "anything else
must not".

### Scenario

A refactor inside `_list_channel_via_rss` introduces an `AttributeError`
or a `TypeError` — say the Atom namespace constant is renamed and one
`find()` call is left returning `None`. Under a widened tuple the bug is
caught, logged as "RSS listing failed", and converted into a yt-dlp call.
Where yt-dlp works, every sync succeeds and the RSS path is silently dead
for as long as the bug lives; where it does not, the operator sees a
transport warning for a bug that has nothing to do with transport. This
is the direction the tuple has already moved once in two commits, and
nothing signals the next step.

### What a test would have to assert

One test in which `_http_get_bytes` raises a `ValueError` (or
`_list_channel_via_rss` is patched to) and `list_items` propagates it
without calling `_yt_dlp_extract_flat`. That is the assertion that turns
the tuple into a decision rather than a default.

The assertion becomes load-bearing only if `_http_get_bytes` returns
parseable feed bytes, and it never will while the patch is left
unconfigured. Two plausible later edits make the mutant survive again:
giving that patch a `return_value` of valid Atom bytes (natural, if the
test is ever extended), or adding `TypeError`/`Exception` to the
`except` tuple (R2-F3). The invariant is currently held by a coincidence
of mock typing, not by the line written to hold it.

### What a test would have to assert

Give the patch `return_value=` the same well-formed Atom bytes the
`TestListItemsChannelRSSFallback` tests use, so that under the mutant the
RSS path *succeeds* and `mock_fetch.call_count == 0` is the assertion
that fails.

## The questions a mutation does not answer

### What does the caller see when `raise exc` fires, and does anything upstream behave differently?

**No.** `list_items` has exactly one production call site,
`SubscriptionManager._sync_diff` (`manager.py:317`), which does not catch
it. `_sync_blocking` propagates, and `worker._execute`'s generic
`except Exception` (`worker.py:180`) handles it identically to any other
RSS failure: `logger.exception`, `_apply_cron_backoff` when
`job.kind == "cron"`, and a `sync_completed` broadcast with
`error="exception"`. The probe confirms it end to end — `raised=HTTPError`,
`last_synced_at` unchanged, no `cooldown_until` written by the manager
(that is the worker's job).

Nothing distinguishes the re-raised exception from a plain RSS failure,
which is the intended shape: the only difference is *which* rows now take
this path, which is R2-F2.

One consequence worth stating: `raise exc` re-raises the **RSS**
exception, so the log line and the WS payload describe the RSS failure
even though yt-dlp also ran and also produced nothing. An operator
reading `HTTP Error 404: Not Found` will look at the feed endpoint, not
at the bot-check page that actually decided the outcome. The
`RSS listing failed ... falling back to yt-dlp` warning is emitted first,
so the sequence is recoverable from the log; nothing is misleading enough
to be a finding.

### Is there an input for which a genuinely empty channel can never be synced?

**Yes, but only while the RSS feed is unavailable, and it is the
documented trade.** A channel with no uploads whose RSS feed answers
normally returns a valid Atom `<feed>` with zero `<entry>`, which
`_list_channel_via_rss` returns as `[]` without touching yt-dlp — r1
verified the root-element guard discriminates that case correctly. The
fallback is only reached when RSS fails, and revised invariant 4 chooses
to raise there rather than accept an empty answer from a source that
cannot be trusted to distinguish "no videos" from "bot check". So:

- empty channel + healthy RSS → syncs, `[]`, fine;
- empty channel + failing RSS → raises on every attempt, for as long as
  the outage lasts. If it has never synced, R2-F2 applies.

This is by design, not a defect. It is flagged only because the
combination above is not merely "delayed" — it is the entry point into
the permanent head group.

### Does `OSError` swallow anything it should not?

**No.** Everything reachable inside the `try` is:
`_http_get_bytes` → `_youtube_opener.open()` + `resp.read()`;
`ET.fromstring(body)`; the `root.tag` comparison; and construction of the
frozen `ItemHeader` dataclass (`registry.py:56`). Only the first does
I/O. `ET.fromstring` parses bytes already in memory and raises
`ParseError` or `TypeError`, never `OSError`; the dataclass raises
nothing. The opener's own non-transport surface is closed too — the
default `build_opener` set includes `FileHandler`/`FTPHandler`, but the
primary URL is always an `https://www.youtube.com/...` string this module
constructs from a regex-validated `UC...` id, and
`_YouTubeOnlyRedirectHandler` rejects any redirect whose hostname is not
in `_YOUTUBE_HOSTS` (a `file://` target has hostname `None` → `""` →
blocked). So every `OSError` reachable here is a transport failure.

The breadth problem in this `except` is not `OSError`; it is that nothing
bounds the tuple at all — R2-F3.

### A note for the triage, not a finding

Revised invariant 4's parenthetical reads *"RSS を経由しない経路
（backfill・playlist）では空は正当な答え"*. The code gates on the
**RSS-attempted** path, not on "backfill". A small backfill reaches
`list_items` as `n_seen + count` (`schemas.py:160-164`), so a backfill of
5 on a fresh subscription arrives with `limit=5`, takes the RSS path, and
*does* raise on an empty fallback. That matches invariant 4's operative
sentence and contradicts its parenthetical. Reading the parenthetical
literally would make that behaviour look like a violation; it is not.

## Trajectory

> *Read the fix diffs in order. Does each round add a branch, a state or
> a prediction that the round before it also added?*

**Yes. Both rounds add to the same enumeration, in the same five lines,
and neither removes anything.**

`460298d` introduced a prediction about *how the RSS fetch can be
unhelpful* and handled each member of it:

```python
class _FeedUnavailable(Exception): ...                 # new member: "not a feed"
...
except (urllib.error.URLError, ET.ParseError, _FeedUnavailable) as exc:
    return self._yt_dlp_headers(url, limit or _RSS_MAX_ITEMS)
...
if root.tag != f"{_ATOM_NS}feed":                      # the branch that detects it
    raise _FeedUnavailable(root.tag)
```

Three named failure shapes, one new exception class, one new guard.

`d9ecefc` does the same thing twice more:

```python
except (
    OSError,                       # + shape 4 (transport, connect + response phase)
    http.client.HTTPException,     # + shape 5 (IncompleteRead, RemoteDisconnected)
    ET.ParseError,
    _FeedUnavailable,
) as exc:
    headers = self._yt_dlp_headers(url, limit or _RSS_MAX_ITEMS)
    if not headers:                # + a new branch: shape 6, "the fallback is
        raise exc                  #   also unhelpful, and silently so"
    return headers
```

The `except` block grew from 5 lines to 13. The diff is `+14 −2` in the
implementation: **fourteen added, two removed, and the two removed are
the old tuple and the old `return` being rewritten in place.** Nothing
was deleted, no branch collapsed, no prediction retired.

The shape is the one `review-workflow.md` names: *each round handling one
more case the last one did not anticipate.* Round one predicted the
failure set `{URLError, ParseError, non-feed}`; round two found two
transport shapes outside it (F3) and one failure mode on the other side
of the fallback (F2), and answered each by extending the list. Size is
not the tell — both fixes are small. The tell is that round two's
additions are the same *kind* of thing as round one's, arrived at the
same way: a reviewer named a case, and a case was added.

Two further observations bearing on it:

- **N12 shows the enumeration is unconstrained from above.** Replacing
  the four-member tuple with `except Exception` leaves 308 tests green.
  There is no test that says the list is a decision rather than a
  default, so nothing will resist the next extension.
- **R2-F2 shows round two's fix reaches into round one's other change.**
  `460298d` added a cap and an ordering; `d9ecefc`'s re-raise decides
  which rows land permanently at the head of that ordering. The two
  halves of round one were presented as independent (RSS fallback;
  scheduler fairness), and round two's fix couples them.

A converging round would have removed a distinction rather than added
one — for instance, deciding the question once as *"did this attempt
produce a usable listing?"* and letting every way of failing to produce
one take the same path, instead of enumerating the ways. That is the
observation; the call is not mine.
