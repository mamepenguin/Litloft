## F1 — Invariant 3 is no longer held by any test: backfill may be routed through RSS and the suite stays green

`[introduced]`

`addons/media_import/backend/subscription/providers/youtube.py:376`

Invariant 3: *backfill (`limit > 15`) does not go through RSS, and the
requested count reaches yt-dlp unchanged.* The gate that enforces it is

```python
if limit is None or limit <= _RSS_MAX_ITEMS:
```

### The mutation

`want=kill`. Replaced the gate with `if True:` — every channel listing,
backfill included, now attempts RSS first.

**Result: survived. 303 passed.**

### Why it survives

`TestListItemsChannelLargeLimitFallback::test_yt_dlp_fallback_when_limit_exceeds_rss`
(`backend/tests/test_youtube_provider_network.py:107`) is the only test for
this gate, and it patches `_yt_dlp_extract_flat` but **not**
`_http_get_bytes`. Before this commit that omission was safe: routing a
backfill into `_list_channel_via_rss` let the real fetch raise straight out
of `list_items` and the test failed. This commit's `except` clause now
catches that exception and re-dispatches to `_yt_dlp_headers(url, limit or
15)` — with `limit=50` still 50 — so every assertion the test makes still
holds.

Run under the mutation, single test, live log:

```
WARNING  ...youtube.py:382 RSS listing failed for UCabcdefghijklmnopqrstuv
         (HTTPError); falling back to yt-dlp
PASSED
```

The test reached out to `youtube.com/feeds/videos.xml` over the network and
passed anyway. The masking does not depend on the network being up: with no
egress the failure is `URLError`, which the same clause catches.

### Earning the label

Same mutation applied to `a2cff5c`'s `youtube.py`, same single test:

```
E       urllib.error.HTTPError: HTTP Error 404: Not Found
FAILED ...::test_yt_dlp_fallback_when_limit_exceeds_rss
```

Killed at the parent, survives at `460298d`. `[introduced]`.

### Scenario

A later edit widens or deletes the `limit <= _RSS_MAX_ITEMS` gate — a
plausible simplification now that "RSS failure is handled". A user presses
Backfill for 200 items on a channel with 2,521 videos. Every backfill first
pays a pointless RSS round trip, and on the RSS path a backfill of any size
silently truncates to the feed's 15 entries whenever the feed happens to be
up. CI stays green through all of it.

### What a test would have to assert

Pin `_http_get_bytes` in that test with `mock_fetch.call_count == 0`,
exactly as `TestListItemsPlaylist::test_playlist_uses_yt_dlp` was amended to
do in this same commit. The playlist test's `assert mock_fetch.call_count ==
0` is what makes invariant 5 mutation-proof (verified: M18 below); the
channel-backfill test needs the same line for invariant 3.

## F2 — After a confirmed RSS failure, a yt-dlp extraction that yields nothing returns `[]`, which the sync records as a successful "no new videos"

`[pre-existing]` in `_yt_dlp_extract_flat`; **made reachable from the cron
channel path by this commit**.

`addons/media_import/backend/subscription/providers/youtube.py:388`
(the fallback call) → `:144-146` (`if not info: return []` /
`entries or []`)

No mutation needed — this is the behaviour of the unmutated tree. Measured
in the baseline image:

```python
# RSS raises HTTPError 404; yt_dlp.YoutubeDL.extract_info returns a tab
# with no entries (the shape a consent / bot-check interstitial produces)
RSS failed AND yt-dlp yielded nothing -> []
RSS failed AND yt-dlp returned None   -> []
```

Both runs logged `RSS listing failed ... falling back to yt-dlp` first, so
the RSS failure was real and confirmed in each.

### Why it matters

This commit adds a guard against exactly this hazard on the RSS side:

```python
if root.tag != f"{_ATOM_NS}feed":
    raise _FeedUnavailable(root.tag)
```

and the test for it says why — *"yields an empty list, which is
indistinguishable from 'no new videos'"*. The yt-dlp half of the same
fallback has no equivalent guard, and the consequence is worse there
because it is the last resort.

`_sync_diff` (`backend/subscription/manager.py:317-372`) has no branch
between the listing and the bookkeeping: `headers == []` means `new_ids ==
[]`, the import loop runs zero times, and then, unconditionally,

```python
self._touch_last_synced_at(subscription_id)
self._clear_cooldown_until(subscription_id)
```

### Scenario

YouTube's feed endpoint is in the outage the commit message describes, and
yt-dlp gets served a bot-check page for this channel rather than an error.
Inputs: `list_items(ref, limit=None)`. Output: `[]`. The subscription
reports `added=0, total_new=0`, `last_synced_at` advances, `cooldown_until`
is cleared, the UI shows a healthy subscription, and it silently imports
nothing every hour for as long as the interstitial lasts. Invariant 4 exists
to prevent precisely this — "swallowing it is indistinguishable from no new
videos, and the cron backoff never fires" — and the declared wording ("an
exception escapes") does not cover the case where yt-dlp reports success
with nothing in it.

Triage note for the author: I read this as A against invariant 4's purpose,
not against its letter. The letter is satisfied; the outcome it was written
to forbid is reachable.

### What a test would have to assert

In the fallback branch only, with `_http_get_bytes` raising and
`_yt_dlp_extract_flat` returning `[]`, `list_items` must raise rather than
return `[]`. The shape that gets there without re-plumbing anything is to
re-raise the captured `exc` when the fallback comes back empty; the
non-fallback yt-dlp paths (backfill, playlist) keep today's behaviour,
where an empty channel is a legitimate answer.

## F3 — The `except` tuple misses every response-phase transport failure, so those subscriptions stay stuck in the backoff this commit exists to clear

`[introduced]` — the `except` clause is code this commit creates.

`addons/media_import/backend/subscription/providers/youtube.py:379-381`

```python
except (
    urllib.error.URLError, ET.ParseError, _FeedUnavailable
) as exc:
```

`urllib.request.AbstractHTTPHandler.do_open` wraps only the *connect and
request* phase in `URLError`. `h.getresponse()` and the `resp.read()` in
`_http_get_bytes` (`:122-123`) are outside that wrapper, so their failures
arrive raw.

Measured against a real socket inside the test image — no mocks, an actual
server that closes early:

```
truncated body                     -> IncompleteRead         URLError? False
connection closed before status    -> RemoteDisconnected     URLError? False
```

and fed back through `list_items`, with `_yt_dlp_extract_flat` available:

```
RemoteDisconnected (getresponse)    -> ESCAPED as RemoteDisconnected
IncompleteRead (resp.read)          -> ESCAPED as IncompleteRead
TimeoutError (read timeout)         -> ESCAPED as TimeoutError
```

(`ssl.SSLError` and a connect-phase `ConnectionResetError` also escape when
raised directly, but real urllib wraps those two into `URLError` during
connect, so they are not part of the claim.)

### Scenario

Inputs: a cron sync of a channel whose feed response is cut off mid-body —
the shape a flaky upstream or a proxy timeout produces during the very
outage this commit targets. Wrong output: the exception leaves
`list_items`, `worker._execute` applies `_apply_cron_backoff`, and the
subscription re-enters the "retry pending" state the commit was written to
get it out of. yt-dlp is never tried, though the spec measured it working
3/3 while the feed was down.

No declared invariant forbids this, so it is a B by R-4. It is reported
because it is a hole in what the change is *for*, and because the spec's
measurement (88 backoffs, all `HTTPError` 404/500) only establishes that
the covered shapes are the common ones today, not that the uncovered ones
do not occur.

### What a test would have to assert

`_http_get_bytes` raising `http.client.IncompleteRead(b"", 10)` must reach
`_yt_dlp_extract_flat`. Catching `OSError` alongside the current three
covers `IncompleteRead`? No — `IncompleteRead` is an `HTTPException`, not
an `OSError`; the tuple needs `(urllib.error.URLError, OSError,
http.client.HTTPException, ET.ParseError, _FeedUnavailable)`, and `OSError`
subsumes `URLError`.

## F4 — The new ordering pins permanently-broken never-synced subscriptions at the head of a now-capped queue

`[introduced]` — neither half exists at `a2cff5c`: before the cap there was
no scarce capacity to compete for, and before the `ORDER BY` change the
order was `id`.

`addons/media_import/backend/subscription/db.py:605` together with
`backend/subscription/scheduler.py:31,80`

Invariant 10 puts never-synced rows first. `_next_backoff_minutes`
(`backend/subscription/manager.py:518-529`) returns the *first* ladder rung
whenever `last_synced_at` is NULL, and `last_synced_at` is only written by
`_touch_last_synced_at` at the end of a *successful* full sync. So a
subscription whose first sync has never succeeded never advances past rung
one. Measured in the test image:

```
ladder: (60, 240, 1440)
  never synced, 1st failure    -> next rung 60 min
  never synced, 5th failure    -> next rung 60 min
  never synced, 50th failure   -> next rung 60 min
  synced long ago, 2nd fail    -> next rung 1440 min
```

A synced subscription escalates to the 24-hour rung on its second failure
and gets out of the way. A never-synced one comes back every 60 minutes,
forever, and the new `ORDER BY last_synced_at IS NOT NULL, ...` guarantees
it is served **before every healthy subscription** each time.

### Scenario

Inputs: K subscriptions created against channels that were deleted or that
yt-dlp cannot canonicalise, so their initial sync failed and
`last_synced_at` stayed NULL; N healthy subscriptions at the default
60-minute cooldown. Capacity is 3 × 60 = 180 accepted enqueues per hour.
Demand is K + N per hour, and the K are always at the front of the list.
Once K + N exceeds 180 the healthy tail is served strictly never, not late
— the ordering is stable, so the same tail loses every hour.

At the population in the spec (51 subscriptions, 28 stuck) demand is ~79/h
against 180/h, so this is not reachable today. It is reported because the
coupling is new, invariant 8 is stated as an absolute ("never permanently
starves"), and the two ingredients that make it bite — a fixed cap and an
ordering that favours the rows that will fail — both arrived in this
commit. `test_overflow_is_consumed_by_later_sweeps` holds invariant 8 only
for the case where every enqueue eventually succeeds; its `_ConsumingManager`
drops each id on accept, so a permanently-eligible id is not modelled.

### What a test would have to assert

Drive `tick_once` repeatedly against a manager whose eligible list keeps
returning a fixed head group (ids that never leave the list) plus a tail,
and assert every tail id appears in `worker.enqueued` within a bounded
number of sweeps. With today's code and a head group of size ≥ the cap,
no tail id ever appears.

### Detector rules

The five new tests were checked against `review-workflow.md` "Detector
rules". No violations: every assertion is an exact `==` against a value
declared in the test, not derived from the run (`called_limit == 15`,
`== 5`, `[never, stale, recent]`, `[2, 2, 1]`, `MAX_ENQUEUE_PER_SWEEP == 3`).
The three scheduler tests set `MAX_ENQUEUE_PER_SWEEP` on the *instance*, so
`test_shipped_cap`'s reading of the class attribute is not contaminated —
confirmed by M13, which kills `test_shipped_cap` alone.

One note on the test image: it has live network egress and a working
yt-dlp. Under M8 and M9, unmocked paths reached `youtube.com` and ran real
extractions. That is the mutants' doing, not the shipped suite's — but it
is the same property that lets F1 hide, so it is worth knowing.
