# R-0 不変条件: Media Import RSS フォールバックと sweep 投入上限

Spec: `2026-09-22-media-import-rss-fallback.md`
Core: `fix/media-import-rss-fallback`（`develop` = `ad441a0e` 基点）
Addon: `fix/rss-fallback`（`a2cff5c` 基点）

この変更が壊してはならないもの。レビュアーの第一視点はこのリストで、
「どの経路もこれを破らないか」を問う。各項目はミューテーションで違反
できる観測可能な文として書く。

## 取得経路

1. **RSS が成功したとき、yt-dlp は呼ばれない。**
2. **RSS の失敗でフォールバックしたとき、yt-dlp に渡る取得上限は 15 を超えない。**
   通常の cron 同期は `limit=None` で来るため、栓が外れるとチャンネル全件
   （実データで最大 2,521 件）が新着として流入する。
3. **backfill（`limit > 15`）は RSS を経由せず、要求された件数がそのまま
   yt-dlp に渡る。** フォールバックの導入で backfill の件数が 15 に縮まない。
4. **フォールバックが新着を1件も返さなかったら、例外が `list_items` の外へ
   出る。** yt-dlp が例外を投げた場合も、成功して空を返した場合も同じ。
   握り潰して空リストを返すと、新着ゼロと区別がつかなくなり、cron backoff も
   発火しない。RSS を経由しない経路（backfill・playlist）では空は正当な答え
   なので、この条件はフォールバック経路にだけかかる。
5. **playlist 購読の経路は変わらない。** 従来どおり yt-dlp 直行で、RSS を
   試さない。

## バックオフ状態機械

6. **`cooldown_until` に未来時刻を書くのは cron 失敗経路だけ。**
   manual / retry / backfill は失敗しても書かない。
7. **フル同期の成功は `cooldown_until` をクリアする。** フォールバック経由で
   成功した場合も同じ。

## スケジューラ

8. **投入上限で溢れた購読は次の sweep で eligible として再び現れる。**
   1 時間あたりの需要が容量（`MAX_ENQUEUE_PER_SWEEP` × 60）以内であるかぎり、
   どの購読も有限回の sweep で投入される。
9. **1 回の sweep で enqueue される件数が上限を超えない。**
10. **eligible の順序は「未同期が先、次に待ち時間の長い順」。**
    id 順に戻ると、上限がある状態では若い id の購読が恒常的に優先される。

## 再生成できないデータ

11. **この変更はいかなる経路でも `subscription_videos` の行を削除しない。**
    取得経路の変更であって、取り込み済みの記録には触れない。

## 改訂

### r1 / F2 — 不変条件 4

「両方が失敗したら例外が出る」を「フォールバックが1件も返さなかったら例外が
出る」に広げた。元の文言は満たされていたが、yt-dlp が bot チェックページを
掴んで**成功して空を返す**経路が残り、`_sync_diff` が `last_synced_at` を
進めて `cooldown_until` をクリアする。条件が禁じようとした結果に、条件の外から
到達できていた。

### r1 / F4 — 不変条件 8

「恒久的に飢えない」という絶対表現を、容量内での保証に改めた。未同期行は
`_next_backoff_minutes` が段を上げられないため60分ごとに戻り、新しい順序では
健全な購読より常に先に出る。需要が容量（180/時）を超える規模では末尾が
飢える。現在の規模（需要 約79/時）では到達しない。根本は未同期行の段が
上がらないことで、これは `a2cff5c` にもある既存の性質。
