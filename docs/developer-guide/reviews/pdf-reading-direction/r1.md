## Checks asked for in the brief

- **pdf.js return shape.** Only one pdfjs-dist is installed (`5.4.296`, `node_modules/.pnpm/pdfjs-dist@5.4.296`). `Catalog.viewerPreferences` (build/pdf.worker.mjs ~38305-38345) accepts `Direction` only as a `Name` and stores `value.name`, i.e. the plain strings `"L2R"` / `"R2L"`; anything else is dropped. The parser's string comparison is correct; no Name-object case reaches the client.
- **Other consumers of `loadedPdf`.** At 36360dec it had exactly three readers (the `f` gating, the button's `disabled`, the viewer mount). All three moved to `loaded`. Nothing else depended on it.
- **Sync throw / reject.** `Promise.resolve().then(() => pdf.getViewerPreferences()).catch(() => null)` handles both correctly by reading. Neither is tested (F1).
- **Slow read / late button.** The read is one worker round-trip against a catalog pdf.js has already parsed before `onLoadSuccess`; no visible regression expected. The only observable is that `f` pressed in that window does nothing (the "opens with f" test had to gain a wait for exactly this reason).
- **Stale guard.** Correct by reading: file change nulls `latestPdfRef` and `loaded`; a replaced Document produces a new proxy, so the old read is discarded by identity. Both the guard and its reset are killed by tests (M6, M7).

## Findings

### F1 [introduced] A — invariant 5 has no test: the unreadable-preferences path can be removed with every test green
M4 (delete `.catch(() => null)`) and M5 (call `pdf.getViewerPreferences()` directly, without the `Promise.resolve().then` wrap) both survive 81/81. Under M4 a rejecting read leaves `loaded` null forever: the full-screen button stays disabled and `f` is dead for that document, with an unhandled rejection. Under M5 a synchronous throw escapes `handleLoad` and does the same. The PdfPreview mock only ever resolves. Missing: a test with `getViewerPreferences` rejecting (and one throwing synchronously) that asserts the button becomes enabled and the viewer opens in the stored direction.

### F2 [introduced] A — invariant 1's timing ("never opens in one direction and turns to the other" / opens in the declared direction) is not held: the gating on the preferences read can be removed
M22 inserts `setLoaded({ pdf, declaredDirection: null })` synchronously in `handleLoad` (i.e. enable the button before the read settles, the pre-change behaviour) — 81/81 pass. In the app, a reader who opens full screen in that window gets the stored direction, and because `readingDirection` is initial state only, the later `declaredDirection="rtl"` never takes effect for that viewing — invariant 1 broken. The R2L PdfPreview test waits for the button to be enabled, by which time the (immediately-resolving) mock has already delivered `R2L`, so it cannot see the order. Missing: a deferred `getViewerPreferences` that asserts the button is disabled (and `f` inert) until it resolves.

### F3 [introduced] A — the L2R half of invariants 1 and 2 is untested
Every declared-direction test uses `"rtl"`. M19 (`declaredDirection === "rtl" ? "rtl" : readReadingDirection()` — ignore a declared L2R) and M20 (storage condition `declaredDirection !== "rtl"` — write storage for an L2R-declared document) both survive. A reader whose stored direction is `rtl` opening an L2R-declared PDF would get RTL (M19), or would have their stored setting overwritten by a switch (M20). Missing: stored `rtl` + declared `ltr` → opens `row`, switch does not write storage.

### F4 [pre-existing] B — the entry half of a split (wide) page is not held by any test, on open or on a switch
M21 (showRightHalf initializer `() => false` plus removing `setShowRightHalf(readingDirection === "rtl")` from both the spread-mode effect and the direction effect) survives here (81/81) and at 36360dec (27/27 in PdfFullscreenViewer.test.tsx). M16 and M17 (each effect's reset removed singly) also survive at both. This change relies on that code for the "half order" part of invariant 1 for a declared-rtl document, so the gap now covers new behaviour too, but the reproduction is identical at the parent.

### F5 [pre-existing] B — the `f` gating is not tested
M9 (drop `loaded !== null` from the `pdf-viewer-open` shortcut's enable condition) survives here and at 36360dec (with `loadedPdf`). Under the mutation, `f` pressed before load sets `fullscreen=true`, and the viewer pops open by itself when `loaded` arrives. The change widens the window in which this matters (now includes the preferences read), which is why F2's test should also press `f`.

## Is anything missing from R-0?
One item: the invariants state what happens when the preferences read fails (5) but not the ordering that the design is built on — *"The full-screen button and `f` stay unavailable until the document's declared direction is known, so the viewer never opens in the stored direction for a document that declares another."* F2 shows nothing holds it. (Invariant 1 implies it only if read as covering the loading window.)
