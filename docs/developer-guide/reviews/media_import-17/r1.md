## Findings

### F1. A dialog opened while the policy is loading is torn down when the policy then resolves to `url_import: false`; the typed URL is lost and `onDialogOpenChange(true)` is never balanced  [introduced]

- Invariant: 6 (the dialog closes other than on success, and loses its input). Also touches 4 (not measured this round).
- `frontend/ImportFromUrlMenuItem.tsx:50-51` (the gate returns `null` for the whole row) together with `:56-63` (the dialog is a child of that row).
- Reproduction (probe P9): policy fetch held pending → click the row → type `https://typed` into the URL field → release the policy response `{media_import: {default: true, features: {url_import: false}}}`.
- Observed: `dialogStillThere: false`, `onDialogOpenChange.mock.calls` = `[[true]]`.
- Expected: the dialog the user opened stays until Cancel / success, or at least the host is told it closed (`[[true],[false]]`).
- Reachable when the Add menu is opened for the first time on a `url_import: false` drive and the row is pressed before `/api/drives/{d}/addon-policies` answers (invariant 1 deliberately draws the row during that window). Mutation M16 (hide once loaded) shows the same shape inside the suite: every dialog test that already has the dialog open fails when the policy settles, i.e. the dialog's lifetime is bound to the gate.
- Consequence against the core branch this is designed for (read, not run — that core change is out of scope and in flux): in `AddButton` at core `1886c7c6`, `addonDialogOpen` disables the menu's `DismissScrim` (`disabled={addonDialogOpen}`) and its Escape shortcut (`menuOpen && !addonDialogOpen`). With the unbalanced `true`, the menu left on screen can be closed neither by an outside press nor by Escape until the trigger or a row is pressed.

### F3. When `resolveSubscriptionUrl` fails, a channel / playlist / feed URL is sent to `POST /link`; and no test pins either the fallback or the arguments `resolve` is called with  [introduced]

- Invariant: 3.
- `frontend/ImportFromUrlDialog.tsx:72-79` (`.catch(() => "unknown" as const)` then `createLoft`).
- Reproduction (probe P4): `resolveSubscriptionUrl` rejects (`Error: 500`), URL `https://www.youtube.com/@someone`, press Import. Observed: `createLoft` called once with that channel URL. `backend/router.py:143-172` (`/link`) does not classify the URL, so this creates a `.loft` reference file for a channel page.
- Mutation D2 (drop the `.catch`, so a resolve failure shows an error instead) → suite green. Mutation D22 (`resolveSubscriptionUrl(trimmed, "")`, i.e. resolve without the drive) → suite green; probe P5 (asserts `resolve` calls are `[[url, "d"]]`) kills it. With a wrong drive argument the real endpoint's `_scoped_drive` would reject every call, the `.catch` would turn every answer into `unknown`, and every channel URL would go to `/link` — with the whole suite green, because the mock never looks at the drive argument.
- Invariant 3 is worded "a URL resolved as channel…", so the resolve-failure path may be outside it; the Manage Composer has the same `unknown` fallback (pre-existing there). Supplied as material: the behaviour is as observed, and neither choice is held by a test.

## Detector-rule notes on the new tests

- `sends the same request whatever surface or fileIds the host adds` (`:305-316`) builds the expected value from an observation (`calls[0]` vs `calls[1]`, rule 5). It still discriminates what it names — M13 (surface forces root), M14 (fileIds hides row), M15 (surface swaps drive) are all killed — and absolute values are held by the neighbouring tests. Recorded, not counted.
- `policyLoaded()` waits for the request, not for the settled state (rule 3), then `stays after…` asserts presence after one `setTimeout(0)`. Presence is also true during loading, so if the policy ever took more than a tick to settle those two cases would pass vacuously. Measured today: M16 (hide once loaded) kills both, so the tick is currently enough. Recorded, not counted.
- Mocks: the API mock spreads `importActual` and overrides four functions with shapes matching `api.ts`; the catalogue fixture carries `addonName`, which `SlotEntryRenderer` needs; the policy fixture matches `PolicyResponse`. The `resolveSubscriptionUrl` mock never inspects its arguments (see F3).
- Backend `test_addon_meta.py` asserts exact equality of the declared slot → ids map (no lower bound). L2 (rename id in `ADDON_META`) is killed by it; L1 (rename the key in `slots.ts`) is killed by the frontend catalogue test. Both sides are pinned to the literal `media-import-url`.
- Information for the supervisor, not a finding: on core `5a72ef2d` only one of the two known "inside the Add menu" tests fails; `closes only the dialog on the first Escape and the menu on the second` passes (and D19, M8, L1, M16 kill it).

## Is anything missing from the R-0 list?

Things a user can hit that none of 1–8 covers:

1. **The dialog's lifetime is bound to the row's gate.** Invariant 6 says it closes only on success, and 4 covers pressing/typing, but nothing says the dialog survives the row re-rendering to `null` (policy settling, catalogue refetch). See F1.
2. **A retry is possible.** After an error or the subscription notice the user can edit and submit again (F2). 6 promises the state is kept, not that it is usable.
3. **What a URL that could not be classified does.** Resolve failure / `unknown` currently means "import as a single video" (F3). Whether that is intended for channel-shaped URLs is undeclared.
4. **Concurrent submits.** 3 says "exactly one", but whether that includes a second Enter while pending is implicit (F4).
5. **Success feedback.** On success the dialog and menu close silently. Whether the new `.loft` becomes visible in the folder the user is viewing, or the user is told the import was queued, is neither declared nor measured here (the Manage page refreshes via `onCreated`; the Add row has no equivalent).
