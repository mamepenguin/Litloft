## Findings

### F1 [pre-existing] policy が開いた後に off へ解決すると、FileActions のメニューが外側 press でも Escape でも閉じなくなる

- 不変条件: none（R-0 の "Recorded, not changed" の延長。記録はダイアログが消えることまでで、ホスト側に残る状態は書かれていない）
- 再現（S4）: `usePolicy` を `{enabled:true,isLoading:true}` で描画 → `File actions` → `Create note` でダイアログを開く → `usePolicy` を `{enabled:false,isLoading:false}` にして rerender。結果: ダイアログは DOM から消え、`[role=menu]` は残る。`document.body` への pointerdown+click 後もメニューは残る。Escape 後もメニューは残る。
- 親 d0614e1 で同じ手順を実行しても出力は完全に同一（`dialog:false menu:true` / 外側 press 後 `menu:true` / Escape 後 `menu:true`）。この変更による差はないので [pre-existing]。
- 原因: `CreateNoteMenuItem` が `return null` で消えるとき `onDialogOpenChange(false)` が呼ばれず、core `FileActions` の `addonDialogOpen` が true のまま残る。そのため `DismissScrim disabled` と Escape ショートカットの `menuOpen && !anyDialogOpen` がどちらも閉じた側に固定される。解除はトリガー `[...]` の再押下（`menuOpen` false → effect がクリア）だけ。
- ユーザーから見える結果: メニューを開いた直後、policy の取得が終わる前に Create note を押し、そのドライブの editor が off だった場合に限り、ダイアログが一瞬出て消え、空のメニューが外側タップでも Escape でも閉じない。発生窓は初回の policy 取得中だけで狭い。

## テストハーネスについて

- knowledge の in-menu テストは `<div role="menu">` と `DialogPortalProvider target={plain div}` で FileActions / sheet の代役を立てている。検査対象は「provider の target に入り menu に入らない」ことと「コールバック順序」なので、この代役で足りる。実物の差は S3 で確認した: sheet の実 target は `Drawer.Content` 直下の `<div ref={setDialogHost}/>`。デスクトップでは provider 無しで `document.body`。どちらでも menu 外という結論は変わらない。
- 実物の FileActions との結合（`onDialogOpenChange(true)` → `DismissScrim disabled`）は core の `FileActions.bundledRows.test.tsx` が保持している（M13 で kill を確認）。ただしそのテストは配置を検査していない。配置を保持しているのは knowledge 側のテストだけ（M1/M2）。
