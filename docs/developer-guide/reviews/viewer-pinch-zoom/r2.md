## Q1 — did bc010658 do what it claims

- **Invariant 6 / r1 F1 (wheel listener in a viewer that mounts closed):** fixed. `frameRef` is now a stable callback (`useCallback(..., [])`) that writes the ref and `setFrameEl`. React calls a stable callback ref only on attach/detach, so it does not loop. It re-renders once when the frame appears. A null-then-same-element call (StrictMode, or close → reopen) runs the effect cleanup and then attaches again. Probe P6 (Harness open → closed → open) showed both the wheel and gesturestart prevented after reopen. Both viewers pass `ref={zoom.frameRef}` directly. The e2e fixture (`e2e-components/fixtures/app.tsx`) does too and still passes. N1 is killed by vitest and by the e2e.
- **Invariant 9 / r1 F3 (reopen at fit):** fixed by adding `open` to the gallery's resetKey. Held by the test (N13 killed). Confirmed live.
- **Invariant 10 / r1 F2 (face shape change):** the archive is fixed and held (N15/N16/N17 killed). The gallery has the same code change, but no test holds it (N14 live, see F4).
- **resetKey including `face.kind`, and a face that changes kind when an image finishes loading.** In the gallery, `face.kind` changes after load only in spread mode, and only for a legacy file with no `image_width/height`. `isCurrentLandscape` is set in the slot-0 `onLoad` and is not reset when the page turns, so the face flips half ⇄ single once the new page loads. A pair never forms from a load in the gallery, because `orientationAt(current)` never returns `portrait` without columns. In the archive, `rememberOrientation` can turn single → pair or single → half when pages load. `canPair` (viewport aspect) also flips pair ⇄ single on rotation. In every case the zoom is reset only if the user zoomed before the face settled. That zoom was applied to a face drawn differently: a half is drawn at 200% width with translateX. Keeping it would leave a transform measured against another shape, which is exactly what invariant 10 forbids. **Acceptable, not a regression**: invariant 10 requires it as written. The rotation case also removes part of known-issue F8 in spread mode.
- **Gesture handler vs the iOS pointer pinch.** Apple's documented order for two fingers is: touchstart(1), gesturestart, touchstart(2), gesturechange…, gestureend, touchend. The pointerdown for finger 1 comes before gesturestart, so `onStart` sees `pointers.size > 0` and leaves `start` null. `onChange` and `onEnd` then do nothing beyond `preventDefault`. There is no double application, and settle on gestureend does not fight the pointer settle, because `start` is null. There are orderings where it does: see F5 (both fingers landing in one touchstart, and a gesturechange after the last pointerup), and F1 and F2 for the non-iOS paths. `preventDefault` on gesturestart/change/end at fit only blocks Safari's page zoom. The frame is `touch-none`, and no click, pointer or touch event depends on those defaults.
- **The e2e change (r1 F7):** the unfalsifiable `visualViewport.scale` assertion is removed. The vitest `defaultPrevented` checks hold the preventDefault.

## Findings

### F1 — A trackpad pinch that spans a page change zooms the new face from the old face's view
- Label: [introduced] (the gesture handler is new in bc010658)
- Invariant: 4 ("Any page change … shows the new face at fit"). Supervisor to decide A or B.
- Severity: LOW-MEDIUM.
- Cause: the reset effect clears `pointers`, `press` and `pinch`, but the gesture handler's `start` is a local of the gesture effect, and nothing clears it on a resetKey change. The pointer pinch stops at a page change (held by "forgets a finger that was down when the picture changed"). The trackpad pinch carries on: the next `gesturechange` computes `zoomAbout(start.view, scale, start.origin)` from the previous face's view and applies it to the new face.
- Reproduction (temporary vitest probe P1, deleted): gesturestart(1) → gesturechange(2) → rerender `resetKey=1` → scale 1 (reset ok) → gesturechange(2.1) → `translate(-220px, -440px) scale(2.1)` → gestureend keeps 2.1. Reachable in desktop Safari when a slideshow tick (the slideshow does not pause while zoomed) or an arrow key lands mid-pinch.

### F2 — A mouse press released outside the frame disables the trackpad pinch, and the page cannot be zoomed either
- Label: [introduced] (the `pointers.current.size > 0` guard in `onStart` is new; the stale mouse entry itself is pre-existing, r1 "Checked")
- Invariant: none broken (6 still holds: the page is not zoomed). B unless the supervisor wants trackpad zoom in the list.
- Severity: LOW.
- Cause: the frame does not capture the pointer, so a mouse drag that ends outside the frame (over the top bar, outside the window) leaves its entry in `pointers`. `onStart` calls `preventDefault()` and then returns because `size > 0`. So a Safari trackpad pinch neither zooms the picture nor the page until the next click inside the frame.
- Reproduction (probe P3): pointerdown mouse id 9 with no pointerup → gesturestart/change(2)/end → scale 1, gesturestart `defaultPrevented` true.

### F3 — The gesture handler's behaviour is mostly unheld by tests
- Label: [introduced]
- Invariant: none listed (trackpad zoom was added by the user's decision after r1). A test gap. N9 and N11 break things a Safari user hits at once, so the supervisor should decide whether they count as A under "a test that lets an A through is an A".
- Survivors (want=kill, result live):
  - N11: `onChange` scales from `viewRef.current` instead of `start.view`. Safari's `scale` is cumulative since gesturestart, so every gesturechange would compound: a real pinch jumps to MAX_SCALE within a few events. The one test sends a single gesturechange.
  - N9: `onEnd` does not settle. A pinch-in below fit stays drawn at 0.5 (probe P4 shows it goes to `""`/settled 1 with the settle), no clamp at release, and `settledScale` goes stale.
  - N12: the zoom origin is ignored (always the top-left). The test only asserts scale.
  - N4: no preventDefault on gesturechange.
  - N8: no clamp during gesturechange (covered at release by the settle, so this one is near-equivalent).

### F4 — Invariant 10 in the folder gallery is not held
- Label: [introduced]
- Invariant: 10. A test that lets an A through is an A.
- Survivor: N14 (drop `face.kind` from ImageGallery's resetKey) is live. Only the archive has the spread-toggle/pair tests. In the gallery, toggling spread in LTR at index 0 or on a portrait/unknown page keeps `open:index:showRightHalf` unchanged. So without `face.kind`, the zoom would survive single → half, exactly r1 F2. Nothing would catch that regression.

### F5 — If gesturestart arrives before any pointerdown, a gesturechange after the last pointerup overwrites the pointer pinch's pan (unverified ordering)
- Label: [introduced]
- Invariant: 5/8 in spirit. B unless the ordering is shown on a device.
- Severity: LOW, a claim.
- Cause: `onStart`'s guard is the only thing that keeps `start` null on iOS. If both fingers land in one touchstart and WebKit dispatches gesturestart before the pointerdowns, `start = {view: FIT, origin}`. Any gesturechange after the last pointerup (while `start` is set) then replaces the settled pointer view with `zoomAbout(FIT, scale, gestureOrigin)`.
- Reproduction (probe P2b): gesturestart → pointer pinch off-centre, both lifted → `translate(-100px, -400px) scale(2)`. Then a late gesturechange(2) → `translate(-200px, -400px) scale(2)`: the view jumps. Apple's documented order has gestureend before the touchend of the lifting finger, which excludes the late gesturechange. Someone needs to verify this on an iPhone. A cheap guard would be clearing `start` in `onPointerDown`, but that is for the author to decide, not this reviewer.
