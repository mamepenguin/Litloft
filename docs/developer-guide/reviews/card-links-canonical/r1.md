- `CollectionDetail` (collections and playlists) wraps its FileGrid and FileList in `FileNavigationOverrideProvider`, so its cards never reach the changed `Link` branch.

A file that goes missing or to trash while a listing is open now opens `RightPaneFile`, which shows its `notFound` pane inside the drive (`RightPaneFile.tsx:92-96`). ## Findings

### F1: [introduced] invariant 2 (borderline), bucket proposal B. `frontend/src/lib/canonicalFileUrl.ts:48-58`
The link is now built from the listing's copy of `file.drive` and `file.folder_path`. The redirect built it from the row it fetched from the backend on every click (`app/files/[id]/page.tsx:52-54`).
Here is when that matters. A listing is on screen. The file's folder, or a parent folder, is renamed or moved, and the listing has not refetched yet. That can happen during the WS latency window, while the WS is disconnected, or on any surface that has no `useWebSocketRefresh`. The card then links to the old path. `FolderBrowser` opens on a folder that no longer exists. `RightPaneFile` still loads the file by id, so the file itself is found.
Evidence: on the parent, the card href is `/files/f1?sort=name&order=asc&nav=folder` for every `folder_path` I tried (search, collections/abc, addons/x, Notes). The href did not depend on the listing's snapshot, and the server used the current row. On HEAD, the href is exactly the snapshot's folder. `DriveHome` refetches on `drive.structure_changed` (`DriveHome.tsx:192`), so the window is small.
No behaviour depends on the prediction, and I found no test that holds either behaviour.

### F2: [pre-existing] invariant 1. `frontend/src/lib/canonicalFileUrl.ts` (`buildCanonicalFileUrl`) together with `app/drive/[name]/layout.tsx`
The file's own-folder URL collides with reserved drive subroutes when the file's top-level folder is named `search`, `addons`, or `collections/<x>`.
- `/drive/d/search?file=f1` matches `isDriveSearchPath`. The layout renders a fullscreen `RightPaneFile` with no tree.
- `/drive/d/addons/x?file=…` goes to the addon route.
- `/drive/d/collections/abc?file=…` goes to a collection page.

Reproduction: I ran the same script on both trees. The final URL is identical on each: HEAD's card href equals the redirect target on the parent, and both classify as search, collection or addon respectively. This commit only makes the card go there directly instead of through a 307, so the finding is not introduced.

## Is anything missing from the invariant list?

1. **Scope of "card or row".** The list does not say whether controls nested in a card count as pressing the card: the match timestamp pill (F5), and the favourite and menu buttons. Invariant 1 should either name the pill or exclude it.
2. **Freshness.** Invariant 2 compares the link with what the redirect would produce "for the same file", but the redirect reads the current row and the link reads the listing's snapshot (F1). The list should say which one is authoritative when the two disagree, or accept that a stale listing links to a stale folder.
3. **Not-found state.** For a file that went missing or to trash after the listing loaded, the list does not say what should happen: the app-level 404 before, the in-drive `notFound` pane now. If "stays in the drive" is the intended outcome, it could be declared.
4. **Collection and playlist parameters.** An invariant such as "a link never drops `collection` / `playlist` / `folder_play`", or "no card caller passes them", would pin down the one query that makes `/files/{id}` behave differently from the canonical URL. Today that holds only because of which callers exist.
