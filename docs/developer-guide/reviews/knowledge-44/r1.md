## Findings

### F1 [introduced] 不変条件: none（3 は「ready は PUT 成功後のみ」「GET/PUT 失敗は failed」で、B13 はどちらも破らない。破るのは「PUT 成功後の rename 失敗で failed に倒さない」という R-0 に無い性質 — 末尾 "Missing from R-0?" 参照）

- ミューテーション B13（`mark_ready()` を rename の後へ移動）が全 428 テストを通過。
- 観測できる fixture は書ける: `_make_client` の `rename_file` が `httpx.ConnectError`（`InternalClient` は transport 例外を `InternalAPIError` に包まず素通しする）を送出する、または `rename_file` 内で `_db_status` を記録して `"ready"` を期待する。実装では body 書き込み済み → `ready`、B13 では `finally` が `failed` に倒す。
- 既存の `test_a_failure_after_the_write_keeps_the_job_ready` は自作 hook（`mark_ready(); raise`）で `_publish` を検査しているだけで、`_publish_clip` 内の `mark_ready` の位置は検査していない。
- 利用者影響: 将来 `mark_ready` が PUT 直後から後ろにずれても検出されず、core への rename が transport エラーで落ちた clip が「本文は書けているのに Dashboard を開き直すと failed」になる。
- 区分案: B（R-0 に載れば A）。

### F3 [introduced] 不変条件: 2 / 7 に隣接（テストの穴）

### F5 [introduced] 不変条件: none（3 は満たす）

- PUT 成功後に `_mark_ready` の DB 書き込みが例外（例: SQLite `database is locked`）を送出すると、`marked` が False のまま `finally` が `_mark_publish_failed` を呼び、**本文は書き込み済みなのに** job は `failed`、`error = "publish: article body was not written"`（事実と逆）、rename も `knowledge.clip.ready` も出ない。
- 再現（一時テスト、実行後削除）: `ClipWorker._mark_ready` を `OperationalError` を投げるものに差し替え、`on_done=_publish_clip` で 1 job 実行。
  - PR `692fbd9`: `calls=['put'] status=failed error=publish: article body was not written`
  - 親 `e13cb66`: `calls=[] status=fetching error=None`（`_mark_ready` が `on_done` 前に落ち、PUT 自体が起きない）
- 同じ形はプロセスが PUT 応答待ちで落ちた場合にも出る: 親では PUT 前に `ready` 済み、PR では `fetching` のまま lease が残り、再起動後の `reclaim_stale_jobs`（空 credential）で保護ドライブなら GET 401 → `failed`（本文あり）。こちらはコードからの導出で、プロセス kill による再現はしていない。
- 利用者影響: 稀。Dashboard を開き直すと、本文の入ったノートの行が failed 表示。区分案: B。

### F6 [pre-existing] 不変条件: none（8 により本 PR の範囲外）

- GET/PUT 失敗（412/401/500）で job は `failed` になるが、`_publish` は `_on_fail` を呼ばないので `knowledge.clip.failed` は出ない（親も PUT 失敗時は無音 return）。ページを開いたままの Dashboard 行と Add メニュー経由の `pendingClips` はスピンし続け、閉じて開き直すと本 PR の lookup で failed になる。開いている画面と開き直した画面で結果が食い違うのは本 PR で見えるようになった。区分案: ledger。

## 確認したが finding にしないもの

- URL を共有する行: `Set` で 1 回だけ問い合わせ、応答の file_id ごとに settle（F3m で kill を確認）。
- 失敗行の再 clip: 重複ダイアログ（`ClipDuplicateDialog`）は `existing[0]` を開く導線のみで status を表示しないので、DB が `failed` になっても表示は変わらない。
- `GET /clips` は `(viewer_id, drive, url)` で絞り `limit(10)`。同 URL を別経路で 10 回以上 clip すると古い行の file_id が応答に無く fetching のまま残るが、これは 4 の想定内。
- StrictMode（開発時のみ）で effect が 2 回走り URL あたり 2 回問い合わせる可能性。本番ビルドでは起きず、settle は冪等なので未計上（未再現）。
- reclaim された job（`drive=""`）の失敗: `test_a_reclaimed_job_that_cannot_read_its_placeholder_reads_failed` が DB の `drive` 列で `GET /clips` に出ることを確認しており、9 を満たす。
