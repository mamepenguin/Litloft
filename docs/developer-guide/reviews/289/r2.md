## Findings

### G1 [introduced] B — the stale-response guard on `setDrivesLoading(false)` is held by no test

N03 (`finally { setDrivesLoading(false) }` unconditionally) survives all 89 tests. The test `does not mark the next opening's list as failed or loaded` cannot see it: no earlier opening ever confirmed a list, so `drives` is `[]` and Save is disabled for that reason alone.
With N03 applied, P07 and P14 fail. P14 is the case that matters: after an earlier opening confirmed `[photos]`, a stale response ends the current opening's loading, and Save is **enabled** before the current opening's list has arrived. That is a save against an unconfirmed list, which `destinationReady` exists to refuse. The guard is correct at `e77e2a77`; no invariant is broken, only undefended. Detector: seed a completed opening before the stale-failure/stale-success case and assert Save is disabled (or "Loading..." still shown) until the current response lands.

### G2 [introduced] B — a close and a reopen in one render leave the panel loading forever

P12: `act(() => { click Cancel; click "Quick note" })`. `openPanel` makes a new opening, but `open` never renders `false`, so the `[open]` effect does not call `loadDrives`. The only in-flight response belongs to the previous opening and is now discarded. Result: one `getDrives` call, "Loading..." shown, Save disabled, and no Retry offered (Retry is shown only when failed). At `59af18ae` the same probe passes, because the previous opening's response was applied.
Reach: none found today. The only `open` callers are the header trigger, the `N` shortcut and knowledge `NotesPage`'s button, each a separate discrete event, which React flushes separately, and the Save-and-open path closes before `router.push`, not before an open. Recorded because it is a new prediction the fix relies on: every opening goes with a `false -> true` render of `open`.

## 4. Trajectory

- `59af18ae` changes the footer layout only (`flex-wrap`, `shrink-0`, a component-fixture spec). It adds no branch, state or prediction to the container logic.
- `b767ead5` **removes** a state (`unresolvedRef`, a shared flag cleared by whichever response landed first) and `requestRef`. It **adds** a per-opening identity (`openingRef` object with an id, and `resolvedOpeningRef`) and one branch in three places ("response of an opening that is no longer current -> do nothing": `try`, `catch`, `finally`). The flag became an id comparison, so this is a replacement rather than an added special case.
- Nothing `b767ead5` adds repeats what `59af18ae` added, so the "two rounds in a row" pattern does not apply here. For context over the whole feature: the parent `553f15d9` passed "this is an opening" as an argument (`loadDrives({ reresolve: true })`); the feature moved that into a shared ref (F1); `b767ead5` moves it into a per-opening object. That is the same fact changing carriers twice, not more cases being piled on.
- The fix adds one prediction: that each opening starts its own fetch through the `[open]` effect (G2). If a later round adds a branch for that, for example a second fetch trigger keyed on the opening id, that would be the second added branch in this area.
