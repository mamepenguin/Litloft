## Findings

### F1 [introduced] A (narrow reach) — a late drive-list response from an earlier opening consumes the next opening's re-resolution

`loadDrives` no longer receives "this is an opening" as an argument; it reads and clears the shared `unresolvedRef` when *any* response lands (`QuickNoteContainer.tsx` `loadDrives`, `const reresolve = unresolvedRef.current; unresolvedRef.current = false;`). If opening 1's `getDrives` is still in flight when the panel is closed and opened again, opening 1's response re-resolves against its (older) list and clears the flag, and opening 2's own response then only "keeps the previous selection". When the accessible list changed between the two requests, the next opening lands on the wrong (still accessible) drive, and a requested drive (`open({ drive })`) is not preselected even though the confirmed list contains it — invariant 4 ("preselects that destination for that opening"). The same path also affects the header button's current-screen resolution, which the parent handled.

Reproduction (vitest, header only, runs unchanged against both trees):
```
driveState.current = "photos"; getDrives -> deferred promises
open (header) -> Cancel -> driveState.current = "notes" -> open (header)
resolve #1 with [photos]; resolve #2 with [photos, notes]
expect destination line to contain "notes / Inbox"
```
- `553f15d9` (parent): passes — the second call was `loadDrives({ reresolve: true })` and re-resolved to `notes`.
- `59af18ae`: fails — `expected 'Destination:photos / Inbox' to contain 'notes / Inbox'`.
- Same with `open({ drive: "notes", folder: "Projects" })` as the second opening: shows `photos / Inbox`.

Reach: needs the accessible-drive set to change between two `getDrives` requests that overlap (close and reopen within one slow request). The wrong destination is an accessible drive and is shown on the collapsed destination line, so nothing reaches a locked drive. Bucketed A only because it literally breaks invariant 4 and the doc-stated reason for re-resolving; the supervisor may well call it B given the reach.

### F2 [introduced] B — the `openRef` "no-op while open" guard is held by no test, and it is reachable

Mutation M09 (delete `if (openRef.current) return;` in `openPanel`) survives all 84 tests. The path is reachable: the quick-note `n` shortcut has `editingOnly` unset, and the shortcuts provider falls through to it while the panel is open whenever focus is on a non-field — the discard confirmation focuses **Discard**. Without the guard, pressing `N` there runs `setDiscardOpen(false)` / `setDestinationOpen(false)` / `setError(null)` and resets `requestRef`/`unresolvedRef` mid-opening, so the confirmation disappears without being answered.

Reproduction: open from header, type "text", press Cancel, wait for focus on Discard, `keyDown(discard, { key: "n" })`, expect Discard still present. Passes at `59af18ae`; fails with M09. The guard is correct today; no invariant is broken, only undefended. (Parent had the equivalent guard inside the `setOpen` updater, also untested.)

### F3 [introduced] B — the "invalid folder falls back to the remembered folder" test cannot tell remembered from default

`uses the drive's remembered folder when the given folder is not a valid path` stores no remembered folder, so its expected `notes / Inbox` is also the plain default. Mutation M05 (invalid folder -> `QUICK_NOTE_DEFAULT_FOLDER` instead of `readQuickNoteFolder(drive)`) survives. Decision (1) as documented in `ADDON-DEVELOPMENT.md` ("replaced by the drive's remembered Quick Note folder") is therefore not held. Detector rule 5: seed a remembered folder different from `Inbox`.

## Implementer decisions judged

1. Requested drive first, accessibility-checked against the fetched list; folder only with such a drive; invalid folder -> remembered; folder without drive ignored. Sound and drive-safe (M01, M02, M03, M04 killed). Only the fallback's dimension is untested (F3). `NotesPage` passes `drive = useCurrentDrive() ?? ""`; `""` is rejected by `!drive`, so no empty-drive request slips through.
2. Resolution on the first successful load of an opening (Retry re-resolves; post-403 keeps a manual choice). Fixes a parent defect (Retry after a failed load kept a previous opening's drive). Killed by M07/M08. The implementation of "first successful load of an opening" is where F1 lives.
3. `open()` no-op while open / outside provider. Correct; the while-open half is untested and reachable (F2).
4. Focus returns to the opener, else the header trigger. Killed both ways (M21, M22). Browser probe: after Cancel -> 破棄 focus returned to 新規ノート.
5. Same toast, per-button "Saving…", both disabled in flight, chord stays Save. Killed (M12, M16, M24, M26).
6. Navigation after close via `buildCanonicalFileUrl(file, file.id, { edit: "1" })` from the response. Killed for order and `edit=1` (M13, M14, M17). M18 (use selected drive/folder instead of the response's) survives — equivalent under the current backend, whose response `folder_path` equals the requested folder; recorded, not a finding.
7. Notes page passes a folder only on All notes with `folder` set, `""` included. Killed (M30, M31, M32, M33).
