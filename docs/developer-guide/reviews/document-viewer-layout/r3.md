## Findings

### R3-1 [pre-existing] The fill's resting colour is not held; with no resting value the fill disappears at rest

- Severity: low. Bucket suggestion: B (invariant 3 only says "no accent at rest"; a transparent fill satisfies it
  literally, but a fine-pointer reader then sees no position at all until hovering).
- What: removing the default `[--scrub-fill:var(--color-warm-silver)]` (P01) leaves the fill `transparent` at rest
  and survives C and E; so does changing it to `--color-text-muted` (P02). The only resting assertion is
  `expect(rest.fill).not.toBe(accent)`.
- Label: the same hole at the parent. At 3010d851c, dropping `bg-warm-silver` from `FILL_CLASS` (P01-parent) survives
  C and E. 6f6f24158 moves the resting value, it does not open the gap.
- Measured (probe, not a test): at HEAD the resting fill equals `--warm-silver` in light (`rgb(145,145,140)`) and dark
  (`rgb(122,102,104)`), both engines, and returns to it after hover in Chromium.
- Fix (cheap): in the rest case of `layout.spec.ts`, assert the fill equals the `--warm-silver` token (the probe
  pattern in `accent()` works for any token).

### R3-2 [pre-existing] WebKit (fixture): after a drag ends, the fill stays accent and the thumb stays shown until the next style recalc

- Severity: low; not measured against the optimised build or a real Safari. Bucket: ledger; worth a look during R-5
  on Safari.
- What: in e2e-epub WebKit, drag with the mouse, release, move the mouse away and wait 1.5 s: the row reads
  `data-dragging="false"`, `:hover` false, the input neither `:focus` nor `:focus-visible` (focus is on the book's
  iframe), yet the fill is still the accent and the knob opacity is 1. Forcing a recalc (toggling the row's
  `display`) restores warm-silver. Chromium returns to rest immediately.
- Label: identical at 3010d851c (fill accent, knob 1 after release), so not introduced by the variable.
- A flat and a nested `[data-dragging="true"] *` test rule injected into the same page both invalidated correctly on
  release, so it is not the attribute selector itself; the fixture's unflattened `@media (hover: hover)` nesting
  (already documented as a WebKit fixture limitation in `layout.spec.ts`) is the likelier cause. Recorded because
  if it reproduces in Safari it breaks invariant 3 ("at rest on a fine pointer ... no thumb and no accent colour")
  after every drag.

## Question 1: does 6f6f24158 do what it claims, and what did it break

**Claim holds.** Reverting only the production file to 3010d851c while keeping the new test (P11) fails the
keyboard-focus case in both engines: the parent's `peer-focus-visible:bg-accent` on the fill never matched, because
the fill is a child of the track, not a sibling of the `peer` input. With the variable set on the track (the input's
sibling) and inherited by the fill, a focused slider now draws an accent fill (P05 killed, both engines).

**What it broke: nothing measured.**

- Hover (Chromium): fill accent on hover, light and dark (probe); dropping the hover setter is killed (P04). WebKit
  hover is not applied in the fixture, as documented in the spec.
- Drag: fill accent while held (probe, both engines). Dropping the drag setter (P06) is killed by C on Pixel 5 only;
  on desktop Chromium hover masks it (under pointer capture the row stays `:hover` even with the pointer 300 px
  off it), and the e2e-epub drag step does not read the fill. Held, once.
- Rest: warm-silver in both themes and both engines (probe), and back to warm-silver after hover in Chromium. The
  resting value itself is unheld (R3-1, pre-existing).
- Coarse drag colour (knob `pointer-coarse:group-data-[dragging=true]/scrub:bg-accent`): killed by C on Pixel 5
  (P09).
- RTL fill (`right: 0` in RTL): killed by V (P10). Not touched by the commit.
- The fill reading a fixed colour instead of the variable (P07): killed by C (both projects) and E.
- `peer-focus` for `peer-focus-visible` on the new setter (P08): live, as declared in r2 (N14): a pointer press
  never focuses the input.
- The accent at rest (default set to accent, P03): killed by E.

## Question 2: is the touch-screen case actually coarse and actually full screen when it measures

Yes, measured with a probe copying the case's steps (Chromium, `hasTouch` + `isMobile`):

- `(pointer: coarse)` and `(hover: none)` both match at the measurement, not only at the assertion before the click.
- `document.fullscreenElement` is the `epub-frame`: this is **native** element full screen (Chromium has
  `requestFullscreen`), not the pseudo path. The frame is 390 x 800, the chrome is 89 px (88 + the 1 px border),
  opacity 1, not `aria-hidden`; the panel is 390 wide (the sheet) and its bottom equals the chrome's top.
- It kills the coarse sum: `pointer-coarse:[--epub-bar:5rem]` (P12, r2's N04, now killed), a coarse scrub row of
  `h-10` (P13, also killed by C), and dropping `+ 1px` (P14).

Two observations, not filed:

- The preview page has no viewport meta, so under `isMobile` the inline page lays out at 980 px (`innerWidth` 980,
  frame 980) whatever `setViewportSize` says; only native full screen brings the frame to 390. The case measures
  only after entering full screen, so it is unaffected, but an inline coarse case written the same way in this
  fixture would be measuring a 980 px layout.
- A phone that has no `requestFullscreen` (iPhone) takes the pseudo path. Forced in the harness (removing
  `requestFullscreen`), the pseudo path at 980 px opens the popover 8 px above the chrome, which is correct for
  that width; the pseudo sheet cannot be measured without the viewport meta. With a zero safe-area inset the two
  paths share the geometry that matters here (`--epub-bar`, `--panel-base`), so the native case holds the coarse sum
  for both; the inset difference is R2-5.
