## Findings

### R1-1 [introduced] In full screen the panel covers the bar's top border (1 px overlap)

- Severity: low. Bucket suggestion: A (invariant 7, "in full screen it sits above the bar and never overlaps it"), trivially small.
- What: `--epub-bar` is 3.75rem / 5.5rem, the bar's own height (20+40 / 44+44). In full screen the bar sits inside
  `epub-chrome-bottom`, which adds `border-t` (1 px) on top of it, so the chrome's top edge is 1 px higher than
  `--panel-base`. The sheet's bottom lands on the bar's top, i.e. over the chrome's border line; the popover's gap
  is 7 px instead of the 8 px it has inline. Inline the border is outside the book box, so inline is exact.
- Evidence (temporary probe spec in e2e-epub, native full screen, both engines, 800 px tall):
  width 390 sheet: `panelBottom 740, chromeTop 739, barTop 740`; width 1000 popover: `panelBottom 732, chromeTop 739`.
  At the parent the panel bottom was 752 vs chrome top 759 (7 px gap, full-width panel) - the overlap is new.
- Fix: base the full-screen offset on the chrome box, e.g. `--panel-base: calc(var(--epub-bar) + 1px)` in full
  screen, or move the border onto the bar so `--epub-bar` measures the whole chrome.

### R1-2 [introduced] The bled canvas still draws a rounded card for the EPUB error state and the PDF loading skeleton

- Severity: low. Bucket suggestion: B (invariant 1 speaks of the viewer box; these are its stand-ins).
- What: the radius reset keys on `[data-viewer-frame]`, which only the PDF root and the EPUB frame carry.
  `EpubPreview`'s error return (`w-full rounded-xl bg-bg-card`, EmptyState + download) and `FilePreview`'s PDF
  `loading` skeleton (`h-96 w-full animate-pulse rounded-xl`) are also the wrapper's first child, now edge to edge
  (the wrapper's negative margins apply to them) but still rounded, i.e. a 12 px-radius card flush to the canvas edges.
- Evidence: `EpubPreview.tsx` error branch, `FilePreview.tsx` PdfPreview `loading`; bleed rule keys on the wrapper
  (`globals.css` `.media-detail-player[data-bleed="true"]`) and the radius on `[data-viewer-frame]` only.
- Fix: key the radius reset on the wrapper's first child (`.media-detail-player[data-bleed="true"] > :first-child`)
  instead of a marker attribute, or add the marker to those two boxes.

### R1-3 [pre-existing] In full screen, an open panel's cover lies over the bar

- Severity: low. Bucket: ledger (pre-existing).
- What: the panel container (`absolute inset-0 z-10`) fills the book box, which in full screen is the whole frame,
  so the cover also sits over the overlaid bar: with the contents open, pressing Aa or the slider only closes the
  panel. `elementFromPoint` at the first bar button and at the slider's centre returns `epub-panel-cover`, in both
  engines, at 1000 and 390 px - at HEAD and identically at cb329495e (the parent's `DismissScrim` was the same
  `absolute inset-0 z-10`). Keyboard switching still works (existing test). Not made worse here.

### R1-4 [introduced] `tsc --noEmit` fails on the component fixture (CI red)

- Severity: high (blocks the frontend tsc job, `.github/workflows/ci.yml` "frontend (tsc / eslint)").
  Bucket by the table: none of A/B/C - it is an error check; fix before merge.
- What: 4f266914d changed `EpubBarArrangement` to `({ loading = false }: { loading?: boolean })` and it is still
  registered in `ARRANGEMENTS: Record<string, () => ReactElement>`.
- Evidence: `pnpm -s tsc --noEmit` -> `e2e-components/fixtures/app.tsx(1853,3): error TS2322 ... Target signature
  provides too few arguments. Expected 1 or more, but got 0.` (the only error in the run). The e2e run is green
  because Vite does not type-check.
- Fix: register a zero-argument wrapper for `"epub-bar"` as was done for `"epub-bar-loading"`, or give the
  parameter a default (`{ loading = false }: { loading?: boolean } = {}`).

### R1-5 [introduced] Nothing holds that the real PDF and EPUB roots are the boxes the radius rule reaches

- Severity: medium. Bucket suggestion: A (invariant 1, "0 px radius", lets a regression through).
- What: `document-bleed.spec.ts` measures a stand-in `<div data-viewer-frame>` in the fixture; `MediaShell.test.tsx`
  checks only `data-bleed` on the wrapper. Dropping `data-viewer-frame` from `PdfPreview`'s root (M07) or from the
  EPUB frame (M08) leaves every suite green, and the shipped viewer is then a rounded card flush to the canvas edges.
- Fix: preferably remove the marker and key the reset on the wrapper's first child (also fixes R1-2); otherwise
  assert the attribute on the real roots (a jsdom row per viewer is enough, the geometry is already held by the fixture).

### R1-6 [introduced] Panel placement in full screen is not held by any test

### R1-7 [introduced] The coarse-pointer drag state (20 px accent thumb, accent fill) is not held

- Severity: medium. Bucket suggestion: A (invariant 3: "on hover, focus or drag it draws the accent thumb and track";
  on a coarse pointer drag is the only way in).
- What: removing the coarse drag knob classes (M23), the drag fill colour (M26) or setting `data-dragging={false}`
  outright (M31) survives. On desktop the hover state masks all three (the mouse is over the row while it drags);
  the Pixel 5 project has no drag case.
- Evidence: a temporary probe in e2e-components (Pixel 5, CDP `Input.dispatchTouchEvent`) measured HEAD correctly:
  dragging `knob 20px rgb(214,48,49)`, fill accent, track 4 px; at rest `knob 8px rgb(98,98,91)`, fill
  `rgb(145,145,140)`, track 2 px. So the code is right today; only the guard is missing.
- Fix: add that touch drag case to `epub-bar.cases.ts` (coarse project).

### R1-16 [introduced] The iOS real-device check on the panel container is still outstanding

- Severity: medium (unverified hazard). Bucket suggestion: B until measured; A if it reproduces.
- What: the touch-point list requires "a real-device check: the panel container on the iOS simulator", and the
  author states it has not been run. The code does keep the iframe outside the `@container` box (the container is
  a sibling of the iframe inside the book box, rendered only while a panel is open), which is what S-11 asked for,
  but the globals.css hazard is recorded for a container *around* an iframe; whether a size container beside a
  same-origin iframe, inside a `position: fixed` pseudo-full-screen frame, is safe on iOS WebKit has not been
  observed. Note also that `container-type: inline-size` implies layout containment, so any `position: fixed`
  descendant a panel grows later would be positioned against the container.
- Fix: run the check (inline and pseudo full screen, portrait and landscape, both panels) before merge (R-5).
