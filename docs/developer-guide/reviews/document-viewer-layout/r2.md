## Findings

### R2-1 [introduced] The coarse half of the full-screen panel placement is still unheld (R1-6 fixed for fine only)

- Severity: low-medium. Bucket suggestion: A (invariant 7, "in full screen it sits above the bar and never
  overlaps it", on a coarse pointer).
- What: the new full-screen cases in `e2e-epub/layout.spec.ts` run in the e2e-epub projects, which are both
  fine-pointer desktop profiles. `pointer-coarse:[--epub-bar:5.5rem]` -> `5rem` (N04; r1's M12) survives every
  suite (V, C, E). `--epub-bar` is a hand-written sum of the two rows' heights (`h-5`/`h-11` + `h-10`/`h-11`), so a
  coarse row change drifts the coarse panel offset silently; on a phone in full screen the sheet would then cover
  (or float above) the bar.
- Evidence: mutation table N04. The fine half is now killed three ways (N01-N03, N05-N07).
- Fix: one coarse full-screen panel case. e2e-epub has no coarse project; either add a Pixel 5 project for this
  spec, or emulate `pointer: coarse` for the one case. Alternatively measure the bar instead of restating its
  height in a variable (see "Question 3" below).

### R2-2 [introduced] The PDF loading placeholder's new marker is not held

- Severity: low. Bucket suggestion: B (r1 put R1-2 in B; the placeholder is a transient stand-in).
- What: 3010d851c adds `data-viewer-frame` to the `next/dynamic` loading placeholder in `FilePreview.tsx` with no
  test; removing it (N11) leaves V, C and E green. The other three markers are now each held by a jsdom row
  (N08, N09, N10 killed). Code added by the fix without a guard.
- Fix (cheap): not worth a harness of its own; either accept as B, or render `FilePreview` for a PDF before the
  dynamic import resolves and assert the placeholder carries the marker.

### R2-3 [introduced] The keyboard-focus case does not hold the accent track (R1-8 fixed for thumb and ring only)

- Severity: low. Bucket suggestion: A (invariant 3, "on hover, focus or drag it draws the accent thumb and track").
- What: the new `layout.spec.ts` case asserts knob opacity 1 and a non-`none` box-shadow on the track, but not the
  fill colour. Removing `peer-focus-visible:bg-accent` from `FILL_CLASS` (N23) survives E and C; the focused slider
  then shows an accent thumb on a grey fill. The fill was always accent at the parent (cb329495e), so the
  focus-only accent is behaviour this branch introduced. r1's R1-8 fix text listed "fill accent" among the three
  assertions; the fix took two.
- Fix: in the same case, assert the fill's `backgroundColor` equals `accent(page)` (the helper is in the file).

### R2-4 [introduced] The full-screen cases wait on an opacity-blind `toBeVisible()` and race the chrome's 2 s idle hide

- Severity: low. Bucket suggestion: B (fails loud as a timeout, never a false green).
- What: `await expect(page.getByTestId("epub-chrome-bottom")).toBeVisible()` passes whether the chrome is shown or
  withdrawn: `useAutoHidingChrome` withdraws with `opacity: 0` + `inert` + `aria-hidden`, and Playwright counts
  `opacity: 0` as visible. The case therefore depends on reaching the `getByRole("button", { name: "Text settings" })`
  click within `CHROME_IDLE_MS` (2000 ms) of entering full screen; after that the button is `aria-hidden`, the role
  query finds nothing, and the case times out. Once the panel is open the chrome is held, so the measurement itself
  is sound.
- Evidence: a temporary `waitForTimeout(2500)` after the `toBeVisible()` line: the chrome read `opacity 0,
  aria-hidden=true`, and all four full-screen cases (both engines, both widths) timed out on the click (restored).
  Unmodified, the case clicks within a few hundred ms, so this is flake headroom on a slow CI runner, not a
  present failure.
- Fix: wait for the thing clicked, e.g. `await expect(chromeBottom).not.toHaveAttribute("aria-hidden", "true")`
  immediately before the click, or move the mouse over the frame first if that counts as activity; or drop the
  `toBeVisible()` line, which holds nothing.

### R2-5 [pre-existing] In native full screen with a bottom safe-area inset, the panel offset leaves out the chrome's inset padding

- Severity: low; unmeasured (the harness cannot set safe-area insets). Bucket: ledger.
- What: the chrome carries `paddingBottom: env(safe-area-inset-bottom)` in both full-screen modes. In pseudo full
  screen the book box also stops at that inset, so `--panel-base` (measured from the book box) lines up. In native
  full screen the book box is `inset-0`, so the chrome's top is `inset + bar + 1px` above the frame bottom while the
  panel sits at `bar + 1px`: a sheet overlaps the bar by the inset. `viewportFit: "cover"` is set in
  `app/layout.tsx`, so the inset is non-zero on a device with a home indicator where element full screen is native
  (iPadOS). The parent (cb329495e) had the same shape (`calc(2.5rem + 0.5rem)` with the same padded chrome), so this
  is not made worse by the branch. Recorded because it is the next term the `--panel-base` restatement would need
  (see the trajectory answer).

## Question 2: trajectory

Read in order:

- 983dccc16: the feature. Introduces two restatements that later rounds touch: `--epub-bar` / `--panel-base` restate
  the full-screen chrome's height (row heights summed by hand into a variable), and `data-viewer-frame` enumerates
  which boxes the bled radius reset applies to.
- 4f266914d: tests and the review record only. No branch, state or prediction.
- 669d5c3e4: a fixture wrapper for a type error. No production change.
- 3010d851c: the first fix round with production changes. It adds one term to the `--panel-base` prediction
  (`+ 1px` for the chrome's border) and two entries to the marker enumeration. It adds no branch and no state.

So no two consecutive rounds have added to the same branch, state or prediction: 3010d851c is the only round that
touched production code after the feature. **By the R-4 test this is not yet a C.**

But both of its production edits are of the shape the trajectory rule watches for: each extends a restatement
by the case the round before did not anticipate. Both restatements still have open terms:

- `--panel-base` does not include the chrome's bottom inset padding in native full screen (R2-5), and its coarse
  value is unheld (R2-1). A next round that adds `+ env(safe-area-inset-bottom)` to it would be the second
  consecutive round adding a term to the same prediction.
- The marker enumeration is now complete as far as I can find, but it is a list that a new stand-in (another
  loading state, another error card) would silently miss; r1 offered `.media-detail-player[data-bleed="true"] >
  :first-child` as the shape that removes the list.

A fix that removes the prediction (anchoring the panel box to the chrome's measured top, or placing the panel
container above the chrome in the flow rather than offsetting it by a restated height) would converge; another
added term would not.

## Question 3: what the `+ 1px` couples to

- **The chrome's `border-t` width.** Held: `border-t-2` (N05) and no border (N06) are both killed by the fine
  full-screen cases in both engines, and so is `+ 2px` (N07). The border is pointer-independent, so fine coverage is
  enough for this coupling.
- **The two rows' heights, through `--epub-bar`.** The variable is a hand sum (`3.75rem` = 20 + 40, `5.5rem` = 44 +
  44). The fine sum is held twice (row heights by the inline cases, the sum by the full-screen cases, N03). The
  coarse sum is held by nothing (N04, R2-1).
- **The chrome's padding.** In pseudo full screen the book box and the chrome both stop at the bottom inset, so they
  agree; in native full screen they do not (R2-5, pre-existing, unmeasurable in the harness).
- The inline mode does not use the term (`0px`); the inline bar's own `border-t` sits outside the book box, so there
  is no inline coupling.
