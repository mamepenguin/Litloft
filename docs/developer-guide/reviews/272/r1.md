## Findings

### F1 [pre-existing] bucket B (supervisor may read it as A): the full-screen file host's URL-sort normalisation is held by no test

Invariant 5: "A file opened with that value in its URL gets folder order for previous/next." There are two file hosts. `RightPaneFile` goes through `resolveFileNavOrdering` (`normalizeSortParam` then `NEIGHBOURS_SORTS`), and this PR added a component test for it. `FileDetailFullScreen.tsx` passes `normalizeSortParam(searchParams.get("sort"))` straight into `useFileNav` (so `/neighbors`), `buildNavUrl` and the gallery's `getDriveFiles`, with no `NEIGHBOURS_SORTS` behind it. The only thing holding that call is the unit test on `normalizeSortParam` itself.

MF8 deletes the call at the call site (`const sort = searchParams.get("sort") ?? undefined`), and `FileDetailFullScreen.test.tsx` stays green (14 passed). With that mutation, `/files/{id}?sort=updated_at` in full screen sends `sort=updated_at` to `/neighbors` (422, arrows stay disabled) and, at this SHA, to the image gallery's listing call, which now answers 200 in `updated_at` order. So the gallery and the arrows walk different orders.

Label: the call site and its test file are unchanged by this PR, and at `ee9717ce` the same mutation also goes unseen (the listing 422s there instead). So the gap is `[pre-existing]`. The PR changes what the mutated path does (a gallery that loads in the wrong order instead of an empty one), and it added the matching test only for the other host.

### F2 [introduced] bucket A (test gap on invariant 4): `test_the_existing_sort_values_still_answer` cannot observe `created_at`, `file_size` or `liked_at` order

Invariant 4: "The existing listing sort values (`created_at`, `title`, `file_size`, `liked_at`, `random`) order exactly as before." The new parametrised test asserts an order only for `title`. For the rest it asserts `status_code == 200`, and its `_seed` fixture could not tell orders apart anyway: every row has `created_at=BASE` and `file_size=1`, so both sorts reduce to id order, and no row is liked.

Mutations MB9 (`created_at` -> `updated_at`) and MB10 (`file_size` -> `updated_at`) survive the new file and all 14 test files that call the listing (357 passed). A fixture can separate them, so these survivors are not inert: rows whose `created_at` / `file_size` order differs from their `updated_at` order (as `test_the_order_does_not_follow_created_at` already does in the other direction). MB12 (`liked_at` -> `updated_at`) survives `test_api_likes.py` too. That is the `onupdate` trap: liking a row writes `liked_at` and bumps `updated_at` through `onupdate` in the same UPDATE, so the two orders match in any fixture that likes rows through the API and edits nothing afterwards.

`created_at` is the default sort of every folder listing, so this mutation shape (one wrong column name in the `getattr` line this PR widens) would reorder every folder with no test failing. Label: the test that claims the invariant is in a file this change creates. The same survivors exist at `ee9717ce`, where nothing claimed the invariant.
