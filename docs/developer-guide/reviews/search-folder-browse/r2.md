## Q1 — F1: "/" during composition

What the fix does: `onChange` skips the browse start when `nativeEvent.isComposing === true`, and
otherwise still requires `previous === "" && next === "/"`.

Measured (jsdom, temporary probe test, deleted), same probe on both SHAs:

| sequence | `2365027f6` | `be63ea940` |
|---|---|---|
| plain `change` "" → "/" (no composition) | browse, value "" | browse, value "" (existing test, still green) |
| Chrome order: compositionstart, input "/" (isComposing), Enter keydown 229, input "/" (isComposing), compositionend | browse starts on the first composing input; ends in browse mode with filter "/" | **never browses**; value "/", no folder-tree request |
| Safari order: compositionstart, input "/" (isComposing), compositionend, input "/" (isComposing false) | browse, value "/" | **never browses**; value "/" |

Why the committed "/" can never start browsing now: every composing input goes to `setQuery(next)`,
so by the time the composition commits `query` is already "/". `startsRootBrowse("/", "/")` is false,
and React does not even fire `onChange` for a commit whose value equals the current value. This holds
whichever order the browser uses for `compositionend` vs the last `input`.

Not verified: real Chrome/Safari event order and whether the macOS Japanese IME puts a half-width "/"
into marked text. I could not drive an IME from this environment. From platform knowledge (unmeasured):
the macOS Japanese IME and Google Japanese Input in kana mode put punctuation, including "/" set to
half-width, into marked text awaiting confirmation, and Chrome reports `isComposing: true` on every
`input` inside a composition including the committing one. If that holds, a kana-IME user can no
longer start browsing with "/" at all. Where an IME inserts "/" without a composition (direct-input
symbol setting; Android keyboards that commit punctuation directly — unmeasured), it still works.

### F1 [introduced] medium — a composed "/" now never starts browsing, against the spec decision the "/"-in-onChange design exists for
- Difference vs `2365027f6`: table above. Before: browse started mid-composition (r1 F1). After: browse
  never starts for any "/" that goes through a composition; "/" stays as search text and file search
  runs for "/".
- Spec "Decisions after the spec review": "/" is detected in `onChange` "so kana IME and Android
  keyboards that report keyCode 229 still reach the root with a half-width '/'". For the kana IMEs that
  compose symbols, that reach is now gone; the fix removed the hazard by removing the feature on that path.
- No R-0 invariant covers IME, so this is not an A by the list. It is the user's call whether "kana IME
  users type `/` then get no browse" is acceptable; if not, supporting it needs the pre-composition
  query (or a compositionend-time decision), i.e. another state — see trajectory.
- The new test ("does not start browsing on a / typed while composing") holds only the mid-composition
  half and does not show what happens on commit, so it cannot tell "deferred to commit" from "dropped".

### F2 [introduced] low, unverified on a device — tapping › on a touch device raises the on-screen keyboard
- `focusInput()` now runs synchronously inside the › click handler, i.e. inside a user gesture. iOS
  Safari and Android Chrome show the soft keyboard for a focus in a user gesture. Before the fix, tapping

  `pointer-coarse`) brings the keyboard up over the lower part of the sheet. r1 F2 already flagged the
  phone case as "possibly deliberate". Whether this is wanted is a product call; the fix does not
  distinguish touch from keyboard. Not measured on iOS/Android.

## Q5 — trajectory

This is the first fix round, so the "two rounds in a row" test cannot fire yet. But plainly: this fix
adds a branch (the `composing` condition in `onChange`) and a prediction ("a composing input is never
the '/' trigger"). F1 above shows that prediction removes the kana-IME path the spec designed for; the
obvious repair (remember the query from before the composition and decide on commit) adds a state.
If the next round does that, it is the second consecutive round adding IME handling to the "/" trigger,
which is the pattern review-workflow.md calls a C. The alternative that removes rather than adds —
e.g. not treating composed input as a trigger and accepting that kana-IME users start browsing with →
on a Folders row or the › — would be a spec decision for the supervisor.
