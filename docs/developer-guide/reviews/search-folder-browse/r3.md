## Q1 — does the fix do what it says

**Entering a folder no longer moves focus.** Yes. Probe (temporary test, removed): desktop, focus
the "Browse trips" › and click it → `document.activeElement` is BODY, not the input (same as
`2365027f6`; at `be63ea940` it was the input). The keyboard paths (→, "/") call `enterFolder` with
focus already in the field, so nothing changes for them. The › is `hidden … pointer-coarse:flex`
(LauncherRow), so only touch-pointer devices can reach the focus loss, which is the case the user
accepted.

**r2 F4 test cleanup.** Correct. The `it.each` "does not record the filter text…" now asserts its
own table value (`/files/r1` for the filtered row, `/drive/main` for the folder); M2 below shows the
value is live. The "opens %s on Enter" title no longer claims a history check it does not make.
The deleted › focus test held the behaviour this fix removes, so deleting it is required, not lost
coverage.

**User-guide "/" text vs code.** Matches, measured in jsdom with a temporary probe:

| sequence | result |
|---|---|
| Safari order: compositionstart, input "/" (isComposing), compositionend, input "/" (not composing) | no browse, value "/" |
| Chrome order: compositionstart, input "/" ×2 (isComposing), compositionend | no browse, value "/" |
| then clear the field and type "/" directly | browse starts |

So a "/" from a composition is searched as text, and a directly typed "/" in an empty field still
starts browsing. Only the mid-composition half is held by a committed test (M4); the commit half
holds because React fires no `onChange` for a commit whose value equals `query` — not a finding, no
line of this fix touches it. Real IME event order was not measurable here (same caveat as r2).
