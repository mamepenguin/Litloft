## Findings

### F-1 [introduced] 不変条件 2 — 空 `file_ids` の早期 return を守るテストが消えた

- 親のテスト `renders nothing when the feed is empty` にあった `expect(mockBatch).not.toHaveBeenCalled()` がこの変更で削除され、置き換えの `it.each("never draws anything when the feed is empty")` は `batchGetFiles` の mock が即座に `[]` を返すので、早期 return を消しても通る。
- ミューテーション M12（`if (page.file_ids.length === 0) { setFiles([]); return; }` を削除）: 新テスト 12 passed = SURVIVED。親のテストファイルを同じ mutant に当てると `renders nothing when the feed is empty` が落ちる（親との差を確認済み。未変更の新コンポーネントに親テストを当てるとこのテストは通る）。
- 観測可能か: probe P2b（空フィード + `batchGetFiles` を pending のままにする）で mutant は `container.firstChild` が非 null → KILLED。未変更コードでは通る。
- ユーザーから見た結果: 本物の `batchGetFiles([])` は `POST /files/batch/get` を投げるので、その往復の間 `total=0, loading=true` で skeleton 行と「See all (0)」が描かれ、応答後に消える。まさにこの PR が消そうとした「出て消えるセクション」が、早期 return 1 つの削除で戻ってもテストが緑のまま。
- 対処の方向: 空ケースで `batchGetFiles` を呼ばないこと（または pending の batch 中に何も描かないこと）を assert に戻す。

### F-2 [introduced] 不変条件 1・2 — 「一瞬も描かない」テストが初回フレームと一過性の描画を観測できない

- 対象はこの変更で作られたテスト `draws nothing until the feed answers, then a loading row with its count` と `it.each(... "never draws anything when %s")`。
- 構造上の理由: (a) `MutationObserver` は `render()` の後に observe を始める。`render()` は act 内で初回 commit と effect（`setTotal(null)` 等）まで流し切るので、初回フレームで描いて effect で消した分は observe 開始前に終わっている。(b) コールバックは `MutationRecord.addedNodes` を見ず、コールバック時点の `container.firstChild` を読むので、同じマイクロタスク区間内で追加→削除された描画は `false` として記録される。
- ミューテーション M21（`useState<number | null>(null)` → `useState<number | null>(0)`。初回 render で `total=0, loading=true` → skeleton と「See all (0)」を 1 render だけ描き、effect の `setTotal(null)` で消える）: 新テスト 12 passed = SURVIVED。
- 観測可能か: probe P1（observe を render 前に container へ張り、`addedNodes` を集計、`takeRecords()` で取りこぼしも回収）で mutant は added > 0 → KILLED、未変更コードは added = 0。P2（空フィード同条件）でも KILLED。
- ユーザーから見た結果: ブラウザでは passive effect は通常 paint 後に走るので、M21 のような退行は Home を開くたびに skeleton 行が一瞬出て消える。不変条件 1 が名指しで禁じる挙動だが、それを主張するテストが検出できない。
- 補足: 同じ理由で、M12 型の「マイクロタスク 1 つ分だけ描く」退行も firstChild 方式では拾えない場合がある（F-1 は mock が即時 resolve なのでそもそも描かれない）。

### F-3 [pre-existing] 不変条件 4・5 — ドライブ切替の競合（応答の順序逆転）を守る `cancelled` ガードがどれもテストされていない

- M8（`if (cancelled) return;` 削除）、M9（`if (!cancelled) setFiles(items)` → `setFiles(items)`）、M10（finally の `if (!cancelled)` 削除）はいずれも新テストで SURVIVED。親コンポーネント + 親テストに同じ変異を当てても 11 passed で生存するので pre-existing。
- 観測可能か（未変更コードでは全部通り、mutant で落ちる）:
  - P3: A の fetch を pending にして B へ切替、B が `{file_ids:["b"], total:12}` で完了した後に A が `{["a"], 300}` で応答 → M8 で B の行の件数が 300 になる。
  - P4: A の batch を pending にして B へ切替、B 完了後に A の batch が解決 → M9 で B の行に A のファイルが出る。
  - P5: A の fetch を pending にして B へ切替、B の batch が pending の間に A が reject → M10 で B の行が loading=false・files=[] になり消える（skeleton → 無 → ファイル）。
- 現在のコードは正しい。テストの穴のみ。pickup の応答が遅い状態でドライブを素早く切り替えると、ガードが退行した場合に前ドライブの件数・ファイルが次ドライブの行に出るが、それを止めるテストがない。

### F-4 [pre-existing] 不変条件 6 — drive が値あり → undefined に変わると前ドライブの行が残る

- probe P6: `drive="A"` で `{["a"], 300}` を描き切った後 `rerender(<PickupWidget drive={undefined} />)` → carousel（A のファイル、件数 300、See all なし）が残る。親コンポーネントでも同じく失敗するので pre-existing。
- no-drive 分岐は `setLoading(false)` しかせず `total` / `files` をリセットしない。既存テスト `renders nothing without a drive` はマウント時に drive がない場合だけを見ている。
- 到達性: 唯一のホスト `DriveHome.tsx` は `props={{ drive: driveName }}` で常に文字列を渡すので、現状ユーザーは到達しない。B 相当。

### F-5 [introduced] 不変条件なし — `total === null` ガードで独立に変化できなくなった項

以下はどの fixture でも挙動を変えられない（probe P1〜P8 でも差が出ない。P6 はベースラインで失敗するため除外）。いずれもガード `total === null` と load 開始時のリセットに包含されている。
- M13: 空 `file_ids` 分岐内の `setFiles([])`。load 開始時に `setFiles([])` 済みで、その間に `files` を書くのは cancelled ガード付きの別 load だけ。
- M16: no-drive 分岐の `setLoading(false)`。drive なしでは `total` は常に null（マウント時）で描画なし。F-4 の遷移でも、in-flight なら `total` は null、完了済みなら `loading` は既に false。
- M20: `totalCount={total ?? undefined}` の `?? undefined`。この行に到達する時点で `total` は非 null。
- M22: `useState(true)` の初期値。初回 render は `total === null` で return するので `loading` は読まれない。
- 挙動上の欠陥ではない。`loading` 状態の初期値・no-drive 分岐はもう意味を持たない、という実装上の記録。

### F-6 [introduced] 不変条件なし（記録済みの穴と矛盾） — `"the files cannot be read"` ケースは実装が満たさない性質を主張している

- `it.each` の 3 行目は「files が読めないとき何も描かない（一瞬も）」と主張するが、R-0 の記録どおり実装は batch の往復中 skeleton を描く。テストが通るのは mock の `mockRejectedValue` がマイクロタスク内で reject し、F-2(b) の firstChild 方式がその区間を見ないからにすぎない。
- 再現 probe P8: fetch `{["a"], 3}`、batch を pending にして 1 tick 流す → `container.firstChild` 非 null（skeleton 行）→ reject 後 null。結果 `{ mid: true, end: false }`。
- 読者への影響: この名前を信じた人は「記録済みの穴は塞がっている」と判断するか、遅い batch の fixture に書き換えた途端に落ちるテストを「実装のバグ」として直しにいく。記録と矛盾する主張なので、この行は削除するのが妥当（最終状態が null であることを見たいなら、"一瞬も" を主張しない別の形で）。

## 非該当として確認したもの

- StrictMode の二重 effect: probe P7（`<StrictMode>` で `{["a"], 300}`）で件数 300・ファイル a・carousel 1 つ。問題なし。
- `total > 0` かつ `file_ids` 空: `total` が入り `loading=false, files=[]` で null。不変条件 2 どおり。
- Home のレイアウトジャンプ: スロットは ContinueWatching と Recently Viewed の間にあり、pickup がある drive では応答到着時に下の行が 1 行分押し下がる。これは「件数が分かるまで描かない」という決定そのものの帰結で、R-0 にも目的にも反しないので finding にしない。

## Missing from R-0?

- F-3 の競合（遅れて届いた前ドライブの応答が次ドライブの件数・ファイル・loading を上書きしない）は不変条件 5 の「keeps neither the previous drive's files nor its count」に読み込めるが、「切替後に遅延到着した応答」を明示していないため、テストは逐次切替だけで満たしたことになっている。明示するかは supervisor 判断。
