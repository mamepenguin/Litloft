## Findings

### F1. A new hold's wait ends on the answer to an earlier, superseded request
- Label: `[introduced]` (`shellImmersive.ts` is created by this commit).
- Invariant: 10's page counterpart ("the wait must end on the answer for the final state"; not yet written in
  `invariants.md`, see the question below). Through Phase 3's `ready` consumer: 5.
- Evidence: `shellImmersive.ts:46-51` — the listener accepts any `page.immersive.applied` with `active: true`;
  `:60-63` starts a new wait on every 0 -> 1 flip while the previous flip's answer may still be in flight. The
  answer carries no request identity, so it cannot be matched to the request that started this wait.
- Reproduction: P1. Shell side, per Phase 1 (`p1-r2.md`): each request laid out before the next arrives is
  answered on its own; requests that arrive before a layout are answered once, for the last. So the stale answer
  is only dangerous when (a) the page releases and re-acquires after the shell has laid out on #1 but before its
  answer reaches the page, and (b) the shell lays out the off before on #2 arrives. Then `b.ready` resolves in the
  wide viewport, which then narrows and widens again. If off and on #2 reach the shell in one turn, it coalesces
  and nothing moves, so the stale answer is harmless.
- Reach: none in Phase 2. The three viewers never read `ready`. It becomes reachable in Phase 3 through quick
  leave/enter during `"opening"` (a key pressed twice fast), where an early `ready` means `capture()`/`grow()`
  run before a narrow+widen. The window is about one shell layout plus the IPC delay.
- Direction: triage. The only complete fix is protocol-level (a request id echoed in the answer), which means
  reopening Phase 1's contract. The alternative is to accept the window as B and record it. No page-only guard
  can tell the two answers apart, since they carry the same `active` and the same size.

### F2. The `active` filter on the answer is held by no test
- Label: `[introduced]`.
- Invariant: 10's page counterpart (as F1). A test that lets an A through is an A.
- Evidence: M5 (drop `|| !message.active` at `shellImmersive.ts:47`) is live. The only test that sends
  `active: false` (`shellImmersive.test.ts:114`) sends it with the *wide* size (402x874) while the viewport is
  402x812. That answer could never match the viewport, so the filter decides nothing there.
- Reproduction: P2 kills M5. The case can happen in the app: the shell answers every `off` with the narrow size
  (Phase 1). If a hold is released and re-acquired and the `off` answer arrives after the new wait has
  subscribed, a filterless wait resolves at once in the narrow viewport. Phase 1's F2 stray `active:false` after
  a commit is another source.
- Direction: send `active:false` at the size the viewport already has, as P2 does.

### F3. `ready` means "the size matches", which can come before the `resize` event Phase 3 is exposed to
- Label: `[introduced]`.
- Invariant: 5 (Phase 3 consumer). **Device-only.** jsdom cannot order a layout-viewport change against an
  event dispatch.
- Evidence: `shellImmersive.ts:38-44` polls `documentElement.clientWidth/Height` every 16 ms. In WebKit a
  layout query returns the new layout-viewport size once the web process has applied the view-size change,
  but the window `resize` event is dispatched at the next rendering update. A 16 ms timer can run between the
  two. `useFrameTransition.ts:252-258` finishes every running animation on `resize`, so a `capture()`/`grow()`
  started from `ready` in that gap has its entry animation cut to the end.
- Reproduction: needs the simulator. Resolve `ready`, start a WAAPI animation on the same turn, and log whether
  a `resize` arrives after it. The plan already expects this ("wait one frame after the ack before
  `capture()`", Phase 3 checklist, and the HIGH risk).
- Direction: decide where that wait lives. If Phase 3 adds it outside `ready`, `ready`'s contract ("the viewport
  has the size") is sound but not enough for its only consumer. The other choice is to put it in `ready`. A
  `resize` after a size match is unambiguous, but none comes when nothing moves (landscape, where the size
  already matches when the answer arrives), so the wait must not depend on one then. Also note that on timeout
  `ready` resolves in whatever viewport the page has. That is the bounded fallback the spec accepts, and Phase 3
  will capture pre-widening in that case.

### F4. The width half of the viewport comparison is held by no test
- Label: `[introduced]`.
- Invariant: none reachable. Only a change of width alone after the answer (height unchanged) would tell the
  difference, and a rotation changes both.
- Evidence: M7 (compare `clientHeight` only, `shellImmersive.ts:21`) is live. Every test starts with the width
  already equal (`setViewport(applied.width, 812)`).
- Reproduction: P3.
- Direction: B. Record and close, or vary the width in the existing test if the width check is meant to stay.

## Device-only (not findings; for Phase 4 / R-5)

- **Invariant 7.** The three top bars are the only top-anchored controls in the viewers. Prev/next are
  `top-1/2`. The PDF viewer's `document-viewer-actions` slot (knowledge `MediaCaptureAction`) draws inside the
  top bar because the viewer strips the selection anchor (`PdfFullscreenViewer.tsx:297-318`), so its floating
  `top: max(8, …)` branch is not reached here. Whether 62 px clears the island in portrait, and that the landscape
  inset is 0, can only be measured on a device (M26-28 cannot be killed in jsdom).
- **Invariant 8.** Nothing in this commit touches `Header` / `h-below-header`. Whether `env()` updates in the
  same layout as the frame is the spec's "measured, not assumed" item.
- **F1/F3 inputs.** Whether `clientWidth/clientHeight` equal the shell's `webView.bounds.size`
  (`WebView.swift:139`) in both states. `viewport-fit=cover` is set (`app/layout.tsx:45`), so they should match,
  but a fractional bounds size (e.g. an iPad window) would never equal the integer `clientWidth`, and every
  open would then wait the full 1000 ms. Measure once.
- **Browser/PWA.** The padding changes nothing outside the shell only while `env(safe-area-inset-top)` is 0
  there. The PWA uses `statusBarStyle: "default"`, which should give 0; Safari is still to be confirmed (spec).

## Is anything missing from the invariants list (page side)?

1. **The page counterpart of 10, as its own line.** Something like: "A hold's `ready` resolves only on the
   answer to the request that started the current hold, or on the timeout; never on an answer to an earlier
   or opposite request." Item 10 as written binds only the shell. F1 and F2 break this line and no other.
2. **Outside the shell, the viewers' layout is unchanged.** The spec's Goal promises this (PWA and browsers stay
   as they are), and the new padding is the only thing that could break it. Item 1 covers waiting, not layout.
