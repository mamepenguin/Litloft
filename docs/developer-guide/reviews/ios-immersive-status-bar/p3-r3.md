## Q1 — Did `aecc894e3` do what it claimed, and what did it break?

- **r2 F1 (StrictMode never opens): fixed.** M1 is killed by both new StrictMode tests. S1–S9 show that under StrictMode every exit, unmount and "opening" path now behaves the same as without it.
- **r2 F2 (manual entry survives rotation during "opening"): held.** M5 is killed by the new test. The test is test-only, as the triage said.
- **r2 F4 (element-fullscreen manual session survives sitting up): held.** M6 is killed by the new test. The test also deletes `document.exitFullscreen` in `afterEach`, so nothing it defines leaks into later tests.
- **The history effect's unmount check.** On a real unmount, the mount effect is still defined before the history effect, so its cleanup runs first and the history cleanup sees `false` and skips the unwind. This is the same as before. M2 and M3 are both killed by "does not navigate when the component unmounts", and S2/S4 show the same result under StrictMode.
  - StrictMode's simulated unmount happens only at mount time. At that point `pseudoOpen` is false, so the history effect has returned without a cleanup, and the check is never consulted.
  - After the remount, the flag is `true` again, which is what the effect needs.
  - `useFrameTransition` returns a memoised object, so `exit` is stable. The history effect therefore never re-runs while open, and the only cleanup that reaches the check is the real unmount.
- **Correction to r2 finding 1's note.** Round 2 said the history check had "the same dev-only flaw" before the fix ([pre-existing]: under StrictMode an exit does not unwind the history entry). That does not reproduce: S1 and S3 pass at `b17a600ea`. `leave` unwinds the entry itself through `unwindHistoryEntry()` before the effect's cleanup runs, so the cleanup's check never decided an exit. The flag being stuck at `false` in development only mattered to the reader that `b860cadb6` added in `.catch`.
- **Broken by this fix:** nothing found. The `.catch` guard (M4, M10) and the rAF guard are unchanged and still killed. React `<Activity>` would also run these cleanups, but the app does not use it and `cacheComponents` is not enabled.
- **Still open from earlier rounds, unchanged by this commit:** r2 F3 (a second element-fullscreen request during "opening"; B), F5 (a late refusal after the session settled; B, pre-existing), and F6 (leaked holder cascades; B, pre-existing, visible again in M4 and M9).

## Q2 — Trajectory

The fix diffs in order:

- `b17a600ea` is the feature. It adds the `"opening"` phase, the hold, `pin`, and the `"opening"` return in `enter`.
- `b860cadb6` (round 1 fix) adds one guard in `.catch` (`!mountedRef.current || phaseRef.current !== "off"`) and removes the `"opening"` return in `enter`. Net branch count is unchanged.
- `aecc894e3` (round 2 fix) adds no branch, no state, no phase and no prediction. It changes the lifecycle of an existing ref, `mountedRef` (from #379), so that it tells the truth under a remount. Its test changes are four tests and one `afterEach` line.

No round repeats the kind of addition the round before it made. Round 2's warning was "another condition on the same `.catch` line would read as patching", and that line is untouched here.

One relation between the rounds should be named. Round 2's defect came from round 1's fix: round 1 gave `mountedRef` a reader in an asynchronous path, and round 2 made the ref correct for that reader. That is a fix inside the previous fix, which is the pattern the rules warn about. However, its shape removes a wrong assumption instead of adding a case, so the loop reads as converging, not as a design being patched.
