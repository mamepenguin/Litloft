## Question 2 — the trajectory

Only one fix round exists, so the rule's "two rounds in a row" cannot yet apply. Read on its own shape, the fix
**removes more than it adds**:
- removed: the "already holds → answer now" branch in `pageAsked` (and with it the prediction "asking for what
  already holds moves nothing"); the `Bool?` `pendingAnswer` (three states) and the `Bool?` `laidOutImmersive`
  with its first-callback guard (the `nil` state and the prediction "the first geometry callback precedes any
  page"); the `answerAfterLayout` hop.
- added: one condition, `laidOutImmersive == immersive`, in the single place that answers, and a second trigger
  (`setNeedsLayout` in `pageAsked` besides the one in the geometry callback).
The answer is now a function of state (owed, and laid out == requested) rather than of which event arrived
first — that is the loop converging, not a design being patched. The one prediction left is the ordering claim
("SwiftUI lays a change out before the web view's next layout"), and the fix no longer depends on it for
correctness: P-A and P-B show the added condition and the second trigger are exactly what keep invariant 10
when that order does not hold. If a later round adds another branch or state to this handshake, that would be
the second consecutive addition to watch for; this round is not it.

## Question 3 — the two expected survivors

Both are live in the suite (mutations 1 and 2, as the author declared). Neither is unreachable: a test reaches
each with one synchronous `webView.layoutIfNeeded()` between the request and SwiftUI's next update (P-A kills
mutation 2 with a stale 812pt answer in portrait; P-B kills mutation 1 with silence in landscape). Nothing in
the app issues such a layout today (`grep layoutIfNeeded ios/Litloft` → none), so in production they depend on
UIKit/WebKit not laying the web view out on its own before the hosting view — plausible but not guaranteed. See F1.

## Findings

### F1. The two guards the author expects to survive are reachable, and no test holds them
- Label: `[introduced]` (both lines are created by `584c64570`: the `laidOutImmersive == immersive` condition and
  `onImmersiveLaidOut = { webView?.setNeedsLayout() }`).
- Invariant: 10, but only under a web-view layout that runs before SwiftUI applies the change; natural run-loop
  ordering does not produce one.
- Evidence: `ios/Litloft/Web/WebView.swift` `webViewDidLayout` guard and `attachBridge`'s `onImmersiveLaidOut`;
  mutations 1 and 2 green in `ImmersiveTests`.
- Reproduction: P-A / P-B above (the coordinator is reachable from a hosted test as
  `webView.navigationDelegate as? Litloft.WebView.Coordinator`). Under mutation 2 the answer carries the
  pre-layout height (812 vs 874); under mutation 1 the landscape request is never answered.
- Direction: if these guards are meant to stay, the two probes are the tests that hold them; otherwise they are
  code the suite cannot distinguish from its absence. Triage decides.

### F2. An answer owed when a main-frame commit (or a WebContent termination) lands is paid to the next page
- Label: `[introduced]` (`answerOwed` is created by this commit; neither `didCommit` nor the termination handler
  clears it).
- Invariant: none (reads wrong). Invariant 3 holds (`immersive == false`); invariant 10 is arguably met (the
  answer matches the final, non-immersive state).
- Evidence: `ios/Litloft/Web/WebView.swift` `pageAsked` / `webViewDidLayout` / `didCommit`.
- Reproduction: P-C — `onPageImmersive?(true)` then `didCommit` → one `page.immersive.applied {active: false,
  402x812}` delivered. In the app that message goes to the page that replaced the one that asked (or is lost if
  the new page's bridge is not up yet). The spec's page resolves its wait only on `active: true`, so the stray
  `false` resolves nothing; it is an unsolicited message, not a wrong answer. At `92e1241a2` the same sequence
  was silent (coalesced true→false), while a commit after a laid-out immersive state sent an unsolicited ack
  there; at the SHA that second case is silent (answer not owed).
- Direction: optional; clearing `answerOwed` where immersive is reset would make the next page receive nothing.
