## Findings

### F1 — Two entries before the first rejection lands take two holds; one is never released
- **Label:** [introduced] (the hold is new in this commit; before it, a double entry only pinned twice, which was harmless)
- **Invariant:** 2 (immersive exactly while a session is open) and 6 (a second press leaves no hold)
- **Evidence:** `useFullscreen.ts:230-249`. The "opening" guard and `isFullscreenRef` are read synchronously in `enter`, but the hold is taken later, in the `.catch`. Two `enter` calls made before either rejection settles both pass the guard, and both catches run `holdImmersive()`. The second overwrites `immersiveRef` without releasing the first, so `holders` stays at 1 after exit.
- **Reproduction:** probe P5, in a v4 stub: `await act(async () => { toggle(); toggle(); })`, `widen()`, `exit()`. `posted` is `[{active:true}]` and never gets `{active:false}`, so the status bar stays hidden until a main-frame commit.
- **Reachability:** both calls must land before the first rejection settles. On an iPhone the WKWebView has no `Element.requestFullscreen` (the shell does not set `isElementFullscreenEnabled`; there is no match under `ios/`). The rejection then settles in microtasks of the same task, so two separate user events cannot interleave with it. The hole opens only where `requestFullscreen` exists and rejects asynchronously, e.g. an iPad or a future shell that enables element fullscreen. Only a device can confirm that.
- **Direction:** in the `.catch`, do nothing if an entry is already in flight: phase not `"off"`, or `immersiveRef.current` set.

### F2 — Unmount before a late rejection takes a hold after unmount
- **Label:** [introduced]
- **Invariant:** 6 (unmount leaves no hold)
- **Evidence:** `useFullscreen.ts:237-249`. The `.catch` does not check `mountedRef`, so a rejection that settles after unmount calls `holdImmersive()` with no cleanup left to release it.
- **Reproduction:** probe P6: `frame.requestFullscreen` returns a pending promise; `toggle()`; `unmount()`; reject; advance 1100 ms. `posted` is `[{active:true}]`.
- **Reachability:** needs the same asynchronous rejection as F1, so it is not reachable on an iPhone shell.
- **Direction:** bail out of the `.catch` when `!mountedRef.current`.

## F3 carry-over (p2-r1): does one `requestAnimationFrame` after `ready` keep the widening's `resize` off the carry?

**Per the HTML event loop, yes, with margin.**
- `ready` resolves from a timer task (the 16 ms poll) or a message task (`__litloft.receive`), once `documentElement.clientWidth/Height` equal the answered size. Both are ordinary tasks, never inside a rendering update.
- A layout viewport size change makes a window `resize` pending, and WebKit dispatches it in `Page::updateRendering`'s resize step.
- In "update the rendering", the resize steps run before the animation-frame callbacks. The rAF requested after `ready` therefore runs in the first rendering update after the size is visible, after that update's resize dispatch, so `pin()` comes after the resize.
- Even without the rAF, the grow starts only in a `ResizeObserver` callback, and ResizeObserver runs after both resize and rAF in the same update. So M10 surviving is expected, and the rAF is belt-and-braces.
- Rotation entries are never carried (`forget()`), so a late rotation resize cannot cut a carry short either.

**What only a device can tell:**
1. Whether iOS WebKit dispatches the widening's `resize` in the first rendering update after `clientWidth` changes. The alternative is a later update, e.g. after a UI-process visible-content-rect or unobscured-size update arrives as a separate IPC.
2. Whether the widening produces a *second* layout-viewport change after the one the poll matched, e.g. the safe-area inset or the minimum layout size applied a layout later. Such a change would finish a running grow.
3. Whether the answered size (points from the web view's frame) ever differs from `clientWidth/Height`. That can happen under a non-1 initial scale or `minimumEffectiveDeviceWidth`. The poll would then never match, and the carry would go ahead after the 1000 ms deadline in whatever viewport is current. Expect a visible ~1 s delay in that case.
4. Whether the narrowing after `settleOff` moves the frame's slot. #379 R-0 item 2 ("rect after exit equals rect before entry") depends on item 8 of this change, which only the simulator can measure.
5. The 60 fps carry and item 9 (the native layer covers the frame after the widening).
