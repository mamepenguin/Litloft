## Findings

### F1. A corrupt deflate stream escapes the generator as `zlib.error` and rolls back the whole drive scan

- Label: `[introduced]` (`generate_epub_thumbnail` / `read_cover_bytes` are new; at `bdff51c1f^` `.epub` is `other` and has no generator, so the same file scans cleanly).
- Invariant: **1** broken ("raises nothing out of the generator"). Also reaches the scanner's drive-level guarantees (see below).
- Where: `backend/app/services/thumbnail.py` `generate_epub_thumbnail`, the `except (EpubCoverError, zipfile.BadZipFile, OSError, RuntimeError, ValueError)` tuple; the read happens in `backend/app/services/epub_cover.py` `_read_bounded` (`f.read(limit + 1)`).
- Reproduction (hostile input, not a mutation): build a valid EPUB, overwrite the compressed bytes of `OEBPS/content.opf` (or `META-INF/container.xml`, or the zeroed tail of a longer OPF) with `0xFF`, keep the headers. `zipfile` decompresses through `zlib.decompressobj`, and a bad block raises `zlib.error`, which is a plain `Exception` subclass — none of the five caught types.
  - `generate_epub_thumbnail(...)` → `RAISED error: Error -3 while decompressing data: invalid block type` (also `invalid distance too far back` for a zeroed tail). The same corruption under bzip2 or LZMA is caught (`OSError` / `BadZipFile`), and a stream cut short is caught as a CRC `BadZipFile`, so this is specific to deflate, i.e. the normal EPUB compression.
  - `write_thumbnail_atomically` only catches `AbandonWrite`, so the error propagates.
  - `_scan_and_register` on a drive holding `bad.epub`, `good.epub`, `notes.txt`: raises the same `zlib.error`; **zero rows registered** for any of the three files. `scan_drive` rolls the session back. Every later scan hits the same file and fails the same way, so on that drive nothing new is registered and missing/recovered detection never runs while the file exists.
  - `register_single_file(bad.epub)` raises too (upload / single-file registration path).
- Tests: no test in `test_epub_thumbnail.py` corrupts a compressed stream (`truncated_cover` truncates the *image* bytes, stored inside a valid deflate stream), so the gap is green.
- Observed with: temporary `tests/test_zz_r1_probe.py` (deleted afterwards) and `scratchpad/epubr1/probe.py`.

### F2. `book.pdf` beside `book.epub` share one thumbnail slot; the PDF's card shows the EPUB cover

- Label: `[introduced]` by the parent/SHA reproduction below. The mechanism is pre-existing (`fileops.path_thumbnail_rel` keys the slot on drive/folder/**stem**, so `x.mp4` + `x.png` already collided); this commit makes it reachable for the pair a book library holds most often — the same title as PDF and EPUB.
- Invariant: none of 1–6 (they are about the EPUB's own row and bytes). User-visible on another file's card.
- Where: `backend/app/services/thumbnail.py` `get_thumbnail_generator` (the new `application/epub+zip` branch) meeting `backend/app/services/fileops.py` `path_thumbnail_rel`.
- Reproduction: drive with `book.pdf` (a blue page, PyMuPDF) and `book.epub` (red EPUB3 cover); `_scan_and_register`; read the centre pixel of each row's thumbnail.
  - at `bdff51c1f`: `book.epub → d/book.jpg (254,0,0)`, `book.pdf → d/book.jpg (254,0,0)` — **the PDF card shows the EPUB's red cover.**
  - at `bdff51c1f^` (`git archive` into `scratchpad/epubr1/parent`): `book.epub → no thumbnail`, `book.pdf → d/book.jpg (0,0,254)` — correct.
  - Which one wins depends on scan order. `physical_delete` of either row unlinks the shared `book.jpg`, blanking the other until the next scan regenerates it.
- No test covers two thumbnailable files with one stem in a folder.
- Per `review-workflow.md` Scope: a shape that does not make this reachable would be needed from the author, or it is raised to the supervisor.

F1 addendum: in a 4000-case random byte-flip fuzz of a valid EPUB (`scratchpad/epubr1/fuzz.py`), 879 cases raised out of `generate_epub_thumbnail`, and every one was `zlib.error`. No other exception type escaped. `upload.py` (`gen_fn` at the upload-completion step) calls it through `write_thumbnail_atomically` without a catch either, so an upload of such a file fails after the bytes are in place.

### F6. The pixel cap is not held before decode

- Label: `[introduced]` (new function).
- Invariant: none as written (1 says ">40 Mpx cover yields no thumbnail", which still holds). The spec's Backend section says "pixel cap 40 Mpx checked before `load()`".
- Where: `backend/app/services/thumbnail.py` `generate_epub_thumbnail`, `width, height = img.size` before `img.thumbnail`.
- Mutation T5b: `img.load()` before reading `img.size`, want=kill → **SURVIVED**. An over-cap cover would be fully decoded (e.g. 8000×5001 RGBA ≈ 160 MB, up to Pillow's own 2×`MAX_IMAGE_PIXELS` error at ~179 Mpx) before being refused. Nothing observes decode order. Only matters if the pixel cap is meant as a memory bound (see the invariant-list answer).

## Security perspectives covered

- **Untrusted archive / zip:** every read is by entry through `zf.open`, and nothing is extracted to disk, so on-disk path traversal is not reachable. The only escaping exception is F1 (`zlib.error`). Encrypted entries, unknown compression methods, bad names and CRC mismatches are caught (F4: untested).
- **Path traversal inside the archive:** `_resolve` rejects `..`, absolute paths, backslashes, colons and percent-encoded `..` after decoding. M7, M9 and M10c survive because they are redundant with other clauses (an equivalent mutant, not a gap). M12 (OPF path not resolved) survives because any cover href resolved against an escaping OPF directory is itself rejected, so the outcome is unchanged.
- **XML:** the expat probe refuses a DOCTYPE in any encoding (M4 and M6 killed, a UTF-16 case exists). Without a DTD, entity expansion is unreachable. Deep nesting within 1 MB returns `False`, not a crash.
- **Image decoders / SSRF / local file read:** Pillow 11.2.1 (libwebp 1.5.0) decodes from `BytesIO` with `formats=` JPEG/PNG/GIF/WEBP. That also keeps the globally registered `pillow_heif` opener out (T1 and T2b killed). No subprocess on any path (tested by `run.assert_not_called()`; T14 killed). Nothing in the path resolves a URL.
- **Resource exhaustion:** see F3 (read bound untested) and F6 (pixel cap after decode untested). The byte caps and the pixel cap themselves are held at their boundaries (M2, M3, M19, M20, T3, T4 killed).
- **Internal API content boundary:** `_CONTENT_READ_ALLOWED_MIMES` excludes EPUB and I1 is killed. `preview-text` is gated on `_OFFICE_MIME_EXTENSIONS` and PUT on `_TEXT_WRITE_ALLOWED_MIMES` (F5). The intelligence addon's `TEXT_MIMES` (checked in the main checkout, since submodules are not in this worktree) does not include `application/epub+zip`.

## Is anything missing from the invariant list?

Yes, two items:

1. **Cross-file isolation.** Nothing says that one EPUB cannot affect *other* files, and both A-class observations here are cross-file effects:
   - F1: one bad EPUB rolls back the registration of every file in the drive, on every scan.
   - F2: an EPUB overwrites a same-stem PDF's thumbnail.

   Suggested: *"Scanning a drive that holds a hostile EPUB registers every other file in it, and leaves every other file's thumbnail unchanged."*
2. **The pixel cap as a memory bound.** If it is meant to bound memory (as the spec says: "checked before `load()`"), invariant 1 should say so: *"a >40 Mpx cover is refused from its header, without being decoded."* As written it only says "no thumbnail" (F6).

Encrypted entries and unsupported compression methods fall under "corrupt zip" and need no separate line, but they need a test (F4).
