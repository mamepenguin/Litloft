## Findings

### F1. A display copy that the browser refuses to allocate is reported as a successful render — `[introduced]`, proposed **A** (invariant 4)

`frontend/src/components/pdf/PdfCanvas.tsx:55-61` and `:64-75`.

Every page on screen now needs two canvases of the full raster size: the cache's raster (`pdfRasterCache.ts:53-73`) and the component's copy (`PdfCanvas.tsx:58-60`). Only the first one's failure is reported. The copy does `canvas.width = …; canvas.getContext("2d")?.drawImage(…)`. If Safari refuses the backing store, `getContext` returns null, or on a canvas that already has a context the draw does nothing. The `?.` swallows this. `onRenderSuccess` fires anyway because it keys on `exact`, the cache's raster, and never on the copy.

Scenario: on an iPad, open full screen on a large scanned PDF and pinch-zoom until the settled raster is near the `MAX_RASTER_PIXELS` budget (16.7 M px ≈ 67 MB). The cache raster allocates. The copy of the same size is the allocation that crosses Safari's total canvas-memory cap. Result: a blank white page (the `bg-white` section) with no `pdfRenderTooLarge`, and the reader has no hint that zooming out is the way back. Before this change the same refusal happened inside react-pdf's own `page.render` (`react-pdf/dist/Page/Canvas.js`: `canvas.getContext` → pdf.js `CanvasGraphics` on a null context throws → `onRenderError`), so the message was shown.

Evidence: the existing test already reproduces the silent half. `PdfCanvas.test.tsx:41` stubs `getContext` to return `null` for every canvas, so the copy never draws. Still, `reports success once the page's raster is drawn` (`:84-95`) passes: `onRenderSuccess` is called once with nothing painted. I did not measure this on a device. It depends on how close the page is to the cap, and F2 below says why this change moves pages closer to it.

### F2. Canvas memory per page on screen roughly doubles to triples on the device class the spec says is memory-bound — `[introduced]`, proposed **C**

`frontend/src/components/pdf/PdfCanvas.tsx:21-24,55-61`; `frontend/src/lib/pdfRasterCache.ts:232-244`.

The spec's design says "The canvas elements belong to the cache, not to the component". The code copies each cached raster into a component-owned canvas of the same pixel size (the comment at `PdfCanvas.tsx:21-24` gives the reason: two viewers of the same key would otherwise steal one element). The fallback rule also keeps the previous raster of a page on screen until the new one is drawn. Estimated for full screen on a 12.9" iPad (dpr 2) with a portrait page, zoom settling at the raster budget (arithmetic from `rasterPixelRatio`, not measured):

| held during a zoom redraw | before (`4acce093a`) | after (`ffed95e99`) |
|---|---|---|
| full-screen page, new size | 67 MB (react-pdf canvas) | 67 MB cache + up to 67 MB copy |
| previous size of that page (fallback) | 0 (react-pdf zeroes it on remount) | ~47 MB (2× zoom raster) |
| inline page under the overlay | ~14 MB | ~14 MB cache + ~14 MB copy |
| prefetched neighbour faces | 0 | ~24 MB |
| **total** | **~81 MB** | **~200–230 MB** |

The spec's "Checked, no action" rejects prefetching two faces ahead because of "iPad Safari's total canvas memory cap". The copy costs more than that rejected second prefetch would have, on every page on screen, all the time. F1 is what hitting the cap looks like. Whether the copy (and so the doubling) is the right shape is a design question, so I propose C: for example, a cached canvas handed out only while one viewer shows a key, falling back to a copy only when two viewers show it at the same time. Raised, not decided.

### F3. A redraw of the page on screen waits for a prefetch that is already running — `[introduced]`, proposed **B**

`frontend/src/lib/pdfRasterCache.ts:196-201` and `:246-247`.

The spec says: "A request for a page on screen always runs before prefetch." `pump()` returns while anything is `running`. `sweep()` cancels the running job only when no owner wants it any more. A running prefetch that is still wanted therefore holds the queue, and a new visible request waits for it to finish. In full screen the prefetch size does not change with zoom (`PdfFullscreenViewer.tsx`, `faceRaster(next.kind, nextBoxes, frame, deviceRatio)`), so a pinch never makes the running prefetch unwanted.

Scenario: on an iPad, open full screen on the scanned PDF from the spec's measurement. The page draws, then the next face's prefetch starts (parse + decode measured at 2.4 s on that device). Pinch-zoom the page within that window. The page stays as the upscaled fallback (blurry) until the neighbour finishes, and only then is the sharp raster started. The page is not blank, so invariant 3 holds and invariant 5 is untouched.

Evidence (scratch test, removed afterwards): a visible request for 5@1 is drawn, prefetch 6@1 starts, then `want("canvas", {visible:[5@2]})` is made. The jobs list stays `['5@1','6@1']` until job 6 resolves, then becomes `['5@1','6@1','5@2']`. The committed test `draws a page on screen before a queued prefetch` (`pdfRasterCache.test.ts:192-213`) holds this waiting behaviour, since it resolves the running prefetch before the visible job appears.

### F4. Zooming the full-screen page that is also shown inline evicts the sharper raster and falls back to the inline one — `[introduced]`, proposed **B**

`frontend/src/lib/pdfRasterCache.ts:238-242` (`if (wanted(other) || e.seq > entry.seq) return false;`).

`isFallback` drops the previous raster of a page as soon as any other raster of that page is wanted and ready, including a different viewer's raster. PdfCanvas then shows `best(page)`, which is that other viewer's raster.

Scenario: open full screen from the inline viewer on page 3, where the inline canvas holds 3@inline and full screen holds a larger 3@fs. Pinch-zoom. The new full-screen canvas mounts and first copies 3@fs, because it is the newest (higher `seq`). The microtask sweep then releases 3@fs, because 3@inline is wanted. `notify` re-renders the canvas, and it copies the smaller inline raster, stretched to the full-screen box. The page goes sharp → visibly blurry → sharp when the new size lands. It is never blank, so invariant 3 holds.

Evidence (scratch test): inline 3@1 and full-screen 3@2 are both ready. Release the full-screen owner and want 3@4. After the flush, `jobs[1].raster.canvas.width === 0` and `cache.best(3) === jobs[0].raster` (the inline one).

### F5. No test holds invariant 6 for any size other than fit, zoom 1, an unbudgeted raster and uniform page sizes — `[introduced]`, proposed **A** (a test that lets an invariant-6 break through)

`frontend/src/components/__tests__/PdfPreview.test.tsx` "prefetches the next then the previous page at the size a turn draws them"; `frontend/src/components/pdf/__tests__/PdfFullscreenViewer.test.tsx` "keeps the face on screen and prefetches…" / "prefetches both pages of the next pair".

The parity tests use one `mockPageBox`/`PORTRAIT` for every page, zoom 1, and a frame small enough that `rasterPixelRatio` never binds. Each mutation below breaks invariant 6 for a user and survives the whole suite:

- **P4** — inline prefetch drops `* zoom` (`PdfPreview.tsx:426`). Inline zoom persists across `PageDown`, so at 150 % every turn renders again. Live.
- **P3** — inline prefetch sizes the neighbour with `currentBox` instead of its own `box` (`PdfPreview.tsx:425`). In a PDF with mixed page sizes (a landscape insert), the turn misses the prefetched raster. Live.
- **P8** — `currentBox = pageBox` (the lagging `onLoadSuccess` box; `PdfPreview.tsx:398`). On a mixed-size PDF the first draw after a turn is at the previous page's size, then again at its own. Live.
- **P5** — inline prefetch uses `deviceRatio` instead of `pageRasterRatio(…)` (`PdfPreview.tsx:431`). Where the budget binds (large page, fit-width on a wide window, 200 %), the key misses and the prefetch allocates an over-budget canvas. Live.
- **F5** — full-screen prefetch uses `deviceRatio` instead of `raster.ratio`. A pair face on a 4K display binds the budget. Live.
- **F7** — full-screen prefetch sizes the neighbour face with the current page's box. Live.
- **F1** — full-screen prefetch includes `zoom.settledScale`. After a turn the zoom resets to 1, so the key misses. Live.

### F6. Nothing holds that two canvases on screen at once each get drawn — `[introduced]`, proposed **B** (see "Missing from the invariant list")

`frontend/src/components/pdf/PdfCanvas.tsx:28`.

Mutation C10 replaces `` `canvas:${useId()}` `` with a constant owner and the whole suite stays green. With it, the two pages of a pair face, or the inline page plus the full-screen page, overwrite each other's `want`. Only the last canvas's page is ever requested. The other page stays `visibility: hidden` forever, and its `visiblePages` entry also closes the prefetch gate for good. None of invariants 1–6 is violated in that state: nothing is cleaned up, nothing prefetches, and there is no failure to report. Every test mounts at most one `PdfCanvas`.

### F7. Survivors that no declared invariant covers, but that change what a user gets — `[introduced]`, proposed **B**

- **C5** — deleting the unmount effect that zeroes the display canvas (`PdfCanvas.tsx:83-91`). react-pdf remounts the renderer on every scale change, so each zoom step then leaves a full-size display canvas for GC. That is the release the cache's own comment says Safari needs. Live.
- **M17** — `keyOf` with `toFixed(0)` instead of `toFixed(4)` (`pdfRasterCache.ts:44`). Scales 2.6 and 3.3 (100 % → 125 % at dpr 2.6) collide, and the old raster is served as "exact" forever. No test has two scales of one page that differ by less than 0.5. Live.
- **M16 / M16b** — `clear()` without `cancelRunning()` (`pdfRasterCache.ts:146`). A render in flight when the viewer unmounts completes into the cleared cache and its canvas is never released. Live. (With the code as written, a scratch test confirms `cancel` is called.)
- **M11** — never forgetting a failed visible key (`pdfRasterCache.ts:203-205`). A page that failed once at a size is never retried at that size, even after zooming away and back. Live.
- **M19** — `best()` choosing the oldest raster instead of the newest (`pdfRasterCache.ts:120`). Live. This is only observable when two rasters of one page coexist, which F4 shows does happen.

## Missing from the invariant list (asked once, round 1)

1. **Liveness: every page on screen is eventually drawn, or reports failure.** Invariants 1–6 are all safety properties. A cache that never draws a page satisfies every one of them (F6/C10 is a concrete such state).
2. **Canvas memory: a bound on how many full-size canvases one page on screen may hold.** The spec treats iPad Safari's total canvas cap as the binding constraint ("Checked, no action"), yet no invariant says the change must not raise the number of canvases held per page (F2).
3. **A picture that fails to reach the screen is reported.** Invariant 4 as written ("when the page on screen fails to render") can be read as covering only the pdf.js render and not the display copy (F1).
