## Findings

### N1. Turning a pair onto a page whose prefetch is running cancels that prefetch and starts the same page again — `[introduced]`, proposed **B**

`frontend/src/lib/pdfRasterCache.ts:238-252` (`nextVisible` skips only `this.running.key`; `if (nextVisible && this.running.prefetch) this.cancelRunning()`).

The running job keeps `prefetch: true` after a canvas asks for the same key as a visible request. The exclusion `this.running?.key !== key` covers a single page. In a pair face it does not help, because the *other* page of the pair is the `nextVisible` that triggers the cancel.

Scenario: full screen, pair mode, on pages 4–5. The prefetch of 6 is running (on the spec's iPad scan, parse + decode ≈ 2.4 s). The reader turns to 6–7. Canvas 7's request is `nextVisible`, so the running render of 6 is cancelled. Once it settles, `pump` starts 6 again (it is first in the visible list), then 7. The drawing done for 6 so far is thrown away. The restart comes within microtasks, inside pdf.js's 100 ms `RENDERING_CANCELLED_TIMEOUT` (`pdf.mjs:14031`, `_abortOperatorList` at `:14800`), so the operator list is most likely kept and the loss is the canvas work, not a new `GetOperatorList`. I did not measure it in a browser. No invariant is broken: 6 was not yet prefetched (invariant 6), and nothing prefetches early (invariant 5).

Evidence (scratch cache test, removed afterwards). `c4`/`c5` are visible and drawn. The viewer prefetches `[6@1, 7@1]` and 6 is running. Then release `c4`/`c5` and want `viewer {visiblePages:[6,7]}`, `c6 {visible 6@1}`, `c7 {visible 7@1}`:
- at `7ed4ccc6b`: jobs `['4@1','5@1','6@1','6@1']`, `jobs[2].cancel` called 1×.
- at `ffed95e99` (temporary worktree): jobs `['4@1','5@1','6@1']`, cancel called 0×. 6 continues and becomes the visible raster.

### N2. Nothing holds what the new priority rule must *not* cancel — `[introduced]`, proposed **B**

`frontend/src/lib/pdfRasterCache.ts:243`, `:250`, `:254`.

Only the positive half is tested ("stops a running prefetch for a page on screen…", which kills K1). Three mutations of the rule's limits survive all 123 tests:
- **K2**: drop `this.running?.key !== key`. Turning a single page onto its own running prefetch then cancels it and renders it again. This is the N1 loss for the single-page case, which the guard exists to prevent.
- **K3**: start visible jobs with `prefetch: true`. A visible render is cancelled by any later visible request.
- **K6**: `if (nextVisible) this.cancelRunning()`, which cancels any running job. Same effect as K3. react-pdf mounts each renderer only after its page loads, so the two canvases of a pair can register in different ticks. Page 4's render is then cancelled when page 5 registers, and started again.

None of these produced a state I could tie to invariants 1–9 (each restart is immediate, so the page is eventually drawn). What they break is the claim in the spec and the commit that a page on screen is drawn first with no wasted work.

### N3. A copy that a canvas no longer shows is not released when the canvas moves to the cached canvas, and no test catches it — `[introduced]`, proposed **A** (a test that lets an invariant-8 break through)

`frontend/src/components/pdf/PdfCanvas.tsx:88-90` (`if (!takenElsewhere) { releaseCopy(copyRef); … }`).

The copy path runs on **every full-screen open**, not only in the rare case of two viewers at one size. When the full-screen canvas mounts, its exact raster is not ready, so `shown = cache.best(page)`. That is the inline page's raster, which is connected in the inline host, so it is copied. When the full-screen raster lands, the canvas switches to the cached canvas, and that line is the only thing that frees the copy.

Mutation **P18** deletes that `releaseCopy(copyRef)`, and all 123 tests stay green. With it, the full-screen page keeps a dead copy of inline size next to its own raster for as long as full screen stays open. That is two full-size canvases for a page once drawn, which invariant 8 forbids.

Evidence (scratch component test, removed afterwards). An inline canvas at scale 1 is drawn, then a full-screen canvas at scale 2 mounts for the same page:
- at open: full screen shows a copy (width 1200, not the inline element). Live canvases: inline 1200, copy 1200, the new job 2400.
- after the full-screen raster resolves, at `7ed4ccc6b`: full screen shows its cached canvas. Live widths `[1200, 2400]`.
- the same with P18: live widths `[1200, 1200, 2400]`. The copy survives, and nothing fails.

### N4. The copy decision is taken once and never revisited when the canvas holding the cached element goes away — `[introduced]`, proposed **B**

`frontend/src/components/pdf/PdfCanvas.tsx:76-118`. The layout effect depends on `[shown, className, cssWidth, cssHeight]`, not on where `shown.canvas` is.

Canvas A shows raster E directly and canvas B shows a copy of E (the same key in both). When A unmounts first:
- (a) B keeps its copy, and E stays alive, detached, because B still wants its key. That is two full-size canvases for one page on screen, indefinitely.
- (b) If B's copy had been refused (`getContext` null), B stays `visibility: hidden` with `pdfRenderTooLarge` reported, although E is now free to be shown directly.

Evidence (scratch component test): (a) after A unmounts, B shows a copy, 2 live canvases, `E.isConnected === false`. (b) `onRenderError` ×1, `onRenderSuccess` ×0, no canvas in B's host, `visibility: hidden`, `E.width === 1200`.

Reachability: I could not construct this in the app. The two viewers are inline and full screen. Inline mounts first, so it holds E. Full screen closes first, and on a resize both remount in the same commit, with deletions before layout effects, so inline takes E again. It needs the holder to unmount alone while the copier stays at the same key. Invariant 7 still holds in (b): the failure is shown.

### N5. A full-screen zoom still falls back to the inline raster, and drops its own sharper one, whenever the inline page drew last (r1 F4, narrowed) — `[pre-existing]`, proposed **B**

`frontend/src/components/pdf/PdfCanvas.tsx:51-58`; `frontend/src/lib/pdfRasterCache.ts:120-128`.

react-pdf remounts the renderer on every scale change (`Page.js:188`, key `${pageIndex}@${scale}/${rotate}`). So on a zoom the new `PdfCanvas` has an empty `shownRef`. `previous` is undefined, and what it shows and holds is `best(page)`, the raster with the highest `seq`. The old instance's raster is not held by anyone after its release. `previous` only takes effect when `renderScale` changes without a remount, which is a `devicePixelRatio` change. Mutation P3 (drop `previous`) survives all tests.

Scenario: full screen is open on page 3, and the window is resized, so both viewers redraw. If the inline raster finishes after the full-screen one, the next pinch-zoom shows a copy of the inline raster stretched to the full-screen box, and the full-screen raster is released. The page goes sharp → blurry → sharp. It is never blank (invariant 3 holds).

Evidence (scratch component test): inline at 1 and full screen at 2 are drawn. Inline goes to 1.5 and is drawn (newer `seq`). Full screen zooms to 3: it shows a 1800-wide canvas (a copy of the inline raster), and the full-screen 2400 raster has width 0. When full screen is the newest raster, the r1 F4 case is fixed. The same test without the inline redraw (full screen zooms 2→3) shows the full-screen 2400 canvas itself, still at width 2400. M19 (`best` picks the oldest) still survives. `best`'s order is now the whole of what decides this.

## Checked, no finding

- **`hold` registration vs the deferred sweep.** The layout effect puts a raster on screen before the passive effect registers `hold`. A sweep in between could only release that raster if the owner that protects it had already let go. That owner is either this canvas's previous instance (its `release` is a passive cleanup) or another viewer's visible request (also a passive effect). React runs every passive unmount of a commit, then every passive mount, in one flush, and `sweep` is queued as a microtask after it. So the old protection and the new `hold` land before the same sweep. A raster released by an earlier, separate sweep is already gone from `ready` when this canvas renders, so `best`/`get` cannot return it. `previous` is guarded by `canvas.width > 0` (P4 is equivalent under this reasoning, and live).
- **`shownRef` read during render.** It is written only in the layout effect, so a discarded concurrent render cannot leave it pointing at something never shown. StrictMode's double render reads the same value twice.
- **Copy path choice (`isConnected` / `parentElement`).** A canvas never takes an element that is connected elsewhere. On a remount the old host is removed in the mutation phase, before the new layout effect, so the new instance takes the element directly (tested: "keeps the previous picture…"). P6 (`takenElsewhere = isConnected`) survives, but I found no path where the layout effect re-runs with the element already in its own host: `cssWidth`/rotation changes remount the renderer. I treat it as equivalent.
- **StrictMode double effects.** Layout: all destroys (the unmount effect empties the host), then all setups (the first effect puts the element back). Passive: `release` (cleanup of the second effect), then `want` (setup of the first), and `sweep` is deferred, so nothing is evicted. `onRenderSuccess` fires twice in development only.
- **`pump` cancel path.** It cannot loop or leave `running` stuck. `cancelRunning` is idempotent (`running.cancelled`), and a cancelled job always reaches `finally`, which clears `running` and schedules another pump. That holds even when cancelled during `await getPage`, where `cancel` is still null. A prefetch cancelled this way is started again only once no visible request is pending, so a steady stream of visible requests postpones prefetch, which is intended. One side effect is not a finding: when the visible render takes over 100 ms, pdf.js force-aborts the cancelled prefetch's operator list and calls `cleanup()` on that page itself (`pdf.mjs:14800-14842`), so the restarted prefetch asks for its operator list again. Invariant 1 covers the page on screen, not the prefetched one.
- **Success/failure order (invariant 9).** Success needs `exact && onScreen === exact`, and `onScreen` is set only after the element is in the host (P7 and P15 killed). A refused copy of the exact raster reports an error and no success (P8 killed). A refused copy of a *fallback* reports nothing and hides the page (P9 and P14 live). At `ffed95e99` the same refusal left a sized but blank display canvas, so that blankness is not new.
- **Memory (invariant 8), single viewer.** Once drawn, the page holds only its cached canvas: the `hold` is dropped when `shown === exact` (P1 killed; "keeps one raster per page on screen once it is drawn"). During a redraw it holds the one on show plus the job in flight. Rapid zoom steps cancel the in-flight job that is no longer wanted.

## Trajectory

There is one fix round, so "two rounds in a row" cannot be judged yet. Measured against the change it fixes:

- **Removed:** the cache's `isFallback` prediction (which unwanted raster is "the fallback"), and the always-on display copy. This is the converging shape: the cache no longer guesses what is on screen, and a canvas declares it (`hold`).
- **Added:**
  - in `PdfCanvas`: a branch (`takenElsewhere` copy vs direct), two states (`copyFailed`, `onScreen`) and one prediction (`previous` via `shownRef`: "what I showed last is what to keep");
  - in `pump`: a flag on `Running` (`prefetch`), a branch (cancel a running prefetch), and an exception to that branch (`running.key !== key`).
- **The fallback choice is now made in two places.** `previous` in the canvas, and `best()`'s `seq` order in the cache. Because react-pdf remounts on every scale change, the second one decides on every zoom and the first almost never (N5, P3 live). The prediction the fix meant to remove survives as `best()`.
- **The `pump` change already has the patching shape.** It is one rule plus one special case (the running key), and N1 is a case the special case did not anticipate: the other page of a pair. The obvious next fix is a second exception (clear `prefetch` when a visible request names the running key, or skip the cancel when the running key is visible). That would be a round adding a branch after a round that added one.

My answer: the memory and fallback half is converging (a prediction removed, a declaration added), apart from `best()` surviving as the remount path. The priority half is being patched.
