## Findings

### R3-1. The new ordering test holds "the page on screen before the next prefetch" only when the page has no picture on show — `[pre-existing]`, proposed **A** (a test that lets an invariant-5 break through)

`frontend/src/lib/__tests__/pdfRasterCache.test.ts:236-262` ("lets a running prefetch finish, then draws the page on screen before the next one"); the rule it holds is `frontend/src/lib/pdfRasterCache.ts:237-247` (`if (nextVisible) { this.start(nextVisible); return; }` ahead of the prefetch search).

The test zooms by replacing the canvas's want with `visible: [1@2]` and **no `hold`**, so the sweep releases `1@1` and page 1 has no raster left. The real zoom path is different: `PdfCanvas` holds the raster it shows (`hold: [1@1]`) until `1@2` is drawn (`PdfCanvas.tsx:58-65`), so the page has a fallback on show exactly when this ordering matters.

Mutation **C4b**: in `pump`, when the pending visible request's page already has a raster (`this.best(nextVisible.pageNumber)`) and a prefetch is pending, start the prefetch instead. This is the plausible "the page has something on screen, draw ahead first" optimisation. All 124 tests in the four PDF files and the whole suite stay green. It breaks invariant 5: a prefetch render starts while the page on screen (`1@2`) has not rendered, and on a zoom the sharp page waits behind every pending prefetch rather than at most the one already running.

Evidence (scratch cache test, removed afterwards): the test above with `hold: [{ pageNumber: 1, renderScale: 1 }]` added to the zoomed want, and prefetch `[2@1, 3@1]`.
- at `aebcbb15a`: jobs `['1@1','2@1','1@2']` (passes).
- with C4b: jobs `['1@1','2@1','3@1']` (fails, "Expected 1@2, Received 3@1").
- the shipped test with C4b: passes.

Label: the same mutation, adapted to the parent's `start(r, prefetch)` signature, is also live at `7ed4ccc6b` (temporary worktree, 123/123 green): the parent's version of this test ("stops a running prefetch…") also zoomed without `hold`. So the gap predates this commit, although this commit rewrote the test and its new name now claims the ordering. The older "starts no prefetch until the pages on screen have rendered" test covers invariant 5 only for a page with no raster at all.

No other finding. What I checked and did not flag is under "Checked, no finding".

## Checked, no finding

- **A running prefetch that never settles.** With no preemption, a prefetch whose render never settles would keep every later request waiting. At `7ed4ccc6b` the preemption could have cancelled such a render, but not one stuck in `await getPage` (its `cancel` is still null there), and at `ffed95e99` it waited the same way. pdf.js renders settle, either resolved or rejected. This is the accepted r1 F3 cost, not a new state.
- **A cancelled job becoming wanted again** (turn away and back quickly). `pump` returns while the cancelled job is still `running`; its `finally` clears `running` and reschedules, and the next `pump` starts the page again. Nothing is lost except the cancelled work.
- **Stale prose.** No comment in `pdfRasterCache.ts`, `PdfCanvas.tsx`, `PdfPreview.tsx`, `docs/user-guide` or `docs/reference` still describes the preemption.
- **The N3 test's copy lookup** (`created.find(c => !jobs.some(j => j.canvas === c) && c.width > 0)`). It cannot pick a job canvas, and `expect(copy).toBeDefined()` fails if no copy was made (T4). It does not assert that the copy was the element on screen at open, but "draws a raster already on show elsewhere into a canvas of its own" does.
