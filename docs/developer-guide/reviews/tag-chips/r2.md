### F1: a tag removed right after it was added stays offered as a chip
Severity: major
Label: [introduced-r2]
Where: `frontend/src/components/EditableTagChips.tsx:203-228` (the `setTagPool` updater in `commit`)

Mutation: none — behaviour probe P1 (`want=live`, i.e. I expected the tag to
disappear from the chips once it was removed). Add `kimchee` on a file in
`clips/`, press its X to take it off again, reopen the field. Observed
`["kimchee", "beef"]` at `e270b934`; `["beef"]` at the parent `e7b9e76c`.
Probe deleted afterwards.

Failure: `commit` only ever *adds* to `prev.scoped`. On the removal call
`next` no longer contains `kimchee`, `addedScoped` is empty, and nothing
takes the synthetic `{ name: "kimchee", count: 1 }` row back out — so the
pool keeps claiming this folder carries a tag that no file in it carries.
`recordRecentTag` already wrote `kimchee` to `localStorage` and nothing
removes it there either, so the ghost renders **first**, ahead of every real
tag. It survives for the rest of the session in that folder, because the
fetch effect is keyed `[file.drive, file.folder_path]` and a move to a
sibling file does not refetch.

This breaks declared invariant 4 (`チップに出るのは、そのファイルのフォルダ配下で
実際にファイルに付いているタグだけである`) — the same invariant the spec's
`### 孤児タグを除外する` section and the `count > 0` filter exist to protect.
A user correcting a typo (`kimchee` → `kimchi`) is then offered the typo at
the top of the list on every file in the folder.

Suggested: in the same updater, drop scoped rows the fold itself put there
that `next` no longer carries. That needs the synthetic rows to be
distinguishable from fetched ones — which is the design question, so:
**design decision — raise** (see `## Trajectory`).

### F2: a refused write leaves the tag it refused offered as a chip
Severity: major
Label: [introduced-r2]
Where: `frontend/src/components/EditableTagChips.tsx:203-228`, against `saver`'s `onError` at `:187-191`

Mutation: none — behaviour probe P2 (`want=live`). `updateFileTags` rejects.
Type `refused`, Enter. The inline `Failed to update tags` appears and the
tag chip is rolled back off the file (`setTags(seedTagsRef.current)`), so the
write demonstrably did not land. Reopen the field: observed
`["refused", "beef"]` at `e270b934`, `["beef"]` at `e7b9e76c`.

Failure: `onError` rolls back `tags` but not `tagPool`. The commit message
says *"the file being written is in the folder, so the entry is true by
construction"*; on this path the file is not written at all, so the entry is
false. Same invariant 4 breach as F1, and the same persistence — the ghost
is offered on every sibling file until the folder changes. Reachable
whenever the backend refuses the PUT (offline, 409, a drive that went
read-only).

Suggested: roll `tagPool` back alongside `tags` in `onError`, or make the
fold conditional on the save landing (`onSaveSuccess`) rather than on
scheduling it. Both are the same design question as F1 — **raise**.

### F7: the session-tag test asserts membership where the full list is declarable
Severity: minor
Label: [introduced-r2]
Where: `frontend/src/components/__tests__/EditableTagChips.test.tsx:623`

Mutation: none — measured the list the test looks at. `chipNames()` at that
point is exactly `["kimchi", "beef", "carrot", "onion"]`, fully determined
by the mocked pools and the one tag typed. The test asserts
`expect(chipNames()).toContain("kimchi")`.

Failure: `toContain` is the membership form of a lower bound. It stays green
if the fold starts emitting a duplicate `kimchi`, if the new entry lands in
the wrong half of the list (frequency instead of recent), or if an unrelated
tag appears. Detector rule 5 — the expected value here does not have to be
built out of the observation, because the whole set is declared by the
fixture.

Suggested: `expect(chipNames()).toEqual(["kimchi", "beef", "carrot",
"onion"])`. The other five new tests already do this.

### F8: the canonical lookup narrows the drive-wide rename, and opens the mirror of it
Severity: minor
Label: [introduced-r2]
Where: `frontend/src/components/EditableTagChips.tsx:266-277`

Mutation: none — behaviour probe P6. The folder's scoped pool is fetched as
`[{ name: "beef", count: 9 }]`. On file A the user types `BEEF` and presses
Enter; `replace_file_tags` (`backend/app/routers/files.py:157-169`) looks the
row up case-insensitively and **renames it to `BEEF`**, so the drive now
holds `BEEF`. `localStorage` recent holds `["BEEF"]`. Move to file B in the
same folder. Observed chip: `beef` at `e270b934`; `BEEF` at `e7b9e76c`.

Failure: `canonical` is built from `prev.scoped`, which is a snapshot taken
when the folder was opened and is not refreshed by a write. When the drift
is the user's own, this session, the snapshot is the stale side — so the
chip offers `beef`, and clicking it renames the drive's row back from `BEEF`
to `beef`, the very rename the commit set out to avoid. Round one's spelling
was the fresh one in that direction.

The fix is still a net improvement: it closes the direction round one's F8
described (another client drifted the casing, the local store is stale), and
that is the one that persists across sessions. This one lasts only until the
folder is refetched. Both are the same upstream behaviour — the shared `Tag`
row renaming to whatever was written last — which the spec's `### チップの
組み立て` section calls normal operation, not an error. Nothing in
`## 不変条件` is broken either way.

Suggested: none in this change. If the rename is ever to be closed it is
closed in `replace_file_tags`, not on the client — **raise if it matters**;
otherwise record and close.

## Trajectory

> Read the fix diffs in order (`4208249a` → `e7b9e76c` → `e270b934`). Does
> each round add a branch, a state or a prediction that the round before it
> also added?

**Yes, all three, and the mechanism is the same one both times.** Answered
from the diffs.

**`4208249a` → `e7b9e76c`** replaced one plain state with a mirror of server
state that carries a claim about itself:

```
- const [allTags, setAllTags] = useState<string[]>([]);
+ const [tagPool, setTagPool] = useState<{ drive; folderPath; all; scoped } | null>(null);
```

and then added the branches that police the claim: the render-time `pool`
memo comparing `drive`/`folderPath`, the `folderPath ? … : Promise.resolve([])`
root branch, `typed ? … : …` in `suggestions`, `typing ? <DismissScrim> : …`,
`scoped.filter((tag) => tag.count > 0)` for orphan rows the server returns
anyway, and the `allowed.has(lower)` filter. It also added a second client
store with its own claim about the drive — `recentTags.ts` on `localStorage`.

**`e7b9e76c` → `e270b934`** adds, on top of each of those:

1. **A branch of the same kind.** `commit` gains
   `prev.drive !== file.drive || prev.folderPath !== file.folder_path` — a
   second guard on the key round one added the first guard for. F3: all
   four mutations of it survive, and the state it guards against is already
   covered by round one's render-time memo.
2. **A state of the same kind, holding a stronger prediction.** The fold now
   writes synthetic `{ name, count: 1 }` rows into `scoped`. Round one's
   mirror predicted *which scope the fetched data belongs to*; round two's
   predicts *what the server now contains*. The commit message states the
   prediction outright — "the entry is true by construction". F1 and F2 are
   two reachable states where it is false: removing the tag again, and the
   write being refused. Neither is handled, because neither was anticipated.
3. **A reconciliation between the two client stores.** `canonical` repairs
   the `recent` list's spelling using `scoped`'s. F8: it moves which of the
   two stores is the stale one rather than removing the staleness.

Nothing was removed. The nearest thing to a removal is `canonical`, and it
substitutes one stale source for another rather than deleting a prediction.

The test for patching in `review-workflow.md` R-4 is "each round handling one
more case the last one did not anticipate", and that is what the diffs show:
round one did not anticipate that the pool needs updating when the user
writes a tag, so round two folds the write in; round two did not anticipate
removal or a refused write, so a round three would fold those in as well —
plus the machinery to tell a synthetic row from a fetched one, which neither
round has. Two of the three round-two additions (the guard and the
reconciliation) are also visibly the same shape as round one's, which is the
other half of the test.

## Checked and cleared

Recorded so a third round does not re-derive them.

- **Duplicate entries from the fold.** `inScoped` is computed once and
  `next` is then filtered against it, so two case-variants inside one `next`
  would both be folded. They cannot occur: `submitTag` rejects a
  case-insensitive duplicate (`:311`), `extractValidTags` dedupes on
  `name.toLowerCase()` before content mode ever sees the list
  (`frontend/src/lib/frontmatter.ts:34-44`), and standalone `initialTags`
  comes from the server's own validator.
- **Ordering from the synthetic `count: 1`.** `Array.prototype.sort` is
  stable, so a folded row lands after real count-1 rows, and it renders in
  the recent half anyway. No reachable reordering.
- **The ghost of F1/F2 crossing a folder.** It does not. `commit`'s guard
  refuses a mismatched pool and a folder change refetches, replacing the
  pool wholesale. Both ghosts are folder-local and session-local.
- **Content mode.** Probe P5: a `.md` file with `tags: [alpha, bravo]`, the
  user removes `alpha`. Only `bravo` is folded, it is on the file so it is
  filtered out of the chips, and `alpha` does not leak. `commit` gaining
  `file.drive` / `file.folder_path` in its deps does not touch the
  content-mode path.
- **The debounced saver's identity.** `saver`'s `useMemo` deps
  (`[contentMode, file.id, file.mime_type, file.filename, file.drive]`) were
  not changed, and the cleanup effect is keyed on `saver`, not on `commit`.
  `debounced save still fires after parent passes a new onTagsChange ref`
  is green. Adding deps to `commit` re-creates `submitTag`, `removeTag` and
  `handleKeyDown`, none of which is a dependency of an effect.
- **Removal.** `removeTag` → `commit(tags.filter(…))` is unchanged; the
  round-two additions are all inside the `setTagPool` updater. The only
  removal-path defect is F1, which is the fold not undoing itself.
- **The new tests' expected values.** Five of the six declare the full chip
  list with `toEqual` against a fixture, so detector rule 5 is satisfied.
  The sixth is F7.
