### F1: a tag created this session is never offered as a chip on a sibling file in the same folder
Severity: major
Label: [introduced]
Where: `frontend/src/components/EditableTagChips.tsx:202-207` (`commit`), read at `:245-250`

Mutation: none needed — this is a behaviour probe, not a surviving mutant.
Added a throwaway test in the worktree (`want=live`, i.e. I expected the
feature to work): type `kimchi` on file A in `clips/`, Enter, then `rerender`
with sibling file B in the same folder and open the chips.
Observed `["beef"]` — `kimchi` absent. Probe removed afterwards.

Failure: `commit` folds a newly typed tag into `prev.all` but leaves
`prev.scoped` untouched, and the fetch effect is keyed
`[file.drive, file.folder_path]`, so moving to another file in the same
folder never refetches. `suggestions` filters the recent list through
`allowed`, which is built from `scoped`. So the tag the user *just used* —
the single strongest "recent" signal, and the one `recordRecentTag` was
written to capture — is filtered out of the chips for the rest of the
session in that folder. Concretely: tag ten clips in `clips/` with a new tag
`kimchi`; every one of the ten needs the tag typed out in full, which is the
exact IME cost the change exists to remove. Typed suggestions *do* offer it
(because `all` is updated), so the two halves of the same feature disagree.

Nothing in `## 不変条件` forbids this — invariant 4 is one-directional
("only tags a file in the folder carries"), and after the add the tag *is*
carried by a file in that folder, so showing it satisfies invariant 4 too.
This is the R-5 class of finding: the invariants hold and the feature still
does not do what it was for.

Suggested: mirror the `all` update in the same `setTagPool` updater — fold
names not already in `scoped` in as `{ name, count: 1 }`. The file being
committed is in this folder, so the new entry is true by construction.

### F3: `DismissScrim` can be deleted from this component with the whole suite, including the dismissal detector, staying green

(`want=kill`) — **survived**. `EditableTagChips.test.tsx` 35/35 green, and

### F7: the anchored-direction hook is now "open" whenever chips exist, including while the field is closed

### F8: a recent chip can carry a spelling the drive does not have, and clicking it renames the tag drive-wide
Severity: minor
Label: [introduced]
Where: `frontend/src/components/EditableTagChips.tsx:247-250`

Mutation: none — read against the backend. `recent` is matched against
`allowed` case-insensitively but then rendered and submitted with the
spelling `localStorage` holds, while `byCount` renders the server's
`Tag.name`. `replace_file_tags` (`backend/app/routers/files.py:157-169`)
looks a tag up with `func.lower(Tag.name) == tag_name.lower()` and, when the
spelling differs, **renames the existing row** to the submitted one.

Failure: recent holds `Beef` (recorded when the user typed it); the drive's
`Tag.name` has since become `beef` (someone typed the lowercase form on
another file). The chip reads `Beef`, and clicking it renames the drive's
tag back to `Beef` everywhere. Narrow, and the spec already reasoned about
this rename when it chose case-insensitive comparison, so this may be an
accepted consequence rather than a defect.

Suggested: render and submit `carried`'s spelling for the recent branch too
— map each allowed lowercase name back to its `Tag.name` instead of
emitting the stored string. Or design decision — raise.
