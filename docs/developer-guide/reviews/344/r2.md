## Trajectory — does `83c3b86c` add what `57f3f03d` also added?

**Yes, in one specific sense, and the shape is worth naming.**

Both rounds' fixes add a prediction about **how many elements one passage is**.

- `57f3f03d` replaced `range.surroundContents(m)` — one element, no arity — with
  `markRange(range)` returning an array, and in the same hunk added
  `const first = marks[0]; if (first && !scrolledRef.current)`. That `first &&`
  is a prediction that the array may be **empty**. (Round 1's finding 8 showed it
  is unreachable from `findPassageRange`; it is defensive only.)
- `83c3b86c` adds `if (marks.length > 1)` plus a per-mark
  `data-citation-seam` attribute read by three new CSS rules. That is a
  prediction that the array may hold **more than one**, and a new piece of state
  that has to stay in step with the stylesheet.

So round two adds one branch and one state, both on the same array, both
consequences of the same root change: a passage that used to be one element is
now N, and every consumer of it has to learn to count. Round one taught the
scroll anchor to count; round two taught the paint. PR 1 adds a third consumer
(the line-numbered viewer), and `selection.toString()` / copy is a fourth.

The counter-evidence, stated fairly:

- Round two touches **nothing** round one added — no guard in `collectSegments`
  was widened, narrowed or given a second case, and no branch in the scroll path
  was re-cut. It is not the same case being handled again.
- Round two's code diff is 11 lines in one function. The rest of the commit is
  tests, a test-setup shim, and CSS.
- Round one's `first &&` is unreachable; round two's `marks.length > 1` is
  reached on every cross-token citation. They are not two attempts at one
  problem.

The spec's `## Checked, no action` names the design that has neither prediction:
**CSS Custom Highlight API** ("PR 0 はノード単位のラップで足りる"). Under it a
passage is one highlight range with no DOM elements, so there is no `marks[0]`
to pick and no seam to flatten. It was deliberately skipped for PR 0.

I am reporting the shape and stopping. R-4 says the author does not assign C and
neither do I.

## 1. [MEDIUM] [introduced] The `marks.length > 1` guard is held by nothing, and dropping it takes the right-hand cap off every single-node citation

`frontend/src/hooks/useHighlightPassage.ts:181`

```ts
if (marks.length > 1) {
  marks.forEach((mark, i) => {
    mark.dataset.citationSeam =
      i === 0 ? "start" : i === marks.length - 1 ? "end" : "mid";
  });
}
```

Mutation `MS1` — `marks.length > 1` → `marks.length > 0` — survives the whole
frontend unit suite (405 tests in `src/hooks` + `MarkdownPreview`, all green) and
both `citation-seams-desktop` cases.

It is not cosmetic-only. With one mark, `i === 0` wins the ternary, so the mark
is tagged `start` and loses `padding-right` and both right-hand corners.
Measured in Chromium against the compiled sheet, inside `.markdown-body`:

| | width | padding L/R | radii (TL/TR/BL/BR) |
|---|---|---|---|
| single mark, no seam attribute | 35.00px | 4px / 4px | 3/3/3/3 |
| same mark tagged `start` | 30.84px | 4px / **0px** | 3/**0**/3/**0** |

That is the common case — a quote that fits one text node — rendered with a
square, unpadded right edge against the following word.

A test that kills it: render a single-node match and assert
`mark.dataset.citationSeam === undefined` (jsdom is enough — this is an
attribute, not a layout), or add a one-mark `#single` block to the
`citation-seams` arrangement and assert its four radii are non-zero.

## 2. [MEDIUM] [introduced] The half of the seam fix that matters in a rendered note is measured nowhere

`frontend/src/app/globals.css:716,722,728` (the `padding-*: 0` declarations)
`frontend/e2e-components/fixtures/app.tsx:951-971` (the only fixture)

The seam rules do two things: flatten the interior corners, and drop the
interior horizontal padding. The only fixture that exercises them is a `<pre>`,
and inside a `<pre>` the horizontal padding is **already** zero from
`pre mark.ask-citation-highlight` (globals.css:737). So the padding half of the
seam rules is inert in the only place it is measured.

Mutation `MC3` — delete `padding-right: 0` from the `start` rule,
`padding-left`/`padding-right` from `mid`, `padding-left` from `end`, leaving
the radii — leaves both `citation-seams-desktop` cases green.

What `MC3` does in production, measured in Chromium against the compiled sheet
with a three-mark run inside `.markdown-body > p` (a quote crossing an `<em>`,
which is the shape `MarkdownPreview` produces for emphasis, inline `<code>` and
links — `MarkdownPreview.tsx:469` puts `markdown-body` on the container):

| | mark 1 pad L/R | mark 2 pad L/R | mark 3 pad L/R | run width | following text x |
|---|---|---|---|---|---|
| `83c3b86c` | 4 / 0 | 0 / 0 | 0 / 4 | 141.8px | 176.6 |
| under `MC3` | 4 / 4 | 4 / 4 | 4 / 4 | 157.8px | 192.6 |

16px of highlighted gap injected inside one passage, 8px at each internal seam,
and the rest of the paragraph pushed 16px right. That is precisely the "chain of
pills" the commit was written to remove, and nothing notices.

The same measurement also **confirms the author's specificity claim**: inside
`.markdown-body`, `.ask-citation-highlight[data-citation-seam="mid"]` (0-2-0)
does beat `.markdown-body mark` (0-1-1) — padding reads `0px`, not `4px`. Read
in a browser, not from the source.

What would fix it: a second block in the `citation-seams` arrangement that is a
`.markdown-body` paragraph rather than a `<pre>`, with the same
marked-vs-plain pair, asserting the three marks' `paddingLeft`/`paddingRight`
and that the marked and plain tails differ by exactly the two outer paddings.

## 3. [MEDIUM] [introduced] "Only the two outer edges of the run are rounded" is asserted in one direction only

`frontend/e2e-components/citation-seams-desktop.spec.ts:64-67`


Every assertion says *this edge is flat*. None says *that edge is round*. Two

Adding `expect(boxes[0].radii[0]).not.toBe("0px")` and

observed value is `2.4px` = 0.15em; a `not.toBe("0px")` avoids pinning the em

## Answers to the questions the brief asked directly

**Can the new tests fail for the right reason?** Mostly yes. The three
`toBeGreaterThan(1)` lower bounds are now `toHaveLength(3)` / `toHaveCount(3)`,
exact, which is detector rule 1 satisfied; round 1's finding 1 shape (an expected
value derived from the observation) is **not** reintroduced — the re-render test
now asserts the literal `1`, and the `scrollSpy.mock.instances[0]` comparison
against `marks[0]` is a positional claim about an independently-obtained DOM
list, not a count copied from the run. The gaps are the three above, all of them
in the new CSS/seam layer rather than in the hook.

**Does CI run the new detector?** Yes — `.github/workflows/ci.yml:210` runs
`pnpm test:e2e:components`, and `spec-viewport.spec.ts` / `projects.ts` /
`componentFixtureParity.test.tsx` all have the new names, so the arrangement and
the spec are both claimed by a project.

**Is the `toBe(plainTail.x)` exact float comparison a flake risk?** No. I drove
the built fixture with the `<pre>` font forced to `serif`, `sans-serif`,
`Georgia`, `Times New Roman`, `Helvetica` and `Courier` as well as the fixture
default: the marked and plain tails were bit-identical in all seven
(`delta: 0`). The control line carries the same `<span>` boundaries as the
subject, so no shaping difference can arise. Exact equality is the right
assertion here.

**The `scrollIntoView` shim in `src/test/setup.ts`.** Its guard and its
placement are both fine. Disabling the shim (`MT1`) fails 20 of the hook file's
tests at `vi.spyOn` ("Cannot spy on scrollIntoView"), so the shim is held.
`vi.spyOn` + `vi.restoreAllMocks()` restores the shim itself (it is an own data
property of `Element.prototype`), and `vitest.config.ts` runs `pool: "forks"`
with isolation on, so each file gets its own jsdom and nothing crosses files
either way. Removing the per-file `Element.prototype.scrollIntoView = vi.fn()`
from `MarkdownPreview.test.tsx` created no dependency on the shim: that file
passes 22/22 with the shim disabled, because its `requestAnimationFrame` is
jsdom's real one and the scroll callback never runs inside the test.

**The `requestAnimationFrame` stub.** No assertion passes for the wrong reason
because of it — dropping the callback from the stub fails both scroll tests. It
does leave the rAF *wrapper* unheld: replacing
`requestAnimationFrame(() => first.scrollIntoView(...))` with a direct
`first.scrollIntoView(...)` keeps all 42 tests green. That wrapper predates
`57f3f03d` (it is in the pre-image of that diff), so `[pre-existing]`, and
holding it would mean asserting on ordering that jsdom cannot observe anyway.
