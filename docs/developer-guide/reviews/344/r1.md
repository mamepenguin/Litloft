## 1. [MEDIUM] [introduced] The new re-render test cannot fail, and does not touch the guard it names

`frontend/src/hooks/__tests__/useHighlightPassage.test.tsx:207-225`

Two independent reasons it holds nothing.

**(a) The expected value is derived from the observation** —
`.claude/rules/review-workflow.md` Detector rule 5:

```
const first = container.querySelectorAll("mark.ask-citation-highlight").length;
...
expect(container.querySelectorAll("mark.ask-citation-highlight")).toHaveLength(first);
```

Mutation `M22` — make `collectSegments` return `[]` so the hook produces **no
marks at all** — leaves this test green (`first` becomes 0, the assertion
compares 0 to 0). `M23` (take only the first segment) is green too.

**(b) The guard it names is never reached.** React 19's `setProp` re-applies
`dangerouslySetInnerHTML` on every update without comparing to the previous
`__html`, so the harness's container is wiped and rebuilt on the rerender. I
measured this: the hook logs `start` and `match wrapped in <mark>` twice, once
per render, i.e. the `container.querySelector(...)` early return at
`useHighlightPassage.ts:83` did not fire either time. Mutation `M15` — delete
line 83 entirely — leaves the committed suite green.

This matters beyond the test, because **the guard is load-bearing in
production**. `TextPreview.tsx:168-176` renders `<pre ref={preRef}>{content}</pre>`
— plain children, not `dangerouslySetInnerHTML`. React does not wipe that, so
without line 83 every `TextPreview` re-render nests another `<mark>` inside the
previous one. Invariant 6 is currently unheld by any test.

A test that does hold it uses a plain-children container. This one is red under
`M15` and green at `57f3f03d`:

```tsx
function PlainFixture({ text, quote }: { text: string; quote: string }) {
  const ref = useRef<HTMLPreElement>(null);
  useHighlightPassage(ref, quote, true);
  return <pre ref={ref}>{text}</pre>;
}

it("does not re-mark a plain-children container on re-render", () => {
  const { container, rerender } = render(
    <PlainFixture text="The quick brown fox jumps." quote="brown fox" />,
  );
  expect(container.querySelectorAll("mark.ask-citation-highlight")).toHaveLength(1);
  rerender(<PlainFixture text="The quick brown fox jumps." quote="brown fox" />);
  expect(container.querySelectorAll("mark.ask-citation-highlight")).toHaveLength(1);
  expect(container.textContent).toBe("The quick brown fox jumps.");
});
```

Keep a rerender test on the `dangerouslySetInnerHTML` harness too if the
re-apply path is wanted, but assert the literal count, not `first`.

## 5. [MEDIUM] [introduced] N marks means N sets of padding, corners and rings — not measured in a browser

`frontend/src/app/globals.css:705-711`

```css
.ask-citation-highlight {
  background-color: var(--highlight-bg);
  padding: 0.05em 0.15em;
  border-radius: 0.15em;
  box-shadow: 0 0 0 1px var(--highlight-bg);
}
```

The rule was written when a citation was one element. This commit makes a
cross-token citation N elements, so the same run now draws N rounded pills, each
with 0.15em of horizontal padding and its own 1px ring, with a visible seam at
every internal boundary. The `MarkdownPreview` fixture already produces 3, and
a real highlighted code line produces one per token.

Inside a `<pre>`, the horizontal padding also shifts every character after each
seam, so a highlighted line no longer aligns with the lines above and below it —
in the viewer PR 1 exists to build.

I did not measure this. `.claude/rules/review-workflow.md` "What a test here
cannot hold" says jsdom reaches none of it, so this needs the R-5 pass or a
`frontend/e2e-components/` case with a real browser. If the seams do show, the
fix is a modifier class on the interior marks that zeroes the adjoining side's
padding and radius; `markRange` already knows the index.

## 6. [LOW] [introduced] A whitespace-only node next to the start endpoint is wrapped although it is outside the matched extent

`frontend/src/hooks/useHighlightPassage.ts:204-219`

Invariant 3 says the marks concatenate to the matched extent, "no more". They
can be one character more:

```
html  = "<p>abc </p>\n<p>def ghi</p>"
quote = "def ghi"
marks = ["\n", "def ghi"]
```

The `\n` text node between the two `<p>`s collapses to nothing in
`findPassageRange`'s haystack (the previous node already ended in a space), so
`locateOffset` resolves the match start to offset 4 of `"abc "` — that is,
`node.length`, a boundary *before* the `\n` node. `collectSegments` is then
faithful to the Range it was handed and marks the `\n`.

The boundary choice is `findPassageRange`'s and is `[pre-existing]`; the visible
artefact is `[introduced]`, because at `ad441a0e` this same range threw in
`surroundContents` and produced no marks at all. The result is a highlighted
line break — in a `<pre>` (`white-space: pre-wrap`) that is a visible sliver at
the end of a line.

Cheapest fix inside the new code: drop a leading or trailing segment whose text
is entirely whitespace, in `collectSegments`. Do not touch `locateOffset`.

## 8. [LOW] [introduced] A zero-segment range would leave the effect running forever, and would never scroll

`frontend/src/hooks/useHighlightPassage.ts:115-122`

If `collectSegments` returns `[]`, `marks[0]` is `undefined`, so the `first &&`
guard skips the scroll **and** skips `scrolledRef.current = true`; no `<mark>`
is inserted, so `container.querySelector` at line 83 never short-circuits, and
the effect re-runs the full `findPassageRange` tree walk on every subsequent
render, forever. Before this commit the same range produced an empty `<mark>`
via `surroundContents` and did scroll.

I could not reach `[]` from `findPassageRange`: `normalise` trims the needle, so
the match always ends on a non-space character, which makes `endOffset > 0`
always true (see the `M8` survivor below), and the same-node `startOffset <
endOffset` guard is likewise unreachable. So this is defensive only — recorded
because the two guards that produce `[]` are new, not because I have an input.

If it is worth closing, `if (!scrolledRef.current)` with a container-top scroll
when `marks.length === 0` costs two lines and matches the no-match path at
line 95.

### Survivors that were meant to survive

- **M1, M3** — semantically equivalent. `splitText(node.length)` produces an
  empty trailing node that nothing reads; `splitText(0)` empties the original
  and returns a node holding the whole text, which is then wrapped. Same DOM.
- **M5, M8, M11** — unreachable guards. `normalise` trims the needle, so a
  match never ends on whitespace and `endOffset` is never 0; `locateOffset`
  never returns a boundary with `startOffset >= endOffset` in one node; and
  `locateOffset` only ever returns `Text` nodes, so the endpoint type check
  cannot throw. All three are defensive and correct to keep.
- **M14** — `first &&` is redundant with the unreachable empty-segments case
  (finding 8); `marks[0]?.scrollIntoView` would behave the same.
- **M17** — `splitText` never produces an empty node under the `end <
  node.length` guard, so a zero-length middle node cannot arise from this code.
- **M18** — the segments address distinct nodes, so `splitText` on one cannot
  invalidate another's offsets; the order is free.
